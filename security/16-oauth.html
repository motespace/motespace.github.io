OAuth 2.0 / Token 鉴权 ​

一、为什么不用 Cookie Session ​

传统 Cookie Session 模式:

登录 → 服务端创建 Session,Set-Cookie 下发
每次请求 → 浏览器自动带 Cookie → 服务端查 Session

问题:

  • CSRF:跨站请求自动带 Cookie
  • CORS 复杂:Cookie 不能跨域(除非 withCredentials)
  • 移动端麻烦:App 没有 Cookie 容器
  • 服务端状态:Session 需要存(无法水平扩展,除非 Redis)

二、Token(无状态)鉴权 ​

登录 → 服务端验证 → 返回 token(明文给客户端)
请求 → 客户端带 token(Authorization header)
验证 → 服务端解码 token(无需查存储)

优势:

  • 无 CSRF(默认不带,需要显式加)
  • 跨域友好
  • 移动端友好
  • 服务端无状态

劣势:

  • token 泄露 = 永久访问(直到过期)
  • 撤销困难(需维护黑名单)
  • 体积大于 session ID

三、JWT(JSON Web Token) ​

3.1 结构 ​

分为 3 段:Header.Payload.Signature

3.2 Header ​

json
{
  "alg": "HS256",     // HMAC SHA256(对称)
  "typ": "JWT"
}

3.3 Payload(数据) ​

json
{
  "sub": "user_123",          // subject(用户)
  "name": "John Doe",
  "iat": 1516239022,          // issued at(签发时间)
  "exp": 1700000000,          // expiration(过期时间)
  "iss": "yoursite.com",      // issuer
  "aud": "client-app",        // audience
  "role": "admin",            // 自定义字段
  "scope": ["read", "write"]  // 权限
}

注意:Payload 不加密,只 base64 编码——任何人都能解出内容。不要在 JWT 里放敏感信息(密码、身份证)。

3.4 Signature ​

ts
// HS256(对称密钥)
const signature = HMAC_SHA256(
  base64UrlEncode(header) + '.' + base64UrlEncode(payload),
  secret  // 服务端持有
)

// RS256(非对称,服务端私钥签,客户端公钥验)
const signature = RSA_SHA256(
  base64UrlEncode(header) + '.' + base64UrlEncode(payload),
  privateKey  // 只有服务端有
)

算法选择:

  • HS256:对称,简单,适合单服务
  • RS256:非对称,适合多服务/微服务(认证服务私钥签,其他服务公钥验)
  • ES256:椭圆曲线,签名短,适合移动端

四、实战:登录流程 ​

4.1 服务端签发 ​

ts
import jwt from 'jsonwebtoken'

const SECRET = process.env.JWT_SECRET!
const REFRESH_SECRET = process.env.REFRESH_SECRET!

// 登录
app.post('/api/login', async (req, res) => {
  const user = await db.user.findUnique({ where: { email: req.body.email } })
  if (!user || !await verifyPassword(req.body.password, user.passwordHash)) {
    return res.status(401).json({ error: 'Invalid credentials' })
  }

  // 短期 access token(15~30 分钟)
  const accessToken = jwt.sign(
    { sub: user.id, role: user.role },
    SECRET,
    { expiresIn: '15m' }
  )

  // 长期 refresh token(7~30 天)
  const refreshToken = jwt.sign(
    { sub: user.id, type: 'refresh' },
    REFRESH_SECRET,
    { expiresIn: '7d' }
  )

  res.json({ accessToken, refreshToken, expiresIn: 900 })
})

4.2 客户端存储 ​

ts
// ❌ 不推荐
localStorage.setItem('token', accessToken)  // XSS 可读

// ✅ 推荐:Access token 存内存(变量),Refresh token 走 HttpOnly Cookie
let accessToken: string

function setAccessToken(token: string) {
  accessToken = token
}

// 服务端下发 Refresh token 用 Cookie
// Set-Cookie: refresh=xxx; HttpOnly; Secure; SameSite=Strict; Path=/api/auth

4.3 客户端请求带 token ​

ts
async function apiFetch(url: string, options: RequestInit = {}) {
  const res = await fetch(url, {
    ...options,
    headers: {
      ...options.headers,
      // access token 在 header
      Authorization: `Bearer ${accessToken}`,
    },
    credentials: 'include',  // 允许带 refresh token cookie
  })

  // 401 时自动刷新
  if (res.status === 401) {
    await refreshAccessToken()
    return apiFetch(url, options)
  }

  return res
}

4.4 服务端验证 ​

ts
// 中间件
function authRequired(req, res, next) {
  const auth = req.headers.authorization
  if (!auth?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Missing token' })
  }
  const token = auth.slice(7)
  try {
    const payload = jwt.verify(token, SECRET)
    req.user = payload
    next()
  } catch (err) {
    return res.status(401).json({ error: 'Invalid token' })
  }
}

五、Refresh Token ​

5.1 为什么需要 ​

Access token 短期(15 分钟)泄露风险大,长期(7 天)撤销困难。Refresh token 用于获取新的 access token。

登录 → 拿到 access + refresh
  ↓
 access 过期(15 分钟后)
  ↓
 用 refresh 换新 access(无感刷新)
  ↓
 refresh 也过期(7 天后)
  ↓
 重新登录

5.2 Refresh token 撤销 ​

短期 access token 泄露时影响有限,但 refresh token 泄露需要立即撤销:

ts
// 方案 1:黑名单(简单但状态化)
const revokedTokens = new Set<string>()

app.post('/api/auth/refresh', (req, res) => {
  const refresh = req.cookies.refresh
  if (revokedTokens.has(refresh)) {
    return res.status(401).json({ error: 'Token revoked' })
  }
  // ...
})

app.post('/api/auth/logout', (req, res) => {
  revokedTokens.add(req.cookies.refresh)
  res.json({ success: true })
})
ts
// 方案 2:服务端有状态记录(user_sessions 表)
type Session = {
  id: string
  userId: string
  refreshTokenHash: string  // 不存明文
  expiresAt: number
  revoked: boolean
  device: string
  ip: string
}

async function isValidSession(refreshToken: string) {
  const hash = sha256(refreshToken)
  const session = await db.session.findUnique({ where: { refreshTokenHash: hash } })
  return session && !session.revoked && session.expiresAt > Date.now()
}

// 撤销
async function revokeSession(refreshToken: string) {
  await db.session.update({
    where: { refreshTokenHash: sha256(refreshToken) },
    data: { revoked: true },
  })
}

5.3 Refresh token 轮换 ​

每次用 refresh token 换 access token 时,也换一个新的 refresh token——旧的失效。这叫 "refresh token rotation"。

ts
app.post('/api/auth/refresh', async (req, res) => {
  const oldRefresh = req.cookies.refresh

  const session = await isValidSession(oldRefresh)
  if (!session) return res.status(401).end()

  // 撤销旧 refresh
  await revokeSession(oldRefresh)

  // 发新 refresh + access
  const accessToken = jwt.sign(...)
  const newRefreshToken = jwt.sign(...)

  // 记录新 session
  await createSession(newRefreshToken, session.userId)

  res.cookie('refresh', newRefreshToken, { httpOnly: true, secure: true })
  res.json({ accessToken })
})

好处:如果旧 refresh 泄露,攻击者用时服务端的"撤销"会先于攻击者;如果攻击者抢先刷新,合法用户的刷新失败 → 告警(可能 token 泄露)。

六、OAuth 2.0 第三方登录 ​

6.1 流程(Authorization Code) ​

1. 用户点"用微信登录"
   ↓
2. 跳到微信 OAuth 服务(/authorize?client_id=xxx&redirect_uri=...)
   ↓
3. 用户在微信同意授权
   ↓
4. 微信回调 redirect_uri?code=AUTH_CODE
   ↓
5. 我们的服务端用 code 换 access_token
   ↓
6. 用 access_token 拉用户信息
   ↓
7. 创建本地账户 / 登录

6.2 实战代码 ​

ts
// 步骤 2:生成授权 URL
app.get('/api/auth/wechat/url', (req, res) => {
  const state = generateRandomToken()  // 防 CSRF
  req.session.oauthState = state

  const url = new URL('https://open.weixin.qq.com/connect/qrconnect')
  url.searchParams.set('appid', WECHAT_APP_ID)
  url.searchParams.set('redirect_uri', 'https://yoursite.com/api/auth/wechat/callback')
  url.searchParams.set('response_type', 'code')
  url.searchParams.set('scope', 'snsapi_login')
  url.searchParams.set('state', state)

  res.json({ url: url.toString() })
})

// 步骤 4:回调
app.get('/api/auth/wechat/callback', async (req, res) => {
  // 验证 state 防 CSRF
  if (req.query.state !== req.session.oauthState) {
    return res.status(400).json({ error: 'Invalid state' })
  }

  // 5. 用 code 换 access_token
  const tokenRes = await fetch('https://api.weixin.qq.com/sns/oauth2/access_token', {
    method: 'POST',
    body: new URLSearchParams({
      appid: WECHAT_APP_ID,
      secret: WECHAT_APP_SECRET,
      code: req.query.code as string,
      grant_type: 'authorization_code',
    }),
  })
  const { access_token, openid } = await tokenRes.json()

  // 6. 拉用户信息
  const userRes = await fetch(`https://api.weixin.qq.com/sns/userinfo?access_token=${access_token}&openid=${openid}`)
  const wxUser = await userRes.json()

  // 7. 创建 / 查找本地账户
  const user = await findOrCreateUser({
    provider: 'wechat',
    openid: wxUser.openid,
    nickname: wxUser.nickname,
    avatar: wxUser.headimgurl,
  })

  // 8. 发 token(走和自建登录一样的流程)
  const token = await issueToken(user)
  res.json({ token })
})

6.3 安全要点 ​

  • state 参数:防 CSRF,必须校验
  • redirect_uri 白名单:不能用用户控制的回调地址
  • client_secret 不暴露前端:只在服务端用
  • 短 code、短 token:code 用一次就失效
  • postMessage 校验 origin:见 iframe 安全章节

七、JWT 安全清单 ​

7.1 签发 ​

  • [ ] 用强随机密钥(openssl rand -hex 64)
  • [ ] 不在 JWT 里放敏感信息(Payload 明文可见)
  • [ ] 短期 access + 长期 refresh
  • [ ] 必要时强制 token rotation

7.2 存储 ​

  • [ ] Access token 存内存(组件 state)
  • [ ] Refresh token 走 HttpOnly Cookie
  • [ ] localStorage 只存非敏感的 UI 偏好

7.3 传输 ​

  • [ ] Authorization: Bearer
  • [ ] 强制 HTTPS
  • [ ] CORS 白名单
  • [ ] 防 CSRF(referer / state / 二次验证)

7.4 撤销 ​

  • [ ] 用户改密码 → 撤销所有 token
  • [ ] 检测异常活动 → 撤销
  • [ ] 退出登录 → 撤销 refresh

🎯 面试常考 ​

Q1：Token 怎么管理?

Access Token 短期、Refresh Token 长期;存储优先 HttpOnly + Secure + SameSite 的 Cookie(防 XSS 读取),localStorage 防不住 XSS。

Q2：怎么防 Token 被盗用?

缩短有效期 + Refresh Token 轮换(每次刷新都换新的,旧的作废)+ 绑定设备/会话 + 检测异常刷新地点。

Q3：JWT 和 Session 怎么选?

JWT 无状态、易水平扩展,但难以主动失效;Session 有服务端存储、可立即踢下线,但需要共享存储。微服务常用 JWT,后台系统常用 Session。

📝 小结 ​

  • Token 存储优先 HttpOnly + Secure + SameSite 的 Cookie(防 XSS 读取);localStorage 防不住 XSS。
  • Refresh Token 轮换 + 检测重放;检测到旧 token 被用说明泄漏,直接吊销整条链。
  • JWT 的三个坑:无法主动失效、载荷大(每个请求都带)、无法撤销。
  • 短有效期 + 服务端黑名单是折中方案。
