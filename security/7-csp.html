CSP(Content Security Policy) ​

一、是什么 ​

CSP 是 HTTP 响应头,告诉浏览器"哪些资源可以加载、哪些行为可以做"。当 XSS 已经发生时,CSP 是最后一道防线——限制恶意脚本能做什么。

二、为什么需要 CSP ​

没有 CSP(默认):
<script>alert(document.cookie)</script>  ← 任意内联脚本执行

有 CSP:
Content-Security-Policy: script-src 'self'
<script>alert(document.cookie)</script>  ← 被浏览器拒绝

CSP 不能阻止 XSS 注入,但能限制 XSS 的破坏范围——无法加载外部恶意 JS、无法上传数据、无法执行内联脚本。

三、CSP 指令详解 ​

3.1 资源加载指令 ​

http
Content-Security-Policy:
  default-src 'self';                              # 默认所有资源只允许同源
  script-src 'self' 'nonce-{RANDOM}' https://cdn.example.com;  # 脚本来源
  style-src 'self' 'unsafe-inline';                # 样式(允许内联,因为多数 UI 库需要)
  img-src 'self' data: https:;                     # 图片(允许任意 HTTPS)
  font-src 'self' https://fonts.gstatic.com;       # 字体
  connect-src 'self' https://api.example.com;      # AJAX / WebSocket / EventSource
  media-src 'self';                                # 音频视频
  frame-src 'self' https://www.youtube.com;          # iframe
  worker-src 'self' blob:;                         # Web Worker / Service Worker
  manifest-src 'self';                             # PWA manifest

3.2 行为限制指令 ​

http
Content-Security-Policy:
  frame-ancestors 'none';                # 防点击劫持(替代 X-Frame-Options)
  base-uri 'self';                       # 防 <base> 劫持
  form-action 'self';                    # form 只能提交到同源
  navigate-to 'self';                    # window.location 只能跳同源
  require-trusted-types-for 'script';    # 强制 Trusted Types
  trusted-types myPolicy;                # 自定义策略名

3.3 其他指令 ​

http
Content-Security-Policy:
  upgrade-insecure-requests;             # HTTP 自动升级到 HTTPS
  block-all-mixed-content;                # 阻止混合内容(HTTPS 页加载 HTTP 资源)
  report-uri /csp-report;                # 违规上报地址
  report-to csp-endpoint;                # Report-To 头替代

四、关键字(必须懂) ​

关键字含义安全性
'self'同源✅ 安全
'none'全部禁止✅ 最严格
'unsafe-inline'允许内联脚本/样式⚠️ 降低防御
'unsafe-eval'允许 eval / setTimeout(string)⚠️ 危险
'nonce-{RANDOM}'匹配特定 nonce✅ 安全
'strict-dynamic'信任由 nonce 脚本加载的脚本✅ 配合 nonce
'sha256-{HASH}'匹配特定 hash✅ 安全但繁琐
data:允许 data: URL⚠️ 慎用
*通配符❌ 不推荐

实战警告:

  • 'unsafe-inline' 会让 CSP 对 XSS 几乎无效(因为 XSS 攻击通常就是内联)
  • 'unsafe-eval' 会让 CSP 失效(JSONP / eval 注入)
  • 业务代码不写 nonce = 业务代码无法执行

五、Nonce 机制(推荐方案) ​

5.1 服务端生成 ​

ts
// 每次响应生成新的 nonce
import crypto from 'crypto'

app.use((req, res, next) => {
  const nonce = crypto.randomBytes(16).toString('base64')
  res.locals.cspNonce = nonce
  next()
})

// 设置 CSP 头
app.use((req, res, next) => {
  const nonce = res.locals.cspNonce
  res.setHeader('Content-Security-Policy', `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic';
    style-src 'self' 'unsafe-inline';
  `.trim())
  next()
})

// 模板引擎:在 <script> 加 nonce
res.render('page', { nonce })
html
<!-- 业务代码 -->
<script nonce="<%= nonce %>">
  // 业务逻辑
</script>

<!-- 第三方库(信任的) -->
<script src="https://trusted-cdn.com/lib.js" nonce="<%= nonce %>"></script>

<!-- 内联事件:不支持 nonce,需要重构成 addEventListener -->

5.2 为什么 nonce 安全 ​

  • nonce 每次请求都重新生成
  • 攻击者无法预测 nonce 值
  • 即使注入了 <script>alert(1)</script>,没有 nonce 就不执行

六、严格 vs 宽松策略 ​

6.1 严格(新项目推荐) ​

http
Content-Security-Policy:
  default-src 'none';
  script-src 'self' 'nonce-{RANDOM}';
  style-src 'self';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'self';
  frame-ancestors 'none';
  base-uri 'none';
  form-action 'self';

6.2 宽松(老项目逐步推进) ​

http
Content-Security-Policy-Report-Only:
  default-src 'self' 'unsafe-inline' 'unsafe-eval' https:;
  report-uri /csp-report

先只报告、不强制,看哪些规则违规,然后逐步收紧。

6.3 过渡策略(实战经验) ​

阶段 1:报告
  Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report
  → 收集违规报告 2~4 周

阶段 2:收紧 script-src
  script-src 'self' 'unsafe-inline' 'unsafe-eval'
  → 把 unsafe-* 干掉,加 nonce

阶段 3:正式启用
  Content-Security-Policy: (与阶段 2 相同)
  → 切换到强制

阶段 4:扩展覆盖
  加上 frame-ancestors / base-uri / form-action

七、上报与监控 ​

7.1 接收 CSP 报告 ​

ts
app.post('/csp-report', express.json({ type: 'application/csp-report' }), (req, res) => {
  const report = req.body['csp-report']
  console.warn('CSP 违规:', {
    blocked: report['blocked-uri'],
    violated: report['violated-directive'],
    line: report['line-number'],
    page: report['document-uri'],
    userAgent: req.headers['user-agent'],
  })
  // 推送到告警平台(Sentry / 自建)
  res.status(204).end()
})

7.2 真实项目:CSP 推动经验 ​

背景:为商户 SaaS 上 CSP,业务方反应"测试环境 OK,线上白屏"。

根因分析:

  • 测试环境未走 CSP,没发现 inline script 问题
  • 线上启用 strict-dynamic 后,所有无 nonce 的 inline script 都被拦截

解决方案:

  1. HTML 自动注入 nonce:用构建工具(html-webpack-plugin / vite-plugin-html)自动给业务内联 script 加 nonce
  2. 第三方库的妥协:部分老库只能用 'unsafe-inline'(CSS),评估后接受
  3. 白名单:CDN 域名加白(script-src https://cdn.jsdelivr.net)
  4. 灰度:先 1% → 10% → 50% → 100%,每个阶段观察 1 周

八、与其他头的关系 ​

头关系
X-Frame-OptionsCSP frame-ancestors 是替代
X-XSS-Protection现代浏览器已忽略(被 CSP 替代)
X-Content-Type-Optionsnosniff,防止 MIME 嗅探

Referrer-Policy防 Referer 泄露,与 CSP 互补

🎯 面试常考 ​

Q1：CSP 是什么?

Content Security Policy,通过响应头告诉浏览器「哪些资源可以加载、哪些脚本可以执行」,是 XSS 的第二道防线。

Q2：CSP 的关键指令?

default-src(兜底)、script-src、style-src、img-src、connect-src、frame-ancestors、object-src。

Q3：怎么落地不炸?

先 Content-Security-Policy-Report-Only 上线收集违规报告,再逐步收紧;内联脚本用 nonce 或 hash 放行,别用 unsafe-inline。

📝 小结 ​

  • CSP 是第二道防线:即使有 XSS,也能限制恶意脚本能干什么。
  • 落地要渐进:先 Content-Security-Policy-Report-Only 收集报告,再逐步收紧。
  • 内联脚本用 nonce / hash 放行,不要 unsafe-inline;script-src 不加 unsafe-eval。
  • object-src 'none'、base-uri 'self'、frame-ancestors 'none' 几乎无副作用,可以直接开。
