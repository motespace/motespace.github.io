前端安全威胁全景 ​

一、为什么需要认识威胁全景 ​

安全防御不是堆砌工具——是 按威胁优先级排兵布阵。

OWASP Top 10 数据显示,Web 应用 80% 以上的入侵都来自已知的、文档化的攻击类型。前端工程师最常面对的 4 类威胁是:

前端常见攻击:
├── XSS(跨站脚本)        ← 最常见,能拿到用户 cookie、伪造操作
├── CSRF(跨站请求伪造)    ← 第二常见,利用用户登录态发请求
├── Clickjacking(点击劫持)  ← 攻击"点击"行为
├── 中间人(MITM)         ← 拦截 HTTPS 通信
└── 供应链攻击(npm 投毒)   ← 近年激增,直接影响前端

下面按"出现频率 × 危害程度"从高到低排列。

二、XSS(跨站脚本攻击) ​

2.1 三种类型 ​

反射型 XSS(Reflected)

  • 用户点击带恶意参数的链接 → 服务端把参数原样塞进 HTML → 恶意脚本执行
  • 典型场景:搜索框、错误提示页、URL 参数
  • 危害:单次点击即可窃取 cookie
html
<!-- 攻击 URL:https://example.com/search?q=<script>alert(document.cookie)</script> -->
<!-- 服务端模板: -->
<div>您搜索的是:<!-- --> <%= q %></div>  <!-- 没转义就注入 -->

存储型 XSS(Stored)

  • 攻击者把恶意内容存进数据库(评论、用户名、富文本)→ 其他用户访问时脚本执行
  • 危害:影响所有访问该页面的用户,持续时间长
  • 案例:2017 年某社交平台名人账号被盗(被私信中存储的 XSS 触发)

DOM 型 XSS(DOM-based)

  • 完全在前端发生,不经过服务端
  • 典型:location.hash / document.referrer / localStorage 等用户可控源直接拼接到 innerHTML / eval
  • 防御要点:不信任任何前端可控的字符串

2.2 真实危害 ​

XSS 不只是弹个窗——能做的事包括:

  • 窃取 cookie / localStorage(免登录拿用户身份)
  • 读取页面 DOM(钓鱼表单、篡改转账金额)
  • 发起任意 HTTP 请求(CSRF 的 XSS 加强版)
  • 挖矿脚本、键盘记录、广告劫持

2.3 防御层级(由弱到强) ​

1. 输入过滤(去掉 < > ' " 等)
2. 输出转义(根据上下文用不同的转义)
3. 富文本 DOMPurify 白名单
4. CSP 限制 inline script
5. HttpOnly cookie 防窃取

永远不要只做第一层——绕过示例:把 <script> 写成 <img src=x onerror=alert(1)>。

三、CSRF(跨站请求伪造) ​

3.1 攻击方式 ​

html
<!-- 用户已登录 bank.com,Cookie 自动带上 -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>

用户访问恶意页面 → 自动发起转账 → 由于 cookie 自动带,服务端以为是用户操作。

3.2 防御 ​

  • SameSite=Lax/Strict Cookie(浏览器级别,2019 后默认 Lax)
  • CSRF Token(表单或 header 带,服务端验证)
  • 关键操作二次确认(密码 / 短信验证码)
  • Referer / Origin 验证(辅助手段)

详见 9-csrf.md 和 8-csrf-samesite.md。

四、Clickjacking(点击劫持) ​

4.1 攻击方式 ​

攻击者把目标站点嵌入透明 iframe,叠在诱饵按钮上。用户以为在点"领奖",实际点在 iframe 里的"确认转账"。

html
<!-- 恶意页面 -->
<iframe src="https://bank.com/transfer?to=attacker&amount=10000"
        style="opacity:0; position:absolute; top:0; left:0; width:100%; height:100%"></iframe>
<button style="position:absolute; top:200px; left:100px">点这里领 100 元</button>

4.2 防御 ​

http
X-Frame-Options: DENY          # 禁止任何 iframe 嵌入(老方案)
# 现代标准
Content-Security-Policy: frame-ancestors 'none'
# 允许特定站点
Content-Security-Policy: frame-ancestors 'self' https://trusted.com

详见 6-clickjacking.md。

五、中间人攻击(MITM) ​

5.1 攻击场景 ​

  • 公共 WiFi:路由器被入侵,流量被监听
  • DNS 劫持:解析到错误 IP
  • 证书伪造:用户忽略证书警告

5.2 防御 ​

  • 强制 HTTPS(HSTS)
  • HSTS preload(浏览器内置 HSTS 列表)
  • 证书钉扎(HPKP)(已弃用,改用 Expect-CT)
  • 不要忽略证书警告(用户侧)

详见 14-mitm.md 和 1-https-tls.md。

六、供应链攻击(近年激增) ​

6.1 真实案例 ​

  • event-stream(2018):流行的 npm 包被注入窃取比特币钱包代码
  • ua-parser-js(2021):周下载 800 万次的包被植入挖矿脚本
  • colors/faker(2022):作者故意破坏,所有版本锁死
  • node-ipc(2022):在俄罗斯/乌克兰 IP 下主动删除用户文件(政治抗议式攻击)

6.2 防御 ​

  • 锁定 lockfile:npm ci 替代 npm install
  • npm audit / Snyk / Dependabot:自动化检测
  • 私有 npm 仓库(内网包隔离)
  • 最小依赖原则:能写原生就别装包
  • Code Review 第三方包

详见 10-deps-security.md。

七、其他常见威胁 ​

威胁一句话说明
SQL 注入前端能做有限:用 ORM 参数化查询,不做字符串拼接
钓鱼攻击教育用户识别 URL,服务端做邮件签名 / DMARC
文件上传漏洞服务端校验 MIME、白名单、存储路径隔离
DDoS前端做不了根治,需要 CDN / WAF
信息泄露不在 console.log 打敏感数据;不返回多余字段
Cookie 窃取HttpOnly + Secure + SameSite
JSONP 劫持早已过时,但老接口还有

八、威胁评估模型 ​

做安全防御时,先量化威胁再排期:

风险 = 可能性 × 影响 × 暴露面

可能性:用户输入是否会被脚本处理? 是否会引用外部资源?
影响:泄露 cookie / 资金损失 / 数据丢失?
暴露面:全网用户 vs 内部用户 vs 后台管理员?

优先修复可能性高 + 影响大 + 暴露面广的项——比如 XSS、CSRF、CSP 缺失、第三方依赖漏洞。

🎯 面试常考 ​

Q1：前端面临哪些主要威胁?

XSS、CSRF、点击劫持、开放重定向、iframe 越权、依赖投毒、敏感信息泄漏(密钥/Token 进 bundle)。

Q2：怎么排优先级?

按「影响面 × 触发难度」排。XSS 和密钥泄漏通常优先,因为一个就能导致全站沦陷;CSRF 次之(现代 SameSite 已缓解大部分)。

Q3：做一次威胁建模怎么入手?

画出数据流图,标出「不可信输入 → 处理 → 敏感操作」的所有边界,每个边界问一句「这里如果不信任会怎样」。

📝 小结 ​

  • 威胁全景:XSS、CSRF、点击劫持、SSRF、开放重定向、依赖投毒、敏感信息泄漏、iframe 越权。
  • 排优先级按「影响面 × 触发难度」,XSS 和密钥泄漏通常最优先(一个就能沦陷)。
  • 威胁建模的起手式:画数据流图,标出「不可信输入 → 处理 → 敏感操作」的边界。
  • 前端能挡一部分,但权限和资金相关的必须服务端。
