第三方依赖安全:供应链攻击防御 ​

一、为什么依赖安全是大问题 ​

平均每个前端项目有 1500+ 个 npm 包(直接 + 间接)。每个包都可能被:

  • 作者主动投毒(ua-parser-js、event-stream、node-ipc)
  • 维护者账号被盗(发新版本植入后门)
  • 拼写错误被钓鱼(crossenv vs cross-env)
  • 间接依赖里有恶意包

真实案例:

2018 event-stream
  流行的流处理库(200万周下载)被攻击者加入窃取比特币钱包的代码
  隐藏在 indirect 依赖 flatmap-stream,2 个月后才被发现

2021 ua-parser-js
  周下载 800 万次的库被入侵,植入密码窃取和挖矿脚本
  多个大厂中招

2022 colors / faker
  作者主动破坏所有版本(marong.js),所有依赖项目崩溃
  "抗议式供应链攻击"

2022 node-ipc
  在俄罗斯 / 乌克兰 IP 检测下主动删除 /usr/local 内的文件
  作者反战抗议,殃及全球用户

二、依赖审计工具 ​

2.1 npm 内置 ​

bash
# 检查已知漏洞
npm audit

# 输出示例
┌─────────────────────────┬──────────────────────────────────┐
│ Moderate                │ Prototype Pollution in minimist │
├─────────────────────────┼──────────────────────────────────┤
│ Package                 │ minimist                         │
│ Patched in             │ >=1.2.6                          │
│ Dependency of          │ @vitejs/plugin-vue               │
│ More info              │ https://github.com/advisories... │
└─────────────────────────┴──────────────────────────────────┘

# 自动修复(可能引入大版本变化,慎用)
npm audit fix

# 只修复低风险
npm audit fix --audit-level=low

# 仅生产依赖
npm audit --production

2.2 高级工具 ​

Snyk(免费层可用):

bash
npm install -g snyk
snyk auth
snyk test
snyk monitor  # 持续监控,新漏洞发邮件

Dependabot(GitHub 内置):

  • 自动 PR 升级有漏洞的依赖
  • 配置 .github/dependabot.yml

Renovate(类似 Dependabot,更可配置):

  • 智能定时多,自动分组 PR

2.4 实战配置 ​

json
// package.json scripts
{
  "scripts": {
    "audit": "npm audit --audit-level=high",
    "audit:prod": "npm audit --production",
    "prebuild": "npm audit --audit-level=high",
    "preinstall": "npx npm-audit-resolver"  // 自定义策略
  }
}
yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    labels:
      - "dependencies"
      - "security"
    # 只更新 patch + minor,不更新 major
    allowed-updates:
      - dependency-type: "production"
        update-types: ["patch", "minor"]

三、依赖锁定 ​

3.1 package-lock.json ​

必须提交到 git,否则 npm install 会装最新版本(可能含漏洞)。

bash
# .gitignore 错误示例
package-lock.json  # ❌ 不要忽略!

# 正确:
# 不写 package-lock.json 到 .gitignore

3.2 npm ci vs npm install ​

命令行为何时用
npm install装最新匹配 package.json 范围的版本开发
npm ci严格按 package-lock.json 装,不修改 lockfileCI / 生产 / Docker
yaml
# CI 示例
- name: Install deps
  run: npm ci  # ✅ 用 ci,不是 install

- name: Build
  run: npm run build
dockerfile
# Dockerfile
COPY package.json package-lock.json ./
RUN npm ci  # ✅ 严格按 lockfile
COPY . .
RUN npm run build

3.3 精确版本 vs 范围 ​

json
{
  "dependencies": {
    "lodash": "4.17.21",         // ✅ 精确版本(关键依赖)
    "react": "^18.2.0",          // ⚠️ 兼容更新(允许 18.x.x)
    "vue": "3.4.21",             // ✅ 精确(避免 ^)
    "element-plus": "~2.4.0"     // ⚠️ 仅 patch(2.4.x)
  }
}

实战经验:

  • 核心依赖(框架、加密库)用精确版本
  • 工具类(日期、工具函数)可用 ^
  • 生产环境严格按 lockfile

3.4 npm shrinkwrap ​

把 npm 自动生成的依赖信息"锁死",即使有人 npm publish 新版本,你的项目也只装这个版本。

bash
npm shrinkwrap  # 生成 npm-shrinkwrap.json

只对已发布到 npm 的库有用,自用项目用 package-lock.json 即可。

四、私有 npm 仓库 ​

4.1 为什么需要 ​

  • 隔离内网包(不暴露给公网)
  • 缓存常用包(提升 CI 性能)
  • 审核第三方包(团队添加白名单)

4.2 方案 ​

Verdaccio(轻量,本地开发):

bash
npm install -g verdaccio
verdaccio  # 启动,默认 4873 端口

# 项目里
npm config set registry http://localhost:4873
npm publish --registry http://localhost:4873  # 发内网包

Nexus / Artifactory(企业级,功能更全):

  • 用户管理、权限控制
  • 包清理、保留策略
  • 与 CI/CD 集成

4.3 配置 .npmrc ​

ini
# .npmrc
registry=https://registry.yourcompany.com/
# 特定 scope 走私有仓库
@yourcompany:registry=https://private.yourcompany.com/
# 公共包走淘宝镜像加速
registry=https://registry.npmmirror.com/

五、Supply Chain 防护清单 ​

5.1 安装阶段 ​

  • [ ] package-lock.json 在 git
  • [ ] CI 用 npm ci 而非 npm install
  • [ ] .npmrc 锁定 registry
  • [ ] 核心依赖精确版本(4.17.21 而非 ^4.17.21)

5.2 审计阶段 ​

  • [ ] npm audit 在 CI,失败阻塞
  • [ ] Dependabot / Snyk 启用
  • [ ] 周报:依赖漏洞清单
  • [ ] 高危漏洞 24 小时内处理

5.3 运行阶段 ​

  • [ ] 生产环境锁定所有版本
  • [ ] 第三方脚本(analytics、A/B 测试)走白名单
  • [ ] CDN 资源 SRI 校验(防 CDN 被入侵)
html
<!-- SRI:验证 CDN 文件没被篡改 -->
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-..."
  crossorigin="anonymous"
></script>
bash
# 生成 SRI hash
cat lib.js | openssl dgst -sha384 -binary | openssl base64 -A

六、真实项目:event-stream 复盘 ​

背景:商户后台用了某个老依赖,事件触发依赖 event-stream,被攻击两个月才被发现。

教训:

  1. 不维护的包 = 风险:超过 1 年没更新的包,考虑 fork 或替换
  2. indirect 依赖更要警惕:dev-only 工具、生产 polyfills,都可能在 install 时被攻击
  3. 发布新版本时 review changelog:突然多了新依赖 / 改了 build 流程,要警觉

防御措施:

bash
# 1. 定期审视 lockfile diff
git diff package-lock.json | grep -E '"version":|"resolved":'

# 2. 用 Socket.dev 检查包的安全评分
# https://socket.dev/

# 3. 用 npm-audit-resolver 自动处理
npx -y npm-audit-resolver@latest

七、企业级方案 ​

7.1 私有包 + 镜像 + 审计 ​

代码 → 私有 Registry → 缓存 + 镜像 → npm audit + Snyk → 部署

7.2 Sigstore(高级) ​

数字签名 npm 包:

bash
npm install -g sigstore
# 安装时验证包签名

但生态还不成熟,实际项目用得少。

7.3 零信任安装 ​

有些企业完全禁公网,所有依赖走内部 mirror:

  • 定期从 npm 同步到内网
  • 内网审核后才有
  • CI/CD 完全离线

🎯 面试常考 ​

Q1：供应链攻击是什么?

依赖被投毒(篡改包、劫持发布账号)、或传递依赖引入恶意代码,攻击者借此进入你的构建产物。

Q2：怎么防?

① 锁文件 + 最小化依赖;② 定期扫漏洞(SCA:Dependabot / Snyk / npm audit);③ 校验包的完整性(integrity 字段);④ 私有源(scope + registry 白名单);⑤ 审查新增依赖的维护者与下载量。

Q3：npm 的 integrity 是什么?

package-lock.json 里的哈希值,安装时校验 tar 包是否被篡改,能防一部分投毒。

📝 小结 ​

  • 供应链攻击的路径:包被投毒、发布账号被劫持、传递依赖引入恶意代码。
  • 防御:锁文件 + 最小化依赖 + CI 跑 SCA 扫描 + 校验 integrity + 私有源白名单。
  • integrity 哈希能防传输中篡改,但防不住源站本身就投毒。
  • 加一个依赖前看维护者、下载量、最后更新时间,这些信号比版本号有用。
