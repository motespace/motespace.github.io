iframe 安全:sandbox、跨源策略与 postMessage ​

一、为什么需要 iframe 安全 ​

iframe 是最容易被忽视的安全边界——它能:

  • 加载第三方内容(广告、widget、登录组件)
  • 跨域访问 DOM(受限制)
  • 调用 postMessage 与父页通信
  • 触发顶层导航(如果不限制)

踩坑案例:

  • 第三方 widget 被入侵 → 跨域读写父页 DOM
  • postMessage origin 未校验 → 接受任何来源消息
  • iframe 可导航父页 → 用户被劫持到恶意站点

二、sandbox 属性 ​

2.1 基础用法 ​

html
<!-- 默认 sandbox="" → 最严格 -->
<iframe sandbox="" src="https://3rd-party.com/widget"></iframe>

<!-- 允许脚本 -->
<iframe sandbox="allow-scripts" src="..."></iframe>

<!-- 多个能力 -->
<iframe sandbox="allow-scripts allow-forms" src="..."></iframe>

2.2 能力清单 ​

值作用风险
allow-forms提交表单中
allow-modals弹 alert、confirm、prompt中
allow-popups弹窗高
allow-popups-to-escape-sandbox弹窗不受 sandbox 限制高
allow-same-originiframe 内容视为同源极高
allow-scripts执行脚本中
allow-top-navigation修改父级 location极高
allow-top-navigation-by-user-activation仅用户交互后导航父页中
allow-downloads下载中

2.3 危险组合 ​

html
<!-- ❌ 等于没 sandbox:allow-scripts + allow-same-origin 让脚本可移除 sandbox 属性 -->
<iframe sandbox="allow-scripts allow-same-origin" src="..."></iframe>

<!-- ❌ 允许 top navigation:恶意脚本可劫持父页 -->
<iframe sandbox="allow-scripts allow-top-navigation" src="..."></iframe>

2.4 推荐配置 ​

html
<!-- 嵌入第三方广告 -->
<iframe sandbox="allow-scripts" src="https://ads.example.com/widget"></iframe>

<!-- 嵌入需要交互的 widget(允许表单,不允许其他) -->
<iframe sandbox="allow-scripts allow-forms allow-popups" src="https://widget.example.com"></iframe>

<!-- 嵌入 OAuth 登录(允许弹窗回调) -->
<iframe sandbox="allow-scripts allow-same-origin allow-popups allow-forms"
        src="https://oauth.provider.com/authorize"></iframe>

三、跨源 iframe 限制 ​

3.1 Same-origin policy ​

https://site-a.com
└── iframe: https://site-b.com  (跨域)
    ├── iframe.contentWindow.foo  ❌ 跨域不能访问
    ├── iframe.contentDocument   ❌ 跨域不能访问
    └── postMessage               ✅ 可以通信

3.2 跨域可以做的 ​

  • 获取 iframe 的 location(只能读,不能改)
  • 调用 postMessage 通信
  • 监听 iframe 的事件(limited)

3.3 跨域不能做的 ​

  • 读 iframe 的 DOM
  • 调 iframe 的 JS 函数
  • 改 iframe 的 location(除非允许 navigate)

四、postMessage 安全 ​

4.1 基础通信 ​

ts
// 父页 → iframe
iframe.contentWindow.postMessage({ type: 'greeting', data: 'hi' }, 'https://widget.com')

// iframe → 父页
window.parent.postMessage({ type: 'ready' }, 'https://parent.com')

注意 targetOrigin:

  • *:不推荐(可能发到恶意 iframe)
  • 具体 origin:'https://trusted.com'

4.2 接收消息的安全检查 ​

ts
window.addEventListener('message', (e) => {
  // ✅ 必须校验 origin
  if (e.origin !== 'https://trusted.com') {
    console.warn('拒绝消息:非法 origin', e.origin)
    return
  }

  // ✅ 必须校验 source(防止恶意 iframe 伪装)
  if (e.source !== expectedWindow) {
    return
  }

  // ✅ 必须校验数据结构
  if (!e.data || typeof e.data.type !== 'string') {
    return
  }

  // ✅ 处理合法消息
  switch (e.data.type) {
    case 'user-info':
      // ...
      break
  }
})

4.3 真实坑点 ​

坑 1:origin 校验不严

ts
// ❌ 危险:只检查 origin 包含某个字符串
if (e.origin.includes('yoursite.com'))  // 'https://attackeryoursite.com' 也能通过!

// ✅ 严格:完全匹配或后缀匹配
const allowed = ['https://www.yoursite.com', 'https://app.yoursite.com']
if (!allowed.includes(e.origin)) return

坑 2:数据没校验就用

ts
// ❌ 危险:直接用消息数据
window.addEventListener('message', (e) => {
  if (e.origin === 'https://trusted.com') {
    document.body.innerHTML = e.data.html  // XSS!
  }
})

坑 3:泄露敏感数据

ts
// ❌ 危险:向 * 发送敏感数据
window.parent.postMessage({ token: userToken }, '*')

// ✅ 只发给可信 origin
window.parent.postMessage({ token }, 'https://parent.com')

五、第三方 widget 集成方案 ​

5.1 反向代理(推荐) ​

用户 → 你的域名 /proxy/widget → 第三方 API

优点:

  • 第三方代码不直接执行在用户浏览器
  • 完全可控
  • CSP 简单

缺点:

  • 增加服务器负载
  • 实现稍复杂

5.2 iframe + sandbox ​

如果必须用 iframe,推荐:

html
<iframe
  sandbox="allow-scripts"
  src="https://widget.example.com"
  referrerpolicy="no-referrer"
></iframe>

5.3 用 Web Component 隔离 ​

ts
class IsolatedWidget extends HTMLElement {
  connectedCallback() {
    const iframe = document.createElement('iframe')
    iframe.sandbox.add('allow-scripts')
    iframe.src = this.getAttribute('src')
    this.appendChild(iframe)
  }
}
customElements.define('isolated-widget', IsolatedWidget)

六、Clickjacking 防御 ​

iframe 也是被 clickjacking 利用的途径:

http
# 自己页面:禁止被嵌入
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

详见 6-clickjacking.md。

七、性能考虑 ​

ts
// 1. lazy 加载
<iframe loading="lazy" src="..."></iframe>

// 2. 用 IntersectionObserver 在视区才加载
useEffect(() => {
  const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        iframe.src = iframe.dataset.src
        observer.disconnect()
      }
    })
  })
  observer.observe(iframe)
}, [])

// 3. 销毁不用的 iframe
useEffect(() => () => {
  iframe.remove()  // 释放内存
}, [])

八、Cookie 与 iframe ​

第三方 iframe 默认带第三方 Cookie(可能用于追踪)。

http
Set-Cookie: id=xxx; SameSite=None; Secure   # 显式声明第三方 cookie

现代浏览器开始限制第三方 Cookie(Chrome 的 SameSite 默认 Lax、ITP 等)。

🎯 面试常考 ​

Q1：跨域 iframe 能做什么?

受同源策略限制,读不到父页面 DOM、拿不到 cookie(除非 SameSite=None),但可以发 postMessage 通信、可以触发跳转和表单提交。

Q2：sandbox 属性有什么?

sandbox="allow-scripts allow-same-origin" 等,逐项限制 iframe 能力:禁表单、禁弹窗、禁顶层导航等。不给 allow-same-origin 就等于给了独立源。

Q3：postMessage 怎么安全用?

① 发送时明确指定 targetOrigin,不要用 *;② 接收时校验 event.origin 白名单;③ 校验 event.source;④ 不把敏感信息放进 message。

📝 小结 ​

  • 跨域 iframe 读不到父页面 DOM、拿不到 Cookie(除非 SameSite=None),但能发 postMessage。
  • sandbox 逐项限制能力:不给 allow-same-origin 就等于独立源,给了就基本等同同源,慎用。
  • postMessage 必须指定 targetOrigin(不要 *),接收方要校验 event.origin 和 event.source。
  • 配合 CSP 的 frame-src / frame-ancestors 双向限制。
