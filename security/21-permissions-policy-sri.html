Permissions-Policy 与 SRI ​

两个「白名单型」安全头:一个限制浏览器能用什么能力,一个保证外链脚本没被篡改。

一、Permissions-Policy ​

通过 Feature-Policy 演进而来,用来声明页面允许使用哪些浏览器能力。

http
Permissions-Policy: geolocation=(self), camera=(), microphone=(), interest-cohort=()

语法 ​

feature=(allowlist) [; feature2=(allowlist2)]
allowlist含义
*允许所有来源(含跨域 iframe)
self只允许同源
() 空完全禁用
("https://a.com")只允许指定来源

常用特性 ​

特性控制什么
geolocation地理位置
camera / microphone摄像头 / 麦克风
payment支付接口
usb / bluetooth硬件访问
fullscreen全屏
interest-cohortFLoC 之类的跨站追踪标识(建议禁用)

用 meta 标签设置 ​

html
<meta http-equiv="Permissions-Policy" content="geolocation=(self), camera=()">

注意:meta 形式不能禁用特性,只能允许。要禁用必须在响应头里写 feature=()。

iframe 级别的控制 ​

html
<!-- 这个 iframe 允许地理位置,但只允许它自己用 -->
<iframe src="/map" allow="geolocation 'self'"></iframe>

<!-- 这个 iframe 完全禁止地理位置 -->
<iframe src="/video" allow="geolocation 'none'"></iframe>

iframe 里的权限是「交集」:外层页面禁了,内层 allow 也开不了。

为什么重要 ​

如果你的页面嵌了第三方 iframe(广告、支付、客服),一个被 XSS 攻破的第三方页面理论上能请求摄像头、麦克风、地理位置。Permissions-Policy 是浏览器层面的最后一道防线,即使你的代码有漏洞也能挡住。

兼容性:Chrome 88+、Firefox 96+、Safari 15.4+。老浏览器忽略这个头,不影响功能。

二、Subresource Integrity(SRI) ​

给外链资源加完整性校验,浏览器会验证内容有没有被篡改。

html
<script
  src="https://cdn.example.com/library.js"
  integrity="sha384-BpB6YVj6lJqNvxQ5zPfNcSjRjcxR4YQqkTQ+DiJmXwHqBIoK7Kq3VjzrWQmM7Xw"
  crossorigin="anonymous">
</script>

三个必要条件 ​

条件说明
integrity哈希值,格式 sha256/384/512- Base64
crossorigin="anonymous"必须有,否则跨域资源会被当成不透明响应,无法校验
资源 CORS 响应头服务器要返回 Access-Control-Allow-Origin

crossorigin 漏了是最常见的错误 —— 少了它,浏览器直接跳过校验,SRI 形同虚设。

怎么生成哈希 ​

bash
# 生成
openssl dgst -sha384 -binary library.js | openssl base64 -A

# 或者用 npm 包
npx subresource-integrity node_modules/library/dist/library.js

哈希会随内容变化 ​

每次更新文件哈希都会变,所以要自动化。webpack 的 webpack-subresource-integrity 插件会自动生成:

js
new WebpackSubresourceIntegrityPlugin({
  hashFuncName: 'sha384',
  output: 'integrity',
})

用 integrity-webpack-plugin 也行。

局限 ​

  • 只对跨域资源有意义 —— 同域资源本来就能被服务器控制,防不了
  • 跨域脚本被 CDN 攻破也防不住 —— 校验值在 HTML 里,如果 HTML 本身被篡改,校验值也会被改
  • 需要浏览器支持 —— IE 不支持

所以 SRI 防的是「第三方资源被中间人/CDN 篡改」,不是「你的页面被 XSS」。两者是不同层面的防护。

三、两个头的配合 ​

http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
Permissions-Policy: geolocation=(self), camera=(), microphone=()
Subresource-Integrity: (per-resource, on <script>)
头防什么防不住什么
CSP页面里执行了不该执行的脚本被允许的源被攻破
Permissions-Policy页面滥用了浏览器能力页面自身逻辑漏洞
SRI外部脚本内容被篡改你的页面被 XSS

三者互补,缺一不可。

🎯 面试常考 ​

Q1: Permissions-Policy 解决什么问题? 限制页面(或 iframe)能使用哪些浏览器能力(地理位置、摄像头、麦克风、USB 等)。即使页面有 XSS 漏洞,浏览器层面也能阻止恶意代码调用这些能力,是「最后一道防线」。

Q2: Permissions-Policy 怎么禁用某个特性? 用 feature=() 空 allowlist。只能在响应头里禁用,meta 标签只能允许不能禁用。

Q3: SRI 的 crossorigin 属性为什么必须加? 因为 SRI 校验需要读取资源的字节内容,而跨域资源默认以「不透明」方式加载(不暴露内容),无法校验。加上 crossorigin="anonymous" 后资源以 CORS 方式加载,内容可读可校验。少了这个属性,SRI 会被静默跳过。

Q4: SRI 能防住什么,防不住什么? 防得住:第三方脚本在传输过程中被篡改(中间人、CDN 被攻破)。防不住:你的页面本身被 XSS(此时 integrity 值也会被一起篡改)、同源资源、IE 浏览器。

Q5: 为什么 iframe 上的权限是交集? Permissions-Policy 在多层嵌套时,外层的限制会向下传递。外层页面禁了 camera=(),内层 iframe 再写 allow="camera" 也开不了。这是刻意的设计,防止用 iframe 绕过策略。

📝 小结 ​

  • Permissions-Policy 用白名单声明页面能用的浏览器能力,禁用只能走响应头。
  • SRI 给外链资源加完整性校验,但必须配 crossorigin="anonymous",否则形同虚设。
  • CSP / Permissions-Policy / SRI 防的是三个不同层面的问题,互补使用。
  • SRI 的哈希要自动化生成(webpack 插件),手工维护必然出错。
