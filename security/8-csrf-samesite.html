CSRF 防御:Token + SameSite + 二次验证 ​

一、为什么需要多重防御 ​

CSRF 防御没有银弹——任何单一防御都有绕过可能。生产环境必须多层防御:

CSRF 防御层级(从外到内):

浏览器层  → SameSite Cookie(2019 后默认 Lax)
请求层    → CSRF Token / 自定义 Header
验证层    → Origin / Referer 校验
业务层    → 二次验证(密码 / 短信)
行为层    → 风控引擎(异常操作拦截)

二、SameSite Cookie(浏览器层防御) ​

2.1 三种取值 ​

http
Set-Cookie: token=xxx; SameSite=Strict
Set-Cookie: token=xxx; SameSite=Lax      # 现代浏览器默认值
Set-Cookie: token=xxx; SameSite=None; Secure   # 显式禁用 SameSite

2.2 行为对比 ​

SameSite跨域 GET跨域 POST(表单)跨域 AJAX
Strict❌ 不带❌ 不带❌ 不带
Lax(默认)✅ 带❌ 不带❌ 不带
None✅ 带✅ 带✅ 带

2.3 实战配置 ​

http
# 严格场景:支付、转账、修改密码
Set-Cookie: session_id=xxx; HttpOnly; Secure; SameSite=Strict; __Host-Session=xxx

# 一般场景:普通登录态
Set-Cookie: token=xxx; HttpOnly; Secure; SameSite=Lax; Path=/

# 跨站必需:第三方 OAuth、嵌入场景
Set-Cookie: cross_token=xxx; SameSite=None; Secure

注意 SameSite=None 必须配合 Secure,否则现代浏览器会拒绝。

2.4 __Host- 前缀 ​

防 Cookie 注入(子域劫持):

http
Set-Cookie: __Host-session=xxx; Secure; Path=/; HttpOnly

约束:

  • 必须 Secure
  • 不能有 Domain 属性
  • Path 必须是 /

如果攻击者在子域写入 Cookie,会被浏览器拒绝。

2.5 SameSite 的局限 ​

  • 老浏览器不支持(IE、所有 Safari < 13)
  • 子域跳转:从 app.example.com 跳到 example.com 算同站
  • GET 仍带 Cookie(Lax 模式):如果有 GET 状态修改操作,仍有风险
  • 第三方嵌入:被嵌入的第三方页面如果要带 Cookie,需要 None

三、CSRF Token(请求层防御) ​

3.1 同步 Token 模式 ​

服务端:生成 token,塞到表单 / 响应。

ts
// 服务端(Express 示例)
app.get('/transfer-page', (req, res) => {
  const csrfToken = generateRandomToken()
  req.session.csrfToken = csrfToken
  res.render('transfer', { csrfToken })
})

// 校验
app.post('/api/transfer', (req, res) => {
  if (req.body.csrfToken !== req.session.csrfToken) {
    return res.status(403).json({ error: 'CSRF token mismatch' })
  }
  // ... 转账逻辑
})

前端:在请求时带 token。

ts
// 1. 表单提交
<form action="/api/transfer" method="POST">
  <input type="hidden" name="csrfToken" value={csrfToken} />
  <button>转账</button>
</form>

// 2. AJAX
async function transfer(amount: number) {
  await fetch('/api/transfer', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrfToken,  // 自定义 Header
    },
    body: JSON.stringify({ amount }),
  })
}

3.2 Double Submit Cookie(无状态) ​

适合 前后端分离 + JWT 场景:

ts
// 服务端下发两个 Cookie
Set-Cookie: csrf=xxx; Path=/         // JS 可读
Set-Cookie: token=xxx; HttpOnly       // 鉴权用,JS 不可读

// 前端:从 csrf Cookie 读,加到 header
const csrfToken = getCookie('csrf')
await fetch('/api/transfer', {
  headers: { 'X-CSRF-Token': csrfToken },
})

为什么安全:攻击者读不到 csrf Cookie(同源策略),无法伪造 header。

3.3 CSRF Token 的局限 ​

  • 增加复杂度(每个表单 / 每个 AJAX 都要带)
  • token 泄露就失效(但可加过期时间)
  • 服务端要管理 token 状态(或者用签名 JWT)

四、Origin / Referer 验证(辅助层) ​

ts
// 服务端检查 Origin
app.post('/api/transfer', (req, res) => {
  const origin = req.headers.origin || req.headers.referer
  const allowed = ['https://yoursite.com', 'https://www.yoursite.com']
  if (!allowed.some(domain => origin?.startsWith(domain))) {
    return res.status(403).json({ error: 'Invalid origin' })
  }
})

实战经验:

  • Origin 由浏览器强制设置,不能被 JS 改
  • Referer 用户可能禁用,但作为辅助手段可以接受
  • HTTPS → HTTPS 时 Referer 完整
  • HTTPS → HTTP 时 Referer 只剩 origin(隐私模式)

六、业务层:二次验证(关键操作) ​

对于真正敏感的操作(转账、修改密码、删除账户),不要只靠技术防御:

ts
// 真实项目:商户后台删除商户
async function deleteMerchant(id: string) {
  // 1. 二次确认(防误操作)
  const confirmed = await showConfirm({
    title: '确认删除',
    message: `确认删除商户 ${id}?该操作不可恢复!`,
    danger: true,
  })
  if (!confirmed) return

  // 2. 重新输入密码(防 session 劫持)
  const password = await showPasswordInput('请输入密码确认')
  if (!await verifyPassword(password)) {
    throw new Error('密码错误')
  }

  // 3. 服务端校验角色 + 频率
  await api.delete(`/merchants/${id}`, {
    headers: { 'X-CSRF-Token': csrfToken },
  })
}

6.1 哪些操作必须二次验证 ​

操作二次验证
转账 / 支付短信验证码 + 密码
修改密码旧密码 + 邮箱验证码
删除账户密码 + 邮箱确认链接
修改手机号旧手机号验证码 + 新手机号验证码
大额退款财务主管审批 + 二次确认

八、真实项目:CSRF 完整方案 ​

背景:智能风控平台的"规则配置"功能,运营人员可修改风控规则。

踩坑:

  • 一开始只用了 SameSite=Lax,被老版 Safari 绕过
  • 加 CSRF Token 后,发现 token 在日志里泄露(XSS)
  • 改用 HttpOnly Cookie 存 token,前端从 X-CSRF-Token Header 读

最终方案:

ts
// 服务端
Set-Cookie: session=xxx; HttpOnly; Secure; SameSite=Strict; __Host-session=xxx
Set-Cookie: csrf=xxx; Path=/; Secure           // JS 可读,带 X-CSRF-Token

// 中间件:校验 CSRF
function csrfProtection(req, res, next) {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next()
  const cookieToken = req.cookies.csrf
  const headerToken = req.headers['x-csrf-token']
  if (!cookieToken || cookieToken !== headerToken) {
    return res.status(403).json({ error: 'CSRF token mismatch' })
  }
  next()
}

// 前端
import { getCookie } from '@/utils/cookie'

async function updateRule(rule: unknown) {
  const csrf = getCookie('csrf')
  await fetch('/api/rules', {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrf,
    },
    body: JSON.stringify(rule),
  })
}

// 关键操作:二次确认 + 密码
async function updateCriticalRule(rule: unknown) {
  const password = await showPasswordModal()
  await updateRule(rule)
  await api.post('/api/rules/audit', { rule, password })
}

九、与其他防御的关系 ​

防御关系
XSSXSS 可绕过 CSRF(攻击者能读 Cookie、能发请求)
CORSCORS 配置错误可能允许跨域读 Cookie
Same-origin policy浏览器底线,Cookie 同源策略是基础

正确顺序:CORS + SameSite + Token + 二次验证 + 风控,任一不能少。

🎯 面试常考 ​

Q1：CSRF 是什么?

诱导已登录用户的浏览器向目标站点发请求,利用的是浏览器会自动带上 Cookie。

Q2：怎么防?

① SameSite Cookie(Lax/Strict)—— 首选;② CSRF Token 校验;③ 校验 Origin/Referer;④ 敏感操作二次确认。

Q3：SameSite 三种模式?

Strict(完全不跨站带)、Lax(顶级导航的 GET 带,默认)、None + Secure(跨站带,必须配 Secure,用于跨站场景)。

📝 小结 ​

  • CSRF 利用的是「浏览器会自动带 Cookie」,本质是浏览器替攻击者发了带凭证的请求。
  • 三层防御:SameSite Cookie(主力)、CSRF Token(通用)、Origin/Referer 校验(补充)。
  • SameSite=Lax 挡得掉表单 POST,但挡不住顶级导航的 GET(如 <img src=...>),所以不能只靠它。
  • 敏感操作加二次验证(验证码 / 短信),这是支付、改密类操作的最后一道。
