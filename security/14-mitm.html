中间人攻击(MITM)与 HTTPS ​

一、是什么 ​

MITM(Man-In-The-Middle,中间人)攻击是攻击者截获、篡改、重放通信双方的流量。对 HTTPS 而言,通常是:

用户                攻击者                服务端
  |  ← HTTPS 请求 →  |   转发(可见)   →  |
  |  ← HTTPS 响应 →  |   篡改/注入 ←    |
  |                  |   转发 →          |
  |  ← 篡改响应 ←    |                  |

二、攻击场景 ​

2.1 公共 WiFi ​

  • 攻击者在咖啡店架"Free_Wifi"热点
  • 用户连上后所有流量经攻击者
  • 没 HTTPS 的网站全部明文可见
  • 即使有 HTTPS,如果没有强制 HSTS,首次连接仍可降级到 HTTP

2.2 DNS 劫持 ​

  • 攻击者改 DNS 响应,把 example.com 解析到恶意 IP
  • 用户访问时实际连到攻击者服务器

2.3 证书伪造 ​

  • 攻击者生成自签名证书
  • 用户忽略"证书无效"警告
  • 攻击者用自签名证书与用户建立"加密"通信(攻击者能解密)

2.4 SSL Stripping ​

  • 用户首次访问 http://example.com
  • 攻击者中间盒把 HTTPS"降级"到 HTTP,与用户明文通信
  • 但攻击者与服务端仍用 HTTPS
  • 用户登录信息泄露

2.5 路由器入侵 ​

家庭路由器弱密码(admin/admin),攻击者入侵后:

  • 改 DNS 配置
  • 注入恶意脚本到非 HTTPS 网站
  • 监控局域网流量

三、真实案例 ​

案例后果
2014 咖啡店 WiFi 攻击一群用户登录邮箱时被截获
2017 某运营商劫持全国大范围 HTTP 网站被插入广告
2018 路由器 DNS 劫持数十万路由器被植入挖矿代码
2020 国家级 BGP 劫持大流量网站被劫持到非预期 IP

四、防御:HTTPS + HSTS ​

4.1 强制 HTTPS ​

nginx
# Nginx:80 → 443
server {
  listen 80;
  server_name example.com;
  return 301 https://$server_name$request_uri;
}
ts
// Express:HSTS
app.use((req, res, next) => {
  if (req.headers['x-forwarded-proto'] !== 'https' && process.env.NODE_ENV === 'production') {
    return res.redirect(`https://${req.headers.host}${req.url}`)
  }
  next()
})

4.2 HSTS(HTTP Strict Transport Security) ​

告诉浏览器:未来访问此域名必须用 HTTPS,即使用户输入 http:// 也自动升级

http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
指令作用
max-age强制 HTTPS 的秒数(1~2 年)
includeSubDomains子域也强制
preload申请加入浏览器内置 HSTS 列表

4.3 HSTS Preload ​

把域名提交到 hstspreload.org,Chrome / Firefox / Safari / Edge 都会内置。浏览器第一次访问就强制 HTTPS,不受首次访问风险影响。

前置条件:

  • 有效 HTTPS 证书
  • 所有子域都 HTTPS
  • 重定向 HTTP 到 HTTPS
  • max-age ≥ 1 年

4.4 HSTS 的局限 ​

  • 首次访问无效:用户第一次访问,还没收到 HSTS 头,可能被 SSL Stripping
  • 用户清除 cookie / 隐私模式:可能丢失 HSTS 状态(部分浏览器)
  • 子域问题:必须 includeSubDomains 或每个子域单独配
  • 回退需要时间:清除 HSTS 后,max-age 时间内仍强制

4.5 Expect-CT(已弃用) ​

曾经的"证书透明度"检查:

http
Expect-CT: max-age=86400, enforce, report-uri="https://example.com/ct-report"

已被弃用(Chrome 107+),CT 检查现在强制,无需 header。

五、证书管理 ​

5.1 免费证书 ​

  • Let's Encrypt(自动续期)
  • Cloudflare(代理 + 免费证书)
  • ZeroSSL(类似 Let's Encrypt)

5.2 商业证书 ​

  • DigiCert、GlobalSign 等
  • 价格几百到几万/年
  • 适合企业级、EV 证书

5.3 通配符证书 ​

*.example.com

适合多子域场景。但要注意:

  • 私钥泄露 = 所有子域全失
  • 需要定期轮换

5.4 自动续期 ​

bash
# Certbot + Let's Encrypt
certbot --nginx -d example.com -d www.example.com

# 自动续期(crontab)
0 3 * * * certbot renew --quiet

六、客户端防护 ​

6.1 不要忽略证书警告 ​

很多用户看到"您的连接不是私密连接"会点继续访问——这是 MITM 的入口。

前端能做:

  • 检测证书错误,显示醒目的"危险"提示
  • 重要操作(支付)检测到非 HTTPS 时,阻止!
ts
// HTTPS-only mode(开发可关)
if (location.protocol !== 'https:' && location.hostname !== 'localhost') {
  showFatalError('此页面必须用 HTTPS 访问')
  throw new Error('Insecure context')
}

6.2 Mixed Content ​

HTTPS 页面加载 HTTP 资源会被浏览器拦截:

html
<!-- ❌ Blocked -->
<img src="http://example.com/image.png">
<script src="http://example.com/lib.js"></script>

强制 HTTPS:

html
<meta http-equiv="Content-Security-Policy" content="upgrade-insecure-requests">

或在服务器配置中自动升级。

七、HTTPS 性能开销 ​

很多人担心 HTTPS 性能差,实际上:

TLS 握手: 1~2 个 RTT(可优化为 0-RTT)
加密开销: < 1% CPU(现代 CPU 有 AES-NI)
加密大小: TLS 1.3 比 TLS 1.2 更紧凑

现代 HTTPS 几乎没有性能问题,而且 HTTP/2、HTTP/3 都强制要求 HTTPS。

优化 ​

nginx
# TLS 1.3(更快、更安全)
ssl_protocols TLSv1.2 TLSv1.3;

# Session Resumption(避免每次握手)
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d;

# OCSP Stapling(避免客户端查证书状态)
ssl_stapling on;

八、API 通信额外加密 ​

对于特别敏感的接口(支付、身份证),HTTPS 不够,需要额外加密:

ts
// 国密 SM2/SM4
import { sm2, sm4 } from 'gm-crypto'

// 客户端:用服务端公钥加密
const ciphertext = sm2.encrypt(data, serverPublicKey)

// 服务端:用私钥解密
const plaintext = sm2.decrypt(ciphertext, serverPrivateKey)
ts
// 或:RSA + AES 混合
// 客户端:生成 AES key,用 RSA 加密 AES key,数据用 AES 加密

何时需要 ​

  • 金融业务(支付、转账、贷款)
  • 医疗数据
  • 政府/军工
  • 行业合规要求(等保)

九、WebSocket 安全 ​

ts
// ❌ 不安全
new WebSocket('ws://example.com/socket')

// ✅ 安全
new WebSocket('wss://example.com/socket')

// WebSocket 也需要鉴权
const ws = new WebSocket('wss://example.com/socket', {
  protocols: [`Bearer.${token}`]  // 自定义 subprotocol 带 token
})

// 服务端校验
ws.on('upgrade', (req) => {
  const token = req.headers['sec-websocket-protocol'].replace('Bearer.', '')
  if (!verifyToken(token)) {
    socket.destroy()
  }
})

十、安全清单 ​

10.1 部署配置 ​

  • [ ] 强制 HTTPS(301 重定向)
  • [ ] HSTS 头(1 年 + includeSubDomains)
  • [ ] HSTS Preload(申请后)
  • [ ] TLS 1.2+(禁用 SSLv3 / TLS 1.0 / 1.1)
  • [ ] 强加密套件(AEAD 优先)

10.2 证书管理 ​

  • [ ] 证书自动续期(crontab)
  • [ ] 过期监控(告警 30 天前)
  • [ ] 私钥不进入 git
  • [ ] 私钥不部署到日志/错误信息
  • [ ] 定期轮换(1~2 年)

10.3 应用层 ​

  • [ ] 关键操作二次验证
  • [ ] 不要在非 HTTPS 上做认证
  • [ ] API 也用 HTTPS / WSS
  • [ ] WebSocket 鉴权
  • [ ] 检测 Mixed Content 并阻止

🎯 面试常考 ​

Q1：中间人攻击怎么发生的?

攻击者插入到客户端与服务器之间,转发并篡改流量。前提是能劫持网络路径或让客户端信任攻击者的证书。

Q2：怎么防?

强制 HTTPS(HSTS 头 + 预加载)、有效证书链、禁用弱密码套件、证书透明度(CT)、客户端证书(双向 TLS)。

Q3：HSTS 有什么用?

让浏览器强制用 HTTPS 访问,连首次访问也不给降级到 HTTP 的机会,防止 SSL strip。

📝 小结 ​

  • MITM 的前提是能插入到客户端与服务器之间,或让客户端信任攻击者的证书。
  • 防护:强制 HTTPS + HSTS(带预加载)+ 有效证书链 + 禁用弱套件 + 证书透明度(CT)。
  • 企业网络的 HTTPS 中间人是真实存在且合法的 —— 它能解密所有流量,所以别在内网传敏感数据。
  • 客户端证书(mTLS)是更高一层的身份认证,成本也更高。
