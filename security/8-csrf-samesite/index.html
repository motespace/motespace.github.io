CSRF 防御:Token + SameSite + 二次验证

一、为什么需要多重防御

Section titled “一、为什么需要多重防御”

CSRF 防御没有银弹——任何单一防御都有绕过可能。生产环境必须多层防御:

二、SameSite Cookie(浏览器层防御)

Section titled “二、SameSite Cookie(浏览器层防御)”

2.1 三种取值

Section titled “2.1 三种取值”

2.2 行为对比

Section titled “2.2 行为对比”
SameSite 跨域 GET 跨域 POST(表单) 跨域 AJAX
Strict ❌ 不带 ❌ 不带 ❌ 不带
Lax(默认) ✅ 带 ❌ 不带 ❌ 不带
None ✅ 带 ✅ 带 ✅ 带

2.3 实战配置

Section titled “2.3 实战配置”

注意 SameSite=None 必须配合 Secure,否则现代浏览器会拒绝。

2.4 __Host- 前缀

Section titled “2.4 __Host- 前缀”

防 Cookie 注入(子域劫持):

约束:

  • 必须 Secure
  • 不能有 Domain 属性
  • Path 必须是 /

如果攻击者在子域写入 Cookie,会被浏览器拒绝。

2.5 SameSite 的局限

Section titled “2.5 SameSite 的局限”
  • 老浏览器不支持(IE、所有 Safari < 13)
  • 子域跳转:从 app.example.com 跳到 example.com 算同站
  • GET 仍带 Cookie(Lax 模式):如果有 GET 状态修改操作,仍有风险
  • 第三方嵌入:被嵌入的第三方页面如果要带 Cookie,需要 None

三、CSRF Token(请求层防御)

Section titled “三、CSRF Token(请求层防御)”

3.1 同步 Token 模式

Section titled “3.1 同步 Token 模式”

服务端:生成 token,塞到表单 / 响应。

前端:在请求时带 token。

3.2 Double Submit Cookie(无状态)

Section titled “3.2 Double Submit Cookie(无状态)”

适合 前后端分离 + JWT 场景:

为什么安全:攻击者读不到 csrf Cookie(同源策略),无法伪造 header。

3.3 CSRF Token 的局限

Section titled “3.3 CSRF Token 的局限”
  • 增加复杂度(每个表单 / 每个 AJAX 都要带)
  • token 泄露就失效(但可加过期时间)
  • 服务端要管理 token 状态(或者用签名 JWT)

四、Origin / Referer 验证(辅助层)

Section titled “四、Origin / Referer 验证(辅助层)”

实战经验:

  • Origin 由浏览器强制设置,不能被 JS 改
  • Referer 用户可能禁用,但作为辅助手段可以接受
  • HTTPS → HTTPS 时 Referer 完整
  • HTTPS → HTTP 时 Referer 只剩 origin(隐私模式)

六、业务层:二次验证(关键操作)

Section titled “六、业务层:二次验证(关键操作)”

对于真正敏感的操作(转账、修改密码、删除账户),不要只靠技术防御:

6.1 哪些操作必须二次验证

Section titled “6.1 哪些操作必须二次验证”
操作 二次验证
转账 / 支付 短信验证码 + 密码
修改密码 旧密码 + 邮箱验证码
删除账户 密码 + 邮箱确认链接
修改手机号 旧手机号验证码 + 新手机号验证码
大额退款 财务主管审批 + 二次确认

九、与其他防御的关系

Section titled “九、与其他防御的关系”
防御 关系
XSS XSS 可绕过 CSRF(攻击者能读 Cookie、能发请求)

🎯 面试常考

Section titled “🎯 面试常考”

Q1：CSRF 是什么?

诱导已登录用户的浏览器向目标站点发请求,利用的是浏览器会自动带上 Cookie。

Q2：怎么防?

① SameSite Cookie(Lax/Strict)—— 首选;② CSRF Token 校验;③ 校验 Origin/Referer;④ 敏感操作二次确认。

Q3：SameSite 三种模式?

Strict(完全不跨站带)、Lax(顶级导航的 GET 带,默认)、None + Secure(跨站带,必须配 Secure,用于跨站场景)。

📝 小结

Section titled “📝 小结”
  • CSRF 利用的是「浏览器会自动带 Cookie」,本质是浏览器替攻击者发了带凭证的请求。
  • 三层防御:SameSite Cookie(主力)、CSRF Token(通用)、Origin/Referer 校验(补充)。
  • SameSite=Lax 挡得掉表单 POST,但挡不住顶级导航的 GET(如 <img src=...>),所以不能只靠它。
  • 敏感操作加二次验证(验证码 / 短信),这是支付、改密类操作的最后一道。
