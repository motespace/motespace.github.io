安全检查清单(部署前必看) ​

复制到 PR 模板 / 上线评审 Checklist,逐项打勾。

一、输入与渲染 ​

  • [ ] 所有用户输入走统一过滤层,不直接拼接到 DOM / SQL / shell
  • [ ] 富文本(评论、商品描述、私信)走 DOMPurify 白名单
  • [ ] URL 跳转校验 protocol(只允许 http/https)
  • [ ] 文件上传校验 MIME 类型 + 扩展名 + 实际内容(防伪装)
  • [ ] JSON 输出避免泄漏堆栈 / 内部错误信息

二、Cookie 与会话 ​

  • [ ] 敏感 Cookie 设 HttpOnly(防 JS 窃取)
  • [ ] 强制 HTTPS 的 Cookie 加 Secure
  • [ ] 跨站请求防护加 SameSite=Lax 或 Strict
  • [ ] Session ID 用 __Host- 前缀(防子域劫持)
  • [ ] 登录态过期时间合理(token 15~30 分钟,refresh 7~30 天)

三、CSP(Content Security Policy) ​

  • [ ] 至少开 Content-Security-Policy-Report-Only 观察违规
  • [ ] default-src 'self' 起步
  • [ ] inline script 用 nonce 机制,不要 unsafe-inline
  • [ ] frame-ancestors 'none' 防点击劫持
  • [ ] base-uri 'self' 防 <base> 劫持
  • [ ] 上线前切换为强制 + 收集违规报告

四、CSRF 与跨域 ​

  • [ ] 关键接口(支付、修改密码)要求 CSRF Token
  • [ ] 浏览器级别防护:Cookie 用 SameSite
  • [ ] CORS 不允许 *,配置白名单
  • [ ] 关键操作二次验证(密码 / 短信 / 邮箱)
  • [ ] 服务端做权限校验,不依赖前端按钮 disabled

五、iframe 安全 ​

  • [ ] 自家页面加 X-Frame-Options: DENY 或 CSP frame-ancestors 'none'
  • [ ] 嵌入第三方 iframe 默认 sandbox=""(最严格)
  • [ ] 父页通过 postMessage 通信,严格校验 origin + source
  • [ ] targetOrigin 不传 '*'

六、第三方依赖 ​

  • [ ] npm audit 无高危漏洞
  • [ ] package-lock.json 进入仓库
  • [ ] CI 集成 Snyk / Dependabot
  • [ ] 关键依赖固定精确版本(不写 ^)
  • [ ] 私有 npm 包走内网仓库

七、网络与传输 ​

  • [ ] 全站强制 HTTPS(301 重定向 + HSTS)
  • [ ] HSTS preload(浏览器内置)
  • [ ] 不忽略证书警告(用户侧)
  • [ ] 敏感接口单独加密(国密 / RSA)
  • [ ] WebSocket 用 TLS(wss://)

八、监控与响应 ​

  • [ ] 错误监控(Sentry / 自建)
  • [ ] 安全事件告警(异常登录、暴力破解、敏感操作)
  • [ ] 操作日志(谁、何时、做了什么)留 6 个月以上
  • [ ] 应急响应流程文档化
  • [ ] 关键资产清单 + 应急预案

九、认证与授权 ​

  • [ ] 密码哈希用 bcrypt / argon2(不用 MD5/SHA1)
  • [ ] 多因素认证(管理员 / 财务角色强制)
  • [ ] 失败登录限速(防暴力破解)
  • [ ] 密码强度校验(8 位 + 复杂度)
  • [ ] 服务端独立校验权限,不只信前端

十、业务场景专项 ​

支付 / 转账 ​

  • [ ] 操作前确认弹窗(显示金额、收款方)
  • [ ] 二次密码 / 短信验证
  • [ ] 限速(同一账户每小时最多 5 笔)
  • [ ] 风控引擎实时检测异常

富文本 / 评论 ​

  • [ ] DOMPurify 白名单
  • [ ] 长度限制(评论 1000 字以内)
  • [ ] 关键词过滤(广告、敏感词)
  • [ ] XSS 检测后端兜底

第三方登录 ​

  • [ ] OAuth state 参数防 CSRF
  • [ ] postMessage 校验 origin
  • [ ] 回调地址白名单
  • [ ] 不通过 popup 直接传 token,走后端换 code

十一、按项目阶段使用 ​

新项目开发期 ​

  • [ ] 选好框架默认安全策略(Next.js 默认 CSP、Svelte 安全头)
  • [ ] 引入 lint 规则(eslint-plugin-security)
  • [ ] CI 集成 SAST(代码扫描)
  • [ ] 关键依赖审计(首次安装时跑一遍)

上线前 ​

  • [ ] 跑一遍完整 Checklist
  • [ ] 渗透测试(关键业务)
  • [ ] 应急响应演练
  • [ ] 备份可用性验证

运营期 ​

  • [ ] 周:依赖审计(npm audit)、监控告警检查
  • [ ] 月:CSP 违规报告审视、权限审计
  • [ ] 季:渗透测试、应急演练、密钥轮换

🎯 面试常考 ​

Q1：上线前安全检查看什么?

传输层(HTTPS/TLS 配置)、认证(密码强度、会话过期、Token 存储)、授权(越权校验)、输入(校验与转义)、前端(XSS/CSRF/点击劫持)、依赖(SCA)、密钥管理。

Q2：哪些是前端能做的?

避免 XSS(不注入 HTML、用框架转义)、防 CSRF(SameSite + Token)、防点击劫持(X-Frame-Options / CSP frame-ancestors)、不把密钥写进代码、第三方脚本用 SRI + CSP 限制。

Q3：最容易被忽略的三条?

① 密钥进了前端 bundle;② 依赖里有已知漏洞没扫;③ 只在前端做了权限判断,接口没做服务端校验。

📝 小结 ​

  • 发版前的闸门,七个维度:传输层、认证、授权、输入、依赖、密钥、监控。
  • 前端不是安全边界 —— 隐藏按钮等于没隐藏,权限必须服务端校验。
  • 最易漏的三条:密钥进了前端 bundle、依赖有已知漏洞没扫、只在前端做了权限判断。
  • 清单要落到具体配置(响应头 / 环境变量 / 扫描命令),否则没法执行。
