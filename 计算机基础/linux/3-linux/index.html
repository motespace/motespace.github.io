🎯 面试常考

Section titled “🎯 面试常考”

Q1：排查「进程占满 CPU」的标准流程?

Section titled “Q1：排查「进程占满 CPU」的标准流程?”

标准四步:

定位到线程后用 jstack &lt;PID&gt;(Java)拿到线程栈,或 pstack/gdb 拿原生栈。

关键概念:CPU 密集型进程的 CPU 时间会被分摊到所有线程, 所以要看单个线程的占用,而不是进程总占用 —— 这是最常见的误区。

同理排查内存:top 看 RES(实际常驻),pmap -x &lt;PID&gt; 看具体占用。

Q2：内存 OOM 了怎么排查?

Section titled “Q2：内存 OOM 了怎么排查?”
  1. 确认是不是被 OOM Killer 杀的:dmesg -T | grep -i "killed process"
  2. 看内存趋势:free -h(重点看 available,不是 free)、vmstat 1
  3. 看谁在吃:top 按内存排序 / ps aux --sort=-%mem | head
  4. 定位到进程后:pmap -x &lt;PID&gt;(看内存映射)、cat /proc/&lt;PID&gt;/status(VmRSS)
  5. 常见原因:
    • 内存泄漏:对象只增不减 → 典型是缓存无上限、监听器没解绑、闭包持有大对象
    • 缓存无上限:最常见的「看起来像泄漏」,其实是有意的缓存但没设 LRU
    • 容器 OOM:limit 太小,或者没设 --memory-reservation

Q3：load average 是什么?怎么解读?

Section titled “Q3：load average 是什么?怎么解读?”

load average 是 1 分钟 / 5 分钟 / 15 分钟的平均可运行任务数(R + D 状态)。

解读:

  • load ≈ CPU 核数 → 刚好跑满
  • load > CPU 核数 → 有任务在排队
  • load 高但 CPU 空闲 → 大概率卡在 D 状态(不可中断 IO),比如磁盘/NFS 慢

对比 CPU 利用率:load 高 + CPU 高 = 真忙;load 高 + CPU 低 = IO 瓶颈, 这是最实用的判别组合。

注意:load 统计的是「可运行 + 不可中断」的任务,在容器里如果宿主机 IO 慢,容器内 load 会异常高。

📝 小结

Section titled “📝 小结”
  • 查 CPU 满:top 找 PID → top -H 找线程 → ps -T 对线程名 → jstack/pstack 拿栈。要看单线程而不是进程总占用。
  • 查内存:先 dmesg | grep -i killed process 确认是不是 OOM Killer,再看 free 的 available、vmstat、pmap。
  • load average 是可运行+不可中断任务的均值,和 CPU 核数比:load 高 CPU 低 = IO 瓶颈(D 状态)。
  • 最常见的「假泄漏」是缓存没设上限,看起来像泄漏其实是设计问题。
