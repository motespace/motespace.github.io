32. Vue3 + 微前端（qiankun / 无界）

Section titled “32. Vue3 + 微前端（qiankun / 无界）”

场景：3 个团队合并一个巨型 Vue3 后台（30 个页面、5 万行代码），技术栈 Vue3 + qiankun / 无界。怎么选？怎么落地？登录态怎么同步？子应用之间怎么通信？样式冲突怎么解决？

1. 选型对比：qiankun vs 无界

Section titled “1. 选型对比：qiankun vs 无界”
维度 qiankun 无界
底层原理 基于 single-spa，JS 沙箱 Web Components 封装，Shadow DOM 样式隔离
样式隔离 CSS Modules / 加前缀，需手动处理 Shadow DOM 原生隔离，天然
JS 沙箱 快照沙箱（原理简单但全局变量污染风险） 代理沙箱（更干净）
Vue3 支持 需手动处理（qiankun 2.x 起完善） 天然支持
通信机制 props / onGlobalStateChange / 事件总线 props / 无界提供的通信 API
接入复杂度 子应用需改 webpack 配置（output library） 极简（类似 iframe 但更强大）
预加载 prefetch 多应用 无界内置预加载
生态 成熟（阿里系），文档多 较新（字节系），社区活跃
适用 React + Vue 混合项目（跨框架） 纯 Vue3 项目（简单场景）

结论：

  • 纯 Vue3 技术栈 → 无界（接入简单、样式隔离省心）
  • 多技术栈混合（React 子应用 + Vue 主应用）→ qiankun
  • 本题按 Vue3 + qiankun 为主讲，无界补充

10. 常见坑 + 解决方案

Section titled “10. 常见坑 + 解决方案”
坑 原因 解决方案
样式冲突 主应用和子应用全局样式冲突 qiankun 严格沙箱 / 无界 Shadow DOM
子应用 404 刷新页面时路由被主应用拦截 Nginx 配置 try_files + error_page 404 fallback
通信丢失 子应用 unmount 后事件监听未清理 onUnmounted 中 eventBus.off()
登录态丢失 子应用无法访问主应用 Cookie 主应用通过 props 传 token / localStorage 共享
样式闪动 子应用加载时白屏 骨架屏 + qiankun prefetch: 'all'
Vue3 全局状态 子应用有自己的 Vue 实例，状态不互通 props 传 Pinia / 全局事件总线 mitt
公共依赖重复加载 每个子应用都加载了相同的 Vue 预加载 prefetch / CDN 共享依赖
沙箱变量污染 qiankun 快照沙箱覆盖主应用全局变量 用 experimentalStyleIsolation + 代理沙箱
子应用请求 baseURL 子应用请求没有正确的 baseURL 子应用 axios 设置 baseURL: window.location.origin

追问：

  • qiankun 和无界哪个更推荐？→ 纯 Vue3 选无界（简单省心）；多框架混合选 qiankun
  • 子应用之间怎么通信？→ props 传值 / 全局事件总线 mitt / qiankun onGlobalStateChange
  • 子应用刷新 404 怎么办？→ Nginx 配置 try_files + error_page 404 = /merchant/index.html
  • 主应用登录态怎么同步给子应用？→ 主应用通过 props 传 token / Cookie 设置 Domain 共享 / localStorage
  • 微前端缺点？→ 首屏增加请求数、调试复杂、样式沙箱有坑；业务简单别用
  • 什么时候不用微前端？→ 团队 < 2 人、独立部署需求不强 → 直接拆 npm 包 / Monorepo
  • 子应用可以独立运行吗？→ 可以！加一个 renderWithQiankun 判断，不在 qiankun 环境时独立挂载

📝 小结

Section titled “📝 小结”
  • 微前端场景题要有决策与取舍意识,不是只讲技术名词。
  • 决策前提:团队规模、是否需要独立发布、是否有共享设计系统的诉求、现有系统耦合度、部署与路由基础设施。
  • 落地方案:qiankun/micro-app 主子应用改造、样式隔离、状态共享(登录态与租户信息)、公共依赖与 CDN、公共组件库与设计系统、路由与 Nginx 的 base path 配置。
  • 常见坑:子应用重复打包公共依赖导致体积膨胀、跨应用跳转与登录态同步、样式污染、发布节奏不一致。
  • 面试加分:能给出「我们评估后暂缓微前端,改用 Monorepo + 模块化」的结论与理由,这比硬上微前端更显判断力。
