52. 撤销 / 重做（Undo/Redo）实现

Section titled “52. 撤销 / 重做（Undo/Redo）实现”

场景：富文本编辑器、画板、表单设计器，怎么实现 Ctrl+Z / Ctrl+Y？

答案要点：

追问：

  • 命令模式 vs 快照模式？→ 命令模式内存小但实现复杂；快照简单但内存大
  • 撤销栈深度限制？→ 限制 50-100 步（防止内存爆炸）
  • 性能优化？→ 节流 + 差异存储 + 结构共享（immer）
  • 富文本编辑器怎么选？→ ProseMirror / Slate / TipTap 都内置历史管理

53. CRDT 冲突解决进阶（协同编辑）

Section titled “53. CRDT 冲突解决进阶（协同编辑）”

场景：多人同时编辑一个文档，A 在第 5 行加字、B 在第 7 行删字，怎么无冲突合并？

答案要点：

追问：

  • CRDT 和 OT 怎么选？→ 协同（多人同时改）选 CRDT；服务器权威性高选 OT
  • Yjs 性能如何？→ 10 万字符 + 100 用户同时编辑 < 100ms 延迟
  • 离线编辑怎么处理冲突？→ CRDT 自动合并，无需用户干预
  • 怎么落地到业务？→ 富文本编辑器（ProseMirror + Yjs）/ 表格（Airtable）/ 设计工具（Figma）

54. 参与需求评审时，前端该输出什么？

Section titled “54. 参与需求评审时，前端该输出什么？”

场景：产品提了个“客户列表要能自定义列、能导出、能批量操作”的需求，评审会上你和后端、产品吵起来了。面试问：你会怎么参与需求评审？

答案要点：

技术方案文档模板（可以直接说你会写这个）：

追问：

  • 需求不清晰怎么办 → 评审时把“未知项”显式列出来(谁在什么时候给结论),别默默假设
  • 产品不改需求但技术实现成本很高 → 给出 2~3 个方案和成本,让产品做取舍,而不是直接说“做不了”
  • 和后端对接口对不上 → 先落接口契约文档,评审纪要里写明责任人和时间

55. 需求排期紧,时间不够怎么办？

Section titled “55. 需求排期紧,时间不够怎么办？”

场景：产品临时插了个紧急需求,老板说两天上线。你怎么排？

答案要点：

面试话术：

“我不会说做不了，也不会默默硬上。我的做法是评估影响面 → 给 2~3 个方案和各自成本 → 让决策者做取舍 → 用功能开关和灰度把上线风险兜住 → 临时方案标注技术债和还债时间。”

协作类回答的通用框架

Section titled “协作类回答的通用框架”

📝 小结

Section titled “📝 小结”
  • 协作类问题的通用框架:澄清需求与边界 → 拆解与排期 → 技术方案与风险 → 沟通机制 → 结果与沉淀。
  • 常见场景:需求变更频繁、与后端/产品/设计对齐、跨团队接口联调、代码规范推行、评审他人代码、新人带教。
  • 关键能力:把技术语言翻译成业务语言,给出可选项与代价,让决策者做选择而不是替他做。
  • 沉淀能力:文档、组件库、规范、自动化脚本,让协作成本随时间下降。
  • 面试加分:讲一次「我推动了什么流程改进,量化了收益」。
