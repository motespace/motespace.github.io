4. 三种策略总结

Section titled “4. 三种策略总结”
场景 策略 原因
GET 查询 Cancel old, keep new 用户想查最新数据，5 秒前的结果已过期
POST 提交 Share promise 防止重复提交，扣款/创建等操作不能并发
超时清理 5s TTL 兜底 避免 Map 无限增长 + 防止旧 Promise 长期占用

5. 调用方写法

Section titled “5. 调用方写法”

追问：

  • 缓存清理怎么做？→ 响应拦截器自动清理；兜底用 setInterval 每 10s 清理超 5s 的
  • 内存泄漏风险？→ setInterval 兜底清理 + Map 不会无限增长
  • POST 有 body 怎么算 key？→ method + url + params + data 全部 JSON 序列化后拼接
  • GET 隔 5 秒再查参数一样算新请求？→ 算！因为 5s 前那个 Promise 已经清理了
  • 多人同时点按钮？→ 同一个用户同一时刻只有一个请求，不同用户 key 不同（因为 token 在 header 里）
  • 为什么 GET 和 POST 策略不同？→ GET 通常是查询（要最新数据），POST 通常是提交（不能重复执行）

场景：服务器有实时数据（股票价格、聊天消息），需要推到前端，怎么实现？

答案要点：

对比：

SSE WebSocket
方向 服务器 → 客户端（单向） 双向
协议 HTTP 独立 WS 协议
自动重连 浏览器原生 自己实现
适用 股票、新闻、通知 聊天、游戏、协同编辑

追问：

  • 什么场景用 SSE 不用 WebSocket？→ 只需服务器推送，客户端不发送（如实时通知）
  • SSE 和长轮询区别？→ SSE 是长连接（服务器主动推），长轮询是短连接（客户端轮询）
  • 移动端兼容性？→ SSE 在 WebView 里兼容性差，WebSocket 更好

📝 小结

Section titled “📝 小结”
  • 请求编排的难点:依赖顺序、并发控制、取消与重试、竞态、弱网与超时、部分失败。
  • 常见问题:串行请求造成瀑布、并发无上限打爆后端、旧响应覆盖新响应(竞态)、组件卸载后仍 setState、失败重试策略不当、接口部分成功如何处理。
  • 解法:并行 + 依赖分层、请求池与并发上限、AbortController 取消、按 key 丢弃过期响应、统一拦截器(loading 计数、错误码映射、重试与退避)。
  • 幂等与去重:同一 key 的重复请求合并(query 层)或由后端幂等键保证。
  • 面试加分:能讲清「如何保证列表快速切换时不会串数据」——请求序号/AbortController + 响应 key 校验。
