10. Cookie 注入时机差异

Section titled “10. Cookie 注入时机差异”

App WebView 注入 Cookie 通常晚于页面 JS 执行，因此：

  • 不能在模块初始化时同步读 Cookie，必须用异步等待（waitForWebViewLanguage / waitForWebViewTheme）。
  • visibilitychange 返回前台时重新检查 Cookie，因为 App 可能已更新。
  • 如果 Cookie 一直没注入，要有兜底超时（2.5s）避免一直等待。

11. iOS WKWebView vs Android WebView 差异

Section titled “11. iOS WKWebView vs Android WebView 差异”
维度 iOS WKWebView Android WebView
postMessage 可靠性 较稳定，但跨域时可能丢消息 部分版本有消息丢失问题
Cookie 注入时机 WKUserScript 注入时机可控制 同步注入，时机较晚
window.nativeToPage 必须 App 主动注入 同左
document.referrer 受 SameSite 限制 无限制
调试 Safari Web Inspector Chrome DevTools (chrome://inspect)

Section titled “12. 降级处理 — 无桥接对象时”

追问：

  • App 没注入 nativeToPage 怎么办？→ 先 isWebView() 判断，为 false 时走普通浏览器逻辑
  • Cookie 一直不注入怎么办？→ waitForWebViewLanguage 内部有 2.5s 超时兜底，超时后用 URL 参数或默认值
  • H5 返回前台时为什么还要刷新用户信息？→ App 可能在 H5 不可见期间修改了登录态（如 App 退出账号），不刷新会导致 H5 展示旧状态并用过期 Token 发起请求
  • 抽奖弹层加载完成怎么通知 App？→ H5 加载完成后主动 postMessage，如 window.lotteryLoadComplete.postMessage('lotteryLoadComplete')，让 App 知道何时可以切走
  • 为什么不所有跳转都用 window.location？→ WebView 内硬跳转会让 WebView 栈丢失，App 无法管理导航历史；用 postMessage 通知 App 处理，App 可以自己决定是开新 WebView 还是 Native 页面

📝 小结

Section titled “📝 小结”
  • H5 适配四大经典问题:rem/vw 方案原理、软键盘弹起导致错位、点击穿透与滚动穿透、安全区(刘海与底部横条)。
  • rem 原理:用 postcss-pxt-to-viewport 或 postcss-pxt-to-rem 把 px 按设计稿比例转成 rem/vw,根字号随视口宽度动态设置(html { font-size: clientWidth / 10 }),实现等比缩放。
  • 安全区:viewport-fit=cover + env(safe-area-inset-*),底部固定按钮要 calc(16px + env(safe-area-inset-bottom))。
  • 软键盘:iOS 用 focusin + scrollIntoView 并延迟等待动画,Android 监听 resize 判断视口高度变化;两者行为不同必须分别处理。
  • 穿透:滚动穿透用 overscroll-behavior: contain + 锁定 body 滚动;点击穿透用 pointerdown 拦截或延迟关闭。
  • 面试加分:说清「为什么 iOS 不触发 resize 而 Android 触发」与「rem 方案的代价是字体与图片不随视口等比时的取舍」。
