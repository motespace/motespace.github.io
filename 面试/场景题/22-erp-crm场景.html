二十二、ERP / CRM 业务场景题 ​

面向 ERP / CRM / 运营后台的 React 岗位。这组题的核心是"业务感"：字段联动、审批流、数据权限、批量导入导出 —— 纯技术题问不出来的部分。

63. 客户列表 5 万条 + 组合筛选很慢 ​

场景：客户管理页有 5 万条数据，支持"名称模糊搜索 + 等级 + 状态 + 成交日期区间"组合筛选。现在是前端拉全量再过滤，页面卡死。

答案要点：

1. 筛选条件全部交给后端,前端只发参数
   GET /api/customers?name=张&level=A&status=1&startDate=...&page=1&pageSize=20

2. 关键:防抖 + 竞态取消
   - 输入框 300ms 防抖
   - 新请求发出时 AbortController 取消上一个
     (旧响应晚到会覆盖新数据,这是"搜索结果错乱"的经典原因)

3. 筛选条件写进 URL query
   - 刷新不丢条件、可以分享链接、后退键可用
   - React Router 的 useSearchParams 即可

4. 分页用后端分页,不要前端 slice
   - showTotal 显示真实总数
   - 快速跳页用 pageSize=50

5. 复杂组合筛选(区间+多选+关联)用"查询条件对象"管理
   - 区分"已输入"和"已提交"两个状态,避免每次输入都发请求
ts
const [draft, setDraft] = useState<Filters>(initialFilters)
const [applied, setApplied] = useState<Filters>(initialFilters)
const abortRef = useRef<AbortController>()

const run = useCallback(async (filters: Filters) => {
  abortRef.current?.abort()
  const controller = new AbortController()
  abortRef.current = controller
  const res = await api.listCustomers(filters, controller.signal)
  setRows(res.list)
}, [])

追问：

  • 用户输入"张"然后快速改成"张三"，只发一次请求 → 防抖 300ms
  • 后端筛选很慢（3 秒）→ 前端加 loading 骨架屏 + 请求超时兜底；根治是后端加组合索引 / ES
  • 导出要求"全部筛选结果"而不是当前页 → 导出接口独立，传筛选条件不传分页

64. Excel 批量导入 5 万行客户 ​

场景：运营要一次性导入 5 万行客户数据（Excel），要求：格式校验、查重、失败行给出原因、成功行入库。

答案要点：

1. 前端只做"预校验 + 分片提交",不保证强一致
   - 解析:SheetJS(xlsx) 读第一行做表头映射
   - 预校验:行级校验(必填/格式/枚举),把错误标在表格里
   - 查重:批量把待查字段(手机号)一次传给后端查重接口,不要一行一请求

2. 分批提交
   - 每批 500~1000 行,串行或并发 2~3(别太多,后端压力大)
   - 每批上报进度(已处理/总数),前端进度条

3. 失败行导出
   - 后端返回失败明细(行号 + 字段 + 原因)
   - 前端生成"错误报告"Excel 让用户下载修改后重传
   - 这是最能体现产品思维的点

4. 大文件解析别卡主线程
   - xlsx 解析放 Web Worker,否则页面假死
   - 5 万行 xlsx 内存峰值可能 500MB+,考虑用 CSV 替代 xlsx

5. 幂等
   - 每次导入生成 batchId,后端按 batchId 去重,重复提交不产生脏数据
ts
// Worker 里解析,主线程只收结果
const worker = new Worker(new URL('./parse.worker.ts', import.meta.url), { type: 'module' })
worker.postMessage({ file })
worker.onmessage = ({ data }) => setRows(data.rows)   // data: { rows, errors }

追问：

  • 解析时页面卡 → Web Worker
  • 用户中途关闭页面 → batchId 存在 localStorage，重新进来可继续查导入状态
  • 导入 5 万行要多久 → 前端 1~2 分钟很正常，关键是把"等待"做成有进度的体验，而不是一个转圈

65. 导出 10 万行 Excel，前端内存爆了 ​

场景：客户列表导出 10 万行，用 SheetJS 生成 Blob，页面直接崩了。

答案要点：

1. 10 万行不要在前端生成 —— 走服务端导出
   POST /api/customers/export  (传筛选条件)
   → 返回 taskId
   → 前端轮询任务状态 / WebSocket 推送
   → 生成完成后给 OSS 签名下载地址,前端 a[download] 触发

2. 前端体验
   - "导出任务已创建,完成后会通知你" + 下载中心列表
   - 大数据量导出要有"导出中心"页面,而不是让用户干等弹窗

3. 一定要在前端做的话
   - 用 CSV(流式拼接字符串)而不是 xlsx
   - 分片生成,每 1 万行 append 一块,最后 new Blob(parts)
   - 或者 File System Access API:直接流式写磁盘,不占内存
     (仅 Chromium 支持,需要降级方案)

4. 兜底
   - 超过阈值(比如 1 万行)前端直接禁用导出,提示走服务端
ts
// 前端兜底:超过阈值就提示
if (total > 10000) {
  message.info('数据量较大,已转为后台导出任务,完成后可在下载中心获取')
  const { taskId } = await api.createExportTask(filters)
  navigate(`/download-center?taskId=${taskId}`)
  return
}

追问：

  • 后端导出要 3 分钟 → 异步任务 + 通知，页面不能阻塞
  • 导出的 Excel 里要不要脱敏手机号 → 按角色判断，导出接口服务端脱敏（别只在前端隐藏）

66. 客户类型不同，表单字段完全不一样 ​

场景：CRM 里"线索 / 商机 / 合同"三类客户，字段差异很大（线索只有联系方式；合同要有金额、付款方式、交付日期）。做成一个表单还是三个？

答案要点：

1. 三种做法
   a) 三个独立表单组件 —— 字段差异大时最清晰,但复用少
   b) 一个大表单 + shouldUpdate 动态显隐 —— 字段少时可用,字段多时表单巨大难维护
   c) Schema 驱动的动态表单 —— 配置化 ERP 最优解

2. Schema 驱动
   type FieldSchema = {
     name: string
     label: string
     type: 'input' | 'select' | 'date' | 'number' | 'custom'
     required?: boolean
     options?: {label,value}[]
     rules?: Rule[]
     visible?: (values) => boolean
     component?: React.ComponentType
   }

3. 关键设计
   - schema 由后端配置接口下发,产品经理在后台配
   - custom 类型允许塞业务组件(地址选择器/客户选择器)
   - visible + useWatch 做联动
   - 表单值统一 schema 校验,提交时按 schema 转 payload

4. 落地注意
   - Schema 渲染的性能:每个字段拆成独立组件,各自 useWatch
   - Schema 版本化:改了字段要兼容历史数据

追问：

  • 为什么不直接写死？→ 后端产品配字段是 ERP 的常态,写死等于每次改字段都要发版
  • Schema 里的校验规则怎么表达？→ 前端定义规则 DSL（required/pattern/max/min/custom fn），后端下发，前端用 Zod 动态编译

67. 审批流：提交 → 审批 → 驳回 → 再提交 ​

场景：ERP 单据审批。状态有：草稿、待审批、已通过、已驳回、已作废。用户能"撤回"，审批人能"驳回并附意见"。

答案要点：

1. 前端用状态机,不是一堆 if
   状态: DRAFT → SUBMITTED → APPROVED | REJECTED → (RESUBMIT) → SUBMITTED
   动作: SUBMIT / WITHDRAW / APPROVE / REJECT / CANCEL

   const TRANSITIONS = {
     DRAFT:     { SUBMIT: 'SUBMITTED', CANCEL: 'CANCELED' },
     SUBMITTED: { APPROVE: 'APPROVED', REJECT: 'REJECTED', WITHDRAW: 'DRAFT' },
     REJECTED:  { RESUBMIT: 'SUBMITTED', CANCEL: 'CANCELED' },
     APPROVED:  { CANCEL: 'CANCELED' },      // 已通过一般不能撤回,只能作废
     CANCELED:  {},
   }

   function can(action: Action, status: Status) {
     return Boolean(TRANSITIONS[status]?.[action])
   }

2. 按钮按状态渲染
   {can('SUBMIT', status) && <Button onClick={submit}>提交</Button>}
   {can('WITHDRAW', status) && <Button onClick={withdraw}>撤回</Button>}

3. 驳回必须带意见
   - Modal 里放 TextArea,必填
   - 意见进审批记录,详情页时间线展示

4. 状态以服务端为准
   - 前端乐观更新 → 后端失败要回滚
   - 多人同时审批:后端做状态机校验(当前状态必须匹配才允许流转)

5. 审批记录时间线
   - Timeline 组件展示:谁、什么时候、做了什么、意见

追问：

  • 提交后想改 → 已提交状态下要"撤回"才能改，草稿才能改
  • 审批人离职了 → 管理员改派,前端不关心
  • 状态在前端写死会不会和后端不一致 → 后端也维护一份，前端只是 UI 投影；关键流转以后端返回的状态为准

68. 两个销售同时改同一条客户记录 ​

场景：销售 A 和 B 同时打开客户详情，A 改了联系方式，B 也改了备注，两人都点保存。后保存的人覆盖了先保存的人。

答案要点：

1. 乐观锁(version 字段)
   GET  /api/customers/1  → { ..., version: 7 }
   PUT  /api/customers/1  body: { ..., version: 7 }
   后端: UPDATE ... SET version = version + 1 WHERE id = 1 AND version = 7
        影响行数 0 → 说明被别人改过,返回 409

2. 前端处理 409
   - 提示"数据已被他人修改,请刷新后重试"
   - 或做字段级合并:把本地改动和服务器最新值 diff,只冲突字段让用户选

3. 编辑前就检测(更友好)
   - 进入编辑时记录 version
   - 提交前或定时(30s)轮询 version,发现变化就提示

4. 悲观锁(强一致场景用)
   - 编辑时加锁 SELECT ... FOR UPDATE
   - 前端需要"锁定人"展示:XXX 正在编辑该客户

5. 字段级合并的坑
   - 只对"不同字段"合并,同字段冲突必须让人决策
   - 合并前要重新拉基线,不能拿 3 个不同版本的数据两两合并

追问：

  • 用户不改就离开 → 释放锁 / 悲观锁要有超时释放
  • 移动端离线编辑 → 用 CRDT 或操作日志 + 重放，参考 后台系统（SaaS）场景题 第 10 题

69. 数据权限：不同角色看到不同行 ​

场景：华东区销售只能看华东区的客户，财务能看到全部但看不到联系方式。行级 + 列级权限怎么做？

答案要点：

1. 行级权限必须后端做
   - 前端过滤是"假过滤",接口返回的数据已经泄露了
   - 后端根据当前用户的角色/组织范围拼 SQL 条件
   GET /api/customers?scope=mine

2. 前端要做的
   - 切换"我负责的 / 我部门 / 全部" → 把 scope 作为筛选条件,而不是本地过滤
   - 默认选中"我负责的",避免用户以为是全部
   - 数据范围提示:页面顶部显示"当前数据范围:华东区"

3. 列级权限(脱敏)
   - 后端按角色脱敏:手机号返回 138****1234
   - 完整值走单独接口,需要二次鉴权 + 记录审计
   - 前端只是隐藏列是不够的

4. 前端按钮级权限
   - <AuthBtn permission="customer:export"> 按钮级
   - 也要注意"无权限时按钮直接不渲染",避免用户点了报错

5. 权限变更的实时性
   - 管理员改了角色权限,用户当前页面要能感知
   - 方案:WebSocket 推送权限变更 → 刷新权限 store → 重新拉数据

追问：

  • 用户导出全部客户会不会绕过行级权限？→ 导出接口同样做范围过滤
  • 前端拿到的权限点很多,全存 localStorage 安全吗？→ 权限点只是"展示用",真正的判定在后端

70. 字典/主数据驱动：不同租户的字段和选项不一样 ​

场景：多租户 SaaS。租户 A 的客户表有"渠道"字段，租户 B 没有；租户 B 的状态下拉有 8 种，租户 A 只有 4 种。

答案要点：

1. 字典接口统一收口
   GET /api/dict?type=customer_status&tenantId=xxx
   → [{ label: '待跟进', value: 'PENDING', ... }]

2. 前端封装 DictSelect / DictTag 组件
   <DictSelect type="customer_status" />
   内部:useDict(type) → 缓存到全局 store,相同 type 只请求一次

3. 字段配置(哪些列显示)也走配置
   GET /api/page-config?page=customer.list
   → { columns: [{ key:'name', visible:true, order:1 }, ...] }
   前端据此动态渲染 Table columns

4. 字典缓存与失效
   - store 里缓存,TTL 或手动刷新
   - 配置变更时通过 WebSocket 推送失效消息

5. 枚举兜底
   - 后端返回了前端不认识的字典值,不能显示 undefined
   - DictTag 兜底显示原始 code

追问：

  • 每个页面都请求一次字典很浪费 → 全局缓存 + 相同 type 复用
  • 字典放前端还是后端 → 业务相关字典必须后端（权限/范围相关）；纯展示常量（如省份）可以前端内置

71. 列表页和详情页数据对不上 ​

场景：列表页显示客户 A 的状态是"待审批"，点进详情刷新后变成"已通过"（同事刚审批了）。列表和详情数据不一致。

答案要点：

1. 明确数据来源
   - 列表页数据 = TanStack Query 的 list 查询
   - 详情页数据 = detail 查询
   两个独立缓存,天然会不一致 —— 这是正常现象,要设计一致性策略

2. 策略 A:失效失效(invalidate)
   - 详情页操作成功后 invalidateQueries(['customers'])
   - 列表回到前台时 staleTime 到期自动重取
   - 简单,但列表会"跳一下"

3. 策略 B:精准更新(setQueryData)
   - 操作成功后直接改对应缓存里的那条记录
   - 体验最顺,但要小心缓存同步逻辑

4. 策略 C:推送(WebSocket)
   - 数据实时性要求高的模块(审批、库存、余额)用推送
   - 收到推送 → 更新 query cache → UI 立刻变
   - 这是 ERP 里"库存/余额"必备的

5. 列表重新可见时刷新
   - 浏览器标签切回前台时 refetch
   document.addEventListener('visibilitychange', () => {
     if (document.visibilityState === 'visible') queryClient.invalidateQueries()
   })

追问：

  • 用户在列表页停留很久 → 加轮询(30s)或订阅推送
  • 乐观更新失败怎么办 → 回滚 + toast 提示

72. 操作审计：谁改了什么 ​

场景：客户信息被改了，要能查到"谁、什么时候、把哪个字段从什么改成了什么"。

答案要点：

1. 前端提供"变更摘要"给后端
   - 提交时对比初始值和提交值,生成 diff
   const diff = diffFields(initialValues, values)
   → [{ field: 'phone', from: '138...', after: '139...' }]

2. 但审计不能只靠前端
   - 前端 diff 可能不全(批量操作、脚本改的)
   - 真正的审计在服务端:拦截器/ORM 变更钩子里记录

3. 前端要做的是"展示"
   - 详情页"操作日志"Tab:Timeline + 表格
   - 显示:操作人、时间、字段、变更前后、IP/设备

4. 敏感字段
   - 前端展示时密码/证件号脱敏
   - 导出日志也要脱敏 + 记录谁导出了日志

5. 合规角度
   - 审计日志只增不改,定期归档
   - 保留期限(等保通常要求 6 个月以上)

追问：

  • 批量修改 100 条怎么记？→ 一次操作一条审计记录 + 明细表关联 batchId
  • 用户能不能删日志？→ 不能，前端不给入口，后端接口也不提供

73. 附件与合同：PDF 在线预览、版本管理 ​

场景：客户要上传合同扫描件，支持在线预览 PDF；合同要保留历史版本；用户想在系统里直接看。

答案要点：

1. 上传走 OSS 直传
   - 前端向后端要上传凭证(STS 临时密钥 / 签名),前端直传 OSS
   - 不经过业务服务器,大文件不占带宽

2. 预览
   - PDF:iframe 嵌 OSS 预览地址,或 pdf.js 渲染(需处理 worker/crossOrigin)
   - Word/Excel:后端转 PDF 后预览(调用 LibreOffice / 第三方服务)
   - 图片:直接 <img> + 缩放
   - 安全:OSS 桶私有,用后端签名 URL,设置短有效期

3. 版本管理
   - 附件表存: id, bizId, version, url, size, uploader, createdAt
   - 新上传 version + 1,旧版本保留
   - 前端展示版本下拉,默认最新

4. 大文件
   - 分片上传 + 断点续传 + 秒传(hash 校验)
   - 前端算 hash 放 Web Worker,别卡主线程
   - 进度条、暂停/继续、失败重试(指数退避)

追问：

  • 预览 PDF 时怎么防止用户下载/截屏？→ 前端做不到完全防，只能加水印 + 短时效签名 URL；真正要防得靠权限和水印
  • 文件名带中文/特殊字符 → 用 id 存库，前端用 content-disposition 的 filename 显示

74. 多租户切换：要清什么 ​

场景：SaaS 后台，切换租户后，页面上的数据还是上一个租户的。

答案要点：

1. 切换租户 = 一次"软重置",要清理的东西列全
   - 查询缓存:queryClient.clear()   ← 最容易漏
   - 全局 store:Zustand/Redux 里跟租户相关的 slice
   - localStorage/sessionStorage:token、用户信息、偏好
   - 运行时配置:字典、菜单、权限点、主题
   - 长连接:WebSocket 断开重连(带新的 tenantId)
   - 正在进行的请求:AbortController 全部取消
   - 定时器:轮询、埋点队列

2. 顺序很重要
   取消请求 → 清缓存 → 清存储 → 重新登录/换 token → 重连 WS → 拉新租户配置 → 跳转首页

3. 更稳的做法:租户切换直接整页跳转
   window.location.href = '/switch-tenant'
   服务端换 token 后 302 到新租户首页
   理由:彻底避免内存残留,实现成本极低,后台系统可接受

4. token 里带 tenantId
   - 后端从 token 解析,前端不传 tenantId 参数(防止越权)
   - 越权风险:前端传 tenantId=别人的 → 后端必须以 token 为准

追问：

  • 切换租户要保留的东西（比如个人偏好）→ 单独存一份 global key,不跟租户 key 混
  • 为什么不用 localStorage 隔离 key？→ 可以做但容易漏 key；clear() 更可靠

75. AI 提效：给 ERP 加 AI 能力 ​

场景：ERP 里想让 AI 帮销售填写客户资料 —— 根据客户名称/公司自动补全工商信息、生成跟进话术；或者在客户详情里做一个"问这家公司"的对话框。

答案要点：

1. 前端视角的三个落点
   a) 表单智能填充
      - 失焦时触发,后端调 LLM + 工商信息 API,前端回填
      - 要有 loading 与"AI 生成"标识,让用户知道哪些是机器填的
   b) 内嵌智能问答
      - SSE 流式输出(参考 /前端/ai-integration/1-streaming)
      - 上下文拼装:当前客户 JSON + 历史跟进记录
   c) 数据洞察
      - 列表页"这批客户有什么共性" → 自然语言查询
      - 前端把筛选条件翻译成 API 参数(结构化输出)

2. 关键工程点
   - 流式:fetch + ReadableStream 或 EventSource,别等全部返回
   - 中断:AbortController,用户切页面时取消
   - 兜底:超时/失败要降级成普通表单,不能卡住主流程
   - 成本:同一问题缓存(RAG),别每次都全量塞上下文

3. 合规(ERP/CRM 尤其重要)
   - 客户数据是敏感数据,出境/外发要走审批
   - 提示词里带 PII 要脱敏
   - AI 输出要标注来源,不能直接当业务数据写库,需要人工确认

追问：

  • AI 结果不准怎么办？→ 全部走"建议 + 人工确认"，不直接落库
  • 怎么评估效果？→ 建一个标注集,离线跑准确率;线上看采纳率(用户是否保留 AI 填的值)

面试答题提示 ​

这组题的通用回答框架(4 步):
1. 先说清业务约束(数据量多少、谁在用、能不能容忍不一致)
2. 再说技术方案(前端做什么 / 后端做什么 / 边界在哪)
3. 主动说坑和取舍(为什么不用另一种方案)
4. 最后说监控与兜底(怎么发现出问题、怎么降级)

面试官最想听的是第 3、4 步。
