前端面试复盘:7 个问题的原理层答案 ​

2026-10 的一次面试。面试官围绕我近两年的两个项目(React SaaS 后台、Web/H5 会员平台) 连续追问。本文记录每个问题我当时的回答、问题出在哪,以及可以直接讲出来的原理层答案。

一、这次面试暴露的真问题 ​

不是不会用,是答在了现象层。

我每个问题的回答模式都一样:

"我们用 XX 方案 / XX 插件 / XX 策略,解决了 YY 问题。"

面试官想问的是为什么是这样、底层怎么实现、踩过什么坑, 而我给的是我用了什么。这两者之间隔着一层,也就是"原理层"。

而且有 3 个问题我答错了(不是不完整,是错的):

问题我当时的回答事实
HTTP/1 vs HTTP/2"HTTP/1 只能传输文本,HTTP/2 什么都能传"完全错。HTTP/1.1 一样能传图片和二进制,问题不在「传什么」,在「怎么传」
移动端适配原理"不知道"原理只有一行:1rem = 视口宽 / 10
PWA 缓存策略"网络优先、缓存优先"只答了名字,没答行为、适用场景、更新机制

二、答题框架(比知识更重要) ​

同一个知识点,答"用了什么"和答"原理 + 踩坑",分数差一个档。

1. 结论先行(10 秒)      —— 一句话给结论,别绕
2. 原理(30 秒)          —— 底层怎么实现的 / 为什么需要这个机制
3. 我的项目(30 秒)      —— 怎么用的 + 踩了什么坑 + 怎么定位的
4. 对比与边界(20 秒)    —— 和替代方案比差在哪、什么场景不适用

"面试官问底层有什么增加时,是在给我机会展示深度",应该主动展开而不是一问一答。

举例——面试官问「移动端怎么适配的」:

  • ❌ "用 postcss 插件把 px 转成 rem"
  • ✅ "rem 方案,原理是运行时把根字号设成视口宽度的 1/10, 设计稿按 750 出图,px 除以 75 就是 rem 值,postcss-pxtorem 自动转。 它的代价是有三个:需要 JS 改根字号所以首屏会闪; 用户调大系统字号不跟随(无障碍问题); 第三方库是 px 必须 exclude 排除。 我在项目里遇到的具体问题是 iOS 键盘弹出时 100vh 不变导致内容被挡, 后来换成 100dvh;还有刘海和小黑条要配 env(safe-area-inset-bottom)。"

第二种答法,面试官会接着往下问,而那正是你想聊的。

三、逐题复盘 ​

Q1 Vue2 Router 的路由模式:hash 还是 history,哪些要 nginx 配合,怎么改 ​

我当时:说了 hash 和 history 两种,history 需要服务端配合,但具体怎么改没讲清。

失分点:只说了「要配合」,没说为什么要配合,以及改哪一条配置。

原理层答案:

两种模式的区别在于路由信息放在哪里:

hash 模式history 模式
URL 形态/#/user/123/user/123
路由信息来源location.hashlocation.pathname
改 URL 会发请求吗不会(fragment 不发给服务器)会
刷新页面服务器收到的是 /,正常服务器收到 /user/123,没有这个文件 → 404
默认静态服务器能用吗能不能

为什么 history 必须服务端配合:hash 模式下 fragment(# 后面的部分)浏览器不会发给服务器, 所以服务器永远只收到 /,返回 index.html 即可,Vue Router 再读 location.hash 渲染组件。

history 模式是真实路径,用户直接访问 /user/123 或刷新时,浏览器会向服务器请求这个 URL, 服务器上根本没有对应的静态文件,于是 404。所以需要「所有找不到文件的请求都回 index.html」这个兜底规则, 让前端路由接管渲染。

nginx 怎么改:

nginx
server {
  root /usr/share/nginx/html;
  index index.html;

  # 静态资源单独处理,避免每次都走 try_files 的文件系统匹配
  location ~* \.(js|css|png|jpg|jpeg|gif|svg|woff2?)$ {
    expires 30d;
    add_header Cache-Control "public, immutable";
  }

  # 关键这一条:history 模式的兜底
  location / {
    try_files $uri $uri/ /index.html;
  }

  # 后端接口前缀,别和前端路由冲突
  location /api/ {
    proxy_pass http://backend;
  }
}

三个容易漏的细节(加分点):

  1. try_files 的顺序很重要,静态资源应该用更精确的 location 先匹配, 否则每个 .js 请求都要先走一遍文件系统匹配再 fallback
  2. 不只是 nginx:Node 服务要开 historyApiFallback(create-react-app / Vite preview 默认开), CDN 也要配回源规则,否则 CDN 会把 /user/123 直接 404 掉,根本到不了源站
  3. 后端接口路径要和前端路由前缀隔离(/api/),否则前端路由 /user/123 会打到后端

我项目里的说法:

"SaaS 后台用的是 Next.js App Router,本身就是 history 模式; H5 那边是纯静态托管 + hash 路由,因为要嵌在 App WebView 里, 运营配置页面的链接还要能被外部直接打开分享。 部署时 nginx 加了 try_files $uri $uri/ /index.html,静态资源单独一个 location 走长缓存。"

Q2 移动端适配怎么做的,原理是什么,遇到什么问题怎么解决 ​

我当时:postcss 插件 px 转 rem;原理不知道;问题答的是「不同分辨率顶部底部内容区不一样,要做兼容」。

失分点:

  • "原理不知道"是最大的失分 —— 这题原理只有一行,背下来就能答
  • "顶部底部不一样"这个描述太模糊,面试官无法判断你真的处理过

原理层答案(核心公式):

设计稿按 750px 宽出图,运行时用 JS 设置根字号:

js
document.documentElement.style.fontSize = Math.min(clientWidth, 750) / 10 + 'px'

于是 1rem = 视口宽 / 10,而 750 设计稿上的 100px 正好等于 1rem(375 屏上 1rem=37.5px)。

换算公式:

rem 值 = 设计稿 px 值 / 75        (设计稿 750 宽)

工程上用 postcss-pxtorem(rootValue: 75)自动转, 必须 exclude: /node_modules/i,因为 Ant Design 4 用 px,一起转会错乱。

vw 方案(postcss-px-to-viewport)的原理更直接:

100vw = 视口宽,  750 设计稿 px = 100vw,  32px = 4.2667vw

纯 CSS 无 JS、无首屏闪烁,但 PC 端要 clamp() 限上限。

我实际遇到的坑(要能说出具体现象和定位方式):

现象原因解法
iOS 键盘弹出,输入框被挡住100vh 是最大视口高度,键盘弹出时不变换 100dvh(动态视口高度),或用 visualViewport 监听 resize 写入 CSS 变量
iPhone 底部小黑条压住按钮没配 viewport-fit=cover<meta viewport ... viewport-fit=cover> + padding-bottom: env(safe-area-inset-bottom)
顶部刘海区域被遮同上env(safe-area-inset-top)
1px 边框在 3x 屏上变 3px 粗rem 转换把 1px 也转了postcss minPixelValue: 2 让 1px 不转,或用 transform: scaleY(0.5) 的伪元素
PC 大屏上布局被撑爆vw/rem 没有上限font-size: clamp(320px, 4.2667vw, 750px)
图片被缩放变糊位图跟着 rem 缩放图片不用 rem 控制宽高,用 srcset 让浏览器选 2x/3x 图

「顶部底部内容区不一样」的准确说法:

"H5 要嵌在 App WebView 里,原生导航栏会遮挡顶部。 我们用 env(safe-area-inset-top) 让内容避开原生栏, 底部用 env(safe-area-inset-bottom) 避开 Home Indicator, 中间的内容区用 flex 布局而不是固定高度,这样键盘弹起时是内容区自己滚动, 不会把整个页面顶走。"

详细的原理和坑清单见 移动端适配:rem / vw 方案原理与坑。

Q3 Vue 数组底层有什么增加吗 ​

我当时:含糊,没答出 Vue 2 和 Vue 3 的差别。

原理层答案:

Vue 2 —— 数组方法劫持:

defineProperty 只能劫持已存在的属性,arr[0] = x 不会触发 setter(因为下标不是已定义属性), arr.length = 0 同理。所以 Vue 2 换了个思路:不改数据,改数组原型上的变更方法。

js
const arrayProto = Array.prototype
const originalPush = arrayProto.push

// 拦截 7 个变更方法
;['push', 'pop', 'shift', 'unshift', 'splice', 'sort', 'reverse'].forEach(method => {
  const original = arrayProto[method]
  Object.defineProperty(arrayProto, method, {
    value(...args) {
      const result = original.apply(this, args)
      const ob = this.__ob__          // 找到 Observer
      let inserted
      switch (method) {
        case 'push':
        case 'unshift':
          inserted = args
          break
        case 'splice':
          inserted = args.slice(2)
          break
      }
      if (inserted) ob.observeArray(inserted)   // 新增元素也要变成响应式
      ob.dep.notify()                           // 通知依赖更新
      return result
    },
    enumerable: false, writable: true, configurable: true
  })
})

底层数据结构:每个被观察的数组上挂一个 Observer 实例(__ob__ 属性), 里面存 dep(依赖收集器)和 value。 数组整体的依赖收集在 ob.dep 上,所以改任何一项都会触发整个数组的重新渲染(粒度粗)。

Vue 2 的坑:arr[0] = x 不触发更新,必须 Vue.set(this.list, 0, x) / this.$set。 Vue.set 内部对数组就是 splice 一下,借道被劫持的 splice 触发 notify。

Vue 3 —— Proxy 统一拦截:

js
const arr = reactive([1, 2, 3])
arr[0] = 9        // ✅ 触发
arr.length = 0    // ✅ 触发
arr.push(4)       // ✅ 触发

Proxy 的 set 陷阱能拦截任意 key(包括索引和 length),所以不再需要重写数组方法。

Vue 3 的两个关键改进:

  1. 依赖收集更精确:Vue 3 用 targetMap(WeakMap → Map)按 key 收集依赖, 改 arr[0] 只通知索引 0 的依赖,不会像 Vue 2 那样整个数组重新渲染
  2. 但 Vue 3 仍然重写了数组方法(arrayInstrumentations):因为 Proxy 的 set 陷阱 只能告诉你「key 被设成了什么」,**拿不到「新增了哪几个元素」**这类信息, Vue 3 包装了 push/pop/splice 等方法,内部调用 toRaw 拿到原始数组操作后, 再手动 trigger 相关的依赖

加分点:Vue 3 的 reactive 是懒代理——第一次访问才创建 Proxy, ref 通过 toReactive 把对象转成 reactive,shallowRef/shallowReactive 跳过深层代理。

Q4 keep-alive 的 activated / deactivated 什么区别,底层怎么实现 ​

我当时:只说了生命周期钩子的区别,底层实现含糊。

原理层答案:

生命周期区别:

钩子触发时机次数实例
mounted / unmounted首次挂载 / 真正销毁1 次创建 / 销毁
activated / deactivated插入 DOM / 从 DOM 移除多次保留

被 KeepAlive 缓存的组件,切走时 unmounted 不会触发,所以只写 onMounted/onUnmounted 的定时器、轮询、视频播放不会停 —— 必须用 onDeactivated 停、 onActivated 恢复。

Vue 3 底层实现:

<KeepAlive> 是抽象组件,它的 render 返回的是被缓存组件的 vnode。三个核心结构:

ts
const cache = new Map<string, VNode>()   // key -> vnode
const keys = new Set<string>()            // 插入有序,用于 LRU
const storageContainer = createElement('div')  // 隐藏的 DOM 容器

流程:

  1. 挂载时:cache.set(key, vnode)、keys.add(key)
  2. 再次渲染时:先查 cache,命中就复用同一个 vnode 实例,触发 update 而不是 mount
  3. 卸载时:不是销毁,而是 patch(vnode, null) 把 DOM 移到 storageContainer, 组件实例和 setup 里的状态全部存活
  4. 命中时:把 DOM 从 storageContainer 搬回页面,触发 activate
  5. 超出 max:按 keys 的顺序淘汰最久未访问的

一句话:KeepAlive 把被缓存组件的 DOM 搬到一个隐藏容器里,下次再搬回来。

Vue 2 的实现差异:缓存在 this.cache / this.keys 两个数组里,并且缓存在 组件实例 上(vnode.componentInstance),命中时通过 activateChildComponent 里的 instance._isMounted 标记判断是否已挂载。

细节加分点:

  • include / exclude 按组件 name 匹配,不是路由名
  • 缓存的是组件实例,所以不同路由用同一个组件时状态会串 → 路由场景必须 <component :is="Component" :key="route.path" />
  • <Transition> 必须在 <KeepAlive> 外层

完整拆解见 KeepAlive 底层实现。

Q5 React 项目最大特点是什么,国际化组件怎么设计、怎么实现 ​

我当时:答了「大量组件封装」+「活动新增表单很多组件嵌套」; 国际化答了「动态的用中英文输入框存到国际化 json 对象存数据库,静态的存国际化 json」。

失分点:

  • 组件封装只答了「封装了什么」,没答为什么这么封装、边界在哪
  • 国际化只答了存哪,没答组件怎么设计(这是面试官真正想问的)

组件封装的答法(讲边界,不讲数量):

"我封装的是稳定的基础能力,不是万能页面组件。 表格、搜索表单、弹窗/抽屉表单、权限按钮、金额输入、多语言字段这几类是高频且稳定的, 我把它们抽成配置驱动的组件,页面只传数据源、字段配置和业务回调。 但审核流程、风险规则这种业务差异大的,我保留成独立组件—— 因为强行统一会让配置复杂度超过业务代码本身。"

国际化的组件设计(这是关键,分静态和动态):

tsx
// 1) 静态文案:语言包 + key
const t = useTranslation()
<Button>{t('common.actions.submit')}</Button>

// 2) 枚举值:后端返回 code,前端映射,不能把中文当 key
<Select options={ORDER_STATUS.map(s => ({ label: t(`order.status.${s.code}`), value: s.code }))} />

// 3) 组件内部有文案怎么办:封装国际化组件,不要在业务组件里散落 key
<I18nText id="activity.rules.title" />          // 纯文案
<I18nSelect id="activity.type" options={...} />  // 带枚举的
<I18nTable columns={columns} data={data} />     // 列头可翻译的表格

// 4) 动态内容(运营配置的文案):存数据库的多语言字段,不是语言包
type MultiLangText = Record<Locale, string>   // { zh-CN: '...', en-US: '...' }
// 数据库存 JSON,前端按当前 locale 取

国际化的实现层:

  • 提取:编译期用 vite-plugin-i18next 之类扫描 key,缺失在 CI 报错 (不能靠人肉 review,key 拼错是运行期才发现)
  • 加载:语言包懒加载 import(\./locales/${locale}.json`)`
  • 检测与切换:navigator.language → 项目兜底语言 → 用户手动选择(存 localStorage) → 同步 document.documentElement.lang
  • 响应式切换:
    • vue-i18n 的 locale 是 ref,切语言自动触发重渲染
    • React 里要保证 provider 的 locale 是 state,或用 useIntl 订阅
  • 格式化:日期/数字/货币必须用 Intl,不能手写 format
    js
    new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(1234.5)
new Intl.DateTimeFormat(locale).format(date)
    不同 locale 的小数点分隔符、货币符号位置、时区都不一样,手写一定错
  • 富文本:翻译后的富文本要再过一遍 DOMPurify(翻译内容同样是不可信输入)

Q6 资源变动发版如何知道,缓存用什么策略,PWA 怎么用缓存策略,没有 PWA 有什么区别 ​

我当时:只答了「网络优先、缓存优先」,发版那部分答得很少。

失分点:这是最能体现工程深度的一题(PWA 正是他项目里做的),却答得最空。

发版如何知道资源变了:

靠 content hash 指纹,不是靠手动维护版本号:

app.a1b2c3d4.js     ← 内容变了 hash 就变,文件名就变

webpack/vite 默认对 [name].[contenthash].js 做指纹。内容一变 → 文件名变 → 浏览器和 CDN 自然认为是新资源,不需要通知前端"我发版了"。

配套的缓存头(这两条必须成对):

nginx
# 带 hash 的静态资源:永久缓存
location ~* \.(js|css|png|jpg|svg|woff2)$ {
  expires 1y;
  add_header Cache-Control "public, max-age=31536000, immutable";
}

# HTML 入口:不缓存,保证发版后能拿到新的资源清单
location = /index.html {
  add_header Cache-Control "no-cache";
}

没有指纹会怎样:文件名不变 → 强缓存没过期 → 用户拿到旧版本。 这就是「发版了但用户还是旧的」的根因。

HTTP 缓存的两层:

强缓存协商缓存
请求不发发,带 If-None-Match / If-Modified-Since
命中直接用本地副本服务端返回 304,不传 body
控制Cache-Control: max-ageETag / Last-Modified

PWA 的缓存策略(Workbox):

策略行为适用
CacheFirst缓存优先,miss 才走网络静态资源、字体、JS/CSS 包
NetworkFirst网络优先,失败回退缓存接口请求、时效性数据
StaleWhileRevalidate先给缓存,同时后台更新中间态数据(用户能接受短暂旧数据)
NetworkOnly只走网络,永不缓存支付、隐私数据
CacheOnly只读缓存离线兜底页

两种缓存时机:

  • 预缓存(Precache):构建时生成 app shell 清单,SW install 事件里全部下载 → 离线可用
  • 运行时缓存(RuntimeCaching):首次请求该资源时才缓存

版本更新机制(这块讲清楚很加分):

1. 构建产物变了 → sw.js 内容变了
2. 浏览器发现新 SW → 触发 install(新 SW 进入 waiting)
3. 所有旧页面关闭后,新 SW 触发 activate
4. activate 事件里清理旧版本的 Cache
5. 新 SW 接管页面

skipWaiting() / clients.claim() 可以让新 SW 立即接管,但有风险: 新旧版本的 HTML 和资源可能不匹配(HTML 是新的、JS 还是旧的)。所以生产上一般是 「提示用户有新版本,点击刷新」而不是静默接管。

没有 PWA 的区别:

纯 HTTP 缓存PWA
控制粒度URL 级,浏览器自动请求级,可以自定义哪些资源缓存、多久、怎么更新
离线不行可以(预缓存 app shell)
缓存位置浏览器 HTTP 缓存Cache Storage(独立于 HTTP 缓存)
更新粒度按 URL 过期时间SW 版本,activate 时整体换代
能缓存接口响应吗能,但和静态资源混在一起能,按策略分别控制

关键:SW 缓存和 CDN/HTTP 缓存是两套完全独立的缓存。 SW 没更新,用户就一直拿 SW 里的旧资源,哪怕 CDN 已经是新的了。

我项目里的说法:

"会员平台 H5 做了 PWA,用的是 Workbox。 app shell(html/关键 CSS/图标)在构建时预缓存,保证弱网和离线能打开; 业务接口走 NetworkFirst,拿不到网络就回退到上次成功的缓存,配合页面上的「当前数据可能不是最新」提示。 静态资源走 CacheFirst,配合 contenthash 文件名做永久缓存。 更新上,sw.js 内容变了浏览器会拉新的,但不静默接管,而是在页面上弹「有新版本」让用户点刷新, 避免新旧资源混用。"

Q7 HTTP/1 和 HTTP/2 有什么区别 ​

我当时:"HTTP/1 应该是只能传输文本,HTTP/2 是很多资源图片、文件都能传输。"

这是我答错的一题。 HTTP/1.1 一样能传图片和二进制(JSON、文件、任何 Content-Type)。 问题不在「能传什么」,在「怎么传」。

原理层答案:

HTTP/1.1 的三个核心问题:

  1. 队头阻塞(TCP 层):一个 TCP 连接上,HTTP/1.1 只能有一个请求在途。 前一个响应没回来,后面的请求只能在浏览器里排队(浏览器对同域名最多开 6 个连接)
  2. 重复头部:每个请求都要带完整的 Cookie、User-Agent、Accept、Referer。 一个几百字节的头部在每个请求里重复一遍,带宽被浪费
  3. HTTP 层队头阻塞:TCP 是字节流,分段传输。某一段丢了,后面所有的字节都要等重传

HTTP/2 的四个改进:

  1. 二进制分帧:不再用 `

分隔的文本报文。一个 TCP 包里有多个 frame, 每个 frame 有 9 字节头:length(3) + type(1) + flags(1) + streamId(4)`

+-----------------------------------------------+
|                 Length (24 bit)                 |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |          ...  |
+---------------+---------------+---------------+
|                   Stream Identifier (31)        |
+-----------------------------------------------+
  1. 多路复用:一个连接上开多个 stream 并行传输,HTTP 层的队头阻塞消失了
  2. 头部压缩(HPACK):静态表(61 个常用头)+ 动态表(增量编码)。 第二次请求的 Cookie/User-Agent 只发索引或差量,几十字节就够
  3. 流优先级 / 服务器推送:可以给某些 stream 更高权重(服务器推送已被 Chrome 弃用)

HTTP/2 仍然存在的问题(这是加分点):

TCP 层的队头阻塞还在。HTTP/2 只解决了 HTTP 层的, 一个 TCP 段丢了,所有 stream 都要等这个段重传。

HTTP/3 就是来解决这个的:把传输层从 TCP 换成 QUIC(基于 UDP), 每条 stream 独立重传,互不影响。附带两个好处: 连接迁移(换网络不用重连,靠 Connection ID)和 0-RTT(会话恢复时首包就能带数据)。

另一个容易漏的点:HTTP/2 是通过 TLS ALPN 协商出来的,不是运行时 Upgrade。 ALPN: h2, http/1.1 → 服务端回 ALPN: h2 → 之后这条连接全走 HTTP/2。

我项目里的说法:

"我们的 CDN 和 Nginx 都开了 HTTP/2,首屏有 20 多个请求。 HTTP/1.1 下这些请求要在 6 个连接上排队,HTTP/2 单连接多路复用就没有排队了, 首屏的 TTFB 和整体完成时间都有明显改善。 但要注意 HTTP/2 只解决了 HTTP 层的队头阻塞,TCP 丢包还是会卡住所有流, 这也是为什么现在 HTTP/3 在往 QUIC 上走。"
