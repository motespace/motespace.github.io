openid vs unionid vs session_key

Section titled “openid vs unionid vs session_key”
字段 作用 是否唯一
openid 用户在当前小程序的唯一标识 同一用户在不同小程序 openid 不同
unionid 用户在同一微信开放平台下多应用的统一标识 唯一（要绑定开放平台）
session_key 微信给后端的“会话密钥”，用于解密加密数据 一次会话

code 的特性

Section titled “code 的特性”
  • 5 分钟有效，只能用一次
  • 每次 wx.login 都会拿到新的 code
  • 不能用 code 直接当登录凭证，必须后端换 openid

六、面试追问

Section titled “六、面试追问”

Q：wx.login 拿到的 code 能直接当登录凭证吗？

A：不能。code 是一次性的临时凭证（5 分钟有效），必须发给后端，后端用 appid + appSecret 换 openid 和 session_key。

Q：appSecret 可以放在小程序端吗？

A：绝对不能！appSecret 是服务端凭证，放在前端会被反编译盗取。必须放在后端。

Q：openid 和 unionid 怎么选？

A：

  • 只需要在小程序内识别用户 → openid
  • 多个应用统一识别（如公众号 + 小程序 + App）→ unionid（要绑定微信开放平台）

Q：登录态过期怎么自动续期？

A：

  1. 前端：每次请求失败 401 时，重新 wx.login + 后端换 token
  2. 后端：用 refresh_token 机制（访问令牌 + 刷新令牌双 token）
  3. 静默续期：在 wx.request 拦截器里，遇到 401 自动续期后重发原请求

📝 小结

Section titled “📝 小结”
  • 流程:wx.login() 拿到临时 code → 发给后端 → 后端用 code 调微信 code2Session 换取 openid/session_key/unionid → 后端签发自己的 token → 前端存储并带上。
  • 关键点:前端不能直接调 code2Session(需要 appSecret),登录态由后端维护。
  • session_key 只用于解密用户敏感数据与校验,不能下发给前端;后端要维护 session 有效期。
  • 前端 token 存 wx.setStorageSync,请求拦截器统一带上;401 时用单例 Promise 锁避免并发重复登录。
  • 获取用户信息:getUserProfile(需用户点击触发)与 getPhoneNumber(需 button open-type),新版本已改为加密数据后端解密。
  • 面试加分:讲清「为什么 code 只能用一次且 5 分钟过期」与「session_key 泄露的风险」。
