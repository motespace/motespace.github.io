CDN 的缓存策略有哪些?

Section titled “CDN 的缓存策略有哪些?”

答案：

策略 说明 适用
缓存整个响应 默认行为,按 Cache-Control 静态资源
忽略 URL 中的某些部分 ignoreUrlParameters: ['utm_source', ...] 避免带追踪参数的 URL 缓存成两份
按规则改写 URL rewrites 把 /api/x 映射到 /api/v2/x
不缓存 bypass 特定路径
边缘函数改写响应 edgeModify 在边缘改 Cache-Control 或响应体

关键:CDN 的缓存键默认包含完整 URL,所以 ?utm_source=xxx 会生成多个副本。要么配置忽略参数,要么在构建时把追踪参数在前端路由层去掉。

HTTP/2 多路复用对前端有什么影响?

Section titled “HTTP/2 多路复用对前端有什么影响?”

答案：直接解决了 HTTP/1.1 的队头阻塞。

HTTP/1.1 HTTP/2
并发方式 6 个 TCP 连接,每连接只能一个在途请求 单连接,多个流并行
队头阻塞 有(一个请求慢,后面的要排队) HTTP 层没有
头部压缩 每次请求带完整 header HPACK,增量编码
优先级 无 支持流优先级

前端影响:

  1. 可以发更多并行请求,不用再靠 domain 分片绕开连接数限制
  2. 请求头更小,首包更快(尤其移动端)
  3. 但 TCP 层仍有队头阻塞 —— 丢一个 TCP 包,所有流都要等重传。这就是 HTTP/3(基于 QUIC)要解决的问题

注意:HTTP/2 服务端推送被 Chrome 弃用了,现在都用 <link rel="preload"> 显式声明。

📝 小结

Section titled “📝 小结”
  • Q11 强缓存 vs 协商缓存:强缓存不发请求直接用本地副本(Cache-Control: max-age / no-cache / no-store / private / s-maxage),协商缓存发请求但返回 304(ETag/If-None-Match 优先,其次 Last-Modified/If-Modified-Since)。
  • no-cache 不是不缓存,而是「缓存但必须校验」;no-store 才是完全不缓存。
  • Q12 前端资源缓存最佳实践:带 hash 的文件名 + 长 max-age + immutable;HTML 不做强缓存(或短缓存 + ETag);API 与静态资源策略分离;CDN 配合版本化路径;Service Worker 做离线与精细控制。
  • 面试加分:能说清「为什么 no-cache 和 no-store 经常被搞混」,以及 ETag 优于 Last-Modified 的原因(秒级精度问题)。
