3.1 为什么用 Map + Set？

Section titled “3.1 为什么用 Map + Set？”
数据结构 优点
Map（key = eventName） O(1) 查找 + 保留插入顺序
Set（value = handlers） 自动去重 + O(1) 添加 / 删除

对比 Object + 普通数组：

  • ❌ 普通对象 key 是字符串（限制）
  • ❌ 数组删除中间项 O(n)

Section titled “3.2 emit 时为什么拷贝 Set？”

原因：如果 handler 内部触发 on / off，会修改原 Set，迭代器会出错。

七、面试追问

Q1: on + emit 的发布订阅模式怎么实现？

Section titled “Q1: on + emit 的发布订阅模式怎么实现？”

答：

  1. on 注册 handler 到 Map（key = eventName）
  2. emit 遍历 Map 调用 handler
  3. off 从 Map 删除 handler

Q2: emit 时如果新增 handler 会被加吗？

Section titled “Q2: emit 时如果新增 handler 会被加吗？”

答：取决于实现。要安全的话 emit 时应该 拷贝一份 handler 集合再迭代。

Q3: once 怎么实现？

Section titled “Q3: once 怎么实现？”

答：包一层 wrapper handler，执行时先 off，再调用原 handler。

Q4: 怎么防止内存泄漏？

Section titled “Q4: 怎么防止内存泄漏？”

答：

  1. 组件 unmount 时手动 off
  2. 用 WeakMap / WeakSet（handler 是 weak reference）
  3. 长生命周期对象（observer）记得清空引用

Q5: EventEmitter 有什么问题？

Section titled “Q5: EventEmitter 有什么问题？”

答：

  • 没有类型安全（事件名 + payload）
  • 监听多时性能差（emit 需要遍历）
  • 跨 Tab 失效（要用 BroadcastChannel）

📝 小结

Section titled “📝 小结”
  • 核心 API:on/off/once/emit,内部用对象存事件名 → 回调数组。
  • 关键设计:emit 时复制回调数组再遍历(防止回调中 off 导致遍历错乱);once 用包装函数执行后自动 off。
  • 内存泄漏风险:不 off 的监听器会一直持有引用;Node 的 EventEmitter 对同一事件超过 10 个监听器会告警(setMaxListeners)。
  • 轻量替代:mitt 只有约 200 行,支持 * 通配监听与 all。
  • 面试话术:讲清「为什么 emit 要复制数组」和「事件总线的生命周期管理」。
