TypeScript 进阶面试题（Q11-Q25）

配合 Q1-Q10 使用。Q1-Q10 覆盖基础概念，本篇覆盖 React 中的类型实战 与 类型体操——这两块才是“熟练掌握 TypeScript”的分水岭。

Q11: 如何给一个 React 组件写泛型？

Section titled “Q11: 如何给一个 React 组件写泛型？”

答：泛型参数放在函数组件的尖括号里，箭头函数需要额外加 <T,>（否则被当成 JSX）。

追问：在 .tsx 里 &lt;T&gt; 会被当成 JSX 标签解析，所以要么用 function 声明，要么写成 <T,>。

Q12: 怎么给自定义 Hook 写类型？

Section titled “Q12: 怎么给自定义 Hook 写类型？”

关键点：调用点推导比在 Hook 内部写死类型更灵活——useUser 返回的 data 自动是 User | undefined，调用方不用再断言。

Q14: satisfies 解决什么问题？

Section titled “Q14: satisfies 解决什么问题？”

答：在保留字面量类型的同时校验结构。这是 TS 4.9 引入的关键字。

典型场景：路由表 / 权限点常量。

一句话记忆：as 是“我不管，你说是就是”；satisfies 是“我帮你检查，但保留原有精度”。

Q15: 模板字面量类型能做什么？

Section titled “Q15: 模板字面量类型能做什么？”

答：做字符串层面的类型运算。

实战：路由参数的类型安全

Q16: 什么是协变和逆变？（函数类型的参数/返回值）

Section titled “Q16: 什么是协变和逆变？（函数类型的参数/返回值）”

答：

strictFunctionTypes 开启后，函数类型的参数才严格逆变（默认只对方法语法宽松）。

实际影响：React 组件的 props 是逆变位置 —— 组件能被赋给“props 更宽松”的位置。

Q17: 联合类型怎么穷尽检查(exhaustiveness)？

Section titled “Q17: 联合类型怎么穷尽检查(exhaustiveness)？”

答：用 never 兜底，漏了分支就编译报错。

React 组件里同样适用——用一个 Record<Status, JSX.Element> 映射表比一堆 if/else 更安全，改状态时 TS 会强制你补齐。

Q18: 索引签名和 Record 的区别？

Section titled “Q18: 索引签名和 Record 的区别？”

追问：Record<string, number> 和 { [key: string]: number } 几乎等价，区别在于 Record 写起来更短，且 Record<K, V> 可以直接用 as const 配合。

实战：动态字典的 key 要收窄

Q19: interface vs type 的选择？

Section titled “Q19: interface vs type 的选择？”

答（实际工程视角）：

场景 选择 原因
对象类型、想被继承/扩展 interface 声明合并、错误信息更友好、跳转到定义体验好
联合类型、交叉类型、映射类型 type interface 表达不了
函数类型 type 更简洁
泛型约束 都可以 看上下文一致性
组件 Props interface 可被 extends 扩展、可声明合并扩展

追问：interface 的声明合并在什么场景是坑？→ 两个同名 interface 会自动合并，可能不是你想要的。用 type 或不同名字避免。

Q21: 类型断言什么时候是安全的？

Section titled “Q21: 类型断言什么时候是安全的？”

答：只在你比编译器更清楚类型时使用（通常是从后端拿到的数据、或 DOM 查询）。

更好的做法：用类型守卫代替断言。

面试话术：“as 是绕过检查，satisfies 是检查并保留精度，类型守卫是真正的运行时校验。接口返回的数据我不信任，一律先校验再使用。”

Q22: unknown 和 any 的实际区别？

Section titled “Q22: unknown 和 any 的实际区别？”

结论：外部输入（接口返回、JSON.parse、用户输入）一律用 unknown，然后收窄。any 只在实在无法收窄的地方用，并且要注释说明原因。

Q24: 枚举有什么坑？什么时候该用？

Section titled “Q24: 枚举有什么坑？什么时候该用？”

坑：

  • 数字枚举是双向映射：enum E { A } → E[0] === 'A'，序列化后是数字
  • 字符串枚举只单向，序列化友好
  • const enum 会被完全内联,不能被动态引用(isolatedModules 下报错)

什么时候用枚举：需要和后端约定数字码、或者需要运行时反射（Object.values(Enum)）。前端业务状态基本都该用 as const 对象。

Q25: TypeScript 编译产物是怎么产出的？

Section titled “Q25: TypeScript 编译产物是怎么产出的？”

关键点：

  • 类型完全擦除，运行时不存在任何类型信息
  • interface / type / as / 泛型：编译后全部消失
  • enum 是唯一会留下运行时代码的 TS 特性(因为要生成对象)
  • namespace 也会生成代码,declare 开头的不会
  • 需要运行时类型信息 → 用 zod 这类 schema 库,或手写类型守卫

面试追问：怎么在运行时知道一个值是不是 User？→ TS 不行,要么手写守卫,要么用 class 的 instanceof,要么用 zod/schema 校验。

附:类型体操速查

Section titled “附:类型体操速查”

⚠️ 类型体操要克制。类型复杂度超过收益就该停——用 any 或拆成简单类型，往往是更好的工程选择。面试里能讲清 infer 和条件类型就够了，不需要现场手写 20 层嵌套。

📝 小结

Section titled “📝 小结”
  • 进阶题的共同主题:类型系统的高级用法,包括泛型组件、条件类型、infer、模板字面量、协变逆变、穷尽检查、satisfies。
  • Q11~13 框架集成:泛型 React 组件(function Select&lt;T&gt;({ options }: { options: T[] }))、自定义 Hook 的类型(T 泛型 + 返回类型)、用 keyof 约束 props 只接受存在的属性。
  • Q14 satisfies:既保留字面量类型推断(不像 as 那样断言成宽类型)又能校验结构,适合配置对象与主题常量。
  • Q15 模板字面量类型:可做路径类型(\/users/${string}``)、事件名映射、字符串枚举替代方案。
  • Q16 协变逆变:函数参数逆变(参数类型要宽)、返回值协变(返回类型要窄),这是 strictFunctionTypes 的基础。
  • Q17 穷尽检查:用 never 兜底 + assertNever(x) 函数,新增联合成员时编译器会报错。
  • Q18 索引签名 vs Record:索引签名约束任意 key,Record<K, V> 是它的语法糖形式。
  • 面试加分:讲清「as 与 satisfies 的区别」和「为什么要理解逆变」。
