智能风控引擎平台 ​

项目概览 ​

时间：2023.08 - 2024.06 公司：华润网络深圳有限公司 角色：前端核心开发 技术栈：Vue 3、Vite、TypeScript、Element Plus、Pinia、ECharts 推荐程度：主讲项目，尤其适合 Vue 岗位

这是一个面向风控运营和策略人员的决策引擎后台，支持规则配置、指标管理、策略管理、数据中心看板和权限管理。项目最初是 Vue 2 + Webpack，后续由我主导迁移到 Vue 3 + Vite。

面试时可以这样概括：

这是一个让策略和运营人员通过页面配置规则、指标和策略的后台系统。业务难点是规则不是普通表单，而是可以递归嵌套的条件树；工程难点是老系统迁移过程中要保持登录、权限和核心业务连续可用。我先保证主链路可运行，再分模块迁移，最后做构建和依赖优化。

业务全貌 ​

这个项目不是单一 CRUD 系统，而是面向风控运营、策略人员和管理人员的决策引擎后台。平台目标是让业务人员可以配置指标、规则和策略，查看执行效果，而不是每次都依赖研发改代码。

可以按 5 个模块讲：

  1. 规则 / 模型：配置规则条件、操作符、字段和值，支持多层条件组合。
  2. 指标体系：原子指标、派生指标、数据源、数据表、字段、聚合方式、业务域分类。
  3. 策略管理：把规则、指标、处置动作组合成可执行策略。
  4. 数据中心 / 看板：展示策略趋势、指标趋势、风险模型效果。
  5. 系统权限：用户、角色、菜单、按钮权限、操作日志。

面试表达：

这个项目最能体现复杂业务拆解。规则引擎不是一个普通表单，它本质上是把业务人员想表达的判断逻辑，转换成前后端都能识别的数据结构。

我负责的内容 ​

  1. 负责规则引擎核心页面，支持条件组嵌套、组合逻辑、操作符、回显、校验和提交转换。
  2. 负责原子指标和派生指标配置，处理数据源、数据库、表、字段级联和聚合方式。
  3. 建设动态路由、按钮级权限和登录安全校验，配合完成渗透测试整改。
  4. 主导 Vue 2 到 Vue 3 + Vite 迁移，处理路由、权限、组件兼容、环境变量、资源加载和构建配置。
  5. 通过生产环境剔除 Mock、按需引入依赖和路由拆包，开发冷启动由 30s+ 降到 1s 级，构建产物减少 30%+。

技术实现 ​

1. 规则引擎条件树 ​

规则可以抽象为条件组和简单条件：

ts
type Operator = 'eq' | 'gt' | 'lt' | 'in' | 'empty'

type SimpleCondition = {
  kind: 'condition'
  id: string
  field: string
  operator: Operator
  value?: string | number | string[]
}

type ConditionGroup = {
  kind: 'group'
  id: string
  link: 'all' | 'any' | 'none'
  children: Array<SimpleCondition | ConditionGroup>
}

组件根据 kind 递归渲染：

  1. group 展示组合逻辑和子节点。
  2. condition 展示字段、操作符和值。
  3. 新增节点时生成稳定 id。
  4. 删除、移动和编辑只修改当前节点。
  5. 编辑时直接把后端树结构映射回相同的数据模型。
  6. 提交前统一校验，再转换成后端规则结构。

不同操作符对应不同控件：

  • 数值比较：数字输入。
  • 集合比较：多选输入。
  • 字段比较：字段选择器。
  • 空值判断：不展示值输入。
  • 日期比较：日期或时间范围控件。

1.1 规则编辑器难点 ​

  1. 递归渲染：复杂条件可以继续包含复杂条件，组件要能递归渲染。
  2. 数据回显：编辑已有规则时，要把后端保存的树结构完整还原到页面。
  3. 操作符联动：选择不同操作符后，右侧控件不同，比如输入框、列表、字段选择或无需输入。
  4. 字段类型联动：字段类型会影响可选操作符和输入值类型，比如字符串、数字、日期、列表。
  5. 提交转换：页面结构要转换成后端规则引擎可执行的结构，不能只满足 UI 展示。

1.2 操作符体系 ​

操作符不是固定展示全部，而是要结合字段类型和业务语义筛选：

  1. 字符串类：以某内容开始、包含、等于、不等于。
  2. 集合类：在列表中、不在列表中。
  3. 空值类：为空、不为空。
  4. 数值比较：大于、大于等于、小于、小于等于。
  5. 字段比较：等于某字段、大于某字段、小于某字段。

比如日期、数字、字符串能用的操作符不完全一样；选择"为空 / 不为空"时右侧不应该再出现输入框。

2. 规则校验和提交转换 ​

不要让每个输入框自己拼接口参数，而是统一在提交阶段处理：

ts
function validateGroup(group: ConditionGroup): string[] {
  const errors: string[] = []

  if (!group.children.length) {
    errors.push(`条件组 ${group.id} 不能为空`)
  }

  for (const child of group.children) {
    if (child.kind === 'group') {
      errors.push(...validateGroup(child))
      continue
    }

    if (!child.field) errors.push(`条件 ${child.id} 缺少字段`)
    if (!child.operator) errors.push(`条件 ${child.id} 缺少操作符`)

    const noValueOperator = child.operator === 'empty'
    if (!noValueOperator && child.value == null) {
      errors.push(`条件 ${child.id} 缺少比较值`)
    }
  }

  return errors
}

function toApiRule(group: ConditionGroup) {
  return {
    relation: group.link,
    conditions: group.children.map((child) =>
      child.kind === 'group'
        ? toApiRule(child)
        : {
            fieldCode: child.field,
            operatorCode: child.operator,
            compareValue: child.value,
          },
    ),
  }
}

3. 原子指标 / 派生指标 ​

原子指标 是最基础的数据口径，比如某个业务表里的某个字段，或者基于字段的基础统计。配置时需要选择数据源、数据库、表、字段、字段类型、业务域等信息。

派生指标 是在原子指标基础上做聚合或组合，比如 COUNT、SUM、AVG、MAX、MIN 这类统计，或者按时间窗口、业务条件生成新的指标口径。前端要处理好级联选择、依赖清理、参数校验和回显。

依赖链：

数据源 -> 数据库 -> 表 -> 字段 -> 字段类型 / 聚合方式

前置项变化时清理所有后置值：

ts
function handleDataSourceChange(sourceId: string) {
  form.setFieldsValue({
    sourceId,
    databaseId: undefined,
    tableName: undefined,
    fieldName: undefined,
    aggregation: undefined,
  })
}

难点：

  1. 数据源变了，数据库、表、字段要清空。
  2. 字段变了，字段类型和可选聚合方式要重新计算。
  3. 不同指标类型对应不同表单项和校验规则。
  4. 编辑回显时，要按层级依次加载选项，否则下级字段没法正确显示。

面试表达：

指标配置的难点是依赖链很长。用户看起来只是选几个下拉框，但前端要保证前置项变化后清理后置值，避免提交一个已经失效的字段组合。

4. Vue 2 到 Vue 3 + Vite 迁移 ​

迁移分阶段进行（不是简单"升级依赖"）：

  1. 构建层：Webpack 改 Vite，补 index.html 入口，配置 alias、dev server、代理和环境变量。
  2. 应用入口：new Vue 改 createApp，全局属性从 Vue.prototype 改到 app.config.globalProperties。
  3. 路由层：Vue Router 2 改 Router 4，addRoutes 改为逐条 addRoute，旧的 require 懒加载改 import()。
  4. Store 层：Vuex 3 升 Vuex 4，保留原有 modules 结构，先降低业务改动风险。
  5. UI 层：Element UI 迁到 Element Plus，重点验证表格、表单、弹窗、分页和日期组件。
  6. 兼容层：生命周期、事件总线、旧插件、静态资源路径、全局组件注册逐步处理。
  7. 优化层：生产环境剔除 Mock，ECharts 和 Element Plus 按需，路由拆包，减少主包体积。

核心原则：迁移目标是降低风险。先保证登录、权限、菜单、核心页面可用，再处理组件兼容和构建优化。这样不会因为迁移影响业务交付。

5. 构建优化 ​

真实测量结果：

  1. 开发冷启动：从 Webpack 的 30s+ 降到 Vite 的 1s 级。
  2. 构建产物：从优化前约 5.68 MiB 降到约 3.92 MiB，减少 30%+。
  3. 对比旧 Vue2 测量 copy：约 5.94 MiB 到约 3.92 MiB，减少 30%+。

做法：

  1. 生产环境不引入 Mock。
  2. 图表库只注册项目用到的图表和组件。
  3. UI 组件和样式按需引入。
  4. 首页和业务模块按路由拆包，避免主包过大。
  5. 检查大依赖是否被全量引入。

面试口径：

Vite 主要解决开发启动慢，不代表最终包体一定变小。包体优化还是要看依赖引入、Mock、图表库、UI 库和路由拆包。我实际做过构建前后测量，所以简历里写 30%+ 更稳。

6. 权限和安全整改 ​

权限链路：

  1. 登录后获取用户、角色和菜单权限。
  2. 根据菜单权限生成动态路由。
  3. 通过权限指令或权限组件控制按钮。
  4. 用户退出或切换身份时重置路由和权限状态。
  5. 接口返回无权限时统一处理兜底。

安全整改：

  1. 登录密码加密传输。
  2. 图形验证码降低撞库和自动化登录风险。
  3. 前端不展示敏感错误信息。
  4. 权限入口控制避免误操作。
  5. 配合渗透测试整改页面和请求层问题。

面试表达：

安全这块不要说成前端能完全防住攻击。前端主要做输入输出、安全展示、入口控制和用户体验层面的防护，真正权限和敏感操作必须后端兜底。

面试追问 ​

Q：规则引擎页面最难的点是什么？

A：最难的是递归条件的数据结构和回显。因为新增、删除、嵌套、操作符切换、字段类型切换都会影响数据结构，如果只按 UI 写，很容易提交结构不稳定。我会把条件组抽成统一节点结构，再做递归渲染和统一转换。

Q：递归规则怎么避免数据错乱？

A：我会让每个节点都有稳定结构和唯一标识，简单条件和条件组分清楚。新增、删除、操作符切换、字段切换都只修改当前节点；提交前统一做一次转换和校验，而不是每个输入框各自拼提交参数。

Q：Vue 2 迁移 Vue 3 你处理了哪些兼容问题？

A：主要有路由懒加载语法、Vue Router 4 动态路由、全局属性、权限指令、Element Plus 组件 API、静态资源路径、环境变量和构建配置。迁移时先跑通主流程，再逐步处理边缘页面。

Q：为什么迁移时没有直接换 Pinia？

A：迁移目标是降低风险，优先解决 Vue 3 和 Vite 升级。原 Vuex modules 还能工作，所以先升到 Vuex 4 保持状态结构稳定，避免同时改框架、路由、UI、状态管理导致问题范围扩大。后续再按模块逐步迁 Pinia 更稳。

Q：Element UI 到 Element Plus 有哪些坑？

A：表格、表单、弹窗、日期选择、消息提示这些组件要重点测。大部分模板写法相近，但事件、插槽、样式类名、全局引入方式和部分 API 会有差异，迁移后要按核心页面逐个验证。

Q：为什么 Vite 后包体不一定天然变小？

A：Vite 主要提升开发启动和构建体验，最终包体还取决于依赖引入方式和静态资源。比如 ECharts、Element Plus、mock 数据如果全量进主包，最终产物不会明显变小。后来我通过生产剔除 mock、按需引入和拆包治理，把构建产物减少 30%+。

Q：指标配置如何处理依赖？

A：用级联选择，前置项变化时清理后置值；编辑回显按依赖顺序依次加载选项；不同指标类型用不同表单和校验规则。

Q：权限怎么做？

A：路由层根据后端菜单和权限生成动态路由，按钮层通过权限指令或权限组件控制操作显示。需要注意的是前端权限只负责体验和入口控制，真正的数据权限仍然由后端校验。

Q：业务方在系统上配错规则怎么办？

A：前端在校验阶段提示字段缺失、操作符冲突、值类型错误；提交时做格式校验；保存后再加上后端二次校验，确保不会因为前端绕过导致错误规则进入执行环境。
