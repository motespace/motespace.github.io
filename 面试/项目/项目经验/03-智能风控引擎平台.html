智能风控引擎平台 ​

项目概览 ​

时间：2023.08 - 2024.06 公司：华润网络深圳有限公司 角色：前端核心开发 技术栈：Vue 3、Vite、TypeScript、Element Plus、Pinia、ECharts（由 Vue 2 + Webpack 迁移） 推荐程度：主讲项目，尤其适合 Vue 岗位

这是一个面向风控运营和策略人员的决策引擎后台，支持规则配置、指标管理、策略管理、数据中心看板和权限管理。项目最初是 Vue 2 + Webpack，后续由我主导迁移到 Vue 3 + Vite。

面试时可以这样概括：

这是一个让策略和运营人员通过页面配置规则、指标和策略的后台系统。业务难点是规则不是普通表单，而是可以递归嵌套的条件树；工程难点是老系统迁移过程中要保持登录、权限和核心业务连续可用。我先保证主链路可运行，再分模块迁移，最后做构建和依赖优化。

业务全貌 ​

这个项目不是单一 CRUD 系统，而是面向风控运营、策略人员和管理人员的决策引擎后台。平台目标是让业务人员可以配置指标、规则和策略，查看执行效果，而不是每次都依赖研发改代码。

可以按 5 个模块讲：

  1. 规则 / 模型：配置规则条件、操作符、字段和值，支持多层条件组合。
  2. 指标体系：原子指标、派生指标、数据源、数据表、字段、聚合方式、业务域分类。
  3. 策略管理：把规则、指标、处置动作组合成可执行策略。
  4. 数据中心 / 看板：展示策略趋势、指标趋势、风险模型效果。
  5. 系统权限：用户、角色、菜单、按钮权限、操作日志。

面试表达：

这个项目最能体现复杂业务拆解。规则引擎不是一个普通表单，它本质上是把业务人员想表达的判断逻辑，转换成前后端都能识别的数据结构。

技术实现 ​

1. 规则引擎条件树（真实代码结构） ​

规则可以抽象为条件组和简单条件。真实代码里用的是 class: 'SMPL' | 'PDCT' 区分（Simple / Predicate），所有节点用统一的 expressions 数组描述左侧字段、操作符和右侧值。

1.1 真实数据结构 ​

ts
// 真实代码片段：airisk-front/src/components/recursionModelCondition.vue
type Operator =
  | 'StartsWith' | 'NotStartsWith' | 'Contains'
  | 'Equal' | 'NotEqual' | 'InList' | 'NotInList'
  | 'IsNull' | 'IsNotNull'
  | 'Field_Equal' | 'Field_Not_Equal'
  | 'Less' | 'Less_Equal' | 'Greater' | 'Greater_Equal'
  | 'Field_Greater' | 'Field_Less' | 'Field_Greater_Equal' | 'Field_Less_Equal'

type SimpleCondition = {
  class: 'SMPL'                    // 简单条件
  id: string
  enabled: boolean
  operator: Operator
  // 关键：expressions 是数组，左侧字段 + 右侧值/字段都放这里
  expressions: [
    { class: 'ENTATTR'; type: string; column: string[] },   // 左侧：实体字段
    { class: 'CONST' | 'ENTATTR'; type: string; value?: any; column?: string[] }  // 右侧：常量或字段
  ]
}

type ConditionGroup = {
  class: 'PDCT'                    // 条件组（可嵌套）
  id: string
  enabled: boolean
  linking: 'All' | 'Any' | 'NotAll' | 'None'   // 组合逻辑：与/或/非与/非或
  conditions: Array<SimpleCondition | ConditionGroup>
}

1.2 操作符设计（真实列表） ​

下面是从 airisk-front 抽出来的真实操作符配置，面试时可以展示操作符如何驱动右侧控件：

ts
// 真实代码片段：recursionModelCondition.vue - contrastFieldList
const contrastFieldList = [
  // 字符串类
  { label: '以...开始',     value: 'StartsWith',    nextType: 'input' },
  { label: '不以...开始',   value: 'NotStartsWith', nextType: 'input' },
  { label: '包含',          value: 'Contains',      nextType: 'input' },
  // 集合类
  { label: '在列表...中',   value: 'InList',        nextType: 'list' },
  { label: '不在列表...中', value: 'NotInList',     nextType: 'list' },
  // 空值类
  { label: '为空',          value: 'IsNull',        nextType: 'empty' },
  { label: '不为空',        value: 'IsNotNull',     nextType: 'empty' },
  // 字段比较类（关键能力：右侧值可以是另一个字段）
  { label: '等于（字段）',  value: 'Field_Equal',    nextType: 'field' },
  { label: '大于（字段）',  value: 'Field_Greater',  nextType: 'field' },
  // 数值比较类
  { label: '大于',          value: 'Greater',       nextType: 'input' },
  { label: '小于等于',      value: 'Less_Equal',    nextType: 'input' },
  // ... 共 17 个
]

nextType 是关键设计：

  • input：右侧渲染输入框（数值/字符串）。
  • list：右侧渲染下拉选择。
  • empty：右侧不渲染输入框（IsNull / IsNotNull 没有"值"概念）。
  • field：右侧渲染字段选择器（不是填值，是选另一个字段）。

1.3 操作符切换时动态改变右侧控件（真实逻辑） ​

ts
// 真实代码片段：recursionModelCondition.vue - changeSelect
changeSelect(type, e, item, index) {
  this.changeItemIndex = index
  const ct = this.contrastFieldList.find(m => m.value === e)

  let obj = {
    class: 'ENTATTR',
    type: ct.nextType.toUpperCase(),
    value: ct.nextType === 'field' ? [] : '',
  }

  const firstType = item.expressions[0].type

  // 关键：nextType 决定右侧表达式 class 和 type
  if (ct.nextType === 'input') {
    obj.class = 'CONST'              // 右侧是常量
    obj.type = firstType              // 类型继承左侧字段类型
  } else if (ct.nextType === 'list') {
    obj.class = 'CONST'
    obj.type = 'LIST'
  } else if (ct.nextType === 'field') {
    obj.type = 'string'               // 字段比较类型固定 string
  }

  if (item.expressions.length > 1) {
    item.expressions.splice(1, 1, obj)
    if (ct.nextType === 'empty') item.expressions.splice(1, 1)  // 关键：empty 不需要右侧
  } else {
    item.expressions.push(obj)
  }
}

设计要点：

  • expressions 数组下标语义固定：[0] 永远是左侧字段，[1] 是右侧值/字段。这样 UI 和数据结构就解耦了，组件递归渲染只看下标。
  • nextType 驱动 UI：empty 操作符把右侧整段 splice 掉，避免 UI 上显示空输入框。
  • field 比较特殊：右侧不是"值"而是另一个字段，所以 value 初始化为 []，UI 渲染字段级联选择器。

1.4 字段类型联动（selectCascader 真实代码） ​

ts
// 真实代码片段：recursionModelCondition.vue - selectCascader
selectCascader(e, item, index) {
  this.changeItemIndex = index
  const lastItem = this.getCascaderObj(e, this.fieldOptions)
  item.expressions[0].type = lastItem[lastItem.length - 1].type

  // 关键：左侧字段切换后，右侧值可能不兼容，必须清空
  if (item.expressions.length > 1) {
    item.expressions.splice(1, 1)
    item.operator = ''
  }
}

设计要点：

  • 左侧字段类型决定可选操作符：字符串字段不能选"大于"、日期字段不能选"包含"。切换字段时要清空右侧和操作符，避免无效组合。
  • 级联选择器路径：用 getCascaderObj 把级联数组（如 ['user', 'profile', 'age']）展开成对象链，取最后一级的 type。

设计要点：

2. 规则校验和提交转换 ​

不要让每个输入框自己拼接口参数，而是统一在提交阶段处理：

ts
function validateGroup(group: ConditionGroup): string[] {
  const errors: string[] = []

  if (!group.children.length) {
    errors.push(`条件组 ${group.id} 不能为空`)
    return errors
  }

  group.children.forEach((node, idx) => {
    if (node.kind === 'group') {
      errors.push(...validateGroup(node))
    } else {
      // 关键：简单条件必须字段 + 操作符 + 值都填了
      if (!node.field) errors.push(`第 ${idx + 1} 行未选择字段`)
      if (!node.operator) errors.push(`第 ${idx + 1} 行未选择操作符`)
      if (needsValue(node.operator) && node.value === undefined) {
        errors.push(`第 ${idx + 1} 行操作符 ${node.operator} 需要填写值`)
      }
    }
  })

  return errors
}

function needsValue(operator: Operator): boolean {
  return operator !== 'IsNull' && operator !== 'IsNotNull'
}

3. 操作符联动：字段类型 × 操作符二维筛选 ​

操作符不是固定展示全部，而是要结合字段类型和业务语义筛选：

  1. 字符串类：以某内容开始、包含、等于、不等于。
  2. 集合类：在列表中、不在列表中。
  3. 空值类：为空、不为空。
  4. 数值比较：大于、大于等于、小于、小于等于。
  5. 字段比较：等于某字段、大于某字段、小于某字段。

比如日期、数字、字符串能用的操作符不完全一样；选择"为空 / 不为空"时右侧不应该再出现输入框。

4. Vue 2 → Vue 3 + Vite 迁移（真实工程细节） ​

4.1 真实迁移脚本（codemod） ​

真实项目里我写了一个 codemod 脚本，处理 Vue 2 → Vue 3 的"高确定性"机械转换：

js
// 真实代码片段：airisk-front/scripts/codemod-vue3.mjs（节选）
const TEMPLATE_TRANSFORMS = [
  // Element Plus 2 重命名
  { id: 'el-submenu-open',  re: /<el-submenu(\s|>)/g, to: '<el-sub-menu$1' },
  { id: 'el-submenu-close', re: /<\/el-submenu>/g,    to: '</el-sub-menu>' },

  // ::v-deep selector → :deep(selector)
  {
    id: 'v-deep-as-combinator',
    re: /::v-deep\s+([^\s,{][^,{]*?)(?=\s*[,\{])/g,
    to: (_, sel) => `:deep(${sel.trim()})`
  },
  {
    id: 'v-deep-block',
    re: /::v-deep\s*\{/g,
    to: ':deep {'
  },

  // <template slot="name"> → <template #name>
  {
    id: 'template-slot-attr',
    re: /<template\s+([^>]*)slot="([\w-]+)"/g,
    to: (_, attrs, name) => {
      const trimmedAttrs = (attrs || '').trim()
      return trimmedAttrs ? `<template ${trimmedAttrs} #${name}` : `<template #${name}`
    }
  },

  // <template slot-scope="scope"> → <template #default="scope">
  {
    id: 'slot-scope',
    re: /<template\s+([^>]*)slot-scope="([^"]+)"/g,
    to: (_, attrs, scope) => {
      const trimmedAttrs = (attrs || '').trim().replace(/\s+$/, '')
      return trimmedAttrs ? `<template ${trimmedAttrs} #default="${scope}"` : `<template #default="${scope}"`
    }
  },

  // .sync 修饰符: :foo.sync="bar" → v-model:foo="bar"
  { id: 'sync-short', re: /:([\w-]+)\.sync="([^"]+)"/g, to: 'v-model:$1="$2"' },
  { id: 'sync-bind',  re: /v-bind:([\w-]+)\.sync="([^"]+)"/g, to: 'v-model:$1="$2"' },
]

设计要点：

  • 只做高确定性转换：模板语法（slot/sync/v-deep）是字符串替换就能搞定的，Options API → script setup 是语义转换，留给人工。
  • dry-run 默认：脚本默认输出 diff 报告而不是直接改文件，CI 跑完 review diff 再决定是否 apply。
  • 用 git ls-files 而不是 glob：避免 .gitignore 误伤要处理的文件。

4.2 真实迁移分层（7 层） ​

  1. 依赖层：vue、vue-router、vuex、element-ui 升级到 vue@3、vue-router@4、vuex@4、element-plus，注意 Vue.prototype 改 app.config.globalProperties。
  2. 路由层：Vue Router 2 改 Router 4，addRoutes 改为逐条 addRoute，旧的 require 懒加载改 import()。
  3. Store 层：Vuex 3 升 Vuex 4，保留原有 modules 结构，先降低业务改动风险。
  4. UI 层：Element UI 迁到 Element Plus，重点验证表格、表单、弹窗、分页和日期组件。
  5. 兼容层：生命周期、事件总线、旧插件、静态资源路径、全局组件注册逐步处理。
  6. 优化层：生产环境剔除 Mock，ECharts 和 Element Plus 按需，路由拆包，减少主包体积。
  7. 脚手架层：保留旧 Webpack 配置用于回滚，新增 Vite 配置走灰度发布。

核心原则：迁移目标是降低风险。先保证登录、权限、菜单、核心页面可用，再处理组件兼容和构建优化。这样不会因为迁移影响业务交付。

4.3 真实 Router 4 迁移坑 ​

js
// 真实代码片段：airisk-front/src/permission.js（迁移后）
router.beforeEach((to, from, next) => {
  let inr = store.getters.initRouter
  let token = localStorage.getItem('risk_token')

  // 关键：Vue Router 4 的 beforeEach 必须显式调用 next()，不调用 = 取消导航
  // 已在默认页点 logo 再 push '/'：保持当前 URL，不切换
  if (token && (to.path === '/' && from.path === inr) && inr != "/") {
    next(false)
    return
  }
  // ...
  store.dispatch('GenerateRoutes').then(accessRoutes => {
    // 关键：VR4 中 addRoute 单条替换 addRoutes（数组批量）
    accessRoutes.forEach(route => router.addRoute(route))
    // 兜底通配符路由（VR4 语法）
    router.addRoute({ path: '/:pathMatch(.*)*', redirect: '/404', hidden: true })
    // ...
  })
})

迁移难点：

  • addRoutes 没了：Vue Router 4 把批量添加路由改成了 addRoute 单条添加，需要 forEach 遍历。
  • 通配符路由语法变了：VR3 的 path: '*' 在 VR4 改成 path: '/:pathMatch(.*)*'。
  • next(false) 语义保留：但很多老代码 return 不调用 next 在 VR3 是放行，在 VR4 是取消导航，这是迁移时最容易踩的坑。

6. 权限和安全整改 ​

6.1 权限链路（真实代码） ​

js
// 真实代码片段：airisk-front/src/permission.js
router.beforeEach((to, from, next) => {
  const token = localStorage.getItem('risk_token')

  if (token) {
    if (store.getters.roles.length === 0) {
      // 首次进入：拉用户信息 → 生成动态路由 → addRoute
      store.dispatch('GetInfo').then(() => {
        store.dispatch('GenerateRoutes').then(accessRoutes => {
          accessRoutes.forEach(route => router.addRoute(route))
          // ...
        })
      })
    } else {
      // 已有角色：直接放行
      next()
    }
    return
  }

  // 白名单：login、auth-redirect、bind、introduce、register
  if (whiteList.indexOf(to.path) !== -1) {
    next()
    return
  }

  next(`/login`)
})

设计要点：

  • 动态路由：登录后根据后端返回的菜单权限生成 accessRoutes，逐条 addRoute。这样不同角色看到的菜单不一样，URL 越权会跳 404。
  • 白名单：/login、/register、/introduce（产品介绍）这些页面不需要登录。

6.2 按钮级权限 ​

真实项目里用 v-hasPermi 自定义指令：

html
<!-- 真实代码片段 -->
<el-button v-hasPermi="['risk:model:add']" @click="handleEdit()">新增模型</el-button>

<a v-has-permi="['risk:field:add']" @click="handleEdit(scope.row,'addField')">创建必备字段</a>
js
// 自定义指令：airisk-front/src/directive/permission/hasPermi.js
app.directive('hasPermi', {
  mounted(el, binding) {
    const requiredPerms = binding.value  // ['risk:model:add']
    const userPerms = store.getters.permissions
    const hasPermission = requiredPerms.some(p => userPerms.includes(p))
    if (!hasPermission) {
      el.parentNode?.removeChild(el)  // 无权限直接移除 DOM
    }
  },
})

设计要点：

  • 数组 OR 关系：['risk:model:add', 'risk:model:edit'] 只要有其中一个权限就显示。
  • 直接 removeChild：比 v-if 更彻底，避免通过 DevTools 改 DOM 把隐藏按钮调出来。

6.3 安全整改 ​

  1. 登录密码加密传输（RSA + JSEncrypt）。
  2. 图形验证码降低撞库和自动化登录风险。
  3. 前端不展示敏感错误信息（敏感错误码映射到友好文案）。
  4. 权限入口控制避免误操作。
  5. 配合渗透测试整改页面和请求层问题。

面试表达：

安全这块不要说成前端能完全防住攻击。前端主要做输入输出、安全展示、入口控制和用户体验层面的防护，真正权限和敏感操作必须后端兜底。

面试追问 ​

Q：规则引擎页面最难的点是什么？

A：最难的是递归条件的数据结构和回显。因为新增、删除、嵌套、操作符切换、字段类型切换都会影响数据结构，如果只按 UI 写，很容易提交结构不稳定。我会把条件组抽成统一节点结构，再做递归渲染和统一转换。

Q：递归规则怎么避免数据错乱？

A：我会让每个节点都有稳定结构和唯一标识，简单条件和条件组分清楚。新增、删除、操作符切换、字段切换都只修改当前节点；提交前统一做一次转换和校验，而不是每个输入框各自拼提交参数。

Q：Vue 2 迁移 Vue 3 你处理了哪些兼容问题？

A：主要有路由懒加载语法、Vue Router 4 动态路由、全局属性、权限指令、Element Plus 组件 API、静态资源路径、环境变量和构建配置。迁移时先跑通主流程，再逐步处理边缘页面。

Q：为什么迁移时没有直接换 Pinia？

A：迁移目标是降低风险，优先解决 Vue 3 和 Vite 升级。原 Vuex modules 还能工作，所以先升到 Vuex 4 保持状态结构稳定，避免同时改框架、路由、UI、状态管理导致问题范围扩大。后续再按模块逐步迁 Pinia 更稳。

Q：Element UI 到 Element Plus 有哪些坑？

A：表格、表单、弹窗、日期选择、消息提示这些组件要重点测。大部分模板写法相近，但事件、插槽、样式类名、全局引入方式和部分 API 会有差异，迁移后要按核心页面逐个验证。

Q：为什么 Vite 后包体不一定天然变小？

A：Vite 主要提升开发启动和构建体验，最终包体还取决于依赖引入方式和静态资源。比如 ECharts、Element Plus、mock 数据如果全量进主包，最终产物不会明显变小。后来我通过生产剔除 mock、按需引入和拆包治理，把构建产物减少 30%+。

Q：指标配置如何处理依赖？

A：用级联选择，前置项变化时清理后置值；编辑回显按依赖顺序依次加载选项；不同指标类型用不同表单和校验规则。

Q：权限怎么做？

A：路由层根据后端菜单和权限生成动态路由，按钮层通过权限指令或权限组件控制操作显示。需要注意的是前端权限只负责体验和入口控制，真正的数据权限仍然由后端校验。

Q：业务方在系统上配错规则怎么办？

A：前端在校验阶段提示字段缺失、操作符冲突、值类型错误；提交时做格式校验；保存后再加上后端二次校验，确保不会因为前端绕过导致错误规则进入执行环境。

Q：Vue Router 4 迁移最常见的踩坑？

A：addRoutes 没了，必须 forEach + addRoute；通配符路由语法变成 /:pathMatch(.*)*；beforeEach 不调用 next() 在 VR4 是取消导航，VR3 是放行——这三个坑最容易在迁移时漏掉。
