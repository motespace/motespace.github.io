会员服务平台 Web / H5 ​

项目概览 ​

时间：2024.08 - 2026.08
角色：前端核心开发
技术栈：Next.js、React、TypeScript、Ant Design、移动端组件、SSR、PWA

这是一个面向 C 端用户的 Web / H5 会员服务平台，覆盖登录注册、业务产品入口、权益活动、账户中心、会员中心、协议和帮助中心。Web 和 H5 分端建设，H5 支持 App WebView 内嵌。

我负责的内容 ​

  1. 负责 Web / H5 双端核心页面和差异化组件。
  2. 复用接口、全局状态、枚举、多语言和安全展示能力。
  3. 封装 App 内嵌 H5 通信，处理标题、跳转和页面状态通知。
  4. 落地验证码、设备摘要、三方登录和行为验证等认证链路。
  5. 处理 Token 生命周期、敏感请求保护、富文本安全展示和 iframe 消息校验。
  6. 实现国际化、主题切换和 PWA 静态资源缓存。

Web / H5 如何拆分 ​

业务逻辑尽量复用，交互和布局按端实现。

复用部分：

  • 接口类型和统一请求层。
  • 登录态、用户信息、语言、主题等全局状态。
  • 枚举、金额格式化、时间处理和安全展示。
  • 活动、账户中心和会员资料的业务数据结构。

分开部分：

  • Web 使用桌面端布局和完整会员中心。
  • H5 使用移动端布局、底部导航、移动弹层和安全区适配。
  • Web 和 H5 使用不同的交互组件，避免强行复用导致体验下降。

技术实现 ​

1. App 内嵌 H5 通信 ​

通信层负责 WebView 检测、消息序列化和浏览器降级，页面只调用业务方法。

  1. 判断 App 是否注入原生 channel。
  2. H5 通过 postMessage 发送导航和页面状态消息。
  3. 页面标题使用独立的标题 channel 通知 App。
  4. 普通浏览器环境回退到 document.title 和 H5 路由。
  5. App 返回 H5 后通过 visibilitychange 重新同步语言、主题和登录状态。
ts
type BridgeMessage =
  | { type: 'NAVIGATE'; payload: { path: string } }
  | { type: 'PAGE_STATE'; payload: { visible: boolean } }

declare global {
  interface Window {
    nativeBridge?: { postMessage(message: string): void }
    titleBridge?: { postMessage(message: string): void }
  }
}

function isWebView() {
  return typeof window !== 'undefined' && Boolean(window.nativeBridge)
}

function sendToApp(message: BridgeMessage) {
  if (!isWebView()) return false

  try {
    window.nativeBridge!.postMessage(JSON.stringify(message))
    return true
  } catch {
    return false
  }
}

export const appBridge = {
  setTitle(title: string) {
    if (isWebView()) {
      window.titleBridge?.postMessage(title)
    } else {
      document.title = title
    }
  },

  navigate(path: string) {
    if (!sendToApp({ type: 'NAVIGATE', payload: { path } })) {
      window.location.assign(path)
    }
  },
}

上面的 channel 名、消息类型和字段均为泛化示例。当前项目主要是 H5 向 App 的单向通知，登录态和语言主要通过 Cookie、store 及后端校验完成，不应说成所有状态都通过 postMessage 双向传输。

2. 登录态初始化和 Token 生命周期 ​

页面加载时：

  1. 从 Cookie / store 读取已有登录态。
  2. 调用后端接口校验 Token。
  3. 校验成功后刷新用户信息、语言、主题和展示环境。
  4. 校验失败时清理 Cookie、store 和页面敏感数据。
  5. 接口返回登录失效时只触发一次清理和跳转。
ts
async function bootstrapAuth() {
  const token = readTokenFromCookie()

  if (!token) {
    clearUserState()
    return false
  }

  const valid = await verifyToken(token)
  if (!valid) {
    clearUserState()
    redirectToLogin()
    return false
  }

  setToken(token)
  await refreshUserInfo()
  return true
}

前端负责登录态编排和页面状态同步，Token 有效性、权限和敏感操作必须由后端最终校验。

3. 设备摘要和三方登录 ​

设备摘要模块在客户端动态加载，避免 SSR 阶段访问浏览器 API。生成的摘要只作为登录 / 注册请求的辅助字段提交，失败时不阻塞普通页面。

三方登录流程：

  1. 前端向后端获取授权地址。
  2. 打开独立窗口。
  3. 监听同源 postMessage 或一次性本地存储消息。
  4. 将成功、取消、超时、关闭和失败统一转换为 Promise。
  5. 只允许流程完成一次，并在结束时移除监听、关闭窗口和清理定时器。
ts
function startExternalLogin(provider: string) {
  return new Promise<{ token?: string }>((resolve, reject) => {
    let finished = false
    const popup = window.open('about:blank', 'auth_window')
    if (!popup) return reject(new Error('popup blocked'))

    const finish = (error?: Error, data?: { token?: string }) => {
      if (finished) return
      finished = true
      window.removeEventListener('message', onMessage)
      window.clearTimeout(timer)
      popup.close()
      error ? reject(error) : resolve(data || {})
    }

    const onMessage = (event: MessageEvent) => {
      if (event.origin !== window.location.origin) return
      if (event.data?.type === 'AUTH_SUCCESS') finish(undefined, event.data.payload)
      if (event.data?.type === 'AUTH_ERROR') finish(new Error('auth failed'))
    }

    window.addEventListener('message', onMessage)
    const timer = window.setTimeout(() => finish(new Error('auth timeout')), 60_000)

    getExternalAuthUrl(provider)
      .then((url) => popup.location.replace(url))
      .catch((error) => finish(error))
  })
}

4. 请求保护和验证挑战 ​

统一请求层负责：

  • 注入 Token、语言、主题、时区和客户端类型。
  • 使用 AbortController 取消相同业务 key 的旧请求。
  • 对约定的敏感请求体做 AES 参数保护。
  • 处理 Token 失效、业务错误、验证挑战和请求重试。
ts
const pending = new Map<string, AbortController>()

async function request<T>(
  url: string,
  body: unknown,
  options: { sensitive?: boolean; cancelKey?: string; retry?: boolean } = {},
) {
  const controller = new AbortController()

  if (options.cancelKey) {
    pending.get(options.cancelKey)?.abort()
    pending.set(options.cancelKey, controller)
  }

  try {
    const raw = JSON.stringify(body)
    const payload = options.sensitive ? encryptPayload(raw) : raw
    const response = await fetch(url, {
      method: 'POST',
      credentials: 'include',
      signal: controller.signal,
      headers: {
        'Content-Type': 'application/json',
        Authorization: getToken() ? `Bearer ${getToken()}` : '',
      },
      body: payload,
    })

    const result = await response.json()

    if (result.code === 'CHALLENGE_REQUIRED' && !options.retry) {
      const challengeToken = await challengeManager.requestToken()
      return request(url, { ...(body as object), challengeToken }, {
        ...options,
        retry: true,
      })
    }

    if (result.code === 'AUTH_EXPIRED') {
      clearUserState()
      redirectToLogin()
      throw new Error('login expired')
    }

    if (!response.ok || result.code !== 'SUCCESS') {
      throw new Error(result.message || 'request failed')
    }

    return result.data as T
  } finally {
    if (options.cancelKey && pending.get(options.cancelKey) === controller) {
      pending.delete(options.cancelKey)
    }
  }
}

前端加密不是绝对安全措施，不能替代 HTTPS、服务端解密校验、权限校验和 Token 管理。

5. 验证挑战并发控制 ​

多个请求同时遇到验证挑战时，使用单例管理器维护 Promise 队列，只展示一个全局验证组件：

ts
class ChallengeManager {
  private queue: Array<(token: string) => void> = []
  private visible = false

  requestToken() {
    return new Promise<string>((resolve) => {
      this.queue.push(resolve)
      this.openOnce()
    })
  }

  private openOnce() {
    if (this.visible) return
    this.visible = true
    // 打开全局验证组件，成功后调用 resolveAll
  }

  resolveAll(token: string) {
    const queue = this.queue.splice(0)
    this.visible = false
    queue.forEach((resolve) => resolve(token))
  }
}

6. 富文本和 iframe 安全展示 ​

富文本统一通过安全组件处理，禁止脚本、iframe、表单、事件属性和未知协议：

tsx
import DOMPurify from 'isomorphic-dompurify'

function SafeHtml({ html }: { html?: string }) {
  const clean = DOMPurify.sanitize(html || '', {
    USE_PROFILES: { html: true },
    FORBID_TAGS: ['script', 'iframe', 'object', 'embed', 'form'],
    FORBID_ATTR: ['srcdoc', 'onerror', 'onclick', 'onload'],
    ALLOW_UNKNOWN_PROTOCOLS: false,
  })

  return clean ? <div dangerouslySetInnerHTML={{ __html: clean }} /> : null
}

iframe 页面加载前校验 URL，收到消息时同时校验来源和消息源：

ts
function parseAllowedUrl(raw?: string | null) {
  if (!raw) return null

  try {
    const url = new URL(raw)
    if (url.protocol !== 'https:' || url.username || url.password) return null
    return url
  } catch {
    return null
  }
}

function isAllowedMessage(event: MessageEvent, iframe: HTMLIFrameElement, url: URL | null) {
  return Boolean(
    url &&
      event.origin === url.origin &&
      event.source === iframe.contentWindow,
  )
}

业务流程怎么讲 ​

1. 登录 / 注册闭环 ​

登录注册通常不止一个接口，而是由多个状态组成：

  1. 用户输入账号，先校验格式和账号类型。
  2. 根据配置判断是否需要一次性验证码或行为验证。
  3. 注册 / 登录时获取设备摘要、来源信息和语言环境。
  4. 验证通过后调用登录接口，返回登录态。
  5. 登录成功后写入 Cookie / store，并刷新用户资料和全局配置。
  6. 根据来源路径回到原页面，或者进入默认首页。

需要重点说明异常状态：

  • 账号不存在或已被限制。
  • 验证码错误、过期或发送频率受限。
  • 人机验证失败，需要重新获取挑战凭证。
  • 登录成功但用户资料刷新失败。
  • App WebView 中 Cookie 注入尚未完成。

前端的职责是把这些状态组织成可恢复的流程，真正的账号校验和风险判断由后端完成。

2. 账户服务和订单状态 ​

账户服务页面可以按“创建 -> 跳转 -> 返回 -> 查询 -> 展示”来讲：

  1. 用户选择服务方式、金额和必要信息。
  2. 前端校验金额格式、必填项和页面状态。
  3. 调接口创建业务单据，获得服务页面地址或业务单号。
  4. 跳转到 iframe、外部页面或 App 页面。
  5. 用户返回时重新查询业务单据状态。
  6. 根据服务端状态展示成功、处理中、失败或需要继续操作。

不能只依赖前端的成功回调，因为用户可能关闭页面、网络中断或从外部页面返回。页面重新可见时重新查询，是这类流程的关键。

3. 活动和内容配置 ​

活动页按“展示 -> 判断资格 -> 参与 -> 领取 -> 记录”拆分：

  1. 展示活动时间、规则、状态和多语言文案。
  2. 根据登录态、用户条件和活动时间控制参与入口。
  3. 提交参与请求并防止重复点击。
  4. 领取奖励或权益后刷新状态。
  5. 在记录页展示参与和处理结果。

前端要区分“按钮不可见”和“接口无权限”两个问题：前者是页面体验，后者必须处理服务端返回。

App 内嵌通信的完整实现 ​

1. 通信边界 ​

项目中的 H5 通过 App 注入的 JavaScript channel 发送消息，主要用于：

  • 页面跳转。
  • 页面标题同步。
  • 页面状态或弹层状态通知。
  • 部分 App 独占能力的加载完成通知。

登录态、语言和主题并不是简单地把所有数据通过 postMessage 传输，而是结合 Cookie、store、URL 参数和页面重新激活进行同步。

2. 为什么需要统一 bridge ​

如果业务页面直接调用原生对象，会产生几个问题：

  1. SSR 阶段没有 window。
  2. 普通浏览器没有 App channel。
  3. iOS / Android 的注入方式可能不同。
  4. 页面自己拼接 payload，协议容易不一致。
  5. App 没响应时没有统一降级方式。

因此桥接层至少需要：

ts
type BridgeMessage = {
  type: 'NAVIGATE' | 'PAGE_STATE'
  payload: Record<string, unknown>
}

function sendToNative(message: BridgeMessage) {
  if (typeof window === 'undefined') return false

  const bridge = window.nativeBridge
  if (!bridge) return false

  try {
    bridge.postMessage(JSON.stringify(message))
    return true
  } catch {
    return false
  }
}

当前项目主要是单向通知。面试时如果被问到如何设计双向回调，可以说：

需要原生返回结果时，可以增加 requestId，在 H5 侧维护等待 Map，并设置超时和清理机制；但当前已落地的页面跳转和标题同步主要是单向通知。

3. WebView 返回前台 ​

App 页面可能会暂时覆盖 H5，用户返回后页面仍然存在，但语言、主题或 Cookie 可能已经变化。因此在根布局监听：

ts
useEffect(() => {
  if (!isWebView()) return

  const syncWhenVisible = () => {
    if (document.visibilityState !== 'visible') return

    void syncLanguageFromCookie()
    void refreshLoginState()
  }

  document.addEventListener('visibilitychange', syncWhenVisible)
  return () => {
    document.removeEventListener('visibilitychange', syncWhenVisible)
  }
}, [])

这个处理也适用于外部授权、支付页面和 App 页面返回后的状态刷新。

认证和请求层的实现细节 ​

1. Token 生命周期 ​

Token 相关逻辑集中在请求层和全局状态层：

  1. 请求前从 Cookie / store 读取当前 Token。
  2. 统一设置认证请求头和语言、主题、时区等上下文。
  3. 页面初始化调用校验接口。
  4. 校验成功后刷新用户信息。
  5. 收到失效错误后只执行一次清理和跳转。
  6. 退出时清理 Cookie、store、缓存和页面敏感数据。
ts
let handlingExpired = false

function handleAuthExpired() {
  if (handlingExpired) return
  handlingExpired = true

  clearUserState()
  redirectToLogin()

  window.setTimeout(() => {
    handlingExpired = false
  }, 1000)
}

这个单次处理很重要，因为多个接口可能同时返回失效状态，不能重复弹窗、重复跳转。

2. 验证挑战队列 ​

验证挑战由全局组件展示，多个请求共享同一个验证流程：

ts
class ChallengeManager {
  private waiting: Array<(token: string) => void> = []
  private opened = false

  requestToken() {
    return new Promise<string>((resolve) => {
      this.waiting.push(resolve)
      if (!this.opened) {
        this.opened = true
        this.openChallengeDialog()
      }
    })
  }

  resolve(token: string) {
    const waiting = this.waiting.splice(0)
    this.opened = false
    waiting.forEach((resolve) => resolve(token))
  }

  private openChallengeDialog() {
    // 通知全局验证组件显示
  }
}

请求收到挑战错误后，拿到临时凭证再重试一次原请求。重试必须有标识，避免验证接口本身再次触发无限重试。

3. 敏感请求参数保护 ​

项目中对约定的敏感请求体进行对称加密封装，服务端负责解密和校验：

ts
function buildRequestBody(data: unknown, sensitive: boolean) {
  const raw = JSON.stringify(data)
  return sensitive ? encryptPayload(raw) : raw
}

面试时必须说明：前端代码和运行时配置无法提供绝对保密，参数加密只是传输链路的一层保护，不能替代 HTTPS、服务端校验、权限控制和 Token 生命周期管理。

三方登录的边界处理 ​

三方登录除了成功，还要处理：

  1. 浏览器阻止弹窗。
  2. 授权地址获取失败。
  3. 用户主动关闭窗口。
  4. 回调消息来源不可信。
  5. 同一回调重复触发。
  6. 超时未完成。
  7. 登录成功后还需要补充绑定信息。

核心实现是“只完成一次 + 及时清理”：

ts
function finishOnce<T>(
  state: { finished: boolean },
  cleanup: () => void,
  resolve: (value: T) => void,
  value: T,
) {
  if (state.finished) return
  state.finished = true
  cleanup()
  resolve(value)
}

监听 message 时先校验 event.origin，再判断消息类型和 payload 结构，不能收到任意窗口消息就当作登录成功。

CI / CD 和工程协作 ​

项目使用 Docker + PM2 部署，配合 Husky / lint-staged 做提交卡口，按 .env.{env} 区分环境构建。

1. 多环境构建 ​

package.json 里的构建脚本按环境区分，每套环境加载独立 .env.{env} 文件：

json
{
  "dev": "next dev -p 5000",
  "build:dev":  "dotenv -e .env.dev  next build && npm run copy:sw",
  "build:test": "dotenv -e .env.test next build && npm run copy:sw",
  "build:pre":  "dotenv -e .env.pre  next build && npm run copy:sw",
  "build:prod": "dotenv -e .env.prod next build && npm run copy:sw",
  "start": "next start"
}

dotenv -e .env.{env} 把对应环境变量注入到 process.env，CI 上按分支 / tag 选择执行哪条构建命令。.env.local 留给本地开发，避免覆盖远程配置。

环境分层：

环境文件用途
dev.env.dev本地 + 联调
test.env.test内部测试
pre.env.pre预发 / 回归
prod.env.prod正式环境

要点：

  • 敏感配置不进仓库，走 CI 平台 Secret 注入，运行时通过 process.env.XXX 读取。
  • 构建出的产物按环境打成不同 tag 的 Docker 镜像。
  • API baseURL、CDN 域名、埋点 KEY 都按环境隔离，避免 dev 流量打错日志系统。

2. Git Hooks 和提交规范 ​

.husky/commit-msg 在每次 commit 时跑 commitlint：

bash
npx --no -- commitlint --edit "$1"

.commitlintrc.json 强制 Conventional Commits：

json
{
  "extends": ["@commitlint/config-conventional"],
  "rules": {
    "type-enum": [2, "always", [
      "feat", "fix", "docs", "style",
      "refactor", "perf", "test", "build",
      "ci", "revert", "chore"
    ]]
  }
}

lint-staged 在 commit 阶段对暂存文件自动跑类型检查 + lint + 格式化：

json
{
  "**/*.{ts,tsx}": [
    "tsc --noEmit",
    "eslint --fix",
    "prettier --write"
  ],
  "**/*.{js,jsx}": [
    "eslint --fix",
    "prettier --write"
  ],
  "**/*.{json,md,html,css,scss}": [
    "prettier --write"
  ]
}

效果：

  1. 提交信息只能用 11 种 type（feat / fix / refactor / perf 等），便于生成 CHANGELOG。
  2. 提交前自动过 tsc --noEmit，明显类型错误进不了仓库。
  3. 格式化在本地跑完，CI 上不再花时间 lint 格式问题。

3. Docker 镜像 ​

Dockerfile 走“分层构建 + 固定版本”的套路：

dockerfile
FROM node:23.9.0

4. PM2 进程管理 ​

js
// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'member-web',
    script: './node_modules/next/dist/bin/next',
    args: ['start', '-p', '5000'],
    exec_mode: 'cluster',
    instances: 2,
    node_args: '--max-old-space-size=4096 --unhandled-rejections=strict',
    autorestart: true,
    watch: false,
    max_memory_restart: '4000M',
    env: {
      NODE_ENV: 'production',
      __NEXT_PRIVATE_MEMORY_LIMIT: '4096',
    },
  }],
}

关键配置：

  1. exec_mode: 'cluster' + instances: 2：Node 单线程事件循环，多核 CPU 必须用 cluster 模式才能吃满。instances 一般设为 CPU 核数 -1，留资源给系统和其他进程。
  2. --max-old-space-size=4096：限制 V8 堆内存，防止内存泄漏拖垮整台机器。
  3. max_memory_restart: '4000M'：进程超过 4GB 自动重启，配合 --max-old-space-size 能让内存泄漏场景自动恢复。
  4. autorestart: true + watch: false：崩溃自动拉起，但生产环境不监听文件变化。
  5. 端口分离：member-web 用 5000，member-mobile 用 3000，Nginx 反向代理对外。

面试追问 ​

Q：你们 CI/CD 用了什么平台？

A：项目主要是 Docker 镜像 + PM2 进程管理，配合公司内部的部署平台拉镜像。分支策略上 feature 分支各自构建 → 合并到主干后构建 pre → 灰度通过后构建 prod。多套 .env.{env} 文件对应不同环境，CI 阶段按分支决定加载哪套。

Q：多环境配置怎么管理？

A：每个环境一个 .env.{env} 文件，CI 平台按分支或 tag 加载。敏感配置（API 密钥、签名密钥）不进文件，走 CI 平台的 Secret 注入，运行时通过 process.env.XXX 读取。

Q：Docker 镜像怎么加速构建？

A：先 COPY package*.json 装包，最后 COPY 源码。这样依赖装好后改源码不会触发重装。生产镜像也可以做多阶段构建，把 devDependencies 剔除，最终镜像只包含 next + 生产依赖。

Q：PM2 cluster 模式 vs fork 模式怎么选？

A：Next.js Node 进程是单线程事件循环，多核 CPU 必须用 cluster 模式才能吃满。instances 一般设为 CPU 核数 -1 留给系统。--max-old-space-size 配合 max_memory_restart 可以让内存泄漏自动恢复。

Q：怎么保证镜像构建可复现？

A：基础镜像固定版本（node:23.9.0），pnpm 版本固定（10.12.1），pnpm-lock.yaml 进版本控制。CI 上如果 lockfile 没变，依赖安装结果是确定的；lockfile 变了才会重装。

Q：commitlint 的 type 怎么和版本发布挂钩？

A：Conventional Commits 的 type 决定版本号：feat 触发 minor，fix 触发 patch，BREAKING CHANGE 触发 major。CI 上 standard-version 或 release-please 会按 commit 自动生成 CHANGELOG 和版本号。

SSR、PWA 和移动端边界 ​

SSR ​

Next.js SSR 下要明确服务端能做什么、不能做什么，避免把浏览器 API 写到顶层或误用同步 API。

服务端能做：

  • 从 req.headers.cookie 读登录态，决定是否 SSR 用户相关首屏。
  • 从 req.headers 读语言、地区、邀请码、AB 分组。
  • 拉公共配置、站点信息、首页资源等可缓存数据。
  • 设置 Cache-Control 控制 HTML 缓存（登录用户私有内容通常 private, no-store）。

服务端不能做：

  • 访问 window、document、localStorage、浏览器事件。
  • 调用依赖这些 API 的库（指纹、设备摘要、富文本编辑器、行为校验、埋点 SDK）。
  • 在公共缓存里 SSR 用户私密数据（账户、余额、订单、认证信息）。

getServerSideProps 边界示例：

ts
export async function getServerSideProps(ctx) {
  const cookie = ctx.req.headers.cookie ?? ''
  const site = await fetchSiteConfig(ctx.locale)
  const token = readTokenFromCookie(cookie)

  const userBasic = token
    ? await fetchUserBasic(token).catch(() => null)
    : null

  return {
    props: { site, userBasic },
  }
}
  • 私密数据（userBasic）只走 SSR 透传，不进 __NEXT_DATA__ 的公共缓存。
  • 接口失败要降级到客户端拉取，而不是直接报错。

Hydration 不一致：

服务端和客户端在以下情况会渲染出不同内容：

  1. new Date()、Math.random() 在两端调用产生不同结果。
  2. 直接读 localStorage / window.__xxx。
  3. 时间格式化和时区在 SSR 渲染不一致。

解决方式：

  1. 时间格式化放到客户端 useEffect。
  2. 随机 ID 在客户端生成或固定成 SSR 阶段。
  3. 用户态数据交给客户端拉取，服务端只负责占位和骨架。
  4. 浏览器专属模块用 dynamic(() => import(...), { ssr: false })。
tsx
import dynamic from "next/dynamic"

const RichEditor = dynamic(() => import("@/components/RichEditor"), { ssr: false })
const Fingerprint = dynamic(() => import("@/utils/fingerprint"), { ssr: false })

function ProfilePanel() {
  const [full, setFull] = useState(null)
  useEffect(() => {
    fetchUserFull().then(setFull)
  }, [])
  if (!full) return <Skeleton />
  return <ProfileCard data={full} />
}

PWA ​

PWA 不是“离线 App”，是改善弱网和重复访问的资源缓存策略。会员平台里要严格区分“能缓存”和“不能缓存”。

能缓存：

  1. 静态资源（JS、CSS、字体、图片、Webpack runtime）。
  2. 应用图标、启动画面、离线兜底页。
  3. 部分公共配置（站点信息、语言字典）。
  4. 非敏感的页面壳（如会员中心非登录页、协议页）。

不能缓存：

  1. 余额、账户、交易记录。
  2. 登录态、Token、用户身份信息。
  3. 支付结果、订单状态、活动奖励记录。
  4. 任何包含私密字段的接口响应。

没有“配置菜单”，区分靠三个信号：

  1. URL 前缀正则：按业务分类（静态 / 敏感 / 公共配置）。
  2. HTTP method：非 GET 一律不缓存。
  3. request.destination：浏览器告诉你的资源类型（script/style/image/font/fetch/document）。
ts
// ===== sw.js 第一段：分类与路由 =====

// 给缓存起名带版本号，发新版本时 VERSION 改一下，activate 阶段会自动清掉旧缓存
const VERSION = "v1.2.0"
const STATIC_CACHE = `static-${VERSION}`   // 静态资源缓存
const SHELL_CACHE  = `shell-${VERSION}`    // 页面壳缓存
const CONFIG_CACHE = `config-${VERSION}`   // 公共配置缓存

// 静态资源：文件名带 hash（Next.js / Webpack 自动加），所以可以永久缓存
// 正则里 \b 表示单词结束，避免 /api/account 误匹配 /api/accounting
const STATIC_PATTERNS = [
  /^\/_next\/static\//,    // Next.js 编译产物目录
  /^\/static\//,           // 项目 /public/static 目录
  /^\/icons\//,            // 应用图标
  /^\/fonts\//,            // 字体文件
  /\.(?:js|css|woff2?|ttf|svg|png|jpg|jpeg|webp|ico)$/,  // 扩展名兜底
]

// 敏感接口：余额、账户、订单、支付、认证
const SENSITIVE_PATTERNS = [
  /^\/api\/auth\//,
  /^\/api\/account\b/,
  /^\/api\/balance\b/,
  /^\/api\/order/,
  /^\/api\/pay/,
  /^\/api\/wallet/,
  /^\/api\/token/,
  /^\/api\/risk/,
]

// 公共配置：站点信息、语言字典这种低频可缓存的
const CONFIG_PATTERNS = [
  /^\/api\/site\/config\b/,
  /^\/api\/i18n\//,
  /^\/api\/public\//,
]

// 路由函数：根据 URL 和 method 决定走哪种缓存策略
function classifyRequest(req) {
  // new URL(req.url) 把字符串解析成 URL 对象，方便取 pathname / search 等
  const url = new URL(req.url)

  // 非 GET 请求一律不缓存：POST/PUT/DELETE 会改服务端状态
  if (req.method !== "GET") return "networkOnly"

  // 敏感接口：网络优先
  // .some(re => re.test(url.pathname)) 检查 pathname 是否命中任一正则
  if (SENSITIVE_PATTERNS.some((re) => re.test(url.pathname))) {
    return "networkFirst"
  }

  // 公共配置：过期再重新拉
  if (CONFIG_PATTERNS.some((re) => re.test(url.pathname))) {
    return "staleWhileRevalidateConfig"
  }

  // 静态资源：缓存优先
  // req.destination 是浏览器告诉你的资源类型，常见值：
  //   "document"  HTML 页面
  //   "script"    JS
  //   "style"     CSS
  //   "image"     图片
  //   "font"      字体
  //   "fetch"     fetch / XHR 请求
  if (
    req.destination === "script" ||
    req.destination === "style" ||
    req.destination === "image" ||
    req.destination === "font" ||
    STATIC_PATTERNS.some((re) => re.test(url.pathname))
  ) {
    return "cacheFirst"
  }

  // 页面导航：req.mode === "navigate" 表示用户主动打开页面
  // 带登录态 Cookie 的走 networkFirst，不带的（公开页）走 SWR
  if (req.mode === "navigate") {
    return hasAuthCookie(req) ? "networkFirst" : "staleWhileRevalidate"
  }

  // 默认兜底
  return "networkFirst"
}

// 判断请求是否带登录 Cookie
function hasAuthCookie(req) {
  // req.headers.get("cookie") 取请求头里的 Cookie 字符串
  // 正则 /(^|;\s)(token|session)=/  匹配 token=xxx 或 session=xxx
  // ?? 是空值合并运算符，左边 null/undefined 时返回右边
  return /(^|;\s)(token|session)=/.test(req.headers.get("cookie") ?? "")
}
ts
// ===== sw.js 第二段：各种策略的实现 =====

const STRATEGIES = {
  // 缓存优先：先返回缓存，缓存没有再走网络
  // 适合：静态资源、文件名带 hash 的资源
  // async 声明这是异步函数，里面可以用 await
  cacheFirst: async (req) => {
    // caches.match(req) 在所有缓存里查找匹配 req 的 Response
    // 找到就返回，没找到返回 null
    const cached = await caches.match(req)
    if (cached) return cached  // 有缓存直接返回

    // 没缓存，去网络请求
    const fresh = await fetch(req)
    // fetch(req) 发起网络请求，返回 Promise<Response>

    // 只缓存成功的响应（状态码 200-299）
    if (fresh.ok) {
      const cache = await caches.open(STATIC_CACHE)
      // caches.open(name) 打开指定名字的缓存，返回 Cache 对象

      // fresh.clone() 因为 Response body 只能读一次，
      // 要同时返回给用户和存进缓存，必须先 clone 一份
      await cache.put(req, fresh.clone())
      // cache.put(req, res) 把“请求和响应”作为一对存进缓存
    }

    return fresh  // 把网络响应返回给页面
  },

  // 网络优先：先请求网络，失败才用缓存
  // 适合：敏感接口、已登录页面
  networkFirst: async (req) => {
    try {
      // try/catch 捕获网络异常（断网、超时、DNS 失败等）
      return await fetch(req)
    } catch {
      // catch 块里处理异常
      const cached = await caches.match(req)
      // Response.error() 返回一个网络错误的 Response
      return cached ?? Response.error()
    }
  },

  // 后台重新验证：先返回缓存（如果有），同时后台请求网络更新缓存
  // 适合：页面壳
  staleWhileRevalidate: async (req) => {
    const cache = await caches.open(SHELL_CACHE)
    const cached = await cache.match(req)
    // 立刻开始后台请求，不阻塞当前返回
    const freshPromise = fetch(req).then((res) => {
      // .then() 是 Promise 成功回调，res 就是 fetch 的结果
      if (res.ok) cache.put(req, res.clone())
      return res
    })
    return cached ?? freshPromise
  },

  // 带过期时间的 SWR：适合公共配置
  staleWhileRevalidateConfig: async (req) => {
    const cache = await caches.open(CONFIG_CACHE)
    const cached = await cache.match(req)

    if (cached) {
      // 从自定义响应头里读缓存时间
      const dateHeader = cached.headers.get("sw-cached-at")
      // Number("123") 把字符串转成数字
      const age = Date.now() - Number(dateHeader ?? 0)
      // Date.now() 返回当前时间戳（毫秒）

      // 30 分钟内：返回缓存 + 后台刷新
      if (age < 30 * 60 * 1000) {
        // 后台刷新但不阻塞返回
        fetch(req).then((res) => res.ok && cache.put(req, res.clone()))
        return cached
      }
      // 超过 30 分钟：走到下面 await fetch 重新拉
    }

    const fresh = await fetch(req)
    // 复制一份原响应的二进制数据
    const body = await fresh.clone().blob()
    // .blob() 把 Response body 转成二进制大对象

    // 构造新响应加一个 sw-cached-at 自定义头
    const tagged = new Response(body, {
      status: fresh.status,
      headers: {
        // Object.fromEntries 把可迭代对象转成普通对象
        // ...obj 是展开运算符，把对象的所有属性平铺出来
        ...Object.fromEntries(fresh.headers),
        // String(num) 把数字转成字符串，因为 HTTP 头都是字符串
        "sw-cached-at": String(Date.now()),
      },
    })
    cache.put(req, tagged.clone())
    return tagged
  },

  // 仅网络：完全不走缓存
  networkOnly: (req) => fetch(req),
}

// ===== 5. 拦截 fetch 事件 =====

self.addEventListener("fetch", (event) => {
  // event.request 是当前被拦截的请求对象
  const strategyName = classifyRequest(event.request)
  // STRATEGIES[strategyName] 从对象里取出对应策略函数
  const strategy = STRATEGIES[strategyName]

  if (strategy) {
    // event.respondWith(promise) 让 SW 返回的 Response 替代网络响应
    // 必须传 Promise，所以策略函数都是 async
    event.respondWith(strategy(event.request))
  }
})

面试口径：

Service Worker 没有配置菜单，是一段 JS。区分缓存策略靠的是三个信号：URL 前缀正则、HTTP method、request.destination。我会按业务把路径分成三类：静态资源（/_next/static/、hash 文件名）走 Cache First，敏感接口（账户、余额、订单、支付、token）走 Network First，公共配置（站点信息、语言字典）走 Stale While Revalidate 再加个过期时间。所有非 GET、带鉴权 Cookie 的请求默认不碰缓存。

移动端 ​

移动端的难点不在响应式布局，而在输入体验、容器环境和跳转差异。

1. 安全区适配

iPhone X 以上和带虚拟导航条的 Android 都有底部安全区：

css
.page {
  padding-bottom: calc(env(safe-area-inset-bottom) + 16px);
}

.fixed-bottom-bar {
  padding-bottom: max(env(safe-area-inset-bottom), 16px);
}

顶部刘海和挖孔用 env(safe-area-inset-top)，底部 home indicator 用 env(safe-area-inset-bottom)。

2. 软键盘遮挡

输入框聚焦时软键盘弹起会遮挡底部内容：

ts
function focusAndScrollIntoView(el: HTMLElement) {
  el.scrollIntoView({ block: "center", behavior: "smooth" })
}

input.addEventListener("focus", () => {
  setTimeout(() => focusAndScrollIntoView(input), 300)
})

表单提交完成后手动收起键盘：

ts
input.blur()
// 或 document.activeElement?.blur()

iOS 上 position: fixed 的元素在软键盘弹起时会跳变，建议表单底部按钮改成 absolute 或跟随滚动布局。

3. 弹层滚动穿透

弹层打开时禁止 body 滚动：

ts
function lockBodyScroll() {
  const scrollY = window.scrollY
  document.body.style.position = "fixed"
  document.body.style.top = `-${scrollY}px`
  document.body.style.width = "100%"
}

function unlockBodyScroll() {
  const scrollY = Math.abs(parseInt(document.body.style.top || "0", 10))
  document.body.style.position = ""
  document.body.style.top = ""
  document.body.style.width = ""
  window.scrollTo(0, scrollY)
}

更简单的方案是在 body 加 overflow: hidden，但 iOS 上有时仍可滚动，需要配合 position: fixed 兜底。

4. WebView 返回前台

H5 在 App WebView 中可能被推到后台，App 在期间更新了登录态、语言、主题：

ts
function handleVisible() {
  if (document.visibilityState !== "visible") return
  void refreshUserInfo()
  syncLanguage()
  syncTheme()
}

document.addEventListener("visibilitychange", handleVisible)

页面进入时也要执行一次，确保拿到最新状态。

5. 按钮防重复点击

按钮短时间内被多次点击会触发多个请求：

ts
function useDebouncedClick(handler: () => void, delay = 500) {
  const [busy, setBusy] = useState(false)
  return async () => {
    if (busy) return
    setBusy(true)
    try {
      await handler()
    } finally {
      setTimeout(() => setBusy(false), delay)
    }
  }
}

支付、提交、领取这类按钮必须做防重，loading 状态和禁用同时使用，避免用户感觉“卡了"再点几次。

6. 弱网和接口超时

ts
async function fetchWithTimeout(
  url: string,
  options: RequestInit,
  timeout = 15000
) {
  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), timeout)
  try {
    return await fetch(url, { ...options, signal: controller.signal })
  } finally {
    clearTimeout(timer)
  }
}

超时后要兜底：

  1. 不阻塞其他模块的渲染。
  2. 给用户明确提示（“网络异常，请重试”）。
  3. 关键操作（支付、提交）失败要保留输入内容，允许重试。

7. H5 和普通浏览器跳转差异

  • H5 在 WebView 内点击外链要询问是否跳转，避免直接跳走丢失 WebView 状态。
  • 唤起其他 App（电话、短信、地图）要通过 App 桥接，普通浏览器用 tel: mailto: 协议。
  • 第三方登录弹窗在 WebView 内可能被拦截，需要提前告知用户或改用 App 原生登录。

面试追问 ​

面试追问 ​

Q：为什么 Web 和 H5 不做成一套页面？

A：业务数据和基础能力可以复用，但布局、信息密度、弹层、手势、输入和 WebView 行为差异很大。强行复用页面会牺牲体验，所以采用“逻辑复用、交互分端”。

Q：App 通信最容易出什么问题？

A：普通浏览器或 SSR 环境没有原生对象，WebView 返回前台时 Cookie / 语言状态可能刚注入，另外页面跳转和原生页面跳转也可能不一致。因此通信层需要环境判断、异常捕获、状态重新同步和浏览器降级。

Q：富文本过滤后为什么还需要后端校验？

A：前端过滤主要保护当前页面展示，不能防止绕过前端直接调用接口提交恶意内容。内容保存、输出和权限都必须由后端校验。

Q：如果多个接口同时触发验证挑战怎么办？

A：使用单例验证管理器维护等待队列，只打开一个全局验证组件。验证成功后把临时凭证分发给等待请求，各请求只允许重试一次，避免重复弹窗和无限重试。

Q：为什么页面从 App 返回后还要重新请求？

A：App 可能在 H5 不可见期间更新了登录态、语言或主题，Cookie 注入也可能晚于页面初始化。通过 visibilitychange 重新同步，可以减少页面展示旧状态的问题。

Q：前端加密能不能防止接口被调用？

A：不能。前端加密主要是约定的参数保护，代码和配置在客户端都可能被分析。真正的安全依赖 HTTPS、服务端解密校验、权限控制、Token 生命周期和风控策略。

Q：三方登录为什么要监听弹窗关闭和超时？

A：用户可能主动关闭授权页，授权服务也可能没有正常回调。如果没有关闭检测和超时，Promise 会一直挂起，页面 loading 也不会结束，所以必须统一清理并返回明确状态。
