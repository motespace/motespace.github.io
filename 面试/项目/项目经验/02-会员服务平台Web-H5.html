会员服务平台 Web / H5 ​

项目概览 ​

时间：2024.08 - 2026.08
角色：前端核心开发
技术栈：Next.js、React、TypeScript、Ant Design（Web）、antd-mobile / HeroUI（H5）、SSR、PWA、FingerprintJS、jsencrypt、isomorphic-dompurify

这是一个面向 C 端用户的 Web / H5 会员服务平台，覆盖登录注册、业务产品入口、权益活动、账户中心、会员中心、协议和帮助中心。Web 和 H5 分端建设，H5 支持 App WebView 内嵌。

面试时可以这样概括：

这个项目的难点不在页面，而在"两端复用 + 安全链路 + 弱网体验"。Web 和 H5 在业务逻辑层共用一套，但交互、组件、安全栈完全不同；登录认证涉及验证码、三方登录、设备指纹、行为校验多个能力，还要保证 XSS、iframe 注入、Token 泄露这些安全边界。

Web / H5 如何拆分 ​

业务逻辑尽量复用，交互和布局按端实现。

复用部分：

  • 接口类型和统一请求层。
  • 登录态、用户信息、语言、主题等全局状态。
  • 枚举、金额格式化、时间处理和安全展示。
  • 活动、账户中心和会员资料的业务数据结构。

分开部分：

  • Web 使用桌面端布局和完整会员中心。
  • H5 使用移动端布局、底部导航、移动弹层和安全区适配。
  • Web 和 H5 使用不同的交互组件，避免强行复用导致体验下降。

技术实现 ​

1. App 内嵌 H5 通信 ​

通信层负责 WebView 检测、消息序列化和浏览器降级，页面只调用业务方法。

  1. 判断 App 是否注入原生 channel。
  2. H5 通过 postMessage 发送导航和页面状态消息。
  3. 页面标题使用独立的标题 channel 通知 App。
  4. 普通浏览器环境回退到 document.title 和 H5 路由。
  5. App 返回 H5 后通过 visibilitychange 重新同步语言、主题和登录状态。
ts
type BridgeMessage =
  | { type: 'NAVIGATE'; payload: { path: string } }
  | { type: 'PAGE_STATE'; payload: { visible: boolean } }

declare global {
  interface Window {
    nativeBridge?: { postMessage(message: string): void }
    titleBridge?: { postMessage(message: string): void }
  }
}

function isWebView() {
  return typeof window !== 'undefined' && Boolean(window.nativeBridge)
}

function sendToApp(message: BridgeMessage) {
  if (!isWebView()) return false

  try {
    window.nativeBridge!.postMessage(JSON.stringify(message))
    return true
  } catch {
    return false
  }
}

export const appBridge = {
  setTitle(title: string) {
    if (isWebView()) {
      window.titleBridge?.postMessage(title)
    } else {
      document.title = title
    }
  },

  navigate(path: string) {
    if (!sendToApp({ type: 'NAVIGATE', payload: { path } })) {
      window.location.assign(path)
    }
  },
}

上面的 channel 名、消息类型和字段均为泛化示例。当前项目主要是 H5 向 App 的单向通知，登录态和语言主要通过 Cookie、store 及后端校验完成，不应说成所有状态都通过 postMessage 双向传输。

2. 登录态初始化和 Token 生命周期 ​

页面加载时：

  1. 从 Cookie / store 读取已有登录态。
  2. 调用后端接口校验 Token。
  3. 校验成功后刷新用户信息、语言、主题和展示环境。
  4. 校验失败时清理 Cookie、store 和页面敏感数据。
  5. 接口返回登录失效时只触发一次清理和跳转。
ts
async function bootstrapAuth() {
  const token = readTokenFromCookie()

  if (!token) {
    clearUserState()
    return false
  }

  const valid = await verifyToken(token)
  if (!valid) {
    clearUserState()
    redirectToLogin()
    return false
  }

  setToken(token)
  await refreshUserInfo()
  return true
}

前端负责登录态编排和页面状态同步，Token 有效性、权限和敏感操作必须由后端最终校验。

3. 设备指纹（FingerprintJS）—— 真实代码 ​

设备指纹是会员体系反垃圾注册、风控前置的核心能力。SSR 项目里不能直接 import FingerprintJS，否则服务端打包会报错。下面是真实落地代码：

ts
// 真实代码片段：member-h5/src/utils/fingerprint/index.ts
import { isBrowser } from '@/utils/common'
import { getItem, setItem } from '../storage'
import { StorageEnum, StorageTypeEnum } from '#/enum'

let fpPromise: ReturnType<typeof import('@fingerprintjs/fingerprintjs').default.load> | null = null
let cachedVisitorId: string | null = null

function loadAgent() {
  if (!fpPromise) {
    // 关键：用动态 import 而不是静态 import，SSR 不会执行到这一行
    fpPromise = import('@fingerprintjs/fingerprintjs').then(({ default: FingerprintJS }) =>
      FingerprintJS.load(),
    )
  }
  return fpPromise
}

export async function getVisitorId(): Promise<string | null> {
  if (!isBrowser()) return null

  // 关键：模块级缓存，第二次调用直接返回
  if (cachedVisitorId) return cachedVisitorId

  try {
    const stored = getItem(StorageEnum.FpVisitorId) as string
    if (stored) {
      cachedVisitorId = stored
      return stored
    }
  } catch {
    // 备注：private mode 下 localStorage 可能抛错，不能让指纹失败阻塞主流程
  }

  try {
    const agent = await loadAgent()
    const result = await agent.get()
    cachedVisitorId = result.visitorId

    try {
      setItem(StorageEnum.FpVisitorId, result.visitorId, StorageTypeEnum.LocalStorage)
    } catch {
      /* ignore */
    }

    return result.visitorId
  } catch (e) {
    // 备注：失败只 warn，不抛异常——指纹是辅助能力，不能因为指纹失败让页面无法访问
    console.warn('[fingerprint] load failed', e)
    return null
  }
}

export function preloadFingerprint() {
  if (!isBrowser()) return
  void getVisitorId()  // 预加载：在登录页挂载时调用，把耗时操作前置
}

export function getCachedVisitorId(): string | null {
  return cachedVisitorId
}

设计要点：

  • 动态 import：FingerprintJS 内部依赖 window、navigator，SSR 直接 import 会打包失败或运行时报错。import('@fingerprintjs/fingerprintjs') 在浏览器环境才加载。
  • 模块级 promise 缓存：避免每次调用都重新 load agent（loadAgent 内部要做很多 canvas 探测）。
  • 三层缓存：内存变量 → localStorage → FingerprintJS。已登录用户切页面不应该再算一次指纹。
  • 失败容错：指纹是辅助字段，注册失败不应该阻塞页面访问。
  • 预加载：在用户打开登录页时调用 preloadFingerprint，登录提交时已经算好了，省一次等待。

4. 三方登录（Google / Facebook）—— 真实代码 ​

三方登录的关键是：结果回调必须能拿到，而不能依赖 popup 主动 postMessage（用户可能关掉 popup、浏览器可能拦截、网络可能断）。下面的真实代码用了 postMessage + localStorage 双通道 + 定时轮询关闭 + 超时兜底 的组合方案：

ts
// 真实代码片段：member-h5/src/utils/thirdAuth.ts
const TIMEOUT = 60 * 1000
const STORAGE_KEY = 'third:auth:message'

export function auth(
  provider: 'gg' | 'fb',
  infos: Partial<MemberRegDto> = {},
): Promise<{ token: string }> {
  if (!isBrowser()) return Promise.reject(new Error('Not a window environment'))

  return new Promise((resolve, reject) => {
    let finished = false
    let closeTimer: ReturnType<typeof setInterval> | null = null
    let timeoutTimer: ReturnType<typeof setTimeout> | null = null

    const popup = window.open('about:blank', `thirdAuthWindow`, `top=0,left=0`)
    if (!popup) {
      reject(new Error('Pop-up window blocked'))
      return
    }

    // ──────── 通道 1：postMessage（同源回调）────────
    function handlePostMessage(event: MessageEvent) {
      // 关键：必须校验 origin，防止恶意页面伪造回调
      if (event.origin !== window.location.origin) return

      const { type, payload } = event.data || {}
      if (type === 'third:auth:success') {
        done({ ...payload, token: payload?.token })
      } else if (type === 'third:auth:duplicate:email') {
        // 关键：邮箱重复也要 resolve，让上层决定是走绑定流程
        done({ ...payload, token: payload?.token })
      } else if (type === 'third:auth:error') {
        fail(payload?.errorCode || 'Auth failed')
      }
    }

    // ──────── 通道 2：localStorage（postMessage 失败降级）────────
    function handleStorage(event: StorageEvent) {
      if (event.key !== STORAGE_KEY) return
      if (!event.newValue) return
      try {
        const { data } = JSON.parse(event.newValue)
        localStorage.removeItem(STORAGE_KEY)  // 关键：一次性消息，读完即删
        const { type, payload } = data || {}
        if (type === 'third:auth:success') done({ ...payload, token: payload?.token })
        else if (type === 'third:auth:duplicate:email') done({ ...payload, token: payload?.token })
        else if (type === 'third:auth:error') fail(payload?.errorCode || 'Auth failed')
      } catch (err) { console.error('Failed to parse storage message', err) }
    }

    const cleanup = () => {
      if (closeTimer) clearInterval(closeTimer)
      if (timeoutTimer) clearTimeout(timeoutTimer)
      window.removeEventListener('message', handlePostMessage)
      window.removeEventListener('storage', handleStorage)
    }

    const done = (params: any) => {
      if (finished) return   // 关键：幂等，保证只 resolve 一次
      finished = true
      cleanup()
      if (!popup.closed) popup.close()
      resolve(params)
    }

    const fail = (err: any) => {
      if (finished) return
      finished = true
      cleanup()
      if (!popup.closed) popup.close()
      reject(err)
    }

    window.addEventListener('message', handlePostMessage)
    window.addEventListener('storage', handleStorage)

    // 1. 前端先请求后端拿授权地址
    providerIns.loginUsingPost1(provider, infos)
      .then((res) => {
        if (!res) return fail('Failed to obtain authorization address')
        popup.location.replace(res)  // 拿到授权地址后再跳转 popup
      })
      .catch(fail)

    // 2. 关键：轮询检测 popup 关闭（用户主动关掉的情况）
    closeTimer = setInterval(() => {
      if (!finished && popup.closed) fail('User closes login window')
    }, 500)

    // 3. 关键：超时兜底（OAuth 服务挂了也不挂死页面）
    timeoutTimer = setTimeout(() => fail('Login timeout'), TIMEOUT)
  })
}

设计要点（这是面试常追问点）：

  • 三通道冗余：postMessage（同源回调）→ localStorage（同源跨窗口）→ close 轮询（用户主动关）。任何一条通道成功都能结束 Promise。
  • finished 幂等：success / duplicate / error 三个分支都可能触发，幂等保证只 resolve/reject 一次，避免后续 close 检测误判。
  • origin 校验：postMessage 不校验 origin 等于敞开大门，任何第三方 iframe 都能伪造回调。
  • popup.location.replace 而不是 window.open：先用空 popup 占位（避免被浏览器拦截），拿到授权地址后再 replace。
  • 轮询关闭：500ms 检测 popup.closed，用户关掉授权页能立即 fail，Promise 不会挂死。
  • 60s 超时：OAuth 服务挂掉时不会无限等待。
  • 邮箱重复特殊处理：三方登录注册时邮箱已被占用，不能 reject，要 resolve 让上层走"账号绑定"流程。

5. 验证码单例管理器（多请求并发只弹一次） ​

会员页面多个接口可能同时触发验证码挑战（如登录、注册、领奖、提现）。如果不收敛，前端会同时弹出多个验证码，体验崩溃。

ts
// 真实代码片段：member-h5/src/utils/captchaManager.ts
type TokenResolver = (token: string) => void

class CaptchaManager {
  private static instance: CaptchaManager    // 单例
  private resolverQueue: TokenResolver[] = []  // 等待队列
  private _show = false
  private listener?: (show: boolean) => void

  static getInstance() {
    if (!CaptchaManager.instance) CaptchaManager.instance = new CaptchaManager()
    return CaptchaManager.instance
  }

  subscribe(listener: (show: boolean) => void) { this.listener = listener }
  get show() { return this._show }

  private setShow(show: boolean) {
    this._show = show
    this.listener?.(show)   // 通知 UI 组件显示 / 隐藏
  }

  public requestToken(): Promise<string> {
    this.setShow(true)
    return new Promise((resolve) => {
      this.resolverQueue.push(resolve)  // 关键：所有请求排队等待同一个 token
    })
  }

  public resolveToken(token: string) {
    this.setShow(false)
    this.resolverQueue.forEach((r) => r(token))  // 一次 resolve 所有等待请求
    this.resolverQueue = []
  }

  public reject() {
    // 关键：失败不清空队列，用户可以重试验证
  }
}

export const captchaManager = CaptchaManager.getInstance()

设计要点：

  • 单例 + 队列：保证全局只有一个验证码弹窗；多个并发请求排队等待同一个 token。
  • subscribe 模式：UI 组件订阅 show 状态变化，避免组件之间互相引用。
  • reject 不清队列：用户验证失败时不清空队列，UI 关闭后再请求可以重新弹出。
  • resolveToken 广播给所有等待者：三个并发请求只需要用户验一次。

6. iframe URL 校验（真实代码） ​

会员活动里经常嵌入支付 / 第三方 iframe。iframe 是常见的安全漏洞来源（点击劫持、跨域通信泄漏）。

ts
// 真实代码片段：member-h5/src/utils/assertAllowedIframeUrl.ts
const NON_PROD = process.env.NEXT_PUBLIC_ENV !== 'prod'

/** 支付 / 外链 iframe：只允许 http(s)，非法协议返回 null */
export function assertAllowedIframeUrl(raw?: string | null): URL | null {
  if (!raw) return null

  let parsed: URL
  try {
    parsed = new URL(raw)
  } catch {
    // 备注：相对路径要拼接 origin 后再解析
    try {
      if (typeof window === 'undefined') return null
      parsed = new URL(raw, window.location.origin)
    } catch {
      return null  // 解析失败直接拒绝
    }
  }

  const protocolOk = parsed.protocol === 'https:' || (NON_PROD && parsed.protocol === 'http:')
  // 关键：拒绝带 username/password 的 URL（可能用于钓鱼）
  if (!protocolOk || !parsed.hostname || parsed.username || parsed.password) {
    return null
  }
  return parsed
}

export function isAllowedIframeMessageOrigin(origin: string, allowedUrl: URL | null): boolean {
  if (!origin || !allowedUrl) return false
  return origin === allowedUrl.origin  // postMessage 必须校验 origin
}

设计要点：

  • 协议白名单：非生产环境允许 http（本地调试），生产只允许 https。
  • 拒绝带 username/password 的 URL：https://evil@bank.com/... 这种 URL 在浏览器地址栏只显示 bank.com，但实际指向 evil 域名，是钓鱼常用手法。
  • origin 严格比对：iframe postMessage 用 === 而不用 includes，避免 origin="https://evil-bank.com.attacker.com" 这种绕过。
  • SSR 安全：typeof window === 'undefined' 时返回 null，相对路径不会在服务端解析。

8. 敏感请求加密（RSA + AES） ​

登录密码、支付密码这类敏感字段，前端用 RSA 公钥加密密码 + AES 加密业务 body 组合：

  • 密码：RSA 公钥加密（防代码被分析后还原密码明文）。
  • 业务 body：AES 加密（性能比 RSA 好，避免大 body 加密太慢）。
  • 后端配合：HTTPS + nonce / 时间戳防重放。

注：前端加密是"约定层"防护，代码和密钥在客户端都能被分析。真正的安全依赖 HTTPS、后端解密校验、Token 生命周期和风控策略。

9.1 国际化 ​

  • 菜单 / 路由：登录后根据 I18n 拉对应语言的菜单。
  • 业务文案：i18next + JSON 词条，按 namespace 拆分（common / auth / activity / payment）。
  • 运行时切换：用 i18next 的 language 检测器，SSR 通过 cookie 拿到语言，浏览器切换时只更新 store。

9.2 主题切换 ​

  • CSS 变量：用 :root 的 CSS 变量定义色板，light / dark 切换只改 data-theme 属性。
  • 图标策略：夜间模式用 darkIconUrl，避免单个图标做多套。

9.3 PWA 离线缓存 ​

  • Service Worker：next-pwa 自动注入，缓存壳页面（layout、icon、首页骨架）。
  • 静态资源：JS / CSS / 图片走 Workbox 缓存策略。
  • 接口缓存：列表类接口走 stale-while-revalidate，详情类走 network-first。
  • 关键限制：支付、提交类接口必须 network-first，否则用户支付完成看到旧的成功页。

按钮短时间内被多次点击会触发多个请求：

ts
function useDebouncedClick(handler: () => void, delay = 500) {
  const [busy, setBusy] = useState(false)
  return async () => {
    if (busy) return
    setBusy(true)
    try {
      await handler()
    } finally {
      setTimeout(() => setBusy(false), delay)
    }
  }
}

支付、提交、领取这类按钮必须做防重，loading 状态和禁用同时使用，避免用户感觉"卡了"再点几次。

6. 弱网和接口超时

ts
async function fetchWithTimeout(
  url: string,
  options: RequestInit,
  timeout = 15000
) {
  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), timeout)
  try {
    return await fetch(url, { ...options, signal: controller.signal })

超时后要兜底：

  1. 不阻塞其他模块的渲染。
  2. 给用户明确提示（"网络异常，请重试"）。
  3. 关键操作（支付、提交）失败要保留输入内容，允许重试。

7. H5 和普通浏览器跳转差异

  • H5 在 WebView 内点击外链要询问是否跳转，避免直接跳走丢失 WebView 状态。
  • 唤起其他 App（电话、短信、地图）要通过 App 桥接，普通浏览器用 tel: mailto: 协议。
  • 第三方登录弹窗在 WebView 内可能被拦截，需要提前告知用户或改用 App 原生登录。

面试追问 ​

Q：为什么 Web 和 H5 不做成一套页面？

A：业务数据和基础能力可以复用，但布局、信息密度、弹层、手势、输入和 WebView 行为差异很大。强行复用页面会牺牲体验，所以采用"逻辑复用、交互分端"。

Q：App 通信最容易出什么问题？

A：普通浏览器或 SSR 环境没有原生对象，WebView 返回前台时 Cookie / 语言状态可能刚注入，另外页面跳转和原生页面跳转也可能不一致。因此通信层需要环境判断、异常捕获、状态重新同步和浏览器降级。

Q：富文本过滤后为什么还需要后端校验？

A：前端过滤主要保护当前页面展示，不能防止绕过前端直接调用接口提交恶意内容。内容保存、输出和权限都必须由后端校验。

Q：如果多个接口同时触发验证挑战怎么办？

A：使用单例验证管理器维护等待队列，只打开一个全局验证组件。验证成功后把临时凭证分发给等待请求，各请求只允许重试一次，避免重复弹窗和无限重试。

Q：为什么页面从 App 返回后还要重新请求？

A：App 可能在 H5 不可见期间更新了登录态、语言或主题，Cookie 注入也可能晚于页面初始化。通过 visibilitychange 重新同步，可以减少页面展示旧状态的问题。

Q：前端加密能不能防止接口被调用？

A：不能。前端加密主要是约定的参数保护，代码和配置在客户端都可能被分析。真正的安全依赖 HTTPS、服务端解密校验、权限控制、Token 生命周期和风控策略。

Q：三方登录为什么要监听弹窗关闭和超时？

A：用户可能主动关闭授权页，授权服务也可能没有正常回调。如果没有关闭检测和超时，Promise 会一直挂起，页面 loading 也不会结束，所以必须统一清理并返回明确状态。

Q：三方登录为什么用 postMessage + localStorage 双通道？

A：postMessage 在跨域或某些 WebView 内可能被吞掉；localStorage 在同源跨窗口场景下能作为降级通道。两者结合能保证任意一条通道拿到结果都能正确 resolve Promise。

Q：设备指纹失败会影响登录吗？

A：不会。指纹是辅助字段，用于风控识别同一设备。失败时只 warn 不抛异常，用户依然可以正常登录 / 注册，只是后端少了辅助判断依据。

Q：SSR 项目里用 FingerprintJS 怎么避免报错？

A：用动态 import（import('@fingerprintjs/fingerprintjs')）而不是静态 import。静态 import 会把 FingerprintJS 打进服务端 bundle，运行时报 window is not defined。动态 import 在浏览器环境才真正加载。

Q：iframe URL 校验为什么拒绝带 username/password 的 URL？

A：https://evil@bank.com 这种 URL 在浏览器地址栏只显示 bank.com，但实际指向 evil 域名，是经典钓鱼手法。前端解析 URL 后要检查 parsed.username 和 parsed.password 是否为空。

Q：邮箱已经被其他账号注册了，三方登录怎么处理？

A：不 reject 当作失败，单独用一个业务码（如 duplicate:email）resolve 让前端走"账号绑定 / 合并"流程。直接失败会让用户体验断裂，明明输对了密码却被告知失败。
