商户管理 SaaS 平台 ​

项目概览 ​

时间：2024.08 - 2026.08
角色：前端核心开发
技术栈：Next.js、React、TypeScript、Ant Design、Zustand

这是一个面向运营团队和合作方的 B 端管理后台，覆盖渠道与合作方管理、用户运营、内容配置、账户服务、交易审核和风险管理。

面试时可以这样概括：

这是一个模块较多的运营管理 SaaS。我的主要工作不是只完成页面，而是把高频后台模式抽成可复用能力，同时通过接口契约和统一请求层降低联调及维护成本。

我负责的内容 ​

  1. 负责渠道运营、用户管理、活动配置、账户服务、交易审核和合作方风险管理等模块。
  2. 沉淀可配置表格、搜索表单、弹窗 / 抽屉表单、权限操作、上传、金额输入和多语言字段组件。
  3. 基于后端接口契约生成类型与请求方法，再通过统一请求层处理 Token、错误码、多环境和重复请求。
  4. 支持中英双语，覆盖菜单、表单校验、枚举值和运营配置内容。
  5. 配合产品、后端和测试处理状态流转、权限边界、接口变更及线上问题。

业务页面模式 ​

大部分页面可以拆成稳定的后台结构：

  1. 搜索区：关键词、状态、时间范围、类型和业务归属等筛选条件。
  2. 操作区：新增、批量处理、导入导出、刷新和列配置。
  3. 表格区：分页、排序、状态标签、长文本、省略和金额格式化。
  4. 行操作：查看、编辑、审核、禁用、日志和更多操作。
  5. 表单弹窗：新增、编辑、审核共用表单基础能力，但根据业务状态控制字段是否可编辑。
  6. 详情抽屉：展示用户资料、审核记录、执行记录和操作日志。

技术实现 ​

1. 可配置表格和搜索表单 ​

把表格列、搜索项和操作项抽成配置，页面只负责传入数据源、字段配置和业务回调。

tsx
type ColumnConfig<T> = {
  key: keyof T
  title: string
  render?: (value: T[keyof T], row: T) => React.ReactNode
}

type SearchField = {
  name: string
  label: string
  type: 'text' | 'select' | 'dateRange'
  options?: Array<{ label: string; value: string }>
}

function BusinessList<T>({
  columns,
  searchFields,
  fetchData,
}: {
  columns: ColumnConfig<T>[]
  searchFields: SearchField[]
  fetchData: (params: Record<string, unknown>) => Promise<T[]>
}) {
  // 真实项目中这里还会处理分页、loading、错误提示和请求取消。
  return null
}

抽象时没有做“万能页面组件”。表格、搜索、权限按钮这类稳定能力通用化；审核流程、风险规则等差异大的业务保留独立组件。

2. 权限控制 ​

权限分为三层：

  1. 路由层：根据用户角色和菜单权限生成可访问路由。
  2. 页面层：没有权限时展示无权限状态或跳转到兜底页面。
  3. 操作层：按钮、操作列和批量操作根据权限码控制显示。
tsx
function PermissionButton({
  code,
  children,
  onClick,
}: {
  code: string
  children: React.ReactNode
  onClick: () => void
}) {
  const permissions = usePermissionStore((state) => state.codes)
  if (!permissions.includes(code)) return null

  return <button onClick={onClick}>{children}</button>
}

面试时要补充：前端权限只负责入口展示和用户体验，后端仍然必须校验数据权限和操作权限。

3. 接口契约和统一请求层 ​

接口协作链路：

  1. 后端维护接口契约。
  2. 前端根据契约生成类型和请求方法。
  3. 统一请求层注入登录态、环境信息和通用请求头。
  4. 统一处理业务成功 / 失败、登录失效、重复请求、文件下载和错误提示。
  5. 页面只关注业务参数和返回数据。
ts
type RequestOptions = {
  path: string
  method?: 'GET' | 'POST'
  body?: unknown
  cancelKey?: string
}

const pending = new Map<string, AbortController>()

async function request<T>(options: RequestOptions): Promise<T> {
  const controller = new AbortController()

  if (options.cancelKey) {
    pending.get(options.cancelKey)?.abort()
    pending.set(options.cancelKey, controller)
  }

  try {
    const response = await fetch(`/api${options.path}`, {
      method: options.method || 'GET',
      credentials: 'include',
      signal: controller.signal,
      headers: {
        'Content-Type': 'application/json',
        Authorization: getToken() ? `Bearer ${getToken()}` : '',
      },
      body: options.body ? JSON.stringify(options.body) : undefined,
    })

    if (response.status === 401) {
      clearLoginState()
      redirectToLogin()
      throw new Error('login expired')
    }

    const result = await response.json()
    if (!response.ok || result.code !== 'SUCCESS') {
      throw new Error(result.message || 'request failed')
    }

    return result.data as T
  } finally {
    if (options.cancelKey && pending.get(options.cancelKey) === controller) {
      pending.delete(options.cancelKey)
    }
  }
}

上面的接口路径、状态码和字段均为脱敏示例。

4. 多语言字段 ​

固定 UI 文案进入语言包，运营配置内容使用多语言对象维护：

ts
type LocalizedText = {
  en: string
  zh?: string
}

function getLocalizedText(value: LocalizedText, locale: 'en' | 'zh') {
  return value[locale] || value.en || ''
}

表单提交前校验主要语言不能为空，语言切换时由组件统一读取当前 locale，避免页面中散落大量条件判断。

5. 内容安全展示 ​

运营配置、协议和帮助内容可能包含 HTML，统一进入安全展示组件：

tsx
import DOMPurify from 'isomorphic-dompurify'

export function SafeHtml({ html }: { html?: string }) {
  const safeHtml = DOMPurify.sanitize(html || '', {
    USE_PROFILES: { html: true },
    FORBID_TAGS: ['script', 'iframe', 'object', 'embed', 'form'],
    FORBID_ATTR: ['srcdoc', 'onerror', 'onclick', 'onload'],
    ALLOW_UNKNOWN_PROTOCOLS: false,
  })

  return safeHtml ? (
    <div dangerouslySetInnerHTML={{ __html: safeHtml }} />
  ) : null
}

前端过滤是展示层防护，内容保存、输出和权限仍需要后端兜底。

业务流程怎么讲 ​

1. 渠道 / 合作方管理 ​

这类模块不是简单的增删改查，通常有一条完整链路：

  1. 创建或导入合作方基础信息。
  2. 配置可用业务范围、结算信息和状态。
  3. 提交审核，进入待审核状态。
  4. 审核通过后才允许继续配置或启用。
  5. 禁用、冻结、审核驳回等状态会影响前台和后台可操作项。
  6. 所有关键动作都需要能追溯到操作记录。

前端主要负责：

  • 根据状态决定字段是否可编辑。
  • 根据权限和状态共同控制按钮。
  • 提交前校验必填、金额、日期和关联项。
  • 操作成功后重新拉取详情或列表，避免本地状态和服务端状态不一致。
  • 对审核、禁用等不可逆操作增加二次确认。

2. 用户运营和内容配置 ​

用户运营页面通常包括用户查询、状态管理、资料查看、行为记录和批量处理。内容配置页面则包括活动、公告、Banner、导航和多语言文案。

这两类页面的共同点是：

  1. 查询条件多，且经常需要组合筛选。
  2. 列表字段和操作权限因角色不同而变化。
  3. 配置内容存在草稿、已发布、已下线等状态。
  4. 运营人员可能在编辑器中输入富文本或上传图片。
  5. 保存成功不等于立即生效，还要区分发布、审核和上下线。

面试时可以说：

我会把配置页面拆成编辑态、预览态和发布态。编辑态关注表单校验，预览态关注安全渲染，发布态关注状态刷新和权限边界，避免把所有逻辑混在一个表单组件里。

3. 账户服务和审核页面 ​

账户服务类页面需要重点处理金额、币种、限额和状态，不适合直接使用普通字符串输入：

  1. 输入时限制数字、精度和小数位。
  2. 展示时统一格式化千分位和小数位。
  3. 提交前保留字符串精度，避免 JavaScript 浮点计算误差。
  4. 根据账户状态、审核状态和权限控制操作。
  5. 提交后以服务端返回结果为准，不直接乐观修改余额或审核结果。

审核页面可以按“待审核 -> 审核中 -> 通过 / 驳回 / 补充材料”来讲。前端负责展示上下文、收集审核意见和处理状态回流，真正的审核结果和幂等控制由后端负责。

组件如何落地 ​

1. 搜索表单与列表联动 ​

搜索表单要处理三个问题：

  1. 表单值如何转换成接口参数。
  2. 快速点击查询时如何取消旧请求。
  3. 翻页、重置和筛选变化后如何保持状态一致。
tsx
function useListQuery<T>(
  load: (params: Record<string, unknown>, signal: AbortSignal) => Promise<T>,
) {
  const [loading, setLoading] = useState(false)
  const [data, setData] = useState<T | null>(null)
  const controllerRef = useRef<AbortController | null>(null)

  const run = async (params: Record<string, unknown>) => {
    controllerRef.current?.abort()
    const controller = new AbortController()
    controllerRef.current = controller
    setLoading(true)

    try {
      const result = await load(params, controller.signal)
      if (!controller.signal.aborted) setData(result)
    } finally {
      if (!controller.signal.aborted) setLoading(false)
    }
  }

  return { data, loading, run }
}

实际项目中可以把分页、排序、筛选值和 URL 查询参数继续封装进去。面试重点不是展示一个 hook，而是说明如何避免旧请求覆盖新查询结果。

2. 弹窗表单的新增 / 编辑复用 ​

新增和编辑可以共用表单，但不要把所有差异写成大量条件判断：

tsx
type FormMode = 'create' | 'edit' | 'audit'

function getFormSchema(mode: FormMode) {
  return [
    { name: 'name', required: mode !== 'audit', disabled: mode === 'audit' },
    { name: 'status', required: false, disabled: mode === 'create' },
    { name: 'remark', required: mode === 'audit', disabled: false },
  ]
}

实际页面还要处理：

  • 编辑打开时异步加载详情。
  • 详情加载完成后再回填表单。
  • 切换记录时清理上一次的校验错误。
  • 关闭弹窗时清理未提交数据。
  • 提交按钮防重复点击。
  • 保存成功后刷新列表并关闭弹窗。

3. 金额输入和精度 ​

金额输入组件的职责不是简单限制正则，还需要区分“输入值”和“展示值”：

ts
function normalizeAmount(input: string, precision = 2) {
  const value = input.replace(/[^\d.]/g, '')
  const [integer = '', decimal = ''] = value.split('.')
  const safeDecimal = decimal.slice(0, precision)

  if (!integer && !safeDecimal) return ''
  return safeDecimal ? `${integer || '0'}.${safeDecimal}` : integer
}

面试时补充：

  • 金额提交尽量保留字符串，不直接依赖浮点数。
  • 币种精度由配置决定，不能把所有金额固定成两位。
  • 最小值、最大值、限额和余额必须以后端校验为准。
  • 展示格式化和提交格式化要分开，避免把千分位字符串直接提交给接口。

接口生成和请求层的真实回答 ​

如果面试官追问具体工具，可以这样回答：

我们基于接口契约使用 swagger-typescript-api 生成类型和请求方法，页面不直接手写接口字段。生成代码外面再包一层请求客户端，统一处理 axios 实例、Token 注入、环境 baseURL、业务错误码、取消请求、文件下载和登录失效。

ts
const api = axios.create({
  baseURL: getApiBaseUrl(),
  timeout: 15_000,
  withCredentials: true,
})

api.interceptors.request.use((config) => {
  const token = getToken()
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  config.headers['X-Language'] = getCurrentLanguage()
  return config
})

api.interceptors.response.use(
  (response) => {
    if (response.data?.code !== 'SUCCESS') {
      return Promise.reject(response.data)
    }
    return response.data.data
  },
  (error) => {
    if (error.response?.status === 401) {
      clearLoginState()
      redirectToLogin()
    }
    return Promise.reject(error)
  },
)

上面的 SUCCESS、请求头和路径均为泛化字段。生成器解决的是类型和请求方法问题，拦截器解决的是请求生命周期问题，两者不能混为一谈。

上传组件怎么讲 ​

文件上传一般分成四步：

  1. 前端校验文件大小、类型和数量。
  2. 调用上传接口获取文件地址或文件标识。
  3. 表单只保存后端返回的文件标识，不直接把 File 对象提交到业务接口。
  4. 上传成功、失败、删除和重新上传都要同步表单状态。
ts
async function uploadFile(file: File) {
  const allowedTypes = ['image/png', 'image/jpeg', 'application/pdf']
  if (!allowedTypes.includes(file.type)) {
    throw new Error('unsupported file type')
  }

  if (file.size > 10 * 1024 * 1024) {
    throw new Error('file is too large')
  }

  const formData = new FormData()
  formData.append('file', file)
  return uploadApi(formData)
}

面试时说明：前端校验是体验优化，服务端仍需重新校验文件类型、大小、内容和权限，不能因为文件扩展名正确就认为安全。

这个项目的工程边界 ​

可以主动讲 ​

  • 配置化表格、表单和权限操作。
  • 接口契约生成和统一请求层。
  • 多语言字段和运营内容管理。
  • 金额精度、审核状态和重复提交。
  • 富文本安全展示和上传状态管理。

不要夸大 ​

  • 不要说前端实现了真正的风控决策。
  • 不要说前端权限能阻止越权，后端必须兜底。
  • 不要把某个简单 UI 组件包装成独立技术创新。
  • 不要为了显得复杂，主动展开真实行业、合作方或交易数据。

项目难点 ​

难点一：后台页面重复但业务差异明显 ​

解决方式是分层抽象：

  • 基础层统一表格、表单、弹窗、上传、金额输入和权限按钮。
  • 业务层保留审核流程、风险规则和账户配置等差异化模块。
  • 页面层通过配置组合，避免每个页面重复实现公共交互。

难点二：接口变化导致联调成本高 ​

通过契约生成类型和请求方法，把字段变化尽早暴露在类型检查阶段；再由统一请求层收敛 Token、错误码和重复请求逻辑。

难点三：权限和状态容易误展示 ​

前端根据权限控制路由、菜单和操作入口；接口返回无权限或状态变化后，页面重新拉取数据并更新可操作状态，避免只依赖初始页面状态。

面试追问 ​

Q：你认为最有价值的组件是什么？

A：可配置表格、搜索表单、弹窗表单、权限按钮、上传和金额输入。它们跨多个业务模块重复出现，复用后能直接减少页面开发和联调成本。

Q：为什么不把所有页面抽成一个通用页面？

A：业务差异大的页面如果强行统一，会导致配置复杂度超过业务代码本身。我选择把稳定交互抽成基础能力，把审核和风险规则等强业务模块保留为局部组件。

Q：前端权限控制安全吗？

A：前端权限主要控制入口和展示，不能代替服务端授权。服务端必须对每次敏感查询和操作做角色、数据范围和业务状态校验。
