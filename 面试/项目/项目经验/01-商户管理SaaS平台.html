商户管理 SaaS 平台 ​

项目概览 ​

时间：2024.08 - 2026.08
角色：前端核心开发
技术栈：Next.js 15、React 18、TypeScript、Ant Design、Zustand、swagger-typescript-api、isomorphic-dompurify、jsencrypt

这是一个面向运营团队和合作方的 B 端管理后台，覆盖渠道与合作方管理、用户运营、内容配置、账户服务、交易审核和风险管理。

面试时可以这样概括：

这是一个模块较多的运营管理 SaaS。我的主要工作不是只完成页面，而是把高频后台模式抽成可复用能力，同时通过接口契约和统一请求层降低联调及维护成本。

我负责的内容 ​

  1. 负责渠道运营、用户管理、活动配置、账户服务、交易审核和合作方风险管理等模块。
  2. 沉淀可配置表格、搜索表单、弹窗 / 抽屉表单、权限操作、上传、金额输入和多语言字段组件。
  3. 基于后端接口契约生成类型与请求方法，再通过统一请求层处理 Token、错误码、多环境和重复请求。
  4. 支持中英双语，覆盖菜单、表单校验、枚举值和运营配置内容（含富文本编辑器多语言）。
  5. 配合产品、后端和测试处理状态流转、权限边界、接口变更及线上问题。

业务页面模式 ​

大部分页面可以拆成稳定的后台结构：

  1. 搜索区：关键词、状态、时间范围、类型和业务归属等筛选条件。
  2. 操作区：新增、批量处理、导入导出、刷新和列配置。
  3. 表格区：分页、排序、状态标签、长文本、省略和金额格式化。
  4. 行操作：查看、编辑、审核、禁用、日志和更多操作。
  5. 表单弹窗：新增、编辑、审核共用表单基础能力，但根据业务状态控制字段是否可编辑。
  6. 详情抽屉：展示用户资料、审核记录、执行记录和操作日志。

1.1 表格 Tooltip 溢出检测（真实代码片段） ​

后台表格里长文本、备注、操作人这类单元格，最容易出现"截断不知道截的是什么"的问题。我没有直接用 ellipsis: true，而是封装了一个 CustomTable，对每个单元格做"真实溢出检测"——只在确实溢出时才显示 Tooltip，并且 Tooltip 内容支持换行查看完整字段。

tsx
// 真实 CustomTable 核心逻辑（节选）
const TooltipCell: React.FC<{ content: ReactNode; showTooltip?: boolean }> = ({
  content,
  showTooltip = true,
}) => {
  const cellRef = useRef<HTMLDivElement>(null)
  const [isOverflowed, setIsOverflowed] = useState(false)

  useEffect(() => {
    checkOverflow()
  }, [content])

  useEffect(() => {
    // 备注：监听窗口缩放和 DOM 变化，避免异步加载数据后溢出判断失效
    const handleResize = () => checkOverflow()
    window.addEventListener('resize', handleResize)

    const observer = new MutationObserver(handleResize)
    if (cellRef.current) {
      observer.observe(cellRef.current, {
        childList: true,
        subtree: true,
        characterData: true,
      })
    }
    return () => {
      window.removeEventListener('resize', handleResize)
      observer.disconnect()
    }
  }, [])

  const checkOverflow = () => {
    if (cellRef.current && showTooltip) {
      const element = cellRef.current
      // 备注：scrollWidth > clientWidth 才算溢出，避免空内容也包一层 Tooltip
      const isTextOverflow = element.scrollWidth > element.clientWidth
      setIsOverflowed(isTextOverflow)
    }
  }
  // ...
}

设计要点：

  • 不是简单 ellipsis: true：Antd 自带 ellipsis 只在 hover 时显示 title，不能换行，长备注被截掉后看不清。
  • 溢出检测双重保险：监听 resize 和 MutationObserver，因为异步加载数据后单元格内容会变化，第一次渲染时可能没溢出。
  • 可关闭：showTooltip: false 用于状态标签、Tag 这种不需要 Tooltip 的场景。

2. 权限控制 ​

权限分为三层：

  1. 路由层：根据用户角色和菜单权限生成可访问路由。
  2. 页面层：没有权限时展示无权限状态或跳转到兜底页面。
  3. 操作层：按钮、操作列和批量操作根据权限码控制显示。
tsx
function PermissionButton({
  code,
  children,
  onClick,
}: {
  code: string
  children: React.ReactNode
  onClick: () => void
}) {
  const permissions = usePermissionStore((state) => state.codes)
  if (!permissions.includes(code)) return null

  return <button onClick={onClick}>{children}</button>
}

面试时要补充：前端权限只负责入口展示和用户体验，后端仍然必须校验数据权限和操作权限。

3. 接口契约和统一请求层（真实核心实现） ​

这块是这个项目里最值得讲的工程能力。我基于 swagger-typescript-api 生成类型 + 请求方法（生成器只解决类型问题），外面再包一层 HttpClient 解决请求生命周期问题。两个职责要分开讲，不然面试官会觉得"你只是用了一个 npm 包"。

3.1 生成器与拦截器职责划分 ​

面试时的标准回答：

我们用 swagger-typescript-api 生成接口类型和请求方法，页面不直接手写字段。生成代码外面再包一层 HttpClient，统一处理 fetch 实例、Token 注入、环境 baseURL、业务错误码、AbortController 取消、文件下载和登录失效。生成器解决"类型"，HttpClient 解决"生命周期"，两者职责不能混。

3.2 真实 HttpClient 关键代码 ​

下面是从 merchant 项目实际抽出来的核心逻辑（已做脱敏）。

3.2.1 请求合并：每次请求统一注入 Cookie 中的 Token、I18n、timezone

ts
// 真实代码片段：merchant/src/utils/http-client.ts
protected mergeRequestParams(
  params1: RequestParams,
  params2?: RequestParams,
): RequestParams {
  return {
    ...this.baseApiParams,
    ...params1,
    ...(params2 || {}),
    headers: {
      ...(this.baseApiParams.headers || {}),
      ...(params1.headers || {}),
      ...((params2 && params2.headers) || {}),
      I18n: CookieService.get('I18n') || 'en',     // 后端根据这个返回多语言错误信息
      Authorization: CookieService.get('Authorization') || '',
      timezone: getTimezoneForRequest(),           // 海外项目必备：客户端时区
    },
  }
}

设计要点：

  • 时区：海外业务跨多时区，前端把 timezone 注入到每个请求，后端用这个时区格式化时间字段。否则列表里 createdAt 会出现"今天 25:00"。
  • 多语言：错误信息来自后端，前端只传 I18n 标识，不在前端做文案翻译兜底。
  • Token 走 Cookie 而非 localStorage：HttpOnly Cookie 可以避免 XSS 直接偷 token，前端通过 credentials: 'same-origin' 自动带上。

3.2.2 取消请求：基于 AbortController 的 cancelToken

后台页面有大量"输入即搜索"场景（搜索框输入触发列表请求），如果不做取消，上一次未完成的请求会覆盖最新结果。

ts
// 真实代码片段
private abortControllers = new Map<CancelToken, AbortController>()

protected createAbortSignal = (cancelToken: CancelToken): AbortSignal | undefined => {
  if (this.abortControllers.has(cancelToken)) {
    const abortController = this.abortControllers.get(cancelToken)
    if (abortController) return abortController.signal
    return void 0
  }
  const abortController = new AbortController()
  this.abortControllers.set(cancelToken, abortController)
  return abortController.signal
}

public abortRequest = (cancelToken: CancelToken) => {
  const abortController = this.abortControllers.get(cancelToken)
  if (abortController) {
    abortController.abort()
    this.abortControllers.delete(cancelToken)
  }
}

设计要点：

  • Map<cancelToken, AbortController>：每个 cancelToken 对应一个控制器，请求完成或失败时记得 delete，否则长时间运行的页面会内存泄漏。
  • 不传 cancelToken 的请求无法取消：避免误伤一次性请求（如下载）。

3.2.3 登录失效处理：单点跳转，避免多次 toast

ts
// 真实代码片段：处理 INVALIDATION（登录失效）码
if (data.code === ResultEnum.INVALIDATION) {
  const lang = CookieService.get('I18n') || 'en'
  const openLogin = getItem(StorageEnum.OpenLogin, StorageTypeEnum.LocalStorage)
  const isLoginPage = location.pathname === '/login'

  if (isLoginPage) return Promise.reject(data)

  if (doRequest) {            // 关键：用模块级变量保证只触发一次
    clearTimezoneOnLogout()
    if (openLogin !== '1') {
      location.replace(`/gate.html`)   // 不在登录页 → 跳登录门
    } else {
      messageManager.error(lang == 'zh'
        ? '您暂未登录或登录信息已过期，请重新登录！'
        : 'You have not logged in or the login information has expired, please log in again!')
      doRequest = false        // 关键：标记已处理，防止后续请求再次触发
      CookieService.set('Authorization', '')
      setTimeout(() => { goLogin() }, 3000)
    }
  }
  return Promise.reject(data)
}

设计要点：

  • 多请求并发时只处理一次：登录失效可能同时触发多个请求，doRequest 模块级变量保证只 toast 一次、只跳一次。
  • 登录页直接拒绝：在登录页触发失效不做跳转，避免循环。
  • gate.html 跳登录门：多套项目用同一个登录门，前端不需要在每个项目配登录地址。

3.2.4 系统繁忙码 SYS_BUSY 单独处理

ts
if (data.code === ResultEnum.SYS_BUSY) {
  messageManager.error(i18n.t('common.serverError.sysBusy'))
} else {
  messageManager.error(data.msg)
}

设计要点：SYS_BUSY 是后端约定俗成的"系统维护中"码，前端用 i18n key 而不是后端 msg，因为后端繁忙文案可能没翻译，前端文案更可控。

3.3 请求链路完整流程 ​

  1. 后端维护 OpenAPI / Swagger 契约。
  2. CI 跑 swagger-typescript-api 生成 data-contracts.ts（类型）和 Api.ts（请求方法）。
  3. Api.ts 内部用我们的 HttpClient，对外暴露类型安全的请求函数。
  4. 页面只调用生成出来的函数，不直接写接口路径和字段。
  5. 接口字段变化 → CI 重新生成 → TypeScript 编译报错 → 提前发现，不等到运行时。

4. 多语言方案 ​

4.1 多语言注入层级 ​

多语言字段分布在三层，需要统一处理：

  1. 菜单 / 路由：登录后根据 I18n 拉对应语言的菜单。
  2. 表单校验：错误信息走 i18n key，不在 JSX 里写死中文。
  3. 枚举值 / 富文本配置：后端返回多语言结构，前端用 <I18nText> 组件按当前语言取值。
  4. 富文本编辑器：wangEditor 要切换界面语言（菜单、placeholder 都得换）。
tsx
// 真实代码片段：merchant WangEditor 切换语言
import { i18nChangeLanguage } from '@wangeditor/editor'
import { useTranslation } from 'react-i18next'

function WangEditor({ language }: WangEditorProps) {
  const { t } = useTranslation()
  useEffect(() => {
    i18nChangeLanguage(language)  // 切换编辑器内置语言
  }, [language])

  // placeholder 也按当前语言
  placeholder: language === 'zh' ? '请输入内容...' : 'Please enter content...'
}

设计要点：

  • 编辑器内置语言和应用语言分开：wangEditor 内部用的是 i18next 的另一个实例，不能直接 i18n.changeLanguage()。
  • placeholder 文案：多语言切换时不能保留旧语言，否则切到英文看到中文 placeholder 很奇怪。

5. 富文本安全展示 ​

5.1 白名单策略（DOMPurify） ​

后台运营内容经常带富文本，最容易出现 XSS 注入。我没有用 dangerouslySetInnerHTML 直接渲染，而是封装了 sanitizeHtml：

ts
// 真实代码片段：merchant/src/utils/sanitizeHtml.ts
import DOMPurify from 'isomorphic-dompurify'

// 富文本编辑器（wangEditor 等）常见输出标签白名单
const ALLOWED_TAGS = [
  'a', 'abbr', 'b', 'blockquote', 'br', 'code', 'div', 'em', 'font',
  'h1', 'h2', 'h3', 'h4', 'h5', 'h6', 'hr', 'i', 'img', 'li', 'ol',
  'p', 'pre', 's', 'span', 'strong', 'sub', 'sup', 'table', 'tbody',
  'td', 'th', 'thead', 'tr', 'u', 'ul',
]

const ALLOWED_ATTR = [
  'align', 'alt', 'class', 'colspan', 'height', 'href', 'rel', 'rowspan',
  'src', 'style', 'target', 'width',
]

let configured = false

function ensureConfig() {
  if (configured) return
  configured = true
  DOMPurify.setConfig({
    ALLOWED_TAGS,
    ALLOWED_ATTR,
    ALLOW_DATA_ATTR: false,         // 拒绝 data-* 属性，防 data-url、data-evil
    ALLOW_ARIA_ATTR: true,          // 允许 aria-*，富文本经常带
    // 允许 http(s)、mailto、tel，以及 data:（编辑器内嵌 base64 图片必须）
    ALLOWED_URI_REGEXP: /^(?:(?:(?:f|ht)tps?|mailto|tel|callto|sms|cid|xmpp|data):|[^a-z]|[a-z+.\-]+(?:[^a-z+.\-:]|$))/i,
  })
}

export function sanitizeHtml(html?: string | null): string {
  if (!html) return ''
  ensureConfig()
  return DOMPurify.sanitize(html) as string
}

设计要点：

  • isomorphic-dompurify：SSR 也能用，避免 Next.js 服务端渲染富文本时报 window is not defined。
  • 白名单而不是黑名单：每次发现新的 XSS 都要更新黑名单，迟早漏；白名单只能放行已知标签。
  • ALLOW_DATA_ATTR = false：data-* 属性是常见攻击载体，富文本里几乎用不到。
  • ALLOWED_URI_REGEXP 必须包含 data:：否则编辑器里粘贴的 base64 图片全被剥掉。
  • configured 单例：DOMPurify.setConfig 是全局的，重复调用浪费性能。

5.2 SafeHtml 组件：项目里唯一允许 dangerouslySetInnerHTML 的地方 ​

tsx
// 真实代码片段：merchant/src/components/safeHtml/index.tsx
import { createElement, HTMLAttributes } from 'react'
import { sanitizeHtml } from '@/utils/sanitizeHtml'

type SafeHtmlTag = keyof HTMLElementTagNameMap

type SafeHtmlProps<T extends SafeHtmlTag = 'div'> = HTMLAttributes<HTMLElement> & {
  html?: string | null
  as?: T
}

/** 唯一允许 dangerouslySetInnerHTML 的封装组件，渲染前自动 XSS 过滤 */
export default function SafeHtml<T extends SafeHtmlTag = 'div'>({
  html, as, ...rest
}: SafeHtmlProps<T>) {
  const Tag = (as ?? 'div') as SafeHtmlTag
  const sanitized = sanitizeHtml(html)
  return createElement(Tag, { ...rest, dangerouslySetInnerHTML: { __html: sanitized } })
}

设计要点：

  • 组件收敛：所有富文本渲染只能走 <SafeHtml>，Lint 规则禁止其他地方用 dangerouslySetInnerHTML。
  • as prop 支持自定义标签：偶尔需要 <SafeHtml as="section" />。

面试口径：富文本过滤只能防当前页面展示，真正的安全依赖后端：保存、输出和权限校验都要后端兜底，前端过滤是"体验层"防护。

6. 金额处理：法币 vs 虚拟币精度差异 ​

这个项目里有法币（USD 等）和虚拟币（USDT 等）混用的场景，币种精度不一样，不能简单用 toFixed(2)。

ts
// 真实代码片段：merchant/src/utils/currencyHelper.ts
const decimals = currencyType === 2 ? 4 : 2  // 虚拟币 4 位小数，法币 2 位

export const formatAmountSmartByCurrencyType = (
  amount: number | string,
  currencyType: number,
): string => {
  const numAmount = Number(amount || 0)

  // 整数不补小数（避免 100 显示成 100.00）
  if (Number.isInteger(numAmount)) return String(numAmount)

  const maxDecimals = currencyType === 2 ? 4 : 2
  const multiplier = Math.pow(10, maxDecimals)
  const truncated = Math.floor(numAmount * multiplier) / multiplier

  // 移除尾部的 0：1.20 → 1.2，0.50000 → 0.5
  return truncated.toString()
}

设计要点：

  • 整数不补小数：100 显示为 100 而不是 100.00，避免长列表视觉噪音。
  • 截断不四舍五入：金融场景必须 Math.floor，不能用 toFixed（toFixed 是四舍五入）。
  • 尾部 0 移除：0.50000 显示为 0.5，避免虚拟币列表里全是 0。

使用场景示例：

ts
// 在表格列里直接复用
const amountRenderer = createAmountSmartRenderer(currencyTypeMap)

columns: [
  {
    title: '金额',
    dataIndex: 'amount',
    render: amountRenderer,  // 渲染时自动按币种精度格式化
  },
]

7. 密码加密：RSA + JSEncrypt ​

后台登录密码不能明文传输，前端用 RSA 公钥加密，后端用私钥解密。

ts
// 真实代码片段：merchant/src/utils/encrypt.ts
import { JSEncrypt } from 'jsencrypt'

// 公钥放在前端代码里没问题，RSA 设计就是公钥可公开
// 真实密钥较长，这里只示意
const publicKey = `-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----`

export const getEncryptedPssword = (pwd: string | undefined) => {
  if (!pwd) return ''
  const encrypt = new JSEncrypt()
  encrypt.setPublicKey(publicKey)
  return encrypt.encrypt(pwd)  // 失败时返回 null，需要判空
}

设计要点：

  • RSA 加密密码是"防偷听"，不是"防重放"：HTTPS 已经防偷听，RSA 主要解决"前端代码被分析后密码不被还原"。但仍需后端配合 nonce / 时间戳防重放。
  • 加密失败返回 null：JSEncrypt 对超长字符串会失败，前端要 if (!encrypted) throw new Error('加密失败')。
  • 私钥绝对不能进前端包：私钥泄漏 = 整套加密体系失效。

8. 金额输入规范化 ​

ts
function normalizeAmount(input: string, precision = 2) {
  const value = input.replace(/[^\d.]/g, '')
  const [integer = '', decimal = ''] = value.split('.')
  const safeDecimal = decimal.slice(0, precision)

  if (!integer && !safeDecimal) return ''
  return safeDecimal ? `${integer || '0'}.${safeDecimal}` : integer
}

面试时补充：

  • 金额提交尽量保留字符串，不直接依赖浮点数。
  • 币种精度由配置决定，不能把所有金额固定成两位。
  • 最小值、最大值、限额和余额必须以后端校验为准。
  • 展示格式化和提交格式化要分开，避免把千分位字符串直接提交给接口。

接口生成和请求层的真实回答 ​

如果面试官追问具体工具，可以这样回答：

我们基于接口契约使用 swagger-typescript-api 生成类型和请求方法，页面不直接手写接口字段。生成代码外面再包一层请求客户端，统一处理 fetch 实例、Token 注入、环境 baseURL、业务错误码、取消请求、文件下载和登录失效。

ts
const api = axios.create({
  baseURL: getApiBaseUrl(),
  timeout: 15_000,
  withCredentials: true,
})

api.interceptors.request.use((config) => {
  const token = getToken()
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  config.headers['X-Language'] = getCurrentLanguage()
  return config
})

api.interceptors.response.use(
  (response) => {
    if (response.data?.code !== 'SUCCESS') {
      return Promise.reject(response.data)
    }
    return response.data.data
  },
  (error) => {
    if (error.response?.status === 401) {
      clearLoginState()
      redirectToLogin()
    }
    return Promise.reject(error)
  },
)

上面的 SUCCESS、请求头和路径均为泛化字段。生成器解决的是类型和请求方法问题，拦截器解决的是请求生命周期问题，两者不能混为一谈。

上传组件怎么讲 ​

文件上传一般分成四步：

  1. 前端校验文件大小、类型和数量。
  2. 调用上传接口获取文件地址或文件标识。
  3. 表单只保存后端返回的文件标识，不直接把 File 对象提交到业务接口。
  4. 上传成功、失败、删除和重新上传都要同步表单状态。
ts
async function uploadFile(file: File) {
  const allowedTypes = ['image/png', 'image/jpeg', 'application/pdf']
  if (!allowedTypes.includes(file.type)) {
    throw new Error('unsupported file type')
  }

  if (file.size > 10 * 1024 * 1024) {
    throw new Error('file is too large')
  }

  const formData = new FormData()
  formData.append('file', file)
  return uploadApi(formData)
}

面试时说明：前端校验是体验优化，服务端仍需重新校验文件类型、大小、内容和权限，不能因为文件扩展名正确就认为安全。

这个项目的工程边界 ​

可以主动讲 ​

  • 配置化表格、表单和权限操作。
  • 接口契约生成和统一请求层（含 timezone / i18n / abort / 登录失效单点处理）。
  • 多语言字段和运营内容管理（含富文本编辑器多语言）。
  • 金额精度、币种差异和重复提交。
  • 富文本安全展示（DOMPurify 白名单）和上传状态管理。

不要夸大 ​

  • 不要说前端实现了真正的风控决策。
  • 不要说前端权限能阻止越权，后端必须兜底。
  • 不要把某个简单 UI 组件包装成独立技术创新。
  • 不要为了显得复杂，主动展开真实行业、合作方或交易数据。

项目难点 ​

难点一：后台页面重复但业务差异明显 ​

解决方式是分层抽象：

  • 基础层统一表格、表单、弹窗、上传、金额输入和权限按钮。
  • 业务层保留审核流程、风险规则和账户配置等差异化模块。
  • 页面层通过配置组合，避免每个页面重复实现公共交互。

难点二：接口变化导致联调成本高 ​

通过契约生成类型和请求方法，把字段变化尽早暴露在类型检查阶段；再由统一请求层收敛 Token、错误码、时区、多语言和重复请求逻辑。接口字段变化时，TypeScript 编译阶段就能发现，不用等到联调。

难点三：权限和状态容易误展示 ​

前端根据权限控制路由、菜单和操作入口；接口返回无权限或状态变化后，页面重新拉取数据并更新可操作状态，避免只依赖初始页面状态。

难点四：登录失效多请求并发时只处理一次 ​

后台页面打开瞬间会同时发几十个接口，登录态过期时如果每个请求都触发 toast 和跳转，用户体验非常糟糕。doRequest 模块级标志位保证只 toast 一次、只跳一次。

难点五：富文本 XSS 防护不能只靠前端 ​

白名单过滤是底线，重要场景（支付说明、运营公告）还要后端二次过滤。SafeHtml 组件只解决"展示"问题，不解决"提交"问题。

面试追问 ​

Q：你认为最有价值的组件是什么？

A：可配置表格、搜索表单、弹窗表单、权限按钮、上传和金额输入。它们跨多个业务模块重复出现，复用后能直接减少页面开发和联调成本。最有技术含量的是 HttpClient——把 Token / I18n / timezone / 取消请求 / 登录失效统一收敛，生成的 API 代码只是薄薄一层业务调用。

Q：为什么不把所有页面抽成一个通用页面？

A：业务差异大的页面如果强行统一，会导致配置复杂度超过业务代码本身。我选择把稳定交互抽成基础能力，把审核和风险规则等强业务模块保留为局部组件。

Q：前端权限控制安全吗？

A：前端权限主要控制入口和展示，不能代替服务端授权。服务端必须对每次敏感查询和操作做角色、数据范围和业务状态校验。

Q：登录失效是怎么处理的？

A：后端约定 INVALIDATION 业务码，前端 HttpClient 拦截后清登录态、跳登录门。多请求并发时用模块级 doRequest 标志位保证只处理一次。

Q：为什么用 Cookie 存 Token 而不是 localStorage？

A：HttpOnly Cookie 可以避免 XSS 直接读取 token，配合 credentials: 'same-origin' 自动带。CSRF 用 SameSite=Lax + 后端校验 Referer / Origin 来防。

Q：swagger-typescript-api 生成出来的代码你们怎么维护？

A：CI 流水线里跑生成命令，生成的 data-contracts.ts 和 Api.ts 直接提交进仓库，不在运行时动态生成。这样接口字段变化会触发编译报错，所有依赖该接口的页面都会暴露出来。

Q：DOMPurify 白名单怎么定？

A：根据编辑器实际输出标签整理。富文本编辑器（wangEditor）能输出的标签都在白名单里，其他一律剥掉。data-* 属性全禁，href / src 用 URI 白名单正则校验。

Q：法币和虚拟币精度不一样怎么处理？

A：币种配置里带 currencyType 字段（1=法币、2=虚拟币），格式化时按类型选 2 位或 4 位小数。整数不补小数，截断不四舍五入（金融场景必须 floor），尾部 0 移除。

Q：RSA 加密密码够安全吗？

A：RSA 只能防"代码被分析后密码不被还原"，不能防重放。真正的安全依赖 HTTPS、后端 nonce / 时间戳、Token 生命周期和风控策略。
