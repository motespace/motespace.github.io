农业数字化项目：App + IoT 大屏 ​

项目概览 ​

时间：2019 - 2020 角色：早期项目，前端开发 技术栈：uni-app、Vue 2、Vuex、ECharts 推荐程度：补充项目

这是一个早期农业数字化项目，包含消费者端、服务人员端 App 和农业物联网监控大屏。面试时建议作为补充项目，用于说明移动端、端能力接入、地图联动和数据可视化经验。

面试时可以这样概括：

这个项目不是单纯摆几个图表，它要把 IoT 实时数据、地图点位、趋势分析和视频监控放在同一个大屏里，让管理方能快速看到基地运行情况。

业务全貌 ​

App 业务线 ​

这是"农业电商 + 果农服务 + 溯源互动"的移动端项目。

消费者版：

  1. 首页展示农场、商品、认养入口、活动。
  2. 用户可以购买农场直供商品。
  3. 用户可以认养果树，查看认养记录和果树信息。
  4. 支持竞拍、订单、支付、物流或状态跟踪。
  5. 扫码查看产地、批次、种植记录等溯源信息。
  6. 通过 IM、直播和果农产生互动。

果农版：

  1. 操作台查看待办和农事信息。
  2. 学习种植技术、查看施肥方案。
  3. 发布或参与橙友圈社区。
  4. 通过问答咨询处理问题。
  5. 与消费者或平台进行沟通。

面试表达：

这个项目是我早期移动端项目，价值是完整跑过交易、认养、溯源、消息、IM 和直播这些移动端业务闭环。现在我不会把它作为主项目，但它能证明我不只做后台，也做过跨端和端能力接入。

IoT 大屏业务线 ​

大屏围绕农业产业做 IoT 可视化，主要展示：

  1. 基地分布：不同果园或基地在地图上的位置。
  2. 环境监测：温度、湿度、光照、雨量、CO2、土壤墒情、PH 等。
  3. 价格指数：不同时间、区域或品类的价格走势。
  4. 产量走势：产量、采摘、销售等趋势。
  5. 结构分布：树龄、土壤、基地类型等占比。
  6. 视频监控：查看果园实时画面，多摄像头预览和云台控制。

面试表达：

这个项目不是单纯摆几个图表，它要把 IoT 实时数据、地图点位、趋势分析和视频监控放在同一个大屏里，让管理方能快速看到基地运行情况。

我负责的内容 ​

  1. 负责移动端首页、商品、认养、订单、支付、扫码溯源、农事服务和社区问答。
  2. 处理消息触达、即时通讯和直播入口。
  3. 对接传感器数据，展示温湿度、光照、雨量、二氧化碳、土壤墒情和酸碱度等指标。
  4. 实现地图点位、数据浮层、底部轮播和视频监控联动。
  5. 处理不同端的生命周期、权限、支付、扫码和页面返回差异。

一分钟介绍 ​

这是一个同时包含移动端和 IoT 大屏的农业数字化项目。App 侧重点是交易、认养、溯源和服务闭环；大屏侧重点是传感器数据、基地地图、趋势图和视频监控联动。我主要负责前端页面、接口协作、跨端适配和数据展示。

App 业务实现 ​

1. 认养业务 ​

可以按流程讲：

  1. 用户进入认养专区，查看可认养果树或果园。
  2. 选择认养对象，查看价格、周期、权益和说明。
  3. 提交认养订单并支付。
  4. 支付成功后生成认养记录。
  5. 用户后续可以查看果树状态、农事记录、图片或直播画面。
  6. 到期或收获阶段关联订单、配送或权益领取。

前端难点：

  1. 认养状态比普通商品多，比如可认养、已认养、待支付、认养中、已到期。
  2. 入口多，首页、详情、订单、个人中心都可能进入认养信息。
  3. 移动端支付结果需要处理返回、刷新和失败重试。

2. 竞拍 / 支付 / 订单 ​

竞拍：

  1. 展示竞拍商品、起拍价、当前价、倒计时。
  2. 用户出价后刷新当前状态。
  3. 竞拍结束后生成结果或订单。

支付：

  1. 订单确认页展示商品、金额、地址、支付方式。
  2. 接入微信 / 支付宝支付。
  3. 支付后处理成功、失败、取消、返回 App 的状态刷新。

订单：

  1. 待支付、待发货、待收货、已完成、已取消等状态。
  2. 订单详情展示商品、支付、配送、售后或溯源入口。
  3. 列表页要处理分页、状态筛选和下拉刷新。

面试表达：

这类移动端业务看起来普通，但状态处理很关键。尤其是支付后用户可能从外部支付页返回，前端不能只依赖本地状态，要重新查订单结果。

3. 扫码溯源 ​

流程：

  1. 用户扫描二维码。
  2. 前端解析二维码里的批次、商品或溯源码。
  3. 调接口查询产地、果园、批次、种植记录、采摘或检测信息。
  4. 页面按时间线或模块展示溯源内容。
  5. 异常码、过期码、无数据要有兜底提示。

价值表达：

扫码溯源本质上是增强农产品可信度。用户不是只看到商品介绍，而是能看到产地、种植和批次信息，形成从购买到信任的闭环。

4. IM / 推送 / 直播 ​

IM：

  1. 支持文字、图片、语音输入。
  2. 消息列表要处理发送中、发送失败、已发送状态。
  3. WebSocket 断开后要重连或提示。
  4. 图片和语音要考虑上传、权限和播放。

推送：

  1. 用于订单、认养、竞拍、社区等消息提醒。
  2. 用户点击消息后回到对应业务页面。
  3. 面试时说"消息触达和页面回流"，不用主动讲底层 API。

直播：

  1. 用户可查看果园实时画面。
  2. 支持多摄像头或直播流切换。
  3. 弱网或无权限时要提示。

5. uni-app 端差异 ​

常见问题：

  1. 不同端生命周期表现不完全一致。
  2. 扫码、支付、推送、录音、相册权限属于端能力，要处理授权失败。
  3. 页面返回、分享、下拉刷新、滚动加载在端上表现不同。
  4. 真机调试和浏览器调试结果可能不一致。

面试表达：

uni-app 开发不能只按 H5 思路写，要考虑端能力和真机表现。像支付、扫码、推送、录音、直播这些功能，我会重点做权限判断、失败提示和返回状态刷新。

IoT 大屏实现 ​

1. IoT 数据刷新 ​

数据刷新可以按模块拆：

  1. 环境指标：温度、湿度、光照、CO2、PH 等短周期刷新。
  2. 趋势图：按分钟、小时或天聚合展示。
  3. 统计卡片：展示当前值、最大值、最小值或变化趋势。
  4. 地图浮层：点位 hover / click 时异步加载详情。
  5. 视频监控：和图表数据不同，更多是流地址和播放状态。

前端处理：

  1. 定时器按模块创建，组件销毁时清理。
  2. 接口异常时保留旧数据或显示兜底状态。
  3. 图表数据统一转换成 ECharts 需要的 xAxis、series、legend。
  4. 窗口尺寸变化时统一触发 resize。
ts
type SensorPoint = {
  time: string
  value: number | null
}

function toLineOption(points: SensorPoint[]) {
  return {
    tooltip: { trigger: 'axis' },
    xAxis: {
      type: 'category',
      data: points.map((item) => item.time),
    },
    yAxis: { type: 'value' },
    series: [
      {
        type: 'line',
        smooth: true,
        data: points.map((item) => item.value),
      },
    ],
  }
}

要区分 0 和无数据，不能简单使用 value || '--'，否则有效的 0 会被误判为空。

2. 地图点位联动 ​

可以按流程讲：

  1. 加载自定义地图数据，注册县区域地图。
  2. 根据基地经纬度绘制点位。
  3. 点位用高亮或波纹效果提示基地位置。
  4. 鼠标移入或点击点位时，请求基地详情和近一段时间环境数据。
  5. 地图 Tooltip / 浮层展示基地名称、温湿度、土壤、光照等关键指标。
  6. 底部基地轮播切换时，同步高亮地图点位并展示对应浮层。

维护一个当前基地 id：

ts
const activeBaseId = ref<string | null>(null)

function selectBase(id: string) {
  activeBaseId.value = id
  loadBaseDetail(id)
}

核心不是某一种散点效果，而是让地图、轮播和指标始终指向同一个当前基地。

3. 图表组件封装 ​

大屏图表可以讲这几类：

  1. 趋势类：折线图展示温湿度、价格、产量变化。
  2. 对比类：柱状图展示基地、区域或品类之间的差异。
  3. 占比类：饼图展示树龄、土壤、品类结构。
  4. 综合类：雷达图展示多维环境状态。
  5. 状态类：水波图展示湿度、水位或容量类指标。
  6. 地图类：区域地图和基地点位联动。

封装重点：

  1. 图表组件不直接写死接口字段，而是接收业务数据后统一转换。
  2. option 基础样式统一，比如字体、颜色、tooltip、legend。
  3. 数据为空时显示空状态，避免图表报错。
  4. 大屏缩放时图表要 resize。

4. 视频监控 ​

前端处理：

  1. 后台返回摄像头列表和播放地址。
  2. 前端支持单屏、多屏切换。
  3. 点击摄像头切换当前画面。
  4. 云台控制通过方向、缩放等按钮调用设备控制接口。
  5. 播放失败、离线、无权限要展示兜底状态。

面试表达：

视频监控不是图表能力，但它能让大屏从"数据展示"变成"现场查看"。我负责的是前端播放、布局切换、摄像头选择和云台操作入口，设备控制和流媒体服务由后端或设备 SDK 支撑。

5. 大屏适配 ​

常见方案：

  1. 以设计稿宽高为基准，比如 1920 x 1080。
  2. 根据当前屏幕宽高计算缩放比例。
  3. 外层容器做整体缩放，内部模块保持设计稿布局。
  4. 图表监听容器变化后执行 resize。
  5. 字体和图表间距不能只靠浏览器自适应，否则大屏会变形。

面试表达：

大屏适配重点是保持视觉比例稳定。普通响应式布局适合业务页面，大屏更常见的是按设计稿比例整体缩放，再配合图表 resize。

面试追问 ​

Q：这个项目最难的地方是什么？

A：移动端的状态闭环和大屏的多模块联动。移动端支付、订单和认养状态需要处理返回和刷新；大屏则要让地图、轮播、指标、图表和视频围绕同一个当前基地同步。

Q：地图点位和底部轮播怎么同步？

A：我会维护一个当前基地 id。轮播切换、地图点击、点位 hover 都更新这个 id，然后地图高亮、浮层内容和右侧指标都从这个状态派生，避免各模块各自维护状态导致不同步。

Q：实时大屏如何避免内存问题？

A：每个定时器都在组件销毁时清理，图表实例避免重复初始化，接口失败时做兜底，窗口变化统一触发 resize，长时间运行比首次显示更重要。

Q：传感器数据为空怎么办？

A：前端要区分 0 和无数据。0 是有效值，无数据要显示占位或暂无数据，不能直接用 value || '--' 这种写法，否则会把有效的 0 误判掉。

Q：支付完成后如何保证状态准确？

A：支付完成不能只依赖本地回调，因为用户可能中途离开或从外部页面返回。前端需要在返回 App / 页面重新可见时刷新订单状态。

Q：为什么这个项目在简历里合并成一个？

A：它们属于同一农业数字化业务背景，一个偏移动端业务闭环，一个偏 IoT 可视化。合并后简历更紧凑，但面试时可以根据岗位分别展开 App 或大屏部分。

Q：为什么不主动讲具体推送 SDK 或地图效果？

A：这些属于实现细节，不是项目核心价值。面试时先讲消息触达、页面回流、地图联动和数据刷新，面试官追问时再说明具体端能力或图表实现。

Q：图表长时间运行怎么避免问题？

A：定时器要在组件销毁时清理，请求要做失败兜底，图表实例避免重复初始化，窗口变化时统一 resize。大屏经常长时间开着，这些比普通页面更重要。
