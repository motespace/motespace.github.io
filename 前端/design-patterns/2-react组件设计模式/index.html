2.1 好的 Props 长什么样

Section titled “2.1 好的 Props 长什么样”

判断标准：当你在加第三个布尔开关时，就该停下来改成枚举或变体了。

2.2 数据形状优先用 children 而不是复合子组件

Section titled “2.2 数据形状优先用 children 而不是复合子组件”

antd 早期用 Select.Option（复合），后来改成 options 属性 + children 混合，正是因为复合写法在动态场景（options.map）里太别扭。

2.3 常见 Props 约定

Section titled “2.3 常见 Props 约定”
Props 约定
value / defaultValue 受控值 / 初始值
onChange 值变化的回调，回调参数是值本身（不是事件）
open / onOpenChange 受控开关
loading 加载态
disabled 禁用
error 错误信息（不要用 status="error" 混着）
options 数据数组，结构 { label, value, disabled }
className / style 必须透传，否则无法定制
children 内容或渲染函数

为什么要这样？因为受控组件里 onChange 传事件会强制调用方写 e => setX(e.target.value)，而值直传可以写成 onChange={setX}。

4.3 实现：用 Context 共享状态

Section titled “4.3 实现：用 Context 共享状态”

优点：

  • 调用方自由组合，不用记一堆 props
  • 子组件之间能共享状态（useDialogContext）
  • 结构可读性强，测试时可单独测子组件

缺点：Context 变化会让所有消费者重渲染 → 用 useMemo + 拆分 Context（状态 Context 和 actions Context 分开）优化。

复合组件的典型使用者：Radix UI、Headless UI、Ant Design 的部分组件。

五、Render Props 与 Children-as-Function

Section titled “五、Render Props 与 Children-as-Function”

局限：每次渲染都会创建新的函数 → 子组件 memo 失效。

改进：把 render 函数当子组件传（element 形式）

React 官方的 “children as elements instead of functions” 优化就是这个思路。

六、Headless 组件(无样式组件)

Section titled “六、Headless 组件(无样式组件)”

价值：

  • 一套交互逻辑，多套视觉风格（ERP 里“深色主题”和“客户自定义主题”能复用）
  • 无障碍（键盘导航、焦点、ARIA）不用重复写
  • Radix UI / Headless UI / Ark UI 都是这个思路

七、Slots 模式(给组件留扩展位)

Section titled “七、Slots 模式(给组件留扩展位)”

关键：预留 extra、footer、renderXxx 这类插槽，让业务方能在不 fork 组件的前提下加东西 —— 这是“提升复用率”最直接的手段。

八、状态提升与 Context

Section titled “八、状态提升与 Context”

Context 的正确用法：跨层传递“稳定、低频变化”的数据（主题、当前用户、路由）。

需要更高性能就用外部状态库（Zustand / Redux Toolkit），配合 selector 订阅，详见 React 状态管理。

九、用 useReducer 管理复杂状态机

Section titled “九、用 useReducer 管理复杂状态机”

单据审批、订单状态这类“多状态 + 多流转”的场景，useState 会失控。

收益：流转规则集中在一处、可单元测试、非法流转被 reducer 挡掉。

十一、面试高频问答

Section titled “十一、面试高频问答”

Q1：你怎么设计一个可复用的业务组件？

Section titled “Q1：你怎么设计一个可复用的业务组件？”

答：

  1. 先问清楚复用边界：几个业务会用？差异在哪？差异大的就别复用
  2. Props 设计最小化：布尔开关超过 2 个就改成枚举/变体；用 children 插槽替代结构配置
  3. 三件套自带：loading / empty / error 状态由组件统一处理
  4. 透传 className / style / ref，保留二次定制能力
  5. 类型完备：泛型 + as const 枚举 + 状态映射表，编译期防错
  6. 配套文档 + 单元测试

Q2：React 里怎么避免“Props Drilling”（透传地狱）？

Section titled “Q2：React 里怎么避免“Props Drilling”（透传地狱）？”

答：三层递进：

  1. 状态提升到最近公共祖先（最轻量，优先用）
  2. Composition（组合）：把子组件作为 props 传下去，替代透传（children / 插槽）
  3. Context：跨多层级的低频数据（用户、主题、路由） 高频变化的数据不要用 Context，会导致全树重渲染，用外部状态库 + selector。

Q3：复合组件（Compound Components）解决了什么问题？

Section titled “Q3：复合组件（Compound Components）解决了什么问题？”

答：避免“一个组件加十几个布尔 props”。调用方用 JSX 子元素自由组合结构，子组件之间通过共享 Context 通信。缺点是 Context 变化会让所有消费者重渲染，要用 useMemo 和 Context 拆分来优化。典型使用者：Radix UI、Headless UI。

Q4：什么场景用 Render Props，什么场景用 Headless？

Section titled “Q4：什么场景用 Render Props，什么场景用 Headless？”

答：

  • Render Props / children as function：父组件掌控循环逻辑，子组件只管渲染。适合列表项渲染。缺点是每次渲染都创建新函数，破坏 memo
  • Headless：无样式的行为组件，交互和 a11y 复用，样式由调用方决定。适合需要多套视觉风格的设计系统

Q5：怎么保证组件的“性能”？

Section titled “Q5：怎么保证组件的“性能”？”

答：

  1. React.memo + 稳定的 props 引用（useMemo / useCallback）
  2. children 作为元素传递而不是函数，避免每次渲染都创建新函数
  3. 长列表虚拟滚动
  4. Context 拆分：状态 Context 和 dispatch Context 分开
  5. 高频变化的状态用外部 store + selector，不用 Context
  6. useDeferredValue / useTransition 拆分紧急与非紧急更新

Q6：一个组件写多少行算合理？

Section titled “Q6：一个组件写多少行算合理？”

答：没有硬标准，但有信号：

  • 超过 300 行 → 考虑拆分
  • useState 超过 8 个 → 考虑 useReducer 或拆分
  • if/else 分支超过 5 个 → 考虑策略模式或配置表
  • 嵌套 JSX 超过 4 层 → 提取子组件
  • 出现“这个 prop 只有在 XX 情况下才有用” → 拆成两个组件

📝 小结

Section titled “📝 小结”
  • 四条原则:单一职责、Props 契约清晰(不把内部状态暴露成 props)、组合优于配置、有边界的状态归属(状态放在能最小化重渲染的那层)。
  • 组件 API 三选一:受控(完全由外部驱动)、非受控(内部管理,适合简单输入)、混合(初值 + 可控,最常用也最容易写错)。
  • 复合组件(Tabs.Trigger/Tabs.Content)适合多实例场景,把内部协调逻辑封装在 Context 里。
  • Headless 组件只提供行为不提供样式,把样式完全交给使用方,适合做设计系统与主题定制。
  • 复杂交互用 useReducer 显式建模状态机,比一堆 useState 布尔值更可控、更易测。
  • 组件库工程实践:用 useControllableValue 统一受控/非受控、透传 ref、透传 data-*、提供 displayName。
  • 面试加分:讲清「组件封装时最常见的三个坑」——ref 透传、children 覆盖、内部状态无法重置。
