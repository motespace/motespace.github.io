Q1: Monorepo 缺点是什么？

Section titled “Q1: Monorepo 缺点是什么？”

答：

  • 构建慢（即使有缓存）
  • 权限控制难（所有人看所有代码）
  • 依赖冲突（版本兼容）
  • 学习成本（新人要理解整个仓库结构）

Q2: 怎么选版本策略？

Section titled “Q2: 怎么选版本策略？”

答：

  • 设计系统/工具库 -> 固定版本
  • 业务代码 -> 独立版本
  • 看用户期待：用户期望看到一个统一版本号还是多个子版本？

Q3: Changesets 好处？

Section titled “Q3: Changesets 好处？”

答：

  • 强制开发者写 changelog
  • 自动 bump 版本
  • 自动生成 release PR
  • 历史变更可追溯

Q4: 大型 Monorepo 怎么避免代码混乱？

Section titled “Q4: 大型 Monorepo 怎么避免代码混乱？”

答：

  • 严格的 package 边界（每个包有 owner）
  • CODEOWNERS 文件
  • 跨包 import 受限（ESLint rules）
  • CI 检查循环依赖

Q5: 单仓 50+ 包，CI 怎么不慢？

Section titled “Q5: 单仓 50+ 包，CI 怎么不慢？”

答：

  • Turborepo 增量构建 + 远程缓存
  • 按需触发（只跑变更包）
  • 拆 CI（按包分类并行）
  • 用 Nx 的 affected 命令

Section titled “面试追问(深化原 Q1-Q5)”

  • 包发布最佳实践? Changesets 管理版本;语义化版本;主版本升级前发 deprecation 警告
  • TypeScript Project References? 子包独立 tsc 编译;references 配置;tsc -b 增量编译
  • ESLint 跨包配置? 根 eslint-config 包;子包 extends;Flat Config(ESLint 9+)更简洁

📝 小结

Section titled “📝 小结”
  • 版本策略三选一:固定版本(lockstep,适合高度耦合的应用 monorepo)、独立版本(每个包自己发版)、混合(基础包固定+业务包独立)。
  • 推荐 Changesets:改包时加一条 changeset,合并后自动 bump 版本并生成 CHANGELOG,解决「手改 package.json 版本」的老问题。
  • 依赖提升(pnpm dedupe/workspace 协议)与循环依赖是 monorepo 最常见的两个坑,循环依赖在构建时会直接死锁。
  • 内部包的禁止外部发布要用 publishConfig.private: true 兜底,防止误发 npm。
  • CI 策略:按改动范围(--affected)跑最小测试集 + 全量构建验证,配 CODEOWNERS 明确各包负责人。
  • 面试加分:能讲一个真实决策,比如「为什么 UI 包用固定版本而业务应用用独立版本」。
