06 多 Agent 协作

多个 AI Agent 分工执行不同子任务，并行工作，汇总结果。

[[toc]]

6.1 为什么需要多 Agent

Section titled “6.1 为什么需要多 Agent”
单 Agent 多 Agent
串行执行，速度慢 并行执行，速度快
一个 Agent 记住所有上下文 每个 Agent 只关注自己负责的部分
任务一多就混乱 分工清晰，可独立验证
适合简单任务 适合复杂端到端任务

任务：重构 member-h5 的登录模块

单 Agent（串行）： Agent 1：分析代码结构（5min）→ 写新代码（10min）→ 写测试（5min）→ 跑测试（3min） 总计：23 分钟

多 Agent（并行）： Agent 1：分析代码结构（5min） Agent 2：写核心逻辑（10min）← 同时开始 Agent 3：写测试用例（5min）← 同时开始 主 Agent：汇总结果 + 跑集成测试（5min） 总计：20 分钟（且测试和代码是并行出的）

6.2 多 Agent 模式

Section titled “6.2 多 Agent 模式”

模式 1：并行生成（最常用）

Section titled “模式 1：并行生成（最常用）”

多个 Agent 同时生成不同的部分，最后由主 Agent 汇总：

主 Agent（你）： 任务：重构 src/utils/ 下的 5 个工具文件

Agent A（负责文件 1-2）： - handleFile.ts - dateUtils.ts

Agent B（负责文件 3-4）： - currency.ts - storage.ts

Agent C（负责文件 5 + 测试）： - request.ts - 编写以上所有文件的单元测试

主 Agent： - 汇总 3 个 Agent 的输出 - 检查是否有冲突 - 运行类型检查 + 测试 - 报告最终结果

模式 2：流水线（Review to Fix to Test）

Section titled “模式 2：流水线（Review to Fix to Test）”
  • Agent 1（Generator）：根据需求生成代码
  • Agent 2（Reviewer）：审查 Agent 1 的代码，列出问题
  • Agent 3（Fixer）：修复 Agent 2 发现的问题
  • Agent 4（Tester）：编写测试用例
  • 主 Agent：汇总测试结果，报告最终状态

模式 3：主从协调

Section titled “模式 3：主从协调”
  • 主 Agent（规划 + 协调）：任务拆解 → 分发给子 Agent → 监控进度 → 汇总结果
  • 子 Agent（执行）：每个子 Agent 独立执行自己的子任务，完成时报告诉主 Agent，遇到问题时向主 Agent 提问

6.4 Agent 协作的坑

Section titled “6.4 Agent 协作的坑”
坑 表现 解决
上下文丢失 子 Agent 改了某个文件，但主 Agent 不知道 用 Thread 消息同步，或者让主 Agent 最后汇总
冲突 两个 Agent 同时改同一个文件的不同地方 让不同 Agent 改不同文件，或者加锁
重复工作 两个 Agent 生成了相同的代码 主 Agent 做去重检查
依赖顺序 Agent B 依赖 Agent A 的输出 必须串行，或者明确依赖关系

6.5 什么场景用多 Agent

Section titled “6.5 什么场景用多 Agent”
场景 用还是不用
多个独立文件同时重构 用（并行生成）
PR 需要拆分（改了 N 个不相关的功能） 用（split-to-prs）
单文件修改 不用（单 Agent 即可）
需要互相依赖的修改 谨慎（确保依赖顺序正确）
技术调研（多个问题并行查） 用（并行调研）

面试常考

Section titled “面试常考”

Q1:为什么需要多 Agent?

Section titled “Q1:为什么需要多 Agent?”

答:

  • 单一 Agent 上下文有限,大型任务容易丢细节
  • 多 Agent 各司其职:研究 / 实现 / 审查 / 文档
  • 类似团队分工:不同角色独立思考 + 协作

Q2:多 Agent 模式 3 种?

Section titled “Q2:多 Agent 模式 3 种?”

答:

  • 串行:A 完成 → B 接续(流水线)
  • 并行:多个 A 同时处理(分工)
  • 协商:Agent 之间互相对话(达成共识)
  • 选:流程明确用串行;独立任务用并行;争议时用协商

Q3:多 Agent 协作的坑?

Section titled “Q3:多 Agent 协作的坑?”

答:

  • 上下文丢失:Agent 之间传递信息不完整
  • 循环依赖:A 等 B,B 等 A
  • 成本爆炸:5 个 Agent = 5 倍 token
  • 原则:每个 Agent 职责清晰;有协调者

📝 小结

Section titled “📝 小结”
  • 多 Agent 的价值在并行与分工:一个查源码、一个改代码、一个写测试、一个做 review,最后由主 Agent 汇总。
  • 模式上分「并行探索」和「流水线协作」;并行适合互不依赖的调研,流水线适合有依赖的实现链。
  • 关键纪律:每个 Agent 一个明确任务 + 独立的写作用域,否则互相覆盖、重复劳动。
  • 常见坑:上下文不共享导致结论冲突、需要等彼此结果造成串行、Agent 数量过多难以追踪。
  • 什么时候值得用多 Agent:任务可切分且可并行(批量迁移、多文件重构、跨库调研);小改动用单 Agent 更快更准。
  • 面试加分:说清「怎么把一个大重构拆成 3 个 Agent 的并行任务,以及怎么合并结果」。
