05 Codex 自动化

用 Codex Automate 和 /loop 实现工程任务自动化，让 AI 帮你监控 CI、依赖更新、发布状态。

[[toc]]

5.1 自动化能做什么

Section titled “5.1 自动化能做什么”
场景 人工做法 自动化做法
依赖版本检查 每周手动查一次 npm outdated 每周 AI 自动查 + 报告 + 评估是否升级
CI 失败通知 等 CI 红了才知道 AI 监控 CI，失败时分析原因 + 报告
PR 冲突处理 手动 merge base + 解决冲突 AI 自动 merge + 解决 + 提交
发布前检查 逐条人工检查 AI 按清单检查，报告异常
定时健康检查 无 每天 AI 检查页面是否可访问

5.2 Codex Automate（定时任务）

Section titled “5.2 Codex Automate（定时任务）”

Codex Automate 是 Codex 的自动化任务功能，可以设置：

  • 触发条件：定时（cron）、GitHub 事件、Slack 消息、Linear 事件等
  • 执行内容：AI Prompt 指令
  • 通知方式：邮件 / Slack / 评论等

创建 Automate 的标准流程

Section titled “创建 Automate 的标准流程”
  1. 确定触发条件（什么时候跑？）
  2. 确定任务内容（要做什么？）
  3. 确定通知方式（结果通知谁？）
  4. 测试运行（验证正确性）
  5. 上线监控

示例 1：每周依赖版本检查

Section titled “示例 1：每周依赖版本检查”

触发：每周一 9:00（cron: 0 9 * * 1）

任务： 检查 member-h5 项目的依赖更新：

  1. 运行 npm outdated –json
  2. 对比 package.json 和 node_modules 版本
  3. 筛选出有 breaking change 的大版本更新
  4. 评估升级风险（是否影响现有功能）
  5. 输出报告，标注：安全更新 / 功能更新 / 破坏性更新

通知：Slack #dev-alerts 频道

示例 2：PR Merge 前自动化检查

Section titled “示例 2：PR Merge 前自动化检查”

触发：PR 检查通过（git_ci 事件）

任务： PR 合并前做最后一次检查：

  1. 确认构建成功（npm run build）
  2. 确认类型检查通过（tsc –noEmit）
  3. 确认 ESLint 无警告
  4. 确认测试覆盖率没有下降
  5. 确认 CHANGELOG 已更新

如果有任何一项失败： - 在 PR 下评论说明失败原因 - 给出修复建议 - 标记需要人工介入

如果全部通过： - PR 下评论：自动检查全部通过，可以合并

示例 3：CI 失败自动分析

Section titled “示例 3：CI 失败自动分析”

触发：CI 检查失败（git_ci）

任务： 分析构建失败的根因：

  1. 读取失败的 CI 日志
  2. 找出第一个报错信息
  3. 分析是代码问题还是 CI 本身问题
  4. 如果是代码问题，给出：
    • 报错文件 + 行号
    • 错误原因
    • 修复建议
  5. 在 PR 下评论报告

5.3 Codex /autopilot（PR 维护）

Section titled “5.3 Codex /autopilot（PR 维护）”

/autopilot 是 Codex 内置的 PR 维护 Agent，核心功能：

  1. Merge 冲突：自动 merge base 并解决冲突
  2. 评论审查：处理 PR 上的 Review 评论（fix / dismiss / ask）
  3. CI 失败：自动修复 CI 问题
  4. 状态汇报：报告当前 PR 状态（可合并 / 阻塞中）

使用 /autopilot

Section titled “使用 /autopilot”

/autopilot 的行为规范

Section titled “/autopilot 的行为规范”
操作 何时做
Fix（修复） 评论指出了真实问题，在 PR 范围内
Dismiss（忽略） 评论无效或已过时，但需要回复说明原因
Ask（提问） 安全/隐私/迁移/并发问题，不确定时不猜

5.4 Codex /loop（定期提醒）

Section titled “5.4 Codex /loop（定期提醒）”

/loop 是在当前 Session 中定期执行一个 Prompt，适合：

  • 定时检查某个状态（每 5 分钟检查一次 CI 状态）
  • 监控某个任务进度
  • 定期给你发状态更新

5.5 自动化安全规则

Section titled “5.5 自动化安全规则”

AI 自动化有风险，以下规则必须遵守：

  1. 禁止 AI 自动合并 PR（merge 必须人工确认）
  2. 禁止 AI 自动修改 CI 配置文件（只修复代码问题）
  3. 禁止 AI 自动发布到生产（必须人工触发）
  4. 涉及安全的操作（权限/密钥/迁移）必须人工确认
  5. AI 发现问题时，只报告，不自动执行修复

面试常考

Section titled “面试常考”

Q1:Codex Automate 什么时候用?

Section titled “Q1:Codex Automate 什么时候用?”

答:

  • heartbeat:监控状态(PR CI / 监控面板);状态变化才通知
  • cron:定时任务(日报、清理、轮询)
  • 原则:不要每分钟刷;只在有意义变化时唤醒

Q2:/autopilot 做什么?

Section titled “Q2:/autopilot 做什么?”

答:

  • 维护 PR 合并就绪
  • 自动 triage 评论、解决冲突、修 CI
  • 失败时通知人介入
  • 适合:CI 长跑、依赖多、需要持续 review 的 PR

Q3:自动化安全规则?

Section titled “Q3:自动化安全规则?”

答:

  • 不能自动推送到 main
  • 不能自动删除 / 改权限
  • 不能自动发外部请求(邮件/通知除外)
  • 所有动作留审计日志

📝 小结

Section titled “📝 小结”
  • 自动化三件套:定时任务(每天扫依赖更新)、PR 维护机器人(CI 失败自动修)、定期巡检(依赖安全、埋点告警)。
  • 自动化的前提是幂等 + 可回滚:任何自动改动都要能被人 review 和一键撤销。
  • 定时任务适合做「只读 + 汇报」的事(周报、依赖巡检),写代码类自动化要限制权限与范围。
  • 安全规则:最小权限、限定目录/分支、白名单操作、留审计日志。
  • 面试加分:讲一个真实自动化案例,比如「每周自动扫描依赖漏洞并提 PR,人工只做确认」。
