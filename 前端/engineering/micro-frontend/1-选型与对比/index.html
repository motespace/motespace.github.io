微前端选型与对比

微前端不是“银弹”，用错了比不用还糟糕。本文用对比表 + 选型决策树帮你判断。

一、5 种主流方案概览

Section titled “一、5 种主流方案概览”
方案 原理 上手成本 隔离性 性能 适用场景
iframe 浏览器原生隔离 ⭐ 极低 ⭐⭐⭐⭐⭐ ⭐⭐ 完全独立子应用
qiankun JS 沙箱 + Proxy ⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐ 已有 SPA 微前端化
micro-app Web Components ⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐ 京东系、追求简单
wujie Web Components + iframe ⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐ 完美隔离 + 简单
Module Federation Webpack 5 / Vite ⭐⭐⭐⭐ ⭐⭐ ⭐⭐⭐⭐⭐ 跨应用共享模块

二、iframe

Section titled “二、iframe”

2.1 原理

Section titled “2.1 原理”

每个子应用是独立 iframe，通过 postMessage 通信。

2.2 优点

Section titled “2.2 优点”
  • ✅ 完美隔离：浏览器原生沙箱
  • ✅ 零改造成本：子应用完全独立
  • ✅ 跨框架：Vue/React/Angular 任意混用

2.3 缺点

Section titled “2.3 缺点”
  • ❌ 通信复杂：只能 postMessage
  • ❌ URL 不同步：iframe 内路由变化主应用不知道
  • ❌ 性能差：iframe 加载 + 多层 window
  • ❌ SEO 不友好：搜索引擎难索引

2.4 适用场景

Section titled “2.4 适用场景”
  • 完全独立的子系统（如管理后台嵌入客服系统）
  • 第三方系统嵌入（如嵌入阿里云控制台）

三、qiankun

Section titled “三、qiankun”

3.1 原理

Section titled “3.1 原理”

基于 single-spa + Proxy 沙箱 + 样式隔离

3.2 沙箱（核心）

Section titled “3.2 沙箱（核心）”

3.3 优点

Section titled “3.3 优点”
  • ✅ JS 沙箱：子应用 window 隔离
  • ✅ CSS 隔离：动态加载 + scope
  • ✅ 生态成熟：阿里出品、生产案例多
  • ✅ 支持所有框架

3.4 缺点

Section titled “3.4 缺点”
  • ❌ 样式隔离不完美（动态样式加载有漏洞）
  • ❌ 改造成本：要改 webpack 配置（暴露 entry）
  • ❌ 性能：每个子应用独立运行时

3.5 适用场景

Section titled “3.5 适用场景”
  • 已有 SPA 微前端化（最常见）
  • 大型中后台
  • 多团队并行开发

四、micro-app

Section titled “四、micro-app”

4.1 原理

Section titled “4.1 原理”

基于 Web Components + Custom Elements

4.2 优点

Section titled “4.2 优点”
  • ✅ 极简：&lt;micro-app url="..." /&gt; 一行集成
  • ✅ 基于 Web 标准：浏览器原生支持
  • ✅ 零改造：子应用几乎不用改
  • ✅ 沙箱完善

4.3 缺点

Section titled “4.3 缺点”
  • ❌ 生态较弱（相比 qiankun）
  • ❌ IE 兼容性差（依赖 Custom Elements）

4.4 适用场景

Section titled “4.4 适用场景”
  • 京东系项目
  • 追求简单 + 快速接入

五、wujie（无界）

Section titled “五、wujie（无界）”

5.1 原理

Section titled “5.1 原理”

Web Components + iframe 沙箱 的混合方案

5.2 优点

Section titled “5.2 优点”
  • ✅ 完美沙箱：浏览器原生隔离
  • ✅ 样式不冲突：iframe 内独立
  • ✅ 预加载：iframe 池加速

5.3 缺点

Section titled “5.3 缺点”
  • ❌ iframe 的部分缺点：URL 同步复杂

5.4 适用场景

Section titled “5.4 适用场景”
  • 完美隔离需求
  • 不想改造子应用

六、Module Federation

Section titled “六、Module Federation”

6.1 原理

Section titled “6.1 原理”

运行时共享模块（不是完整应用）

  • 应用 A 暴露 Button 组件
  • 应用 B 在运行时通过 import('@appA/Button') 加载

6.2 优点

Section titled “6.2 优点”
  • ✅ 运行时共享：无需发布 npm 包
  • ✅ 跨应用复用：组件库、工具库
  • ✅ 独立部署：每个应用独立发版

6.3 缺点

Section titled “6.3 缺点”
  • ❌ 构建工具绑定：要 Webpack 5 / Vite Federation
  • ❌ 调试复杂：跨应用 source map
  • ❌ 版本管理：依赖冲突处理

6.4 适用场景

Section titled “6.4 适用场景”
  • 设计系统跨应用共享
  • 微前端 + 组件库统一
  • 多团队复用基础能力

七、选型决策树

Section titled “七、选型决策树”

八、面试高频追问

Section titled “八、面试高频追问”

Q1: 怎么选微前端方案？

Section titled “Q1: 怎么选微前端方案？”

答：看 4 个维度：

  1. 隔离性需求：完美隔离 → iframe/wujie；JS 隔离 → qiankun
  2. 改造成本：不改造 → iframe/micro-app；愿意改造 → qiankun/MF
  3. 生态：成熟案例 → qiankun
  4. 技术栈：Webpack 5 → MF 优势；Vite → micro-app/wujie

Q2: qiankun 的沙箱有什么坑？

Section titled “Q2: qiankun 的沙箱有什么坑？”

答：

  • 动态加载 CSS 会有全局污染（用 scope 模式）
  • Proxy 不支持 with 语句
  • 浏览器 API（如 localStorage）需要自己封装

Q3: Module Federation vs qiankun 怎么选？

Section titled “Q3: Module Federation vs qiankun 怎么选？”

答：

  • MF：跨应用共享模块（组件、工具），不是完整微前端
  • qiankun：完整子应用微前端化
  • 可以组合：qiankun 子应用之间用 MF 共享设计系统

Q4: 微前端的性能问题怎么优化？

Section titled “Q4: 微前端的性能问题怎么优化？”

答：

  1. 预加载：子应用空闲时加载
  2. keep-alive：子应用不卸载
  3. 共享公共依赖：避免重复加载（MF 天然解决）
  4. 路由级缓存

Q5: 微前端怎么调试？

Section titled “Q5: 微前端怎么调试？”

答：

  • 主应用 + 子应用分别调试
  • 子应用独立运行时（绕过主应用）
  • 用 __webpack_require__ 调试联邦模块

面试追问(深化原 Q1-Q5)

Section titled “面试追问(深化原 Q1-Q5)”
  • 微前端 3 大流派? 路由分发(qiankun)、构建时(Module Federation)、iframe(隔离最强)
  • qiankun vs Module Federation 选哪个? 多技术栈选 qiankun;同技术栈(Vue/React 混)选 MF
  • 微前端适合什么场景? 多团队独立交付;历史系统迁移;独立域名/子应用
  • 不推荐场景? 小型项目(2-3 人团队);性能敏感(子应用加载开销)

📝 小结

Section titled “📝 小结”
  • 五种方案要按隔离强度分类:iframe(浏览器级隔离)> qiankun/micro-app(JS 沙箱)> wujie(Worker + Web Worker 隔离)> Module Federation(无隔离,只做模块共享)。
  • iframe 隔离最彻底但通信难(要靠 postMessage)、体验差(独立滚动与路由);qiankun 走 Proxy 沙箱 + HTML entry,接入成本适中,是国内最常见选择。
  • wujie 的核心创新是用 Web Worker 隔离 JS 上下文,主应用 DOM 通过 Proxy 操作,解决了沙箱里拿不到真实 DOM 的问题。
  • Module Federation 不是微前端框架,而是构建期模块共享,适合组件级复用(微应用共享设计系统),不适合运行时隔离的多团队应用。
  • 选型决策:需要强隔离与独立部署 → iframe/qiankun;需要共享依赖与设计系统 → Module Federation;团队规模小 → 别上微前端。
  • 面试必须讲的坑:样式隔离(scoping/Shadow DOM)、全局状态共享、公共依赖重复打包导致体积膨胀、跨应用跳转与登录态同步。
