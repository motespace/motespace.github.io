测试体系与选型

测试不是“加分项”，是“基础设施”。本文按“测试金字塔 → 选型 → 覆盖率”组织。

一、测试金字塔

Section titled “一、测试金字塔”

比例建议

Section titled “比例建议”
类型 数量 速度 覆盖目标
单元测试 70% < 1ms/个 工具函数、纯逻辑、Hook
组件测试 20% < 100ms/个 UI 组件 + 表单 + 状态
E2E 测试 10% < 30s/个 关键用户路径

二、3 种测试类型详解

Section titled “二、3 种测试类型详解”

单元测试（Unit Test）

Section titled “单元测试（Unit Test）”

测试一个独立函数、类、Hook：

优点：

  • 速度极快（无 IO）
  • 容易写、容易维护
  • 覆盖率高（能测到边界）

缺点：

  • 测不到组件交互
  • 测不到真实 DOM

组件测试（Component Test）

Section titled “组件测试（Component Test）”

测试 React/Vue 组件，渲染 + 交互：

优点：

  • 测试用户视角的组件行为
  • 接近真实使用

缺点：

  • 比单元测试慢
  • 需要 jsdom / happy-dom

E2E 测试（End-to-End）

Section titled “E2E 测试（End-to-End）”

测试完整用户流程，真实环境跑：

优点：

  • 测试真实流程
  • 跨浏览器 / 跨设备
  • 信心最高

缺点：

  • 慢、不稳定
  • 难调试

三、主流测试框架选型

Section titled “三、主流测试框架选型”

3.1 单元测试

Section titled “3.1 单元测试”
框架 速度 配置 兼容 推荐
Jest 中 中 老牌 React/Vue 老项目
Vitest 快 低 Vite 原生 Vite 项目
Mocha + Chai 中 高 老 自定义需求
Node Test Runner 中 低 内置 小项目

推荐：Vite 项目用 Vitest（速度 + 兼容性 + API 类似 Jest）

3.2 组件测试

Section titled “3.2 组件测试”
框架 用途
@testing-library/react React 组件测试
@testing-library/vue Vue 组件测试
Vue Test Utils Vue 官方测试工具
jsdom Node 端模拟 DOM
happy-dom 比 jsdom 快 3x

3.3 E2E 测试

Section titled “3.3 E2E 测试”
框架 浏览器 速度 推荐
Playwright Chromium / Firefox / WebKit 快 多浏览器
Cypress Chromium / Firefox / Edge 中 调试体验好
Puppeteer Chromium 快 Chrome only
Selenium 全浏览器 慢 跨语言

推荐：Playwright（速度快 + 多浏览器 + 官方维护 + 录屏）

5.3 覆盖率配置在哪配

Section titled “5.3 覆盖率配置在哪配”

覆盖率有两个维度,要分开设:

维度 含义 建议
统计范围 哪些文件算进覆盖率 include 只圈业务代码,exclude 排掉测试文件与入口
阈值红线 低于多少就失败 核心逻辑 70%+;全项目别一刀切

具体的 vitest.config.ts 配置写法、thresholds 字段含义、覆盖率报告生成 → Vitest 单元测试

六、Mock 策略

6.1 单元测试 Mock

6.2 组件测试 Mock

Section titled “6.2 组件测试 Mock”

组件测试的 Mock 分两类:

  • 模块级:vi.mock / vi.stubGlobal 替换掉模块或全局(如 fetch)
  • 网络级:MSW 在网络层拦截,请求真的发出去了,只是被 mock server 应答——更接近生产

原则:优先 mock 到最外层边界(网络),而不是把组件内部拆碎;mock 越靠里,测试越接近「测 mock」。

具体写法(vi.stubGlobal / MSW handler / findBy 等待异步)→ Vitest 单元测试 第五节

6.3 MSW（Mock Service Worker）

Section titled “6.3 MSW（Mock Service Worker）”

推荐：拦截真实网络层，比 mock 函数更接近真实。

九、面试高频追问

Section titled “九、面试高频追问”

Q1: 你们的测试覆盖率？

Section titled “Q1: 你们的测试覆盖率？”

答：业务代码 70%+，工具库 85%+。CI 会卡死低于阈值。

Q2: 单元测试和 E2E 测试怎么选？

Section titled “Q2: 单元测试和 E2E 测试怎么选？”

答：

  • 单元：测工具函数、纯逻辑、Hook
  • 组件：测组件交互、表单
  • E2E：测关键路径（登录、支付）
  • 比例 70:20:10

Q3: 怎么 Mock HTTP 请求？

Section titled “Q3: 怎么 Mock HTTP 请求？”

答：推荐 MSW（Mock Service Worker）。拦截 Service Worker 层，比 mock fetch 更真实。

Q4: 怎么测试异步组件？

Section titled “Q4: 怎么测试异步组件？”

答：用 findBy 查询（自动等异步），或者 waitFor 等待。

Q6: 测试金字塔是什么？

Section titled “Q6: 测试金字塔是什么？”

答：底层多（单元）、中间中（组件）、顶层少（E2E）。成本和速度权衡。

面试追问(深化原 Q1-Q5)

Section titled “面试追问(深化原 Q1-Q5)”
  • 测试金字塔? 单元(70%) + 集成(20%) + E2E(10%);底层快、上层慢
  • 测试覆盖率意义? 衡量测试广度,不衡量质量;盲目追求 100% 会写无意义测试
  • TDD 适合什么? 业务逻辑、工具函数、bug 修复;不适合 UI 探索
  • Mock 策略? 单元测试 mock 一切;集成测试 mock 外部;E2E 不 mock

📝 小结

Section titled “📝 小结”
  • 测试金字塔不是教条:现代前端更偏倒金字塔(E2E 少而精 + 集成测试为主 + 大量单元测试),因为 E2E 慢且易碎。
  • 三种类型:单元测试(纯函数/组件逻辑)、集成测试(组件 + 真实交互,用户行为保障)、E2E(真实浏览器跑关键路径)。
  • 选型:Vite 项目用 Vitest(与 Vite 同源,快)、E2E 用 Playwright(跨浏览器、自动等待、并行、trace 调试)。
  • 覆盖率是参考不是目标:核心业务逻辑(工具函数、状态机、金额计算)要求高覆盖,展示组件不强求。
  • Mock 策略:mock 越靠近被测对象越好;接口用 MSW 在网络层拦截,比 mock 模块更接近真实。
  • 面试加分:讲「我们怎么把 E2E 从 40 分钟压到 8 分钟」——并行 + 只测核心路径 + 用 API 复用登录态。
