测试体系与选型 ​

测试不是"加分项"，是"基础设施"。本文按"测试金字塔 → 选型 → 覆盖率"组织。

一、测试金字塔 ​

        /\
       /E2E\         <- 少而精：关键路径
      /------\
    /  组件测试  \      <- 中等：UI 组件 + 交互
   /------------\
  /   单元测试     \    <- 多：函数、工具、Hook
 /----------------\

比例建议 ​

类型数量速度覆盖目标
单元测试70%< 1ms/个工具函数、纯逻辑、Hook
组件测试20%< 100ms/个UI 组件 + 表单 + 状态
E2E 测试10%< 30s/个关键用户路径

二、3 种测试类型详解 ​

单元测试（Unit Test） ​

测试一个独立函数、类、Hook：

js
// 测试 utils/format.ts
test('formatMoney formats CNY', () => {
  expect(formatMoney(1234.56, 'CNY')).toBe('¥1,234.56')
})

优点：

  • 速度极快（无 IO）
  • 容易写、容易维护
  • 覆盖率高（能测到边界）

缺点：

  • 测不到组件交互
  • 测不到真实 DOM

组件测试（Component Test） ​

测试 React/Vue 组件，渲染 + 交互：

jsx
// 测试 Button 组件
test('Button calls onClick when clicked', () => {
  const onClick = vi.fn()
  render(<Button onClick={onClick}>Click</Button>)
  fireEvent.click(screen.getByText('Click'))
  expect(onClick).toHaveBeenCalledTimes(1)
})

优点：

  • 测试用户视角的组件行为
  • 接近真实使用

缺点：

  • 比单元测试慢
  • 需要 jsdom / happy-dom

E2E 测试（End-to-End） ​

测试完整用户流程，真实环境跑：

js
// Playwright
test('user login flow', async ({ page }) => {
  await page.goto('/login')
  await page.fill('input[name="username"]', 'tom')
  await page.fill('input[name="password"]', '123456')
  await page.click('button[type="submit"]')
  await expect(page).toHaveURL('/dashboard')
})

优点：

  • 测试真实流程
  • 跨浏览器 / 跨设备
  • 信心最高

缺点：

  • 慢、不稳定
  • 难调试

三、主流测试框架选型 ​

3.1 单元测试 ​

框架速度配置兼容推荐

五、覆盖率指标 ​

5.1 4 个维度 ​

- 行覆盖 (Line Coverage)：执行到的代码行数 / 总行数
- 分支覆盖 (Branch Coverage)：执行到的分支数 / 总分支数
- 函数覆盖 (Function Coverage)：执行到的函数数 / 总函数数
- 语句覆盖 (Statement Coverage)：执行到的语句数 / 总语句数

5.2 合理目标 ​

项目类型行覆盖率
工具库80%+
业务代码60-70%
长期维护70%+
新项目70%+

5.3 Vitest 覆盖率配置 ​

ts
// vitest.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html', 'json'],
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['src/**/*.test.{ts,tsx}', 'src/main.ts'],
      thresholds: {
        lines: 70,
        branches: 60,
        functions: 70,
        statements: 70,
      },
    },
  },
})

六、Mock 策略 ​

6.1 单元测试 Mock ​

ts
import { vi } from 'vitest'

// Mock 函数
const onClick = vi.fn()
expect(onClick).toHaveBeenCalled()

// Mock 模块
vi.mock('./api', () => ({
  fetchUser: vi.fn().mockResolvedValue({ name: 'tom' }),
}))

// Mock 时间
vi.useFakeTimers()
vi.advanceTimersByTime(1000)

6.2 组件测试 Mock ​

tsx
import { render, screen, fireEvent } from '@testing-library/react'
import { vi } from 'vitest'

// Mock 整个 fetch
vi.stubGlobal('fetch', vi.fn(() =>
  Promise.resolve({
    json: () => Promise.resolve({ name: 'tom' }),
  })
))

test('shows user data', async () => {
  render(<UserProfile userId="123" />)
  expect(await screen.findByText('tom')).toBeInTheDocument()
})

6.3 MSW（Mock Service Worker） ​

推荐：拦截真实网络层，比 mock 函数更接近真实。

ts
// src/mocks/handlers.ts

七、测试驱动开发（TDD） ​

7.1 红-绿-重构循环 ​

1. 红：写失败的测试
2. 绿：让测试通过（写最小实现）
3. 重构：优化代码（保持测试通过）

7.2 实战：写 formatMoney 的 TDD ​

ts
// 1. 红
test('formatMoney formats CNY', () => {
  expect(formatMoney(1234.56, 'CNY')).toBe('¥1,234.56')  // 函数不存在
})

// 2. 绿（最小实现）
function formatMoney(n: number, currency: string): string {
  return `¥${n}`  // 不对但让测试通过
}

// 3. 重构
function formatMoney(n: number, currency: string): string {
  const formatter = new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency,
  })
  return formatter.format(n)
}

九、面试高频追问 ​

Q1: 你们的测试覆盖率？ ​

答：业务代码 70%+，工具库 85%+。CI 会卡死低于阈值。

Q2: 单元测试和 E2E 测试怎么选？ ​

答：

  • 单元：测工具函数、纯逻辑、Hook
  • 组件：测组件交互、表单
  • E2E：测关键路径（登录、支付）
  • 比例 70:20:10

Q3: 怎么 Mock HTTP 请求？ ​

答：推荐 MSW（Mock Service Worker）。拦截 Service Worker 层，比 mock fetch 更真实。

Q4: 怎么测试异步组件？ ​

答：用 findBy 查询（自动等异步），或者 waitFor 等待。

Q6: 测试金字塔是什么？ ​

答：底层多（单元）、中间中（组件）、顶层少（E2E）。成本和速度权衡。

面试追问(深化原 Q1-Q5) ​

  • 测试金字塔? 单元(70%) + 集成(20%) + E2E(10%);底层快、上层慢
  • 测试覆盖率意义? 衡量测试广度,不衡量质量;盲目追求 100% 会写无意义测试
  • TDD 适合什么? 业务逻辑、工具函数、bug 修复;不适合 UI 探索
  • Mock 策略? 单元测试 mock 一切;集成测试 mock 外部;E2E 不 mock
