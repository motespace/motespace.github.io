Q1: 怎么定性能指标？

Section titled “Q1: 怎么定性能指标？”

答：4 类——加载性能（TTFB/FCP/LCP）、交互性能（INP）、视觉稳定（CLS）、网络性能（接口耗时）。再叠业务指标（首屏可点击、关键接口 P95）。

Q2: LCP 怎么测？

Section titled “Q2: LCP 怎么测？”

答：用 web-vitals 库的 onLCP，自动监控页面上最大的内容绘制时间。

Q3: 性能报警阈值怎么定？

Section titled “Q3: 性能报警阈值怎么定？”

答：基于历史均值 + 业务需求。LCP > 2.5s 是 Google 推荐阈值。报警阈值设 4s（更宽松，避免误报）。

Q4: Performance Budget 怎么落地？

Section titled “Q4: Performance Budget 怎么落地？”

答：Lighthouse CI 集成到 GitHub Actions，每次 PR 自动跑 Lighthouse，分数 < 90 或某指标超阈值则 CI 失败。

Q5: 自建监控 vs Sentry？

Section titled “Q5: 自建监控 vs Sentry？”

答：

  • Sentry：错误监控 + Source Map 还原是王者
  • 自建：性能埋点、业务埋点、漏斗分析更灵活
  • 实战：错误用 Sentry，性能/业务用自建 + Grafana

面试追问(深化原 Q1-Q5)

Section titled “面试追问(深化原 Q1-Q5)”
  • 性能埋点 2 种方式? Performance API(精准);上报打点(自定义)
  • FCP/LCP 怎么采集? new PerformanceObserver(entryTypes: ['paint']) / ['largest-contentful-paint']
  • INP 替代 FID? FID 只测首次输入;INP 测整个会话(更准,2024 替代 FID)
  • 长任务监控? PerformanceObserver({ entryTypes: ['longtask'] });> 50ms 卡顿
  • 数据上报策略? 抽样(10%)、节流(每分钟最多 N 条)、合并(batch 发送)

📝 小结

Section titled “📝 小结”
  • 指标分三层:Web Vitals(LCP/INP/CLS)、真实用户监控(RUM,采集真实用户数据)、业务指标(下单成功率、页面转化)。
  • 用 PerformanceObserver 采集 LCP/CLS/INP/FID 与资源耗时,配合 navigator.connection、UA 一起上报。
  • 报警要基于同比/环比而非固定阈值:错误率突增、P95 恶化、转化率下跌,比「错误数 > 100」更有效。
  • 分母很重要:错误率要看「受影响用户数 / 活跃用户数」,只看错误数在大盘下跌时会误报。
  • 性能预算:在 CI 里给 bundle 体积、关键指标设上限并卡住构建;这是把性能治理前移到 CI 而不是上线后救火。
  • 数据可视化用 Grafana + Prometheus(指标)+ Loki(日志),前端上报走自建采集接口或 Sentry Performance。
  • 面试常问「怎么用数据驱动优化」——先埋点定义指标 → 看分布不看均值 → 找长尾 → 定预算 → CI 卡口。
