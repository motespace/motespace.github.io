线上问题定位与降级

“用户说页面打不开了，你怎么查？”——比“你会不会写代码”更能区分 1 年和 5 年的候选人。

一、报障排查 SOP

Section titled “一、报障排查 SOP”

🔑 止损优先于定位。这是资深工程师的思维：线上问题先止血，再查因。面试时把这个顺序说出来，比背一堆工具名有用。

二、常见根因速查表

Section titled “二、常见根因速查表”
现象 高频根因
页面白屏,Console 报 404 发版后资源路径变了(CDN 域名/base 配置错)
页面白屏,Console 报语法错误 chunk 分包后某个 JS 未发布成功 / 缓存了旧 HTML 引用了已删的 chunk
样式全丢 CSS 加载失败 / CSP 拦截 / 打包抽出了 CSS 但没部署
接口全 401 Token 过期 / 刷新逻辑有并发 bug / 域名变更
特定用户才出错 数据脏(字段为 null/超长)/ 浏览器版本 / 权限数据不同
特定区域才出错 DNS / CDN 节点 / 运营商劫持
偶发白屏 竞态条件 / 偶发接口失败未兜底 / 内存泄漏累积
首屏慢 未做代码分割 / 巨型依赖(如 moment/lodash 全量) / 图片未压缩

“chunk 404” 是发版最经典的事故：HTML 被 CDN 缓存了，指向了新版本里已经不存在的 chunk。解决：html 文件设置 no-cache + hash 文件长缓存，或用 index.html 不缓存策略。

3.1 功能开关(Feature Flag)

Section titled “3.1 功能开关(Feature Flag)”

⚠️ 开关的代价：代码里会堆积 if (flag) 分支。实践建议：

  • 开关到期必须清理(建个 TODO 任务,约定下线日期)
  • 用 if (flag) return <New/>; return <Old/> 这种“早返回”结构,而不是满屏三元表达式

六、面试高频问答

Section titled “六、面试高频问答”

Q1：线上用户说“页面打不开”，你的排查顺序是什么？

Section titled “Q1：线上用户说“页面打不开”，你的排查顺序是什么？”

答：

  1. 先确认影响面（多少用户、什么功能、什么时间开始）
  2. 看监控：错误率、接口成功率、资源加载失败、白屏率
  3. 按版本 release 聚合，看是不是新版本引入
  4. 用 Sentry 的用户操作轨迹复现
  5. 先止损（回滚/关开关/降级），再深入定位
  6. 事后复盘，产出带 owner 和 deadline 的改进项

Q2：前端怎么做降级？

Section titled “Q2：前端怎么做降级？”

答：

  • 开关降级：功能开关从远端拉，支持按租户/百分比灰度
  • 数据降级：缓存数据兜底（placeholderData）、接口重试策略区分 4xx/5xx
  • 渲染降级：ErrorBoundary 局部兜底而不是整页白屏、骨架屏代替空白
  • 极端降级：按顺序关功能直到主流程可用
  • 前提是每条降级路径都有测试，否则真降级时才发现是坏的

Q3：发版后白屏怎么快速定位？

Section titled “Q3：发版后白屏怎么快速定位？”

答：

  • Console 看是不是 chunk 404 / JS 语法错误
  • Network 看哪个资源挂了
  • 回头查发版记录：是不是改了 base/CDN 路径、删了旧 chunk、缓存了 HTML
  • 应急：清 CDN 缓存 + 回滚 html
  • 根治：html 不缓存 + chunk 长缓存 + 发布前资源校验脚本

Q4：怎么保证降级功能本身不会挂？

Section titled “Q4：怎么保证降级功能本身不会挂？”

答：降级路径也要有测试覆盖(CI 里跑 e2e,专门测开关关闭的分支);开关要有监控(谁在用、走的是新路径还是老路径);开关要设下线时间,避免长期分叉。老路径不能只靠人记得维护。

Q5：错误率怎么定义才有意义？

Section titled “Q5：错误率怎么定义才有意义？”

答：用分母(总请求数/总 PV)算比例,不用绝对数。配合时间窗口和持续时长(for: 5m)避免瞬时抖动误报。再按 release、页面、接口维度切分,才能定位到具体是谁的问题。

📝 小结

Section titled “📝 小结”
  • 排查 SOP:先止血(降级/回滚/关开关)→ 再定位(错误聚合、用户反馈、日志、复现)→ 最后复盘定改进。
  • 前端能做的降级:功能开关(关掉出问题的模块)、接口兜底数据、静态兜底页、请求超时返回缓存、局部错误边界。
  • 发布策略:灰度(按用户比例/租户/白名单)→ 观察指标 → 全量;必须能一键回滚,所以前端产物要带版本号且不可变(内容 hash 文件名)。
  • 回滚的前提是「上一版本产物还在」,所以要保留 N 个历史版本并让 CDN 支持按版本回切。
  • 复盘模板:时间线、影响面、根因(直接+深层)、处置过程、待改进项(必须有 owner 和 deadline)。
  • 面试加分:讲一次真实事故:现象 → 定位手段 → 止血 → 长期改进(加监控/加测试/加开关)。
