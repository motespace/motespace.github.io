UniApp 跨端选型与综合问题

面试里最常问的是「原生小程序、uni-app、Taro、React Native 怎么选」。 这题考的不是 API 熟不熟,而是你知不知道每条路线的代价。

1. 四条路线的本质差异

Section titled “1. 四条路线的本质差异”

关键分界:

小程序 H5 原生 App
原生小程序 ✅ ❌ ❌
uni-app ✅ ✅ ✅(通过原生插件/或打包成小程序)
Taro ✅ ✅ ✅(RN)
React Native ❌ ❌ ✅

2. 逐个对比

Section titled “2. 逐个对比”

2.1 原生小程序

Section titled “2.1 原生小程序”
  • 优势:性能天花板最高、平台新特性第一时间可用、审核通过率高
  • 代价:一套代码只能跑一个平台;组件库生态弱;没有热更新
  • 适合:只做微信小程序、追求极致性能或用平台新能力(比如微信的「同声传译」类 API)

2.2 uni-app

Section titled “2.2 uni-app”
  • 优势:
    • Vue 语法,前端同学零成本上手
    • 一套代码编译到微信/支付宝/抖音/百度 + H5 + App(uni-app x 用 Kotlin 写原生层)
    • 生态成熟:组件库、插件市场、DCloud 的云打包
    • 条件编译做平台差异隔离
  • 代价:
    • 性能有损耗:uni-app 的 DOM 方案在 App 端走 WebView,复杂交互不如原生
    • 各平台差异只能靠条件编译硬扛,代码会分裂
    • 社区问题排查成本高(底层是各端的坑)

2.3 Taro

Section titled “2.3 Taro”
  • 优势:React 语法 + TS;同样一套编译到小程序/H5/RN;小程序端性能比 uni-app 的 DOM 方案更可控
  • 代价:生态比 uni-app 小;RN 端仍要写原生;React 开发者才顺手

2.4 React Native

Section titled “2.4 React Native”
  • 优势:真原生视图,性能和交互体验接近原生;一套 iOS/Android
  • 代价:不能编译到小程序;要装 RN 环境;原生模块要自己写桥接;首屏和包体都比 WebView 大

3. 选型决策树

Section titled “3. 选型决策树”

务实建议:先用 uni-app/Taro 把 80% 的功能铺到多端,再把剩下 20% 的性能敏感页面 用条件编译换成各端原生实现。这叫「渐进式多端」,比一上来就写两套代码现实得多。

4. 渐进式多端的具体做法

Section titled “4. 渐进式多端的具体做法”

条件编译的坑:

  • 条件块里的代码其它平台完全不存在,写错也不会报错,只在对应平台暴露
  • 条件块不能跨越函数体边界,要在语法完整的位置
  • 平台标识写错(如 MP-WEIXIN 写成 mp-weixin)不报错,条件块直接失效——必须实测

5. 多端一致性怎么保证

Section titled “5. 多端一致性怎么保证”

5.1 抽象「能力」而不是「平台」

Section titled “5.1 抽象「能力」而不是「平台」”

5.2 差异用配置表收敛

Section titled “5.2 差异用配置表收敛”

5.3 自动化多端回归

Section titled “5.3 自动化多端回归”

关键是让差异在 CI 里暴露,而不是在用户手里。至少要有:

  • 各端的编译产物大小检查(防止某端突然膨胀)
  • 关键路径的端自动化测试
  • 条件编译块的静态检查(比如用脚本扫 // #ifdef 后面的平台标识是否合法)

6. 常见坑

Section titled “6. 常见坑”
坑 表现 解决
条件编译标识写错 条件块静默失效 用脚本校验标识在白名单里
CSS 单位混用 小程序端 rpx / H5 端 px 用变量统一
组件在两端行为不同 一端正常一端错 关键交互在两端都做真机验证
第三方 SDK 不支持某端 编译失败或运行报错 选型时确认 SDK 的平台支持矩阵
包体积超限 小程序主包 2MB 上限 分包 + 独立分包 + 组件按需引入

7. 面试常考

Section titled “7. 面试常考”

Q1:原生小程序、uni-app、Taro 有什么区别?怎么选?

Section titled “Q1:原生小程序、uni-app、Taro 有什么区别?怎么选?”

答:原生小程序性能最好但只能一个平台、组件生态弱; uni-app 用 Vue 语法编译到小程序/H5/App,生态最成熟、生态问题排查成本高; Taro 是 React 版同类。选型看:团队技术栈(前端 Vue 就 uni-app,React 就 Taro)、 是否只做微信、性能要求有多高、是否需要原生能力。 务实做法是渐进式多端:先一套代码铺 80%,性能敏感的页面用条件编译换各端原生实现。

Q2:uni-app 的性能损耗在哪?

Section titled “Q2:uni-app 的性能损耗在哪?”

答:主要在 App 端——传统 uni-app 走 WebView + DOM 渲染,复杂列表和频繁交互不如原生; uni-app x 用 Kotlin 重写运行时,性能显著改善但生态要重新适配。 小程序端因为渲染模型本身就是异步 setData,损耗相对小。

Q3:条件编译怎么用?有什么坑?

Section titled “Q3:条件编译怎么用?有什么坑?”

答:// #ifdef MP-WEIXIN / // #endif 让代码只在指定平台参与编译。 坑:平台标识写错不报错,条件块直接失效,只有真机才暴露; 条件编译不能跨函数体,要在语法完整的位置; 第三方 SDK 常常只支持部分平台,编译期才报错。

Q4:多端怎么保证行为一致?

Section titled “Q4:多端怎么保证行为一致?”

答:把差异收敛到两层——能力层(storage/login/share 这些做统一抽象, 内部用条件编译)和配置层(平台差异用配置表)。再加 CI 里的多端产物检查和自动化测试, 让差异在流水线里暴露而不是用户手里。
