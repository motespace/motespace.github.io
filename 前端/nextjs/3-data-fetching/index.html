Q1:App Router 数据获取新方式?

Section titled “Q1:App Router 数据获取新方式?”

答:

  • Server Component 直接 await fetch() / await db.query()
  • 不需要 useEffect / SWR / React Query
  • 优势:零客户端 JS、自动去重(同一请求一次)
  • 数据流:Server 拉 → RSC payload → Client hydrate

Q3:客户端数据获取怎么选?

Section titled “Q3:客户端数据获取怎么选?”

答:

  • 静态 → 服务端 fetch(零客户端 JS)
  • 用户特定 → Server Component + cookies
  • 实时/交互(点赞、搜索) → Client + SWR / React Query
  • 乐观更新 → Server Actions + useOptimistic
  • 原则:能服务端拉就不客户端拉(性能 + SEO)

Q4:为什么 Server Component 自动去重?

Section titled “Q4:为什么 Server Component 自动去重?”

答:

  • 同一渲染周期,React 缓存 fetch 结果
  • 多个组件 await 同一 URL → 只发 1 次请求
  • 比 React Query 还好用(零配置)

📝 小结

Section titled “📝 小结”
  • 服务端组件里 fetch 默认带缓存(Next 15 起默认不缓存,需显式 next: { revalidate } 或 cache: 'force-cache'),这是 15 的重大变更,面试要能说清。
  • 并行 vs 串行:无依赖的请求用 Promise.all 并行;有依赖的先 await 前一个再取下一个,否则会形成请求瀑布。
  • generateStaticParams 让动态路由在构建期生成静态页,配合 dynamicParams 控制未预渲染路径的行为。
  • 数据获取要分层:首屏关键数据服务端取,次要数据客户端 useEffect / SWR 取,避免把整个页面拖成 SSR。
  • 错误处理:错误边界靠 error.tsx(客户端组件)+ notFound() + redirect(),不要用 try/catch 吞异常。
  • 面试加分:能说清「RSC 里不能用 useState」的原因——RSC 是无状态的服务端渲染,交互必须下沉到 Client Component。
