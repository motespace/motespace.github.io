Next.js 性能优化体系

Next.js 的性能优化和原生 React 最大的不同:它把「服务端」变成了一个可利用的资源。 能不下发到浏览器的代码就别下发,能在服务端算的就别在客户端算。

1. 先明确 Next.js 的三个渲染时机

Section titled “1. 先明确 Next.js 的三个渲染时机”
时机 触发 适合
Build time 构建时 内容固定(SSG)
Request time 每次请求 内容因人而异(SSR)
Revalidation 过期后后台重算 内容会变但能接受延迟(ISR)

选错时机 = 性能问题的根源。默认 App Router 是静态生成,内容变动要靠 revalidate 或 revalidatePath 触发。

2. 减少下发给浏览器的 JS

Section titled “2. 减少下发给浏览器的 JS”

2.1 组件只在客户端时才加载

Section titled “2.1 组件只在客户端时才加载”

'use client' 标记的组件会连同它的依赖一起进客户端 bundle。 一个 echarts 就能让 bundle 翻几倍——所以:

  • 第三方图表/编辑器/富文本一律 dynamic import
  • 只有真正需要交互的叶子组件才标 'use client'
  • 服务端组件里不要 import 客户端组件的库

2.2 服务端组件直接拿数据

Section titled “2.2 服务端组件直接拿数据”

对比传统写法:客户端组件 → useEffect 请求 /api/posts/:id → API 路由 → DB。 RSC 路线少一次往返、少一层 API 代码、客户端 bundle 里没有请求逻辑。

2.3 第三方脚本用 next/script

Section titled “2.3 第三方脚本用 next/script”

strategy 决定加载时机:

  • beforeInteractive:渲染前,只用于埋点等必须最早的
  • afterInteractive(默认):hydration 后
  • lazyOnload:浏览器空闲时
  • worker:Web Worker 里(实验性)

3. 优化加载指标

Section titled “3. 优化加载指标”

3.1 LCP:最大内容填充

Section titled “3.1 LCP:最大内容填充”

LCP 通常是首屏的主图或大标题块。关键是让 LCP 元素尽早出现。

priority 会生成 &lt;link rel="preload" as="image"&gt;,让浏览器提前下载。 别忘了配 sizes,否则会下载过大的图。

3.2 next/image 的三个能力

Section titled “3.2 next/image 的三个能力”
  • 自动格式协商:按 Accept 头给 WebP/AVIF
  • 尺寸优化:按显示尺寸生成,不用自己压缩
  • 懒加载:默认 loading="lazy",首屏图要 priority

3.3 next/font

Section titled “3.3 next/font”
  • 构建时下载并自托管,消除第三方域名的 DNS + TLS + 请求
  • 自动生成 @font-face + preload
  • display: swap 避免字体阻塞渲染

3.4 预连接

Section titled “3.4 预连接”

提前完成 DNS + TCP + TLS,减少真实请求的等待。

4. 缓存与重新验证

Section titled “4. 缓存与重新验证”

Next.js 15 的缓存模型按「数据源」区分:

数据 缓存 失效方式
fetch 默认 不缓存 cache: 'no-store' 关掉
fetch + next: { revalidate: 60 } 缓存 60 秒 时间到 / revalidateTag
unstable_cache 显式缓存 revalidateTag / revalidatePath
use cache(新) 按 tag 缓存 revalidateTag

revalidateTag / revalidatePath 是 ISR 的核心:改完数据不用重新构建, 只在下次访问时后台重算。

5. 流式渲染减少 TTFB

Section titled “5. 流式渲染减少 TTFB”

服务端按块推 HTML,浏览器拿到第一块就能画,后面的边到边渲染。 TTFB 从「最慢组件」降到「第一块」。

配合 loading.tsx 做路由级 loading UI。

6. 路由级优化

Section titled “6. 路由级优化”

6.1 路由本身就是分割单元

Section titled “6.1 路由本身就是分割单元”

App Router 每个 page.tsx 天然是独立 chunk,不需要手动配置。

6.2 预取

Section titled “6.2 预取”

视口内的链接自动预取(生产环境默认只在 hover 时预取,可开 prefetch 强制)。 列表页给每一行都加 Link,用户鼠标划过就把下一页拉下来了。

6.3 Middleware 放在边缘

Section titled “6.3 Middleware 放在边缘”

鉴权、A/B 分流、重写路径这类「每个请求都要做」的事放 middleware, 但 middleware 里不能访问数据库(Edge Runtime 没有 Node API)—— 要查库就把判断放到 layout 或 page 里。

7. 度量:别凭感觉优化

Section titled “7. 度量:别凭感觉优化”

把指标上报到自己的看板,按路由分组看,才知道该优化哪个页面。

本地用 Lighthouse 看实验室数据,线上用 RUM 看真实用户数据——两者经常不一致。

8. 优化清单(按性价比排序)

Section titled “8. 优化清单(按性价比排序)”
  1. next/image + priority(首屏图)
  2. next/font 自托管
  3. 第三方库 dynamic import
  4. 能用服务端组件的别用客户端组件
  5. fetch 明确设缓存策略,别让默认行为猜
  6. revalidateTag 做精确失效
  7. Suspense 做流式,降 TTFB
  8. 预连接第三方域
  9. 上报 Web Vitals,按路由定位
  10. 分析产物体积:next build 的 First Load JS 那一列

9. 面试常考

Section titled “9. 面试常考”

Q1:Next.js 怎么做 SEO 优化?

Section titled “Q1:Next.js 怎么做 SEO 优化?”

答:用 SSG 或 ISR 输出完整 HTML(而不是 CSR 的空壳),爬虫拿到的是渲染后的内容; 配 metadata / Metadata API 出 title、description、OG 标签; 加 robots.txt / sitemap.xml(App Router 有 sitemap.ts 约定); 结构化数据用 JSON-LD;图片用 next/image 固定宽高避免 CLS。

Q2:next/image 有什么优势?

Section titled “Q2:next/image 有什么优势?”

答:按 Accept 协商 WebP/AVIF、按显示尺寸生成图、默认懒加载(priority 关闭)、 自动给 srcset/sizes 做响应式、图片没加载时预留尺寸避免布局抖动。 配合 priority 给首屏 LCP 图做 preload。

Q3:怎么优化 Core Web Vitals?

Section titled “Q3:怎么优化 Core Web Vitals?”

答:LCP——首屏大图用 next/image + priority,服务端渲染别等客户端; INP——减少长任务,重的计算放服务端或 Web Worker,交互事件里避免同步重计算; CLS——给图片/字体/广告位显式预留尺寸,字体用 next/font 避免替换抖动。 再配 Suspense 流式降 TTFB。

Q4:App Router 的缓存怎么理解?

Section titled “Q4:App Router 的缓存怎么理解?”

答:Next 15 把缓存按数据源区分:fetch 默认不缓存(要显式 next.revalidate), use cache / unstable_cache 按 tag 缓存,写操作后用 revalidateTag / revalidatePath 精确失效。页面级可以用 export const revalidate = 60 设过期时间。

Q5:什么时候用 Middleware,什么时候不用?

Section titled “Q5:什么时候用 Middleware,什么时候不用?”

答:Middleware 适合每个请求都要做的轻量判断:鉴权、重定向、A/B 分流、路径重写。 它跑在 Edge Runtime,不能访问数据库和 Node API。需要查库的鉴权要放到 layout 或 page 里做。
