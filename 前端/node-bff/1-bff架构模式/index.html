BFF 架构模式

BFF（Backend For Frontend）= 服务前端的“专属后端”。

一、什么是 BFF

Section titled “一、什么是 BFF”

核心思想：前端要什么数据，BFF 给你组装好，不用前端多次请求。

二、为什么需要 BFF

Section titled “二、为什么需要 BFF”

Section titled “2.1 场景：电商商品详情页”

2.2 BFF 的优势

Section titled “2.2 BFF 的优势”
优势 场景
聚合 多微服务数据组装
协议转换 gRPC / GraphQL / RESTful 转
数据裁剪 只返回前端需要的字段
鉴权 / 限流 集中处理
缓存 Redis 集成
安全 隐藏内部微服务地址
性能 一次返回比多次请求快

2.3 BFF 的代价

Section titled “2.3 BFF 的代价”
  • 额外一层网络跳
  • 增加维护成本
  • 需要懂后端的前端工程师（或前端团队招后端）

Q1: BFF 和 API Gateway 区别？

Section titled “Q1: BFF 和 API Gateway 区别？”

答：

  • API Gateway：通用入口，处理鉴权、限流、协议转换
  • BFF：前端专属，每个端（Web / Mobile）独立部署

Q2: BFF 怎么聚合接口？

Section titled “Q2: BFF 怎么聚合接口？”

用大 Promise.all 并发调用多个微服务，然后组装数据返回前端。

Q4: BFF 的可观测性怎么做？

Section titled “Q4: BFF 的可观测性怎么做？”

答：结构化日志（pino）+ APM（OpenTelemetry）+ 监控（Grafana）。

Q5: BFF 团队怎么组织？

Section titled “Q5: BFF 团队怎么组织？”

答：

  • 小团队：前端工程师兼 BFF
  • 中团队：前端团队 + BFF 团队协作
  • 微前端：每个 BFF 对应一个微应用

面试追问(深化原 Q1-Q5)

Section titled “面试追问(深化原 Q1-Q5)”
  • BFF vs API Gateway? BFF 业务聚合(为前端定制);API Gateway 通用路由 + 鉴权
  • BFF 适合什么场景? 多端(PC/Mobile/小程序)需不同数据;聚合多个微服务;老系统迁移过渡
  • BFF 层谁来维护? 通常前端团队(GraphQL/Node);少数情况后端
  • BFF 性能考虑? 缓存(Redis)、批请求、字段裁剪(只返回前端需要);避免变慢网关

📝 小结

Section titled “📝 小结”
  • BFF 是为前端定制的一层,目的是聚合、裁剪、适配多个后端接口。
  • 典型收益:一次请求返回前端要的数据,减少瀑布请求;隐藏后端接口差异。
  • 代价是多一层网络跳转(延迟)和一层缓存失效逻辑。
  • 不要把 BFF 做成「后端逻辑的搬家」—— 计算密集的逻辑应该留在后端。
