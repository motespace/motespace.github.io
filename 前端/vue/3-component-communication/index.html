五、跨组件状态共享(兄弟 / 任意层级)

Section titled “五、跨组件状态共享(兄弟 / 任意层级)”

Props / Emit / Provide-Inject 处理了 父子 / 跨层级 的传值, 但还有一类场景 —— 任意组件之间(兄弟、跨多层级、跟父子无关的全局)—— 需要单独的处理方式。

5.1 现有方案的局限

Section titled “5.1 现有方案的局限”
方案 局限
Props 单向,只能父子传
Emit 子传父,只能父子
Slot 内容分发,不是数据共享
Provide / Inject 跨层级,但同一 source 只能注入一份

5.2 真实场景

Section titled “5.2 真实场景”

典型需求:

  • 兄弟组件互传:列表选中 → 详情更新
  • 全局状态:登录用户、主题色、语言、购物车数量
  • 跨任意层级的事件总线:通知 toast 弹出、跨页面刷新

六、EventBus(事件总线)

Section titled “六、EventBus(事件总线)”

EventBus = 一个全局的事件中心,任何组件可以 发事件 或 订阅事件, 适合“通知类”场景(不关心谁响应)。

6.1 Vue 2 经典实现 —— new Vue()

Section titled “6.1 Vue 2 经典实现 —— new Vue()”

Vue 2 直接利用 Vue 实例作为事件总线,零依赖。

优缺点:

✅ 优点 ❌ 缺点
零依赖,接入快 全局单例,事件流难追踪
简单直观 必须手动 $off,否则内存泄漏
适合一次性通知 字符串事件名,TypeScript 无法校验
$on/$off 散落在各组件,代码组织散乱

6.2 Vue 3 为什么移除 $on / $off?

Section titled “6.2 Vue 3 为什么移除 $on / $off?”

Vue 3 彻底移除了实例的 $on / $off / $once,官方在 Vue 3 RFC 中给出的原因:

  1. 代码组织变差 —— 事件订阅逻辑散落在各组件的 mounted,缺少集中管理
  2. 类型支持弱 —— 字符串事件名,TypeScript 完全无法校验
  3. 与新方案重叠 —— Provide/Inject + 响应式数据已经能覆盖大部分场景
  4. SSR 不友好 —— $on 注册的事件在 SSR 期间会丢失,水合后需要重新订阅

6.4 该不该用 EventBus?

Section titled “6.4 该不该用 EventBus?”

⚠️ 2024+ 的官方建议:能用 Pinia / Provide+reactive 解决的,不要用 EventBus。

场景 推荐方案
全局状态(用户/主题/购物车) Pinia
中小型全局状态 Provide + reactive
一次性的“通知”事件(toast 弹出) mitt / VueUse
父子组件通信 Props + Emit(永远第一选择)

七、跨组件状态共享(什么时候该「上升」)

Section titled “七、跨组件状态共享(什么时候该「上升」)”

前面六节都是自上而下的通信(props / emit / slot / provide-inject / 事件总线)。但当多个组件要共享同一份会变化的数据时,逐层透传就变成了「props 地狱」——此时要把状态提升到更高的层级。

7.1 状态放在哪一层:判断标准

Section titled “7.1 状态放在哪一层:判断标准”
状态的使用范围 放哪 用什么
一个组件内部 组件内 ref / reactive
父子之间 父组件 props + $emit
隔了 2~3 层 共同祖先 provide / inject
任意层级的多个组件 全局 store Pinia

核心原则:能局部就别全局。全局状态的代价是:所有订阅者都要为它的变化买单,调试链路变长,还容易出现「谁改的」说不清。

7.2 三种全局方案的定位

Section titled “7.2 三种全局方案的定位”
方案 定位 适用
Provide + reactive 零依赖的轻量方案 中小型项目、主题切换、简单全局数据
Pinia Vue 3 官方推荐 新项目默认选择
Vuex Vue 2 时代主流 维护老项目;新项目不推荐

7.3 什么时候该上状态管理库

Section titled “7.3 什么时候该上状态管理库”

三个信号,出现任意一个就该上:

  1. 同一个数据被 3 个以上不相关组件消费
  2. 需要跨路由/跨页面共享(购物车、登录态、主题)
  3. 组件层级已经深到需要大量透传 props

Pinia 的完整用法(定义 store / getters / actions / 持久化)、Vuex 4 的结构、Vuex → Pinia 迁移、选型对比表 → 状态管理

常见追问

Section titled “常见追问”

Q: Pinia 为什么去掉 mutation?

mutation 最初是为了支持 DevTools 时间旅行（同步记录 state 变更）。 Pinia 通过 Proxy 拦截所有 state 修改，能记录更细粒度的变化，无需显式 mutation。 代码更简洁：store.count++ 直接修改即可，DevTools 仍能追踪。

Q: 怎么从 Vuex 迁移到 Pinia?

  1. 每个 Vuex module → 一个独立 Pinia store
  2. mutations 内容合并到 actions（或者直接删除）
  3. getters 直接保留（Pinia getter 写法一样）
  4. state.x.y → useStore().y（自动扁平化，少一层）

Q: Pinia 怎么用 SSR（Nuxt / Next 集成）?

→ Vue 3 新项目默认 Pinia；Vue 2 老项目继续用 Vuex 3。

Q3:Provide + reactive 和 Pinia 的区别?

Section titled “Q3:Provide + reactive 和 Pinia 的区别?”
维度 Provide + reactive Pinia
适用规模 中小型全局态 大型 / 多人协作
DevTools ❌ ✅ 时间旅行
SSR 需手动处理 ✅ 自动序列化
持久化插件 需手写 ✅ pinia-plugin-persistedstate
学习成本 低 中

→ 简单主题切换 / 用户信息用 Provide;复杂业务用 Pinia。

📝 小结

Section titled “📝 小结”
  • 通信方式按耦合度排序:props/emit(父子)→ provide/inject(跨层级)→ 事件总线(全局,慎用)→ 状态管理(跨组件共享状态)。
  • provide/inject 适合「跨层级传递依赖」(主题、i18n、表单上下文),默认值可作为降级。
  • v-model 是 value + input 事件的语法糖,组件上用 modelValue/update:modelValue(Vue 3)。
  • 事件总线的问题:无法追踪来源、无法类型推导、组件销毁后监听残留 —— 新项目优先用状态管理或 provide/inject。
