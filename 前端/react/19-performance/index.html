React 性能优化体系

React 的性能问题只有一句话:渲染树太大,或者渲染得太频繁。 优化之前先定位是哪一类,否则容易做一堆没用的 useMemo。

1. 先定位:性能问题出在哪

Section titled “1. 先定位:性能问题出在哪”

1.1 用 Profiler 量化

Section titled “1.1 用 Profiler 量化”

React DevTools → Profiler → 录制一次交互,看:

  • 哪些组件渲染了(火焰图宽度)
  • 为什么渲染(右侧 “Why did this render?” 提示:props changed / state changed / context changed / parent rendered)
  • 单次渲染耗时

没有度量就没有优化。先记录基线(比如列表滚动掉帧到 30fps),优化后再对比。

1.2 常见结论分布

Section titled “1.2 常见结论分布”
现象 大概率原因
一次输入触发整页重渲染 状态放得太高
组件频繁重渲染但 props 没变 父组件每次渲染都创建新的对象/函数/数组
首次渲染很慢 组件太大 / 包太大 / 没做代码分割
滚动卡顿 长列表没虚拟化
输入有明显延迟 每次输入都跑了重计算

2. 三条优化主线

Section titled “2. 三条优化主线”

2.1 减少渲染次数

Section titled “2.1 减少渲染次数”

状态下沉

Section titled “状态下沉”

状态下沉到「兄弟组件」

Section titled “状态下沉到「兄弟组件」”

选中状态只影响某一行,就该放在行组件内部(或用一个状态库按 id 存)。

React.memo 冻结子树

Section titled “React.memo 冻结子树”

memo 做浅比较(Object.is)。props 里传的是对象/函数/数组时,每次渲染都是新引用, memo 会失效——所以下面这招必须配套用。

稳定引用

Section titled “稳定引用”

别无脑 useMemo。它的成本本身不为零(依赖数组比较 + 闭包分配), 只有当计算确实昂贵、或引用需要稳定时才用。

经验法则:useMemo 用于「算一次要很久」,useCallback 用于「传给 memo 子组件的函数」。 其它情况先不加,加了反而更难读。

2.2 减少每次渲染的工作量

Section titled “2.2 减少每次渲染的工作量”

虚拟化长列表

Section titled “虚拟化长列表”

超过 100 行就应该虚拟化——只渲染可视区域的行。

虚拟化不能配 SEO 需要的完整 DOM,内容型长列表慎用。

避免在渲染期做重计算

Section titled “避免在渲染期做重计算”

用 CSS 代替 JS 动画

Section titled “用 CSS 代替 JS 动画”

能用 transform / opacity 就别动 width / height / top——前者不触发布局。

2.3 减少 DOM 操作与包体积

Section titled “2.3 减少 DOM 操作与包体积”

代码分割 + 懒加载

Section titled “代码分割 + 懒加载”

首屏用不到的重组件一律 lazy。配合路由级分割(Next.js 的 App Router 默认按路由分割)。

图片与字体

Section titled “图片与字体”
  • 用 next/image / <img loading="lazy" decoding="async"> 避免首屏加载非首屏图片
  • 给图片显式尺寸,避免 CLS(布局偏移)
  • 字体用 font-display: swap 或 next/font 自托管

避免内联对象

Section titled “避免内联对象”

3. 状态库层面:减少订阅范围

Section titled “3. 状态库层面:减少订阅范围”

Redux / Zustand / Jotai 的一个共同点是:订阅粒度。

Redux 用 useSelector 指定切片,Zustand 的选择器天然生效, Jotai 的 atom 本身就是最小订阅单元。

但别为了「优化」引入状态库——组件多、props 传两层以上才考虑。

4. 反模式清单

Section titled “4. 反模式清单”
反模式 问题 改法
状态放在顶层 App 一次输入触发全树渲染 状态下沉
props 传对象字面量 每次都是新引用,memo 失效 useMemo / 提到组件外
props 传内联箭头函数 同上 useCallback
在渲染期调用副作用 警告 + 重复执行 移到 useEffect
长列表全量渲染 DOM 节点过多 虚拟化
滥用 useMemo/useCallback 增加心智负担,还引入闭包坑 只在确实需要时用
Context 塞大对象 任何变更都广播给所有消费者 拆分 Context / 用选择器订阅
首屏加载全部依赖 白屏时间长 路由级分割 + lazy

5. 面试常考

Section titled “5. 面试常考”

Q1:React 性能优化有哪些手段?

Section titled “Q1:React 性能优化有哪些手段?”

答:先定位再优化。分三条线:减少渲染次数(状态下沉、React.memo、稳定引用、状态库选择器订阅)、 减少渲染工作量(useMemo 缓存重计算、虚拟化长列表、CSS 代替 JS 动画)、 减少首屏成本(路由级代码分割、lazy、图片懒加载与显式尺寸)。 关键是先说清楚「为什么这次渲染发生了」——props 变了?state 变了?context 变了?父组件重渲染?

Q2:React.memo 什么时候会失效?

Section titled “Q2:React.memo 什么时候会失效?”

答:浅比较用的是 Object.is。props 里有对象字面量、数组、内联函数时,每次渲染都是新引用, memo 直接失效。要配合 useMemo / useCallback 把引用稳定下来。另外 context 变化、 父组件重渲染导致的子组件重渲染,memo 也拦不住(memo 只拦 props 引起的)。

Q3:useMemo 是不是越多越好?

Section titled “Q3:useMemo 是不是越多越好?”

答:不是。它本身有成本(依赖比较 + 闭包分配),而且无脑加会让依赖数组写错、 引入 stale closure。只有两类场景值得用:计算确实昂贵;引用需要稳定传给 memo 子组件。 其余场景直接算就好。

Q4:长列表卡顿怎么解决?

Section titled “Q4:长列表卡顿怎么解决?”

答:超过约 100 行用虚拟化(@tanstack/react-virtual),只渲染可视区 + overscan 缓冲, 外层容器固定高度并滚动,内层用绝对定位 + translateY 摆放行。注意虚拟化后 DOM 里没有全部内容,对 SEO 敏感的场景要慎用。

Q5:key 用 index 有什么问题?

Section titled “Q5:key 用 index 有什么问题?”

答:index 是位置,不是身份。列表中间插入/删除/排序时,React 会认为同一个位置的 是同一个组件,复用旧实例——导致状态串行、非受控输入框的值错位、动画错乱。 key 应该用数据的稳定唯一 id。
