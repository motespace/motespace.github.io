React 组件设计与生命周期

面试题问的是「有哪些钩子、什么顺序」,体系里真正要解决的是三个问题: 状态该放在哪、组件该不该更新、副作用该在哪收尾。本文按这三条线串起来讲。

1. 组件设计的三个层次

Section titled “1. 组件设计的三个层次”

1.1 展示型组件:只收 props,没有状态

Section titled “1.1 展示型组件:只收 props,没有状态”

判断标准:同一个组件在不同页面用法不一致时,往往说明状态放错位置了。

1.2 容器型组件:管状态,不含业务渲染细节

Section titled “1.2 容器型组件:管状态,不含业务渲染细节”

1.3 自定义 Hook:把「有状态的逻辑」抽出来复用

Section titled “1.3 自定义 Hook:把「有状态的逻辑」抽出来复用”

Hooks 的本质是「函数组件里的状态机」——每次渲染都是一次函数调用,状态存在调用栈之外。

2. 受控组件 vs 非受控组件

Section titled “2. 受控组件 vs 非受控组件”

2.1 受控:值在 React 里

Section titled “2.1 受控:值在 React 里”

2.2 非受控:值在 DOM 里,靠 ref 读

Section titled “2.2 非受控:值在 DOM 里,靠 ref 读”

2.3 怎么选

Section titled “2.3 怎么选”
场景 选择 原因
表单需要实时校验 / 联动 受控 每次输入都要跑校验逻辑
简单输入、只关心最终值 非受控 少一次渲染,大表单性能差很多
混用 受控为主,单个简单字段用非受控 全受控会让每个按键都触发整棵子树渲染

常见坑:受控组件的 value 传了 undefined 会变成非受控,再传字符串就会报 value prop on input should not be null。要允许清空就写 value={value ?? ''}。

2.4 一个输入框同时需要「实时校验」和「大量字段」

Section titled “2.4 一个输入框同时需要「实时校验」和「大量字段」”

折中:受控但把校验防抖;或者用 useDeferredValue 把校验延后。

3. 组件通信:按距离选方案

Section titled “3. 组件通信:按距离选方案”

Context 不是状态管理方案。它解决的是「传递」问题,不是「更新」问题: Context 值变了,所有消费者都会重渲染。React 19 起可以给 &lt;Context&gt; 传 &lt;Provider value={}&gt; 让 value 支持选择器订阅,但那属于进阶用法。

4. 生命周期:类组件时代到函数组件

Section titled “4. 生命周期:类组件时代到函数组件”

4.1 类组件生命周期(需要维护老项目时要知道)

Section titled “4.1 类组件生命周期(需要维护老项目时要知道)”

关键点:

  • render 必须是纯函数,不能有副作用
  • componentDidMount / componentDidUpdate 才是「提交后」阶段,能访问 DOM
  • getDerivedStateFromProps 是静态方法,拿不到 this
  • shouldComponentUpdate 返回 false 会跳过本次渲染

4.2 函数组件的等价物

Section titled “4.2 函数组件的等价物”
类组件 函数组件 说明
constructor / getDerivedStateFromProps useState + 渲染期比较 受控式派生状态
componentDidMount useEffect(() => {...}, []) 挂载后
componentDidUpdate useEffect(() => {...}, [deps]) 依赖变化后
componentWillUnmount useEffect(() => () => {...}, []) 返回的清理函数
shouldComponentUpdate React.memo 浅比较 props
getSnapshotBeforeUpdate useLayoutEffect 读 DOM 布局后再写

Section titled “4.3 useEffect 的执行时机”

规则:能在渲染期算出来的值就别放进 useEffect。

5. setState 的机制

Section titled “5. setState 的机制”

5.1 批处理

Section titled “5.1 批处理”

React 18 起,所有更新都自动批处理(不再区分事件回调内/外)。

函数式更新是必须的:连续 setCount(count + 1) 拿到的都是同一个旧 count,结果只 +1。

5.2 状态更新是「排队」不是「立即」

Section titled “5.2 状态更新是「排队」不是「立即」”

5.3 什么时候会重渲染

Section titled “5.3 什么时候会重渲染”
  • 本组件的 state 变了
  • 父组件重渲染了(即使 props 没变,默认也会重渲染)
  • 消费了变化的 Context
  • useSyncExternalStore 订阅的外部数据变了

父组件重渲染 = 所有子组件重新执行渲染函数(但 React 会比较结果,DOM 没变就不动)。

这就是 React.memo 存在的意义。

5.4 状态该放在哪

Section titled “5.4 状态该放在哪”

原则:离使用位置最近的地方放。

6. HOC 与 Hooks 的取舍

Section titled “6. HOC 与 Hooks 的取舍”

6.1 高阶组件:函数接收组件,返回新组件

Section titled “6.1 高阶组件:函数接收组件,返回新组件”

优点:不侵入组件内部,老代码(非 Hook)也能用。 缺点:包装层多一层,props 被改写后调试困难,TypeScript 类型推导容易出错。

Section titled “6.2 现在怎么选”
需求 方案
复用「有状态的逻辑」 自定义 Hook
复用「给组件加一个 prop」 组合优于包装:直接把组件当 children 传
给组件加能力但不改实现 HOC / 渲染 props 的组件
一次性的小包装 直接写在用到的地方

6.3 super() 与 super(props)

Section titled “6.3 super() 与 super(props)”

只在类组件里出现:

super(props) 把 props 挂到 this.props;super() 不传参数则 this.props 是 undefined。 React 16.3 之后可以直接用类属性 state = {},连 constructor 都不用写。

函数组件没有这个问题——这就是 Hooks 取代类的理由之一。

7. 面试常考

Section titled “7. 面试常考”

Q1:受控组件和非受控组件的区别?什么时候用哪个?

Section titled “Q1:受控组件和非受控组件的区别?什么时候用哪个?”

答:受控的值存在 React state 里,每次输入都触发渲染;非受控的值存在 DOM 里,靠 ref 读。 需要实时校验/联动的用受控,简单表单字段多的用非受控;混用时受控字段的 value 要写 ?? '' 兜底。

Q2:类组件生命周期有哪些?React 16 之后呢?

Section titled “Q2:类组件生命周期有哪些?React 16 之后呢?”

答:挂载 constructor → getDerivedStateFromProps → render → componentDidMount; 更新 getDerivedStateFromProps → shouldComponentUpdate → render → getSnapshotBeforeUpdate → componentDidUpdate; 卸载 componentWillUnmount。 16.3 之后新代码都用函数组件,对应关系: componentDidMount → useEffect(fn, []),componentDidUpdate → useEffect(fn, [deps]), componentWillUnmount → useEffect 返回的清理函数,shouldComponentUpdate → React.memo。

Q3:setState 之后为什么立刻读到的还是旧值?

Section titled “Q3:setState 之后为什么立刻读到的还是旧值?”

答:setState 是「排队更新」,不会同步改掉当前渲染闭包里的变量;本次渲染的 count 是渲染开始时的快照。 要基于最新值计算就用函数式更新 setCount(c => c + 1)。

Q4:React.memo 和 useMemo 有什么区别?

Section titled “Q4:React.memo 和 useMemo 有什么区别?”

答:React.memo 缓存的是组件——props 浅比较相等就跳过这次渲染; useMemo 缓存的是计算结果——依赖不变就不重算。 useMemo 缓存的是值不是组件,useCallback 是 useMemo(() => fn, deps) 的语法糖, 用于稳定传给 memo 子组件的函数引用。

Q5:HOC 有什么问题?现在还常用吗?

Section titled “Q5:HOC 有什么问题?现在还常用吗?”

答:HOC 会多一层包装,props 被改写后不好调试,类型推导容易出错,而且和 Hooks 混用时 「函数组件套函数组件」可读性差。现在优先用自定义 Hook(复用逻辑)和组合(reuse UI); HOC 主要用在给类组件或第三方组件加能力这种没法改内部的场景。

Q6:为什么 Hooks 只能在组件顶层调用?

Section titled “Q6:为什么 Hooks 只能在组件顶层调用?”

答:Hooks 靠调用顺序来对应到组件实例里的状态槽位,条件调用会让顺序错位, 渲染之间就串了。ESLint 的 rules-of-hooks 就是校验这个。
