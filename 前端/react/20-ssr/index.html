React 服务端渲染体系

SSR 解决两件事:首屏白屏和SEO。 但它引入了一整套新问题(数据一致性、hydration、环境判断),面试里最常被追问的就是这些坑。

1. 为什么需要 SSR

Section titled “1. 为什么需要 SSR”
方案 首屏 SEO 复杂度
CSR(SPA) 白屏时间长,要等 JS 下载执行 差,爬虫看到空壳 低
SSR 服务端出好 HTML,秒开 好 中
SSG 最好(纯静态) 好 低,但内容不能动态

判断标准:内容是否需要被搜索引擎看到?首屏是否是主要转化路径?

2. SSR 的完整流程

Section titled “2. SSR 的完整流程”

关键在第⑥步:服务端渲染的是静态 HTML,没有事件;客户端要把 React 树「接」到这个已有 DOM 上,这个过程叫 hydration(注水)。

3. hydration 的三个经典坑

Section titled “3. hydration 的三个经典坑”

3.1 时间/随机数不一致

Section titled “3.1 时间/随机数不一致”

解法:只在客户端渲染,或把初始值从服务端传下来。

3.2 浏览器 API 不存在

Section titled “3.2 浏览器 API 不存在”

解法:渲染期只用 props/state,浏览器 API 全放 useEffect;或用 typeof window !== 'undefined' 判断;或用框架提供的 useIsomorphicLayoutEffect。

3.3 数据不一致

Section titled “3.3 数据不一致”

服务端用 A 数据渲染,客户端用 B 数据渲染 → 结构不匹配,整棵树重渲染。

解法:把服务端取到的数据序列化传给客户端,客户端首帧直接用这份数据, 不再重新请求。这叫 数据脱水(dehydration)。

4. 三种渲染模式的取舍

Section titled “4. 三种渲染模式的取舍”

SSG(静态生成)

Section titled “SSG(静态生成)”

构建时把每条数据的 HTML 都生成出来。最快最便宜,但内容更新要重新构建。

适合:博客、产品文档、marketing 页。

ISR(增量静态再生)

Section titled “ISR(增量静态再生)”

静态生成 + 给页面设过期时间,过期后后台异步重建。兼顾快和新鲜。

SSR(每次请求都渲染)

Section titled “SSR(每次请求都渲染)”

内容每次都不同(用户个性化、实时数据)时才用。成本最高:每次请求都要跑一次 React 渲染。

流式 SSR + Suspense

Section titled “流式 SSR + Suspense”

Next.js App Router 默认行为:HTML 分块返回,慢的部分用 Suspense 占位, 不用等最慢的组件。

价值:TTFB 从「最慢组件的耗时」变成「第一个块的耗时」。

5. RSC:React Server Components

Section titled “5. RSC:React Server Components”

Next.js 13.5+ / React 19 的方向:组件在服务端执行,不打包给客户端。

收益:服务端组件里可以直接访问数据库/文件系统,不用写 API 层; 客户端 bundle 里没有这些依赖,体积天然更小。

代价:

  • 服务端组件不能有 state / effect / 事件处理
  • 边界要清楚:哪些组件需要交互,就加 'use client'
  • 不能在服务端组件里 import 浏览器专属的库

6. 选型决策

Section titled “6. 选型决策”

性能对比(同一条内容):

模式 TTFB FCP 交互就绪 服务端成本
CSR 中 晚 晚 无
SSR 中 中 晚 高
SSG 极低 早 晚(要下 JS) 一次性
流式 SSR 低 早 晚 中高
RSC + 流式 极低 很早 视交互组件 中

7. 面试常考

Section titled “7. 面试常考”

Q1:SSR 的原理是什么?和 CSR 有什么区别?

Section titled “Q1:SSR 的原理是什么?和 CSR 有什么区别?”

答:SSR 是服务端执行 React 组件拿到完整 HTML 再返回,客户端下载 JS 后做 hydration 把事件绑定到已有 DOM 上。CSR 是浏览器下载 JS 后才开始渲染,首屏白屏长。 SSR 首屏快、SEO 好;CSR 首屏慢、SEO 差。

Q2:hydration 是什么?会遇到什么问题?

Section titled “Q2:hydration 是什么?会遇到什么问题?”

答:hydration 是客户端把 React 树「接」到服务端已渲染的 DOM 上。常见问题: 时间/随机数不一致(服务端和客户端算出的值不同)、浏览器 API 不存在(window 报错)、 数据不一致(客户端重新请求的数据和服务器不同)。 解法分别是:初始值从服务端传下来、浏览器 API 放 useEffect、数据脱水后客户端首帧直接用。

Q3:SSG / SSR / ISR 怎么选?

Section titled “Q3:SSG / SSR / ISR 怎么选?”

答:内容固定不变 → SSG;内容会变但能接受分钟级延迟 → ISR(配 revalidate); 内容因人而异或必须实时 → SSR。ISR 兼顾了 SSG 的速度和 SSR 的新鲜度,成本最低。

Q4:什么是 RSC?和普通 SSR 有什么区别?

Section titled “Q4:什么是 RSC?和普通 SSR 有什么区别?”

答:RSC 是「组件在服务端执行」,服务端组件的代码不进客户端 bundle,能直接访问数据库, 不需要 API 层。普通 SSR 是「渲染在服务端,但组件代码仍要发给客户端做 hydration」。 RSC + 'use client' 边界是现在 Next.js App Router 的核心模型。

Q5:首屏优化有哪些手段?

Section titled “Q5:首屏优化有哪些手段?”

答:服务端渲染或 SSG(消除白屏)、代码分割和懒加载(减少 JS 体积)、 图片懒加载 + 显式尺寸(避免 CLS)、字体自托管 + font-display、 预连接关键域、内联首屏关键 CSS、CDN 缓存静态资源。
