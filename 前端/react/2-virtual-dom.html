Virtual DOM 深度 ​

一、什么是 Virtual DOM ​

Virtual DOM 是用 JS 对象描述真实 DOM 节点的轻量级树形表示。

js
// React.createElement 返回的就是虚拟 DOM
const vnode = {
  type: 'div',                  // 元素类型
  props: {
    className: 'container',
    children: [
      {
        type: 'h1',
        props: { children: 'Hello' },
      },
    ],
  },
}

本质:把 DOM 结构数据化,放进 JS 引擎操作。

二、为什么需要 Virtual DOM ​

2.1 直接操作 DOM 的问题 ​

js
// ❌ 直接 DOM 操作
const div = document.querySelector('.list')
div.innerHTML = `<li>${user.name}</li><li>${user.email}</li>`
// 浏览器每次都重排重绘,性能差

问题:

  • 性能差(DOM 操作是昂贵的)
  • 状态难追踪(直接改 DOM,React/Vue 不知道)
  • 跨平台难(React Native、小程序不能用 DOM)

2.2 Virtual DOM 的好处 ​

1. 性能:
   - 多次局部更新合并成一次 DOM 操作
   - diff 算法最小化变更

2. 状态管理:
   - 状态变化 → 新 VDOM → diff → 更新 DOM
   - 数据流可追踪、可回放

3. 跨平台:
   - 同一套 VDOM → 不同渲染器(React DOM、React Native、小程序)

三、Virtual DOM 工作流程 ​

state 变化
  ↓
render():返回新的 VDOM 树
  ↓
diff(virtualDOM, oldVirtualDOM):找出差异
  ↓
patch:把差异应用到真实 DOM

3.1 详细步骤 ​

js
// 1. JSX → VDOM
const vdom = <div className="box">{name}</div>
// React.createElement('div', { className: 'box' }, name)

// 2. diff 阶段
const patches = diff(oldVdom, newVdom)

// 3. patch 阶段
patch(container, patches)

四、Diff 算法 ​

4.1 传统 diff 的复杂度 ​

如果用普通树 diff 算法,O(n³) 复杂度(太慢)。

4.2 React 的优化策略 ​

React 用三个启发式假设,把复杂度降到 O(n):

1. 不同类型的元素 → 整体替换
   <div>...</div> → <span>...</span>
   不递归,直接销毁重建

2. 同类型元素 → 更新属性,递归子节点
   <div className="a"> → <div className="b">
   只改属性,递归子节点

3. 子节点列表用 key 标识
   <li key="1"> <li key="2"> <li key="3">
   通过 key 匹配,识别移动/插入/删除

4.3 key 的作用 ​

jsx
<ul>
  {items.map(item => <li key={item.id}>{item.name}</li>)}
</ul>
js
// 没 key:React 按顺序匹配(可能错位)
// A B C  →  B C D
// A B C    D E F
// React 以为 A→B, B→C, C→D, 然后新增 E、F

// 有 key:
[<li key="a">A</li>, <li key="b">B</li>, <li key="c">C</li>]
// →
// [<li key="b">B</li>, <li key="c">C</li>, <li key="d">D</li>]
// React 知道 b、c 保留,删 a,新增 d

实战经验:

  • 不要用 index 当 key(重排时 index 错位)
  • 用稳定的唯一 ID(数据库 id、crypto.randomUUID())

五、Virtual DOM 不是银弹 ​

5.1 性能瓶颈场景 ​

jsx
// ❌ 大列表每次全量重建
{bigList.map(item => <Item data={item} />)}

// ✅ 用 React.memo / shouldComponentUpdate 优化
const Item = React.memo(({ data }) => <div>{data.name}</div>)

// ✅ 或拆分状态,减少 re-render 范围

5.2 真实场景对比 ​

场景                          直接 DOM      Virtual DOM
简单文本更新                     快           慢一点(diff 开销)
复杂列表更新(>100 项)             慢           更快(批量更新)
状态管理                         差           好
跨平台                           不支持        支持

Virtual DOM 适合:

  • 复杂应用、频繁更新
  • 状态管理要求高
  • 跨平台

Virtual DOM 不适合:

  • 简单页面、更新很少(用 svelte、solid.js 这类编译时优化更合适)
  • 极致性能(直接 DOM 操作)

六、Virtual DOM vs 其他方案 ​

6.1 Svelte / Solid.js(无 VDOM) ​

svelte
<script>
  let count = 0
</script>

<button on:click={() => count++}>{count}</button>

特点:编译时优化,运行时直接操作 DOM,没有 VDOM 中间层。

性能: Svelte/Solid > React/Vue(同场景)
体积: Svelte/Solid << React/Vue
心智: React/Vue > Svelte/Solid(后者学习曲线更陡)

6.2 React Server Components ​

服务端渲染 React 组件,减少客户端 JS:

jsx
// Server Component
async function Note({ id }) {
  const note = await db.notes.get(id)
  return <NoteWithMarkdown note={note} />
}

特点:组件在服务端执行,客户端只接收 HTML + 序列化数据。

6.3 选择建议 ​

新项目、复杂业务    → React/Vue(成熟生态)
性能敏感           → Svelte/Solid.js
SEO + 性能         → Next.js(Nuxt.js)

七、实战优化技巧 ​

7.1 减少 re-render 次数 ​

jsx
// 用 React.memo 包裹
const Item = React.memo(({ data }) => <div>{data.name}</div>)

八、面试常考 ​

提示:VDOM 相关的算法细节(双端指针、key 复用、双缓存)在 3-diff.md。 本章聚焦"VDOM 作为整体"的深度问题:Element 结构、render pipeline、调度、和 Vue/编译时方案的对比。

Q1:Virtual DOM 一定比直接操作 DOM 快吗? ​

直接答案:不一定。VDOM 的真正价值不在"快",而在"通用"。

简单场景下 VDOM 反而更慢:

js
// 简单更新:直接 DOM 一次调用搞定
document.getElementById(''count'').textContent = ''1''
// 零额外开销

// VDOM 同样场景的开销:
// 1. createElement 返回新 VDOM 对象(GC 压力)
// 2. diff 对比(O(n))
// 3. 找到变更的 fiber
// 4. commit 到 DOM
// 累计开销反而更大

VDOM 真正解决的问题:

维度直接 DOMVDOM
心智成本命令式、状态散落声明式、状态集中
批量更新手动 debounce框架自动批处理
跨平台不支持DOM / Native / Canvas / PDF
测试 / 回放几乎不可能fiber tree 可序列化
性能(单次小更新)可能更快diff 开销拖累
性能(复杂更新)容易抖动批处理 + diff 更稳

Rich Harris(Svelte 作者)的 "Virtual DOM is pure overhead" 核心观点:

VDOM 不是性能优化。它把"命令式 DOM 操作"包装成"声明式状态映射", 这层抽象的开销,只在状态变更足够复杂时,才被分摊值。

面试追问:

  • 那为什么不直接用模板字符串 + innerHTML?
    • 失去细粒度更新、丢失事件监听、无法 diff、可能 XSS
  • React 为什么不做编译时优化?
    • 在做了(React Forget,2026 年逐步开放),但生态包袱重

Q2:React diff 为什么是 O(n)? ​

传统 tree diff:求两棵树的最小编辑距离 = O(n³)(Zhang-Shasha 算法变种)。 1 万节点 = 10¹² 次对比,完全不可用。

React 的"作弊":放弃"最小更新",换 O(n)。

三条启发式:

  1. 类型不同 → 整树替换

    jsx
    <div>...</div> → <span>...</span>
// 直接卸载 div 子树,重建 span
// 不递归对比,因为跨类型 DOM 复用价值低

  2. 同类型 → 复用 DOM 节点,递归对比 props 和 children

    jsx
    <div className="a"> → <div className="b">
// 保留 DOM 节点,更新 className
// 递归对比 children

  3. 同级比较(不跨层级)

    jsx
    // 不会把 A 的子树挪到 B 父节点去用
// 减少对比空间

  4. 列表用 key(Map 查找 O(1))

    js
    // 老: [{key: ''a''}, {key: ''b''}, {key: ''c''}]
// 新: [{key: ''b''}, {key: ''c''}, {key: ''d''}]
// 用 Map 建立 oldKey → fiber 索引
// 一次遍历新数组,O(1) 查老 fiber

复杂度分析:

  • 每个节点 O(1) 对比
  • 一棵树 O(n) 遍历
  • 总 O(n)

代价:不是"最小更新"。React 团队实测 ~95% 场景命中启发式假设。

面试追问:

  • 类型不同的子树就一定不能复用吗?
    • 理论上能,React 选择不这么做,收益小成本大
  • 为什么不跨层级比较?
    • DOM 节点有 owner,跨层级移动要改 ref 引用,复杂度爆炸

Q3:为什么列表要加 key?index 当 key 有什么坑? ​

key 的作用:标记"同一逻辑元素"在多次 render 间的身份,让 React 复用正确的 fiber。

没 key 的情况:

jsx
// 老: [<li>A</li>, <li>B</li>, <li>C</li>]
// 新: [<li>B</li>, <li>C</li>, <li>D</li>]
// React 按顺序对比:
//   第 0 个: A → B(更新)
//   第 1 个: B → C(更新)
//   第 2 个: C → D(更新)
// 看起来"对了",但 li 的内部 state 没变——
// A 的 input value 留在了 B 的 input 里

用 index 当 key 的真实坑:

jsx
// 场景:表格删除中间行
function Table({ rows }) {
  return rows.map((row, i) => <Row key={i} row={row} />)
}

// rows = [{id: 1}, {id: 2}, {id: 3}]
// 删除 id=2 后:
// rows = [{id: 1}, {id: 3}]
// key 分别是 0、1
// React 视角:key=0 还在、key=1 还在 → 复用
// 但 key=1 现在对应 {id: 3},原本是 {id: 2}
// Row 内部 state(编辑标志、展开状态、滚动位置)全是 id=2 的残留

正确做法:

jsx
// ✅ 用稳定 ID
rows.map(row => <Row key={row.id} row={row} />)

// ✅ 临时数据用 uuid
items.map(item => <Item key={crypto.randomUUID()} />)

唯一能用 index 的场景(极少):

  • 纯展示
  • 无组件 state
  • 永不重排 / 过滤

面试追问:

  • 头部插入项目,index 有什么问题?
    • 原 [A, B, C] 变成 [X, A, B, C]
    • key=0 的内容从 A 变成 X
    • 看起来 React 复用,实际数据流是反的
    • A、B、C 的组件 state 全错位

Q4:React Element(VDOM 节点)的内部结构是什么? ​

最小结构(React 17 源码简化):

js
const element = {
  $$typeof: Symbol(react.element),  // 防 XSS:JSON 无法伪造
  type: ''div'',                     // ''div'' | Component | Symbol(react.fragment) | Symbol(react.provider)
  key: null,                         // 用于 reconciliation
  ref: null,                         // 拿到真实 DOM / 实例
  props: {                           // 不可变
    className: ''box'',
    children: [...],
    __source: { fileName, lineNumber },  // dev 警告用
    __self: {},
  },
  _owner: {                          // 内部:当前渲染的 fiber
    tag: 0,
    stateNode: null,
    element: null,
  },
}

关键属性说明:

属性作用
$$typeof跨 realm 安全 + 防 XSS。攻击者即使注入了 JSON,也无法伪造 Symbol
type字符串 = 原生元素;函数 = 函数组件;类 = 类组件;Symbol = Fragment/Provider
keyreconciliation 时识别身份
ref拿到真实 DOM 节点 / 组件实例
props.children可能是字符串、数字、数组、嵌套 element
_ownerdebug 用,指向"当前正在 render 的组件"(用于"can''t update during render"警告)

Element 是不可变的——每次 render 都创建新对象,React 通过引用比较 + key 判断是否变化。

$$typeof 防 XSS 原理:

  • JSON.parse 不会创建 Symbol → 攻击者无法注入伪造的 element
  • 浏览器 <script> 收到的 JSON 数据 parse 后是普通对象,缺 $$typeof → React 不认,直接拒绝渲染

面试追问:

  • Element 和 Fiber 什么关系?
    • Element = 描述(props、type、key),轻量、不可变
    • Fiber = 工作单元(state、effect、双链表指针),可变、有生命周期
    • 一棵 element 树对应一棵 fiber 树
  • 为什么 Element 不可变?
    • 不可变让 reference equality 判断"是否变化"成为可能
    • 配合 memo,浅比较简单可靠

Q5:从 state 变化到 DOM 变化的完整 pipeline ​

jsx
function App() {
  const [count, setCount] = useState(0)
  return <div onClick={() => setCount(count + 1)}>{count}</div>
}

完整流程:

1. 用户点击 → onClick 触发 setCount(1)
2. React 把 update 加入 hook 的 update queue(环形链表)
3. 调度器决定:当前 update 的优先级
   - 同步事件(input)→ 高优先级,立即执行
   - useTransition → 低优先级,可中断
4. 进入 render phase(可中断):
   a. 调用 App() → 返回新 element 树
   b. 把 element 树转成 workInProgress fiber 树
   c. 每个 fiber 对比 oldFiber / newElement → 打 effectTag
   d. 如果时间片用完,让出主线程,下次接着跑
5. 进入 commit phase(不可中断):
   a. 收集 effect list(DOM 变更、useLayoutEffect 回调)
   b. 一次性 commit 到 DOM
   c. 调度 useEffect(不阻塞 paint)
6. 浏览器 paint

两个阶段的核心差异:

阶段可中断副作用失败回滚
Render✅(Fiber)❌ 纯计算✅ 丢弃 workInProgress
Commit❌✅ DOM / effect❌ 已落地难撤回

面试追问:

  • 为什么要分两阶段?
    • 保证 DOM 不出现中间态。Commit 一次原子落地
    • Render 失败重试成本低(内存数据),Commit 失败用户看到残缺 UI
  • React 18 useTransition 怎么"中断"?
    • fiber 循环里检查剩余时间;快过期就 return null 让出
    • 下次从中断点续跑(双 fiber 树,workInProgress 暂存)
    • 断了不污染 current 树

Q6:setState 同步还是异步?React 18 automatic batching ​

React 17 行为:

jsx
// 场景 1:合成事件 → 异步批处理 ✅
button.addEventListener(''click'', () => {
  setA(1)
  setB(2)
  // 只触发一次 render
})

// 场景 2:setTimeout / Promise → 不批处理 ❌
setTimeout(() => {
  setA(1)
  setB(2)
  // 触发两次 render
}, 0)

React 18 行为:全部批处理 ✅

jsx
// 不管是合成事件、setTimeout、Promise、原生事件——全部批
setTimeout(() => {
  setA(1)
  setB(2)
  // 只触发一次 render
}, 0)

原理(简化):

  • React 17 用同步 isBatchingUpdates 标志,事件入口 batchedUpdates(() => callback),callback 内 setState 进 update queue,退出后 flush
  • React 18 改用 scheduler 统一管理 update,所有 update 进入 scheduler,等当前事件循环结束再 flush
  • 因此 setTimeout / Promise / microtask 也能批

什么时候 setState 是"同步"的?

  • 在 commit phase 同步调用(如 useEffect 里 setState 配合 useSyncExternalStore)
  • 在 concurrent 渲染中用 flushSync 强制同步
  • 自定义 hook 用 useSyncExternalStore 订阅外部 store

面试追问:

  • 怎么绕过 batching 拿"中间值"?
    • 用 flushSync(() => { setA(1) }) 强制立即 render
    • 或用 ref 暂存
  • 批处理一定会减少 render 吗?
    • 大多数情况会,但 update 优先级不同时可能多次 render
    • 高优先级 update 打断低优先级 → 多次 render

Q7:Virtual DOM 和 Fiber 是什么关系? ​

早期 React(<= 15):

  • VDOM 树 = 递归处理的对象树
  • render 一旦开始必须跑完
  • 大型应用会卡顿(长任务 > 50ms)

React 16+ 引入 Fiber:

  • Fiber 架构 = 重新实现的"VDOM 节点"数据结构
  • 每个 element 有一个对应 fiber
  • fiber 是链表(child / sibling / return),可以中断/恢复

Fiber 节点结构(简化):

js
{
  // === VDOM 信息 ===
  type, key, elementType,

  // === 状态 ===
  pendingProps,      // 本次要更新的 props
  memoizedProps,     // 上次 render 用的 props
  memoizedState,     // 上次的 state(hook 链表头)
  alternate,         // 上一个 fiber(双缓存)

  // === 链表指针 ===
  return: parentFiber,
  child: firstChildFiber,
  sibling: nextSiblingFiber,

  // === 副作用 ===
  flags,             // Placement | Update | Deletion | ...
  subtreeFlags,
  lanes,             // 调度优先级
  childLanes,

  // === 关联 ===
  stateNode,         // DOM 节点 / 实例
  updateQueue,       // useState / useReducer 的 update 队列
}

Element vs Fiber 对比:

维度ElementFiber
创建时机每次 rendermount 时 + 每次 render
可变性不可变可变(双树切换)
数据结构树(嵌套对象)链表(child/sibling/return)
包含 props✅✅ + memoizedProps
包含 state❌✅ memoizedState
包含 effect❌✅ flags / effect list
中断❌✅(return null 让出)
真实 DOM不一定有stateNode 关联 DOM

双缓存:

  • current fiber = 屏幕上正在显示的树
  • workInProgress fiber = 正在计算的树
  • commit 阶段交换两棵树引用,原子切换
  • 中断/失败时直接扔掉 workInProgress,current 树完好

面试追问:

  • Fiber 用链表而不是树,为什么?
    • 树结构遍历需要递归栈,中断要保留栈帧,实现复杂
    • 链表用循环遍历,可以随时中断(把指针存下来),恢复时继续循环

Q9:React 18 / 19 引入的并发特性对 VDOM 有什么影响? ​

VDOM 本身没变,变的是调度方式。

React 18 关键能力:

API作用VDOM 影响
automatic batching所有场景批处理 setStaterender 次数减少
useTransition标记更新为"非紧急"紧急更新可打断非紧急
useDeferredValue派生值延后更新输入流畅,渲染滞后
Suspense数据 ready 前显示 fallback让子树 VDOM 暂停
useSyncExternalStore订阅外部 store保证并发下的数据一致

React 19 新增:

  • Server Components 稳定:服务端只 render,不发送 VDOM 给客户端
  • Actions:把"用户操作"显式化(useActionState、useOptimistic)
  • use API:在 render 里读 Promise/Context,Suspense 自动整合
  • React Forget(编译器):自动 memo,比手写 useMemo 更准

VDOM 视角的变化:

旧心智:一棵 element 树 = 一次 render
新心智:render 是个"区间",可能跑多次、中断、重启
VDOM 是"声明",不再是"步骤"

Server Components 怎么工作:

  • 服务端 render 组件,输出序列化 payload(RSC stream,不是 HTML)
  • 客户端收到后和 Client Component 一起 hydrate
  • 服务端组件不参与客户端 VDOM 树
  • 优势:零 JS 包体积、直接访问数据库、组件跨服务器边界复用

面试追问:

  • 怎么决定用 Client Component 还是 Server Component?
    • 需要交互(状态、事件)→ Client
    • 纯展示 + 数据获取 → Server
    • 默认 Server,需要交互时加 ''use client'' 指令
  • 并发特性会不会破坏现有应用?
    • React 18 严格保持兼容(automatic batching 是新行为,大多数应用受益)
    • 真正的破坏性变化要 opt-in(useTransition、<Suspense>)

Q10:Vue 的 VDOM 和 React 有什么不同? ​

核心差异:编译时优化 vs 运行时 diff。

Vue 3 的 patch flag:

vue
<template>
  <div>
    <p>static text</p>           <!-- patchFlag: 0(无动态) -->
    <p>{{ count }}</p>            <!-- patchFlag: 1(文本) -->
    <p :class="cls">text</p>     <!-- patchFlag: 2(class) -->
    <input :value="v" />         <!-- patchFlag: 1(props) -->
  </div>
</template>
js
// Vue 3 编译产物(简化)
createVNode(''p'', null, ''static text'', 0)        // 不参与 diff
createVNode(''p'', null, ctx.count, 1 /* TEXT */)  // 只 diff 文本
createVNode(''p'', { class: ctx.cls }, null, 2)     // 只 diff class

React 每次都 diff 所有 props:

jsx
// 即使 count 不变,React 仍会 shallow compare 所有 props
<div className={cls}>{count}</div>

场景ReactVue 3Solid

  • React 不是劣势吗?
    • React Forget(编译器)正在做类似的事
    • React 生态成熟度、跨端能力仍是优势
    • Vue 3 编译时优化对 .vue 单文件组件最有效,复杂 JSX 场景优势减弱
  • Svelte 5 的 runes 比 React 还激进?
    • 是,完全无 VDOM,编译成命令式 DOM 操作
    • 性能极优,但生态和工具链不如 React 成熟

Q11:什么场景 VDOM 反而是负担? ​

三种 VDOM 不合适的场景:

1. 极致性能场景(动画、游戏、可视化)

js
// 1000 个粒子、60fps
// 每次 frame 都要更新位置
// VDOM 创建 + diff + commit 累计 5ms,剩余 11ms 才够 paint
// → 直接操作 Canvas / WebGL

2. 大型列表(1 万+ 行)

js
// 1 万个 VDOM 节点 ≈ 几百 KB 临时对象
// 每次 diff 全量 → GC 压力
// → 虚拟列表(react-window)只渲染可视区

3. 静态内容多

js
// 99% 内容不变
// 仍然 diff 10000 个 props
// → 用 Vue 3 编译时 / Solid signals 跳过静态

VDOM 的隐藏成本:

  • GC 压力:每次 render 创建几千个临时对象,触发 minor GC
  • diff 复杂度😮(n) 但 n 大时仍可观
  • 内存占用:保留前后两棵 fiber 树(双缓存)

面试追问:

  • React 完全不能用在大列表?
    • 能,要用虚拟列表(react-window、react-virtuoso)
    • 配合 React.memo + 稳定 key,单页 1 万行也能跑到 60fps
  • 那完全用直接 DOM 行不行?
    • 命令式开发成本高、状态分散、难维护
    • 只在"局部高频更新"用 imperative handle(useImperativeHandle)

Q12:实战中怎么降低 VDOM 开销? ​

1. 减少 re-render 范围

jsx
// ❌ 父组件 state 变,所有子组件都 re-render
function App() {
  const [count, setCount] = useState(0)
  return (
    <>
      <Counter count={count} />
      <HeavyList />  {/* 不需要 re-render 但被牵连 */}
    </>
  )
}

  return (
    <>
      <Counter />    {/* count 在这里 */}
      <HeavyList />
    </>
  )
}

3. 稳定引用

jsx
// ❌ 每次 render 创建新对象
<Row config={{ color: ''red'' }} />

// ✅ 用 useMemo
const config = useMemo(() => ({ color: ''red'' }), [])
<Row config={config} />

// ❌ 内联函数
<Row onClick={() => do(id)} />

// ✅ useCallback
const handle = useCallback(() => do(id), [id])
<Row onClick={handle} />

面试追问:

  • React.memo 一定能优化吗?
    • 不一定。如果 props 引用总在变,浅比较开销反而比直接 render 更大
    • 需要先稳定引用(useMemo / useCallback)
  • useMemo 一定能优化吗?
    • 不一定。useMemo 本身有"存上次结果"的内存和比较开销
    • 只在"计算量大"或"作为 memo 组件 prop"时用
