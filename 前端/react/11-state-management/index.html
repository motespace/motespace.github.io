React 状态管理

状态管理是 React 应用的核心问题。本文从最简单的 useState 讲起，覆盖 Context、Redux、Zustand、MobX，按“够用就好”的顺序排列。

1. 状态分类（先想清楚再选工具）

Section titled “1. 状态分类（先想清楚再选工具）”

在选状态管理工具之前，先把状态分清楚：

类别 例子 推荐方案
局部状态 表单输入、弹窗显隐 useState / useReducer
跨组件状态 主题、当前用户、购物车 Context / Zustand
服务端状态 列表数据、详情数据 React Query / SWR
全局复杂状态 多模块协同、撤销重做 Redux Toolkit / MobX

常见误区：把所有状态都扔进 Redux / Zustand，结果一个表单 onChange 也触发整个 store 更新。

2. useState：基础款

Section titled “2. useState：基础款”

setState 的关键点：

  • 不会立即更新（批处理）。
  • 对象 / 数组必须返回新引用（不可变更新）。
  • 函数式更新获取最新值。

3. useReducer：复杂状态用 reducer 管

Section titled “3. useReducer：复杂状态用 reducer 管”

当状态有多个子值、依赖前一个状态、或者更新逻辑复杂时，用 useReducer 替代多个 useState。

useReducer 适用场景：

  • 多个状态互相依赖。
  • 状态更新有多种类型（增删改查）。
  • 想把所有更新逻辑集中到 reducer 里测。

4. Context：跨组件传值

Section titled “4. Context：跨组件传值”

Context 解决“props drilling”（父 → 子 → 孙 → 曾孙一层层传）问题。

Context 性能陷阱：

Context 不适合频繁更新的状态：比如输入框 onChange 触发更新 → 所有消费者组件都重渲染。这种情况要用状态管理库（Zustand / Redux）。

5. Zustand：轻量级状态管理（推荐）

Section titled “5. Zustand：轻量级状态管理（推荐）”

Zustand 是我实际项目用得最多的状态库。优点：

  • API 极简（5 分钟上手）。
  • 不需要 Provider，直接 create。
  • 性能好，组件只订阅自己用到的 slice。
  • TypeScript 友好。

7. MobX：响应式风格

Section titled “7. MobX：响应式风格”

MobX 用 observable 把状态变成可观察的，组件用 observer 包裹自动响应。适合“类 OOP 思维”的项目。

MobX 特点：

  • 写法接近原生 JS，不用记 reducer/action 概念。
  • 细粒度响应（只更新真正用到状态的组件）。
  • 缺点：心智模型不一样，团队需要学习成本。

8. 服务端状态：React Query / SWR

Section titled “8. 服务端状态：React Query / SWR”

前端状态 ≠ 服务端状态。列表、详情这些“来自后端的数据”不应该用 Redux/Zustand 管，应该用专门的服务端状态库。

React Query 自动处理的事：

  • 缓存（同样的 queryKey 不重复请求）。
  • 失效和重取（mutation 后自动 refetch）。
  • 加载 / 错误状态。
  • 乐观更新（先改 UI，再请求）。
  • 轮询、分页、无限滚动。

9. 选型建议

Section titled “9. 选型建议”
项目规模 推荐方案
1-3 页面 useState + useReducer
中小项目（10+ 组件） Context + Zustand
中大型项目（多模块协作） Redux Toolkit + RTK Query
大量服务端状态 React Query / SWR（不管用啥状态库都要叠这个）
已有 OOP / 响应式思维 MobX

真实项目经验：

  • 商户管理 SaaS / 会员服务平台用的是 Zustand + React Query，轻量足够。
  • 复杂规则配置类应用（如风控平台）适合 Redux + Redux Toolkit，时间旅行调试很爽。
  • 不要把列表数据放 Redux/Zustand：会重复缓存，刷新逻辑写起来很痛苦。直接用 React Query。

11. 面试常考

Section titled “11. 面试常考”
题目 答案要点
Context 性能问题 value 引用变化触发所有消费者重渲染；用 useMemo 或状态库
Redux vs Zustand Redux 标准化（团队/调试/撤销）；Zustand 轻量（中小项目）
为什么需要 React Query 服务端状态有缓存/失效/重试/分页等复杂需求，不是简单 useState 能搞定
MobX vs Redux 思维差异 MobX 面向对象 + 响应式；Redux 函数式 + 单向数据流
状态提升 vs Context vs 全局库 简单：状态提升；中等：Context；复杂：状态库

| 状态提升 vs Context 性能? | 状态提升 re-render 范围小;Context value 引用变触发所有消费者 | | Redux Toolkit 解决了什么? | 简化 action/reducer 模板;内置 immer、createSlice、RTK Query | | 怎么避免 Context 性能问题? | 拆 Context(按职责);值用 useMemo;不传整个对象 | | Recoil/Jotai 适合什么? | 原子化状态(atom);适合细粒度订阅 + 复杂派生 | | 状态库选型怎么定? | 简单:useState/useReducer;中等:Context;复杂:Zustand/Redux;服务端:React Query |

面试追问

Section titled “面试追问”
  • 什么时候用 Context 而不是 props drilling? 3 层以上 prop 透传、或多个组件共享
  • Zustand 比 Redux 简洁在哪? 无 action/reducer 模板;直接 set;支持 selector 订阅
  • React Query 是状态库吗? 严格说不是,是服务端数据同步层(缓存、失效、重试)
  • MobX 缺点? 团队心智成本(响应式 vs 不可变);调试相对 Redux 难(无 time-travel)
  • 什么时候该上 Redux? 多人协作 + 复杂业务 + 需要撤销/重做 + 严格状态追溯

12. 真实项目经验

Section titled “12. 真实项目经验”

12.1 商户管理 SaaS（Next.js）

Section titled “12.1 商户管理 SaaS（Next.js）”
  • 全局状态：用 Zustand 管当前用户、权限码、I18n、主题。
  • 服务端状态：用 React Query 管列表、详情、分页、搜索。
  • 表单状态：用 react-hook-form + zod（schema 校验）。

12.2 风控平台（Vue 3）

Section titled “12.2 风控平台（Vue 3）”
  • Pinia（Vue 3 的状态库，类 Zustand）+ Vue Query。
  • 不用 Vuex 4：Pinia 的 TypeScript 支持和 Composition API 集成更好。

选型原则：够用就好。不要为了用 Redux 而用 Redux，中小项目 Zustand/Pinia 完全够用。

📝 小结

Section titled “📝 小结”
  • 先分类再选工具:组件内部 useState → 跨组件 Context → 跨页面 Zustand/RTK → 服务端数据 TanStack Query;不要一上来就 Redux。
  • useState 适合离散状态,useReducer 适合「多字段、有事件语义、有顺序要求」的复杂状态,reducer 天然可测。
  • Context 只解决传递,不解决更新性能——value 变化会让所有消费者重渲染,必须拆分 Provider 或配合 selector。
  • Zustand 的关键是 selector 订阅(只订阅用到的切片)+ 浅比较,不写 selector 是最常见的性能坑。
  • 服务端状态和客户端状态本质不同:前者要缓存、失效、重试、去重,交给 Query/SWR,不要塞进 Redux。
