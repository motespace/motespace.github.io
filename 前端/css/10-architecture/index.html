CSS 架构与工程化

一、为什么需要 CSS 架构

Section titled “一、为什么需要 CSS 架构”

CSS 写多了,容易出现:

架构的目标:

  • 命名规范 → 避免冲突
  • 拆分粒度 → 易于维护
  • 复用机制 → DRY
  • 样式隔离 → 不互相影响

Section titled “二、命名规范”

2.1 BEM(Block Element Modifier)

Section titled “2.1 BEM(Block Element Modifier)”

BEM = 块 + 元素 + 修饰符。

优点:

  • 命名自带结构
  • 一眼看出归属
  • 不依赖其他类

缺点:

  • 类名长(card__header__title__link--active)
  • 嵌套深时繁琐

Q1:CSS Modules 怎么实现的?

Section titled “Q1:CSS Modules 怎么实现的?”

答:

  • 构建工具(webpack/vite)处理 CSS Modules
  • 每个类名编译时加 hash(_class_1a2b3)
  • 类名全局唯一,不冲突

Section titled “Q2:BEM 的好处?”

答:

  • 命名规范,易理解
  • 自带层级关系
  • 不依赖其他类
  • 适合中型项目

Q3:CSS-in-JS 优缺点?

Section titled “Q3:CSS-in-JS 优缺点?”

答:

  • 优:动态样式、主题、组件级作用域
  • 缺:运行时开销、SSR 复杂、调试难
  • 实战:不推荐大型项目用,小型项目可

面试追问(深化原 Q1-Q3)

Section titled “面试追问(深化原 Q1-Q3)”
  • CSS Modules 配合 TypeScript 类型提示? typed-css-modules 自动生成 .d.ts
  • BEM 元素嵌套过深怎么办? 超过 3 层(.block__elem__sub__sub)考虑改组件化
  • CSS-in-JS 的 SSR 性能? styled-components 旧版有 hydration 性能问题;emotion / vanilla-extract 更轻
  • 现代项目选型推荐? 原子化(Tailwind) + 局部(CSS Modules);大型项目:vanilla-extract(零运行时)

📝 小结

Section titled “📝 小结”
  • CSS 架构要解决三件事:命名(BEM/CSS Modules)、组织(分层与目录)、复用(变量与 mixin)。
  • CSS Modules 是编译期把类名哈希化,天然隔离,适合组件化项目。
  • 原子化 CSS(Tailwind)的价值是约束取值集合(间距只用 4 的倍数),消除「随手写 margin: 13px」的不一致。
  • CSS-in-JS 的运行时开销是真实成本,大型项目更推荐 CSS Modules 或零运行时方案(如 vanilla-extract)。
