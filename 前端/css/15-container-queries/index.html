容器查询

媒体查询问的是「屏幕多大」,容器查询问的是「我所在的容器多大」——这是组件化响应式真正需要的。

一、媒体查询的困境

Section titled “一、媒体查询的困境”

问题:组件不知道自己在哪。这张卡片可能在侧栏(窄),也可能在主区(宽),媒体查询只能看视口,于是:

  • 卡片在宽视口的窄侧栏里 → 被误判为「够宽」,两列被挤扁
  • 卡片在窄视口的宽主区里 → 被误判为「不够宽」,浪费空间

容器查询让组件根据「自己所在的容器」来布局,不再依赖视口。

二、三个属性

Section titled “二、三个属性”

container-type 的取值

Section titled “container-type 的取值”
值 含义 副作用
inline-size 只在行内轴(通常是宽度)上建立查询容器 最常用,对布局影响最小
size 宽度和高度都查询 会阻止元素按内容撑开(高度也被约束)
normal 不建立容器 默认值

注意:container-type: size 会让元素失去「按内容决定高度」的能力,通常要用 inline-size。

查询容器的名字

Section titled “查询容器的名字”

命名容器用来精确指定查询对象,避免嵌套时选错。

三、容器查询单位

Section titled “三、容器查询单位”

容器查询带来一组新单位,相对于查询容器而不是视口:

单位 含义 典型用法
cqw 容器宽度的 1% font-size: 4cqw 随容器缩放
cqh 容器高度的 1% 少用
cqi 容器行内尺寸的 1% 等价于 cqw(横排时)
cqb 容器块尺寸的 1% 等价于 cqh
cqc 容器查询尺寸的 1% 最近可用容器的尺寸

这比媒体查询的 clamp(1rem, 5vw, 2rem) 更好:组件放到哪都合适,不用管视口多大。

六、注意事项

Section titled “六、注意事项”

1. 不能查询自身

Section titled “1. 不能查询自身”

必须查询祖先的容器。

2. 容器查询不能查询「距离视口多远」

Section titled “2. 容器查询不能查询「距离视口多远」”

这是刻意的设计:如果能查,又会退化成媒体查询的问题。

3. container-type 会创建层叠上下文和包含块

Section titled “3. container-type 会创建层叠上下文和包含块”

这会影响内部的 position: fixed 定位(会相对容器而不是视口)。这是已知的取舍。

4. 浏览器支持

Section titled “4. 浏览器支持”

Chrome / Edge 105+、Safari 16+、Firefox 110+,已全面可用。

🎯 面试常考

Section titled “🎯 面试常考”

Q1: 容器查询解决了什么问题? 让组件根据「自己所在的容器尺寸」布局,而不是视口尺寸。同一个卡片组件放在侧栏和主区能自动采用不同布局,解决了「组件不知道自己被放在哪」的问题。

Q2: container-type: inline-size 和 size 的区别? inline-size 只在行内轴(通常是宽度)建立查询容器,元素高度仍由内容决定,推荐使用;size 同时约束宽度和高度,元素失去按内容撑开高度的能力,一般不用。

Q3: 容器查询单位 cqw 和 vw 有什么区别? vw 是视口宽度的 1%,cqw 是最近查询容器宽度的 1%。容器查询单位让组件的字号、内边距等随自己所在的容器缩放,而不是随视口。

Q4: 样式查询怎么用? 在容器上定义自定义属性(--theme: dark),用 @container style(--theme: dark) 查询它的值。注意被查询的属性必须能继承到容器里,通常定义在容器的父元素上。

Q5: 容器查询的浏览器支持如何? Chrome / Edge 105+、Safari 16+、Firefox 110+,已全面可用,可以用 @supports (container-type: inline-size) 做检测。

📝 小结

Section titled “📝 小结”
  • 媒体查询问「屏幕多大」,容器查询问「我的容器多大」——后者才是组件级响应式需要的。
  • container-type: inline-size 建立查询容器,@container 查询,cqw 等单位随容器缩放。
  • 样式查询让主题切换可以纯 CSS 实现。
  • container-type 会创建层叠上下文并成为 fixed 的包含块,这是需要注意的副作用。
