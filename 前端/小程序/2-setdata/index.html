setData 原理与性能

setData 是小程序性能问题里最常见的一个来源: 你传了多少数据,就可能产生多少渲染成本。

1. setData 到底做了什么

Section titled “1. setData 到底做了什么”

关键点:setData 不是「设置 DOM」,而是「更新数据 + 触发一次数据到视图的同步」。 成本 = 传输数据量 + 视图层重渲染量。

3.1 频率过高

Section titled “3.1 频率过高”

解法:高频变化不进 setData,直接操作节点。

3.2 单次数据量过大

Section titled “3.2 单次数据量过大”

列表一次 setData 几千条,即使只改了其中一项,也可能因为 diff 成本而卡顿。

解法:

  • 分页 / 分段渲染(先渲染首屏,滚动到底再追加)
  • 用 wx:key 正确标识,让 diff 更精确
  • 超过一定量用「虚拟列表」思路,只渲染可视区域

Q1:setData 的原理是什么?有什么性能问题?

Section titled “Q1:setData 的原理是什么?有什么性能问题?”

答:setData 做两件事——在逻辑层更新 this.data,然后把变更部分序列化跨线程发给视图层, 视图层据此做 diff 并更新 DOM。所以成本取决于「传输的数据量」和「受影响的组件数量」。 问题:频率高(滚动事件里调用)、单次数据量大(整个列表)、传了视图用不到的字段。 解法:用路径语法只传变化字段、高频数据不进 setData 直接操作节点、长列表分段渲染。

Q2:为什么 setData 不能传整个数组?

Section titled “Q2:为什么 setData 不能传整个数组?”

答:因为视图层收到后要 diff 出受影响的组件。传整个数组时,框架无法确定 「哪些项真的变了」,只能对整个列表做比较,组件越多、数组越大成本越高。 正确做法是 this.setData({ [list[${i}]]: item }) 精确到下标, 或者按需 append,让 diff 范围最小。

Q3:页面隐藏后还 setData 会怎样?

Section titled “Q3:页面隐藏后还 setData 会怎样?”

答:仍会走完整的通信和渲染流程,浪费 CPU 和带宽。页面不可见时应该停掉 定时器、动画和订阅,在 onHide 里清理,onShow 里恢复。
