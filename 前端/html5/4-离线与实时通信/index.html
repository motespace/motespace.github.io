离线与实时通信

Service Worker / IndexedDB / WebSocket / SSE / Web Worker —— 这一组能力真正改变了前端架构。

一、Web Storage vs IndexedDB

Section titled “一、Web Storage vs IndexedDB”
维度 localStorage sessionStorage IndexedDB
容量 5~10MB 5~10MB 几百 MB~GB
类型 只能存字符串 字符串 结构化对象(结构化克隆)
同步 同步(阻塞主线程) 同步 异步
索引 ❌ ❌ ✅
事务 ❌ ❌ ✅
后台可用 ❌ ❌ ✅
适用 token、偏好 临时态 离线草稿、大数据缓存、文件

面试点：为什么 IndexedDB 适合存结构化大数据？→ 异步不阻塞主线程、有索引可查询、支持事务保证一致性、容量大。

坑：Safari 曾经对 IndexedDB 有 50MB 限制；隐私模式下写入会失败；IE 完全不支持。

二、Service Worker

Section titled “二、Service Worker”

2.1 生命周期

Section titled “2.1 生命周期”

2.2 注册与生命周期管理

Section titled “2.2 注册与生命周期管理”

最大的坑：

🔑 Service Worker 会缓存住“坏版本”。用户第一次加载了有 bug 的 JS，SW 把它缓存了，即使你发版修复，用户不强制刷新就一直用旧的。解决办法：

  1. 静态资源用 hash 文件名，HTML 不缓存（Cache-Control: no-cache）
  2. SW 里 skipWaiting() + clients.claim()
  3. 检测到新版本时提示用户刷新，而不是静默替换

2.3 什么时候不要用 Service Worker

Section titled “2.3 什么时候不要用 Service Worker”

内部 ERP 通常不需要 Service Worker。PWA/营销页/移动端 H5 才值得上。这个判断本身在面试里是加分项（知道什么时候不该用）。

三、实时通信

Section titled “三、实时通信”

3.1 WebSocket

Section titled “3.1 WebSocket”

要点：

要点 说明
心跳 30s ping/pong,防止中间设备掐断空闲连接
指数退避 + 抖动 避免“惊群”
重连后重新订阅 服务端重启后订阅关系会丢
消息去重 重连可能收到重复消息
页面隐藏时 可以降频或断开,省电省流量

3.2 SSE(Server-Sent Events)

Section titled “3.2 SSE(Server-Sent Events)”

SSE vs WebSocket：

维度 SSE WebSocket
方向 单向(服务端 → 客户端) 双向
协议 HTTP 独立协议(握手后升级)
重连 浏览器自动 需自己实现
编码 UTF-8 文本 文本/二进制
跨域 走普通 HTTP,CORS 简单 需处理 Origin 校验
适用 大屏数据推送、通知、日志流 聊天、协同编辑、游戏

大屏/通知用 SSE 就够，省掉 WebSocket 的心跳和重连代码。AI 流式输出也是 SSE 的典型场景（见 /前端/ai-integration/1-streaming）。

五、面试高频问答

Section titled “五、面试高频问答”

Q1：localStorage 和 IndexedDB 怎么选？

Section titled “Q1：localStorage 和 IndexedDB 怎么选？”

答：localStorage 同步、只存字符串、5MB 左右，适合 token 和偏好设置；IndexedDB 异步、结构化对象、可建索引、支持事务、容量大，适合离线草稿、列表缓存、大数据。ERP 场景：token 存 localStorage，离线草稿和列表缓存用 IndexedDB。

Q2：Service Worker 有什么坑？

Section titled “Q2：Service Worker 有什么坑？”

答：

  1. 缓存住坏版本 —— 需要版本化缓存名 + skipWaiting + 提示用户刷新
  2. 调试困难 —— 改代码看不到效果，要“更新 Service Worker”/“清除缓存”
  3. 拦截所有 fetch —— 一个 SW 写错，整个应用都挂
  4. 不该用的场景别用 —— 后台管理系统实时性强，缓存反而是负担

Q3：WebSocket 断线重连怎么实现？

Section titled “Q3：WebSocket 断线重连怎么实现？”

答：监听 onclose 触发重连，指数退避 + 随机抖动（1s、2s、4s…上限 30s），抖动避免服务端恢复时所有客户端同时重连打垮它；重连成功后要重新订阅（服务端重启会丢订阅关系）；配合 25~30s 心跳检测半开连接；消息带递增 id 做去重。

Q4：SSE 和 WebSocket 怎么选？

Section titled “Q4：SSE 和 WebSocket 怎么选？”

答：只需服务端推送（数据大屏、通知、日志、AI 流式输出）就用 SSE——它是普通 HTTP，浏览器自动重连，跨域简单。只有需要高频双向通信（聊天、协同编辑）才用 WebSocket。

Q5：什么任务该放 Web Worker？

Section titled “Q5：什么任务该放 Web Worker？”

答：CPU 密集且不需要 DOM 的任务——大文件解析（Excel/CSV）、hash 计算、加解密、图像处理、大数组运算。判断标准：如果主线程在 100ms 内无法完成，或者执行时页面明显卡顿，就该搬走。用 Transferable 传大数组避免拷贝。

Q6：怎么实现离线可用（PWA）？

Section titled “Q6：怎么实现离线可用（PWA）？”

答：三件套：

  1. Service Worker 缓存静态资源（缓存优先）和接口（网络优先+兜底缓存）
  2. Web App Manifest 声明可安装、图标、启动画面
  3. IndexedDB 存离线数据 再配合版本化缓存 + 提示用户更新新版本。

📝 小结

Section titled “📝 小结”
  • 离线能力的技术底座是 Service Worker,不是 localStorage。
  • 实时通信三选一:WebSocket(双向)/ SSE(服务端单向)/ 轮询(最简单)。
  • 离线要预缓存 app shell,否则断网时连页面都打不开。
  • App 内嵌 H5 还有一层:postMessage 和原生通信,要注意 origin 校验。
