大型项目目录结构 ​

100+ 页面、多团队、长期维护的项目，目录结构决定生死。

一、3 种常见组织方式 ​

方式结构适用
按技术类型（type-first）components/, pages/, utils/小型项目
按业务模块（feature-first）features/user/, features/order/中大型项目（推荐）
按 DDD 限界上下文（bounded context）domains/billing/, domains/payment/微前端 / 大型企业级

二、按业务模块（feature-based） ​

2.1 结构 ​

src/
  ├── app/                    # 应用初始化
  │   ├── App.tsx
  │   └── router.tsx
  │
  ├── features/               # 业务模块
  │   ├── user/
  │   │   ├── components/
  │   │   │   ├── UserCard.tsx
  │   │   │   └── UserList.tsx
  │   │   ├── pages/
  │   │   │   ├── UserListPage.tsx
  │   │   │   └── UserDetailPage.tsx
  │   │   ├── api.ts          # 该 feature 的 API
  │   │   ├── types.ts
  │   │   ├── hooks.ts        # useUser 等
  │   │   ├── store.ts        # 状态管理
  │   │   ├── routes.tsx      # 子路由
  │   │   └── index.ts        # 公开 API
  │   │
  │   ├── order/
  │   │   └── (类似结构)
  │   │
  │   └── ...
  │
  ├── shared/                 # 跨 feature 共享
  │   ├── ui/                # 通用组件
  │   ├── api/               # API 封装
  │   ├── hooks/              # 通用 Hook
  │   ├── utils/              # 工具函数
  │   ├── types/              # 通用类型
  │   └── config/             # 配置
  │
  └── core/                   # 基础设施
      ├── http.ts
      ├── auth.ts
      └── storage.ts

2.2 优点 ​

  • ✅ 一个 feature 一个目录，团队协作无冲突
  • ✅ 删除业务时整个目录删除
  • ✅ 跨 feature 复用放 shared/

2.3 关键：feature 之间不直接依赖 ​

ts
// ❌ features/order 直接依赖 features/user
import { UserCard } from '@/features/user/components/UserCard'

// ✅ 通过公开 API
import { UserAvatar } from '@/features/user'  // 从 index.ts 导出

features/user/index.ts：

ts
// 公开 API（白名单）
export { UserAvatar } from './components/UserAvatar'
export { useUser } from './hooks'
export type { User } from './types'
// 不导出 UserCard 等内部组件

2.4 ESLint 强制边界 ​

js
// eslint.config.js
rules: {
  'import/no-restricted-paths': ['error', {
    zones: [
      {
        from: './src/features/user/**',
        target: './src/features/order/**',
        message: 'features/order 不能直接依赖 features/user，用共享 API',
      },
    ],
  }],
}

三、按 DDD 限界上下文 ​

3.1 结构（适合微前端） ​

src/
  ├── domains/
  │   ├── identity/           # 身份上下文
  │   │   ├── User.ts
  │   │   ├── Role.ts
  │   │   ├── Permission.ts
  │   │   ├── api.ts
  │   │   └── ui/             # 该域的 UI
  │   │
  │   ├── billing/            # 计费上下文
  │   │   ├── Order.ts
  │   │   ├── Invoice.ts
  │   │   ├── Payment.ts
  │   │   ├── api.ts
  │   │   └── ui/
  │   │
  │   ├── inventory/          # 库存上下文
  │   │
  │   └── shared-kernel/      # 共享内核
  │       ├── Money.ts
  │       └── Address.ts
  │
  ├── app/                    # 应用层（编排）
  │   └── application-services/
  │
  └── infrastructure/         # 基础设施
      └── http.ts

3.2 适用场景 ​

  • 微服务后端 + 微前端
  • 多个独立团队
  • 业务复杂、需要清晰边界

四、具体决策 ​

4.1 业务模块之间如何通信？ ​

1. 共享内核（shared-kernel）
   - Money、Address 等通用类型
   - 放 src/shared/

2. 事件总线（Event Bus）
   - 跨模块触发解耦
   - 用 mitt / 自定义事件

3. 状态管理
   - 全局状态（Zustand / Redux）
   - 模块读写全局 state

4. URL / 路由
   - /user/123 -> 跳转到 order 上下文
   - 通过 URL 传 ID

4.2 通用组件 vs 业务组件 ​

src/shared/ui/        # 通用组件（无业务）
  Button.tsx
  Input.tsx
  Modal.tsx

src/features/user/ui/ # 业务组件（带 user 业务）
  UserCard.tsx          # 用了 user 业务逻辑

4.3 页面归属 ​

src/app/pages/        # 应用入口页（登录、首页）
src/features/{feature}/pages/  # 各业务模块的页面

五、真实案例：某中后台 SaaS ​

src/
  ├── app/
  │   ├── App.tsx
  │   ├── router.tsx

八、面试高频追问 ​

Q1: 你们项目怎么组织目录？ ​

答：feature-based。一个业务模块一个目录（features/user/），里面有 pages/components/api/types/hooks。跨 feature 通过 shared/ 复用，feature 之间通过公开 API（index.ts）通信。

Q2: 为什么用 feature-based 而不是 type-based？ ​

答：

  • type-based（components/、pages/）一个特性散落在多个目录，改一个 feature 要改 4-5 个目录
  • feature-based 一个 feature 自包含，删除 feature = 删除目录

Q3: feature 之间怎么通信？ ​

答：

  • 通过 shared/
  • 通过 index.ts 公开 API
  • 通过全局状态（Zustand）
  • 通过 URL/路由
  • 通过事件总线

Q4: 大型项目入口在哪里？ ​

答：src/app/App.tsx 是应用入口，src/app/router.tsx 是路由（懒加载各 feature 的 pages）。

Q5: 微前端怎么分？ ​

答：每个微应用是一个独立的 apps/{name}/，独立部署、独立仓库（也可以同 monorepo）。

面试追问(深化原 Q1-Q5) ​

  • 大目录分业务域怎么分? src/modules/order/ / src/modules/user/;每个域内自闭环(components + hooks + store + api)
  • 单仓 vs 多仓? 单仓(monorepo) 适合共享代码;多仓适合权限隔离 / 独立发布
  • circular dependency 怎么避免? ESLint import/no-cycle;service 层单向依赖
  • 公共组件库放哪? 独立仓库 / packages/ui(monorepo);业务侧通过版本管理
