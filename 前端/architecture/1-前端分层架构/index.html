  • ❌ 改了 A 模块，B 模块炸了
  • ❌ 组件依赖混乱
  • ❌ 难测试、难重构

Section titled “3.2 业务层”

  • 用例管理（CRUD、状态机）

Section titled “3.3 数据层”

  • 存储（localStorage / IndexedDB）
  • 工具（日期、格式化）

Q1: 你们项目怎么分层？

Section titled “Q1: 你们项目怎么分层？”

答：4 层架构——UI 层（纯渲染）、业务层（用例）、数据层（API）、基础设施层（网络、存储、工具）。单向依赖，下层不依赖上层。

Q2: 为什么需要分层？

Section titled “Q2: 为什么需要分层？”

答：

  • 解耦（可独立测试、可替换实现）
  • 边界（团队协作）
  • 易维护（修改影响范围可控）

Q3: 业务逻辑放 UI 还是业务层？

Section titled “Q3: 业务逻辑放 UI 还是业务层？”

答：放业务层。

  • UI 层只渲染 + 处理交互
  • 业务规则（“订单已支付不能修改”）放业务层
  • 否则 UI 组件没法跨项目复用

Q4: DDD 在前端怎么应用？

Section titled “Q4: DDD 在前端怎么应用？”

答：领域模型（实体、值对象、聚合）放 src/domain/，业务规则（领域服务）放业务层。数据层只是“获取领域模型”。

Q5: 小项目值得做吗？

Section titled “Q5: 小项目值得做吗？”

答：

  • 小项目（< 10 页面）：单层即可
  • 中项目（10-100 页面）：2 层（UI + 数据）
  • 大项目（100+ 页面）：4 层

面试追问(深化原 Q1-Q5)

Section titled “面试追问(深化原 Q1-Q5)”
  • MVC 在前端还适用吗? React/Vue 是 MVVM 或单向数据流;MVC 的“控制器”被组件替代
  • 分层架构核心原则? 上层依赖下层,下层不依赖上层;每层有清晰职责
  • 4 层 vs 3 层架构? 加 Service 层封装业务逻辑,UI 只负责展示
  • DDD 适合前端吗? 战术设计可用(聚合、值对象);战略设计一般后端为主

📝 小结

Section titled “📝 小结”
  • 分层的目的不是「好看」,而是让改动的影响范围可控。
  • 典型四层:页面层(路由与编排)/ 组件层(展示)/ 业务层(领域逻辑)/ 基础层(请求、工具)。
  • 依赖方向必须单向向内:基础层不认识业务层,业务层不认识页面层。
  • 判断分层是否合理:改一个接口字段,要动几个目录?超过两层说明分层错了。
