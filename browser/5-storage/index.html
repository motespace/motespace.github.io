浏览器存储深度专题:从 Cookie 到 IndexedDB 的全景指南

浏览器存储是前端工程师绕不开的话题。登录态、用户偏好、表单草稿、离线数据、PWA 缓存——不同场景选错存储方案,要么性能塌方,要么安全事故。本文按“为什么 → 怎么用 → 选哪个 → 安全 → 实战”五段式展开,配完整代码示例和真实项目经验。

[[toc]]

一、为什么需要浏览器存储

Section titled “一、为什么需要浏览器存储”

1.1 HTTP 是无状态的

Section titled “1.1 HTTP 是无状态的”

HTTP 协议从设计上就是“无状态”的——服务器处理完一个请求就忘了客户端是谁。这意味着:

要让服务器“记住”客户端,客户端必须主动告知身份——这就是 Cookie 的本质。

1.2 Cookie 的硬限制

Section titled “1.2 Cookie 的硬限制”

Cookie 作为最早的浏览器存储方案,有三条硬伤:

限制 数值 后果
单 Cookie 大小 ~4 KB 只能存小数据(token、session ID)
单域名 Cookie 数 ~50 个 多了被截断
每次请求自动携带 ✅ 大 Cookie 让每个请求都臃肿

这就是为什么需要更优方案——Web Storage、IndexedDB、Cache API 填补了大容量、不随请求发送、不限数量的存储需求。

1.3 五种存储定位

Section titled “1.3 五种存储定位”
存储 大小 生命周期 随请求带 定位
Cookie ~4 KB 可配 ✅ 登录态、CSRF Token
LocalStorage 5~10 MB 永久(手动清) ❌ 用户偏好、轻量缓存
SessionStorage 5~10 MB 标签页关闭即清 ❌ 表单草稿、跨页面状态
IndexedDB 几百 MB~几 GB 永久(可申请持久化) ❌ 结构化大数据、离线数据
Cache API 看配额(总配额的一部分) 手动管理 ❌ Service Worker 资源缓存

每种存储都有明确的“主战场”,下面逐个深度剖析。

9.1 商户后台:从 localStorage 迁到 IndexedDB

Section titled “9.1 商户后台:从 localStorage 迁到 IndexedDB”

问题: 商户管理 SaaS 的“操作历史”功能,需要存几千条记录(操作类型、时间、用户、payload)。最初用 localStorage,刷新页面后报错:

根因:

  • 几千条 JSON 序列化后 ~3 MB,接近 localStorage 5 MB 配额
  • 一旦塞点图片 base64 或者别的,就超了
  • 写入是同步的,几千条操作历史刷新页面加载要 200ms+

方案迁移到 IndexedDB:

效果:

  • 容量从 5 MB → 几百 MB(无压力)
  • 同步阻塞 → 异步,首屏加载 200ms+ → <50ms
  • 支持复杂查询(按用户、按时间范围)
  • 索引建立后,查询从 O(N) → O(log N)

详见 /browser/14-project-pitfalls.md 六节。

🎯 面试常考

Section titled “🎯 面试常考”

Q1：Cookie / localStorage / sessionStorage 怎么选?

Cookie 会被自动带上且可设 HttpOnly/SameSite,适合存会话 ID;localStorage 持久但 JS 可读,适合偏好设置;sessionStorage 标签页关闭即清。

Q2：存储容量?

Cookie 每条约 4KB 且总数受限;localStorage/sessionStorage 一般 5~10MB(各浏览器不同)。大数据别往里放。

Q3：IndexedDB 什么时候用?

数据量大(离线缓存、文件、复杂对象)时。异步 API、支持索引和事务,比 localStorage 强得多但复杂度也高。

📝 小结

Section titled “📝 小结”
  • Cookie 自动携带但有 4KB 限制和路径/域约束;localStorage 同步、持久、5~10MB、JS 可读。
  • 存储 Token 优先 HttpOnly Cookie(防 XSS 读);但注意 Cookie 自动带上,CSRF 要另外防。
  • 大数据(离线缓存、文件、结构化数据)用 IndexedDB:异步、支持索引和事务。
  • 所有 Web Storage 都是同步 API,读写会阻塞主线程,大数据别放。
