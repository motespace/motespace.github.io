HTTP 缓存:从强缓存到 CDN 的完整体系

系列:浏览器原理 / 第四章

本篇聚焦浏览器侧 HTTP 缓存,涵盖强缓存、协商缓存、缓存位置、刷新行为、CDN 协作、实战配置与项目踩坑。

配套阅读:网络篇《HTTP 缓存机制》关注协议层;本篇关注浏览器实现与工程落地。

一、为什么 HTTP 缓存是性能优化之首

Section titled “一、为什么 HTTP 缓存是性能优化之首”

浏览器加载一个页面的总耗时,网络往返往往占大头。HTTP 缓存的目标只有一个:让重复请求“几乎免费”。

两个层面优化:

  • 减少请求数:直接命中缓存,根本不发请求;避免 DNS、TCP、TLS 握手
  • 减少响应体积:即使要发请求(协商缓存 304),body 也是空的

典型场景:一个打包后的 JS 文件 app.4f3a.js 大小 500KB,gzip 后 130KB。强缓存命中后,浏览器零网络开销;协商缓存命中(304),只需几十字节往返。两者差距是几百倍。

真实数字:

场景 单次耗时 100 用户 PV 节省
无缓存(200 + 500KB body) ~250ms 25s 总和
协商缓存(304 + 0 body) ~30ms 3s 总和
强缓存命中(0 请求) ~0ms 0

在首屏场景下,缓存命中率 95% 意味着 100 个资源里只有 5 个真正走网络,这是 Lighthouse Performance 评分从 70 提升到 95+ 的关键杠杆之一。

更进一步,缓存是 0 RTT 优化 的基础。如果连 304 都不想要,就只有强缓存一种选择——这也是为什么 Vite/Webpack 产出的资源都默认带 hash 文件名 + immutable 头。

对照案例:某电商首页有 30 个静态资源(JS/CSS/图片/字体),平均每个 100KB。未命中缓存时首屏 800KB 下载量,耗时 1.8s;开启 immutable 后二次访问下载量 0,耗时 50ms(其余是 HTML 解析)。差距是 36 倍。

三、强缓存深度

Section titled “三、强缓存深度”

3.1 Expires(HTTP/1.0,已废弃)

Section titled “3.1 Expires(HTTP/1.0,已废弃)”

原理:服务器返回资源的过期时间(绝对时间戳),浏览器拿本地时间和这个值比较,没过期就用本地副本。

致命缺陷:

  • 依赖客户端时钟。如果用户改系统时间或跨时区,缓存判断立刻失准
  • 时间戳是绝对值,服务器时间一旦漂移就出 bug
  • HTTP/1.1 的 Cache-Control: max-age 用相对秒数,完美避开这些问题

实战中 Expires 只作为 HTTP/1.0 兼容兜底,主键仍然是 Cache-Control。

3.2 Cache-Control 完整指令表

Section titled “3.2 Cache-Control 完整指令表”
指令 含义 典型值
max-age=N 相对秒数,缓存 N 秒 max-age=3600
s-maxage=N 共享缓存(CDN)专用,覆盖 max-age s-maxage=86400
public 允许任何中间缓存(CDN/代理)存 标志位
private 只允许浏览器缓存,CDN 不许存 标志位
no-cache 强制每次都要协商(走 304 流程) 标志位
no-store 完全不缓存任何位置 标志位
must-revalidate 过期后必须重新验证,不能直接用 标志位
immutable 永不过期(配合 hash 文件名) 标志位
stale-while-revalidate=N 过期后 N 秒内先用旧值,后台刷新 stale-while-revalidate=60
stale-if-error=N 过期后 N 秒内,如果源站 5xx 仍用旧值 stale-if-error=86400
proxy-revalidate 中间代理必须重新验证(类似 must-revalidate) 标志位
no-transform 中间代理不允许改 Content-Encoding 等 标志位

3.3 关键指令逐条精解

Section titled “3.3 关键指令逐条精解”

max-age

Section titled “max-age”
  • 单位是 秒,不是毫秒
  • 起点是 响应离开服务器的时刻,不是浏览器接收的时刻
  • 命中后浏览器不发请求,直接 200 from disk/memory cache

public vs private

Section titled “public vs private”
  • private:只有用户浏览器能存,中间代理(CDN/公司网关)不能缓存
  • 适用于带用户信息的响应(登录后的 HTML、用户头像 JSON)
  • 反之,public 表示“任何人都能缓存”,适合静态资源

实战经验:登录后的 HTML 一律加 private + no-cache,否则 CDN 把张三的 HTML 缓存给李四,直接串号。

no-cache vs no-store

Section titled “no-cache vs no-store”

最容易搞混的两个:

指令 缓存吗? 走 304 吗? 重新下载吗?
no-cache 缓存 每次都问 没变就不下
no-store 不缓存 不问 每次都下

记忆口诀:

  • no-cache 等于 “缓存但要验证”
  • no-store 等于 “别存任何东西”

s-maxage

Section titled “s-maxage”
  • 浏览器看到 max-age:60,缓存 1 分钟
  • CDN 看到 s-maxage:86400,缓存 1 天
  • 一个响应头,两边各算各的,互不干扰。这就是 §九 的伏笔。

must-revalidate

Section titled “must-revalidate”

默认行为下,缓存过期后浏览器可以直接用本地副本(stale),不重新验证。 must-revalidate 强制“过期后必须问服务器”。

实战场景:金融/医疗数据,过期哪怕 1 秒都不可用,必须 must-revalidate。

immutable

Section titled “immutable”

承诺给浏览器:这个 URL 未来一年内不会变,刷新页面也不要来问我。

  • 配合 hash 文件名使用(app.abc123.js 里 abc123 是内容指纹)
  • 文件名变了意味着新版本,旧 URL 自然过期
  • 浏览器收到 immutable 后,用户按 F5 也不会发请求

实测:immutable 资源在用户主动刷新页面时,网络面板里 304 都不会出现,真正 0 RTT。

stale-while-revalidate

Section titled “stale-while-revalidate”

时序图:

  • 0~60s:新鲜期,直接用
  • 60~360s:过期但可用,先用旧值,同时后台发请求刷新
  • 360s 后:缓存被淘汰

实战意义:用户感知 0 等待,后台悄悄把新版本拉回来。下次访问就是新的。

stale-if-error

Section titled “stale-if-error”

源站返回 5xx 错误时,7 天内用旧副本顶上,不报错给用户。

适用场景:营销活动页、新闻详情页,宁可显示旧内容也别显示 502。

Section titled “四、协商缓存深度”

4.1 Last-Modified / If-Modified-Since

Section titled “4.1 Last-Modified / If-Modified-Since”

服务器比对文件 mtime,一致则返回 304,否则 200 + 新文件。

缺陷(秒级精度):

结果:版本 B 的修改永远不会被发现,服务器永远返回 304 给用户,新代码发不出去。

其他缺陷:

  • 文件改了但 mtime 没动(touch、git checkout、CDN 回源)→ 304 但内容已变
  • 时间戳只能精确到秒,1 秒内的修改丢
  • 没有跨语言统一哈希,文件复制后时间就变

5.3 哪些资源进 memory cache

Section titled “5.3 哪些资源进 memory cache”

经验之谈(Chrome 实现细节,版本相关):

资源类型 Memory 还是 Disk? 原因
体积小(几十 KB)的 JS/CSS Memory 优先 进程内复用成本极低
同页面内多次引用的图片 Memory 优先 避免重复 IO
大 JS 文件(> 1MB) Disk 占内存大,挤掉其他资源
字体文件 Disk 太大,常驻又不一定复用
视频 Disk 或不缓存 体积小,缓存收益低

实战规律:

  • 用户点链接打开新页面 → 大量 from memory cache,首屏飞快
  • 用户刷新当前页(F5)→ memory cache 清空,大多走 disk cache
  • 用户开新 Tab(同站)→ 共享 disk cache,memory cache 不共享

10.1 案例一:没 hash 导致 30% 用户拿到旧 JS

Section titled “10.1 案例一:没 hash 导致 30% 用户拿到旧 JS”

背景:某 SaaS 后台管理系统,2023 年 8 月一次大版本发版。

事故现象:

  1. 检查服务器返回的响应头:/static/app.js 没有 contenthash
  2. 服务器返回 Cache-Control: max-age=3600(1 小时)
  3. CDN 缓存 1 天
  4. 30% 用户在过去 1 小时内访问过,缓存里是旧 JS

  3. HTML 配 Cache-Control: no-cache
  4. CDN 清旧缓存
  5. 半小时后全量生效,反馈清零

10.2 案例二:CDN 没 Vary: Accept-Encoding 导致部分用户拿错数据

Section titled “10.2 案例二:CDN 没 Vary: Accept-Encoding 导致部分用户拿错数据”

背景:某资讯门户 CDN 加速,2024 年 3 月。

事故现象:

  • 客服收到反馈:“网页排版乱了”
  • 报错集中在 Chrome 用户
  • 其他浏览器正常

根因排查:

  1. 抓包发现,部分 Chrome 用户拿到的 CSS 是 gzip 压缩后的字节流
  2. 但 CSS 文件没有 Content-Encoding: gzip 头
  3. 浏览器以为没压缩,直接当文本解析 → 乱码

根因深挖:

  1. 源站 nginx 配置了 gzip on
  2. CDN 配置里 没有勾选“保留源站 Content-Encoding”
  3. CDN 把压缩数据当原始数据缓存了
  4. 部分用户(可能是 CDN 边缘节点缓存版本不一致)拿到压缩字节流但没看到编码头

修复方案:

  1. nginx 加 gzip_vary on;(自动输出 Vary: Accept-Encoding 头)
  2. CDN 强制“按 Vary 头分桶缓存”
  3. CDN 清缓存
  4. 加监控:检测资源 Content-Encoding 和 Vary 头一致性

后续改进:

  • nginx 全局开启 gzip_vary on
  • CDN 配置模板强制 Vary 头
  • CI 里加检查项:静态资源响应头必须有 Vary: Accept-Encoding

HTML 也配 max-age 发版后用户拿旧 HTML → 白屏 HTML 必须 no-cache
没 hash 文件名 用户永远拿旧 JS Webpack/Vite 加 contenthash
Vary: * CDN 不缓存,流量全打源站 检查 nginx gzip_vary on
public + 用户数据 跨用户串数据 用户数据必须 private
POST 没 no-store 表单重复提交 POST 一律 no-store
旧 hash 文件立刻删 部分用户 404 → 白屏 保留旧文件 7 天
no-cache 和 no-store 混用 配置错误 no-cache 不缓存验证,no-store 完全不存
Memory Cache 在刷新时丢失 F5 后所有小 JS 重新下载 这是浏览器默认行为,合理
服务端默认 Cache-Control 接口被缓存导致数据不一致 默认 private, no-cache
CDN 不按 Vary 分桶 部分用户拿错数据 CDN 强制按 Vary 分桶
nginx add_header 在 if 块 头不生效 用 map 或独立 location
immutable 配 no-cache head 冲突,immutable 被忽略 不要混用

10.6 案例六:跨版本兼容的缓存策略升级

Section titled “10.6 案例六:跨版本兼容的缓存策略升级”

背景:某中后台系统从 jQuery 时代迁到 React,需要双轨运行 6 个月让老用户适应。

事故现象:

  • 升级期间,部分用户拿到 React 版,部分拿到 jQuery 版
  • 两版本接口路径冲突,报错率飙升 15%

根因排查:

  1. 老版 /static/app.js 没 hash 文件名,缓存 1 天
  2. 新版也用 /static/app.js,但内容完全不同
  3. 老缓存命中后,用户继续跑老代码

修复方案:

  1. 新版部署到 /static/v2/app.abcd.js(目录 + hash 双保险)
  2. 旧 /static/app.js 强制 no-cache
  3. 用 &lt;script&gt; 标签根据 cookie 判断用户加载哪个版本
  4. 灰度 6 个月后,统一到新版本

经验教训:任何“版本切换期”必须有 hash 隔离,否则缓存就是把双刃剑。

10.7 案例七:营销页 CDN 缓存导致活动推迟显示

Section titled “10.7 案例七:营销页 CDN 缓存导致活动推迟显示”

背景:某电商双 11 营销活动,活动页内容需要精确到秒切换。

事故现象:

  • 0 点活动开始,但部分用户看到的还是预热页
  • 持续 5 分钟才全量生效

根因排查:

  1. 活动页用 max-age=600(10 分钟)
  2. CDN 缓存 30 分钟
  3. 0 点改内容,CDN 还返回旧版

修复方案:

  1. 营销页配置 max-age=60, s-maxage=60(短缓存)
  2. CDN 配置 Cache-Control: max-age=60 强制覆盖
  3. 0 点前 5 分钟手动 Purge 一次

经验教训:内容时效性强的页面,缓存上限 = 业务可接受的延迟。

11.7 性能监控指标

Section titled “11.7 性能监控指标”

线上观察缓存是否生效,必须监控这几个指标:

CDN 命中率:

健康值:静态资源 90%+,API 接口 0%(除非明确配置)。

回源比:

健康值:静态资源 < 10%,营销页 < 30%。

首字节时间(TTFB):

强缓存命中:TTFB 接近 0。 CDN 命中:TTFB 几十 ms。 回源:TTFB 几百 ms 到几秒。

监控告警配置:

指标 告警阈值 含义
CDN 命中率突降 20% 5 分钟 缓存配置可能被改
回源 QPS 飙升 1 分钟 可能被攻击或配置错
4xx/5xx 比例 > 1% 持续 5 分钟 资源失效或源站故障
静态资源 404 > 0 旧 hash 文件被删太快

14.2 缓存决策的 8 个关键问

Section titled “14.2 缓存决策的 8 个关键问”
  1. 资源是否会被重复请求? 不会 → 不缓存。会 → 强缓存。
  2. 资源是否会变? 会变 → 协商缓存(ETag)。不变 → 强缓存(immutable)。
  3. 响应是否包含用户隐私? 是 → private。否 → public。
  4. 缓存对 CDN 是否合理? 合理 → public。不合理 → private。
  5. 过期后是否可用旧值? 是 → stale-while-revalidate。否 → must-revalidate。
  6. POST 还是 GET? POST → no-store。GET → 看场景。
  7. 资源是否带 hash? 带 → 一年时长。不带 → 短时长或协商缓存。
  8. CDN 缓存多久? 用 s-maxage 控制。

14.3 缓存性能优化清单

Section titled “14.3 缓存性能优化清单”
  • 静态资源全部带 hash 文件名
  • 静态资源全部 max-age=31536000, immutable
  • HTML 永远 no-cache
  • API 默认 private, no-cache
  • POST 一律 no-store
  • 启用 gzip + gzip_vary on
  • nginx/Express 配 Vary 头
  • CDN 强制按 Vary 分桶
  • 服务器保留旧 hash 文件 7 天
  • 监控 CDN 命中率、回源比
  • 监控静态资源 404
  • Service Worker 用 SWR 策略
  • 字体/图片用 immutable
  • 营销页用短缓存 + 强制 Purge

🎯 面试常考

Section titled “🎯 面试常考”

Q1：强缓存和协商缓存的区别?

强缓存直接用本地副本不发请求(由 Cache-Control / Expires 控制);协商缓存发请求但只带 If-None-Match / If-Modified-Since,服务端返回 304 表示用缓存。

Q2：怎么配置?

带 hash 的静态资源用 max-age=31536000, immutable;HTML 用 no-cache(仍会校验但能拿到最新)。

Q3：Cache-Control 常用指令?

max-age、s-maxage(CDN 缓存)、no-cache(可缓存但必须校验)、no-store(不缓存)、immutable、must-revalidate、stale-while-revalidate。

📝 小结

Section titled “📝 小结”
  • 两层:强缓存(不发请求)→ 协商缓存(304)。顺序不能反。
  • no-cache 是「缓存但每次验证」,no-store 才是「不缓存」,最容易搞混。
  • 带 hash 的静态资源长缓存 immutable,HTML 入口 no-cache —— 标准搭配。
  • 「改了不生效」优先查:文件名有没有 hash、SW 缓存换代没、Vary 头全没。
