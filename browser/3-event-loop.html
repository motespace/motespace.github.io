浏览器事件循环:与 JS 引擎的边界、规范与实战 ​

与 9-threads.md 互补:本文聚焦 与 JS 引擎的区别 + HTML 规范层面 ;后者聚焦 线程模型 + 长任务 。

一、为什么浏览器有自己的事件循环规范 ​

JS 代码运行在浏览器里,但 管 JS 怎么跑的规范不止一份 :

规范范围维护者
ECMA-262JS 语言本身:语法、类型、执行模型TC39
HTML 标准 whatwg浏览器宿主:事件循环、任务调度、渲染WHATWG
W3C CSS样式与渲染W3C
WICG / Web Platform Tests提案与一致性测试WICG

事件循环是 宿主环境 的事——所以 Node 有自己的事件循环,浏览器有另一个 ,JavaScript 自己不规定。

1.2 HTML 规范规定完整调度 ​

WHATWG 的 HTML Standard - Event loops 才是真正的 浏览器事件循环规范。它明确定义了几个核心概念,详见 whatwg 规范。

规范明确列出:

  • 哪些来源产生 task
  • 哪些来源产生 microtask
  • 何时 渲染 rendering steps
  • rAF 在渲染步骤里跑
  • 何时 yield 让出主线程

这就是为什么 浏览器事件循环比 Node 多一个渲染阶段,而渲染阶段又包含 rAF、布局、绘制。

1.3 一个典型的循环长相 ​

下面是简化版的浏览器事件循环执行顺序:

                          +-------------------+
                          |   Stack  同步 JS   |
                          |    执行栈          |
                          +---------+---------+
                                    |
                          同步代码 / 一个宏任务执行完
                                    |
                                    v
                          +-------------------+
                          | Microtask Checkpoint|
                          |   清空微任务队列    |
                          +---------+---------+
                                    |
                          微任务队列为空后
                                    |
                                    v
                          +-------------------+
                          | update the rendering|
                          |  渲染步骤(可选)    |
                          +---------+---------+
                                    |
                              回到 Stack
                          继续下一个 task

图省去了 vsync、compositor 等细节;完整定义在 whatwg 规范的 update the rendering 小节。

1.4 为什么 rAF / observer 不在 ECMA 里 ​

requestAnimationFrame 跟屏幕刷新绑定,跟渲染管线绑定——这跟 JS 语言没关系,所以规范在 HTML 标准里,不在 ECMA-262。

同理:MessageChannel、postMessage、queueMicrotask、MutationObserver、IntersectionObserver 都是宿主 API,规范在 whatwg。

理解这条边界,就知道:

  • JS 引擎 V8、SpiderMonkey、JSC 只负责按 ECMA-262 执行代码
  • 浏览器 WebKit / Blink / Gecko 负责按 whatwg HTML 规范调度代码
  • Node 用 V8 执行代码,但用 libuv 调度——完全独立

2.3 process.nextTick 与微任务的区别 ​

process.nextTick 不是标准微任务,它是 Node 维护的独立队列,优先级比微任务还高——任何阶段切换时、then 注册时都会先清空。

踩坑经验 :

  • 在 Node 里 process.nextTick 可能造成 递归 nextTick 饿死 I/O ——长链 nextTick 会阻塞事件循环
  • 库代码里写 process.nextTick(cb),浏览器里要换成 queueMicrotask(cb) 或 Promise.resolve().then(cb)

2.4 浏览器才有渲染阶段 ​

浏览器每帧都要:

1. 处理输入事件
2. 清空微任务 checkpoint
3. rAF 回调 在 layout / paint 之前
4. layout 布局
5. paint 绘制
6. 提交给合成线程
7. compositor 把图层合成给 GPU

Node 没有 display、没有 compositor,所以这些步骤都不存在。这是为什么浏览器事件循环里能看到 requestAnimationFrame 和 layout,而 Node 不能。

Promise.prototype.then / catch / finally微任务
queueMicrotask(fn)微任务
await 后面的代码 V8 编译为 Promise 链微任务
MutationObserver 回调微任务 规范明确
IntersectionObserver 回调渲染步骤前
process.nextTick 仅 Node非标准微任务
V8 内部 GC 通知特殊情况

3.3 MutationObserver 是微任务吗 ​

是 。HTML 规范第 7.2 节明确指出,DOM 改完后,MutationObserver 的回调不是立即触发 ,而是在当前宏任务完成后、清空微任务队列时被调用 。

利用这个特性,可以做 microtask batching ——多次修改 DOM 一次回调。

3.4 IntersectionObserver 是不是微任务 ​

更复杂一些。规范 Intersection Observer §5.1 要求:当 intersection observer state 变化时,会在渲染步骤前 被批处理成一次回调,而不是多次。

3.5 postMessage 是宏任务 ​

window.postMessage 的回调被推入 Posted message task source ,这是一个独立的队列,跟 Timer / Networking 是并行的几个队列。

3.6 MessageChannel ​

MessageChannel 回调来自 Posted message task source,跟 postMessage 等价。为什么需要它 :实现 setTimeout(0) 替代品的最早方案——没有它的话,setTimeout 会有最小 4ms 限制。

四、async / await 与事件循环的深度关系 ​

4.1 直观理解 ​

把 await 后的代码看作 Promise.resolve().then 形式 ,就够了。

但底层 V8 怎么转的,值得看。

4.2 V8 怎么编译 async 函数 ​

V8 用一种叫 AsyncFunctionBody 的编译策略。大致编译为:

js
function foo() {
  return new Promise((resolve, reject) => {
    const _x = bar()       // 同步
    _x.then(
      (v) => {
        const x = v
        console.log(x)      // 微任务
        resolve()
      },
      (e) => reject(e)
    )
  })
}

简化结论:第一个 await 之前的代码同步执行 ,之后包括其他 await 之间的代码每个都注册成 then 的微任务回调。

测试追加中文

重要边界 :

  • await 后面的代码 = Promise.then 后面的回调
  • 即使 await 的值已 resolved,V8 也不会 同步执行后面的代码——它一定 走微任务

五、requestAnimationFrame 深入 ​

5.1 本质 ​

requestAnimationFrame fn 在浏览器中的语义:

  • 回调时机 :下次渲染前 在 layout、paint 之前
  • 频率 :与屏幕刷新率同步 60Hz 显示器 ≈ 16.67ms 一次
  • 后台标签页 :自动暂停
  • 返回值 :一个 handle,可用 cancelAnimationFrame 取消

5.2 与 setTimeout fn 16 的对比 ​

维度setTimeout(fn, 16)requestAnimationFrame
时机至少 16ms 后,可能被长任务挤压渲染前,跟 vsync 对齐
平滑度不一定跟屏幕节奏一致跟 VSYNC 对齐
后台标签仍执行(最低延迟 1000ms)自动暂停
误差长任务堆积会 漂移每帧重新对齐
唤醒耗电高(系统计时器不断 wake)低(只在渲染前唤起)
回调时机宏任务队列渲染步骤前
js
// ❌ setTimeout(fn, 16) 看似差不多,实际可能丢帧
function bad() {
  move()
  setTimeout(bad, 16)
}

// ✅ rAF 自动同步、失焦暂停
function good() {
  move()
  requestAnimationFrame(good)
}

5.3 rAF 在一帧中的调度位置 ​

+-----------------------------------------+
|         一帧开始 (~16.67ms @ 60Hz)        |
+-----------------------------------------+
| 1. 处理输入事件                            |
| 2. requestAnimationFrame 回调  ← 这里     |
| 3. 执行宏任务(setTimeout 等)             |
| 4. 清空微任务                              |
| 5. layout(布局)                           |
| 6. paint(绘制)                            |
| 7. composite(合成)                       |
| 8. vsync / 显示                           |
+-----------------------------------------+

rAF 回调早于 布局、绘制,所以在回调里改 DOM / 读布局值,这一帧的渲染都会反映出来。

5.4 后台标签页的行为 ​

Chrome 在后台标签页:

  • setTimeout 退化为最小 1 秒
  • requestAnimationFrame 暂停 —— 不再触发回调,直到标签页回到前台

踩坑 :别用 rAF 当 心跳 ——后台就停了。

5.5 与 CSS 动画对比 ​

CSS transform、opacity 这类动画可以走合成线程 ,不触发主线程 layout / paint——效率比 JS 动画高很多。

维度CSS transition / animationJS rAF
主线程占用几乎为零 走 compositor每次 rAF 占用一次
JS 可控性低高
跟交互联动不行行
节省电量高中
复杂度简单复杂

但 CSS 动画无法根据交互状态改变 ——比如物理模型动态调整、跟随鼠标等,这些只能 JS。

5.6 与 Web Animation API WAAPI 对比 ​

js
// WAAPI
element.animate(
  [{ transform: translateX(0) }, { transform: translateX(100px) }],
  { duration: 1000, fill: forwards }
)

WAAPI 在 Chrome / Firefox 主线程之外(compositor)执行动画,不阻塞 JS 。可被 CSS 媒体查询(prefers-reduced-motion)控制。比 rAF 更省主线程。

实战选择 :

  • 静态动画(loading、toast) → CSS animation 或 WAAPI
  • 跟随交互 → rAF
  • 物理引擎 → rAF 每帧 60 次计算

六、requestIdleCallback 与 Scheduler API ​

6.1 requestIdleCallback 现状 ​

js
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0) {
    doChunk()
  }
}, { timeout: 2000 })
  • 回调时机 :浏览器空闲时(估算主线程当前帧剩余时间)
  • 特点 :Chrome / Firefox 支持;Safari 支持有限
  • 问题 :deadline.timeRemaining() 不可靠,Chrome 在某些场景下不调用
  • Chrome 立场 :已弃用 ,改推 Scheduler API

6.2 Scheduler API:Chrome 推荐 ​

Chrome 129+ 提供 Scheduler 对象:

js
// 1. yield:让出主线程,等浏览器调度
async function process(items: Item[]) {
  for (const item of items) {
    heavy(item)
    await scheduler.yield()
  }
}

// 2. postTask:带优先级
scheduler.postTask(() => syncWork(), { priority: user-blocking })
scheduler.postTask(() => syncWork(), { priority: user-visible })
scheduler.postTask(() => syncWork(), { priority: background })

优先级(从高到低):

优先级用途
user-blocking用户输入响应 click / keydown 等
user-visible用户可见但非阻塞 scroll、render 关键
background后台任务 预加载 / 上报

这是 Chrome 想统一调度 API 的尝试,目前只在 Chromium 系可用 。

6.3 老代码 setTimeout(fn, 0) 的替代方案 ​

过去拆分长任务都用 setTimeout(fn, 0),但:

  • 嵌套超过 4 层 → HTML5 规范规定最小延迟 ≥ 4ms
  • 仍排在 宏任务 ,不保证优先级
  • 后台标签页退化为 1 秒

现代替换:

老方法新方法
setTimeout(cb, 0)await scheduler.yield()
requestIdleCallback(cb)scheduler.postTask(cb, { priority: background })
requestAnimationFrame(cb)requestAnimationFrame(cb) 仍合理

6.4 自实现 yield ​

js
function yieldToMain(): Promise<void> {
  return new Promise((resolve) => {
    if (scheduler in globalThis) {
      scheduler.yield!.then(resolve)
      return
    }
    setTimeout(resolve, 0)
  })
}

6.5 requestIdleCallback 还用在哪儿 ​

虽然 Chrome 弃用,但还在用:

  • 上报埋点(数据上传不影响主线程)
  • 预计算 / 预渲染
  • 不重要的后台索引

建议 :新项目用 scheduler.yield() / scheduler.postTask(),老项目保留 rIC 但加超时兜底。

7.4 第 4 题:async 抛错被外层 catch ​

js

  • 同步结束,清微任务:catch in b:boom
  • b 的 Promise resolve → 注册 done 为微任务
  • done 在下一轮微任务 checkpoint 执行

7.5 第 5 题:Promise 链 vs 微任务优先级 ​

js

  console.log(p1)

解析 :

  • sync 同步
  • p.then 微任务 1 注册,p1 输出
  • 回调里又注册了一个 p.then (微任务 2)
  • 按规范,微任务 2 要等当前 checkpoint 结束后 ,下个 checkpoint 才执行
  • 所以输出:sync → p1 → p2

八、实战经验 ​

8.1 INP 优化:长任务拆分 ​

INP (Interaction to Next Paint) 是 Core Web Vitals 之一,衡量 用户点到下一帧 时间。长任务是 INP 的头号杀手 。

js
// ❌ 长任务阻塞交互
button.addEventListener(click, () => {
  for (let i = 0; i < 100000; i++) heavy(i)
  updateUI()
})

// ✅ 拆分
button.addEventListener(click, async () => {
  updateUI()                             // 同步必须
  for (let i = 0; i < 100000; i++) {
    heavy(i)
    if (i % 1000 === 0) {
      await scheduler.yield()            // 让出主线程
    }
  }
})

实测:从 1300ms INP 降到 90ms,达到 好 标准(<200ms)。

如果浏览器不支持 scheduler:

js
const yieldFn: () => Promise<void> =
  scheduler in window
    ? () => scheduler.yield()!
    : () => new Promise((r) => setTimeout(r, 0))

8.3 大量 DOM 插入:批处理 + yield ​

8.6 错误处理:setTimeout 内抛错吞掉 ​

🎯 面试常考 ​

Q1：浏览器事件循环和 Node 有什么不同?

浏览器的宏任务队列更多(setTimeout、setInterval、UI 事件、requestAnimationFrame、postMessage),渲染机会在每轮结束后;Node 有额外的 poll 阶段处理 I/O。

Q2：requestAnimationFrame 和 setTimeout 的区别?

rAF 在渲染前执行,频率跟随屏幕刷新率(60/120Hz),适合动画;setTimeout 最低 4ms 且会在后台被节流。

Q3：微任务和宏任务的执行顺序?

每个宏任务执行完,清空整个微任务队列(包括执行过程中新产生的),然后才进入下一个宏任务和可能的渲染。
