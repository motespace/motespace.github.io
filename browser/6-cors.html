跨域与 CORS:从同源策略到工程落地 ​

本文是 12-security.md 的姊妹篇。本文讲跨域「怎么做」,12-security.md 讲跨域「怎么防」。两者重叠较小,读者可按需选读。

一、为什么需要跨域 ​

互联网早期(1995 年前),浏览器对跨域访问的限制很少。但 Web 应用兴起后,恶意页面读取用户网银 DOM、窃取 Cookie、伪造请求转账等问题层出不穷。Netscape 在 Navigator 2 中引入同源策略(Same-Origin Policy),成为现代浏览器的安全基石。

同源策略保护三类资源:

  • DOM:防止跨域页面读取你的页面结构
  • Cookie/Storage:防止跨域页面访问你的登录态和本地数据
  • AJAX 响应:防止跨域页面读取后端接口返回的隐私数据

但工程现实是:跨域才是常态。

1.1 跨域是工程常态 ​

场景跨域原因
前后端分离前端 https://app.com,后端 https://api.com,域名不同
微前端(qiankun / micro-app)主应用 https://main.com,子应用 https://sub.com
第三方 API调用 https://api.openai.com,从你自己的 https://chat.com 发起
CDN 静态资源img.example-cdn.com 与 app.example.com
嵌入式支付/地图父页面嵌入 https://pay.partner.com 的 iframe
多业务线子域merchant.example.com 与 admin.example.com

实战经验:在 SaaS 商户后台体系,我们有 4 套独立部署的前后端(主站、商家中心、运营后台、开放平台),任意两者之间都跨域,跨域请求占总网络请求 65% 以上。再考虑第三方 API(地图、支付、统计),跨域比例会更高。

跨域不是例外,是默认状态。理解跨域机制,等于理解现代 Web 工程的一半通信模型。

1.2 同源策略的副作用 ​

同源策略保护了安全,也带来了约束。下面这段代码,在浏览器控制台报错是大多数前端开发者第一次遇到的 CORS 问题:

js
// https://app.com 上的 JS
fetch('https://api.example.com/data')
  .then(r => r.json())
  .catch(err => console.log('跨域失败', err))

报错:

js
Access to fetch at 'https://api.example.com/data' from origin 'https://app.com' 
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is 
present on the requested resource.

这条错误信息里有几个关键点:

  1. Access-Control-Allow-Origin 是服务端必须返回的响应头
  2. 浏览器在客户端做了拦截,不是网络层失败
  3. 实际请求可能已经发出去了,且服务端可能也返回了 200

是的 — CORS 失败时,真实请求仍然到达了服务端。只是浏览器拒绝把响应交给 JS。这也是为什么「为什么 POST 失败但数据库多了一条记录」的诡异 bug 会发生。

1.3 跨域是问题的两面 ​

跨域机制既保护了你(防止恶意页读你的 Cookie),也限制了你(自己的页面无法访问第三方 API)。理解跨域,要两面都看到:

  • 防的视角(安全):12-security.md 详解
  • 用的视角(工程):本文详解

接下来我们从源头 — 同源策略 — 开始。

二、同源策略详解 ​

2.1 什么是「源」(Origin) ​

URL 由 5 部分组成:

https://www.example.com:443/path/to/page?query=1#hash
|        |              |   |              |       |
scheme   host           port path          query   fragment

同源策略只看前三段:scheme + host + port。三者完全相同才算同源。

URL AURL B是否同源原因
https://example.comhttps://example.com是三者相同
https://example.comhttps://api.example.com否host 不同
https://example.comhttp://example.com否scheme 不同
https://example.comhttps://example.com:8080否port 不同
https://example.comhttps://example.com/path2是path 不影响

注意:大多数 URL 协议默认隐藏端口 — HTTPS 默认 443,HTTP 默认 80。所以 https://example.com 等价 https://example.com:443。

2.2 经典反例 ​

子域名不算同源:

js
// https://app.example.com 上的 JS
fetch('https://api.example.com/data')   // 跨域!子域名不同
fetch('https://example.com/data')        // 也跨域!

子域在 DNS 层就属于不同的「site」,现代浏览器默认 site-per-process 隔离渲染进程,自然不允许跨域访问。

协议不同不算同源:

js
fetch('http://api.com/data')   // 跨域!还混合内容

端口不同不算同源:

js
// https://app.com:443 上的 JS
fetch('https://app.com:8080/data')   // 跨域!

域名 vs IP:

js
fetch('https://192.168.1.1/api')   // 跨域(host 不同)

虽然 IP 解析到 example.com,但浏览器按字面 host 判断。

file:// 协议:

js
// 本地 HTML
fetch('file:///Users/me/data.json')   // 跨域!

file:// 协议没有 host,Chrome 按规则视为不同源。

2.3 IE 行为差异(已淘汰但偶尔考) ​

浏览器特殊行为
IE 8 及以下不区分协议(http/https 算同源)
IE 8 及以下不区分端口(80/443/8080 算同源)
Edge Legacy跟随 IE
现代浏览器严格按 scheme + host + port 判定

这些 IE 行为是历史包袱。2014 年后所有现代浏览器统一了严格同源判定。面试时偶尔会被问到,答出现代标准并提一句 IE 差异即可。IE 已于 2022 年 EOL,不要再依赖老行为。

2.4 同源策略影响哪些操作 ​

操作同源限制
DOM 读取(Cookie / Storage / iframe.contentWindow)跨域禁止
fetch / XMLHttpRequest 读响应跨域禁止(CORS 解除)
Canvas drawImage跨域图片被污染(tainted)
WebSocket不受同源限制(服务器校验 Origin)
postMessage允许跨域(需校验 origin)
<script src>允许跨域加载(拿不到响应内容)
<img src> / <link href>允许跨域加载(只用于显示)
CSS @font-face允许跨域加载(需 CORS 头)

注意几个关键豁免:

  • <script> 允许跨域请求,但 JS 拿不到响应内容(这是 JSONP 的基础)
  • 跨域图片加载成功后会污染 Canvas,导致 canvas.toDataURL() 抛 security error
  • WebSocket 不受同源策略限制(浏览器不拦截 WS 连接),但服务端必须校验 Origin 头防 CSRF

2.5 历史:从弱同源到强同源 ​

1995  Netscape Navigator 2:Same-Origin Policy 雏形
      仅限制 Cookie 不能跨域读取
      DOM 没有隔离

1996  IE 3:Netscape 同源策略的 IE 实现
      加入 active content 检查

2000  IE 5:扩展到脚本、Cookie、DOM

2007  HTML5 起草:跨文档消息(postMessage)、跨域存储提案

2009  CORS 草案进入 W3C

2014  Fetch 标准统一 CORS 实现 + Promise 模式

2018  Chrome 默认 site-per-process,CORS 更严格

2020+ COOP/COEP 推动浏览器全面跨源隔离(防 Spectre)

三、跨域请求的完整分类 ​

3.1 三层分类 ​

跨域请求按复杂度分三类:

  1. 简单请求(Simple Request) — 浏览器直接发,不预检
  2. 预检请求(Preflighted Request) — 浏览器先发 OPTIONS 询问,服务端确认后再发真实请求
  3. 带凭据的请求(Credentialed Request) — 需配合简单/预检,但额外要求 Access-Control-Allow-Credentials: true

3.2 简单请求判定条件 ​

必须同时满足所有以下条件,否则就是非简单请求,触发预检:

http
1. 方法是:GET / HEAD / POST 之一
2. 请求头是浏览器自动设置的简单头:
   - Accept
   - Accept-Language
   - Content-Language
   - Content-Type(只允许 3 个值之一,见下)
3. Content-Type 必须是以下之一:
   - application/x-www-form-urlencoded
   - multipart/form-data
   - text/plain
4. 没有自定义请求头(Authorization / X-Custom-* 等)
5. 没在 ReadableStream 上调用 getReader(罕见)

任一条件不满足,就是非简单请求,触发预检。

3.3 实际项目中的非简单触发器 ​

场景触发预检的原因
POST + application/jsonContent-Type 不在三种简单类型
PUT / DELETE / PATCH方法不是 GET/HEAD/POST
加 Authorization 头自定义头
加 X-Token / X-Request-ID自定义头
加 custom-version自定义头
用 ReadableStream 上传不在简单请求范围
用 FormData + FileContent-Type: multipart/form-data(简单);但其他条件可能不满足

实战经验:fetch 默认 Content-Type 不带,但很多代码会写 Content-Type: application/json,这个直接触发预检。我们曾经有个项目初期全是 POST + JSON,每个 API 调用都要先发 OPTIONS,无形中增加 50% QPS。改成 GET + query string + text/plain 后,跨域请求数直降一半。

3.4 带凭据请求(credentials) ​

跨域请求默认不带 Cookie(浏览器限制)。要带 Cookie 必须满足以下全套:

  1. 客户端:fetch(..., { credentials: 'include' }) 或 xhr.withCredentials = true
  2. 服务端响应头:Access-Control-Allow-Credentials: true
  3. 服务端响应头:Access-Control-Allow-Origin 不能是 *,必须明确写域名
  4. 服务端响应头(可选):Vary: Origin(配合动态 origin)
  5. 客户端:能且仅能指定单一 origin,不能传 *
js
// 客户端
fetch('https://api.example.com/data', {
  credentials: 'include',   // 带上 cookie
  headers: {
    'Content-Type': 'application/json',   // 触发预检
    'X-Token': 'xxx'                       // 自定义头,也触发预检
  }
})

注意:credentials: 'include' 让请求带 Cookie,但不会绕过 CORS 检查。如果服务端没返回 Allow-Origin,照样失败。

3.5 credentials 的三种值 ​

js
fetch(url, { credentials: 'omit' })        // 默认,不带 cookie
fetch(url, { credentials: 'same-origin' }) // 同源才带,跨域不带
fetch(url, { credentials: 'include' })     // 跨域也带 cookie

same-origin 是 fetch 的默认值之一,适用于大部分场景。需要跨域带 cookie 时显式 include。

3.6 全部请求方法一览 ​

HTTP/1.1 共 9 种方法,CORS 视角下:

方法CORS 行为实际请求类型
GET简单直接发
HEAD简单直接发
POST看 Content-Type简单或预检
PUT预检OPTIONS + PUT
DELETE预检OPTIONS + DELETE
PATCH预检OPTIONS + PATCH
OPTIONS总是发(预检方法)用于协商
CONNECT一般不通过浏览器-
TRACE一般不通过浏览器-

四、简单请求完整流程 ​

简单请求直接发,服务端响应一个 Access-Control-Allow-Origin 头,浏览器检查后决定是否把响应交给 JS。

完整时序图:

  浏览器(app.com)                       服务器(api.com)
       │                                       │
       │  GET /api/user HTTP/1.1               │
       │  Origin: https://app.com              │
       │ ──────────────────────────────────────>│
       │                                       │
       │  HTTP/1.1 200 OK                      │
       │  Access-Control-Allow-Origin:         │
       │    https://app.com                    │
       │  Vary: Origin                         │
       │  Content-Type: application/json       │
       │                                       │
       │  {"name":"张三"}                      │
       │ <──────────────────────────────────────│
       │                                       │
   检查: 源匹配? ──── 是 ──> JS 拿到响应

关键点:

  • 浏览器自动加 Origin 头,JS 不能控制
  • 服务端必须回 Access-Control-Allow-Origin 头,否则浏览器拒绝给 JS
  • 服务端可以回 *(通配)但不能和 credentials 一起用(后文 §十三 详细说)

4.1 一个完整的 Node.js Express 简单请求例子 ​

js
// 客户端:https://app.com
fetch('https://api.com/user')
  .then(r => r.json())
  .then(console.log)

// 服务端(Express 中间件)
app.use((req, res, next) => {
  const origin = req.headers.origin
  // 白名单
  const allow = ['https://app.com', 'https://admin.com'].includes(origin)
  if (allow) {
    res.header('Access-Control-Allow-Origin', origin)
    res.header('Vary', 'Origin')   // 重要!防止 CDN 串缓存
  }
  next()
})

app.get('/user', (req, res) => {
  res.json({ name: '张三' })
})

4.2 浏览器到底在检查什么 ​

JS 拿到响应后,浏览器在 JS 引擎里跑一个同源检查:

function shouldExpose(origin, allowOrigin) {
  // 1. allowOrigin 是 *  → 允许
  // 2. allowOrigin === origin → 允许
  // 3. allowOrigin 是数组? → 找 origin
  // 4. 否则 → 拒绝
}

通配符 * 在 credentials 模式下不生效——浏览器看到 Access-Control-Allow-Credentials: true 会检查 Allow-Origin 是不是具体域名,如果是 * 直接拒绝。

五、预检请求完整流程 ​

非简单请求(POST + JSON、PUT、DELETE、自定义头)必须先发一个 OPTIONS 请求询问服务端:"我能这么干吗?"服务端同意后浏览器才发真实请求。

5.1 时序图 ​

  浏览器(app.com)                       服务器(api.com)
       │                                       │
       │  OPTIONS /api/order HTTP/1.1          │
       │  Origin: https://app.com              │
       │  Access-Control-Request-Method: POST  │
       │  Access-Control-Request-Headers:      │
       │    content-type, x-token              │
       │ ──────────────────────────────────────>│  ← 预检(无 body)
       │                                       │
       │  HTTP/1.1 204 No Content              │
       │  Access-Control-Allow-Origin:         │
       │    https://app.com                    │
       │  Access-Control-Allow-Methods:        │
       │    POST, GET, OPTIONS                 │
       │  Access-Control-Allow-Headers:        │
       │    Content-Type, X-Token              │
       │  Access-Control-Max-Age: 86400        │
       │ <──────────────────────────────────────│
       │                                       │
       │  POST /api/order HTTP/1.1             │
       │  Origin: https://app.com              │
       │  Content-Type: application/json       │
       │  X-Token: xxx                         │
       │  {"item":"book"}                      │
       │ ──────────────────────────────────────>│  ← 真实请求
       │                                       │
       │  HTTP/1.1 201 Created                 │
       │  Access-Control-Allow-Origin:         │
       │    https://app.com                    │
       │  Location: /order/123                 │
       │ <──────────────────────────────────────│
       │                                       │

5.2 预检缓存:Access-Control-Max-Age ​

浏览器把预检结果缓存一段时间(由 Access-Control-Max-Age 控制),缓存期内不再发 OPTIONS。

浏览器默认 Max-Age
Chrome5 秒(忽略服务器值,有安全顾虑)
Firefox5 秒
Safari5 秒(对凭证请求 1 天)
Edge5 秒

注意:Chrome 等现代浏览器把 Max-Age 上限强制为 5 秒(即便服务器返回 86400),防 CSRF。所以别太依赖长 Max-Age。

5.3 真实项目:从每秒 1 个 OPTIONS 到 0 个 ​

曾经有个项目,前端每发一个 POST 都触发预检,QPS 翻倍。优化路径:

  1. 把频繁调用的 GET 接口改成 POST + JSON(触发预检)— 错误
  2. 改回 GET + query string(简单请求)— OK,但数据量受限
  3. 用 Content-Type: text/plain 传 JSON 字符串(简单请求)— OK,后端 parse
  4. 后端主动 Access-Control-Max-Age: 86400 — 实际上 Chrome 强制 5 秒

最终方案:不依赖 Max-Age,而是改接口设计:

  • 实时数据用 WebSocket
  • 不需要预检的用 GET
  • 需要 POST 的接口走"非预检路径"(Content-Type 限定为 text/plain)

六、完整 CORS 响应头详解 ​

6.1 服务端响应头 ​

响应头必填?作用
Access-Control-Allow-Origin必填允许的源,或 *
Access-Control-Allow-Credentials凭证请求必填是否允许带 Cookie
Access-Control-Allow-Methods预检响应允许的 HTTP 方法
Access-Control-Allow-Headers预检响应允许的自定义请求头
Access-Control-Expose-Headers可选JS 可以读的额外响应头
Access-Control-Max-Age可选预检缓存时间(秒)

6.2 客户端请求头(浏览器自动加) ​

请求头谁加的作用
Origin浏览器自动当前源(URL 三段)
Access-Control-Request-Method浏览器自动(预检)真实请求的方法
Access-Control-Request-Headers浏览器自动(预检)真实请求的自定义头

JS 无法控制这些头——它们由浏览器根据当前页面源、目标 URL 自动生成。

6.3 Access-Control-Allow-Origin 三种值 ​

http
# 1. 通配(最不安全)
Access-Control-Allow-Origin: *

# 2. 单一具体源
Access-Control-Allow-Origin: https://app.com

# 3. 动态(根据 Origin 头反射)
# 服务端代码
const origin = req.headers.origin
if (allowList.includes(origin)) {
  res.setHeader('Access-Control-Allow-Origin', origin)
  res.setHeader('Vary', 'Origin')   // 必须!否则 CDN 错乱
}

6.4 Access-Control-Expose-Headers ​

默认情况下,JS 只能读 7 个简单响应头:Cache-Control、Content-Language、Content-Type、Expires、Last-Modified、Pragma。要读其他头,服务端必须 Expose:

http
Access-Control-Expose-Headers: X-Request-Id, X-Rate-Limit-Remaining

否则 response.headers.get('X-Request-Id') 拿到 null。

七、JSONP 原理(为什么过时) ​

JSONP 是早期绕过同源的方案,利用 <script src> 不受同源限制的特性。

7.1 实现 ​

js
// 客户端
function jsonp(url, params, callbackName) {
  return new Promise((resolve) => {
    window[callbackName] = (data) => {
      resolve(data)
      document.body.removeChild(script)
    }
    const query = new URLSearchParams({ ...params, callback: callbackName })
    const script = document.createElement('script')
    script.src = `${url}?${query}`
    document.body.appendChild(script)
  })
}

jsonp('https://api.com/data', { id: 1 }, 'cb')
  .then(console.log)
js
// 服务端
app.get('/data', (req, res) => {
  const data = { id: 1, name: '张三' }
  res.send(`${req.query.callback}(${JSON.stringify(data)})`)
  // 响应:cb({"id":1,"name":"张三"})
})

浏览器执行 <script>,把响应当成 JS 代码运行——执行 cb({...}),刚好是注册的全局函数。

7.2 为什么 JSONP 过时了 ​

缺点说明
只能用 GETPOST/PUT/DELETE 没法 JSONP
XSS 风险服务端返回的内容会被当成 JS 执行
错误处理差<script> 加载失败没法捕获(已被 fetch try/catch 替代)
没法传复杂头没法带 Authorization / Content-Type
没法用 async/await只能 callback

结论:新项目不要用 JSONP。如果维护老项目,可以保留,但要严格过滤 callback 参数防注入。

八、Nginx 反向代理(生产最常用) ​

核心原理:浏览器到 nginx 是同源(都被代理到同一个域名),nginx 再去后端是服务端内部通信,不受浏览器同源策略限制。

8.1 完整 nginx.conf 例子 ​

nginx
server {
  listen 80;
  server_name app.com;

  # API 反向代理
  location /api/ {
    # 转发到后端真实地址
    proxy_pass http://backend-server:8080/;
    
    # 保留原始 Host(后端可能要看)
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    
    # 超时
    proxy_connect_timeout 5s;
    proxy_read_timeout 30s;
  }
  
  # 静态资源
  location /static/ {
    alias /var/www/static/;
    expires 30d;
  }
  
  # 预检请求直接返回 204
  location /api/ {
    if ($request_method = 'OPTIONS') {
      add_header Access-Control-Allow-Origin "$http_origin" always;
      add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
      add_header Access-Control-Allow-Headers "Content-Type, Authorization, X-Token" always;
      add_header Access-Control-Allow-Credentials "true" always;
      add_header Access-Control-Max-Age "86400" always;
      add_header Content-Length 0;
      return 204;
    }
  }
}

8.2 为什么这是最佳实践 ​

优势说明
不暴露真实后端用户看到的是 app.com,看不到 api.com
不增加 OPTIONS浏览器认为同源,根本不预检
统一鉴权nginx 层加 token 校验,后端无状态
缓存友好走 app.com 域名,浏览器缓存正常
HTTPS 统一只需要给 app.com 配证书

生产环境 90% 的跨域问题用 Nginx 代理解决。后端不用写一行 CORS 代码。

8.3 反向代理的代价 ​

  • 延迟 +1(多一跳网络)
  • nginx 单点(可加 LVS / Keepalived)
  • 流式响应需要特殊配置(proxy_buffering off)

九、Vite / Webpack DevServer 代理(开发) ​

开发环境经常碰到"前端 localhost:3000 调后端 localhost:8080,跨域"——用 dev server 代理最快。

9.1 Vite proxy 完整配置 ​

ts
// vite.config.ts
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    port: 3000,
    proxy: {
      // 1. 字符串形式
      '/api': 'http://localhost:8080',
      
      // 2. 对象形式(完整控制)
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,   // 把 Host 头改成后端的
        rewrite: (path) => path.replace(/^\/api/, ''),
        // path 是 /api/user → /user
      },
      
      // 3. WebSocket 代理
      '/ws': {
        target: 'ws://localhost:8080',
        ws: true,
      },
      
      // 4. 多个后端
      '/api/v1': {
        target: 'http://user-service:8080',
        changeOrigin: true,
      },
      '/api/v2': {
        target: 'http://order-service:8081',
        changeOrigin: true,
      },
    },
  },
})

9.2 Webpack DevServer 同样思路 ​

js
// webpack.config.js
module.exports = {
  devServer: {
    port: 3000,
    proxy: [
      {
        context: ['/api'],
        target: 'http://localhost:8080',
        changeOrigin: true,
        pathRewrite: { '^/api': '' },
      },
    ],
  },
}

9.3 真实坑:代理后 Cookie 丢失 ​

changeOrigin: true 改 Host 头,但不复制 Cookie。如果后端用 Cookie 鉴权,需要:

ts
'/api': {
  target: 'http://localhost:8080',
  changeOrigin: true,
  cookieDomainRewrite: 'localhost',  // 把后端 cookie 域名改回 localhost
  onProxyRes(proxyRes) {
    // 或者手动改 Set-Cookie
    const cookies = proxyRes.headers['set-cookie']
    if (cookies) {
      proxyRes.headers['set-cookie'] = cookies.map(c =>
        c.replace(/Domain=[^;]+/i, 'Domain=localhost')
      )
    }
  },
}

十、postMessage 跨域(适用于 iframe / Window) ​

父子页面跨域,或同页面用 window.open 打开子窗口时,postMessage 是唯一安全的跨域通信方式。

10.1 父页 → 子 iframe ​

js
// 父页:https://app.com
const iframe = document.getElementById('pay-iframe')
iframe.contentWindow.postMessage(
  { type: 'pay', orderId: '123', amount: 100 },
  'https://pay.partner.com'  // targetOrigin,必须明确写,不能写 *
)

// 子页(支付):https://pay.partner.com
window.addEventListener('message', (e) => {
  // 1. 必检 origin(防恶意源伪造消息)
  if (e.origin !== 'https://app.com') return
  // 2. 校验 source(防 source 伪造)
  if (e.source !== window.parent) return
  // 3. 处理数据
  if (e.data.type === 'pay') {
    handlePay(e.data.orderId, e.data.amount)
  }
})

10.2 子页 → 父页(回传支付结果) ​

js
// 子页(支付)
window.parent.postMessage(
  { type: 'pay-result', success: true, orderId: '123' },
  'https://app.com'  // 同样要明确 origin
)

// 父页
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://pay.partner.com') return
  if (e.data.type === 'pay-result') {
    if (e.data.success) {
      showSuccess()
    } else {
      showError()
    }
  }
})

10.3 安全三件套(必做) ​

  1. targetOrigin 永远明确写——不能 *、不能省略
  2. 接收方必检 e.origin——不校验就是 XSS 入口
  3. 消息内容做白名单校验——不直接 eval、不直接 JSON.parse 后当代码跑

十一、WebSocket 跨域 ​

WebSocket 不受同源策略限制——浏览器不拦截 WS 连接。

11.1 客户端 ​

js
// 任何源都可以连接
const ws = new WebSocket('wss://api.example.com/socket')
ws.onopen = () => ws.send('hello')
ws.onmessage = (e) => console.log(e.data)

11.2 服务端必须校验 Origin ​

js
const WebSocket = require('ws')
const wss = new WebSocket.Server({ port: 8080 })

wss.on('connection', (ws, req) => {
  // 必检 Origin,防 CSRF(恶意页连接你的 WS)
  const origin = req.headers.origin
  const allow = ['https://app.com', 'https://admin.com']
  if (!allow.includes(origin)) {
    ws.close(1008, 'Origin not allowed')
    return
  }
  
  ws.on('message', (data) => {
    console.log('收到:', data)
  })
})

踩坑经验:很多人误以为 WS 跨域"安全",不校验 Origin——结果被恶意页面从任意域建立连接、消耗资源。Origin 校验不是 CORS,是防滥用。

十三、CORS 实战坑 ​

13.1 * + credentials 必死 ​

http
# ❌ 错
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true

浏览器直接拒绝,不解释。凭证模式下必须明确 origin:

http
# ✅ 对
Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Credentials: true
Vary: Origin

13.2 缺 Vary: Origin 导致 CDN 串 ​

服务端按 Origin 反射,但 nginx/CDN 没加 Vary: Origin:

  • 请求 1:Origin: https://a.com → 响应 Allow-Origin: https://a.com → CDN 缓存
  • 请求 2:Origin: https://b.com → CDN 返回 Allow-Origin: https://a.com → 浏览器拒

修复:响应里加 Vary: Origin,告诉 CDN 按 Origin 头分别缓存。

13.3 预检不带 Cookie ​

OPTIONS 预检不带 Cookie(浏览器限制)。所以预检阶段不能读 session——只能放行公共接口或用其他方式鉴权(API key)。

13.4 反向代理丢失 Authorization ​

nginx 默认会丢弃某些带下划线的自定义头(如 X_Token)。修复:

nginx
# 启用下划线头
underscores_in_headers on;

# 或者用连字符命名(推荐)
proxy_set_header X-Token $http_x_token;

13.5 跨域请求服务端没收到 Cookie ​

  • Cookie 设了 SameSite=Strict(默认就阻止跨域)
  • Cookie 没设 Domain=.example.com(子域不共享)

十四、真实项目经验 ​

14.1 子域之间共享登录态 ​

场景:商户后台 merchant.example.com,运营后台 admin.example.com,API 在 api.example.com。子域间要共享登录 Cookie。

踩坑:Cookie 默认只发给完全相同子域。merchant.example.com 拿不到 admin.example.com 的 Cookie,导致 API 一直 401。

修复:

http
# API 设置 Cookie 时
Set-Cookie: token=xxx; 
  Domain=.example.com;       ← 关键!加 . 让所有子域共享
  Path=/; 
  Secure; 
  SameSite=Lax; 
  HttpOnly

注意:

  • Domain=.example.com 前面的 . 在现代浏览器可省略
  • SameSite=Lax 允许顶级导航带 Cookie
  • HttpOnly 防 XSS 偷 token
  • Secure 强制 HTTPS

14.2 第三方支付 iframe 通信 ​

场景:商户后台嵌入第三方支付 iframe,父页要通知 iframe"开始支付",iframe 完成后通知父页"支付成功"。

实现:

js
// 父页发起支付
payIframe.contentWindow.postMessage({
  type: 'pay',
  orderId: 'O123',
  amount: 9999,
}, 'https://pay.partner.com')

// 父页接收结果
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://pay.partner.com') return
  if (e.data.type === 'pay-success') {
    showSuccessModal(e.data.orderId)
  } else if (e.data.type === 'pay-fail') {
    showErrorModal(e.data.reason)
  }
})

踩坑:早期没校验 e.origin,结果有恶意页通过 window.opener.postMessage 伪造消息触发支付成功弹窗——后来严格校验 origin 才解决。

14.3 跨域 API 调试的小技巧 ​

bash
# 用 curl 直接打 API,模拟跨域
curl -H "Origin: https://app.com" \
     -H "Access-Control-Request-Method: POST" \

# 看响应头是否有正确的 CORS 头

十五、面试回答模板 ​

30 秒版 ​

同源策略限制浏览器跨域访问(协议+域名+端口),三种方案:1) 后端开 CORS 响应头;2) Nginx 反向代理让浏览器认为同源;3) 跨域用 postMessage(WebSocket 不受同源限制)。生产环境 90% 用 Nginx 代理,因为不增加 OPTIONS 请求、Cookie 通行、缓存友好。

90 秒版 ​

同源策略是浏览器为安全做的限制,只看 URL 的协议、域名、端口。跨域有三种主流方案:CORS 是后端返回 Access-Control-Allow-Origin 头,简单请求直接放行,非简单请求先发 OPTIONS 预检;Nginx 反向代理让浏览器到 nginx 是同源,nginx 再去后端是服务端通信不受限,生产环境 90% 用这个;postMessage 适用跨域 iframe 通信,必须校验 e.origin 防伪造。

几个实战坑:Access-Control-Allow-Origin: * 配 credentials: true 浏览器拒;Vary: Origin 漏配会让 CDN 缓存串;OPTIONS 预检不带 Cookie 没法鉴权;SameSite=Strict Cookie 默认就阻止跨域。

常见追问 ​

  • Q: 预检请求能被缓存吗? A: 能,通过 Access-Control-Max-Age。但 Chrome 强制 5 秒上限,Firefox 类似。
  • Q: 凭证请求一定要明确 origin,为什么? A: * 等于"任何域都能带 Cookie 访问",等于没鉴权,浏览器拒绝。
  • Q: WS 不受同源限制,服务端还要校验 Origin 吗? A: 要!WS 不受浏览器拦截,但服务端要主动防滥用。
  • Q: 浏览器发跨域请求时,服务端能看到 Cookie 吗? A: 默认看不到。要看到需客户端 credentials: 'include' + 服务端 Allow-Credentials: true + 明确 origin。
