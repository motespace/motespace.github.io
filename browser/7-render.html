浏览器渲染流程深度解析:从像素到 GPU ​

一、为什么面试官 100% 会问渲染流程 ​

在所有浏览器面试题里,渲染流程是出现频率最高的一类——大厂一面、二面、三面几乎必问。它不是单纯的"八股文",而是所有前端性能优化的理论根基:

  • 页面卡顿 → 渲染链路哪一步耗时过长
  • 首屏白屏 → HTML/CSS/JS 谁阻塞了渲染
  • 动画掉帧 → 用了 left/top 还是 transform,触发 layout 还是 composite
  • 滚动卡顿 → 是否在滚动事件里读写 DOM
  • 内存泄漏 → 是否创建了过多 will-change 合成层
  • 响应延迟 → 主线程被长任务阻塞,合成线程无能为力

可以说,不懂渲染流程,就不会做性能优化;不会性能优化,架构选型、组件设计、技术调研都会走弯路。

它也是排查"页面奇怪问题"的入口——比如:

  • "为什么我的 div 设置了样式不显示?" → CSSOM 没构建完,选择器写错
  • "为什么动画看起来一抽一抽的?" → 每一帧都触发 layout,主线程满载
  • "为什么滚动到某个位置会卡一下?" → scroll 监听里读了 offsetHeight
  • "为什么 GPU 占用飙高?" → will-change 用得太多,合成层撑爆显存

本文是这个系列最"重"的章节——把渲染的每个阶段拆开讲透。它和 1-architecture、9-threads、performance/1-browser-rendering 形成纵深:

  • 1-architecture 讲浏览器整体进程/线程
  • 9-threads 讲主线程的异步模型
  • performance/1-browser-rendering 讲性能侧总览
  • 本文讲渲染流水线每个阶段的内部机制

二、关键路径全景图 ​

浏览器把 HTML/CSS/JS 变成屏幕像素,要走完一条非常长的流水线。这条流水线不是一根直线,而是多个线程协作的结果。

关键点:

  • 主线程负责 JS、DOM 构建、CSSOM 构建、Layout、Paint——最繁忙,任何长任务都会卡住它
  • 合成线程独立于主线程,所以滚动、transform 动画即使主线程阻塞也流畅
  • 光栅线程把矢量绘制变成位图,多个并行提高效率
  • GPU 进程最终把位图合成推给显卡

每帧预算:60fps = 16.67ms,主线程的工作要在这个时间内完成,否则掉帧。

2.1 每个阶段在哪条线程 ​

阶段线程备注

CSS -> CSSOM主线程不阻塞 DOM
Render Tree主线程不显示的节点不进
Layout主线程计算几何
Paint主线程绘制像素
分层合成线程找独立的合成层
光栅化光栅线程(并行)矢量转位图
合成最终帧合成线程把图层合并
推给 GPUGPU 进程最终输出

2.2 实战经验 ​

  • 主线程是最贵的资源:任何把 JS/布局/绘制压在主线程的事都要警惕
  • 合成线程是免费的(transform 动画):能不打扰主线程就别打扰
  • GPU 上传有成本:每次新合成层上传,第一次贵、之后便宜

三、DOM 构建深度 ​

DOM(Document Object Model)是渲染流水线的入口。它的构建过程不是简单的"读字符串",而是分阶段:

HTML 字节流
    v UTF-8 / GBK 解码
   字符串
    v Tokenizer(分词器)
   Token 流(StartTag/EndTag/Char/Comment/Doctype)
    v Tree Builder(树构造器)
   DOM 节点
    v 挂到 DOM 树上
   Document 树

**Tokenizer(分词器)**逐字符扫描 HTML 字节流,识别出开始标签、结束标签、属性、文本、注释等 Token。

Tree Builder根据 HTML 规范(https://html.spec.whatwg.org/multipage/parsing.html)的状态机算法,把 Token 变成 DOM 节点,并挂到树上。状态机很精巧:遇到 <p> 里又 <p> 会自动闭合前面的 <p>(自动纠错)、<table> 里遇到 <tr> 会自动补 <tbody>、<select> 里遇到 <option> 等等——这些"宽容"的规则让前端写错 HTML 也不会乱掉。

3.1 关键阻塞点 ​

html
<!-- 阻塞 HTML 解析 -->
<script src="app.js"></script>

<!-- 不阻塞解析,HTML 解析完再执行 -->
<script defer src="app.js"></script>

<!-- 不阻塞解析,下载完立即执行(顺序不保证) -->
<script async src="app.js"></script>

为什么 <script> 会阻塞 HTML 解析?

因为 JS 可能会调用 document.write() 改写 DOM,或者读取 document.querySelector()。如果不等 JS 执行完就继续解析 HTML,JS 看到的 DOM 是不一致的(规范约定的)。

为了保证脚本执行时的 DOM 是"当前的",浏览器选择最稳妥的方案:遇到 <script> 就停。

async 和 defer 的区别:

  • async:下载完立刻执行,可能 HTML 还没解析完——适合独立脚本(GA、广告)
  • defer:HTML 解析完、DOMContentLoaded 之前按序执行——适合有依赖的主脚本

3.2 其他资源 ​

html
<!-- 不阻塞解析,但阻塞渲染(下面会讲) -->
<link rel="stylesheet" href="style.css">

<!-- 不阻塞解析,异步解码 -->
<img src="..." alt="...">

<!-- 不阻塞解析,异步加载 -->
<iframe src="..."></iframe>

<link>(CSS)虽然不阻塞 HTML 解析,但阻塞渲染——必须等 CSSOM 构建完才能 Render Tree。下一节细讲。

<img> 和 <iframe> 浏览器异步下载和解码,不阻塞 HTML 解析,只阻塞渲染前的尺寸计算(因为 layout 需要知道图片的固有尺寸)。

3.3 实战经验 ​

  • 首屏 HTML 越小越好:HTML 解析是串行的,内容多 = 解析时间长 = 阻塞渲染
  • 关键 JS 用 defer:不阻塞解析,顺序保证
  • 第三方脚本用 async:GA、广告 SDK,不影响主流程
  • 慎用 document.write:会清空整个文档,等于从头解析——老的统计脚本偶尔这么干,会导致页面白屏

四、CSSOM 构建 ​

CSSOM(CSS Object Model)是 DOM 树对应的样式树。和 DOM 不同,CSSOM 只关心样式——每个节点带有 computedStyle。

4.1 解析过程 ​

CSS 解析器(在 Blink 里叫 CSSParser)在主线程跑:

CSS 字节流
    v UTF-8 解码
   字符串
    v Tokenizer
   CSS Tokens(选择器、属性、值)
    v Parser
   CSSRule(规则节点)
    v 关联到 CSSOM 树
   StyleSheetList -> CSSStyleSheet -> CSSRuleList

CSS 选择器的匹配是从右到左的——浏览器先找 div,再过滤 class="item" 的,再保留父辈是 .node 的。这是为了尽早"拒绝"无关节点。

4.2 CSS 阻塞渲染,不阻塞 DOM 解析 ​

这是非常重要的特性:

html
<head>
  <!-- CSS 在这里,不阻塞 HTML 解析,但阻塞渲染 -->
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <!-- DOM 继续解析 -->
  <div>...</div>
  <!-- 直到 CSSOM 完成才开始 Render Tree -->
</body>

为什么不阻塞 DOM 解析?

DOM 解析只关心 HTML 结构,不关心样式。CSS 在 head 里下载时,浏览器并行解析 HTML body,等 CSS 下载完 + CSSOM 构建完 + body 已构建完,才能合并成 Render Tree。

为什么阻塞渲染?

没有 CSSOM 就不知道每节点的样式,Render Tree 就没法构建,只能等。

4.3 优化 CSS 阻塞 ​

优化加载顺序:内联关键 CSS

html
<head>
  <style>
    /* 关键 CSS(首屏用到的) */
    body { margin: 0; font: 14px sans-serif }
    .header { background: #333; color: #fff }
    /* ... */
  </style>
  <!-- 非关键 CSS 异步加载 -->
  <link rel="preload" href="non-critical.css" as="style"
        onload="this.onload=null;this.rel='stylesheet'">
</head>

预加载关键 CSS:

html
<link rel="preload" href="critical.css" as="style">

<link rel="preload" as="style"> 提前发起请求,且不阻塞渲染。一旦需要,通过 rel='stylesheet' 切换即可。

4.4 实战经验 ​

  • 首屏关键 CSS 内联:避免请求 RTT,首屏最快
  • CSS 压缩:gzip / brotli,白名单数据可减 60-70%
  • CSS 用 class 不用复杂选择器:解析更快(避免后代/兄弟选择器)
  • CSS-in-JS 慎用:运行时生成 CSS,会延后 CSSOM 构建——SSR 是必须的

五、Render Tree 构建 ​

Render Tree 是DOM + CSSOM 的并集,只包含可见节点。

5.1 哪些节点不进 Render Tree ​

html
<!-- 不进 Render Tree -->
<head>
  <meta> <title> <script> <style> <!-- 这些不显示 -->
</head>

<div style="display: none">不显示</div>

<!-- 进 Render Tree -->
<div style="visibility: hidden">不可见但占位</div>

为什么 display: none 不进?

display: none 的元素既不显示也不占位,自然没有几何信息可以算。visibility: hidden 占位但不显示,需要算几何信息。

5.2 渲染树 vs DOM 树 ​

DOM 树                 CSSOM 树
  |                       |
  +------ 并集 -----------+
                    v
              Render Tree
              |-- div.display-none  <- 不在
              |-- div.visibility-hidden  <- 在(占位)
              +-- div  <- 在

Render Tree 是 RenderObject 树(Blink 里的实现),不是 DOM 节点,但一一映射到 DOM。

5.3 实战经验 ​

  • display: none 和 visibility: hidden 选择:不影响布局的隐藏用 visibility(不会触发布局);不需要占位的用 display: none(节省渲染资源)
  • 伪元素 ::before / ::after 进 Render Tree:虽然是 CSS 生成的,但有几何信息
  • <input type="hidden"> 不进 Render Tree:它是表单数据,不渲染

六、Layout(回流/重排) ​

Layout 是计算每个 RenderObject 几何信息的过程——位置(x, y)、尺寸(width、height)、margin、padding、border。

6.1 Layout 算法 ​

Render Tree
    v
   脏标记(谁变了)
    v
  递归布局
    |-- 从布局树根节点开始
    |-- 自上而下计算位置
    +-- 自下而上返回尺寸
    v
  布局树(Box Layout)
    |-- 每个节点的 box 模型
    +-- 缓存(无脏标记可复用)

浏览器有 Layout 缓存——没有 dirty 标记的子树可以复用上次的布局结果。这是为什么"批量修改 DOM 只触发一次 layout"。

6.2 触发 Layout 的操作 ​

触发操作说明
增删 DOMappendChild / removeChild / replaceChild
元素尺寸width / height / padding / border
元素位置top / left / margin
内容变化innerText / textContent / value
字体变化font-size / font-family
浏览器窗口resize 事件
读取布局信息offsetWidth / clientHeight / getComputedStyle
滚动scrollTop / scrollLeft(可能触发)

特别强调"读":读 offsetWidth 不是单纯的查询,是强制让浏览器把脏布局清掉——浏览器必须给你准确的几何信息,所以必须 layout。

6.3 Layout 一定触发 Paint ​

因为 Layout 之后像素变了——一次 Paint 必然发生。

6.5 增量布局 vs 全局布局 ​

现代浏览器对 Layout 做了优化,不是每次都重新布局整个页面——它有脏位(Dirty Bit) 机制:

全局 Layout: 某个节点 dirty
    v
从 dirty 节点向上找最近的有 dirty 祖先(Ancestor Chain)
    v
从那个祖先节点开始重新 layout(只重算子树)
    v
子树 layout 完成后,父节点收集尺寸信息
    v
继续向上,直到根节点(但只算"脏部分")

实战意义:

  • 改 <body> 子元素的 width → 只 layout 这个子树,不重排整个页面
  • 改 <body> 的 width → 整个 body 链 layout,但 body 内已经 layout 过的子树可能复用缓存
  • 读 <body> offsetHeight → 强制把整条脏链 layout 到根
  • flex / grid 容器的子项 layout 较复杂,子树更大

6.6 不同的 Layout 算法 ​

元素Layout 算法复杂度
display: blockBlock LayoutO(n)
display: inlineInline LayoutO(n) 简单
display: flexFlex LayoutO(n) 中等
display: gridGrid LayoutO(n²)
display: tableTable LayoutO(n) 复杂
position: absolute / fixed不参与普通 layout局部
float触发 BFC影响兄弟

性能影响:

  • Grid 和 Table 是最贵的——多级嵌套时谨慎
  • position: absolute / fixed 元素不参与普通 layout,只算自己的尺寸——更快
  • float 会强制 BFC + 清浮动,影响兄弟节点 layout

6.4 实战经验 ​

  • 动画首次写入 比每次写入好
  • 读 <body> offsetWidth 会 layout 整个页面(从根节点递归下来)
  • iframe 内 layout 不影响主页面(独立渲染进程)
  • 隐藏的 <body> 显示后整体 layout 一次(display: none -> block)

七、Paint(重绘) ​

Paint 是把 Layout 的结果画到屏幕像素上。绘制顺序是:

1. 背景色(background-color)
2. 背景图(background-image)
3. 边框(border)
4. 子节点(children)
5. 轮廓(outline)

7.1 触发 Paint 的操作 ​

CSS 属性触发
color / backgroundRepaint
box-shadow / border-radiusRepaint
visibility: visible <-> hiddenRepaint(visibility 不影响 layout)
outlineRepaint

7.2 Paint 不一定触发 Layout ​

Layout -> Paint       必然
Color change -> Paint  不触发 Layout

颜色、背景改变不改变几何信息,所以不需要重新 Layout。

7.3 实战经验 ​

  • 阴影和圆角代价高:每个像素都要重画,大范围阴影 = 性能灾难
  • will-change: opacity 提前提示浏览器 Paint
  • <canvas> 绘制复杂:每帧重绘整个 canvas,GPU 友好但 canvas 内容很多时仍慢

八、Composite(合成) ​

Composite 是浏览器渲染流程的最后一步——把多个图层合成最终画面,推给 GPU 显示。

8.1 合成层(GraphicsLayer)概念 ​

合成层是浏览器为提升渲染性能而做的分层优化——把页面分成多个独立图层,每个图层独立绘制、独立变换、独立上传 GPU。

            DOM + CSSOM
                |
                v
           Render Tree
                |
                v
             Layout(全局)
                |
                v
             Paint(全局)
                |
                v
   +------------------------------------------+
   |          合成线程分层(Layers)            |
   |                                          |
   |   +--------------------------------+     |
   |   |   GraphicsLayer 1:根层         |     |
   |   |   (整个文档)                  |     |
   |   +--------------------------------+     |
   |   |   GraphicsLayer 2:导航栏       |     | <- position: fixed 提升
   |   +--------------------------------+     |
   |   |   GraphicsLayer 3:动画元素     |     | <- transform 提升
   |   |   transform: translateZ(0)    |     |
   |   +--------------------------------+     |
   |   |   GraphicsLayer 4:视频         |     | <- <video> 自动提升
   |   +--------------------------------+     |
   |                                          |
   |   每层独立上传 GPU,独立变换             |
   +------------------------------------------+
                |
                v
          合成(Composite)
                |
                v
           GPU -> 屏幕

为什么分层?

如果 transform 一个元素,该元素单独成层,只需上传一次到 GPU;之后变化只更新这一层,其他层完全不动——这是 transform 性能好的根本原因。

8.2 提升为合成层的属性 ​

触发条件说明
transform: translateZ(0) / translate3d经典 GPU 加速 hack
transform: scale() / skew() / rotate()任何 transform 值(非 none)
will-change: transform提前声明
opacity < 1半透明元素独立层
position: fixed固定定位元素
<video> / <canvas> / <iframe>媒体元素
filter 非 none滤镜

8.3 为什么 transform 性能好 ​

left/top 动画:
  改变几何 -> Layout -> Paint -> Composite
  每帧都要 layout + paint,主线程满载

transform 动画:
  改变层变换 -> 仅 Composite
  GPU 直接做,主线程 0 工作

核心:transform 不影响其他元素的几何,只影响自己的"合成变换"——其他层完全不动,GPU 直接渲染。60fps 稳如老狗。

8.5 主线程到合成线程的 Commit 时序 ​

主线程完成 Layout + Paint 后,通过 IPC 把"层信息"推给合成线程。这个过程是异步的:

主线程                              合成线程                              光栅线程(4 个并行)
   |                                  |                                       |
   | Layout + Paint 完成               |                                       |
   |                                  |                                       |
   |--- Layer Commit(IPC) -----------> |  推层信息                              |
   |    | - 每个层的几何                |                                       |
   |    | - 每个层的绘制指令           |                                       |
   |    | - 层的位变换                |                                       |
   |                                  |                                       |
   |                                  | 分层(已有缓存则跳过)                 |
   |                                  |                                       |
   |                                  |--- 派发栅格化任务 -------------------> |
   |                                  |                                       | 栅格化
   |                                  |                                       | (矢量转位图)
   |                                  |                                       |
   |                                  |<-- 栅格化结果(IPC) ----------------- |
   |                                  |                                       |
   |                                  | 合成最终帧                            |
   |                                  |                                       |
   |                                  v                                       |
   |                              GPU 进程                                    |
   |                              显示到屏幕                                 |
   v                                                                          |
继续处理下一帧的 JS                                                            |

关键点:

  • 提交(Commit)是异步的:主线程推完数据后不等合成线程完成,继续下一帧
  • 分层结果可缓存:如果层结构没变,合成线程直接复用上次的栅格化结果
  • transform 动画不重新分层:层结构稳定,合成线程独立处理层位移——主线程 0 工作

8.4 实战经验 ​

  • 动画元素必加 transform:这是底线
  • position: fixed 元素自动提升:但慎用为层过多
  • <video> / <iframe> 独立层:这意味着它们有自己的渲染上下文,内部 layout 不影响主页面

九、强制同步布局(Layout Thrashing) ​

Layout Thrashing 是最常见的性能反模式——JS 读写 DOM 交替,导致每次读都触发 layout。

9.1 反例代码 ​

js
// 经典反例:读写交替
function layoutThrashExample() {
  for (let i = 0; i < 100; i++) {
    const height = element.offsetHeight      // 读:触发 layout
    element.style.height = (height + 1) + 'px'  // 写:标记 dirty
    // 下次循环又读 offsetHeight,又是 layout
  }
}
// 100 次循环 = 100 次 layout,主线程满载

9.2 为什么读 offsetWidth 触发 layout ​

浏览器有布局缓存机制——脏标记的节点才需要重算。但是读操作需要准确数据,所以必须把脏标记清掉,这次必须 layout。

写 style.width = '100px'  -> 标记 dirty(不立即 layout)
读 offsetWidth             -> 强制 layout(给准确数据)
写 style.height = '200px'  -> 标记 dirty
读 offsetHeight            -> 又强制 layout

每次读都触发 layout——100 次循环 = 100 次 layout。

9.3 正确写法:批量读写 ​

js
// 正确:分离读写
function layoutGoodExample() {
  // 先读:一次性 layout(布局缓存复用)
  const height = element.offsetHeight
  // 再写:标记 dirty(下次布局时统一算)
  for (let i = 0; i < 100; i++) {
    element.style.height = (height + i + 1) + 'px'
  }
}
// 100 次循环 = 1 次 layout

为什么对? 浏览器会把多次 style 写入合并为一次 layout。

9.4 时间线示意: ​

   反例:读写交替
   时间 ---------------------------------> v
   v=0ms    读 offsetWidth   --> layout(同步等待)
   v=0.1ms  写 style.width   --> 标记 dirty
   v=0.2ms  读 offsetWidth   --> layout(同步等待) <- 同步等待
   v=0.5ms  写 style.height  --> 标记 dirty
   v=0.6ms  读 offsetHeight  --> layout(同步等待)
   ...
   v=100ms  共 100 次 layout,主线程满载

   正确:读写分离
   时间 ---------------------------------> v
   v=0ms    读 offsetWidth   --> 1 次 layout
   v=0.1ms  写 style.width   --> 标记 dirty(不立即 layout)
   v=0.2ms  写 style.height  --> 标记 dirty(不立即 layout)
   ...
   v=10ms   100 次写 + 1 次 layout

9.5 Vue/React 为何用虚拟 DOM ​

虚拟 DOM 的核心价值之一就是批量更新——把所有写操作合并,最后一次性 layout + paint:

js
// 每次 setState 都触发 layout
function App() {
  const [a, setA] = useState(0)
  const [b, setB] = useState(0)
  return (
    <div>
      <span>{a}</span>
      <span>{b}</span>
    </div>
  )
}
setA(1)                  // 触发 layout
setB(2)                  // 又触发 layout

虚拟 DOM 会把多次 setState 合并为一次 commit,只触发一次 layout。

9.6 实战经验 ​

  • 不要在 scroll / resize 监听里读 offsetWidth —— 这是最高频的踩坑
  • 动画中不要读 DOM:rAF 回调里读 offsetHeight,每帧 layout
  • 用 fastdom 库:Facebook 的 fastdom 帮你做读写分离

十、避免回流的实战技巧 ​

回流(layout)是最贵的操作——必须优化。

10.1 必触发 vs 可避免 vs 不触发 ​

操作触发回流性能
改变 width/height必触发差
改变 margin/padding必触发差
改变 left/top必触发差
innerHTML必触发差
class 切换(改变样式)必触发中
transform 改变不触发好
opacity 改变不触发好
visibility: hidden不触发 layout好
display: none触发 layout差(但隐藏元素不算渲染)

10.2 减少回流的具体方法 ​

1. 合并多次 DOM 操作为一次

js
// 多次回流
for (let i = 0; i < 100; i++) {
  const div = document.createElement('div')
  div.textContent = i
  container.appendChild(div)  // 每次 append 都回流
}

// 一次性回流
const fragment = document.createDocumentFragment()
for (let i = 0; i < 100; i++) {
  const div = document.createElement('div')
  div.textContent = i
  fragment.appendChild(div)
}
container.appendChild(fragment)  // 仅 1 次回流

2. 离线 DOM 操作

js
// 显示中操作,每次都回流
container.style.display = 'block'
container.style.width = '100px'   // 回流 1
container.style.height = '200px' // 回流 2

// 隐藏后操作,只回流 1 次
container.style.display = 'none'  // 隐藏(无回流)
container.style.width = '100px'   // 不回流(不渲染)
container.style.height = '200px'  // 不回流
container.style.display = 'block' // 恢复(回流 1 次)

3. 脱离文档流

css
.position-absolute {
  position: absolute;  /* 脱离文档流 */
}

.position-fixed {
  position: fixed;  /* 脱离文档流 */
}

position: absolute / fixed 元素不影响其他元素布局——它们的变化不会让兄弟/父子 layout。

4. CSS contain 属性

css
.card {
  contain: layout;   /* 子节点 layout 不影响外部 */
}

.widget {
  contain: paint;   /* 子节点 paint 不超出范围 */
}

.heavy-component {
  contain: strict;   /* layout + paint + size */
}

contain 告诉浏览器:我的内部变化不会影响外部。浏览器可以只 layout 我这个子树,不需要递归到根。

10.3 实战经验 ​

  • 大列表用虚拟滚动:只渲染可见区域的 DOM,减少回流节点数
  • CSS 动画用 transform:天然不回流
  • flex 比 float 性能更好:float layout 算法更复杂
  • 表格 layout 慎用:table-layout 切换很贵

十一、GPU 加速与陷阱 ​

GPU 加速 = 合成层 + GPU 进程渲染。但用错了反而拖慢。

11.1 will-change 的正确用法 ​

css
/* 错误:滥用 will-change */
* {
  will-change: transform;  /* 所有元素独立层,内存爆炸 */
}

/* 正确:动画前加,结束移除 */
.animated {
  /* 默认状态 */
}

.animated.is-animating {
  will-change: transform;  /* 动画时加 */
}

/* 动画结束后移除 class,will-change 也清掉 */

为什么不能滥加?

每个 will-change = 一个合成层 = 独立 GPU 内存。1000 个元素 = 1000 个图层,内存吃光,GPU 上传时间爆炸。

保留期:

js
// 正确:动画结束后清除
element.classList.add('is-animating')  // 添加 will-change
element.addEventListener('animationend', () => {
  element.classList.remove('is-animating')  // 移除 will-change
})

11.2 3D transform 创建合成层 ​

css
/* 经典 hack */
.gpu {
  transform: translateZ(0);   /* 或 translate3d(0,0,0) */
}

/* 现代写法 */
.gpu {
  will-change: transform;
}

translateZ(0) 强制创建合成层——但要慎用,只给真正需要的元素。

11.3 太多合成层反而更慢 ​

问题:页面 1000 个元素,每个都 translateZ(0)。

1000 个合成层
每个上传 GPU 占内存
+ 浏览器要管理 1000 层的合成顺序
+ 滚动时重新计算每层的可见性
= 内存爆炸 + GPU 满载 + 滚动卡顿

经验值:超过几十个合成层就要警惕,超过几百个几乎肯定卡。

11.4 常见陷阱 ​

11.5 Paint Holding(绘制保持) ​

Paint Holding:Chrome 76+ 引入的优化——同一 URL 二次访问时,保留上次的 Paint 结果直到新的内容渲染完成。

用户从 A 页面点回 B 页面
    v
Chrome 立刻显示 B 上次的画面(保留,不重绘)
    v
后台重新加载 B 的内容
    v
新内容就绪后,一次性替换画面
    v
用户无感知切换(回退/前进几乎瞬间)

实战经验:

  • 路由切换瞬间看到旧内容 → Paint Holding 在工作,这是正常的
  • 如果新内容加载很快,用户几乎看不出切换
  • 在 Performance 面板里可以看到:前 100ms 是旧画面(缓存),之后才是新画面
  • 用 BFCache(Back/Forward Cache)可以更进一步:页面直接不重新加载
陷阱说明
* { will-change: transform }全局滥用,千万不要
will-change 不清除元素销毁前应 will-change: auto
用 top/left 动画改用 transform
大面积 box-shadow改用 filter: drop-shadow(GPU 友好)
<canvas> 2d context改用 WebGL

十三、真实项目经验 ​

13.1 IoT 大屏:从 10 FPS 到 55 FPS ​

背景:物联网数据大屏,10000 个数据点实时更新(传感器读数)。

错误实现:

js
function updateDashboard(dataPoints) {
  dataPoints.forEach((point, i) => {
    const dot = document.getElementById(`dot-${i}`)
    dot.style.left = point.x + 'px'   // 触发 layout
    dot.style.top = point.y + 'px'    // 又触发 layout
  })
}
// 10000 次 layout,10 FPS(主线程满载)

问题:

  • 10000 个 left/top 修改 -> 10000 次回流 -> 主线程爆炸
  • FPS:10 FPS(每秒只能渲染 10 帧)

优化方案:用 transform 替代 left/top

js
function updateDashboardFast(dataPoints) {
  dataPoints.forEach((point, i) => {
    const dot = document.getElementById(`dot-${i}`)
    dot.style.transform = `translate(${point.x}px, ${point.y}px)`  // 仅触发 composite
  })
}
// 10000 次 transform,但 GPU 直接做,不占主线程

进一步优化:减少 DOM 操作

js
function updateDashboardFaster(dataPoints) {
  // 批量写入 GPU 缓存
  requestAnimationFrame(() => {
    dataPoints.forEach((point, i) => {
      const dot = document.getElementById(`dot-${i}`)
      dot.style.transform = `translate(${point.x}px, ${point.y}px)`
    })
  })
}

优化结果:

  • FPS:55 FPS(从 10 FPS 提升到 55 FPS)
  • 主线程空闲时间:之前满载 -> GPU 进程接管后,主线程基本空闲
  • 整体感受:流畅(从卡顿到丝滑)

13.2 会员 H5 商品列表:虚拟列表 + will-change ​

背景:会员 H5 商品列表,1000+ 商品,滚动需要流畅。

错误实现:

html
<!-- 1000 个商品都渲染,DOM 节点爆炸 -->
<div v-for="item in 1000 items">
  <ProductCard :item="item" />
</div>

问题:

  • 1000 个 ProductCard -> 1000 个 DOM 节点 -> 滚动时 layout 整个列表 -> 卡顿

优化方案:虚拟列表 + will-change

Step 1: 虚拟列表(只渲染可见 30 个)

vue
<template>
  <div class="virtual-list" @scroll="onScroll">

        v-for="item in visibleItems"

        :style="{ transform: `translateY(${item.top}px)` }"
      >
        <ProductCard :item="item" />
      </div>
    </div>
  </div>
</template>

Step 2: will-change 提示合成

css
.virtual-list-item {

}

优化结果:

  • DOM 节点:1000 -> 30(97% 减少)
  • 滚动 FPS:45 FPS -> 稳定 60 FPS
  • 滚动响应延迟:从 80ms 降到 16ms

13.4 案例三:移动端 H5 商品详情页 sticky header 抖动 ​

背景:移动端 H5 商品详情页,顶部有 sticky 的"加入购物车"按钮,滚动时要跟随页面滚动。

错误实现:

css

13.5 性能优化黄金法则 ​

经过这些真实项目,总结出三条黄金法则:

法则一:动画必走 transform

css
/* 错误:触发 layout + paint */
transition: top 0.3s, left 0.3s, width 0.3s;

/* 正确:仅 composite */
transition: transform 0.3s, opacity 0.3s;

法则二:大列表 DOM 节点必须 < 100

  • 1000+ 节点列表必用虚拟滚动
  • 或者 pagination 分页加载
  • 或者 windowing 按需渲染

法则三:scroll / resize 监听必加读写分离

js
// 错误:读写交替
window.addEventListener('scroll', () => {
  const h = element.offsetHeight      // 读,触发 layout
  element.style.transform = `translateY(${h}px)`  // 写,标记 dirty
})

// 正确:fastdom 或 rAF 节流
import fastDom from 'fastdom'
window.addEventListener('scroll', () => {
  fastDom.measure(() => {
    // 读操作
    const h = element.offsetHeight
    fastDom.mutate(() => {
      // 写操作
      element.style.transform = `translateY(${h}px)`
    })
  })
})
项目优化前优化后关键改动
IoT 大屏10 FPS55 FPSleft/top -> transform
会员 H545 FPS / 80ms 延迟60 FPS / 16ms 延迟全列表 -> 虚拟列表 + will-change

核心经验:

  • 动画必用 transform——这是底线
  • 大列表必用虚拟滚动——DOM 节点数 < 100 是健康
  • 合成层用前想清楚——不是越多越好

  • 9-threads:合成线程怎么跑(独立于主线程,异步)
  • 本文:合成线程做什么(分层、合成最终帧)

本文与 1-architecture 的关系:

1-architecture 讲渲染进程里有几条线(主线程、合成线程、IO 线程),本文讲主线程内部的工作(DOM/CSSOM/Layout/Paint)。

本文与 performance/1-browser-rendering 的关系:

那篇是性能侧总览(Critical Rendering Path),重点讲优化策略。本文是深度展开(每个阶段的内部机制 + 代码 + DevTools + 实战)。
