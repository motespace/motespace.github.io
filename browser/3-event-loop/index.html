浏览器事件循环:与 JS 引擎的边界、规范与实战

与 9-threads.md 互补:本文聚焦 与 JS 引擎的区别 + HTML 规范层面 ;后者聚焦 线程模型 + 长任务 。

一、为什么浏览器有自己的事件循环规范

Section titled “一、为什么浏览器有自己的事件循环规范”

JS 代码运行在浏览器里,但 管 JS 怎么跑的规范不止一份 :

规范 范围 维护者
ECMA-262 JS 语言本身:语法、类型、执行模型 TC39
HTML 标准 whatwg 浏览器宿主:事件循环、任务调度、渲染 WHATWG
W3C CSS 样式与渲染 W3C
WICG / Web Platform Tests 提案与一致性测试 WICG

事件循环是 宿主环境 的事——所以 Node 有自己的事件循环,浏览器有另一个 ,JavaScript 自己不规定。

1.2 HTML 规范规定完整调度

Section titled “1.2 HTML 规范规定完整调度”

WHATWG 的 HTML Standard - Event loops 才是真正的 浏览器事件循环规范。它明确定义了几个核心概念,详见 whatwg 规范。

规范明确列出:

  • 哪些来源产生 task
  • 哪些来源产生 microtask
  • 何时 渲染 rendering steps
  • rAF 在渲染步骤里跑
  • 何时 yield 让出主线程

这就是为什么 浏览器事件循环比 Node 多一个渲染阶段,而渲染阶段又包含 rAF、布局、绘制。

1.4 为什么 rAF / observer 不在 ECMA 里

Section titled “1.4 为什么 rAF / observer 不在 ECMA 里”

requestAnimationFrame 跟屏幕刷新绑定,跟渲染管线绑定——这跟 JS 语言没关系,所以规范在 HTML 标准里,不在 ECMA-262。

同理:MessageChannel、postMessage、queueMicrotask、MutationObserver、IntersectionObserver 都是宿主 API,规范在 whatwg。

理解这条边界,就知道:

  • JS 引擎 V8、SpiderMonkey、JSC 只负责按 ECMA-262 执行代码
  • 浏览器 WebKit / Blink / Gecko 负责按 whatwg HTML 规范调度代码
  • Node 用 V8 执行代码,但用 libuv 调度——完全独立

二、浏览器事件循环 vs Node 事件循环

Section titled “二、浏览器事件循环 vs Node 事件循环”

2.1 核心差异表

Section titled “2.1 核心差异表”
维度 浏览器 Node.js
规范 HTML Standard whatwg libuv + Node 文档
任务队列 多类型 每个 task source 一个队列 6 个阶段
微任务队列 1 个 1 个 + process.nextTick 独立队列
渲染阶段 有(每帧执行 update the rendering) 没有
rAF 有 没有
调度优先级 隐式 task source + rAF + idle 显式 setImmediate / nextTick / setTimeout
长任务自动让出 不自动 不自动

2.3 process.nextTick 与微任务的区别

Section titled “2.3 process.nextTick 与微任务的区别”

process.nextTick 不是标准微任务,它是 Node 维护的独立队列,优先级比微任务还高——任何阶段切换时、then 注册时都会先清空。

踩坑经验 :

  • 在 Node 里 process.nextTick 可能造成 递归 nextTick 饿死 I/O ——长链 nextTick 会阻塞事件循环
  • 库代码里写 process.nextTick(cb),浏览器里要换成 queueMicrotask(cb) 或 Promise.resolve().then(cb)

三、宏任务与微任务详解

Section titled “三、宏任务与微任务详解”

3.1 浏览器宏任务来源完整列表

Section titled “3.1 浏览器宏任务来源完整列表”

来自 HTML Standard § Tasks:

来源 队列 / 命名 类型
DOM 事件回调 click / input 等 DOM Manipulation task source 宏任务
setTimeout / setInterval Timer task source 宏任务
网络 I/O 完成 fetch / Image Networking task source 宏任务
window.postMessage Posted message task source 宏任务
整个 script 解析执行 Script task source 宏任务
requestAnimationFrame 在 update the rendering 步骤里 特殊时机
历史导航 / popstate Navigation 宏任务
img onerror / onload DOM Manipulation 宏任务

注意:不同 task source 是独立队列 ——这意味着规范要求浏览器 把同 source 的任务批次取完,再换源 。但具体取哪源的下一个是浏览器实现的偏好。

3.2 微任务来源

Section titled “3.2 微任务来源”
来源 类型
Promise.prototype.then / catch / finally 微任务
queueMicrotask(fn) 微任务
await 后面的代码 V8 编译为 Promise 链 微任务
MutationObserver 回调 微任务 规范明确
IntersectionObserver 回调 渲染步骤前
process.nextTick 仅 Node 非标准微任务
V8 内部 GC 通知 特殊情况

3.3 MutationObserver 是微任务吗

Section titled “3.3 MutationObserver 是微任务吗”

是 。HTML 规范第 7.2 节明确指出,DOM 改完后,MutationObserver 的回调不是立即触发 ,而是在当前宏任务完成后、清空微任务队列时被调用 。

利用这个特性,可以做 microtask batching ——多次修改 DOM 一次回调。

3.4 IntersectionObserver 是不是微任务

Section titled “3.4 IntersectionObserver 是不是微任务”

更复杂一些。规范 Intersection Observer §5.1 要求:当 intersection observer state 变化时,会在渲染步骤前 被批处理成一次回调,而不是多次。

3.5 postMessage 是宏任务

Section titled “3.5 postMessage 是宏任务”

window.postMessage 的回调被推入 Posted message task source ,这是一个独立的队列,跟 Timer / Networking 是并行的几个队列。

3.6 MessageChannel

Section titled “3.6 MessageChannel”

MessageChannel 回调来自 Posted message task source,跟 postMessage 等价。为什么需要它 :实现 setTimeout(0) 替代品的最早方案——没有它的话,setTimeout 会有最小 4ms 限制。

4.3 面试题 1:最经典的输出顺序

Section titled “4.3 面试题 1:最经典的输出顺序”

输出:4 1 3 6 8 2 7

逐行解析 :

  • 同步执行:4 → 进入 async1 输出 1 → await async2 进入 输出 3 → await 让出 2 排到微任务 → Promise executor 同步执行 输出 6 → then 注册微任务 7 → 输出 8
  • 同步栈空,清微任务:2 → 7

这里没有 setTimeout,所以没有 宏任务后 环节。

4.3 面试题 1:最经典的输出顺序

Section titled “4.3 面试题 1:最经典的输出顺序”

输出:4 1 3 6 8 2 7

逐行解析 :

步 执行 微任务队列
1 console.log 4 同步 -
2 async1 进入 → log 1 同步 -
3 await async2 调用 → log 3 同步 -
4 async2 返回 Promise,await 让出,把 log 2 注册成微任务 A A: log 2
5 new Promise executor → log 6 同步 A
6 then 注册微任务 B A, B: log 7
7 console.log 8 同步 A, B
8 同步栈空,清空微任务 A
9 继续取下一个 B
10 队列为空 -

这里没有 setTimeout,所以没有 宏任务后 环节。

输出:4 1 3 6 2 5

4.5 面试题 3:多个 then 的顺序

Section titled “4.5 面试题 3:多个 then 的顺序”

输出:A C F B E

常见误区 :then 注册的顺序 ≠ 回调执行顺序。

p1 已经 resolved,但所有 then 都是异步注册到微任务队列 ——不管它注册时 Promise 是什么状态,回调一定 在栈空后异步执行。

所以按注册顺序:B、E。

为什么 D 没输出?它是被 then 返回 的值,不是回调,会被串到 p2 的 fulfillment 里。

4.6 面试题 4:await 嵌套 Promise

Section titled “4.6 面试题 4:await 嵌套 Promise”

输出:s1 b1 a1 s2 a2 b2

要点 :await 一层套一层,先追到底再回头。

4.7 面试题 5:async 函数抛错被外层 catch

Section titled “4.7 面试题 5:async 函数抛错被外层 catch”

输出:1 caught boom

V8 编译 f 时,对 throw 后的代码不注册微任务,而是把 f 的 Promise reject ——g 的 await 走 catch 分支,log 在 catch 微任务里执行。

注意:2 不会输出 ——f 抛错的时候 g 已经在 await 上了,console.log(2) 还没执行。

五、requestAnimationFrame 深入

Section titled “五、requestAnimationFrame 深入”

5.1 本质

Section titled “5.1 本质”

requestAnimationFrame fn 在浏览器中的语义:

  • 回调时机 :下次渲染前 在 layout、paint 之前
  • 频率 :与屏幕刷新率同步 60Hz 显示器 ≈ 16.67ms 一次
  • 后台标签页 :自动暂停
  • 返回值 :一个 handle,可用 cancelAnimationFrame 取消

Section titled “5.2 与 setTimeout fn 16 的对比”

6.3 老代码 setTimeout(fn, 0) 的替代方案

Section titled “6.3 老代码 setTimeout(fn, 0) 的替代方案”

过去拆分长任务都用 setTimeout(fn, 0),但:

  • 嵌套超过 4 层 → HTML5 规范规定最小延迟 ≥ 4ms
  • 仍排在 宏任务 ,不保证优先级
  • 后台标签页退化为 1 秒

现代替换:

老方法 新方法
setTimeout(cb, 0) await scheduler.yield()
requestIdleCallback(cb) scheduler.postTask(cb, { priority: background })
requestAnimationFrame(cb) requestAnimationFrame(cb) 仍合理

7.1 第 1 题:async / await 顺序(出现率最高)

Section titled “7.1 第 1 题:async / await 顺序(出现率最高)”

输出:D A C E F H B G

逐行解析 :

  • D 同步
  • A 进入 async1,同步执行直到 await
  • C await async2 调用,async2 里 console.log C 同步
  • await 让出,B 注册为微任务
  • E 同步
  • F new Promise executor 同步执行
  • then 注册微任务 G
  • H 同步
  • 同步栈空,清微任务:先 B (来自 async1 的 await)、后 G (来自 then)

7.2 第 2 题:setTimeout + Promise + 微任务全部出场

Section titled “7.2 第 2 题:setTimeout + Promise + 微任务全部出场”

输出:1 4 6 5 2 3

解析 :

  • 同步:1、4(在 Promise executor 里)、6
  • 微任务:5(then 回调)
  • 然后取下一个宏任务(setTimeout 回调):2 → 回调里注册新微任务 3 → 微任务 checkpoint → 3

坑 :容易把 3 写到 2 之前——错。setTimeout 回调先 执行,然后才注册微任务 3。

7.3 第 3 题:setTimeout + Promise + rAF 混合

Section titled “7.3 第 3 题:setTimeout + Promise + rAF 混合”

输出:1 6 4 5 2 3

解析 :

  • 同步:1、6
  • 微任务:4(then 注册时 executor 同步 resolve);4 里又注册 → 5
  • 同一帧内取下一个宏任务(setTimeout 回调):2
  • 渲染步骤前,rAF 回调:3

注意:rAF 不一定 比当前帧的 setTimeout(0) 早——规范的执行顺序是:

setTimeout(0) 仍然可能在本帧内执行,如果主线程之前够闲的话。但渲染前一定 rAF 。

7.4 第 4 题:async 抛错被外层 catch

Section titled “7.4 第 4 题:async 抛错被外层 catch”

输出:1 catch in b:boom done

解析 :

  • b() 同步到 await a(),进入 a
  • a 输出 1,抛错 → a 的 Promise reject
  • b 的 await 走 catch 分支,注册微任务 catch in b:boom
  • 同步结束,清微任务:catch in b:boom
  • b 的 Promise resolve → 注册 done 为微任务
  • done 在下一轮微任务 checkpoint 执行

7.5 第 5 题:Promise 链 vs 微任务优先级

Section titled “7.5 第 5 题:Promise 链 vs 微任务优先级”

输出:sync p1 p2

解析 :

  • sync 同步
  • p.then 微任务 1 注册,p1 输出
  • 回调里又注册了一个 p.then (微任务 2)
  • 按规范,微任务 2 要等当前 checkpoint 结束后 ,下个 checkpoint 才执行
  • 所以输出:sync → p1 → p2

总结 :同一 Promise 的链式 then 默认按注册顺序执行 ,但子级回调里注册的微任务,会排在所有同 checkpoint 微任务之后 。

🎯 面试常考

Section titled “🎯 面试常考”

Q1：浏览器事件循环和 Node 有什么不同?

浏览器的宏任务队列更多(setTimeout、setInterval、UI 事件、requestAnimationFrame、postMessage),渲染机会在每轮结束后;Node 有额外的 poll 阶段处理 I/O。

Q2：requestAnimationFrame 和 setTimeout 的区别?

rAF 在渲染前执行,频率跟随屏幕刷新率(60/120Hz),适合动画;setTimeout 最低 4ms 且会在后台被节流。

Q3：微任务和宏任务的执行顺序?

每个宏任务执行完,清空整个微任务队列(包括执行过程中新产生的),然后才进入下一个宏任务和可能的渲染。

📝 小结

Section titled “📝 小结”
  • 浏览器的宏任务队列更多(timer / I/O / UI 事件 / rAF / postMessage),微任务(Promise)在每轮宏任务后清空。
  • 微任务优先级高于宏任务,但同属微任务的按 FIFO。
  • rAF 在渲染前执行,频率跟随刷新率,适合动画;setTimeout 最低 4ms 且后台被节流。
  • 长任务(>50ms)会让页面卡住,解法是拆分或用 scheduler.yield()。
