浏览器线程与异步:深入事件循环 ​

一、为什么需要理解线程模型 ​

JS 是单线程的——但浏览器不是。理解哪些任务在哪跑:

  • JS 同步执行 → 主线程
  • 定时器、网络、文件读取 → 浏览器后台(多线程)
  • DOM 事件 → 主线程(任务队列)
  • Web Worker → 独立线程

踩坑经验:

  • "为什么我的定时器不准时?" → 主线程被长任务阻塞
  • "为什么动画掉帧?" → 同步计算 + 强制同步布局
  • "为什么 setTimeout(fn, 0) 不立即执行?" → 任务队列不是实时消费的

二、主线程的"单线程"到底是什么 ​

"JS 单线程"指的是执行栈只有一条——同一时间只能执行一段 JS 代码。但:

浏览器内:
├── 主线程(JS / 布局 / 绘制)
├── 合成线程(滚动 / transform)
├── IO 线程(网络 / 文件)
├── Web Worker 线程(独立 JS)
├── 定时器线程(计数)
└── GPU 进程(3D 加速)

JS 引擎内(主线程):
└── 单线程执行栈(call stack)

主线程虽然"单",但任务可以并行进行(只是 JS 执行是单线程的)。

三、事件循环详细流程 ​

         主线程                任务队列
         │                        │
   ┌─────▼─────┐                  │
   │ Call Stack │                  │
   │  (执行 JS) │                  │
   └─────┬─────┘                  │
         │ 同步代码                │
         ▼                        │
   ┌─────────────┐                │
   │ 栈空?       │                │
   └─────┬───────┘                │
         │ 是                      │
         ▼                        │
   ┌──────────────────┐          │
   │ 清空微任务队列     │ ← Promise / queueMicrotask
   └─────┬────────────┘          │
         │                        │
         ▼                        │
   ┌──────────────────────┐      │
   │ 取出 1 个宏任务        │ ← setTimeout / I/O
   └─────┬────────────────┘      │
         │                        │
         ▼                        │
   ┌──────────────────────┐      │
   │ 渲染(布局 + 绘制)?    │      │
   └─────┬────────────────┘      │
         │ 是                      │
         ▼                        │
   ┌──────────────────────┐      │
   │ 合成 → GPU 显示       │      │
   └─────┬────────────────┘      │
         │                        │
         └──────── 循环 ──────────┘

关键点:

  • 每帧(16.67ms @ 60fps)一个循环
  • 微任务全部清空才换宏任务
  • 渲染机会视情况(requestAnimationFrame 时一定渲染)

四、宏任务 vs 微任务 ​

4.1 分类 ​

类型来源
宏任务setTimeout / setInterval / setImmediate(Node)/<script>(整体)
微任务Promise.then / catch / finally / queueMicrotask / MutationObserver / process.nextTick(Node)

4.2 优先级 ​

微任务 > 宏任务(在同帧内)

实际执行顺序:

  1. 当前宏任务
  2. 当前宏任务产生的所有微任务
  3. 渲染(可选)
  4. next宏任务
  5. ... 循环

### 4.3 经典面试题

```js
async function async1() {
  console.log('1')
  await async2()
  console.log('2')
}

async function async2() {
  console.log('3')
}

console.log('4')

setTimeout(() => console.log('5'), 0)

async1()

new Promise(resolve => {
  console.log('6')
  resolve()
}).then(() => console.log('7'))

console.log('8')

// 输出:4 1 6 8 3 2 7 5
// 解析:
// 同步:4 1 6 8
// 微任务(栈空后):3(来自 await async2 内的 console.log 先执行)
//   实际 await 后面的 console.log('2') 和 promise.then 的 console.log('7') 都在微任务
// 微任务全部:2 7
// 宏任务:5

五、长任务与调度 ​

5.1 长任务的影响 ​

主线程任务执行时,其他 JS 不能执行,包括事件回调。

js
// ❌ 长任务:1 秒
button.addEventListener('click', () => {
  heavyCalculation()  // 1 秒,期间所有 click 事件丢失
})

// 用户点 5 次,只触发 1 次(其他都丢了)

5.2 拆分长任务 ​

ts
async function processInChunks(items: any[], chunkSize = 50) {
  let index = 0
  while (index < items.length) {
    const chunk = items.slice(index, index + chunkSize)
    chunk.forEach(item => heavyProcess(item))
    index += chunkSize

    // 让出主线程,让浏览器处理事件
    await new Promise(resolve => setTimeout(resolve, 0))
  }
}

或者用 scheduler.yield()(Chrome 129+):

ts
async function processInChunks(items: any[]) {
  for (const item of items) {
    heavyProcess(item)
    await scheduler.yield()  // 让浏览器处理高优先级任务
  }
}

5.3 requestAnimationFrame(下一帧渲染前) ​

ts
function animate() {
  // 更新动画
  element.style.transform = `translateX(${x}px)`
  x += 1
  // 在下一帧前继续
  requestAnimationFrame(animate)
}
requestAnimationFrame(animate)

rAF 同步屏幕刷新率(60fps = 每 16.67ms 一次),适合动画。

5.4 requestIdleCallback(空闲时) ​

ts
requestIdleCallback(() => {
  // 浏览器空闲时执行(不影响交互)
  sendAnalytics()
}, { timeout: 2000 })
// 2 秒后强制执行,即使不空闲

注意:Chrome 弃用了 requestIdleCallback,改用 Scheduler API:

ts
await scheduler.yield()

六、定时器不准确的原因 ​

6.1 setTimeout(fn, 0) 实际是 ~4ms ​

js
const t0 = Date.now()
setTimeout(() => {
  console.log(`实际:${Date.now() - t0}ms`)  // 4ms+,HTML5 规范
}, 0)

HTML5 规定 setTimeout 最小延迟 4ms(嵌套超过 5 层变 1ms)。

6.2 定时器被任务"挤压" ​

js
// 主线程跑了 100ms 长任务
// setTimeout 1000ms 在等,但前一个 100ms 没结束
// 实际触发时间 = 100ms(长任务) + 1000ms = 1100ms

6.3 performance.now() vs Date.now() ​

js
performance.now()  // 精确到微秒,单调递增(不受系统时间影响)
Date.now()         // 毫秒,系统时间(可能被改)

七、Web Worker 独立线程 ​

Web Worker 是真正的并行 JS 执行——有自己的全局对象。

js
// main.js
const worker = new Worker('worker.js')
worker.postMessage({ data: hugeArray })
worker.onmessage = (e) => console.log(e.data)

// worker.js
self.addEventListener('message', (e) => {
  const result = heavyCalculation(e.data)
  self.postMessage(result)
})

Worker 不能访问:

  • DOM / window / document
  • 主线程的全局变量
  • localStorage

Worker 可以访问:

  • self(WorkerGlobalScope)
  • setTimeout / setInterval
  • fetch / XMLHttpRequest
  • IndexedDB
  • WebSocket
  • importScripts(同步加载其他脚本)

详见 /解决方案/1-手写mini-react方案(详见 /解决方案/1-手写mini-react方案) 和 /performance/27-web-worker.md。

八、Service Worker(网络代理 + 后台) ​

Service Worker 是另一种 Worker,常用于 PWA:

js
// sw.js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request)
    })
  )
})

注册:

js
navigator.serviceWorker.register('/sw.js')

特点:

  • 后台运行(页面关闭后仍可执行)
  • 拦截网络请求
  • 实现离线缓存、消息推送
  • 必须在 HTTPS(localhost 除外)

九、SharedWorker(多 Tab 共享) ​

js
// shared-worker.js
const ports = []
self.addEventListener('connect', (e) => {
  const port = e.ports[0]
  ports.push(port)
  port.addEventListener('message', (e) => {
    // 同步给所有连接的 Tab
    ports.forEach(p => p.postMessage(e.data))
  })
})

注意:Chrome 计划弃用 SharedWorker,推荐用 BroadcastChannel + localStorage。

十、实战经验 ​

10.1 INP 优化(Interaction to Next Paint) ​

核心指标:用户交互到下一帧的时间。

ts
// ❌ 事件回调跑长任务
button.addEventListener('click', () => {
  heavyWork()  // 阻塞,INP 高
})

// ✅ 拆分
button.addEventListener('click', async () => {
  // 必须同步的部分
  updateUI()
  // 长任务拆分
  await scheduler.yield()
  heavyWork()
})

10.2 setTimeout 节流的局限 ​

js
// ❌ 滚动监听不节流
window.addEventListener('scroll', () => {
  updatePosition()
})

// ✅ rAF 节流
let ticking = false
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      updatePosition()
      ticking = false
    })
    ticking = true
  }
})

10.3 避免 Layout Thrashing ​

js
// ❌ 循环读写 DOM(读写交替触发 layout)
for (let i = 0; i < 100; i++) {
  const height = element.offsetHeight  // 读
  element.style.height = (height + 1) + 'px'  // 写
  // → 每次循环都 layout
}

// ✅ 先读,再写
const height = element.offsetHeight  // 一次读
for (let i = 0; i < 100; i++) {
  element.style.height = (height + i + 1) + 'px'
}

🎯 面试常考 ​

Q1：浏览器有哪些线程?

每个渲染进程有自己的主线程(JS 执行)、合成线程、IO 线程、GPU 进程、浏览器进程。网络请求和渲染可以并行。

Q2：为什么长任务会卡?

JS 在主线程执行,一个超过 50ms 的任务会让主线程无法响应点击、无法渲染新帧,表现为卡顿。

Q3：怎么解决长任务?

拆分任务(scheduler.yield() / requestIdleCallback)、把计算挪到 Web Worker、减少主线程 JS 总量。

📝 小结 ​

  • 渲染进程有主线程(JS)、合成线程、IO 线程;浏览器进程、GPU 进程独立。
  • 主线程既跑 JS 又跑渲染任务,长任务会同时阻塞交互和出帧。
  • 解法:拆任务、把纯计算挪到 Worker、减少主线程 JS 总量。
  • scheduler.yield() 让出主线程,比 setTimeout(0) 更精确(不保证时序)。
