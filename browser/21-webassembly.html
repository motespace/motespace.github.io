WebAssembly 入门 ​

浏览器里的「原生速度」——把 C / Rust / Go 编译成 WASM,在浏览器里跑。

一、什么时候该用 WASM ​

场景适合度
图像 / 视频 / 音频编解码⭐⭐⭐⭐ 几乎所有生产级实现(Ffmpeg.wasm)都用它
加密 / 哈希 / 签名验签⭐⭐⭐⭐ 需要跨语言一致性和高性能
游戏引擎(Unity / Unreal 导出)⭐⭐⭐⭐
PDF 解析 / 渲染⭐⭐⭐⭐
图像处理(滤镜、缩放)⭐⭐⭐
通用计算(科学计算、线性代数)⭐⭐⭐
普通业务逻辑、DOM 操作❌ 反而更慢(有 JS ↔ WASM 边界开销)

关键判断:WASM 替代的是计算密集的纯计算,不是所有 JS。DOM 操作、字符串处理这些,WASM 帮不上忙。

二、最小示例 ​

Rust:

rust
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}
bash
cargo install wasm-pack
wasm-pack build --target web --release
js
import init, { add } from './pkg/index.js'

await init()          // 加载 .wasm,必须先 await

console.log(add(2, 3))  // 5

注意:await init() 是必须的 —— 在它完成前调用导出的函数会报错。

三、和 JS 互操作的三种方式 ​

1. 基础数值传递(最快) ​

js
const result = add(2, 3)          // 数字直接传

只适合纯数值计算,零拷贝。

2. 线性内存共享(最快,但要自己管) ​

WASM 实例有一块 ArrayBuffer 内存,JS 可以直接读写。

js
const memory = new WebAssembly.Memory({ initial: 256 })  // 256 页 = 16MB
// Rust 侧: let buf = memory.grow(...)
const ptr = alloc(len)                // Rust 侧分配,返回指针
const view = new Uint8Array(memory.buffer, ptr, len)   // JS 侧直接看同一块内存

这是高性能场景的正解:一次拷贝都没有。

3. JS 字符串 / 对象(最慢) ​

js
// Rust 侧用 wasm-bindgen 暴露的 API
const result = greet('世界')          // 字符串会经历编码 → 分配 → 解码

WASM 内部没有字符串和对象,这些都要跨边界转换,开销大。所以接口设计要尽量用数字和 TypedArray。

四、加载方式 ​

1. fetch + instantiateStreaming(推荐) ​

js
const { instance } = await WebAssembly.instantiateStreaming(
  fetch('/calc.wasm'),
  { env: { memory: ... } }
)

浏览器会边下载边编译,比等完整下载快。

2. import 直接引入(需要正确的 MIME) ​

js
import init from './calc.wasm'
await init()

要求服务器返回 Content-Type: application/wasm,否则 instantiateStreaming 会失败。

3. 实例化 JS 胶水代码 ​

js
const imports = { env: { log: console.log } }
const { instance } = await WebAssembly.instantiate(bytes, imports)

五、性能的真实情况 ​

对比何时 WASM 更快
纯数值计算常常快 1.5~10 倍
字符串处理通常更慢(跨边界开销)
DOM 操作更慢(WASM 不能碰 DOM)
跨边界调用频繁更慢(每次调用都有开销)

结论:WASM 的收益来自「把一大块纯计算搬出去一次算完」,而不是「逐次调用更快」。边界调用是它最大的成本。

六、开发体验 ​

语言工具链适合
Rustwasm-pack / wasm-bindgen最主流,生态好,内存安全
C / C++Emscripten复用现有 C++ 代码(ffmpeg、图像库)
GoTinyGoGo 开发者
AssemblyScript类似 TS 的语法前端团队想试 WASM
C#Blazor / dotnet-wasm.NET 生态

给前端团队的建议:先用 AssemblyScript 试水(语法像 TS),真要上生产再考虑 Rust。

七、实际项目里的用法 ​

js
// 图片压缩:主线程上传前先压缩,避免卡顿
async function compress(file) {
  // 也可以放到 Worker 里做,彻底不占主线程
  const { compress_image } = await import('./wasm/image.js')
  return compress_image(new Uint8Array(await file.arrayBuffer()))
}
js
// 在 Worker 里跑 WASM,主线程完全无感
const worker = new Worker('/wasm-worker.js', { type: 'module' })
worker.postMessage({ type: 'compress', buffer }, [buffer])  // transferable,零拷贝

注意:WASM 计算虽然快,但它仍然占着调用线程。想彻底不卡 UI,应该放进 Web Worker。

🎯 面试常考 ​

Q1: WebAssembly 什么时候比 JS 快? 纯数值计算密集的场景(编解码、加密、图像处理、游戏引擎、物理仿真)。涉及字符串、对象、DOM 操作时通常比 JS 慢,因为跨边界有编码和分配开销。

Q2: WASM 和 JS 通信的开销在哪? ① 字符串和对象要序列化/反序列化;② 每次调用都有固定的边界开销;③ 内存不能直接共享(除非用线性内存)。所以接口要设计成「一次调用传一大块 TypedArray」,而不是「高频小调用」。

Q3: 线性内存是什么? WASM 实例的一块可增长的 ArrayBuffer。JS 侧用 new Uint8Array(memory.buffer, ptr, len) 直接读写,零拷贝,是高性能互操作的方式。

Q4: WebAssembly.instantiateStreaming 有什么好处? 浏览器边下载边编译,不用等完整下载再编译,首字节到可用更快。需要服务器返回 Content-Type: application/wasm。

Q5: 为什么图像处理经常用 WASM? 因为是纯计算且数据量大:一张 4000×3000 的图片有 4800 万像素,JS 逐像素处理会长时间占用主线程。WASM 能在 Worker 里几倍速度处理完,主线程完全无感。

📝 小结 ​

  • WASM 替代的是「计算密集的纯计算」,不是所有 JS;DOM 和字符串操作反而更慢。
  • 核心成本在 JS ↔ WASM 的边界,接口设计要减少跨界次数、优先传 TypedArray。
  • 想要不卡 UI,应该把 WASM 放进 Web Worker。
  • 前端团队可以先用 AssemblyScript 试水,生产级再上 Rust。
