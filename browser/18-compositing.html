层叠上下文与合成层 ​

「为什么我的 z-index 加到 9999 还是被盖住」——答案几乎总是:你不在同一个层叠上下文里。

一、三棵独立的树 ​

CSS 里常被混为一谈的三件事,其实是三套独立的排序规则:

树决定什么排序依据
层叠上下文(Stacking Context)谁盖住谁z-index + 层叠顺序
层叠顺序(Stacking Order)同层级内的绘制次序规范定义的 7 步
文档顺序(DOM Order)同层级同 z-index后面的盖前面的

关键😒-index 只在同一个层叠上下文内比较。不同上下文之间,比的是上下文自身在父上下文里的 z-index。

二、什么会创建层叠上下文 ​

以下任一条件成立,元素就成为层叠上下文的根:

  1. 根元素 html
  2. 定位元素且 z-index !== auto(即 position: fixed / sticky,或有 z-index 的 absolute / relative)
  3. opacity < 1
  4. transform 不为 none(含 translate / rotate / scale)
  5. filter 不为 none(含 backdrop-filter)
  6. perspective 不为 none
  7. will-change 指定了上述任一属性
  8. contain: paint / layout / content
  9. mix-blend-mode 不为 normal
  10. flex / grid 子项且 z-index 不为 auto
  11. <template>、will-change: contents 等特殊情况
html
<div class="a">      <!-- 层叠上下文 A,z-index: 1 -->
  <div class="a1" style="position:absolute; z-index: 9999">A1</div>
</div>
<div class="b">      <!-- 层叠上下文 B,z-index: 2 -->
  <div class="b1" style="position:absolute; z-index: 1">B1</div>
</div>

A1 的 z-index 是 9999,B1 是 1,但 B 整体盖住 A —— 因为 A1 的 9999 只在 A 内部有效,A 的 z-index 是 1 < B 的 2。

这就是「z-index 9999 无效」的根因:你被困在一个低层叠上下文的盒子里了。

三、层叠顺序的 7 个层次 ​

同一个层叠上下文内,按这个顺序从下往上绘制:

7. 负 z-index 的定位子元素
6. 块级背景 / 浮动 / 内联元素
5. z-index: auto / 0 的定位元素
4. 正 z-index 的定位子元素
3. 背景与边框(层叠上下文根元素自身)
2. z-index: 负的子层叠上下文
1. z-index: 0 的子层叠上下文

四、合成层(Compositing Layer) ​

层叠上下文是「谁盖谁」的规则,合成层是「GPU 怎么画」的机制,两者独立。

浏览器会把某些元素提升为独立合成层,单独占一块 GPU 内存,单独绘制:

触发条件说明
will-change: transform / opacity显式提升
transform / translate / rotate / scale通常会提升
opacity < 1(且有动画)提升
position: fixed提升
<video> / <canvas>提升
正在播放动画的元素提升
backdrop-filter提升

为什么 transform 动画更流畅 ​

属性触发阶段是否触发合成
width / height / topLayout否
background-color / colorPaint否
opacityComposite是
transformComposite是

改 width 会触发重排 → 重绘 → 合成,三步全走;改 transform 只走合成,GPU 直接搬图层。

css
/* ❌ 触发重排,每帧都在算布局 */
.box { transition: width 0.3s; }

/* ✅ 只触发合成 */
.box { transition: transform 0.3s; }
.box:hover { transform: translateX(10px); }

五、代价:合成层不是越多越好 ​

每个合成层都占一块 GPU 内存(纹理),层太多会导致:

  • 显存爆炸:移动端 GPU 显存有限,层过多可能直接掉帧
  • 过度绘制:层叠的透明区域被重复绘制,填充率浪费
  • 合成开销:层数多时 GPU 的合成 pass 也变多
css
/* ❌ 给每个列表项都提层,100 项 = 100 个合成层 */
li { will-change: transform; }

/* ✅ 只给真正在动的元素提层 */
.scrolling-list li.active { will-change: transform; }

规则:will-change 只在动画即将开始时加上,动画结束后移除。 常驻 will-change 会白白占用显存。

js
el.addEventListener('mouseenter', () => el.style.willChange = 'transform')
el.addEventListener('mouseleave', () => el.style.willChange = 'auto')

六、调试手段 ​

js
// 看某个元素在哪个层叠上下文里
const el = document.querySelector('.a1')
console.log(getComputedStyle(el).zIndex)          // '9999'
console.log(getComputedStyle(el).transform)       // 'none' → 没创建层叠上下文?
console.log(getComputedStyle(el.parentElement).zIndex)  // 父上下文才是关键

DevTools 面板:

  • Layers 面板:能看到所有合成层,以及哪些层因为什么被提升
  • Rendering 面板 → Paint flashing:高亮所有重绘区域
  • Rendering 面板 → Layer borders:显示每层边界

七、排查「z-index 失效」的步骤 ​

1. 元素有没有真的创建层叠上下文?
   → transform / opacity / filter / will-change 任意一个不为 none
2. 往上找一层,那个祖先的 z-index 是多少?
   → 真正在比较的是这一层的 z-index
3. 那个祖先是否也在某个更上层的上下文里?
   → 继续往上找,直到 html
4. 兄弟元素里有没有同 z-index 的?
   → 同 z-index 时看 DOM 顺序,后者盖前者

🎯 面试常考 ​

Q1: z-index 9999 还是被盖住,为什么? 因为 z-index 只在同一个层叠上下文内有效。元素被 transform / opacity / filter 等属性创建了一个层叠上下文,它就只能在那个上下文内部比较。要比较的是创建上下文的那个祖先的 z-index。

Q2: 哪些属性会创建层叠上下文?position 非 static 且 z-index 非 auto、opacity < 1、transform、filter / backdrop-filter、perspective、will-change 指向这些属性、contain: paint/layout/content、mix-blend-mode、flex/grid 子项带 z-index。

Q3: 为什么 transform 做动画比 width 流畅?width 触发 Layout → Paint → Composite 三阶段;transform 只触发 Composite,浏览器可以直接在 GPU 上变换已有图层,不重算布局也不重绘。前提是元素已被提升为独立合成层。

Q4: will-change 用多了有什么问题? 每个 will-change: transform 都会提前创建合成层,占 GPU 显存。移动端显存有限,层过多会导致显存溢出甚至页面崩溃。正确做法是只在动画即将开始时加,结束后移除。

Q5: 怎么用 DevTools 排查层叠问题? Layers 面板看合成层及其提升原因,Rendering 面板的 Layer borders 显示层边界,Paint flashing 高亮重绘区域。

📝 小结 ​

  • 层叠上下文决定「谁盖谁」,合成层决定「GPU 怎么画」,两者独立但常被混谈。
  • z-index 只在同一个层叠上下文内有效,「z-index 9999 无效」几乎都是这个原因。
  • transform / opacity 只触发合成,所以动画更流畅;width / top 会触发重排。
  • will-change 会提前占显存,只在动画开始前加、结束后移除。
