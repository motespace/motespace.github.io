一、为什么面试官爱问这道题 ​

前端面试圈有个"祖传题":从输入 URL 到页面渲染,中间发生了什么? 几乎每家前端面试必问。原因不是面试官偷懒,而是这道题恰好覆盖了前端 80% 的知识面。

               这道题考察的体系
              ┌──────────┴──────────┐
         网络层(60%)              浏览器内核(40%)
   ┌─────────┴─────────┐         ┌──────┴──────┐
  DNS/TCP/TLS/HTTP                解析          渲染
                                  DOM/CSSOM    Render Tree
                                  Layout       Paint
                                  Composite

具体能考察的能力:

  • 网络基础:URL 解析、DNS 解析、TCP 三次握手、TLS 握手、HTTP 协议版本演进
  • 浏览器内核:HTML 解析 → DOM、CSS → CSSOM、JS 阻塞模型、渲染流水线
  • 工程素养:preload / prefetch / preconnect 区别、defer / async 选择、关键资源内联策略
  • 性能优化实战:能引出真实案例(下文有 5 个项目数字)

简历里写"性能优化"几乎是标配,但不掌握这道题等于裸面。

更深一层的考察价值:

  • 能区分"背诵型"和"理解型"候选人 —— 背诵的只能复述框架,理解的能讲清楚"为什么"
  • 能看出技术视野 —— 是否理解 HTTP 协议演进(HTTP/1.1 → HTTP/2 → HTTP/3)
  • 能看出工程经验 —— 是否能说出自己项目里优化的具体数字
  • 能引出更多追问(为什么 3 次握手、HTTP/2 解决了什么、TCP 队头阻塞在哪一层)

接下来按 11 个主要阶段展开,每个阶段配实战场景。

二、URL 解析:浏览器拿到的不只是字符串 ​

浏览器点击链接或地址栏回车,先拿到 URL 字符串。第一步就是解析它的结构。

2.1 URL 的组成 ​

  https://user:pass@example.com:8080/path/to/page?a=1&b=2#hash
   \__/   \____/    \_________/ \__/ \____________/ \______/ \__/
   协议     凭证        主机      端口      路径         查询    片段

各部分的作用:

  • protocol:协议,常见 http / https / file / data / blob
  • user:pass:基本认证凭证,几乎不用,浏览器会弹窗
  • host = hostname:port:浏览器请求时实际连接这个
  • pathname:服务端路径,大部分框架基于它做路由
  • query:查询参数,键值对
  • hash:#hash,浏览器不发给服务端,只用于前端定位

2.2 用 new URL() 拆解 ​

现代浏览器提供 URL 接口,不用再写正则拆 URL:

js
const url = new URL("https://user:pass@example.com:8080/path?a=1&b=2#hash")

console.log(url.protocol)  // "https:"
console.log(url.host)      // "example.com:8080"
console.log(url.hostname)  // "example.com"
console.log(url.port)      // "8080"
console.log(url.pathname)  // "/path"
console.log(url.search)    // "?a=1&b=2"
console.log(url.hash)      // "#hash"
console.log(url.origin)    // "https://example.com:8080"
console.log(url.username)  // "user"
console.log(url.password)  // "pass"

实战经验:

  • host 含端口,hostname 不含 —— CORS 调试时容易混淆
  • origin 是协议 + 主机 + 端口,同源策略靠它判断
  • searchParams 是 URLSearchParams,支持 .get("a")、getAll("a")、append("c", "3")
js
const params = new URL("https://example.com/?a=1&a=2").searchParams
params.get("a")      // "1"  (取第一个)
params.getAll("a")   // ["1", "2"]
params.has("b")      // false
params.append("c", "3")
params.toString()    // "a=1&a=2&c=3"

Vue 项目的 vue-router 用这个解析 query,React 项目 react-router-dom v6 也是。

2.3 URL 编码:encodeURIComponent vs encodeURI ​

URL 只能出现 ASCII 子集。中文、空格、# ? / & = 等必须编码成 %XX 形式。

两种编码方式的根本区别:

函数编码字符保留字符
encodeURIComponent几乎所有特殊字符A-Z a-z 0-9 - _ . ! ~ * ( )
encodeURI同上,但保留 URL 结构字符; / ? : @ & = + $ , #
js
// ✅ 编码 URL 参数值(只编码值,不编码结构)
encodeURIComponent("张三")
// "%E5%BC%A0%E4%B8%89"

encodeURIComponent("https://example.com/?a=1")
// "https%3A%2F%2Fexample.com%2F%3Fa%3D1"
// (连 / ? : & = 都被编码)

// ✅ 编码整个 URL,保留 URL 结构字符
encodeURI("https://example.com/?a=1")
// "https://example.com/?a=1"

// ❌ 错误:用 encodeURI 编码参数
encodeURI("name=张三&age=20")
// 中间不会编码 &,直接发给后端会被当成分隔符

项目实战踩坑:商户后台"批量导出订单"功能,前端把订单号(含 ? # &)直接拼到 URL,后端解析失败。修复:永远用 encodeURIComponent 编码参数值。

URLSearchParams 也提供编码,但默认对空格用 +(form-urlencoded 风格)而不是 %20:

js
new URLSearchParams({ a: "hello world" }).toString()
// "a=hello+world"

new URLSearchParams({ a: "张三" }).toString()
// "a=%E5%BC%A0%E4%B8%89"

服务端期待 + 还是 %20 取决于后端实现。一般用 encodeURIComponent 最稳。

2.4 hash 路由 vs history 路由 ​

URL 解析完后,SPA 还要决定是 hash 还是 history 路由:

SPA 路由模式:
├── hash 模式
│   URL: http://example.com/#/user/123
│   • 浏览器只请求 example.com 一次(只看 # 之前的部分)
│   • 改 location.hash 触发视图切换
│   • 监听 hashchange 事件
│   • 服务端不用配,部署简单
│
└── history 模式(HTML5 History API)
    URL: http://example.com/user/123
    • 真的改了 pathname
    • pushState / replaceState 改 URL,不发请求
    • 监听 popstate(浏览器前进后退)
    • 服务端 /user/123 必须 fallback 到 index.html

项目实战:

  • 商户后台用 hash 模式 —— 老 Nginx,懒得配 fallback
  • 风控引擎平台用 history 模式 —— Vue 3 + Vite,需要 try_files $uri /index.html;
  • SSR 必须用 history 模式(SEO 友好,否则爬虫只看到空)

注意:Vue Router v4 / React Router v6 的 createBrowserRouter 默认就是 history 模式,部署时务必配服务端 fallback:

nginx
# nginx
location / {
  try_files $uri $uri/ /index.html;
}

Netlify 用 _redirects:

/*    /index.html   200

三、DNS 域名解析:从域名到 IP 的旅程 ​

URL 拆完,浏览器拿到 example.com。下一步是查 IP。

3.1 DNS 查询完整顺序 ​

  浏览器进程内 DNS 缓存 (Chrome 默认 ~60s)
        ↓ 没命中
  操作系统 DNS 客户端缓存
        ↓
  /etc/hosts 文件 (Windows: C:\Windows\System32\drivers\etc\hosts)
        ↓
  本地 DNS 服务器(递归解析,ISP 提供:8.8.8.8 / 114.114.114.114)
        ↓
  根域名服务器(Root DNS,全球 13 组 + 任播)
        ↓ 知道 .com 在哪
  顶级域名服务器(.com / .cn / .org)
        ↓ 知道 example.com 在哪
  权威域名服务器(注册商配置,例如 ns1.example.com)
        ↓ 返回最终 IP
  最终 IP 返回给浏览器 → 缓存

每一级都有缓存。整个查询耗时 0~200ms,弱网下能到 500ms+。

3.2 递归查询 vs 迭代查询 ​

  • 递归查询:客户 → 本地 DNS,中间过程本地 DNS 全包办,客户最终拿到 IP
  • 迭代查询:客户 → 根 DNS,根返回"xx 在 y 这台机器上" → 客户自己查 → 一路追下去

实际是混合的:

  • 本机到本地 DNS 是递归
  • 本地 DNS 到根、顶级、权威是迭代(本地 DNS 自己跑)

本机一般不用自己查,本地 DNS 代劳。

3.3 DNS 缓存的 TTL ​

$ dig example.com

example.com.    300    IN    A    1.2.3.4
;             ^^^ TTL 5 分钟
  • TTL 太短:DNS 解析频繁,慢
  • TTL 太长:换 IP 后用户拿到老地址,切流量要等 TTL 过期

项目实战:

  • CDN 灰度发布时,把 TTL 调到 60~120 秒,让 DNS 快速收敛
  • 正常生产 300~3600 秒(5 分钟 ~ 1 小时)
  • 不重要的子域名可以长一点
  • Chrome 进程内 DNS 缓存默认 ~60s,可在 chrome://net-internals/#dns 查看和清除

3.4 DNS 预解析 (dns-prefetch / preconnect) ​

DNS 查询在弱网下经常 200~500ms,通过提前解析抢时间:

html
<!-- 只提前解析 DNS -->
<link rel="dns-prefetch" href="//cdn.example.com">
<link rel="dns-prefetch" href="//api.partner.com">

<!-- preconnect:解析 + TCP + TLS,~省 100-300ms -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>

应用场景:

  • 第三方统计(Google Analytics、百度统计、Sentry)
  • 第三方字体(fonts.gstatic.com)
  • 多 CDN 域名(图床、回源)
  • 跨域 API 服务

性能数据:

  • 强网(4G/WiFi):dns-prefetch 省 ~50ms
  • 弱网(3G/4G 切换):省 ~200~500ms

注意:Chrome 会自动把 dns-prefetch 升级为 preconnect(如果发现资源真的被使用)。所以 dns-prefetch 写起来更轻量。

项目实战:会员端 H5 用 CDN 域名 static.member-cdn.com 服务图片,通过 preconnect 让首屏图片加载提前 100~200ms。

3.5 DNS 污染与劫持 ​

某些运营商会篡改 DNS 响应:

真实:example.com → 1.2.3.4
被劫:example.com → 6.6.6.6 (钓鱼站)

两种攻击:

  • DNS 污染(Spoofing):运营商在 UDP 53 端口伪造响应包,因为 DNS 用 UDP 无连接,客户端无法验证
  • DNS 劫持:更彻底,改本地 DNS 服务器或家用路由器 DNS 设置

解决方案 1:HTTPDNS(阿里云、腾讯云都有)

传统 DNS:用户 → UDP 53 端口 → 本地 DNS → 权威 DNS
HTTPDNS:用户 → HTTPS 443 端口 → HTTPDNS 服务 → 权威 DNS

HTTPDNS 走 HTTPS,运营商看不到域名,无法劫持

实战:商户后台在外网访问时,部分省份运营商劫持 api.example.com。接入阿里云 HTTPDNS 后,劫持率从 ~5% 降到 ~0.5%。

解决方案 2:DoH (DNS over HTTPS) / DoT (DNS over TLS)

  • Chrome / Firefox 都支持 DoH,Chrome 默认开启
  • 公共 DoH:https://dns.quad9.net/dns-query、https://1.1.1.1/dns-query
  • 完全加密、运营商无法篡改
  • 在浏览器 chrome://settings/security 配置

3.6 DNS 与 Connection 复用 ​

Chrome 网络栈会复用最近连接:

如果 host + port + 协议 + 加密 都匹配最近连接,且连接还活着
    → 直接复用,省 TCP + TLS 握手(几十 ~ 几百 ms)

经验:

  • 第三方资源尽量用同一域名(同 connection 复用)
  • HTTP/2 多路复用更彻底 —— 同 connection 并行发多个请求
  • Same-origin 资源天然复用,跨域才会触发新握手

优化策略:

  • 静态资源合并到同一域名(CDN 域名收敛)
  • API 用单独域名(避免 JS / CSS 抢同一 connection)
  • 第三方 SDK 数量少(每个域名一次握手)

四、TCP 三次握手:三次是必须的 ​

IP 拿到,浏览器通过 socket 发 TCP 连接。TCP 是面向连接的,连之前要三次握手确认双向收发能力。

4.1 三次握手流程 ​

         客户端                              服务端
           │                                    │
           │ ─────── SYN (seq=x) ────────────→  │  第 1 次:客户端说"我能发"
           │                                    │
           │ ←──── SYN + ACK (seq=y, ack=x+1) ── │  第 2 次:服务端说"我能收+我能发"
           │                                    │
           │ ─────── ACK (seq=x+1, ack=y+1) ──→ │  第 3 次:客户端说"我能收"
           │                                    │
           │          连接建立,可以发 HTTP 数据了 │

字段:

  • SYN:同步序号,标记连接建立
  • ACK:确认序号,告诉对方"我收到你前面发的"
  • seq:序号,标识数据包顺序,TCP 是字节流协议

4.2 为什么是三次,不是两次或四次 ​

两次(省掉第 3 次)的灾难:会收到"失效的旧 SYN 报文"。

客户端发 SYN(seq=x),网络卡了
       ↓
客户端超时重传 SYN(seq=x)
       ↓
重传的 SYN 到了服务端
       ↓
服务端发 SYN+ACK,连接建立
       ↓
此时第一次的 SYN 终于到了
       ↓
服务端以为又是一个新连接,又开一个
       ↓
(没第三次 ACK,客户端无法确认这个连接)
       ↓
服务端开了两个空连接,等不到 ACK,超时关闭,浪费资源

四次:多余,三次已足够。"三次"是为了在不可靠信道上用最少的次数达成双向确认。

更深的理由:

  • 第 1 次:客户端确认"自己能发"
  • 第 2 次:服务端确认"自己能收 + 能发"
  • 第 3 次:客户端确认"自己能收"

三次之后,双方都确认了"对方能收发"。

类比:打电话

  • A:听到我说话吗?(SYN)
  • B:听到了,我也能说话,你听得到我吗?(SYN+ACK)
  • A:听到了。(ACK)

如果你只问 2 次,A 说"听到了"但 B 不知道 A 听不听到自己的回话,可能重复说话浪费。

4.3 为什么是四次挥手 ​

TCP 是全双工 —— 客户端 → 服务端、服务端 → 客户端是两个独立方向。关闭时两边要各自关闭一次。

         客户端                              服务端
           │                                    │
           │ ─────── FIN ─────────────────────→ │  客户端:不再发了
           │ ←────── ACK ──────────────────────  │  服务端:知道了
           │                                    │
           │ ←────── FIN ──────────────────────  │  服务端:我也关了
           │                                    │
           │ ─────── ACK ─────────────────────→ │  客户端:收到
           │                                    │
       (服务端收到 ACK 后进 TIME_WAIT,等 2MSL 后释放)

TIME_WAIT 要等 2MSL(2 * Maximum Segment Lifetime,~60-240 秒) 的原因:

  • 保证最后一个 ACK 能到服务端(丢了的话服务端会重发 FIN)
  • 让这次连接的所有报文从网络中消失(避免和后续新连接冲突)

项目踩坑:高并发服务端 TIME_WAIT 几万,占用端口。新连接报 Cannot assign requested address。修复:

bash
# Linux 内核参数
sysctl -w net.ipv4.tcp_timestamps=1
sysctl -w net.ipv4.tcp_tw_reuse=1     # 允许复用 TIME_WAIT
sysctl -w net.ipv4.tcp_fin_timeout=10 # FIN 等待缩短(默认 60)

或者更彻底:长连接复用(同一连接发多个请求),从应用层绕过 TIME_WAIT。

4.4 HTTP/1.1 / HTTP/2 / HTTP/3 的连接模型 ​

版本连接模型队头阻塞握手 RTT头部
HTTP/1.0每请求新连接严重(连接)1(TCP)文本
HTTP/1.1keep-alive 复用应用层1(TCP)文本
HTTP/2多路复用应用层无,传输层有1(TCP)二进制 + HPACK
HTTP/3(QUIC)UDP + 自定义传输无0二进制 + QPACK

项目实战:商户后台迁移 HTTP/2:

  • 首屏 30+ 个 JS chunk
  • HTTP/1.1:6 个连接各跑 5 个请求,串行 ~4s
  • HTTP/2:1 个连接并行,首屏降到 1.4s(-65%)

五、TLS 握手(简化版):HTTPS 的安全基础 ​

HTTPS = HTTP + TLS。在 TCP 之上加一层加密,确保传输数据不会被中间人偷看或篡改。

5.1 TLS 1.2 vs TLS 1.3 ​

TLS 1.2 (RSA 模式,2-RTT 握手):

         客户端                              服务端
           │                                    │
           │ ── ClientHello ──────────────────→  │  列出支持的 cipher
           │                                    │
           │ ←── ServerHello + Certificate ────  │  选 cipher + 发证书
           │                                    │
           │ ── ClientKeyExchange ────────────→  │  用公钥加密 pre-master secret
           │                                    │
           │ ←── Finished ────────────────────  │  双方开始加密通信

需要 2 个 RTT 才能开始发 HTTP 请求。

TLS 1.3 (1-RTT 握手,默认):

         客户端                              服务端
           │                                    │
           │ ── ClientHello (带 ECDHE 公钥) ───→ │  客户端先算好密钥材料
           │                                    │
           │ ←── ServerHello + Finished ───────  │  服务端也算密钥
           │                                    │
           │  开始加密通信                        │

TLS 1.3 强制 1-RTT(0-RTT 可选)。顺手把 cipher suite 从 30+ 砍到 5 个,更安全更快。

5.2 关键概念 ​

  • 证书(Certificate):服务端发,第三方 CA 签发(Let's Encrypt、DigiCert)
  • SNI(Server Name Indication):一个 IP 多 HTTPS 站点必备 —— 客户端告诉"我要连 example.com"
  • ALPN:TLS 握手时一并定 HTTP/2 还是 HTTP/1.1,省一次往返
  • OCSP Stapling:服务端主动去 CA 查证书状态,客户端不用单独查
  • 0-RTT:客户端和服务端之前连过,直接基于 PSK 发数据,0 往返。但有重放攻击风险,只在幂等请求用

5.3 HTTPS 性能影响 ​

TLS 握手开销:
├── TLS 1.2 RSA:     2 RTT    ~200-400ms
├── TLS 1.2 ECDHE:   1.5 RTT  ~150-300ms
└── TLS 1.3:         1 RTT    ~100-200ms
                    (0-RTT 可 ~50ms,但有重放风险)

优化手段:

  • TLS 1.3 启用(浏览器默认,服务端 Nginx 也开)
  • Session Resumption(Session ID / Session Ticket)
  • OCSP Stapling
  • False Start(TLS 1.2 下凑出 1-RTT)

项目实战:移动 App 升级 TLS 1.3 + 0-RTT,二次启动 HTTPS 握手从 ~200ms 降到 ~50ms,首屏提前 150ms。

5.4 证书过期 ​

项目踩坑:Let's Encrypt 证书只有 90 天有效期。某次商户后台证书过期没续,网站打不开 2 小时。修复:监控 curl -I 检查证书有效期,提前 14 天告警。

bash
# 自动续期
certbot renew --quiet --no-self-upgrade

# 监控脚本
DOMAIN=api.example.com
EXPIRY=$(echo | openssl s_client -connect $DOMAIN:443 -servername $DOMAIN 2>/dev/null \
  | openssl x509 -noout -enddate | cut -d= -f2)
DAYS_LEFT=$(( ($(date -d "$EXPIRY" +%s) - $(date +%s)) / 86400 ))
[ $DAYS_LEFT -lt 14 ] && echo "证书快过期了,还剩 $DAYS_LEFT 天"

5.5 HTTPS vs HTTP 性能对比 ​

首屏时间(HTTPS vs HTTP):
├── HTTP:        ~600ms
├── HTTPS TLS 1.2: ~900ms (+ 50%)
└── HTTPS TLS 1.3: ~700ms (+ 16%)

纯握手开销 ~100-300ms,但收益:数据传输加密、防劫持、SEO 友好。

现代项目:HTTPS 已经默认,HTTP 被各浏览器标记为不安全。

6.4 HTTP 状态码分类 ​

1xx - 信息: 100 Continue, 101 Switching Protocols
2xx - 成功: 200 OK, 201 Created, 204 No Content, 206 Partial Content
3xx - 重定向: 301 Moved Permanently, 302 Found, 304 Not Modified
4xx - 客户端错误: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xx - 服务端错误: 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

实战经验:

  • 304 走的是协商缓存,文件没变,服务端不返回 body,只返回 304 状态
  • 301 vs 302:301 是永久重定向,浏览器会缓存,以后直接走新地址;302 是临时,每次都问
  • 502 通常是 Nginx 上游(应用)挂了,503 是应用主动拒绝(限流)

6.5 HTTP/1.1 keep-alive 与队头阻塞 ​

HTTP/1.0:
请求 1 ── TCP 连接 ────→ 关闭
请求 2 ── TCP 连接 ────→ 关闭
请求 3 ── TCP 连接 ────→ 关闭
每次新连接,三次握手浪费!

HTTP/1.1 keep-alive:
请求 1 ─┐
请求 2 ─┼── 长连接复用 ──
请求 3 ─┘
但:请求要排队,队头阻塞!
如果请求 1 慢,2 和 3 都得等

实际浏览器:对同一域名开 6~8 个并行连接(队头阻塞的妥协方案)。移动端浏览器可能只开 4~6 个。

6.6 HTTP/2 多路复用 ​

HTTP/2:
请求 1 ─┐
请求 2 ─┼── 同一 TCP 连接,二进制分帧,按需交错
请求 3 ─┘

特性:
├── 多路复用:单连接并行多个请求/响应
├── HPACK 头压缩:常见头部压缩 ~80%
├── 二进制分帧:二进制协议,非文本
├── 流量优先级:Stream 依赖(实际效果有限)
└── Server Push(已废弃,见 §9.4)

关键点:HTTP/2 的多路复用打掉应用层队头阻塞,但 TCP 层队头阻塞还在(一个包丢了后续都等)。

项目实战:把 6 个并行 TCP 连接合并为 1 个 HTTP/2,首屏时间降 30%。

6.7 HTTP 缓存策略 ​

指令含义
Cache-Control: max-age=3600强缓存 1 小时
Cache-Control: no-cache不强缓存,每次问服务器(可能 304)
Cache-Control: no-store完全不缓存
Cache-Control: public中间 CDN 可缓存
Cache-Control: private只浏览器缓存,中间节点不要
ETag: "abc"文件指纹,变才变
Last-Modified: ...文件修改时间
Vary: Accept-Encoding根据请求头不同缓存不同版本

实战套路:

ts
// 文件名带 hash(强缓存 1 年)
// main.abc123.js

Cache-Control: public, max-age=31536000, immutable

// HTML 不缓存
Cache-Control: no-cache, must-revalidate

构建工具(Vite / Webpack)自动给静态资源加 hash,内容变 → 文件名变 → 强制更新。

项目踩坑(详见 项目踩坑):商户后台某次紧急 bug 修复上线后,30% 用户仍报问题 —— 因为他们浏览器缓存了旧版 JS。修复:文件名加 hash + HTML 不缓存。

7.2 资源标签的阻塞行为 ​

┌──────────────────────────┬──────────────┬──────────────┐
│ 标签                     │ DOM 解析     │ 渲染         │
├──────────────────────────┼──────────────┼──────────────┤
│ <link rel="stylesheet"> │ 不阻塞       │ 阻塞         │
│ <script>(无标记)         │ 阻塞         │ 阻塞         │
│ <script async>           │ 下载不阻塞   │ 不阻塞       │
│                          │ 执行时阻塞   │              │
│ <script defer>           │ 不阻塞       │ 不阻塞       │
│                          │ DOM 完顺序执行│              │
│ <script type="module">   │ 不阻塞(defer)│ 不阻塞       │
│ <img>                    │ 不阻塞       │ 不阻塞       │
│ <iframe>                 │ 不阻塞       │ 不阻塞       │
└──────────────────────────┴──────────────┴──────────────┘

<link rel="stylesheet">:

  • 异步下载 CSS,不阻塞 DOM 解析(网络线程并发)
  • 但阻塞渲染(没 CSSOM 无法构建 Render Tree)
  • 早期 Chrome 会"猜测"渲染,等 CSS 加载完 layout 重做一次(FOUC)

<script>(无 async/defer):

  • 阻塞 DOM 解析
  • 下载完立即执行(可能修改 DOM)
  • 执行完才能继续解析 HTML
  • 这就是为什么 script 标签要放 <body> 底部

<script async>:

  • 异步下载,下载不阻塞 DOM
  • 下载完立刻执行(可能打断 DOM 解析)
  • 多个 async 顺序不确定(谁先下完谁先跑)
  • 适用:第三方脚本(广告、统计),互相无依赖

<script defer>:

  • 异步下载
  • 等 DOM 解析完,在 DOMContentLoaded 前按文档顺序执行
  • 多个 defer 保证顺序
  • 适用:应用代码(vendor.js + app.js)

<script type="module">:

  • 默认 defer 行为
  • ES Module 加载规范
  • 浏览器还可能自动做 tree-shaking 优化

7.3 执行时序图 ​

html
<script src="a.js"></script>
<script async src="b.js"></script>
<script defer src="c.js"></script>
<script defer src="d.js"></script>
<script type="module" src="e.js"></script>
下载阶段(并行):
  ├── a.js 下载 ────┐
  ├── b.js 下载 ────┤
  ├── c.js 下载 ────┤ 全部并行
  ├── d.js 下载 ────┤
  └── e.js 下载 ────┘

执行阶段(顺序):
  a.js 下载完 → 立刻执行 → 阻塞 DOM 解析
  (在 a 执行期间,b/c/d/e 可能下载完但要等)

  a.js 执行完 → 继续解析 HTML

  b.js async → 下载完立刻执行(可能打断 DOM)
  c.js defer → DOM 完后,先于 d 执行
  d.js defer → c 之后再执行
  e.js module → 类似 defer

DOMContentLoaded 触发:
  defer + module 全部执行完才触发

7.4 DOMContentLoaded vs load ​

HTML 解析完 ──┬──→ DOMContentLoaded 事件
              │
              │  (defer + module 脚本执行完才触发 DCL)
              │
              ▼
         (子资源加载中:图片、iframe、字体、CSS)
              │
              ▼
         所有资源到位 ──→ load 事件

项目代码:

js
document.addEventListener("DOMContentLoaded", () => {
  // 首屏 DOM OK,业务 JS 可跑
  initApp()
})

window.addEventListener("load", () => {
  // 所有资源加载完
  analytics.track("page_loaded")
})

实战套路:

  • DCL 触发首屏埋点
  • load 触发"页面完整"指标
  • LCP(Largest Contentful Paint)才是现代首屏指标,见 Web Vitals

7.5 解析中的内置优化 ​

预解析(Speculative Parsing):

Chrome 会"猜"后面有什么资源,提前发请求:

html
<head>
  <link rel="stylesheet" href="main.css">      <!-- Chrome 立刻请求 -->
  <script src="app.js"></script>                <!-- Chrome 立刻请求(因为同步 script) -->
</head>
<body>
  <img src="hero.jpg" alt="...">                <!-- 解析到时,后台已请求 -->
</body>

预加载扫描器(Preload Scanner):Chrome 的 HTML 解析器边解析边扫描 <link>、<img>、<script src> 等 URL,交给网络线程预请求,不等解析到。

实战经验:JS 动态插入的资源不享受预解析 —— 这是 SPA 性能优化的痛点。

js
// ❌ 动态 img 不预解析,要等 JS 跑到这行才发请求
const img = new Image()
img.src = "hero.jpg"

// ✅ 用 <link rel=preload as=image> 提前通知浏览器
// 解决方法:HTML 里提前写
// <link rel="preload" href="hero.jpg" as="image">

7.6 错误处理解析 ​

HTML 解析器对错误非常宽容:

html
<!-- 即使下面这些"错误",浏览器也会尽量渲染 -->
<html><body><p>Hello
<p>World
<table>
  <!-- 表格里随便放 div 也行 -->
  <div>随便放</div>

<!-- 没有 </html> </body> 也行 -->

八、渲染流水线(简要) ​

详细见 渲染流程。这里只概述三个阶段。

8.1 Layout / Reflow(回流 / 重排) ​

计算每个节点的几何信息(坐标、尺寸)。

js
// ❌ 触发布局
element.style.width = "100px"
element.style.height = "200px"
element.offsetWidth  // 读 → 触发 layout

性能影响:最贵的阶段,主线程同步进行。

8.2 Paint(重绘) ​

把像素画到图层。

js
// 触发 paint,不触发 layout
element.style.backgroundColor = "red"
element.style.color = "blue"
element.style.visibility = "hidden"

性能影响:中,主线程同步,但比 layout 便宜。

8.3 Composite(合成) ​

把多个图层合并到一张图,交给 GPU 显示。

css
/* 只触发合成,不触发 layout 和 paint */
transform: translateX(100px);
opacity: 0.5;
will-change: transform;

性能影响:最便宜,由合成线程独立处理,主线程卡顿也不影响合成。

8.4 三阶段对比表 ​

操作LayoutPaintComposite
transform✗✗✓
opacity✗✗✓
width/height✓✓✓
top/left✓✓✓
background✗✓✓
color✗✓✓

关键实战:transform 比 top/left 动画流畅 —— 前者只走合成线程,后者把主线程打满,掉帧严重。

js
// ❌ left 动画:每帧 layout + paint
function animate(dom, x) {
  dom.style.left = x + "px"
  if (x < 100) requestAnimationFrame(() => animate(dom, x + 1))
}

// ✅ transform 动画:只 composite
function animateFast(dom, x) {
  dom.style.transform = `translateX(${x}px)`
  if (x < 100) requestAnimationFrame(() => animateFast(dom, x + 1))
}

九、性能优化点:完整武器库 ​

9.1 四个 "pre" 的区别 ​

指令优先级行为时机场景
<link rel="preload">高立刻下载,标记为"必用"文档解析时首屏 CSS/JS/字体
<link rel="prefetch">低空闲时下载浏览器空闲下个页面
<link rel="preconnect">高提前握手(DNS+TCP+TLS)立刻第三方域名
<link rel="dns-prefetch">中只解析 DNS立刻第三方追踪
html
<!-- preload:首屏关键字体 -->
<link rel="preload" href="/fonts/main.woff2" as="font" crossorigin>

<!-- prefetch:下个页面资源 -->
<link rel="prefetch" href="/next-page.html">

<!-- preconnect:CDN -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>

<!-- dns-prefetch:第三方追踪 -->
<link rel="dns-prefetch" href="//www.google-analytics.com">

实战经验:

  • preload 不要乱用 —— 用太多反而抢首屏关键资源带宽
  • preconnect 在弱网下价值最大
  • 现代浏览器合并 dns-prefetch 和 preconnect(自动找到资源后升级)

9.2 关键 CSS 内联 + 非关键 CSS 异步 ​

html
<head>
  <!-- 关键 CSS(~5-10 KB)内联 -->
  <style>
    body { margin: 0; font-family: sans-serif; background: #fff; }
    .hero { padding: 20px; min-height: 100vh; }
    .nav { display: flex; gap: 16px; }
  </style>

  <!-- 非关键 CSS 异步加载 -->
  <link id="async-css" rel="stylesheet" href="main.css" media="print">
  <script>
    document.getElementById("async-css").addEventListener("load", function() {
      this.media = "all"
    })
  </script>
  <noscript><link rel="stylesheet" href="main.css"></noscript>
</head>

原理:media="print" 让浏览器认为是打印样式,不阻塞屏幕渲染。onload 时切换 media="all" 生效。

实战:IoT 大屏项目,把关键 CSS 从 150KB 抽到 8KB 内联,首屏 FCP 从 2.5s 降到 1.4s(详见 §10.2)。

9.3 defer 加载非关键 JS ​

html
<head>
  <!-- defer:不阻塞 DOM,DCL 前执行 -->
  <script defer src="/js/vendor.js"></script>
  <script defer src="/js/app.js"></script>

  <!-- 关键同步 JS 放 <body> 底部,代码量最小 -->
</head>
<body>
  <div id="app"></div>

  <script>
    // ~几行同步初始化
  </script>
</body>

9.4 HTTP/2 Server Push(已废弃,了解即可) ​

HTTP/2 服务端推送 —— 服务端主动把资源推到客户端,不等浏览器解析后发请求。

nginx
# nginx server push 配置
location /index.html {
  http2_push /style.css;
  http2_push /app.js;
}

但是:Server Push 已被 Chrome、Firefox 弃用。原因:

  • 浏览器 preload 能力已覆盖
  • Push 命中率差(经常推到客户端发现已有)
  • 实现复杂、副作用多

实战上:用 preload + HTTP/2 多路复用就够了,别用 Server Push。

字体 preload:

html
<link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin>

实战:中文字体常常 1~3MB,必须 subset:

bash
# 只保留常用字
pyftsubset "SourceHanSans.otf" --text-file=common-chars.txt -o subset.woff2

# subset 后从 3MB 降到 ~50KB

9.7 第三方脚本治理 ​

第三方脚本(统计、广告、A/B 测试)经常是性能黑洞。

实战套路:

html
<!-- ❌ 直接放 head -->
<script src="https://hm.baidu.com/hm.js"></script>

<!-- ✅ defer 加载,不阻塞首屏 -->
<script defer src="https://hm.baidu.com/hm.js"></script>

<!-- ✅ 或 lazy:等首屏完才加载 -->
<script>
window.addEventListener("load", () => {
  const s = document.createElement("script")
  s.src = "https://hm.baidu.com/hm.js"
  document.body.appendChild(s)
})
</script>

项目实战:商户后台 5 个第三方脚本(defer + load 后挂),DCL 从 1.8s 降到 1.2s。

9.8 减少 JS 执行时间 ​

js
// ❌ 主线程跑长任务
button.addEventListener("click", () => {
  heavyCalculation()  // 1 秒,期间所有 click 事件丢失
})

// ✅ 拆分长任务
async function processInChunks(items, chunkSize = 50) {
  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize)
    processChunk(chunk)
    await new Promise(resolve => setTimeout(resolve, 0))  // 让主线程喘息
  }
}

或者用现代 API:

ts
async function processInChunks(items: any[]) {
  for (const item of items) {
    heavyProcess(item)
    await scheduler.yield()  // Chrome 129+, 让浏览器处理高优先级任务
  }
}

10.1 商户后台:分析脚本 defer,DCL 从 1.8s 降到 1.2s ​

问题:商户后台接入了百度统计 + Sentry 监控 SDK,两者都用 <script src> 同步加载,阻塞 DOM 解析。

检测:

Lighthouse 报告:
- FCP: 1.8s
- DCL: 1.8s
- LCP: 2.4s
- TBT: 350ms

问题代码:

html
<head>
  <link rel="stylesheet" href="main.css">
  <script src="https://hm.baidu.com/hm.js?xxx"></script>
  <script src="https://browser.sentry-cdn.com/xx/bundle.min.js"></script>
</head>

百度统计和 Sentry 都在 head 里,阻塞 DOM 解析。

修复:

html
<head>
  <link id="async-css" rel="stylesheet" href="main.css" media="print">
  <script>
    document.getElementById("async-css").addEventListener("load", function() {
      this.media = "all"
    })
  </script>
  <!-- 关键 CSS 抽 6KB 内联 -->

</head>
<body>
  <!-- defer 加载:不阻塞 DOM,DCL 前按顺序执行 -->
  <script defer src="https://hm.baidu.com/hm.js?xxx"></script>
  <script defer src="https://browser.sentry-cdn.com/xx/bundle.min.js"></script>
</body>

十一、面试回答模板:30 秒 + 90 秒 ​

11.1 30 秒版(简短复述) ​

输入 URL 到首屏,大致分 8 步:

  1. URL 拆 protocol/host/path/query/hash
  2. DNS 查 IP —— 浏览器缓存 → 系统缓存 → hosts → 本地 DNS → 根 → 顶级 → 权威
  3. TCP 三次握手,防失效 SYN
  4. TLS 握手(HTTP/2: 1-2 RTT,HTTP/3: 0-RTT)
  5. HTTP 请求/响应(HTTP/1.1 keep-alive,HTTP/2 多路复用)
  6. 浏览器解析 HTML → DOM,CSS → CSSOM,script 阻塞 DOM,DCL 前 defer 执行
  7. 渲染树 → Layout → Paint → Composite
  8. 性能优化:preload / preconnect / defer,内联关键 CSS

11.2 90 秒版(讲完整,带实战) ​

从输入 URL 到首屏,分 8 步讲:

1. URL 解析。浏览器先看 protocol/host/port/path/query/hash,传参记得用 encodeURIComponent 编码,SPA 区分 hash 和 history 模式。

2. DNS 查询。先查浏览器缓存(~60s)、系统缓存、hosts,再问本地 DNS 递归查根、顶级、权威。CDN 切流量要调短 TTL,首屏第三方域名用 dns-prefetch 提前解析。运营商劫持用 HTTPDNS 绕过。

3. TCP 三次握手。三次是为了双向确认 + 防失效 SYN。HTTP/1.1 一个连接一次一个请求,HTTP/2 多路复用打掉队头,HTTP/3 直接走 QUIC 0-RTT。

4. TLS 握手。HTTPS 性能关键。TLS 1.2 RSA 2-RTT,ECDHE 1.5-RTT,TLS 1.3 强制 1-RTT,0-RTT 还能省二次握手。SNI 解决一机多站,ALPN 顺手定 HTTP 版本。

5. HTTP 请求。请求行 + 请求头(Host/Cookie/User-Agent/Authorization/Referer/Origin),响应行 + 响应头(Cache-Control/Set-Cookie/CSP/HSTS)。HTTP/1.1 keep-alive 复用,HTTP/2 单连接多路复用 + HPACK 头部压缩。

6. 浏览器解析。字节流 → HTML Parser → Token → DOM。CSS Parser → CSSOM。<link rel=stylesheet> 不阻塞 DOM 阻塞渲染。<script> 不加标记阻塞 DOM。defer 不阻塞 DOM,DCL 前按顺序执行。async 下载完立刻执行,不保证顺序。type=module 默认 defer。

7. 渲染流水线。DOM+CSSOM → Render Tree(排除 display:none)→ Layout 计算坐标 → Paint 绘像素 → Composite 合成。transform / opacity 只走 Composite,width / height / top / left 走 Layout。

8. 性能优化(我做过):

  • 分析脚本 defer(我们商户后台 DCL 1.8s → 1.2s)
  • 关键 CSS 内联 + 非关键 CSS 异步(IoT 大屏 FCP 2.5s → 1.4s)
  • preconnect 第三方域名(风控平台点击响应 400ms → 200ms)
  • HTTP/2 多路复用 + Brotli(农业 App 首屏 4s → 1.4s)
  • preload 关键字体,别用 Server Push(Chrome 已废)

11.3 追问预案(常见追问 + 标准答案) ​

Q: 为什么是 3 次握手不是 2 次? A: 2 次无法确认客户端"收到服务端的 SYN+ACK"。如果只 2 次,服务端发出的 SYN+ACK 如果丢,客户端以为连接失败,服务端却以为建立了 —— 浪费资源,还被失效的旧 SYN 报文攻击。

Q: TLS 1.3 怎么做到 1-RTT? A: 客户端在 ClientHello 里把 ECDHE 公钥参数一起发了,服务端收到后用客户端公钥 + 自己私钥算出共享密钥,直接进入加密通信。

Q: defer 和 async 核心区别? A: defer 在 DCL 前按文档顺序执行,多个 defer 保证顺序。async 下载完立刻执行,多个 async 顺序不确定。

Q: HTTP/2 还有啥改进? A: 多路复用、HPACK 头压缩、二进制分帧、流量优先级(Stream Priority)。Server Push 已废弃。

Q: 为什么 Server Push 被弃用? A: 浏览器 preload 更准确,Push 命中率差(经常推到客户端发现已有),实现复杂。

Q: HTTP/3 为什么换 UDP? A: TCP 队头阻塞在传输层(一个包丢,后续包等),QUIC 基于 UDP 重新实现传输,在 UDP 上做了自己可靠的流式传输,避免队头。

Q: 关键 CSS 内联多少合适? A: ~10-15KB(覆盖首屏),多了反而阻塞首字节(TTFB 不变,但 HTML 变大)。

Q: 为什么 transform 比 left 动画流畅? A: transform 只走 Composite,合成线程独立处理,主线程卡顿不影响。left 触发 Layout,主线程同步进行,卡顿直接掉帧。

Q: prefetch 会浪费流量吗? A: 会。预取的资源如果用户没用,流量浪费。prefetch 命中率通常 30%-60%,可以接受但要监控。

Q: link rel=preload 和 modulepreload 区别? A: modulepreload 是 ES Module 版本,会自动 preload 模块 + 所有 import 的依赖。

Q: 为什么 HTTP 缓存要分强缓存和协商缓存? A: 强缓存(max-age)省一次请求,协商缓存(ETag)保证文件变了能拿到新版本。生产上静态资源用强缓存 1 年 + 文件名 hash,HTML 用协商缓存。

Q: DOMContentLoaded 为什么不包括 async 脚本? A: async 脚本下载完立刻执行,不保证顺序,可能打断 DOM 解析;defer 才保证 DCL 前按顺序执行完毕。所以 DCL 等 defer + module,不包含 async。

Q: 协商缓存为什么还要发请求? A: 强缓存 max-age 内不发请求,过期后浏览器用 ETag / Last-Modified 去问服务端"我本地这个版本还能用吗",服务端回 304(没变)或 200 + 新内容。304 不带 body,只确认版本。

Q: CDN 切流量怎么操作? A: 把域名 TTL 调短(60-120s)→ 改 DNS A 记录指向新 CDN → 观察流量切换曲线 → TTL 过期后大部分用户走新 CDN。不能直接改 TTL,要提前调短等老缓存过期。

Q: HTTP/1.1 keep-alive 的队头阻塞怎么解决? A: HTTP/1.1 时代只能开多个连接(浏览器 6-8 个)。彻底解决靠 HTTP/2 多路复用。
