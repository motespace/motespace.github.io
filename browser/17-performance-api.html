性能测量 API 全家桶 ​

想知道「到底慢在哪」,得先能精确测量。浏览器给了三组测量 API。

一、三组 API 的分工 ​

API回答什么问题入口
Navigation Timing这次导航的各阶段耗时performance.getEntriesByType('navigation')[0]
Resource Timing每个资源加载了多久performance.getEntriesByType('resource')
User Timing我自己埋的标记耗时performance.mark() / measure()

再加一个 PerformanceObserver 做实时上报(上一节讲过)。

二、Navigation Timing:一次导航的时间账单 ​

js
const nav = performance.getEntriesByType('navigation')[0]

// 关键时间点(全部相对导航开始)
console.log('DNS 解析   ', nav.domainLookupEnd - nav.domainLookupStart)
console.log('TCP 连接   ', nav.connectEnd - nav.connectStart)
console.log('TLS 握手   ', nav.secureConnectionStart > 0 ? nav.connectEnd - nav.secureConnectionStart : 0)
console.log('请求-响应  ', nav.responseEnd - nav.requestStart)
console.log('DOM 解析完 ', nav.domContentLoadedEventEnd)
console.log('完全加载   ', nav.loadEventEnd)

// 最关键的三个派生指标
const ttfb = nav.responseStart - nav.startTime        // 首字节时间
const fcp  = nav.responseStart - nav.startTime        // ≈ TTFB
const domInteractive = nav.domInteractive             // DOM 可交互

三个核心派生指标 ​

指标算法意义
TTFBresponseStart - startTime服务端多快(含 DNS + TCP + TLS + 服务端处理)
FCPpaint entries 里 first-contentful-paint首次内容出现
DOMContentLoadeddomContentLoadedEventEndDOM 解析完,可执行 JS

快速定位「慢在哪」 ​

js
function diagnose(nav) {
  const dns  = nav.domainLookupEnd - nav.domainLookupStart
  const tcp  = nav.connectEnd - nav.connectStart
  const req  = nav.responseEnd - nav.requestStart
  const ttfb = nav.responseStart - nav.startTime

  if (ttfb > 800) return '服务端慢:TTFB ' + ttfb + 'ms,先查后端与 CDN'
  if (dns > 100) return 'DNS 慢:' + dns + 'ms,考虑预解析或换 DNS'
  if (tcp > 300) return '连接慢:' + tcp + 'ms,考虑 HTTP/2 或长连接'
  if (req > 500) return '服务端处理慢:' + req + 'ms'
  return 'TTFB 正常,瓶颈在资源加载或渲染,去看 Resource Timing'
}

三、Resource Timing:每个资源的账单 ​

js
const resources = performance.getEntriesByType('resource')

// 找出最慢的 5 个
resources
  .sort((a, b) => b.duration - a.duration)
  .slice(0, 5)
  .forEach(r => {
    console.log(
      r.name.slice(-50),
      '耗时', Math.round(r.duration) + 'ms',
      '大小', r.transferSize + 'B',
      '协议', r.nextHopProtocol
    )
  })

关键字段 ​

字段含义坑
duration完整耗时(fetchStart → responseEnd)含排队,不一定等于下载时间
transferSize实际传输字节跨域且无 Timing-Allow-Origin 时是 0
encodedBodySize压缩后大小真实资源体积
decodedBodySize解压后大小与 encoded 的比值就是压缩率
nextHopProtocolh2 / http/1.1能看出是否走了 HTTP/2
initiatorTypescript / img / fetch资源类型
renderBlockingStatus是否阻塞渲染非阻塞资源可以提前加载

跨域资源拿不到详细数据(transferSize = 0),除非服务端加:

Timing-Allow-Origin: https://your-site.com

四、User Timing:自己埋标记 ​

js
// 打标记
performance.mark('start-parse')
doHeavyWork()
performance.mark('end-parse')

// 量区间
performance.measure('parse-duration', 'start-parse', 'end-parse')
console.log(performance.getEntriesByName('parse-duration')[0].duration)

// 标记渲染点
performance.mark('hero-rendered')

在 DevTools 的 Performance 面板和 Web Vitals 报告里,这些标记会直接显示在时间线上,排查「某个函数拖慢了几百毫秒」非常直观。

注意:performance.mark() 本身几乎零成本,可以放心用。

五、Buffer 与长任务 ​

js
// 观察长任务
const po = new PerformanceObserver(list => {
  for (const e of list.getEntries()) {
    console.log('长任务:', Math.round(e.duration), 'ms', e.attribution)
  }
})
po.observe({ type: 'longtask', buffered: true })

e.attribution 能告诉你这个长任务是哪个脚本干的。

六、Performance API 的两个坑 ​

坑 1:精度受限 ​

出于指纹攻击防护,performance.now() 在跨域 iframe 等场景下精度会被降低(通常 5~100 微秒)。日常测量够用,但别拿它做纳秒级基准。

坑 2:数据是「事后」的 ​

getEntriesByType() 是回看 —— 数据在你调用时才产生。长任务、资源加载这些必须在事件发生时用 PerformanceObserver 实时监听才能不漏。

js
// ❌ 事后拉取:可能已经错过
const paints = performance.getEntriesByType('paint')

// ✅ 实时监听:buffered 补发
new PerformanceObserver(l => {/* ... */}).observe({ type: 'paint', buffered: true })

🎯 面试常考 ​

Q1: TTFB 和 FCP 有什么区别? TTFB(responseStart - startTime)是服务端返回第一个字节的时间,反映后端与网络;FCP 是浏览器首次绘制内容的时间,受 TTFB、资源下载、JS 执行、渲染阻塞共同影响。FCP 慢但 TTFB 正常,问题就在前端资源。

Q2: 怎么定位首屏慢在哪? 按 Navigation Timing 拆:TTFB > 800ms 是服务端问题;DNS/TCP 段异常是网络问题;TTFB 正常就去看 Resource Timing 找最慢的资源,再看是不是 render-blocking。

Q3: transferSize 为什么是 0? 跨域资源在没有 Timing-Allow-Origin 响应头时,浏览器出于隐私保护不暴露大小。此时用 encodedBodySize 也不准,只能通过服务端日志或 PerformanceObserver 的其他方式估算。

Q4: performance.mark 和 measure 的区别?mark 打一个时间点,measure 量两个(或多个)时间点之间的区间。排查具体函数耗时用 mark + measure,比手动 Date.now() 相减更准确,也更容易在 DevTools 里看。

Q5: 为什么推荐 PerformanceObserver 而不是 getEntriesByType? getEntriesByType 是「回看」,只有你调用时才拿数据,期间产生的条目可能已经被清理或你根本不知道发生了。PerformanceObserver 是「订阅」,事件发生时立即回调,配合 buffered: true 还能补发注册前的条目。

📝 小结 ​

  • Navigation Timing 给「这一次导航」的时间账单,Resource Timing 给「每个资源」的时间账单,User Timing 给你自己的埋点。
  • 排查首屏先用 Navigation Timing 判断是后端还是前端,再用 Resource Timing 找具体资源。
  • renderBlockingStatus 能直接告诉你哪些资源在阻塞渲染。
  • 数据是事后的,实时监控必须用 PerformanceObserver + buffered: true。
