项目踩过的坑:浏览器相关真实案例 ​

来自简历项目"01 商户管理 SaaS"、"02 会员 Web/H5"、"03 智能风控引擎平台"、"04 农业数字化 App + IoT 大屏"的浏览器相关踩坑经验。

一、Cookie 跨域丢失 ​

问题:服务端没设 SameSite=None; Secure,HTTPS 站点下 Cookie 默认不发。

踩坑: 商户后台 API 在 api.example.com,前端在 app.example.com(同站但跨子域)。登录成功后 Cookie 没带上来,后端一直返回 401。

修复:

http
Set-Cookie: token=xxx; SameSite=None; Secure; Path=/; Domain=example.com

注意:

  • SameSite=None 必须配 Secure
  • Domain=example.com 让所有子域都能访问
  • 测试:用 document.cookie 看是否带

详见 /security/8-csrf-samesite.md。

二、强缓存导致代码更新失效 ​

问题:不带 hash 的 JS 文件用 Cache-Control: max-age=3600,更新后用户拿不到新版本。

踩坑: 商户后台某次紧急 bug 修复上线后,30% 用户仍报问题——因为他们浏览器缓存了旧版 JS。

修复:

ts
// 1. 文件名带 hash
// main.abc123.js 而不是 main.js

// 2. HTML 不缓存
Cache-Control: no-cache, must-revalidate

// 3. 静态资源长期缓存
Cache-Control: public, max-age=31536000, immutable

构建工具(Vite/Webpack)自动给文件名加 hash,确保内容变了文件名变 → 强制更新。

三、Layout Thrashing(强制同步布局) ​

问题:循环里读写 offsetWidth 触发反复回流,掉帧严重。

踩坑: IoT 大屏 10000+ 数据点的图表滚动时掉帧到 10 FPS。Chrome DevTools 显示:Layout 占了 80% 时间。

原因分析:

js
// ❌ 循环里交替读写
for (let i = 0; i < 1000; i++) {
  const height = element.offsetHeight  // 读,触发 layout
  element.style.height = (height + 1) + 'px'  // 写,标记 dirty
}
// 下次读再 layout... 1000 次 layout

修复:

js
// ✅ 全部读完再写
const height = element.offsetHeight  // 一次读
for (let i = 0; i < 1000; i++) {
  element.style.height = (height + i + 1) + 'px'
}

// ✅ 用 transform(不触发 layout)
element.style.transform = `translateY(${i}px)`

检测:

  • Chrome DevTools Performance 面板
  • 看 "Layout" 事件耗时
  • 看 "Forced reflow" 警告

四、图片没指定宽高导致 CLS ​

问题:用户看到的文字突然跳动,体验差。

踩坑: 会员端 H5 商品列表,图片加载完毕后整个列表往下"抖"了一下。Lighthouse CLS 0.25(阈值 0.1)。

修复:

html
<!-- 给所有 img 显式宽高 -->
<img src="product.jpg" width="200" height="200" alt="商品">

<!-- 或者用 aspect-ratio CSS -->
<style>
.product-img {
  aspect-ratio: 1 / 1;
  width: 100%;
  background: #f5f5f5;
}
</style>

Lighthouse CLS:0.25 → 0.05(优秀)

五、PWA Service Worker 缓存没失效策略 ​

问题:缓存用了旧版本资源,新版本发布后用户拿不到。

踩坑: 商户后台用 Service Worker 缓存了 app shell,某次接口协议变更后,老 SW 还用旧版 JS,导致接口报错。

修复:

js
// sw.js - 版本号管理
const VERSION = 'v2'
const CACHE_NAME = `app-${VERSION}`
const STATIC_CACHE = `static-${VERSION}`

self.addEventListener('install', (event) => {
  // 立即激活新 SW,跳过 waiting
  self.skipWaiting()
})

self.addEventListener('activate', (event) => {
  // 清除旧版本缓存
  event.waitUntil(
    caches.keys().then(keys => {
      return Promise.all(
        keys.filter(k => !k.includes(VERSION))
            .map(k => caches.delete(k))
      )
    })
  )
  // 接管所有页面
  return self.clients.claim()
})

版本管理套路:

  • 内容 hash 做版本号(自动)
  • 每次 deploy 都生成新 cache key
  • activate 阶段清理旧 cache

六、localStorage 容量超限 ​

问题:localStorage 通常限制 5~10MB,大量数据写入会抛 QuotaExceededError。

踩坑: 商户后台的"操作历史"功能把几千条历史存 localStorage,刷新后报错。

修复:

ts
function safeSetItem(key: string, value: string) {
  try {
    localStorage.setItem(key, value)
  } catch (e) {
    if (e instanceof DOMException && e.name === 'QuotaExceededError') {
      // 清理过期数据
      clearOldData()
      localStorage.setItem(key, value)
    } else {
      throw e
    }
  }
}

function clearOldData() {
  Object.keys(localStorage).forEach(key => {
    if (key.startsWith('cache:') && /* 时间过期 */) {
      localStorage.removeItem(key)
    }
  })
}

实战经验:

  • localStorage 适合存 < 1MB 数据
  • 大数据用 IndexedDB(无大小限制,但慢)
  • 重要数据别存 localStorage(可被 XSS 读)

七、Back/Forward Cache(BFcache) 行为异常 ​

问题:浏览器前进/后退用了 BFcache,JS 状态可能丢失。

踩坑: 会员端从"商品列表" → "详情" → 后退,期望"列表"保留滚动位置和筛选条件,但实际重置了。

修复:

ts
// 监听 pageshow 事件(包含 BFcache 恢复)
window.addEventListener('pageshow', (event) => {
  if (event.persisted) {
    // 从 BFcache 恢复
    restoreState()
  } else {
    // 首次加载
    initState()
  }
})

// 主动不缓存(不常用)
window.addEventListener('beforeunload', () => {
  // 不要无条件阻止(影响 BFcache)
  // 必要时用 navigator.sendBeacon
})

八、CORS 凭证丢失 ​

问题:withCredentials: true 但后端没设 Access-Control-Allow-Credentials: true。

踩坑: 登录接口 /api/login,前端带 cookie 但一直 401。最后发现后端 nginx 漏了 Access-Control-Allow-Credentials: true。

修复:

nginx
add_header Access-Control-Allow-Credentials true always;

注意:配 Allow-Credentials: true 时,Allow-Origin 不能是 *,必须是具体 origin。

九、跨域 iframe 无法通信 ​

问题:父页和跨域 iframe 用 iframe.contentWindow.foo() 调用,直接报跨域错误。

踩坑: 商户后台嵌入第三方支付 iframe,想调用 iframe.pay(),直接 SecurityError。

修复: 用 postMessage:

js
// 父页 → iframe
iframe.contentWindow.postMessage({
  type: 'pay',
  orderId: '123',
  amount: 100,
}, 'https://payment-provider.com')

// iframe 监听
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://parent.com') return
  if (e.data.type === 'pay') {
    handlePay(e.data.orderId, e.data.amount)
  }
})

详见 /security/11-iframe-security.md。

十、移动端 300ms 点击延迟 ​

问题:老版移动浏览器在 click 前等 300ms,看用户是否要双击缩放。

修复:

html
<meta name="viewport" content="width=device-width">

或者:

css
html {
  touch-action: manipulation;  /* 禁用双击缩放 */
}

现代浏览器已移除(只要 viewport meta 正确),老浏览器需要 FastClick 库。

十一、滚动穿透问题 ​

问题:弹层打开时,底层页面仍能滚动。

修复:

ts
// 弹窗打开时
function openModal() {
  document.body.style.overflow = 'hidden'
  // iOS:还要 fixed 定位
  document.body.style.position = 'fixed'
  document.body.style.width = '100%'
}

// 关闭时恢复
function closeModal() {
  document.body.style.overflow = ''
  document.body.style.position = ''
}

更好的方案:用 overscroll-behavior: contain:

css
.modal {
  overscroll-behavior: contain;  /* 滚动不传到 body */
}

十二、URL 编码陷阱 ​

问题:encodeURIComponent vs encodeURI 用错。

js
// ✅ 编码 URL 参数(查询字符串、路径片段)
encodeURIComponent('https://example.com/?a=1')
// 'https%3A%2F%2Fexample.com%2F%3Fa%3D1'

// ✅ 编码整个 URL
encodeURI('https://example.com/?a=1')
// 'https://example.com/?a=1'

// ❌ 错误用法:用 encodeURI 编码参数
encodeURI('https://example.com/?name=张三')
// 不会编码中文字符,服务端解析出错

实战经验:

  • URL 参数(查询字符串):encodeURIComponent
  • 整个 URL:new URL() 解析
  • 解码:decodeURIComponent

十三、第三方 Cookie 限制 ​

问题:Chrome 已开始禁用第三方 Cookie(ITP)。

影响:

  • 第三方登录 widget 可能丢失登录态
  • 跨站点追踪失效
  • 嵌入广告/分析受限制

应对:

  • 重要 Cookie 放第一方(主域)
  • 用 SameSite=None; Secure
  • 用 Storage Access API(用户主动授权)

🎯 面试常考 ​

Q1：浏览器相关的常见坑?

① 服务端渲染与客户端渲染不一致(hydration 报错);② 定时器/事件监听未清理导致内存泄漏;③ setData/大列表导致主线程长任务;④ 缓存策略不一致导致版本错乱。

Q2：hydration 错误怎么排查?

通常是不确定性渲染(随机数、Date.now、浏览器 API 直接在 render 里调用)。改成只在 useEffect 里访问 window/document,或用 suppressHydrationWarning。

Q3：怎么提前发现这类问题?

真实用户监控 + 自动化端到端测试(Playwright)覆盖关键路径,比等用户反馈快得多。

📝 小结 ​

  • 最隐蔽的坑:SSR 与 CSR 渲染结果不一致导致 hydration 报错 —— 根因是渲染期调用了随机数、Date.now 或 window。
  • 定时器/事件监听没清理 → 内存泄漏,单页应用里尤其致命。
  • setData / 大列表导致主线程长任务 → 掉帧。
  • 缓存策略不一致导致版本错乱(Service Worker 与 HTTP 缓存是两套)。
