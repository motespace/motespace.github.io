浏览器安全模型:同源策略、Cookie、沙箱 ​

一、浏览器安全的三层防线 ​

┌──────────────────────────────────┐
│ Layer 3: Sandbox                  │ ← 浏览器层(进程隔离)
│   - 多进程架构                    │
│   - iframe sandbox              │
│   - 站点隔离(Site Isolation)     │
└──────────────────────────────────┘
┌──────────────────────────────────┐
│ Layer 2: Same-Origin Policy       │ ← 同源策略(浏览器)
│   - DOM / Cookie / Storage      │
│   - AJAX(CORS)                  │
│   - iframe(父子通信)            │
└──────────────────────────────────┘
┌──────────────────────────────────┐
│ Layer 1: 用户/开发者             │ ← 实践
│   - HTTPS                      │
│   - CSP                        │
│   - 输入验证 + 输出转义           │
└──────────────────────────────────┘

任何一层被绕过都可能造成安全事件——所以多层防御是关键。

二、同源策略(Same-Origin Policy) ​

2.1 同源判定 ​

origin = protocol + host + port

https://example.com:443/path
↑        ↑             ↑
protocol host         port

判断同源:三者必须完全相同

http://example.com   ≠   https://example.com  (协议不同)
http://example.com   ≠   http://api.example.com (host 不同)
http://example.com   ≠   http://example.com:8080 (端口不同)

实战经验:

  • 子域(api.example.com 与 example.com)不同源——需要 CORS 或 document.domain
  • localhost 与 127.0.0.1 不同源(IE 算同源,Chrome 算不同源)

2.2 同源策略的限制 ​

资源类型同源可访问跨源默认
DOM✅❌ iframe 跨域不能读
Cookie✅❌ 跨域不发送
localStorage / sessionStorage✅❌
IndexedDB✅❌
Cache API✅❌
AJAX / fetch✅❌ 除非 CORS
WebSocket✅✅(协议允许)
postMessage✅✅ 但要校验 origin
Canvas✅跨域图片被污染(tainted)
CSS✅部分限制

2.3 同源策略的豁免 ​

html
<!-- 1. document.domain(老方案,已被弃用) -->
<!-- 两个页面都设置相同的 document.domain,可以互相访问 -->
<script>document.domain = 'example.com'</script>

<!-- 2. JSONP(老方案,几乎不用了) -->
<script src="https://api.example.com/data?callback=fn"></script>

<!-- 3. CORS(现代方案) -->
Access-Control-Allow-Origin: https://yoursite.com

三、Cookie 的同源与作用域 ​

3.1 Cookie 三大属性 ​

http
Set-Cookie: token=xxx; HttpOnly; Secure; SameSite=Lax
属性作用
DomainCookie 作用域名(默认当前域)
Path作用路径
Secure仅 HTTPS 发送
HttpOnlyJS 不可读
SameSite跨站是否带(Strict / Lax / None)
Max-Age / Expires过期时间

3.2 Domain 范围 ​

http
# 仅 example.com
Set-Cookie: id=xxx; Domain=example.com
# api.example.com 也带(子域)

# 仅 www.example.com
Set-Cookie: id=xxx; Domain=www.example.com

3.3 __Host- 前缀 ​

防 cookie 注入:

http
Set-Cookie: __Host-id=xxx; Secure; Path=/; HttpOnly

约束:

  • 必须 Secure
  • 不能有 Domain 属性
  • Path 必须是 /

好处:Cookie 注入攻击(如子域写 cookie)无法生效。

四、CORS(跨源资源共享) ​

4.1 简单请求 ​

http
GET /api/data HTTP/1.1
Origin: https://yoursite.com

服务端:

http
Access-Control-Allow-Origin: https://yoursite.com
Access-Control-Allow-Credentials: true
Vary: Origin

4.2 预检请求(OPTIONS) ​

非简单请求会先发 OPTIONS:

http
OPTIONS /api/data HTTP/1.1
Origin: https://yoursite.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

服务端:

http
Access-Control-Allow-Origin: https://yoursite.com
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

4.3 实战配置(Nginx) ​

nginx
location /api {
  # 允许指定 origin(不能用 *)
  add_header Access-Control-Allow-Origin $http_origin always;
  add_header Access-Control-Allow-Credentials true always;
  add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
  add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;

  # 预检缓存
  add_header Access-Control-Max-Age 86400;

  if ($request_method = 'OPTIONS') {
    return 204;
  }

  proxy_pass http://backend;
}

4.4 常见误区 ​

js
// ❌ 危险:Access-Control-Allow-Origin: *
// 配合 withCredentials:true 浏览器会拒绝
res.header('Access-Control-Allow-Origin', '*')
res.header('Access-Control-Allow-Credentials', 'true')

// ✅ 正确:动态匹配
res.header('Access-Control-Allow-Origin', req.headers.origin)  // 单 origin
res.header('Access-Control-Allow-Credentials', 'true')
res.header('Vary', 'Origin')  // 重要!否则可能被覆盖

五、iframe 安全 ​

详见 /security/11-iframe-security.md。核心要点:

html
<!-- 自己的页面:禁止被嵌入 -->
<!-- HTTP: X-Frame-Options: DENY -->
<!-- CSP: frame-ancestors 'none' -->

<!-- 嵌入第三方:严格 sandbox -->
<iframe sandbox="allow-scripts" src="..."></iframe>

六、沙箱(Sandbox) ​

6.1 iframe sandbox ​

值作用
""最严格(什么都不允许)
allow-scripts允许脚本
allow-forms允许表单
allow-same-origin视为同源(危险)
allow-top-navigation修改父级 URL(危险)
allow-popups弹窗

6.2 浏览器进程沙箱 ​

渲染进程
├── Chrome sandbox(Linux: setuid sandbox)
├── Windows: token-level integrity
├── macOS: Seatbelt sandbox
└── 都是 OS 级别的隔离

实际效果:

  • 渲染进程被入侵 → 攻击者仍受限于浏览器 API 权限
  • 读/写文件需通过浏览器主进程(IPC)
  • 不能直接访问用户文件系统

6.3 Site Isolation(站点隔离) ​

Chrome 67+ 启用了 Site Isolation:

https://bank.com   → 渲染进程 A
https://evil.com   → 渲染进程 B
                       (不能读 A 的内存)

iframe 跨站也独立:
https://bank.com/iframe-with-ads
  └── https://ads.com → 独立进程(不是 A)

好处:Spectre / Meltdown 类 CPU 漏洞下,跨站内存读取被阻止。

七、CSP(内容安全策略) ​

详见 /security/7-csp.md。核心:

http
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-{RANDOM}';
  object-src 'none';
  frame-ancestors 'none';

八、混合内容(Mixed Content) ​

HTTPS 页面加载 HTTP 资源,浏览器会拦截:

html
<!-- ❌ Mixed Content:被动(blocked) -->
<img src="http://example.com/img.png">
<!-- ❌ Mixed Content:主动(blocked) -->
<script src="http://example.com/lib.js"></script>

强制 HTTPS:

html
<meta http-equiv="Content-Security-Policy" content="upgrade-insecure-requests">

或服务端:

nginx
add_header Content-Security-Policy "upgrade-insecure-requests" always;

九、Referrer-Policy ​

控制 Referer 头的内容:

http
Referrer-Policy: strict-origin-when-cross-origin
值行为
no-referrer不发送
same-origin同源发送完整 URL
strict-origin跨域只发送 origin
strict-origin-when-cross-origin同源完整,跨域只 origin(默认)
unsafe-url总是发送完整(慎用)

十、其他浏览器安全机制 ​

10.1 Permissions Policy ​

控制哪些功能可用:

http
Permissions-Policy: camera=(), microphone=(), geolocation=(self)
功能默认
camera / microphone询问
geolocation询问
notifications询问
payment询问
usb / serial / hid询问
accelerometer / gyroscope询问

10.2 COOP / COEP(跨源隔离) ​

http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

效果:

  • 跨窗口引用关系断开(防 Spectre)
  • 启用 SharedArrayBuffer(需要 cross-origin isolated)
  • 性能 API 更精确(performance.measureUserAgentSpecificMemory())

10.3 Subresource Integrity(SRI) ​

html
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-..."
        crossorigin="anonymous"></script>

CDN 被入侵 → 文件 hash 不匹配,浏览器拒绝执行。

十一、常见踩坑 ​

场景问题
第三方 iframe 被入侵攻击者可读父页 DOM(同源情况),或弹广告
混合内容HTTPS 页面加载 HTTP 资源被拦截
postMessage 不校验 origin接受恶意来源消息
cookie 没 SameSiteCSRF 风险
Cookie 没 SecureHTTP 明文传输
Cookie 没 HttpOnlyXSS 偷 cookie

🎯 面试常考 ​

Q1：浏览器的同源策略限制什么?

限制跨源读取 DOM、存储、Cookie 和 XHR 响应;但允许发跨源请求(所以 CSRF 要单独防)。

Q2：沙箱 iframe 能隔离到什么程度?

sandbox 不给 allow-same-origin 时 iframe 是独立源,父页面完全访问不到它;给了就基本等同于同源,慎用。

Q3：CSP 和 iframe sandbox 怎么配合?

CSP 的 frame-ancestors 限制「谁可以嵌入我」,sandbox 限制「我能做什么」,两个方向一起用。

📝 小结 ​

  • 同源策略限制跨源读取(DOM、存储、Cookie、XHR 响应),但不阻止发请求 —— 这是 CSRF 的根源。
  • iframe 用 sandbox 逐项限制能力,不给 allow-same-origin 即独立源。
  • CSP 的 frame-ancestors 和 Permissions-Policy 是浏览器层的兜底。
  • 「跨源能干什么」比「跨源不能干什么」更重要 —— 安全设计要基于后者。
