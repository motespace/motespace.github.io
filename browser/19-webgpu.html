WebGPU 入门 ​

浏览器里的高性能图形与计算 API,WebGL2 的继任者。

一、WebGL 的天花板 ​

WebGL2 已经用了十几年,但它有几个硬伤:

问题表现
单线程所有 GL 命令都要过 JS → 渲染线程,主线程忙时直接掉帧
状态机式 APIbindBuffer / bindTexture / useProgram 一大堆全局状态,切换成本高
能力受限没有 compute shader、没有异步队列、没有时间戳查询
无法共享资源显存里的数据没法直接给 compute 用

二、WebGPU 的核心差异 ​

js
const adapter = await navigator.gpu.requestAdapter()
const device = await adapter.requestDevice()
const canvas = document.querySelector('canvas')
const ctx = canvas.getContext('webgpu')
const format = navigator.gpu.getPreferredCanvasFormat()
ctx.configure({ device, format, alphaMode: 'premultiplied' })

// 着色器用 WGSL(WebGPU Shading Language)
const module = device.createShaderModule({ code: /* WGSL */ `
  @vertex
  fn vs_main(@builtin(vertex_index) i: u32) -> @builtin(position) vec4f {
    var pos = array(vec2f(-1.0,-1.0), vec2f(3.0,-1.0), vec2f(-1.0,3.0));
    return vec4f(pos[i], 0.0, 1.0);
  }
  @fragment
  fn fs_main() -> @location(0) vec4f {
    return vec4f(1.0, 0.0, 0.0, 1.0);
  }
`})

const pipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: { module, entryPoint: 'vs_main' },
  fragment: { module, entryPoint: 'fs_main', targets: [{ format }] },
})

function frame() {
  const encoder = device.createCommandEncoder()
  const pass = encoder.beginRenderPass({
    colorAttachments: [{
      view: ctx.getCurrentTexture().createView(),
      clearValue: { r: 0, g: 0, b: 0, a: 1 },
      loadOp: 'clear', storeOp: 'store',
    }],
  })
  pass.setPipeline(pipeline)
  pass.draw(3)
  pass.end()
  device.queue.submit([encoder.finish()])
  requestAnimationFrame(frame)
}
frame()

三、WebGPU 相对 WebGL 的六点提升 ​

1. 真正的多线程 ​

命令编码在 Web Worker 里做,主线程只负责提交。渲染线程不再被 JS 阻塞。

2. 显式的资源绑定 ​

不用全局 bindXXX,而是建 bind group,把一组资源绑到管线上:

js
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [
    { binding: 0, resource: { buffer: uniformBuffer } },
    { binding: 1, resource: texture.createView() },
  ],
})
pass.setBindGroup(0, bindGroup)

好处是同一套资源绑定可以复用,不用反复切换状态。

3. Compute Shader ​

浏览器里终于能跑通用计算:

wgsl
@group(0) @binding(0) var<storage, read_write> data: array<f32>;

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) id: vec3u) {
  let i = id.x;
  if (i < arrayLength(&data)) {
    data[i] = data[i] * 2.0;
  }
}

典型用途:图像滤镜、粒子模拟、物理计算、密码学运算。

4. 显式的资源管理 ​

js
// 显式销毁,避免显存泄漏
buffer.destroy()
texture.destroy()

WebGL 里只能靠「等 GC 回收」,这是 WebGL 应用显存泄漏的常见原因。

5. 时间戳查询 ​

可以测量 GPU 每个 pass 的实际耗时,做真正的 GPU 性能分析。

6. 多画布 / 多设备 ​

GPUDevice 可以转移给 Worker,也可以在不同 canvas 之间共享资源。

四、什么时候该用 ​

场景建议
3D 模型渲染(Three.js 场景)✅ WebGPU 更快,但要评估生态兼容性
视频 / 图片实时滤镜✅ Compute shader 是杀手锏
粒子系统 / 物理仿真✅ 计算量大,多线程收益明显
3D 图表 / 数据可视化✅ GPU 加速
普通 DOM 页面❌ 完全用不上
已有的 WebGL 项目⚠️ 先用 WebGL,不要为了新 API 重写

五、兼容性与现状 ​

js
if (!navigator.gpu) {
  // 回退到 WebGL 或给出提示
}
  • Chrome / Edge:113+ 桌面版已支持
  • Safari:18+ 已支持(2024 年底)
  • Firefox:141+ 支持(Windows),其他平台在推进
  • 移动端:Android Chrome 已支持,iOS Safari 尚不支持

结论:桌面端已经可用,移动端要谨慎。生产环境务必做能力检测和降级。

六、WebGPU vs Three.js / Babylon.js ​

大多数项目不需要直接写 WebGPU:

  • Three.js:已支持 WebGPURenderer(WebGPURenderer + WebGPUBackend),写熟悉的 Three.js 代码就能用上 WebGPU,还能自动降级到 WebGL
  • Babylon.js:WebGPU 支持更完整,是目前 Babylon 的默认后端之一

除非你在做非常底层的图形研究,否则用引擎的 WebGPU 后端比自己从零写管线划算得多。

🎯 面试常考 ​

Q1: WebGPU 和 WebGL 的核心区别? ① WebGPU 支持多线程(命令编码可放在 Worker);② 显式的 bind group 取代全局状态机;③ 支持 compute shader;④ 显式资源销毁,显存可控;⑤ 支持时间戳查询做 GPU 分析;⑥ WGSL 取代 GLSL,语法更现代且有类型系统。

Q2: 怎么在 WebGL 项目里用上 WebGPU? 不要重写。用 Three.js 的 WebGPURenderer 或 Babylon.js 的 WebGPU 后端,它们会自动做能力检测和降级。

Q3: WebGPU 的兼容性怎么样? 桌面端 Chrome / Edge / Safari 已支持,Firefox Windows 版也支持;移动端主要只有 Android Chrome,iOS Safari 尚不支持。必须做能力检测和 WebGL 降级。

Q4: 什么是 compute shader? 一种在 GPU 上执行通用计算的着色器,不产出图像而是读写 buffer。适合图像处理、粒子模拟、物理计算这类数据密集型任务,是 WebGL 做不到的。

Q5: WebGL 应用常见的显存泄漏原因? WebGL 没有显式的资源销毁接口,只能依赖 GC。纹理、buffer、framebuffer 在 GPU 上的占用不受 JS GC 管理,导致显存持续增长。WebGPU 的 destroy() 明确解决了这个问题。

📝 小结 ​

  • WebGPU 解决 WebGL 的四个痛点:单线程、全局状态机、无 compute shader、资源无法显式释放。
  • 核心概念是 bind group(显式资源绑定)和 WGSL(带类型的着色器语言)。
  • 生产环境优先用 Three.js / Babylon.js 的 WebGPU 后端,自己做能力检测和降级。
  • 移动端支持尚不完整,iOS 尤其要谨慎。
