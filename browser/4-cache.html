HTTP 缓存:从强缓存到 CDN 的完整体系 ​

系列:浏览器原理 / 第四章

本篇聚焦浏览器侧 HTTP 缓存,涵盖强缓存、协商缓存、缓存位置、刷新行为、CDN 协作、实战配置与项目踩坑。

配套阅读:网络篇《HTTP 缓存机制》关注协议层;本篇关注浏览器实现与工程落地。

一、为什么 HTTP 缓存是性能优化之首 ​

浏览器加载一个页面的总耗时,网络往返往往占大头。HTTP 缓存的目标只有一个:让重复请求"几乎免费"。

两个层面优化:

  • 减少请求数:直接命中缓存,根本不发请求;避免 DNS、TCP、TLS 握手
  • 减少响应体积:即使要发请求(协商缓存 304),body 也是空的

典型场景:一个打包后的 JS 文件 app.4f3a.js 大小 500KB,gzip 后 130KB。强缓存命中后,浏览器零网络开销;协商缓存命中(304),只需几十字节往返。两者差距是几百倍。

真实数字:

场景单次耗时100 用户 PV 节省
无缓存(200 + 500KB body)~250ms25s 总和
协商缓存(304 + 0 body)~30ms3s 总和
强缓存命中(0 请求)~0ms0

在首屏场景下,缓存命中率 95% 意味着 100 个资源里只有 5 个真正走网络,这是 Lighthouse Performance 评分从 70 提升到 95+ 的关键杠杆之一。

更进一步,缓存是 0 RTT 优化 的基础。如果连 304 都不想要,就只有强缓存一种选择——这也是为什么 Vite/Webpack 产出的资源都默认带 hash 文件名 + immutable 头。

对照案例:某电商首页有 30 个静态资源(JS/CSS/图片/字体),平均每个 100KB。未命中缓存时首屏 800KB 下载量,耗时 1.8s;开启 immutable 后二次访问下载量 0,耗时 50ms(其余是 HTML 解析)。差距是 36 倍。

浏览器缓存层次(由近到远)
┌────────────────────────────────────────┐
│  Service Worker Cache(可编程)          │ ← JS 控制,粒度最细

一句话总结:

  • 强缓存 决定"用不用本地副本"
  • 协商缓存 决定"本地副本是不是最新"
  • 缓存位置 决定"副本存在哪一层"

2.3 三类缓存策略对照 ​

策略适用资源典型响应头
强缓存带 hash 的 JS/CSS/图片/字体max-age=31536000, immutable
协商缓存HTML、用户数据 APIno-cache + ETag
不缓存POST 请求、敏感数据no-store

三、强缓存深度 ​

3.1 Expires(HTTP/1.0,已废弃) ​

http
Expires: Wed, 21 Oct 2026 07:28:00 GMT

原理:服务器返回资源的过期时间(绝对时间戳),浏览器拿本地时间和这个值比较,没过期就用本地副本。

致命缺陷:

  • 依赖客户端时钟。如果用户改系统时间或跨时区,缓存判断立刻失准
  • 时间戳是绝对值,服务器时间一旦漂移就出 bug
  • HTTP/1.1 的 Cache-Control: max-age 用相对秒数,完美避开这些问题

实战中 Expires 只作为 HTTP/1.0 兼容兜底,主键仍然是 Cache-Control。

3.2 Cache-Control 完整指令表 ​

指令含义典型值
max-age=N相对秒数,缓存 N 秒max-age=3600
s-maxage=N共享缓存(CDN)专用,覆盖 max-ages-maxage=86400
public允许任何中间缓存(CDN/代理)存标志位
private只允许浏览器缓存,CDN 不许存标志位
no-cache强制每次都要协商(走 304 流程)标志位
no-store完全不缓存任何位置标志位
must-revalidate过期后必须重新验证,不能直接用标志位
immutable永不过期(配合 hash 文件名)标志位
stale-while-revalidate=N过期后 N 秒内先用旧值,后台刷新stale-while-revalidate=60
stale-if-error=N过期后 N 秒内,如果源站 5xx 仍用旧值stale-if-error=86400
proxy-revalidate中间代理必须重新验证(类似 must-revalidate)标志位
no-transform中间代理不允许改 Content-Encoding 等标志位

3.3 关键指令逐条精解 ​

max-age ​

http
Cache-Control: max-age=31536000
  • 单位是 秒,不是毫秒
  • 起点是 响应离开服务器的时刻,不是浏览器接收的时刻
  • 命中后浏览器不发请求,直接 200 from disk/memory cache

public vs private ​

http
Cache-Control: private
  • private:只有用户浏览器能存,中间代理(CDN/公司网关)不能缓存
  • 适用于带用户信息的响应(登录后的 HTML、用户头像 JSON)
  • 反之,public 表示"任何人都能缓存",适合静态资源

实战经验:登录后的 HTML 一律加 private + no-cache,否则 CDN 把张三的 HTML 缓存给李四,直接串号。

no-cache vs no-store ​

最容易搞混的两个:

指令缓存吗?走 304 吗?重新下载吗?
no-cache缓存每次都问没变就不下
no-store不缓存不问每次都下

记忆口诀:

  • no-cache 等于 "缓存但要验证"
  • no-store 等于 "别存任何东西"

s-maxage ​

http
Cache-Control: max-age=60, s-maxage=86400
  • 浏览器看到 max-age:60,缓存 1 分钟
  • CDN 看到 s-maxage:86400,缓存 1 天
  • 一个响应头,两边各算各的,互不干扰。这就是 §九 的伏笔。

must-revalidate ​

http
Cache-Control: max-age=60, must-revalidate

默认行为下,缓存过期后浏览器可以直接用本地副本(stale),不重新验证。 must-revalidate 强制"过期后必须问服务器"。

实战场景:金融/医疗数据,过期哪怕 1 秒都不可用,必须 must-revalidate。

immutable ​

http
Cache-Control: max-age=31536000, immutable

承诺给浏览器:这个 URL 未来一年内不会变,刷新页面也不要来问我。

  • 配合 hash 文件名使用(app.abc123.js 里 abc123 是内容指纹)
  • 文件名变了意味着新版本,旧 URL 自然过期
  • 浏览器收到 immutable 后,用户按 F5 也不会发请求

实测:immutable 资源在用户主动刷新页面时,网络面板里 304 都不会出现,真正 0 RTT。

stale-while-revalidate ​

http
Cache-Control: max-age=60, stale-while-revalidate=300

时序图:

0s        60s              360s
├──────────┼─────────────────┤
│  fresh    │     stale     │
│           │   (用旧值 + 后台刷新)
  • 0~60s:新鲜期,直接用
  • 60~360s:过期但可用,先用旧值,同时后台发请求刷新
  • 360s 后:缓存被淘汰

实战意义:用户感知 0 等待,后台悄悄把新版本拉回来。下次访问就是新的。

stale-if-error ​

http
Cache-Control: max-age=86400, stale-if-error=604800

源站返回 5xx 错误时,7 天内用旧副本顶上,不报错给用户。

适用场景:营销活动页、新闻详情页,宁可显示旧内容也别显示 502。

3.4 实战组合 ​

http
# HTML(永远要最新)
Cache-Control: no-cache

# 带 hash 的 JS/CSS(一年不过期)
Cache-Control: public,max-age=31536000, immutable

# CDN 加速 + 浏览器短缓存
Cache-Control: public, max-age=60, s-maxage=86400, stale-while-revalidate=300

# 私密 API(用户相关)
Cache-Control: private, no-cache

# 金融/医疗(过期一秒都不能用)
Cache-Control: no-cache, must-revalidate

四、协商缓存深度 ​

4.1 Last-Modified / If-Modified-Since ​

http
# 服务器首次响应
Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT

# 浏览器二次请求
If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT

服务器比对文件 mtime,一致则返回 304,否则 200 + 新文件。

缺陷(秒级精度):

12:00:00  编辑器保存(版本 A)
12:00:00  编辑器再保存(版本 B,mtime 还是 12:00:00)
12:00:01  编辑器再保存(版本 C,mtime 才是 12:00:01)

结果:版本 B 的修改永远不会被发现,服务器永远返回 304 给用户,新代码发不出去。

其他缺陷:

  • 文件改了但 mtime 没动(touch、git checkout、CDN 回源)→ 304 但内容已变
  • 时间戳只能精确到秒,1 秒内的修改丢
  • 没有跨语言统一哈希,文件复制后时间就变

4.2 ETag / If-None-Match ​

http
# 服务器首次响应
ETag: "abc123def"

# 浏览器二次请求
If-None-Match: "abc123def"

服务器计算资源指纹(常见:文件大小 + mtime / SHA-1 / MD5 / 弱化版本号),比对请求里的 ETag。

强 ETag vs 弱 ETag ​

http
ETag: "abc123"            # 强 ETag:字节级一致
ETag: W/"abc123"          # 弱 ETag:语义级一致
  • 强 ETag:哪怕一个字节不同,ETag 必变
  • 弱 ETag:语义相同时不要求字节一致(gzip 压缩后也算同一资源)

生成方式 ​

js
// Node.js Express
const etag = require('etag')
app.get('/app.js', (req, res) => {
  res.setHeader('ETag', etag(fileBuffer))  // 基于内容哈希
  // ...
})

// Next.js 自动
res.setHeader('ETag', generateETag(body))

// nginx 默认:文件最后修改时间 + 文件大小
# etag on;  # 开启

4.3 ETag vs Last-Modified 对比 ​

维度ETagLast-Modified
精度字节级 / 内容哈希秒级 mtime
计算成本哈希计算(略慢)读文件 stat(快)
1s 内多次修改能区分漏判
mtime 不变的修改能识别漏判
集群多节点各节点 ETag 必须一致一致
适用场景文件经常改、对一致性要求高文件极少改、追求性能

实战经验:优先 ETag,Last-Modified 作为兜底。两者都存在时,服务器优先比对 ETag(RFC 7232 规定)。

4.4 协商缓存实战 ​

js
// Express 示例
app.get('/api/user/:id', (req, res) => {
  const user = getUser(req.params.id)
  const etag = generateETag(JSON.stringify(user))
  if (req.headers['if-none-match'] === etag) {
    return res.status(304).end()  // 不带 body
  }
  res.setHeader('ETag', etag)
  res.setHeader('Cache-Control', 'private, no-cache')
  res.json(user)
})

4.5 304 vs 200 的体积差 ​

304 响应示例(从 Chrome Network 面板看到的):

HTTP/1.1 304 Not Modified
ETag: "abc123def"
Date: Wed, 21 Oct 2026 07:28:00 GMT

# body 长度为 0

200 响应:

ETag: "abc123def"

差距:1.2KB vs 0.15KB(响应头)。节省 88% 带宽。这就是为什么大列表接口一定要开 ETag。

五、缓存位置(Memory / Disk / Service Worker) ​

5.1 三层位置对比 ​

位置持久化读取速度容量谁控制关闭 Tab 后果
Service Worker Cache持久(可持久)中API 配额JS 代码不影响(独立线程)
Memory Cache不持久(进程内存)最快受限(进程大小)浏览器立即丢失
Disk Cache持久(磁盘)中大(LRU)浏览器保留

5.2 DevTools Network 面板的 Size 列 ​

观察 Network 面板每行的 Size 列,常见值:

  • from memory cache:从内存取的副本,JS/CSS 体积小、同页面内多次引用时常见;读取开销几乎为 0,关闭 Tab 立即清空
  • from disk cache:从磁盘取的副本,大文件、图片字体、刷新页面后还在;读取走磁盘 IO,通常 10ms 内
  • 资源大小:真实走网络下载的体积
  • (ServiceWorker):命中 SW 拦截,真实走 SW 缓存 API

5.3 哪些资源进 memory cache ​

经验之谈(Chrome 实现细节,版本相关):

资源类型Memory 还是 Disk?原因
体积小(几十 KB)的 JS/CSSMemory 优先进程内复用成本极低
同页面内多次引用的图片Memory 优先避免重复 IO
大 JS 文件(> 1MB)Disk占内存大,挤掉其他资源
字体文件Disk太大,常驻又不一定复用
视频Disk 或不缓存体积小,缓存收益低
跨 Tab 共享的图片Disk进程间不能共享内存

实战规律:

  • 用户点链接打开新页面 → 大量 from memory cache,首屏飞快
  • 用户刷新当前页(F5)→ memory cache 清空,大多走 disk cache
  • 用户开新 Tab(同站)→ 共享 disk cache,memory cache 不共享

5.4 Service Worker Cache(可编程式) ​

js
// sw.js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then((cache) =>
      cache.addAll(['/app.css', '/app.js'])
    )
  )
})

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request)
    })
  )
})

优势:可实现离线可用、自定义策略(Cache First / Network First / Stale While Revalidate)。

劣势:

  • 第一次注册 SW 后,旧资源全失效(必须用 hash 文件名)
  • SW 一旦出错,整个站点缓存挂掉
  • iOS Safari 支持较新版本才完善

六、Vary 头 ​

6.1 解决的问题 ​

CDN 缓存的核心假设是 URL 相同 = 响应相同。但同一 URL 可能因为请求头不同返回不同响应:

URL: /article.json
请求 A(Accept-Encoding: gzip)→ 压缩版(5KB)
请求 B(Accept-Encoding: identity)→ 原始版(20KB)

如果 CDN 把 A 缓存给 B,B 收到压缩数据但以为没压缩 → 解压出乱码

6.2 实战 Vary 头 ​

http
Vary: Accept-Encoding
Vary: Accept-Encoding, Origin
Vary: Accept-Encoding, Accept-Language

含义:响应因这些请求头不同而不同,缓存按请求头分别存储。

6.3 常见 Vary 维度 ​

维度用途典型场景
Accept-Encoding区分压缩/非压缩静态资源、API
Accept-Language区分语言国际化站点(zh/en)
Origin区分跨域CORS 接口
User-Agent区分移动/PC响应式站点(慎用,缓存爆炸)
Cookie区分登录态慎用,基本把缓存打爆

6.4 nginx 配置 ​

nginx
location ~* \.(js|css|png|jpg|svg)$ {
  gzip on;
  gzip_types text/css application/javascript;

  # 关键:告诉 CDN 按 Accept-Encoding 分桶
  add_header Vary Accept-Encoding;

  expires 1y;
  add_header Cache-Control "public, max-age=31536000, immutable";
}

实战经验:Vary: *(不可缓存) 等于告诉 CDN "这个响应永远别缓存",所有请求都回源。

6.5 CDN 配置强校验 ​

不同 CDN 对 Vary 处理不一致:

CDN默认按 Vary 分桶?配置项
Cloudflare是Vary: Accept-Encoding 自动识别
阿里云需手动开启"智能压缩" + 缓存配置
AWS CloudFront需 Cache Policy 设置Vary 字段
Fastly是Vary 直接生效

实战教训:某次 CDN 升级后默认行为改了,导致 Vary 失效,所有用户拿到 gzip 后的字节流。回滚 + 强制按 Vary 分桶才解决。

八、实战:hash 文件名 + immutable ​

8.1 为什么需要 hash ​

核心矛盾:用户浏览器里可能缓存了 1 年前的 JS,但服务器已经发版了 N 次。

如果文件名不变:

/app.js  ← 用户拿到的还是 1 年前的版本

如果文件名带 hash:

/app.abc123.js  ← 用户拿不到这个 URL,自然重新请求
/app.def456.js  ← 新版本,新 URL,命中强制缓存

8.5 HTML 必须 no-cache ​

http
# 这是错的
Cache-Control: max-age=3600

如果 HTML 也缓存 1 小时:

  • 用户拿旧 HTML
  • 旧 HTML 引用 app.abc123.js(旧 hash)
  • 服务器已经把 abc123.js 删了(发版清理旧资源)
  • 用户看到白屏

正确做法:

http
# HTML:始终去服务器验证
Cache-Control: no-cache

# JS/CSS/图片:一年不过期
Cache-Control: public, max-age=31536000, immutable

8.6 为什么是 31536000 秒 ​

365 × 24 × 60 × 60 = 31,536,000 秒。刚好一年。

这是社区共识:带 hash 的资源能缓存一年。Google、Facebook 等大厂都遵循这个数字。

理论上你可以写 max-age=999999999(超过一年),但部分实现会按"整数溢出"理解,反而出问题。一年是个安全值。

8.7 Vary 与 immutable 的冲突 ​

immutable 资源通常不需要 Vary(JS/CSS 内容由 hash 决定,不依赖请求头)。但如果你的 JS 会根据 Accept-Encoding 返回不同字节(比如源码映射),仍然需要 Vary: Accept-Encoding。

实战中为了安全,所有 gzip 启用的静态资源都加:

nginx
gzip_vary on;  # 自动加 Vary: Accept-Encoding
add_header Cache-Control "public, max-age=31536000, immutable";

10.2 案例二:CDN 没 Vary: Accept-Encoding 导致部分用户拿错数据 ​

背景:某资讯门户 CDN 加速,2024 年 3 月。

事故现象:

  • 客服收到反馈:"网页排版乱了"
  • 报错集中在 Chrome 用户
  • 其他浏览器正常

根因排查:

  1. 抓包发现,部分 Chrome 用户拿到的 CSS 是 gzip 压缩后的字节流
  2. 但 CSS 文件没有 Content-Encoding: gzip 头
  3. 浏览器以为没压缩,直接当文本解析 → 乱码

根因深挖:

  1. 源站 nginx 配置了 gzip on
  2. CDN 配置里 没有勾选"保留源站 Content-Encoding"
  3. CDN 把压缩数据当原始数据缓存了

  1. nginx 加 gzip_vary on;(自动输出 Vary: Accept-Encoding 头)
  2. CDN 强制"按 Vary 头分桶缓存"
  3. CDN 清缓存
  4. 加监控:检测资源 Content-Encoding 和 Vary 头一致性

后续改进:

  • nginx 全局开启 gzip_vary on
  • CDN 配置模板强制 Vary 头
  • CI 里加检查项:静态资源响应头必须有 Vary: Accept-Encoding

10.4 案例四:SPA 部署后部分用户白屏 ​

10.5 案例五:immutable 没生效导致每次刷新都 304 ​

背景:某 Webpack 5 项目,目标 max-age=31536000, immutable。

事故现象:

  • DevTools Network 面板每次刷新都看到 304
  • 实际应该有 200 from disk cache(0 RTT)
  • 用户体感"每次刷新都慢"

根因排查:

  1. 抓包发现响应头里 没有 immutable 字段
  2. Webpack 配置正确生成了 contenthash 文件名
  3. 但 nginx 配置在静态资源 location 里 add_header 没生效
  4. 原因——nginx 的 add_header 在 if 块里默认不继承

错误配置:

nginx
location / {
  if ($request_uri ~ "\.[a-f0-9]{8}\.(js|css)$") {
    add_header Cache-Control "public, max-age=31536000, immutable";  # 不生效
  }
  try_files /index.html;
}

修复方案:

nginx
# 方案 A:用 map(推荐)
map $request_uri $cache_control_header {
  default "no-cache";
  ~*\.[a-f0-9]{8}\.(js|css)$ "public, max-age=31536000, immutable";
}

server {
  add_header Cache-Control $cache_control_header;
}

# 方案 B:用独立 location
location ~* \.[a-f0-9]{8}\.(js|css)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

经验教训:nginx 的 add_header 在 if、limit_except 块里不继承,必须用 map 或独立 location。

14.1 Chrome 缓存决策树(伪代码) ​

简化版 Chromium 内部逻辑(基于 net/http/http_response_headers.cc):

cpp
bool ShouldUseCache(headers) {
  // 1. no-store 完全不缓存
  if (headers.Has('Cache-Control: no-store')) {
    return false;
  }

  // 2. 检查 freshness(freshness_lifetime)
  auto freshness = ComputeFreshnessLifetime(headers);
  auto age = ComputeCurrentAge(headers);

  if (age < freshness) {
    return true;  // 强缓存命中
  }

  // 3. 过期了,看 stale-while-revalidate / stale-if-error
  if (headers.Has('stale-while-revalidate')) {
    auto swr_window = ParseDuration(headers['stale-while-revalidate']);
    if (age < freshness + swr_window) {
      TriggerBackgroundRevalidation();  // 后台刷新
      return true;  // 用旧值
    }
  }

  // 4. 过期了,看 ETag/Last-Modified 做协商
  if (headers.Has('ETag') || headers.Has('Last-Modified')) {
    return false;  // 走 304 流程
  }

  // 5. 没有协商标识,直接重新下载
  return false;
}

14.2 freshness_lifetime 计算 ​

| 头 | 计算方式 | | 头 | max-age | | 头 | 优先级高于 max-age,但只对共享缓存(CDN)有效 | | 头 | Expires - Date | | 头 | 启发式(Last-Modified 时间差 × 10%) |

启发式缓存(Heuristic):

cpp
// 没有 max-age 也没有 Expires,但有 Last-Modified
// Chrome 默认按"上次修改时间到现在"的 10% 算 freshness
auto heuristic = (Date - Last-Modified) * 0.1;

这就是为什么没显式 max-age 的资源也能被缓存一会儿。

  // 2. 同页面引用次数
  if (reference_count > 1) {
    return true;  // 同页面多次引用 → memory
  }

  // 3. 是否 no-store
  if (no_store) {
    return false;
  }

  // 4. 默认 disk
  return false;
}

简化版,实际 Chrome 实现比这复杂得多(版本相关)。

14.5 Service Worker 缓存策略详解 ​

js
// 1. Cache First(适合静态 JS/CSS/字体)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request).then((response) => {
        const clone = response.clone()
        caches.open('v1').then((cache) => cache.put(event.request, clone))
        return response
      })
    })
  )
})

// 2. Network First(适合 API 数据)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request).catch(() => caches.match(event.request))
  )
})

// 3. Stale While Revalidate(适合新闻列表)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const fetchPromise = fetch(event.request).then((response) => {
        const clone = response.clone()
        caches.open('v1').then((cache) => cache.put(event.request, clone))
        return response
      })
      return cached || fetchPromise
    })
  )
})

// 4. Cache Only(纯离线)
self.addEventListener('fetch', (event) => {
  event.respondWith(caches.match(event.request))
})

// 5. Network Only(必须实时)
self.addEventListener('fetch', (event) => {
  event.respondWith(fetch(event.request))
})

14.2 缓存决策的 8 个关键问 ​

  1. 资源是否会被重复请求? 不会 → 不缓存。会 → 强缓存。
  2. 资源是否会变? 会变 → 协商缓存(ETag)。不变 → 强缓存(immutable)。
  3. 响应是否包含用户隐私? 是 → private。否 → public。
  4. 缓存对 CDN 是否合理? 合理 → public。不合理 → private。
  5. 过期后是否可用旧值? 是 → stale-while-revalidate。否 → must-revalidate。
  6. POST 还是 GET? POST → no-store。GET → 看场景。
  7. 资源是否带 hash? 带 → 一年时长。不带 → 短时长或协商缓存。
  8. CDN 缓存多久? 用 s-maxage 控制。

🎯 面试常考 ​

Q1：强缓存和协商缓存的区别?

强缓存直接用本地副本不发请求(由 Cache-Control / Expires 控制);协商缓存发请求但只带 If-None-Match / If-Modified-Since,服务端返回 304 表示用缓存。

Q2：怎么配置?

带 hash 的静态资源用 max-age=31536000, immutable;HTML 用 no-cache(仍会校验但能拿到最新)。

Q3：Cache-Control 常用指令?

max-age、s-maxage(CDN 缓存)、no-cache(可缓存但必须校验)、no-store(不缓存)、immutable、must-revalidate、stale-while-revalidate。
