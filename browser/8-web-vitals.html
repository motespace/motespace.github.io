Web Vitals:Core Web Vitals 详解、测量与实战优化 ​

Core Web Vitals(LCP / INP / CLS)是 Google 2020 年推出、2024 年全面替代 FID 的核心性能指标。本文从"是什么、怎么测、怎么优化"三段式展开,配合真实项目数字。

一、为什么 Web Vitals 这么重要 ​

1.1 它是 Google 搜索排名因子 ​

2020 年 5 月,Google 宣布 Core Web Vitals(CWV) 纳入搜索排名。2021 年 5 月,Page Experience 信号全面生效。2024 年 3 月,INP 正式取代 FID,成为新的交互指标。

SEO 圈流传一句话:"同等内容下,LCP 好的排前面。"

1.2 它是前端工程师的"必考+必做" ​

  • 面试必考:几乎所有 P5+ 前端面试都会问 LCP/CLS/INP 含义
  • 必做:项目接入 RUM 监控,数据驱动优化
  • 必报:周报/月报里没 LCP 数字,说明没在管性能

1.3 三层关系 ​

Web Vitals(Google 提出的所有性能指标,约 10+ 个)
    ↓
Core Web Vitals(2024 年官方"最重要 3 个",SEO 用)
    ├─ LCP(Largest Contentful Paint)← 加载性能
    ├─ INP(Interaction to Next Paint)← 交互性能
    └─ CLS(Cumulative Layout Shift)← 视觉稳定性
    ↓
Lab / Field 测量(Lighthouse / RUM)

二、三大核心指标详解 ​

2.1 LCP(Largest Contentful Paint) ​

含义:视口内最大可见元素的渲染时间。Google 选取"最大"是为了反映用户真正看到的主要内容。

判定:浏览器在 largest-contentful-paint PerformanceEntry 里记录。常见 LCP 元素:

元素是否算 LCP说明
<img>✅包括背景图
<svg> 内嵌✅不包括 <img src="*.svg">(要等图像解码)
<video> 封面✅视频首帧
大块文本✅一段 H1 / P 文字
<canvas>✅自己画的
background-image: url()✅通过 CSS 加载的
display: none 元素❌不可见
屏幕外元素❌视口外

阈值(Google 官方):

等级LCP含义
良好≤ 2.5 秒75% 百分位
需改进2.5 ~ 4.0 秒
差> 4.0 秒

2.2 INP(Interaction to Next Paint) ​

含义:从用户交互(点击、键盘输入)到浏览器渲染下一帧的耗时。取整个页面生命周期中最差的若干次交互(2 秒内连续交互只算 1 次)。

为什么取代 FID:FID 只测"首次输入"延迟,INP 测所有交互。SPA 时代用户点 10 次按钮,FID 只能反映第一次。

阈值:

等级INP含义
良好≤ 200 毫秒75% 百分位
需改进200 ~ 500 毫秒
差> 500 毫秒

测量范围:

事件算 INP 吗
click✅
keydown / keyup✅
pointerdown✅
touchstart✅
mousemove❌(连续事件)
scroll❌
wheel❌

2.3 CLS(Cumulative Layout Shift) ​

含义:累积布局偏移,量化页面"跳动"程度。每次意外布局变化都累计分数。

计算公式:

layout shift score = impact fraction × distance fraction

impact fraction  = 视口高度 × 视口宽度(受影响的面积)
distance fraction = 元素偏移最大距离 / 视口最大尺寸

示例:一张图加载后把文字向下挤 200px,图占视口 50% × 50% 面积:

impact fraction  = 0.5
distance fraction = 200 / 1080 ≈ 0.185
shift score = 0.5 × 0.185 = 0.0925

阈值:

等级CLS含义
良好≤ 0.175% 百分位
需改进0.1 ~ 0.25
差> 0.25

注意:用户点击导致的布局变化(如点开菜单)不算 CLS。只有"意外"才算。

三、其他关键指标 ​

指标含义阈值(良好)
FCP First Contentful Paint首次内容渲染(任何文字/图片/canvas/svg)≤ 1.8s
TTFB Time to First Byte首字节时间(服务端响应)≤ 800ms
TBT Total Blocking Time主线程被长任务阻塞的总时间≤ 200ms
TTI Time to Interactive完全可交互时间≤ 3.8s
SI Speed Index视觉填充速度(0~4.3s 视频)≤ 3.4s
LCP上面讲≤ 2.5s
INP上面讲≤ 200ms
CLS上面讲≤ 0.1

CWV 关系图:

                TTFB ≤ 800ms
                     ↓
                FCP  ≤ 1.8s
                     ↓
                LCP  ≤ 2.5s  ← CWV #1
                     ↓
                TTI  ≤ 3.8s  (Lab 指标)
                     ↓
                TBT  ≤ 200ms (Lab 指标)
                     ↓
                INP  ≤ 200ms ← CWV #2
                     ↓
                CLS  ≤ 0.1   ← CWV #3

#手段适用难度

6.3 关键 CSS 内联 + 异步加载非关键 CSS ​

html

    .hero { background: url('hero.jpg'); height: 100vh }
    .nav { ... }
  </style>
  
  <!-- 2. 非关键 CSS 异步加载(不阻塞渲染) -->
  <link rel="preload" href="main.css" as="style" onload="this.onload=null;this.rel='stylesheet'">

6.4 LCP 图片 preload + fetchpriority ​

html
<!-- LCP 图(首屏大图)提前声明 -->

<!-- LCP 图本身也要标 -->
<img src="/hero.jpg" alt="..." fetchpriority="high" width="1200" height="600">

fetchpriority="high":告诉浏览器这个资源优先级最高,会插队下载。

html

6.6 SSR vs CSR 对 LCP 的影响 ​

模式LCP 表现原因
CSR(客户端渲染)差(3~5s)HTML 是空的,要等 JS 加载+执行+请求 API+渲染
SSR(服务端渲染)中(1~2s)HTML 已包含内容,只等 hydration
SSG(静态生成)好(<1s)HTML 提前生成,CDN 分发
Streaming SSR好(0.5~1.5s)边生成边流式输出

Lighthouse 优化建议:"Use a more efficient image format" / "Eliminate render-blocking resources" / "Reduce server response times" / "Preload largest contentful paint image"。

7.3 图片宽高的两种写法 ​

html
<!-- 1. HTML 显式 width/height(推荐) -->
<img src="product.jpg" width="800" height="400" alt="商品">

<!-- 2. CSS aspect-ratio -->
<style>
.product-img {
  aspect-ratio: 2 / 1;  /* 浏览器按比例预留空间 */
  width: 100%;
  background: #f5f5f5;
}
</style>

关键:aspect-ratio 必须配合 width: 100%,否则图片按原尺寸加载,撑出布局。

7.4 字体优化:size-adjust + font-display: optional ​

css
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: optional;   /* 关键!字体 100ms 没加载完就用 fallback,不切换 */
  size-adjust: 105%;        /* 微调字宽,让 fallback 视觉接近 */
  ascent-override: 90%;
  descent-override: 22%;
  line-gap-override: 0%;
}

font-display: optional 比 swap 更激进——根本不切换,避免 CLS。代价是字体可能没生效。

8.2 INP 优化 6 手段 ​

#手段说明
1拆分长任务setTimeout(0) / scheduler.yield()
2事件回调用 transitiondocument.startViewTransition()
3减少 DOM 操作虚拟列表 / 增量渲染
4debounce / throttle 滚动事件避免高频触发
5Web Worker 跑重计算主线程只做 UI
6避免同步 XHR / localStorage用 async API

8.3 长任务拆分(最常用) ​

ts
// ❌ 一次性跑 500ms 任务
function processAll(items: any[]) {
  for (const item of items) {
    heavyProcess(item)  // 单项 5ms × 100 = 500ms
  }
}

// ✅ 用 scheduler.yield()(Chrome 129+)
async function processAllWithYield(items: any[]) {
  for (let i = 0; i < items.length; i++) {
    heavyProcess(items[i])
    if (i % 50 === 0) {
      await scheduler.yield()  // 让浏览器处理输入事件
    }
  }
}

// ✅ 降级:用 setTimeout(0) 让出主线程
async function processAllWithTimeout(items: any[]) {
  const chunks = chunkArray(items, 50)
  for (const chunk of chunks) {
    chunk.forEach(heavyProcess)
    await new Promise(r => setTimeout(r, 0))  // 让出主线程
  }
}

8.4 View Transitions API(新) ​

ts
// 用户点击切换 Tab 时,用 View Transition 平滑过渡
button.addEventListener('click', () => {
  if (document.startViewTransition) {
    document.startViewTransition(() => {
      updateUI()
    })
  } else {
    updateUI()  // 降级
  }
})

View Transition 把同步 DOM 变化变成异步动画,避免阻塞主线程,INP 直接降一档。

8.5 避免的事件回调常见坑 ​

ts
// ❌ click 回调里跑重计算
button.addEventListener('click', () => {
  heavyCalculation()  // 200ms 阻塞
  updateUI()
})

// ✅ 拆分:先更新 UI,后台算
button.addEventListener('click', async () => {
  updateUI()                  // 同步,先反馈
  await scheduler.yield()     // 让浏览器渲染
  heavyCalculation()          // 后台算
})

十、真实项目经验 ​

10.1 商户后台首屏 LCP 从 4.2s 到 1.8s ​

场景:商户后台 4.2s LCP,用户反馈"打开慢"。

根因(Lighthouse 报告):

  • 首屏 JS bundle 380KB
  • 首屏 CSS 110KB,阻塞渲染
  • LCP 是一张 banner 图,2.5MB,SSR HTML 里没 preload

修复:

  1. 关键 CSS 提取并内联(110KB → 8KB 内联,非关键用 media="print" onload="this.media='all'" 异步)
  2. JS 拆包:路由懒加载 + vendor 拆分(380KB → 首屏 95KB)
  3. LCP 图:<link rel="preload" as="image" fetchpriority="high"> + 压缩到 180KB WebP
  4. 字体:<link rel="preload" as="font" crossorigin> + font-display: swap
  5. 加 HTTP/2 + Brotli 压缩

结果:

指标优化前优化后提升
LCP4.2s1.8s-57%
FCP2.1s0.9s-57%
TBT680ms120ms-82%
Lighthouse 性能分5292+40

10.2 会员 H5 商品列表 CLS 0.25 → 0.05 ​

场景:会员 H5 商品列表,CLS 0.25,远超阈值,体验差。

根因:商品图片没指定宽高,加载完后整列"抖一下"。

修复:

  1. 给所有 <img> 加 width="200" height="200"
  2. 列表项容器用 aspect-ratio: 1 / 1
  3. 字体切换用 font-display: optional 避免 fallback → 主字体跳动
  4. 顶部 banner 用 min-height: 120px 占位

结果:

指标优化前优化后
CLS0.250.05
Lighthouse 性能分7896
用户反馈"页面跳"经常0

10.3 移动端 H5 商品搜索 INP 800ms → 90ms ​

场景:用户输入搜索关键词,每按一个键卡 800ms,INP 远超 200ms 阈值。

根因:

  • input 事件同步发起 4 个 fetch(联想词 / 历史 / 推荐 / 商品)
  • 每次输入都跑 200ms 数据处理
  • DOM 一次性插入 200+ 节点

修复:

  1. debounce 300ms:避免每个键击触发
  2. fetch 并行 + AbortController:取消上一次未完成请求
  3. web worker 处理数据:主线程不卡
  4. 虚拟列表:200 节点 → 屏内 20 节点
  5. input 回调里先更新 UI(同步),后台算数据

结果:

指标优化前优化后
INP(键击→反馈)800ms90ms
用户感知"卡"明显流畅
服务端 QPS高(无效请求)-60%

十二、面试回答模板 ​

30 秒版 ​

Core Web Vitals 是 Google 2020 年推出的核心性能指标,2024 年由 LCP(最大内容渲染)、INP(交互到下一帧)、CLS(累积布局偏移)三个组成。LCP ≤ 2.5s 反映加载,INP ≤ 200ms 反映交互,CLS ≤ 0.1 反映视觉稳定。生产用 web-vitals 库 + sendBeacon 上报,自家 RUM 监控 P75 百分位。

90 秒版 ​

Web Vitals 是 Google 提出的用户体验量化指标,Core Web Vitals 是其中最重要的 3 个,2024 年由 LCP / INP / CLS 组成(取代了 FID)。

  • LCP(Largest Contentful Paint)反映加载性能,目标是 ≤ 2.5s,常见 LCP 元素是大图或大段文字。优化手段有:关键 CSS 内联、LCP 图片 preload + fetchpriority、SSR 替代 CSR。
  • INP(Interaction to Next Paint)反映交互,目标是 ≤ 200ms。优化手段有:拆分长任务(scheduler.yield())、事件回调里先更新 UI 后台算、用 Web Worker。
  • CLS(Cumulative Layout Shift)反映视觉稳定,目标是 ≤ 0.1。优化手段有:图片显式 width/height、字体 font-display: optional、预留动态内容空间。

生产用 web-vitals 库 + navigator.sendBeacon 上报,聚合到自家监控,看 P75 百分位。CI 用 lighthouse-ci 和 size-limit 卡性能预算。

常见追问 ​

  • Q: LCP 元素是图片,但图片 lazy load,会算 LCP 吗? A: 不会。LCP 只算"渲染到视口内"的元素。lazy load 还没加载的图不是 LCP。如果你想让首屏 banner 是 LCP,不要 lazy load。
  • Q: INP 200ms 内一定好吗? A: 不一定。要看 P75 百分位。如果 5% 用户 500ms,那 75% 都可能是 200ms,符合阈值,但仍有 5% 体验差。
  • Q: CLS 0.05 算差吗? A: 0.05 < 0.1,算良好。但 CLS 是累加的,连续多次小偏移也会"晋级"成差。
  • Q: 怎么在本地看真实 LCP 元素? A: DevTools → Performance → 录制,找"LCP"标记,或用 PerformanceObserver + largest-contentful-paint 拿 entry.element。
