网络面试高频 Q&A ​

一、HTTP 基础 ​

Q1:HTTP 和 HTTPS 的区别? ​

答:

HTTP:明文传输,80 端口
HTTPS:HTTP + TLS 加密,443 端口

HTTPS 在 HTTP 基础上加:

  • TLS 握手(身份认证 + 密钥交换)
  • 数据加密(防窃听)
  • 数据完整性校验(防篡改)
  • 数字证书(防中间人)

Q2:HTTPS 握手过程? ​

答:

TLS 1.2 (2-RTT):
1. ClientHello → 服务端
   (支持的协议版本、加密套件、随机数)
2. ServerHello + Certificate + ServerHelloDone
   (选定协议、套件、服务端证书)
3. ClientKeyExchange + ChangeCipherSpec + Finished
   (用证书公钥加密 pre-master secret)
4. 服务端 ChangeCipherSpec + Finished
   (解密 pre-master,生成 master key)

TLS 1.3 (1-RTT):
1. ClientHello + key_share
2. ServerHello + Certificate + Finished + key_share
   (服务端可以提前算好证书)
3. Client Finished

Q3:HTTP/1.1 的队头阻塞? ​

答: HTTP/1.1 一个 TCP 连接上一个请求-响应完成后才能发下一个。即使浏览器开 6 个连接,也只是缓解。

HTTP/2 多路复用:一个 TCP 连接上多流,流内仍可能有队头阻塞(TCP 层丢包)。 HTTP/3 / QUIC:独立的流,一个流丢包不影响其他流。

Q4:HTTP/2 vs HTTP/1.1 改进? ​

答:

  1. 二进制分帧:代替文本协议
  2. 多路复用:单连接并行多请求
  3. 头部压缩:HPACK 算法
  4. 服务器推送:已弃用(实际很少用)
  5. 流量优先级:高优先级帧先发

Q5:HTTP/3 基于什么?为什么? ​

答:QUIC(基于 UDP)。

  • 解决 TCP 队头阻塞
  • 0-RTT 握手(更快)
  • 内置 TLS 1.3
  • 连接迁移(WiFi 切 4G 不重连)

二、缓存 ​

Q6:强缓存 vs 协商缓存? ​

答:

强缓存:
  不发请求,直接用本地缓存
  Cache-Control: max-age=3600
  
协商缓存:
  发请求,服务端判断是否过期
  命中:返回 304 Not Modified,用本地缓存
  Cache-Control: no-cache

Q7:Cache-Control 常用值? ​

答:

max-age=N    缓存 N 秒
no-cache     缓存但需要重新验证
no-store     不缓存
public       任何地方都能缓存(CDN)
private      只能浏览器缓存
immutable    内容永不变(强缓存 + 不重新验证)
must-revalidate 过期必须重新验证

Q8:ETag vs Last-Modified? ​

答:

Last-Modified:
  - 服务端返回资源最后修改时间
  - 客户端下次带 If-Modified-Since
  - 缺点:秒级精度,文件改了时间可能不变

ETag:
  - 服务端返回资源指纹(hash)
  - 客户端下次带 If-None-Match
  - 更精确(基于内容)
  - 计算有开销

实战:两者都用,服务端优先判断 ETag

三、跨域与安全 ​

Q9:CORS 简单请求 vs 预检? ​

答:

简单请求(直接发):
  - GET / POST(无自定义头)
  - Content-Type: text/plain / multipart/form-data / application/x-www-form-urlencoded
  - 不触发预检

预检请求(先发 OPTIONS):
  - PUT / DELETE / PATCH
  - 自定义 Header(如 X-Token)
  - application/json
  - 检查服务器是否允许

Q10:CORS 关键 Header? ​

答:

请求:
  Origin: https://yoursite.com
  
响应:
  Access-Control-Allow-Origin: https://yoursite.com  (不能用 *)
  Access-Control-Allow-Credentials: true             (允许 Cookie)
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
  Access-Control-Allow-Headers: Content-Type, Authorization
  Access-Control-Max-Age: 86400                      (缓存预检结果)
  Vary: Origin                                         (重要!)

Q11:SameSite 三个值? ​

答:

Strict:
  - 跨域任何请求都不带 cookie
  - 最严格,适用于支付、修改密码

Lax(现代默认):
  - 跨域 GET 带 cookie,POST 不带
  - 平衡:防 CSRF 表单,允许普通链接

None:
  - 跨域都带
  - 必须配合 Secure
  - 用于嵌入场景(第三方 iframe)

Q12:CSRF 防御? ​

答:

  1. SameSite Cookie(浏览器级)
  2. CSRF Token(请求级,每次表单带)
  3. Referer / Origin 验证(辅助)
  4. 关键操作二次验证(密码、短信)

四、TCP / UDP ​

Q13:TCP 三次握手? ​

答:

1. 客户端 → SYN → 服务端
2. 服务端 → SYN + ACK → 客户端
3. 客户端 → ACK → 服务端

为什么三次?
  - 双方确认收发能力
  - 两次不够:服务端不知道客户端能收到响应

Q14:TCP 四次挥手? ​

答:

1. 客户端 → FIN → 服务端(我要关了)
2. 服务端 → ACK → 客户端(收到)
3. 服务端 → FIN → 客户端(我也关了)
4. 客户端 → ACK → 服务端(收到)

为什么四次?
  - TCP 全双工,两边都要关
  - 服务端收到 FIN 后可能还有数据要发

Q15:TCP 怎么保证可靠? ​

答:

  • 序号(Sequence Number):包有编号,接收方按序组装
  • ACK + 重传:接收方确认,丢失重传
  • 滑动窗口:流量控制
  • 拥塞控制:慢启动、拥塞避免(Cubic、BBR)

Q16:TCP vs UDP? ​

答:

TCP:可靠、顺序、流量控制、拥塞控制,慢(握手、确认)
UDP:不可靠、无顺序、无控制,快(无握手)

适用:
  TCP - HTTP/HTTPS/WebSocket/SSH/FTP
  UDP - DNS/直播/WebRTC/QUIC

五、DNS ​

Q17:DNS 解析过程? ​

答:

1. 浏览器缓存
2. 系统缓存(操作系统)
3. hosts 文件
4. 本地 DNS(LDNS)
5. 根 DNS → TLD DNS → 权威 DNS
6. 返回 IP,缓存回客户端

Q18:DoH / DoT 是什么? ​

答:

  • DoH(DNS over HTTPS):DNS 查询用 HTTPS 加密(端口 443)
  • DoT(DNS over TLS):DNS 查询用 TLS 加密(端口 853)
  • 防止运营商/防火墙劫持、监听 DNS 查询

六、WebSocket ​

Q19:WebSocket vs HTTP? ​

答:

WebSocket:
  - 一次握手,长期连接
  - 全双工
  - 头部 2~14 字节
  - 适合实时通信

HTTP:
  - 每次请求-响应
  - 单向(除非轮询)
  - 头部几百~几 KB
  - 适合一次性请求

Q20:WebSocket 心跳? ​

答:

  • WebSocket 长连接会被 NAT / 防火墙静默断开
  • 客户端定期发 Ping(或者业务消息)
  • 服务端响应
  • 30 秒一次是常见频率
  • 断开后自动重连(指数退避)

七、性能优化 ​

Q21:首屏优化有哪些? ​

答:

网络层:
- HTTP/2 / HTTP/3
- Brotli 压缩
- CDN
- preconnect / dns-prefetch / preload

资源层:
- 关键 CSS 内联
- 图片懒加载 + 显式宽高
- 字体 font-display: swap
- 路由懒加载

渲染层:
- SSR / SSG / Streaming
- Suspense 边界
- 骨架屏

JS 层:
- 路由拆包
- 按需引入
- tree-shaking

Q22:为什么 HTTP/2 后不需要雪碧图? ​

答: HTTP/2 多路复用,一个连接能并行下载多个小文件。雪碧图反而:

  • 增加 HTTP 缓存复杂度
  • 不能单独失效(改一个像素整个 sprite 失效)
  • 维护成本高

HTTP/2 时代:细颗粒度资源更优。

Q23:HTTPS 比 HTTP 慢多少? ​

答:

  • 现代 CPU 有 AES-NI 指令集,加密开销 < 1%
  • TLS 1.3 1-RTT 握手(相比 TLS 1.2 2-RTT)
  • HTTP/2 强制 HTTPS,反而比 HTTP/1.1 快(多路复用)
  • 实际:几乎无性能差距

八、综合题 ​

Q24:输入 URL 到页面渲染经历了什么? ​

答:

1. URL 解析
2. DNS 解析 → IP
3. TCP 连接(三次握手)
4. TLS 握手(HTTPS)
5. HTTP 请求
6. 服务器响应
7. 浏览器解析 HTML → DOM 树
8. 解析 CSS → CSSOM
9. 合并 → Render Tree
10. 布局(Layout)
11. 绘制(Paint)
12. 合成(Composite)
13. 显示

Q25:从 network 优化角度如何优化? ​

答:

  1. 减少请求数:合并、雪碧图、删除冗余
  2. 减小请求体积:压缩(gzip/Brotli)、图片优化、tree-shaking
  3. 缓存:强缓存、协商缓存、Service Worker
  4. 协议优化:HTTP/2、HTTP/3、TLS 1.3
  5. 就近访问:CDN、Anycast
  6. 预测加载:prefetch、preload

Q26:跨域方案对比? ​

答:

方案适用限制
CORS现代 API 跨域复杂请求需预检
JSONP老 API(GET)仅 GET,难维护
postMessageiframe 跨域需校验 origin
Nginx 反代老项目快速解决单点
CORS Anywhere开发临时用生产不安全

Q27:TCP 三次握手中可以携带数据吗? ​

答:

  • 第三次 ACK 可以携带数据(此时客户端已确认能收到)
  • 前两次不能(防止攻击)

Q28:HTTPS 一定安全吗? ​

答:不一定。

  • HTTPS 只防传输层窃听/篡改
  • 应用层漏洞(XSS、CSRF、SQL 注入)HTTPS 防不了
  • 用户主动忽略证书警告
  • 自签名证书滥用

安全是纵深防御:HTTPS + CSP + 输入验证 + 鉴权。
