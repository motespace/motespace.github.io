Q1：完整 HTTP 请求流程是怎样的?

Section titled “Q1：完整 HTTP 请求流程是怎样的?”
  1. DNS 解析:浏览器缓存 → 系统缓存 → 递归 DNS → 根 → TLD → 权威,拿到 IP
  2. TCP 三次握手:确认收发能力、交换 ISN
  3. TLS 握手(HTTPS):验证证书链与域名、协商会话密钥(TLS 1.3 是 1-RTT)
  4. HTTP 请求/响应:报文按 HTTP 格式收发
  5. 服务端处理 → 返回响应(可能命中 CDN 或服务端缓存)
  6. 浏览器解析渲染:HTML → DOM、CSS → CSSOM → Render Tree → Layout → Paint → Composite

排障切入点:用 DevTools Network 面板的 Timing 拆成 Queueing / Stalled / DNS / Initial connection / SSL / Request sent / Waiting(TTFB) / Content Download。

Q2：Token 刷新时多个请求同时 401 怎么办?

Section titled “Q2：Token 刷新时多个请求同时 401 怎么办?”

用单例 Promise 合并刷新。多个并发请求都发现 token 过期时, 只让第一个真正去刷新,其余等它的结果:

不做合并的后果:10 个并发请求 → 10 次刷新 → 后端把前 9 个 refresh token 都作废了 (轮换机制下每个 token 只能用一次),最后谁都拿不到新 token。

配套:并发场景下后端要允许 refresh token 有短暂的重用窗口,或者用 「旧 token 也能换一次」的宽松策略。

Q3：请求重复提交怎么防?

Section titled “Q3：请求重复提交怎么防?”

分两层:

  1. 前端:按钮 loading + disabled,useRef 标志位防连点
  2. 后端:幂等键(idempotency key)—— 客户端为一次「业务操作」生成唯一 ID, 请求带上,后端用 用户ID + 幂等键 做唯一约束,重复请求直接返回首次的结果

只有前端防是不够的:网络重试、用户刷新页面、多端登录都会绕过前端。

📝 小结

Section titled “📝 小结”
  • 完整的 HTTP 流程要能按顺序讲出来:DNS → TCP → TLS → HTTP → 缓存策略 → 错误处理。
  • HttpClient 的核心职责:统一错误码映射、Token 注入与刷新、重复请求取消、并发去重。
  • Token 刷新要用单例 Promise 合并并发请求,否则多个 401 会同时触发刷新,互相把对方的 refresh token 作废。
  • 网络层优化的顺序:先看 TTFB(服务端),再看 Resource Timing 找慢资源,最后才动前端。
