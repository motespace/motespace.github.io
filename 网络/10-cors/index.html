🎯 面试常考

Section titled “🎯 面试常考”

Q1：CORS 解决了什么问题?为什么它是浏览器强制的?

Section titled “Q1：CORS 解决了什么问题?为什么它是浏览器强制的?”

CORS(跨源资源共享)让服务器显式声明哪些源可以跨域读它的响应。

为什么是浏览器强制:同源策略是浏览器的安全边界,防止恶意网站读你的银行页面。 CORS 是这个边界的「开口」——服务器说「我这个接口允许 https://a.com 读」,浏览器才放行响应给 JS。

关键:CORS 只管读取。跨域的请求照样会发出去、照样会有副作用。 这就是 CSRF 必须单独防的原因。

Q2：简单请求和预检请求的区别?什么会触发预检?

Section titled “Q2：简单请求和预检请求的区别?什么会触发预检?”

简单请求同时满足三个条件:方法 ∈ {GET, HEAD, POST}、只含 CORS 安全列表头 (Accept、Content-Type 等)、Content-Type ∈ {application/x-www-form-urlencoded, multipart/form-data, text/plain}。

→ 浏览器直接发请求,响应回来后再检查响应头允不允许读。

预检(preflight):不满足上述条件时,浏览器先发一个 OPTIONS 请求问服务器 「我准备发个 PUT、带 X-Token 头,行不行?」,服务器同意(200 + Access-Control-Allow-*)才发真正的请求。

常见的触发预检:JSON(application/json)、PUT/DELETE/PATCH、自定义头、Authorization 头。

Q3：带 Cookie 的跨域要注意什么?

Section titled “Q3：带 Cookie 的跨域要注意什么?”

两个坑,都会让请求失败:

  1. Access-Control-Allow-Origin 不能是 *,带凭证时必须写具体源 并且要加 Access-Control-Allow-Credentials: true
  2. 源必须完全一致,包括协议、端口。https://a.com 和 https://a.com:443 是同一个, 但 http://a.com 不是。前端 fetch 的 mode: 'cors' + credentials: 'include'

另一个坑:服务端读 Origin 头时如果拼错了(多了个斜杠),返回的 Access-Control-Allow-Origin 和请求的 Origin 不一致,浏览器直接拒绝—— 但报错信息很模糊,只在 Console 里说 CORS error,不看 Network 面板很难定位。

Q4：CORS 能防 CSRF 吗?

Section titled “Q4：CORS 能防 CSRF 吗?”

不能。

CORS 限制的是「能不能读响应」,CSRF 利用的是「副作用已经发生」。 跨域表单提交是简单请求,不需要预检,浏览器照样发出去。

区别:

  • CSRF:攻击者诱导浏览器带着你的 Cookie 发请求 → 需要 SameSite / Token / Origin 校验来防
  • CORS:控制谁能读响应 → 防的是「恶意网站偷你的数据」

两者防护目标不同,不能互相替代。

📝 小结

Section titled “📝 小结”
  • CORS 是服务器声明「哪些源能读我的响应」,由浏览器强制执行。
  • 简单请求直接发、非简单请求先发 OPTIONS 预检;JSON / PUT / DELETE / 自定义头都会触发预检。
  • 带 Cookie 时 Allow-Origin 不能是 *,必须是精确的源,且要加 Allow-Credentials。
  • CORS 防的是「偷数据」,CSRF 防的是「发副作用」,两者不能互相替代。
