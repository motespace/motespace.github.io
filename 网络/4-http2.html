HTTP/2 机制:分帧、多路复用与 HPACK ​

这一篇只讲 HTTP/2 自己的机制:它怎么在一条 TCP 连接上并行跑多个请求。

相邻专题:

  • 演进全景(为什么需要 HTTP/2)→ HTTP 协议演进
  • 队头阻塞的由来与浏览器端的绕行手段 → HTTP/1.1 队头阻塞与绕行手段
  • HTTP/3 与 QUIC → HTTP/3 与 QUIC 深度

一、HTTP/2 到底改了什么 ​

一句话:方法、状态码、头字段的语义完全不变,变的只是传输格式。

HTTP/2 传的还是「文本语义」的内容(JSON、HTML、图片都行),和 HTTP/1.1 一样。改动集中在传输层:

改进解决的问题
二进制分帧文本协议解析慢、无法表达「哪个片段属于哪个请求」
多路复用一条连接上并行跑几十上百个流,不需要浏览器多开连接
头部压缩(HPACK)每次请求都带完整头,重复头浪费带宽
流优先级 / 服务器推送让关键资源优先传输(推送已被弃用)

HTTP/1.1 时代的绕行手段(6 连接、域名分片、雪碧图、内联)为什么会被废弃,见 3-http1-problems。

二、二进制分帧(Binary Framing) ​

2.1 帧结构 ​

HTTP/1.1 是文本报文,靠 \r\n 分隔;HTTP/2 把每个请求/响应拆成帧(frame),每帧有固定的 9 字节头:

+-----------------------------------------------+
| Length(24) | Type(8) | Flags(8) | Stream ID(32) |
+-----------------------------------------------+
| Payload (可变长度)                            |
+-----------------------------------------------+
字段长度含义
Length24 bitpayload 长度(最大 16MB)
Type8 bit帧类型(DATA / HEADERS / SETTINGS / RST_STREAM / WINDOW_UPDATE ...)
Flags8 bit依赖类型的标志位(如 END_STREAM、END_HEADERS、ACK)
Stream ID32 bit流标识,最高位保留,值为奇数(客户端发起的流)

2.2 为什么要二进制 ​

HTTP/1.1:
  ┌────────────┐
  │ Request 1  │  ← 文本格式，靠 \r\n 切分
  └────────────┘
  ┌────────────┐
  │ Request 2  │
  └────────────┘

HTTP/2:
  ┌─────┐ ┌─────┐ ┌─────┐
  │帧1-1│ │帧1-2│ │帧2-1│  ← 二进制帧，可交错
  └─────┘ └─────┘ └─────┘
  同一个 TCP 连接，并行传输

三个好处:

  1. 解析快:固定长度头部,不需要扫描分隔符
  2. 能表达归属:Stream ID 让接收方知道这一帧属于哪个请求——这是乱序传输的前提
  3. 能承载控制信息:SETTINGS、WINDOW_UPDATE、RST_STREAM 这些帧在 HTTP/1.1 里根本没有对应物

2.3 常见帧类型 ​

帧类型作用
DATA传输请求/响应体
HEADERS传输请求/响应头(HPACK 压缩后)
SETTINGS双方协商连接参数(初始窗口大小、最大帧大小等)
WINDOW_UPDATE流控:告知对方「我还能接收多少字节」
RST_STREAM立即终止某个流
PING保活与 RTT 探测
PRIORITY设置流优先级(已废弃,见第五节)

三、多路复用(Multiplexing) ​

3.1 流与流 ID ​

  • 一个 HTTP/2 连接上有多个流(stream),每个流承载一个独立的请求/响应
  • 每个流有唯一 ID,客户端发起的流用奇数 ID(1、3、5、7...),服务端发起的用偶数
  • 单个连接上可同时存在几十到上百个活跃流(HTTP/1.1 同一域名只有 6 条连接)

3.2 乱序发送、按 ID 重组 ​

客户端                                服务端
   |  Stream 1 帧 (请求 A)          |
   |  ───────────────────────────→ |
   |  Stream 3 帧 (请求 B)          |
   |  ───────────────────────────→ |
   |                                |  处理 A(慢) + 处理 B(快)
   |  Stream 3 帧 (响应 B)         |
   |  ←─────────────────────────── |
   |  Stream 1 帧 (响应 A)         |
   |  ←─────────────────────────── |

关键:不再有「队」的概念。响应 B 可以先于响应 A 到达,由 Stream ID 把它交给正确的上层。

3.3 流的生命周期 ​

idle ──(HEADERS)──→ open ──(END_STREAM)──→ half-closed(remote) ──→ closed
  • idle:流被创建但还没用
  • open:双向都可以传
  • half-closed(local):本端发完了,还能收
  • half-closed(remote):对端发完了
  • closed:双向都结束

一个请求用完的流 ID 不能复用,这是 HTTP/2 与 HTTP/1.1 keep-alive 复用连接的根本差异。

3.4 流量控制 ​

HTTP/2 有两级窗口:

  • 连接级窗口:整个连接还能收多少字节
  • 流级窗口:某一条流还能收多少字节

接收方通过 WINDOW_UPDATE 帧给发送方「发粮」;发送方发出的字节数超过窗口就必须停下等。

这解决了一个 HTTP/1.1 没有的问题:HTTP/1.1 里,一个慢速下载的大文件会占满整条 TCP 连接,把同连接上的其他请求一起拖死。HTTP/2 的流级窗口让每条流各管各的。

四、头部压缩(HPACK) ​

HTTP/1.x 每次请求都带完整头(几百字节到几 KB),而实际请求之间大量头是重复的。

HPACK 的做法是表 + 索引:

4.1 静态表与动态表 ​

  • 静态表:61 个常用头字段(name + value)预先约定好,直接用索引
  • 动态表:连接期间双方各自维护一张表,新出现的头按「先进先出」追加,超过上限就淘汰最老的

4.2 编码方式 ​

HTTP/1.1:每次都带完整 header
GET /api/users HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 ...
Accept: */*
Cookie: session=abc123 ...

HTTP/2:重复头只发索引
:authority  → 索引 1
:method GET → 索引 2
:path /api/users → 索引 4
user-agent → 动态表索引 58

两种编码:

  • 索引编码:表里有的,发一个索引号(1~2 字节)
  • 字面量编码:表里没有的,发「名字 + 值」(值可以选用 Huffman 编码再压缩)

4.3 效果与注意 ​

  • 头部体积通常能减少 80%~90%
  • 敏感头不进动态表:因为动态表在连接内共享且带索引,明文下极易被攻击者推断内容(这也是 HTTP/2 强制 TLS 的原因之一)
  • 动态表大小每个连接独立,所以连接复用率越高,压缩效果越好

五、流优先级与服务器推送 ​

5.1 优先级 ​

可以给不同流设置不同的传输权重,让关键资源(如 LCP 图片)优先发送。

现状:HTTP/2 的优先级机制(PRIORITY 帧)已被废弃,因为实际效果不理想且实现复杂。现在判断优先级主要靠浏览器的资源加载启发式 + rel=preload 显式声明。

5.2 Server Push 为什么被废弃 ​

Server Push 让服务端在响应某个资源时主动推送关联资源(如 JS/CSS),省掉客户端再发请求。

废弃原因:

  1. 预测不准:服务端猜错了要推什么,反而浪费带宽
  2. 优先级冲突:浏览器自己判断资源优先级更准(比如首屏 LCP 图片)
  3. 实现复杂:要维护推送队列、要处理重复推送

替代方案:用 <link rel="preload"> / rel="prefetch"> / rel="modulepreload"> 显式声明意图,浏览器在正确时机加载。这才是现在推荐的做法。

六、为什么 HTTP/2 强制要求 TLS ​

HTTP/1.1 可以跑在明文 TCP 上(所以有 http://),HTTP/2 强制要求 TLS(即 h2,明文的 h2c 几乎没人用)。

原因都是安全:

  • 多路复用放大风险:所有请求走一条连接,任何中间人篡改一条流就能影响整条连接
  • HPACK 动态表泄露:动态表在连接内共享,明文下极易被推断出访问了哪些站点与携带了什么信息
  • 请求走私(CL/TE 混淆):伪头设计需要严格的长度校验来防止走私攻击

协商方式:HTTP/2 不是运行时 Upgrade 出来的,而是通过 TLS ALPN 协商——ClientHello 里带 ALPN: h2, http/1.1,服务端在 ServerHello 里回 ALPN: h2。 细节见 内容压缩与 ALPN。

七、实战:HTTP/2 配置 ​

7.1 Nginx ​

nginx
server {
  listen 443 ssl http2;
  ssl_certificate     /path/to/cert.pem;
  ssl_certificate_key /path/to/cert.key;

  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256;
  ssl_prefer_server_ciphers on;
}

新版 Nginx(1.25.1+)推荐写成 listen 443 ssl; + http2 on;,老写法 listen 443 ssl http2; 仍可用但会有 deprecation 警告。

7.2 应用层 ​

js
// Next.js / Node 服务通常自动支持 HTTP/2:
// 前面挂 Nginx / 云负载均衡启用 http2 即可,应用无需改动

7.3 怎么确认真的用上了 HTTP/2 ​

浏览器 DevTools → Network → 右键表头 → Protocol 列:

  • 显示 h2 → HTTP/2
  • 显示 http/1.1 → 还在用 HTTP/1.1

命令行:

bash
curl -I --http2 https://example.com

Chrome 内部页 chrome://net-internals/#http2 能看到所有 HTTP/2 会话的详情。

🎯 面试常考 ​

Q1:HTTP/2 到底改了哪四件事? ​

  1. 二进制分帧:每帧 9 字节头(length 3 + type 1 + flags 1 + streamId 4),取代 HTTP/1.1 的 \r\n 文本分隔
  2. 多路复用:一个连接上多个 stream 并行,HTTP 层没有队头阻塞
  3. 头部压缩(HPACK):静态表(61 项)+ 动态表,重复头只发索引,通常能压掉 80~90%
  4. 流优先级 / 服务器推送:优先级机制已废弃,推送已被 Chrome 弃用,改用 rel=preload

注意:HTTP/2 传的还是「文本语义」的内容(JSON、HTML、图片都行),和 HTTP/1.1 完全一样,变的只是传输格式。

Q2:HTTP/2 的队头阻塞解决了吗? ​

只解决了一半,而且是最关键的那一半。

  • HTTP 层:解决了。多路复用让一个慢请求不再阻塞其他 stream
  • TCP 层:没解决。TCP 是字节流,分段传输,丢一个 TCP 段后面所有字节都得等它重传,所有 stream 一起卡住——哪怕它们的数据本身完好

这就是 HTTP/3 换 QUIC(基于 UDP)的动机:让每条 stream 独立重传。

应用层与传输层队头阻塞的完整辨析见 3-http1-problems 的 2.3 节。

加分表述:「HTTP/2 解决了应用层的队头阻塞,HTTP/3 解决了传输层的队头阻塞。」

Q3:为什么 HTTP/2 需要 TLS?HTTP/1.1 需要吗? ​

HTTP/1.1 可以跑明文 TCP(所以有 http://),也可以跑 TLS。

HTTP/2 强制要求 TLS,原因是安全而非性能:

  • 多路复用让所有请求走一条连接,任何中间人篡改一条流就能影响整条连接
  • HPACK 动态表在连接内共享,明文下极易被攻击者推断内容
  • 伪头设计需要防止请求走私(CL/TE 混淆)

浏览器只支持 https:// 的 h2,明文 h2c 几乎没人用。协商靠 TLS ALPN,不是运行时 Upgrade。

Q4:Server Push 是什么?为什么被废弃了? ​

服务端在响应某个资源时,主动把关联资源(如 JS/CSS)一并推给客户端,省掉客户端再发请求。

废弃原因:

  1. 预测不准:服务端猜错了要推什么,反而浪费带宽
  2. 优先级冲突:浏览器自己判断资源优先级更准(比如首屏 LCP 图片)
  3. 实现复杂:要维护推送队列、要处理重复推送

替代方案:用 <link rel="preload"> / rel="prefetch"> / rel="modulepreload"> 显式声明意图。

Q5:HTTP/2 的流 ID 是怎么用的? ​

每个流有唯一 ID,客户端发起的流用奇数 ID,服务端发起的用偶数。帧头里带 Stream ID,接收方据此把乱序到达的帧重组回各自的流——这正是多路复用能实现的前提。一个连接上最多 2^31 条流,但同时活跃的一般只有几十条。

📝 小结 ​

  • HTTP/2 换了传输格式没换语义:二进制分帧(9 字节头 + Stream ID)、多路复用(乱序发送按 ID 重组)、HPACK(静态表 + 动态表,省 80~90% 头部)、流优先级。
  • 帧是 HTTP/2 的基础抽象:DATA / HEADERS / SETTINGS / WINDOW_UPDATE / RST_STREAM 各自承载不同职责,HTTP/1.1 里没有对应物。
  • 多路复用带来两个新东西:流状态机(流 ID 不可复用)与两级流控(连接级 + 流级窗口),后者解决了「一个大文件拖死整条连接」。
  • 队头阻塞只解决了一半:HTTP 层解决了,TCP 层的要靠 HTTP/3 的 QUIC。
  • HTTP/2 强制 TLS(多路复用放大风险 + HPACK 动态表泄露 + 防请求走私),通过 ALPN 协商而非 Upgrade;Server Push 已被废弃,改用 rel=preload/prefetch。
  • 上线后先确认真的用上了:DevTools 的 Protocol 列应显示 h2。
