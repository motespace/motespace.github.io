DNS 解析流程与优化

一、为什么需要 DNS

Section titled “一、为什么需要 DNS”

人类记不住 IP 地址(203.0.113.42),但记得住域名(example.com)。

DNS(Domain Name System)就是域名 → IP 的翻译系统——互联网的“电话簿”。

二、域名的层级结构

Section titled “二、域名的层级结构”

完整域名(FQDN):www.example.com.(末尾有点表示根)

三、DNS 解析完整流程

Section titled “三、DNS 解析完整流程”

浏览器输入 https://www.example.com,实际是 IP 之前,要先解析:

总耗时:

  • 缓存命中:< 1ms
  • 缓存未命中:20~200ms(取决于递归查询)
  • 跨网查询:几百 ms

面试常考点:

1. 递归 vs 迭代查询

  • 客户端 → LDNS 是递归(LDNS 帮客户端问到底,客户端只发一次)
  • LDNS → 根 → TLD → 权威 是迭代(每层只告诉 LDNS 去问下一级,不亲自问)

2. 为什么需要这么多层?

  • 分级缓存,根 DNS 不必承载所有查询压力(全球每天万亿次 DNS 查询)
  • 任何一级失效,都不会全局瘫痪

3. 前端优化点

  • DNS 预解析:<link rel=“dns-prefetch” href=“//example.com”>`n- 减少不同域名的数量(每个新域名都要 DNS 查询)
  • 长连接 + HTTP/2 多路复用

🎯 面试常考

Section titled “🎯 面试常考”

Q1：DNS 解析的完整流程?为什么第一次慢第二次快?

Section titled “Q1：DNS 解析的完整流程?为什么第一次慢第二次快?”

以访问 www.example.com 为例:

  1. 浏览器缓存:查 Chrome 的 DNS 缓存(有 TTL)
  2. 操作系统缓存:查 hosts 文件、/etc/resolv.conf 指向的本机 DNS 缓存
  3. 本地 DNS 服务器(递归解析器,一般是运营商/公司内网):
    • 查根 DNS:. → 拿到 TLD 服务器地址
    • 查 TLD 服务器(如 .com)→ 拿到该域名的权威 DNS 地址
    • 查权威 DNS(example.com 的 NS)→ 拿到目标 IP
    • 权威服务器返回带 TTL 的记录,递归器缓存后返回给客户端
  4. 浏览器拿到 IP,发起 TCP/TLS/HTTP

第二次快:记录被缓存在递归器和浏览器里,TTL 内直接命中。

注意:递归 DNS 和迭代 DNS 是两种模式 —— 客户端→递归器是递归查询 (递归器替你问到底),递归器→各级 DNS 是迭代查询(每次只问一步,拿下一步的地址)。

Q2：TTL 怎么选?太长太短分别有什么问题?

Section titled “Q2：TTL 怎么选?太长太短分别有什么问题?”

TTL 是这条记录可以被缓存多久。

  • 太长(比如 24h):DNS 变更后,很多客户端要等很久才能拿到新 IP, 表现为「域名换了服务器,有的用户还是老 IP」,排查时很痛苦
  • 太长:CDN 切换、故障转移、生效新配置都变慢
  • 太短(比如 60s):DNS 查询量暴涨,权威服务器压力大,解析延迟上升

实践:

  • 一般的业务域名 300~600s 是平衡点
  • 预发布可以临时调小(60s),正式发布时调回
  • 切换 IP 前主动把 TTL 降到 60s 并等一个 TTL,再切,最后调回
  • CDN 域名给长 TTL(不会变),源站给短 TTL

变化生效时间 = TTL + 客户端缓存 + 中间层缓存,不是立即。

Q3：DNS 污染是什么?怎么防?

Section titled “Q3：DNS 污染是什么?怎么防?”

DNS 污染(缓存投毒):攻击者伪造 DNS 响应,把域名解析到恶意 IP。

防御:

  1. DoH(DNS over HTTPS):把 DNS 查询包在加密的 HTTPS 里,中间人无法篡改
  2. DoT(DNS over TLS):同上,端口 853
  3. DNSSEC:给 DNS 记录做数字签名,验证失败直接丢弃(部署复杂)

前端能做的:用 DoH 的公共 DNS(浏览器支持 https://dns.google/dns-query), 或者在 H5 里内置自己的域名解析服务绕开本地 DNS。

注意:DoH 防的是传输中的污染,防不住「运营商本身返回了错误结果」这种情况。

Q4：DNS 预解析(prefetch)是什么?什么时候用?

Section titled “Q4：DNS 预解析(prefetch)是什么?什么时候用?”

在页面加载时提前发起 DNS 查询,等用户真正点击链接时,TCP/TLS 已经省了一次 RTT。

适用:首页有多个明显的出口(导航、搜索),提前解析这些域名的 DNS。 注意预解析只是解析 IP,不下载资源(那才是 prefetch/preload 的事)。

收益有限:现代浏览器的 DNS 缓存 + 预连接已经覆盖了大部分场景。 真正省时间的是 rel="preconnect" —— 直接把 TCP+TLS 也建好,省两个 RTT。

📝 小结

Section titled “📝 小结”
  • DNS 是分层分布式数据库:浏览器缓存 → 系统缓存 → 递归器 → 根 → TLD → 权威,每一级都有缓存。
  • TTL 决定了变更生效时间(TTL + 各级缓存),切 IP 前要主动降 TTL 并等一个周期。
  • 递归查询 vs 迭代查询:客户端用递归,递归器用迭代。
  • DoH/DoT 解决传输途中的 DNS 污染;preconnect 比 prefetch 省的时间更多(省的是 TCP+TLS 两个 RTT)。
