HTTP 协议演进:从 0.9 到 HTTP/3 ​

这一篇只讲主线:每个版本是为了解决上一代的什么问题而生的。

机制细节另有专篇,不要在本篇展开:

  • HTTP/1.1 的问题与浏览器端的绕行手段 → HTTP/1.1 队头阻塞与绕行手段
  • HTTP/2 的分帧 / 多路复用 / HPACK 怎么工作 → HTTP/2 机制:分帧、多路复用与 HPACK
  • HTTP/3 与 QUIC → HTTP/3 与 QUIC 深度
  • 报文结构 → HTTP 报文结构

一、一条主线:让「同一条连接上并行跑多个请求」 ​

Web 的演进史本质上是一条并发能力主线:

版本传输层同一连接能否并行队头阻塞它真正解决的问题
HTTP/0.9TCP❌ 一次一个—能取到页面
HTTP/1.0TCP❌ 一次一个应用层能带元数据(头、状态码)
HTTP/1.1TCP❌ 一次一个应用层连接可复用 + 虚拟主机
HTTP/2TCP✅ 多流传输层把并行收回协议层
HTTP/3QUIC(UDP)✅ 独立流无把并行下沉到传输层

每次演进都是同一件事:HTTP/1.1 用「多开连接」绕开并行限制,HTTP/2 用「一条连接多流」正面解决,HTTP/3 再把并行的粒度下沉到每条流独立重传。

二、HTTP/0.9(1991):能取到页面就行 ​

极简设计:

  • 只有 GET 方法
  • 响应只能是 HTML
  • 没有头、没有状态码
  • 传输完就关闭连接
客户端:GET /
服务器:<html><body>Hello World</body></html>
连接关闭

当时的 Web 就是一堆互相链接的静态 HTML,这个设计完全够用。

三、HTTP/1.0(1996, RFC 1945):能带元数据了 ​

核心改进:

  • 引入 POST、HEAD 方法
  • 引入 HTTP 头(Content-Type、Authorization、User-Agent)
  • 引入状态码(200、404、500)
  • 引入版本号
GET /index.html HTTP/1.0
User-Agent: Mozilla/1.0
Accept: text/html

HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 123

<html>...</html>

遗留问题:

  • 每个请求都要新建 TCP 连接(3 次握手 + 慢启动)
  • 一个 HTML 引用 10 个 JS/CSS → 10 次连接建立,大量时间浪费在握手和慢启动上

这一条直接催生了 HTTP/1.1 的持久连接。

四、HTTP/1.1(1999, RFC 2068 / 2616):让连接能被复用 ​

HTTP/1.1 至今仍是最广泛使用的版本,它有五个关键改动。

4.1 持久连接(Keep-Alive) ​

默认 Connection: keep-alive
同一个 TCP 连接可以连续发多个请求

省掉了每个请求一次的 TCP 握手 + TLS 握手,这是当时最大的性能收益。

4.2 Host 头与虚拟主机 ​

Host 头让一个 IP 可以承载多个域名,虚拟主机成为可能——这是今天「一台服务器跑几百个站点」的前提。

4.3 分块传输(Chunked) ​

Transfer-Encoding: chunked:响应长度未知时也能边生成边传输,不必先算好 Content-Length。

4.4 缓存与范围请求 ​

  • ETag / If-None-Match、Last-Modified / If-Modified-Since → 协商缓存
  • Range → 字节范围请求,支持断点续传与视频拖拽

4.5 遗留问题:管线化与队头阻塞 ​

HTTP/1.1 还有管线化(pipelining):不等响应就发下一个请求。但因为响应必须按请求顺序返回,服务端要维护一个有序队列,实现复杂且容易让慢请求堵住整条连接,所以浏览器几乎从不启用。

于是 HTTP/1.1 落进一个尴尬境地:

  • 一条连接上只能有一个请求在途 → 应用层队头阻塞
  • 浏览器只好对同一域名开 6 条连接来绕开

这套 workaround 的细节、代价,以及 HTTP/2 如何把它收回协议层,见 HTTP/1.1 队头阻塞与绕行手段。

五、HTTP/2(2015, RFC 7540):把并行收回协议层 ​

目标:解决 HTTP/1.1 的队头阻塞,但不改变 HTTP 语义——方法、状态码、头字段的语义完全不变,变的只是传输格式。

四项核心改进(机制见 HTTP/2 机制:分帧、多路复用与 HPACK):

改进解决的问题
二进制分帧文本协议无法高效解析;帧带 stream id 才能乱序
多路复用一条连接上并行跑几十上百个流,不再需要 6 连接 workaround
头部压缩(HPACK)每次请求都带完整头太浪费,重复头只发索引
流优先级让关键资源优先传输

效果:一次页面加载从「6 连接 × 5 批」变成「1 连接 × 30 流」。

遗留问题:传输层仍是 TCP。TCP 是字节流,丢一个包后面所有字节都得等重传,所有流一起卡住。这叫传输层队头阻塞,HTTP/2 解决不了。

六、HTTP/3(2022, RFC 9114):换掉传输层 ​

核心改变:抛弃 TCP,基于 QUIC(Quick UDP Internet Connections)。

为什么必须换传输层:

  • TCP 改不动:改 TCP 需要操作系统升级,部署周期以年计
  • TCP 层队头阻塞在 HTTP/2 时代成为主要瓶颈
  • 握手太慢:TCP + TLS 1.2 需要 5 个 RTT

QUIC 的四个关键收益(细节见 HTTP/3 与 QUIC 深度):

  1. 0-RTT / 1-RTT 握手——首次连接 1-RTT,复用连接可 0-RTT
  2. 独立流——每条流独立 ACK 与重传,一个流丢包不阻塞其他流(彻底解决传输层队头阻塞)
  3. 内置 TLS 1.3——无法禁用,顺带统一了加密基线
  4. 连接迁移——用 64-bit Connection ID 标识连接,手机切 WiFi 时 IP 变了也不断连

现状:主流浏览器与 CDN 均已支持,Nginx 1.25+ 提供 http3 on。

八、实战选型 ​

新项目:Nginx 开启 HTTP/2(基本免费),HTTP/3 视 CDN 与网络情况
老项目:升级 Nginx 并启用 HTTP/2,收益最明显
高延迟 / 移动网络:HTTP/3 收益最大
弱网 / 丢包率高:HTTP/3 优势明显
内网应用:HTTP/1.1 也完全够用

关键提醒:HTTP/2 时代,那些「为 HTTP/1.1 设计的优化」很多变成了反模式——雪碧图、域名分片、内联大段 CSS/JS。详见 HTTP/1.1 队头阻塞与绕行手段 的实战部分。

🎯 面试常考 ​

Q1:HTTP/0.9 到 1.1 的关键改进分别是什么? ​

  • 0.9:只有 GET,无 header 无状态码,只能传 HTML
  • 1.0:加了状态码、Content-Type、Content-Length,支持 POST
  • 1.1(至今最广泛):持久连接(默认 keep-alive)、Host 头(虚拟主机的前提)、分块传输 chunked、缓存指令、Range 范围请求
  • 2:二进制分帧 + 多路复用 + 头部压缩 → HTTP/2 专题
  • 3:换到 QUIC(UDP),解决 TCP 层队头阻塞 → HTTP/3 专题

本质线索:1.1 的每一项改进,都在解决「同一条连接上多个请求互相拖累」或「同一个 IP 上多个站点互相冲突」这两个问题。

Q2:为什么 HTTP/1.1 默认 keep-alive?这带来了什么新问题? ​

默认持久连接后,发第二个请求就不用重新 TCP 握手,省掉一个 RTT。

新问题是队头阻塞:一条连接上 HTTP/1.1 只能有一个请求在途,第一个响应没回来,后面全排队。浏览器的应对是对同一域名开 6 条连接,但这又撞上了每域并发连接数上限。

所以 HTTP/2 的多路复用不是「优化」,是把 HTTP/1.1 的这个 workaround 收回协议层。展开见 3-http1-problems。

Q3:HTTP/2 和 HTTP/3 最本质的区别是什么? ​

HTTP/2 换了传输格式,HTTP/3 换了传输层。

  • HTTP/2 仍是 TCP 上的二进制分帧,并行粒度是「流」,但底层字节流必须顺序交付 → 传输层队头阻塞仍在
  • HTTP/3 是 UDP 上的 QUIC,并行粒度下沉到「独立重传」 → 彻底消除传输层队头阻塞

一句话:HTTP/2 解决应用层队头阻塞,HTTP/3 解决传输层队头阻塞。

📝 小结 ​

  • 演进主线只有一条:让同一条连接上并行跑多个请求。1.1 用多连接绕开,2 用多路复用正面解决,3 用 QUIC 把并行下沉到每条流。
  • HTTP/1.1 五个关键改动:持久连接、Host 头(虚拟主机前提)、分块传输、缓存指令、范围请求。
  • keep-alive 省掉一个 RTT,却引入了应用层队头阻塞,浏览器只能靠「同域名 6 连接」绕——这是 HTTP/2 存在的直接原因。
  • HTTP/2 换的是传输格式,HTTP/3 换的是传输层,这是两者最本质的区别。
  • 机制别混:HTTP/1.1 的问题看 3,HTTP/2 的实现看 4,QUIC 看 13。
