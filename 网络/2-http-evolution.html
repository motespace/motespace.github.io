HTTP 协议演进:从 0.9 到 HTTP/3 ​

一、为什么 HTTP 不断演进 ​

Web 应用越来越复杂:

  • 1995:一个 HTML 文档 + 几张图 → HTTP/0.9 够用
  • 2000:CSS + JS + 多媒体 → HTTP/1.0 引入头
  • 2010:单页应用、视频、API → HTTP/1.1 持久连接
  • 2020:实时音视频、HTTP/2 + 微服务 → HTTP/3 解决队头阻塞

每次演进都解决具体问题。

二、HTTP/0.9(1991) ​

极简设计:

  • 只有 GET 方法
  • 响应只能是 HTML
  • 没有头、没有状态码
  • 连接关闭
客户端:GET /
服务器:<html><body>Hello World</body></html>
连接关闭

三、HTTP/1.0(1996, RFC 1945) ​

核心改进:

  • 引入 POST、HEAD
  • 引入 HTTP 头(Content-Type、Authorization、User-Agent)
  • 引入状态码(200、404、500)
  • 引入版本号
GET /index.html HTTP/1.0
User-Agent: Mozilla/1.0
Accept: text/html

HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 123

<html>...</html>

问题:

  • 每个请求都要新建 TCP 连接(3 次握手 + 慢启动)
  • 一个 HTML 引用 10 个 JS/CSS → 10 次连接建立

四、HTTP/1.1(1999, RFC 2068 / 2616) ​

核心改进(解决 1.0 的连接问题):

4.1 持久连接(Keep-Alive) ​

默认 Connection: keep-alive
同一个 TCP 连接可以发多个请求

但仍然有队头阻塞:一个响应回来前,后续请求不能发(同一个连接)。

4.2 管道化(Pipelining) ​

理论上可以不等响应就发下一个请求,但实际浏览器很少启用(服务端要按顺序响应,实现复杂)。

4.3 其他改进 ​

  • Host 头(支持虚拟主机)
  • Chunked 传输编码(响应长度未知时分块)
  • 缓存指令(ETag、If-None-Match、Last-Modified、If-Modified-Since)
  • 范围请求(Range 头,断点续传)
  • Transfer-Encoding: chunked

五、HTTP/2(2015, RFC 7540) ​

目标:解决 HTTP/1.1 的队头阻塞,不改变 HTTP 语义。

5.1 二进制分帧 ​

HTTP/1.x 是文本协议,HTTP/2 是二进制协议。

HTTP/2 帧格式:
+-----------------------------------------------+
| Length(24) | Type(8) | Flags(8) | Stream ID(32) |
+-----------------------------------------------+
| Payload (可变长度)                            |
+-----------------------------------------------+

每个请求/响应被拆成多个帧,帧可以乱序发送,接收方按流 ID 重组。

5.2 多路复用(Multiplexing) ​

核心特性:一个连接上同时跑多个流,互不阻塞。

HTTP/1.1:6 个 TCP 连接 × 1 个流 = 6 流(浏览器对同域最多 6 连接)
HTTP/2:1 个 TCP 连接 × 多流 = 几十到几百流

效果:

  • 消除应用层队头阻塞
  • 减少 TCP 连接数(降低握手成本)
  • 充分利用单连接带宽

5.3 头部压缩(HPACK) ​

HTTP/1.x 每次请求都带完整头(几百字节到几 KB)。

HTTP/2 用 HPACK 算法:

  • 客户端和服务端维护"头部表"
  • 重复头只发索引号
  • 静态表(61 个常用头)+ 动态表(自定义)
HTTP/1.1:User-Agent: Mozilla/5.0 ... (200+ bytes)
HTTP/2:索引 23 → 索引引用 (1 byte)

5.4 服务器推送(Server Push) ​

服务端可以主动推送资源给客户端(不需要客户端请求)。

请求:GET /index.html
服务器主动推送:/style.css、/script.js

现状:Chrome 已弃用(复杂、缓存难处理),实际项目很少用。

5.5 流量优先级 ​

每个流可以设优先级(1~256),高优先级帧优先发送。

5.6 HTTP/2 的局限 ​

TCP 队头阻塞:虽然应用层不阻塞,但 TCP 层丢包会重传,所有流都得等。HTTP/3 解决这个。

六、HTTP/3(2022, RFC 9114) ​

核心改变:抛弃 TCP,基于 QUIC(Quick UDP Internet Connections)。

6.1 为什么不用 TCP? ​

  • TCP 改不动(改 TCP 协议需要操作系统升级,部署太慢)
  • TCP 队头阻塞问题难解决
  • TCP 三次握手慢

6.2 QUIC 的优势 ​

1. 0-RTT / 1-RTT 握手

TCP + TLS 1.2:3 次握手 + 2-RTT TLS = 5-RTT
TCP + TLS 1.3:3 次握手 + 1-RTT TLS = 4-RTT
QUIC:1-RTT(首次),0-RTT(已连接)

2. 独立流(解决队头阻塞)

QUIC 是 UDP 上实现的可靠传输,每个流独立:

  • 流 A 丢包,只阻塞流 A
  • 流 B 不受影响

3. 内置 TLS 1.3

TLS 1.3 必须,无法禁用。

4. 连接迁移(Connection Migration)

传统 TCP 连接靠四元组(src IP、src port、dst IP、dst port)。手机切 WiFi 时,IP 变了,连接断开。

QUIC 用 64-bit Connection ID 标识连接,不依赖 IP,WiFi 切换无感。

5. 更好的拥塞控制

QUIC 应用层实现拥塞控制(BBR、Cubic),可以更快迭代。

6.3 HTTP/3 现状 ​

  • Chrome / Firefox / Edge / Safari 都支持
  • Cloudflare、Fastly 等 CDN 默认开启
  • Nginx 1.25+ 支持(http3 on directive)
  • 国内 CDN:腾讯云、阿里云都支持

6.4 启用方式 ​

Nginx:

nginx
server {
  listen 443 ssl;
  http2 on;
  http3 on;
  quic_retry on;
  add_header Alt-Svc 'h3=":443"; ma=86400';  # 告知客户端 HTTP/3 可用
}

CDN 配置:

  • Cloudflare:网络选项勾选 HTTP/3
  • 阿里云 DCDN:协议配置启用 QUIC

注意事项:

  • HTTP/3 用 UDP 443,防火墙要放行
  • Alt-Svc 头告诉浏览器 HTTP/3 可用,浏览器下次会尝试
  • 失败 fallback 到 HTTP/2 或 HTTP/1.1

七、协议对比 ​

特性HTTP/1.1HTTP/2HTTP/3
协议层TCPTCPQUIC(UDP)
多路复用❌(应用层队头阻塞)✅(同连接多流)✅(独立流)
头部压缩❌✅(HPACK)✅(QPACK)
握手TCP + TLS 1.2TCP + TLS 1.3内置 TLS 1.3
队头阻塞应用 + TCP 层TCP 层无
服务器推送❌✅(已弃用)✅
0-RTT❌❌✅
连接迁移❌❌✅
部署难度低中中

八、实战选型 ​

新项目:直接上 HTTP/2(Nginx 自动),HTTP/3 视情况
老项目:升级 Nginx + 启用 HTTP/2,收益明显
高延迟网络(移动):HTTP/3 收益最大
弱网/丢包高:HTTP/3 优势明显
内网应用:HTTP/1.1 也够用
