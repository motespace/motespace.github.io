WebSocket:全双工实时通信

一、为什么需要 WebSocket

Section titled “一、为什么需要 WebSocket”

HTTP 是请求-响应模式,客户端不发请求,服务端就不能主动推数据。

要实现“服务端主动推送”,HTTP 时代有几种方案,但都有缺陷:

方案 缺点
轮询(setInterval 拉) 浪费带宽,实时性差
长轮询(hold connection) 服务端资源占用高
SSE(Server-Sent Events) 单向,只能服务端推

WebSocket 是真正的全双工解决方案——一次握手,长期双向通信。

二、WebSocket 握手

Section titled “二、WebSocket 握手”

虽然 WebSocket 是独立的协议,但握手通过 HTTP——这样可以复用 HTTP 基础设施(端口、反向代理、鉴权等)。

关键头:

  • Upgrade: websocket:升级协议
  • Connection: Upgrade:连接升级
  • Sec-WebSocket-Key:客户端随机 base64
  • Sec-WebSocket-Accept:服务端对 Key 加 magic string 后 SHA-1 再 base64

101 Switching Protocols 表示握手成功,之后切换到 WebSocket 协议。

Q1：WebSocket 握手是怎么完成的?

Section titled “Q1：WebSocket 握手是怎么完成的?”

客户端发一个 HTTP Upgrade 请求:

服务端回 101 Switching Protocols 并带上 Sec-WebSocket-Accept(由 key 算出的固定值), 之后这条 TCP 连接就不再是 HTTP 了,开始传 WebSocket 帧。

注意:握手虽然在 HTTP 层完成,但它不是普通 HTTP 请求—— 没有 body、没有状态码语义,失败时回的是普通 HTTP 状态码(如 401)。

Q2：心跳为什么必须做?

Section titled “Q2：心跳为什么必须做?”

检测假死连接。中间设备( NAT 网关、负载均衡)通常有空闲超时, 连接在应用层看起来还开着,实际已被 silently 关闭,双方都不知道。

心跳要应用层发 ping 帧(不是 TCP keepalive),服务端回 pong。 约定:超过 N 秒没收到 pong 就认为连接已死,主动关闭并走重连。

关键:心跳间隔必须小于中间设备的空闲超时,否则设备先断了你还在等。 常见做法:心跳 30s、连续 3 次无响应判定断开。

Q3：WebSocket 断了怎么重连?直接 setTimeout 重连有什么问题?

Section titled “Q3：WebSocket 断了怎么重连?直接 setTimeout 重连有什么问题?”

直接 setTimeout 重连的问题:

  1. 惊群:服务重启后,所有客户端同时重连,把服务再打垮一次
  2. 无抖动:重连时间完全一致,永远撞在一起
  3. 无限重连:服务明确拒绝时还在重连

正确做法是指数退避 + 抖动:

连接成功后把 attempt 归零。

Q4：WebSocket 和 SSE、长轮询怎么选?

Section titled “Q4：WebSocket 和 SSE、长轮询怎么选?”
WebSocket SSE 长轮询
方向 双向 服务端→客户端 服务端→客户端
协议 独立协议(Upgrade) HTTP(纯文本流) HTTP
实现成本 高(需长连接网关) 低(原生 EventSource) 中
二进制 支持 只支持 UTF-8 文本 只支持文本
自动重连 要自己写 浏览器原生支持 要自己写

选型:

  • 服务端单向推送(通知、行情、日志流)→ SSE,简单太多
  • 双向低频交互(IM、协同编辑)→ WebSocket
  • 只需要 HTTP 轮询且频率低 → 长轮询

📝 小结

Section titled “📝 小结”
  • WebSocket 是应用层协议,握手借道 HTTP 的 Upgrade 完成,之后就是 TCP 上的双向帧传输。
  • 和 HTTP 长轮询的区别:长轮询每次都要重新建请求、延迟高;WebSocket 建一次连接后双向随时推。
  • 生产环境三件套:心跳(ping/pong 检测假死)、指数退避 + 抖动重连、鉴权在握手阶段做(URL 带 token 或首帧认证)。
  • 集群下要做广播(Redis Pub/Sub),否则消息只到一台机器;还要处理用户多端登录时的连接清理。
