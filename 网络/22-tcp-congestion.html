TCP 拥塞控制 ​

「网络慢」有很多种,拥塞是其中最容易被忽略的一种:链路没坏,但大家都在抢带宽。

一、两个不同的"堵" ​

类型原因表现解法
拥塞(congestion)网络中间的路由器队列满了,包被丢弃重传RTT 抖动大、丢包率上升拥塞控制算法
带宽限制(bandwidth)物理链路容量有限速率稳定在上限升级带宽

拥塞控制解决的是第一个。注意:链路利用率 100% 本身就是一种拥塞 —— 队列一满,延迟就会暴涨(排队时延)。

二、四个阶段 ​

1. 慢启动(Slow Start) ​

cwnd(拥塞窗口)从 1 个 MSS 开始,每个 RTT 翻倍。

cwnd: 1 → 2 → 4 → 8 → 16 → 32 → 64 ...

指数增长,目的是快速探测链路的最大容量。慢启动只在前几个 RTT 有效。

2. 拥塞避免(Congestion Avoidance) ​

ssthresh 达到后,改为每个 RTT 增加 1 个 MSS(线性增长)。

cwnd: 64 → 65 → 66 → 67 ...

线性增长是为了避免再次把网络打爆。

3. 快重传(Fast Retransmit) ​

接收方收到3 个重复 ACK 时,不等超时,立刻重传丢失的那个包。

text
发送方发出 seq=1..8
接收方返回 ACK=4
发送方发出 seq=9,接收方回 ACK=4
发送方发出 seq=10,接收方回 ACK=4   ← 第 3 个重复 ACK
发送方立刻重传 seq=4              ← 快重传,不等 RTO

4. 快恢复(Fast Recovery) ​

发生丢包后,cwnd 不退回 1,而是减半(从 ssthresh 开始),继续线性增长。

ssthresh = cwnd / 2
cwnd = ssthresh      ← 不回到 1,避免吞吐骤降

完整的 Reno 状态机 ​

          慢启动                 拥塞避免
   cwnd=1 ──────────→ ssthresh ──────────→ 
     ↑                                      │
     │                                      │ 3 重复 ACK
     │                                      ▼
     └──────────────  超时重传 ←───────── 快恢复
              cwnd=1, ssthresh = cwnd/2

三、拥塞窗口与发送窗口 ​

实际能发多少,取两者的较小值:

发送窗口 = min(cwnd, rwnd)
         └ 拥塞窗口   └ 接收窗口
  • cwnd:网络能承受多少(拥塞控制决定)
  • rwnd:对端接收缓冲区还能收多少(流量控制决定)

流量控制是「别把对方撑爆」,拥塞控制是「别把网络撑爆」,两者独立。

四、CUBIC 与 BBR ​

CUBIC(默认) ​

Linux 默认算法。用三次函数在 RTT 内做更激进的增长,靠近 ssthresh 时增长变缓。

W(t) = C·(t - K)³ + W_max
  • 优点:在高 BDP 链路上(比如 10Gbps)比 Reno 快得多
  • 缺点:仍然是丢包驱动的,必须先丢包才知道拥塞了

BBR(Bottleneck Bandwidth and RTT) ​

Google 提出,思路完全不同:不靠丢包检测拥塞,靠测带宽和 RTT。

维护两个模型:

  • BtlBw:瓶颈带宽(通过测量历史最大吞吐估计)
  • **RTprop`:传播时延(历史最小 RTT 估计)

然后用这两个值算出理想发送量:

BDP = BtlBw × RTprop

发送速率围绕 BDP 做上下调节,始终留出 10% 的余量避免排满队列。

对比CUBICBBR
拥塞信号丢包带宽和 RTT 测量
队列时延高(填满队列才发)低(主动留余量)
弱网表现一般好很多
部署成本内核默认需内核模块 / 云厂商支持

结论:BBR 在跨境、无线、丢包不严重的链路上体验明显更好;但它可能对下游不友好(抢带宽),所以在共享网络里要克制使用。

五、实际调优 ​

bash
# 查看当前拥塞窗口
ss -ti | grep -i cwnd

# Linux:启用 BBR
echo "net.ipv4.tcp_congestion_control = bbr" >> /etc/sysctl.conf
sysctl -p

# 增大初始拥塞窗口(BDP 大的链路)
net.ipv4.tcp_slow_start_after_idle = 0
nginx
# 提高 socket 缓冲区(高带宽高时延链路)
proxy_buffer_size 16k;
proxy_buffers 8 16k;

六、怎么判断"我遇到的是拥塞" ​

现象可能是
RTT 稳定但吞吐上不去带宽瓶颈(正常,不是拥塞)
RTT 明显抖动 + 丢包拥塞
同一时刻多台机器互相拖慢共享链路的拥塞
大包全丢、小包正常路径 MTU 黑洞(不是拥塞)

测量:用 ping 观察 RTT 波动,用 mtr --tcp 看路径上哪一跳开始丢包。

🎯 面试常考 ​

Q1: 慢启动和拥塞避免的区别? 慢启动阶段 cwnd 每个 RTT 翻倍(指数增长),用于快速探测链路容量;达到 ssthresh 后进入拥塞避免,每个 RTT 只加 1 个 MSS(线性增长),避免把网络打爆。

Q2: 快重传的触发条件? 接收方连续收到 3 个重复 ACK,发送方判定为丢包并立刻重传,不等 RTO 超时。

Q3: 拥塞窗口和接收窗口的区别? cwnd 由拥塞控制算法决定,表示网络能承受多少;rwnd 由接收方的 TCP 栈决定,表示对端缓冲区还能收多少。实际发送窗口取两者较小值。前者防"把网络撑爆",后者防"把对方撑爆"。

Q4: BBR 和 CUBIC 的核心区别? CUBIC 是丢包驱动的:必须先丢包才知道拥塞了,代价是填满队列导致高时延。BBR 主动测量瓶颈带宽和最小 RTT,算出 BDP 后留 10% 余量发送,时延低且在弱网下表现更好。

Q5: 怎么排查是不是拥塞? 看 RTT 是否明显抖动、丢包率是否上升,用 mtr --tcp 定位丢包起点。如果 RTT 稳定而吞吐上不去,那是带宽瓶颈而不是拥塞。

📝 小结 ​

  • 拥塞控制和流量控制是两回事:一个防撑爆网络,一个防撑爆对端。
  • 四个阶段:慢启动(指数)→ 拥塞避免(线性)→ 快重传(3 个重复 ACK)→ 快恢复(减半不归零)。
  • CUBIC 靠丢包检测拥塞,BBR 靠测带宽和 RTT,后者时延低、弱网表现好。
  • 链路上还有第三类问题(MTU 黑洞)和第四类(带宽上限),排查时别混为一谈。

五、半连接与全连接 ​

三次握手完成前,连接处于半连接状态:客户端已发出 SYN 并收到 SYN+ACK,但最后的 ACK 还没发出去(或者还没收到)。此时服务端会保留这个连接状态一段时间。

状态含义风险
半连接握手未完成SYN Flood:攻击者发大量 SYN 但从不回 ACK,服务端半连接队列被占满
全连接握手完成,可以传数据正常的活跃连接

防护:

  • SYN Cookie:服务端不存半连接状态,把状态编码进 SYN+ACK 里,收到 ACK 时再解码还原。代价是丢失部分 TCP 选项
  • 限制半连接队列长度(net.ipv4.tcp_max_syn_backlog)
  • SYN Flood 防护:限速 + 清洗
bash
# 查看半连接队列
ss -s | grep SYN-RECV
