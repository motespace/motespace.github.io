Cookie 与 Session 深度解析 ​

一、为什么需要会话管理 ​

HTTP 是无状态协议——每次请求都是独立的,服务端不知道"这个请求和上一个是不是同一个用户发的"。

要实现"登录后保持登录状态",需要一种会话机制:

  • 服务端:Session(服务端内存/存储中的状态)
  • 客户端:Cookie(浏览器自动带上的小数据)

二、Cookie 是什么 ​

Cookie 是服务端通过 Set-Cookie 头让浏览器存储、之后自动在请求中带上的一小段数据。

第一次请求:
浏览器 → 服务端:GET /login
服务端 → 浏览器:HTTP/1.1 200 OK
  Set-Cookie: session=abc123; Path=/; HttpOnly

后续请求:
浏览器 → 服务端:GET /dashboard
  Cookie: session=abc123    ← 自动带上

关键认识:

  • Cookie 是服务端通过 Set-Cookie 响应头让浏览器存储的一小段数据
  • 浏览器只在同源 + 符合属性条件时才会自动带上,这是和 localStorage 的核心区别

2.1 Cookie 容量与数量 ​

  • 单个 Cookie 4KB 左右(浏览器差异)
  • 一个域名最多 ~50 个 Cookie
  • 总数有限,大数据用 localStorage / IndexedDB

三、Cookie 六大属性 ​

3.1 Domain ​

http
Set-Cookie: id=xxx; Domain=example.com
  • 不指定:只对当前域生效
  • 指定:对当前域和所有子域生效
example.com     ← 包含
api.example.com ← 包含
mail.example.com ← 包含

3.2 Path ​

http
Set-Cookie: id=xxx; Path=/api

只对 /api 及子路径生效。

实战经验:默认用 Path=/,简化配置。

3.3 Max-Age / Expires ​

http
Set-Cookie: id=xxx; Max-Age=3600        # 1 小时
Set-Cookie: id=xxx; Expires=Wed, 21 Oct 2026 07:28:00 GMT
  • 不设置:会话 Cookie(浏览器关闭就删除)
  • 设置:持久化

3.4 HttpOnly ​

http
Set-Cookie: id=xxx; HttpOnly

JS 读不到(document.cookie 看不到)——防 XSS 偷 cookie。

3.5 Secure ​

http
Set-Cookie: id=xxx; Secure

只在 HTTPS 传输——防明文泄露。

3.6 SameSite ​

http
Set-Cookie: id=xxx; SameSite=Strict
Set-Cookie: id=xxx; SameSite=Lax        # 默认
Set-Cookie: id=xxx; SameSite=None; Secure
SameSite跨域 GET跨域 POST 表单跨域 AJAX
Strict❌❌❌
Lax(默认)✅❌❌
None✅✅✅

实战配置:

  • 支付/转账/敏感:Strict
  • 一般登录态:Lax(默认)
  • 跨站必需(嵌入场景):None + Secure

实战配置建议:

  • 支付/银行/敏感操作:Strict — 任何跨站都不带,最安全(代价:从外部链接进入会丢登录态)
  • 一般登录态:Lax(默认) — 平衡安全(防 POST CSRF)与体验(允许链接跳转带登录态)
  • 跨站必需(SSO / 嵌入场景):None + Secure — Chrome 拒绝 SameSite=None 但不带 Secure 的 Cookie

四、SameSite 实战踩坑 ​

4.1 老浏览器默认不是 Lax ​

Chrome 80+(2020)开始默认 Lax
Firefox 同上
Safari:历史版本兼容 Lax

4.2 表单 POST 跨站不带(Lax 模式) ​

html
<!-- 跨站表单提交,Lax 不带 Cookie -->
<form action="https://bank.com/transfer" method="POST">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>

<!-- 结果:Lax 不带 Cookie,服务端认为是未登录用户,转账失败 -->
<!-- CSRF 防御生效 -->

4.3 顶层导航 GET 带(Lax) ​

用户点击链接 → 跨站 → Cookie 带上(GET)

所以 Lax 是平衡点:防止 POST 表单 CSRF,但允许普通链接跳转带 Cookie。

4.4 None 必须 Secure ​

http
# ❌ Chrome 拒绝
Set-Cookie: id=xxx; SameSite=None

# ✅ Chrome 接受
Set-Cookie: id=xxx; SameSite=None; Secure

五、__Host- 前缀 ​

防 Cookie 注入(子域写 Cookie 攻击):

http
Set-Cookie: __Host-session=xxx; Secure; Path=/; HttpOnly

约束:

  • 必须 Secure
  • 不能有 Domain 属性
  • Path 必须是 /

实战:重要 Cookie 用 __Host- 前缀。

六、Cookie 安全最佳实践 ​

6.1 必加属性 ​

http
Set-Cookie: session=xxx;
  HttpOnly;          # 防 XSS 读
  Secure;            # 只 HTTPS
  SameSite=Lax;      # 防 CSRF
  Path=/;
  Max-Age=3600

6.2 完整安全配置 ​

ts
// 服务端(Express)
res.cookie('session', token, {
  httpOnly: true,       // 防 XSS
  secure: true,         // 仅 HTTPS
  sameSite: 'lax',      // CSRF 防护
  maxAge: 24 * 60 * 60 * 1000,
  domain: '.example.com',  // 所有子域可用
  path: '/',
})

6.3 SameSite=None + Secure 配置 ​

ts
// 跨域场景(嵌入第三方)
res.cookie('cross_token', value, {
  httpOnly: true,
  secure: true,         // 必填
  sameSite: 'none',     // 显式 None
  maxAge: 3600 * 1000,
})

七、Session 机制 ​

7.1 服务端 Session ​

登录请求 → 验证账号密码
         → 生成唯一 session ID(uuid)
         → 存到服务端(Session Store)
         → Set-Cookie: session=<id>

后续请求 → Cookie: session=<id>
         → 服务端查 Session Store
         → 找到用户信息
         → 执行业务逻辑

7.3 Session vs JWT 对比 ​

SessionJWT
存储服务端客户端
状态有状态无状态
撤销易难
跨服务需要共享 session store天然支持
性能每次查 session仅解码
体积session ID 小JWT 几百字节

选型:

  • 单体应用:Session + Cookie
  • 分布式 + 移动端:JWT
  • 需要频繁撤销:Session
  • 微服务:JWT

八、Cookie 与 CSRF ​

详见 /security/8-csrf-samesite.md。要点:

防御层级:
1. SameSite Cookie(浏览器级)
2. CSRF Token(请求级)
3. Origin 校验(辅助)
4. 关键操作二次验证(业务级)

九、Cookie 的隐私 ​

9.1 第三方 Cookie ​

跨站请求时:
- SameSite=None 才带
- 现代浏览器开始限制(ITP / Chrome 的 Privacy Sandbox)

9.2 跟踪 Cookie ​

广告联盟常用第三方 Cookie 跨站追踪用户
Firefox / Safari 已默认屏蔽
Chrome 在 2024 后逐步废弃第三方 Cookie

9.3 Storage Access API ​

跨站 Cookie 访问需要用户授权:

js
document.requestStorageAccess().then(() => {
  // 现在能读第三方 Cookie
})

十、实战案例 ​

10.1 项目:风控平台登录 ​

ts
// 真实代码
res.cookie('Authorization', token, {
  httpOnly: true,        // XSS 读不到
  secure: true,          // 仅 HTTPS
  sameSite: 'lax',       // CSRF 防护
  maxAge: 24 * 60 * 60 * 1000,
  domain: '.example.com', // 主域 + 子域
  path: '/',
})

10.2 项目:跨域 SSO ​

ts
// 用户在 auth.example.com 登录
// 需要在 app.example.com / admin.example.com 共享登录态

// 方案 1:SameSite=None; Secure(显式)
res.cookie('sso_token', value, {
  sameSite: 'none',
  secure: true,
  domain: '.example.com',
  httpOnly: true,
})

// 方案 2:共享 Cookie + 统一登录服务
// 所有子域共用 .example.com 的 Cookie
