DNS 解析流程与优化 ​

一、为什么需要 DNS ​

人类记不住 IP 地址(203.0.113.42),但记得住域名(example.com)。

DNS(Domain Name System)就是域名 → IP 的翻译系统——互联网的"电话簿"。

二、域名的层级结构 ​

www.example.com.
│   │       │    │
│   │       │    └─ 根域(Root)
│   │       └────── 顶级域(TLD):.com
│   └────────────── 二级域:example.com
└────────────────── 子域名:www

完整域名(FQDN):www.example.com.(末尾有点表示根)

三、DNS 解析完整流程 ​

浏览器输入 https://www.example.com,实际是 IP 之前,要先解析:

1. 浏览器缓存(Chrome: ~60s~30min)
   ↓ 命中,返回
2. 系统缓存(操作系统的 DNS 缓存)
   ↓ 命中,返回
3. 本地 hosts 文件
   ↓ 命中,返回
4. 本地 DNS 服务器(LDNS,如 8.8.8.8、114.114.114.114)
   ├─ 查询 LDNS 缓存
   └─ 如果 LDNS 没缓存,向根 DNS 发起递归查询
5. 根 DNS 服务器
   ↓ 返回 .com 顶级域 TLD 服务器地址
6. TLD DNS 服务器(.com)
   ↓ 返回 example.com 权威 DNS 服务器地址
7. 权威 DNS 服务器
   ↓ 返回 www.example.com 的 IP
8. 缓存回客户端

总耗时:

  • 缓存命中:< 1ms
  • 缓存未命中:20~200ms(取决于递归查询)
  • 跨网查询:几百 ms

面试常考点:

1. 递归 vs 迭代查询

  • 客户端 → LDNS 是递归(LDNS 帮客户端问到底,客户端只发一次)
  • LDNS → 根 → TLD → 权威 是迭代(每层只告诉 LDNS 去问下一级,不亲自问)

2. 为什么需要这么多层?

  • 分级缓存,根 DNS 不必承载所有查询压力(全球每天万亿次 DNS 查询)
  • 任何一级失效,都不会全局瘫痪

3. 前端优化点

  • DNS 预解析:`n- 减少不同域名的数量(每个新域名都要 DNS 查询)
  • 长连接 + HTTP/2 多路复用

四、DNS 记录类型 ​

类型用途示例
A域名 → IPv4example.com → 93.184.216.34
AAAA域名 → IPv6example.com → 2606:2800:220:1:248:1893:25c8:1946
CNAME域名 → 域名www.example.com → example.com
NS指定权威 DNSexample.com → ns1.cloudflare.com
MX邮件服务器example.com → mail.example.com
TXT文本记录(SPF、DKIM)v=spf1 include:_spf.google.com ~all
SRV服务定位_sip._tcp.example.com
PTRIP → 域名(反向)用于日志、邮件验证

五、DNS 查询方式 ​

5.1 递归查询 ​

客户端 → 本地 DNS:帮我查 www.example.com
本地 DNS:我去问其他 DNS,你等着
本地 DNS → 根 → TLD → 权威 → 返回 IP
本地 DNS → 客户端:给你 IP

特点:客户端只发一次请求,本地 DNS 负责全部。

5.2 迭代查询 ​

客户端 → 根 DNS:www.example.com 在哪?
根 DNS:你去问 .com 的 NS

客户端 → .com NS:www.example.com 在哪?
.com NS:你去问 example.com 的 NS

客户端 → example.com NS:www.example.com 在哪?
example.com NS:93.184.216.34

特点:客户端自己一步步问,实际很少用(本地 DNS 默认递归)。

5.3 实际:本地 DNS 递归,根/TLD/权威迭代 ​

LDNS 帮你递归 → 根 → TLD → 权威
LDNS 把结果返回给你(整个链路你只等一次)

六、DNS 优化 ​

6.1 浏览器层面 ​

减少 DNS 查询次数:

  • 同一域名一次性查完所有资源
  • 跨域资源预解析:<link rel="dns-prefetch">
html
<!-- 提前解析第三方域名,降低后续请求延迟 -->
<link rel="dns-prefetch" href="//api.example.com">
<link rel="dns-prefetch" href="//cdn.example.com">
<link rel="dns-prefetch" href="//fonts.googleapis.com">

预连接(更强):

html
<link rel="preconnect" href="https://api.example.com" crossorigin>

preconnect 比 dns-prefetch 多做:DNS 解析 + TCP 握手 + TLS 握手。

6.2 操作系统 / 网络层面 ​

减少 DNS 解析次数:

  • 同源资源放同一域名(用 HTTP/2 后已不是必须)
  • 减少第三方域名数量

用本地 DNS 缓存:

js
// Chrome 配置
chrome://flags/#dns-httpssvcb

// 启用 DNS over HTTPS(DoH)
chrome://flags/#dns-over-https

6.3 DoH / DoT(DNS over HTTPS / TLS) ​

传统 DNS:明文 UDP,可能被劫持
DoH: DNS over HTTPS(443)
DoT: DNS over TLS(853)

好处:DNS 查询加密,防运营商/防火墙劫持。

主流 DoH 服务:

  • https://dns.cloudflare.com/dns-query(1.1.1.1)
  • https://dns.google/dns-query(8.8.8.8)
  • https://dns.quad9.net/dns-query(9.9.9.9)

6.4 服务端优化 ​

TTL 设置:

记录类型        推荐 TTL
A/AAAA 记录     300~3600(5 分钟到 1 小时)
CNAME          3600(1 小时)
NS              86400(1 天)

TTL 越短:变更生效越快,但查询越多。 TTL 越长:缓存友好,但变更生效慢。

七、CDN 与 DNS ​

7.1 CDN 的 DNS 智能解析 ​

CDN 提供商(Cloudflare、阿里云)会做智能 DNS 解析:

用户在北京 → 解析到 北京 CDN 节点
用户在上海 → 解析到 上海 CDN 节点
用户在美国 → 解析到 美国 CDN 节点

7.2 DNS 负载均衡 ​

www.example.com
  → 1.2.3.4 (50%)
  → 5.6.7.8 (30%)
  → 9.10.11.12 (20%)

DNS 服务器返回不同 IP,实现流量分配。

7.3 健康检查 ​

DNS 服务会剔除不健康的节点:

  • 节点宕机 → 不返回该 IP
  • 节点延迟高 → 优先返回其他

八、DoH/DoT 实战 ​

8.1 浏览器配置 ​

Chrome:

chrome://settings/security → 使用安全 DNS
选择 Cloudflare(1.1.1.1)或 Google(8.8.8.8)

Firefox:

about:preferences#general → 网络设置 → 启用基于 HTTPS 的 DNS

8.2 操作系统配置(macOS) ​

bash
# 设置 DoH
sudo networksetup -setdnsservers "Wi-Fi" 1.1.1.1
sudo networksetup -setdnsservers "Wi-Fi" "https://dns.cloudflare.com/dns-query"

8.3 Node.js ​

js
const { Resolver } = require('dns').promises

const resolver = new Resolver({
  servers: ['1.1.1.1', '8.8.8.8'],  // 用 Cloudflare + Google
})

resolver.resolve4('example.com').then(console.log)

九、HTTP/3 的 Alt-Svc 与 DNS ​

HTTP/3 通过 DNS 或 Alt-Svc 头告知客户端:

http
Alt-Svc: h3=":443"; ma=86400
第一次请求:HTTP/2
第二次请求:浏览器看到 Alt-Svc → 尝试 HTTP/3
浏览器用 Happy Eyeballs 探测

实战:服务端启用 HTTP/3 后,会自动通过 HTTP/2 响应告诉客户端"试试 HTTP/3"。

十、安全考虑 ​

10.1 DNS 劫持 ​

攻击者修改 DNS 响应 → 用户访问恶意 IP

防御:

  • DNSSEC(DNS 签名验证)
  • DoH / DoT(加密 DNS 查询)

10.2 DNS 投毒 ​

攻击者伪造 DNS 响应,污染缓存

防御:

  • DNS-over-HTTPS(DoH)
  • 源端口随机化
  • 0x20 编码(大小写混淆)

10.3 DNS Rebinding ​

攻击者控制恶意域名 → DNS 解析到内网 IP
浏览器绕过同源策略,访问内网服务

防御:

  • 浏览器侧:Public Suffix List
  • 服务端:Host 头验证

十一、性能对比 ​

无 DNS 缓存: 100~300ms(递归查询)
有本地缓存: 1~5ms(命中)
LDNS 命中:    10~30ms
DoH 启用:     +5~20ms(加密成本)

十二、实战建议 ​

12.1 关键路径 ​

  • 关键资源域名 → 用 preconnect
  • 第三方域名 → 用 dns-prefetch

12.2 自有服务 ​

  • 选 LDNS 快的(国内 114.114.114.119、阿里 223.5.5.5)
  • 多 LDNS 备份

12.3 CDN 选择 ​

  • 全球用户 → Cloudflare / Fastly(支持 DoH)
  • 国内用户 → 阿里云 / 腾讯云(就近解析)

12.4 隐私 ​

  • 浏览器开 DoH
  • 用 1.1.1.1 / 9.9.9.9(承诺不记录)
