Q1：HTTPS 解决了什么问题?

Section titled “Q1：HTTPS 解决了什么问题?”

三个,按重要性:

  1. 机密性:传输内容不被中间人看到(对称加密)
  2. 完整性:内容不被篡改(摘要 + 签名)
  3. 身份认证:确认对方真是那个服务器(证书链 + 域名校验)

不解决的是:服务器本身被攻破、客户端被入侵、DNS 劫持(除非用 DoH)。 所以 HTTPS 只保护「传输途中」,端到端安全还得靠应用层(HSTS、CSP、JWT 签名)。

Q2：HTTPS 为什么用对称加密?性能上不是对称更快吗?

Section titled “Q2：HTTPS 为什么用对称加密?性能上不是对称更快吗?”

因为非对称加密只能加密很少的数据(RSA 2048 位一次最多 245 字节),而且很慢。

标准做法是混合加密:

  1. 握手阶段用非对称(ECDHE)协商出共享密钥 —— 慢,但只做一次
  2. 之后用对称(AES-GCM)加密业务数据 —— 快,可以加密任意量

TLS 1.3 把这个过程压到 1-RTT:ECDHE 密钥交换 + 服务端证书签名可以合并在同一个 ServerHello 里,而且去掉了 RSA 密钥交换(有前向安全风险)。

Q3：证书链是什么?中间人能不能自己签一个证书骗我?

Section titled “Q3：证书链是什么?中间人能不能自己签一个证书骗我?”

证书链:根 CA → 中间 CA → 域名证书。浏览器内置了根 CA 的公钥。

中间人骗不了的原因:他可以伪造一张证书,但没有根 CA 或中间 CA 的私钥,就签不出 能被浏览器验证通过的证书链。根 CA 的私钥在 CA 机构手里。

前提是浏览器信任那个根 CA —— 这就是企业代理(公司 HTTPS 中间人证书)、 以及「自签名证书报红」的原因。

校验三件事:签发 CA 在信任链里、域名匹配、有效期没过期。

Q4：混合内容(mixed content)是什么?为什么会拦截?

Section titled “Q4：混合内容(mixed content)是什么?为什么会拦截?”

HTTPS 页面里加载 HTTP 资源(或反过来)就是混合内容。

现代浏览器直接拦截主动内容(脚本、iframe、fetch),因为它能读取页面数据, 在 HTTPS 页面里传明文等于把 HTTPS 的保证作废。被动内容(图片)历史上只是警告, 现在也会被拦截并升级成 HTTPS 请求。

排查:DevTools → Security 面板,或者看 Console 里的 Mixed Content 警告。

📝 小结

Section titled “📝 小结”
  • HTTPS 的三件事:机密性(对称加密)、完整性(摘要签名)、身份认证(证书链),都不解决端点自身的安全。
  • 混合加密:握手用非对称(ECDHE)协商密钥,数据用对称(AES-GCM)加密;TLS 1.3 把握手压到 1-RTT。
  • 证书链靠「根 CA 私钥不外泄」防伪,前提是浏览器信任那个根 CA——这就是自签名证书报红的原因。
  • 混合内容会被浏览器拦截(主动内容),排查看 DevTools Security 面板和 Console。
