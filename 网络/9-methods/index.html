HTTP 方法语义与 REST 设计

一、HTTP 方法的本质

Section titled “一、HTTP 方法的本质”

HTTP 方法(METHOD)是对资源的操作类型——服务端看到 POST /users/123 就能理解“创建/修改 user 123”。

二、七大方法详解

Section titled “二、七大方法详解”

2.1 GET

Section titled “2.1 GET”

语义:获取资源(只读)。

特点:

  • 幂等(多次调用结果一致)
  • 安全(不修改服务端状态)
  • 可缓存
  • URL 长度限制(实际 ~2000 字符)
  • 参数在 URL(?key=value)

适用场景:列表查询、详情查询。

2.2 POST

Section titled “2.2 POST”

语义:创建资源或执行操作(非幂等)。

特点:

  • 不幂等(多次调用会创建多条记录)
  • 参数在 body(任意大小)
  • 不可缓存(默认)

适用场景:注册、登录、表单提交、调用非幂等操作。

2.3 PUT

Section titled “2.3 PUT”

语义:全量更新资源(幂等)。

特点:

  • 客户端提供完整资源表示
  • 多次调用结果一致(最终状态相同)
  • 通常配合 If-Match(乐观锁)

适用场景:完整替换一个资源。

2.4 PATCH

Section titled “2.4 PATCH”

语义:部分更新资源。

特点:

  • 客户端只提供要改的字段
  • 不幂等(取决于实现)

适用场景:增量更新,只改部分字段。

2.5 DELETE

Section titled “2.5 DELETE”

语义:删除资源(幂等)。

特点:

  • 幂等(多次调用结果一致:资源不存在)
  • 通常返回 204 No Content

适用场景:删除资源。

2.6 HEAD

Section titled “2.6 HEAD”

语义:同 GET,但响应只返回头,不返回 body。

用途:

  • 检查资源是否存在(200 vs 404)
  • 检查最后修改时间(Last-Modified)
  • 健康检查

2.7 OPTIONS

Section titled “2.7 OPTIONS”

语义:查询支持的 HTTP 方法和跨域信息。

用途:

  • CORS 预检请求(见 6-cors.md)
  • API 自描述(Allow 头)

三、幂等性详解

Section titled “三、幂等性详解”

幂等:多次执行同一请求,服务端状态最终一致。

为什么幂等重要:

  • 客户端可以安全重试(网络失败时)
  • 中间件、代理可以缓存
  • 实现更简单(不用复杂的去重逻辑)

实战经验:

  • 支付、退款等关键操作必须幂等
  • 实现:用 unique request ID,服务端去重

四、安全性(Safe)与幂等性(Idempotent)

Section titled “四、安全性(Safe)与幂等性(Idempotent)”
方法 安全(Safe) 幂等(Idempotent)
GET ✅ ✅
HEAD ✅ ✅
OPTIONS ✅ ✅
PUT ❌ ✅
DELETE ❌ ✅
POST ❌ ❌
PATCH ❌ ❌(可能)

Safe:不修改服务端状态。 Idempotent:多次调用结果一致。

GET 是两者都是;DELETE 不是 Safe 但 Idempotent;POST 两者都不是。

六、GraphQL / gRPC vs REST

Section titled “六、GraphQL / gRPC vs REST”

6.1 REST 优点

Section titled “6.1 REST 优点”
  • 简单、直观
  • HTTP 原生支持
  • 缓存友好
  • 工具链成熟(Swagger / OpenAPI)

6.2 REST 缺点

Section titled “6.2 REST 缺点”
  • Over-fetching:获取的字段可能用不到
  • Under-fetching:一个页面要多个请求
  • 版本管理(API v1、v2)

6.3 GraphQL 解决

Section titled “6.3 GraphQL 解决”
  • 客户端精确声明需要的字段
  • 单个 endpoint
  • 强类型 schema

6.4 gRPC 适用

Section titled “6.4 gRPC 适用”
  • 微服务之间通信
  • 高性能(Protobuf 二进制)
  • 流式调用(server / client / bidirectional)

7.3 REST 设计原则

Section titled “7.3 REST 设计原则”
  • 资源用名词

📝 小结

Section titled “📝 小结”
  • 方法语义看三个属性:Safe(只读不改)、Idempotent(重复执行结果相同)、Cacheable(能否被缓存)。
  • GET/HEAD 是 Safe 且 Idempotent;PUT/DELETE 是 Idempotent 但不 Safe;POST 既不安全也不幂等;OPTIONS 用于查询通信选项与 CORS 预检。
  • 幂等性的意义在重试:GET/PUT/DELETE 出错可安全重试,POST 重试可能造成重复下单,所以要靠幂等键(Idempotency-Key)。
  • REST 资源用名词(/orders/{id}),动作用 HTTP 方法表达;复杂动作用子资源(/orders/{id}/cancel)。
  • 状态码语义要准确:200 成功、201 创建(带 Location)、204 无内容、400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突、429 限流、500 服务端错误。
  • 对比:GraphQL 解决「多次请求拼装」但缓存与 HTTP 语义弱;gRPC 走 HTTP/2 二进制,性能好但调试与浏览器支持受限。
  • 面试加分:讲清「为什么 PUT 幂等而 POST 不幂等」——幂等取决于服务端实现方式与请求体语义。
