HTTP/1.1 队头阻塞与绕行手段 ​

这一篇只讲 HTTP/1.1 自己的问题,以及浏览器在协议层解决之前怎么绕。

相邻专题:

  • 演进全景(为什么会有这一堆 workaround)→ HTTP 协议演进
  • HTTP/2 如何把 workaround 收回协议层 → HTTP/2 机制:分帧、多路复用与 HPACK
  • HTTP/3 如何解决传输层队头阻塞 → HTTP/3 与 QUIC 深度

一、什么是队头阻塞 ​

队头阻塞(Head-of-Line Blocking, HoL Blocking)是 HTTP/1.1 最核心的性能问题。

1.1 直观例子 ​

想象超市结账:

  • 一条队 5 个人,最前面的人在算 100 件商品
  • 后面 4 个人都得等,即使他们只要付 1 件

HTTP/1.1 一个连接(一个「队」)上:

  • 请求 1 慢,后面的请求都得等

1.2 HTTP/1.1 连接特性 ​

HTTP/1.1 默认 Keep-Alive:
- 一个 TCP 连接可以发多个请求
- 但响应必须按请求顺序返回(FIFO)
- 一个慢响应阻塞所有后续响应
客户端                         服务端
  |  请求 1 (慢)              |
  |  ─────────────────────→  |
  |                           |  处理 1 用 1s
  |  请求 2 (快)             |
  |  ←─── 等待中... ────────  |
  |                           |  处理 2 只要 0.1s
  |  ←───── 响应 1 终于回来 ──|
  |  请求 2 现在才发出去 ────→|
  |  ←───── 响应 2 立刻回来 ──|

响应 2 本来 100ms 就能返回,实际等了 1000ms+。

二、为什么会这样 ​

2.1 设计原因 ​

HTTP/1.x 是文本协议 + 顺序解析:

  • 浏览器通过响应顺序判断哪个响应对应哪个请求
  • 乱序返回会导致解析混乱
  • 解决方案简单粗暴:严格顺序

2.2 不支持多路复用的后果 ​

浏览器对同一域名最多开 6 个并发连接:

连接 1: 请求 A → 等响应 A
连接 2: 请求 B → 等响应 B
连接 3: 请求 C → 等响应 C
连接 4: 请求 D → 等响应 D
连接 5: 请求 E → 等响应 E
连接 6: 请求 F → 等响应 F

第 7 个请求?排队等前面完成。

实际项目:一个 HTML 引用 30 个 JS/CSS,前 6 个并发,后面 24 个排队。

2.3 两个层次的队头阻塞 ​

这是本篇最核心的概念,后面 HTTP/2 与 HTTP/3 的所有差异都从这里展开:

层次发生在哪表现谁能解决
应用层(HTTP 层)HTTP/1.1 的响应必须按序返回一个慢接口堵住后面所有请求HTTP/2 多路复用
传输层(TCP 层)TCP 是字节流,必须顺序交付丢一个包,连接上所有数据都得等重传HTTP/3 的 QUIC

应用层:HTTP/1.1 的协议设计就要求顺序返回,慢请求无法绕过。

传输层:

TCP 是字节流:
- 包 1、2、3、4、5 顺序发送
- 包 3 丢失 → 接收方等待包 3 重传
- 包 4、5 已经在接收方缓存,但不能交给应用层(TCP 是顺序的)
- 所有数据都阻塞,直到包 3 到达

关键:HTTP/2 的多路复用让应用层的流可以并行,但底层 TCP 仍是串行的——流 A 的包丢了,流 B、C、D 全部要等。这就是 HTTP/2 解决了一半、HTTP/3 才彻底解决的原因。

三、HTTP/1.1 时代的绕行手段 ​

HTTP/1.1 没有真正的解法,浏览器和工程上只能绕。以下五种是历史上真实用过的办法,每一种都有代价。

3.1 多连接 ​

浏览器对同域名最多 6 个并发连接(Chrome 实际就是 6)。

代价:增加 TCP + TLS 握手成本;而且 6 条对现代页面(30+ 资源)根本不够。

3.2 域名分片(Domain Sharding) ​

把资源分散到多个子域,每个子域各享 6 条连接:

html
<!-- 主域:example.com -->
<!-- 分片:static1.example.com、static2.example.com -->
<link rel="stylesheet" href="https://static1.example.com/a.css">
<link rel="stylesheet" href="https://static2.example.com/b.css">

效果:6 连接 × 3 子域 = 18 并发。

代价:增加 DNS 查询与握手;HTTP/2 时代必须禁用(多路复用已经解决并发问题,分片反而浪费连接)。

3.3 资源合并 ​

把多个小资源合并成一个大资源,减少请求数:

  • 雪碧图(CSS Sprite):多个小图标合并成一张大图,background-position 定位
  • 合并 JS / CSS:一个大 bundle 而不是多个小文件

代价:维护差(改一个图标要重出整张 sprite)、缓存粒度大(改一行 JS 整个 bundle 失效)。

HTTP/2 时代必须禁用:请求数不再是瓶颈,大 bundle 反而拖慢首屏。

3.4 内联资源 ​

html
<style>body { background: red; }</style>
<script>console.log('inline')</script>

代价:HTML 体积大、不能单独缓存、阻塞关键路径。

HTTP/2 时代少用:头部压缩已经让重复头几乎不花钱,而内联牺牲了缓存能力。

3.5 preload / prefetch ​

html
<!-- preload:高优先级,提前加载当前页面关键资源 -->
<link rel="preload" href="/critical.css" as="style">

<!-- prefetch:低优先级,提前加载下个路由的资源 -->
<link rel="prefetch" href="/next-page.js">

优点:不改变资源结构,只是提前加载,在 HTTP/2 时代依然是推荐做法(替代被废弃的 Server Push)。

3.6 五种手段的共同点 ​

它们本质都在做同一件事:减少请求数或增加并发数,而不是让一条连接真正并行。所以:

  • 每个手段都有代价(握手、缓存粒度、维护成本)
  • 都不是协议层的解决方案
  • HTTP/2 一出来,大部分就该被废弃了

四、HTTP/2 如何把这个 workaround 收回协议层 ​

HTTP/2 不再让浏览器去「多开连接」,而是让一条连接内部并行:

  • 一个 TCP 连接,多个流(stream),每个流有独立 ID
  • 请求和响应都拆成帧(Frame),帧带流 ID
  • 帧可以乱序发送和接收,接收方按流 ID 重组
  • 不再有「队」的概念

一句话:一个连接、多条流、乱序发送、按流 ID 重组,不再有「队」的概念。

机制细节(帧结构与帧类型、流状态机、两级流控、HPACK)见 HTTP/2 机制:分帧、多路复用与 HPACK。

注意:HTTP/2 只解决了应用层队头阻塞,传输层的还在(见 2.3)。

五、性能对比 ​

以「首屏 30 个资源」为例:

方案并发方式耗时
HTTP/1.1(6 连接)6 个一批,分 5 批约 1000ms
HTTP/2(多路复用)1 连接 30 流并行约 300~500ms
HTTP/3(弱网 2% 丢包)流独立重传约 200~400ms

弱网下差距最明显:HTTP/2 的传输层队头阻塞在丢包时会让所有流一起卡住,而 HTTP/3 只重传出问题的那条流。

六、HTTP/2 时代的实战清单 ​

6.1 反模式(HTTP/1.1 时代的优化,现在要拆掉) ​

❌ 雪碧图        → 拆成独立图片,配合 HTTP/2 多路复用
❌ 域名分片      → 合并到一个域名
❌ 内联大段 CSS/JS → 独立文件,长期缓存
❌ 合并成超大 bundle → 拆小包,按需加载 + preload 关键 chunk

6.2 HTTP/2 时代仍然要做的优化 ​

  • 压缩:Brotli 优于 gzip(协商过程见 内容压缩与 ALPN)
  • 缓存:Cache-Control + ETag(见 HTTP 缓存机制)
  • 图片优化:AVIF / WebP + 显式宽高
  • 懒加载:非关键资源延迟加载
  • preload:关键资源显式声明优先级
  • CDN:就近分发,顺带吃到 HTTP/2 与 HTTP/3

6.3 启用 HTTP/2 ​

Nginx 侧加一个 http2 参数即可,应用层无需改动。

完整配置(含 TLS 套件)与验证方法(DevTools Protocol 列、curl -I --http2)见 HTTP/2 机制:分帧、多路复用与 HPACK。

🎯 面试常考 ​

Q1:HTTP/1.1 队头阻塞是什么? ​

答:HTTP/1.1 一个 TCP 连接上,响应必须按请求顺序返回,前面的慢响应会阻塞后面的响应。

Q2:浏览器为什么最多 6 个并发连接? ​

答:因为 HTTP/1.1 一条连接有队头阻塞,只能靠多开连接绕开。RFC 2616 建议 2 个,实际浏览器(如 Chrome)用 6 个。

Q3:HTTP/2 怎么解决的? ​

答:

  • 单 TCP 连接上多路复用,多个 stream 并行
  • 请求/响应拆成帧,帧带 stream ID,可以乱序发送
  • 接收方按 stream ID 重组

→ 机制细节见 4-http2

Q4:HTTP/2 还有队头阻塞吗? ​

答:有,但只剩传输层。TCP 丢一个段,后面所有字节都得等它重传,所有 stream 一起卡住——哪怕它们的数据本身完好。HTTP/3 / QUIC 用 UDP + 独立流彻底解决。

Q5:既然 HTTP/2 已经解决了并发,为什么还需要 preload? ​

答:preload 解决的是优先级问题,不是并发问题。HTTP/2 的流可以并行,但资源仍然要争抢带宽;用 rel=preload 显式告诉浏览器「这个资源是 LCP,优先给我」,比让浏览器猜更准。它也是 Server Push 被废弃后的替代方案。

📝 小结 ​

  • 队头阻塞分两层:应用层(HTTP/1.1 必须按序返回)与传输层(TCP 顺序交付,丢一个包全部要等)。这个区分是整个 HTTP 演进的关键。
  • HTTP/1.1 时代的五种绕行手段(多连接、域名分片、资源合并、内联、preload/prefetch)本质都是减少请求数或增加并发数,不是协议层解法。
  • HTTP/2 用二进制分帧 + 多路复用把 workaround 收回协议层,但只解决了应用层;传输层要靠 HTTP/3 的 QUIC。
  • 性能数据要会讲:同样 30 个资源,HTTP/1.1 约 1000ms,HTTP/2 约 300~500ms,弱网下 HTTP/3 优势最明显。
  • HTTP/2 时代要拆掉的反模式:雪碧图、域名分片、内联大段资源、超大 bundle;仍然保留:压缩、缓存、图片优化、懒加载、preload、CDN。
