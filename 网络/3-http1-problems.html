HTTP/1.1 队头阻塞详解 ​

一、什么是队头阻塞 ​

队头阻塞(Head-of-Line Blocking, HoL Blocking)是 HTTP/1.1 最核心的性能问题。

1.1 直观例子 ​

想象超市结账:

  • 一条队 5 个人,最前面的人在算 100 件商品
  • 后面 4 个人都得等,即使他们只要付 1 件

HTTP/1.1 一个连接(一个"队")上:

  • 请求 1 慢,后面的请求都得等

1.2 HTTP/1.1 连接特性 ​

HTTP/1.1 默认 Keep-Alive:
- 一个 TCP 连接可以发多个请求
- 但响应必须按请求顺序返回(FIFO)
- 一个慢响应阻塞所有后续响应
客户端                         服务端
  |  请求 1 (慢)              |
  |  ─────────────────────→  |
  |                           |  处理 1 用 1s
  |  请求 2 (快)             |
  |  ←─── 等待中... ────────  |
  |                           |  处理 2 只要 0.1s
  |  ←───── 响应 1 终于回来 ──|
  |  请求 2 现在才发出去 ────→|
  |  ←───── 响应 2 立刻回来 ──|

响应 2 本来 100ms 就能返回,实际等了 1000ms+。

二、为什么会这样 ​

2.1 设计原因 ​

HTTP/1.x 是文本协议 + 顺序解析:

  • 浏览器通过响应顺序判断哪个响应对应哪个请求
  • 乱序返回会导致解析混乱
  • 解决方案简单粗暴:严格顺序

2.2 不支持多路复用的后果 ​

浏览器对同一域名最多开 6 个并发连接:

连接 1: 请求 A → 等响应 A
连接 2: 请求 B → 等响应 B
连接 3: 请求 C → 等响应 C
连接 4: 请求 D → 等响应 D
连接 5: 请求 E → 等响应 E
连接 6: 请求 F → 等响应 F

第 7 个请求?排队等前面完成。

实际项目:一个 HTML 引用 30 个 JS/CSS,前 6 个并发,后面 24 个排队。

三、HTTP/1.1 的解决方案(历史手段) ​

3.1 多连接 ​

js
// 浏览器对同域名最多 6 个并发连接(Chrome 实际 6)

缺点:

  • 增加 TCP 握手成本(每次新连接)
  • 仍不够,现代页面 30+ 资源很常见

3.2 域名分片(Domain Sharding) ​

html
<!-- 把资源分散到多个子域,每个子域 6 个连接 -->
<!-- 主域:example.com -->
<!-- 分片:static1.example.com、static2.example.com -->
<link rel="stylesheet" href="https://static1.example.com/a.css">
<link rel="stylesheet" href="https://static2.example.com/b.css">

效果:6 连接 × 3 子域 = 18 并发

缺点:

  • 增加 DNS 查询
  • 增加 TCP 握手
  • HTTP/2 时代禁用

3.3 资源合并 ​

把多个小资源合并成一个大资源,减少请求数:

雪碧图(CSS Sprite):
  多个小图标合并成一张大图,background-position 定位

合并 JS / CSS:
  一个大 bundle.js 而不是多个小文件

缺点:

  • 维护差(改一个图标要重新合并整个 sprite)
  • 缓存粒度大(改一行 JS 整个 bundle 失效)
  • HTTP/2 时代禁用

3.4 内联资源 ​

html
<style>body { background: red; }</style>
<script>console.log('inline')</script>

缺点:

  • HTML 体积大
  • 不能单独缓存
  • 阻塞关键路径
  • HTTP/2 时代少用

3.5 preload / prefetch ​

html
<!-- preload:高优先级,提前加载 -->
<link rel="preload" href="/critical.css" as="style">

<!-- prefetch:低优先级,提前加载下个路由 -->
<link rel="prefetch" href="/next-page.js">

优点:不改变资源结构,只是提前加载。

四、HTTP/2 的解决方案(根本) ​

HTTP/2 通过多路复用彻底解决:

HTTP/2 单连接:
- 一个 TCP 连接,多个流(stream)
- 每个流有 ID(1、3、5、7、...)
- 请求和响应都拆成帧(Frame)
- 帧可以乱序发送和接收
- 接收方按流 ID 重组
客户端                                服务端
   |  Stream 1 帧 (请求 A)          |
   |  ───────────────────────────→ |
   |  Stream 3 帧 (请求 B)          |
   |  ───────────────────────────→ |
   |                                |  处理 A(慢) + 处理 B(快)
   |  Stream 3 帧 (响应 B)         |
   |  ←─────────────────────────── |
   |  Stream 1 帧 (响应 A)         |
   |  ←─────────────────────────── |

核心:不再有"队"的概念,所有流并行。

五、HTTP/2 的局限 ​

虽然 HTTP/2 多路复用解决了应用层队头阻塞,但TCP 层仍有队头阻塞:

TCP 是字节流:
- 包 1、2、3、4、5 顺序发送
- 包 3 丢失 → 接收方等待包 3 重传
- 包 4、5 已经在接收方缓存,但不能交给应用层(TCP 是顺序的)
- 所有数据都阻塞,直到包 3 到达

HTTP/2 多路复用 → 应用层流可以并行,但底层 TCP 仍是串行:

  • 流 A 的包丢了 → TCP 重传 → 流 B、C、D 全部等待

六、HTTP/3 / QUIC 的最终解决方案 ​

HTTP/3 基于 QUIC(UDP),QUIC 是流级别的:

QUIC 包:
- Header | Stream 1 Frame | Stream 3 Frame | Stream 5 Frame
- 每个流独立 ACK / 重传
- 一个流丢包,只阻塞那个流
Stream 1: 正常
Stream 3: 丢包 → 只重传 Stream 3
Stream 5: 不受影响

七、真实性能数据 ​

7.1 HTTP/1.1(6 连接) ​

首屏 30 个资源:
- 6 个并发 → 5 批
- 每批 200ms(平均)
- 总耗时:1000ms

7.2 HTTP/2(多路复用) ​

首屏 30 个资源:
- 单连接,30 个流并行
- TCP 队头阻塞存在,但资源加载并行
- 总耗时:300~500ms

7.3 HTTP/3 ​

首屏 30 个资源 + 弱网(2% 丢包):
- 流独立,丢包不影响其他流
- 总耗时:200~400ms

八、实战经验 ​

8.1 HTTP/2 配置 ​

nginx

  listen 443 ssl http2;
  # ...
}

# 或
http {
  http2 on;  # 老语法

8.2 HTTP/2 时代,反模式 ​

❌ 雪碧图:不合并,直接独立图 ❌ 域名分片:合并到一个域名 ❌ 内联 CSS / JS:独立文件,长期缓存 ❌ 合并 JS bundle:拆成小包,按需加载

8.3 HTTP/2 仍要的优化 ​

  • 压缩(Brotli > gzip)
  • 缓存(Cache-Control + ETag)
  • 图片优化(AVIF / WebP + 显式宽高)
  • 懒加载(非关键资源)
  • preload(关键资源)
  • CDN

九、面试常考 ​

Q1:HTTP/1.1 队头阻塞是什么? ​

答:HTTP/1.1 一个 TCP 连接上,响应必须按请求顺序返回,前面的慢响应阻塞后面的响应。

Q2:浏览器为什么最多 6 个并发连接? ​

答:HTTP/1.1 一个连接有队头阻塞,只能开多个连接绕开。RFC 2616 建议 2 个,实际浏览器 6 个。

Q3:HTTP/2 怎么解决的? ​

答:

  • 单 TCP 连接多路复用
  • 请求/响应拆成帧
  • 帧带流 ID,可以乱序
  • 接收方按 ID 重组

Q4:HTTP/2 还有队头阻塞吗? ​

答:有,但在 TCP 层。TCP 丢包会阻塞所有 HTTP/2 流。HTTP/3 / QUIC 用 UDP + 独立流彻底解决。
