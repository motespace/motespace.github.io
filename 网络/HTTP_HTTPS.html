1. OSI 七层模型 vs TCP/IP 四层 ​

OSI 七层             TCP/IP 四层           对应协议
─────                ─────                ──────
应用层              ─┐

会话层              ─┘
传输层                传输层              TCP / UDP
网络层                网络层              IP / ICMP / ARP
数据链路层          ─┐
物理层               ├─ 网络接口层         Ethernet / Wi-Fi
                   ─┘

前端关注：应用层（HTTP）、传输层（TCP）。

版本年份核心特性

4. HTTP/2 革命性改进 ​

4.1 二进制分帧（Binary Framing） ​

HTTP/1.1:
  ┌────────────┐
  │ Request 1  │  ← 文本格式
  └────────────┘
  ┌────────────┐
  │ Request 2  │
  └────────────┘

HTTP/2:
  ┌─────┐ ┌─────┐ ┌─────┐
  │帧1-1│ │帧1-2│ │帧2-1│  ← 二进制帧，可交错
  └─────┘ └─────┘ └─────┘
  同一个 TCP 连接，并行传输

4.2 多路复用（Multiplexing） ​

连接 A：
  请求 1 → 响应 1
  请求 2 → 响应 2
  请求 3 → 响应 3

HTTP/2 中：
  单连接上并行传输，没有队头阻塞

4.3 头部压缩（HPACK） ​

http
# HTTP/1.1：每个请求都带完整 header

Accept: */*

# HTTP/2：相同 header 复用 + Huffman 编码
# 头部大小减少 80-90%

4.4 服务器推送（Server Push） ​

HTTP/2：
  浏览器请求 /index.html

5. HTTPS 详解 ​

5.1 为什么需要 HTTPS ​

HTTP 问题：
1. 明文传输：抓包可看所有内容（密码、Cookie）
2. 不验证身份：可能连接到伪装的服务器
3. 不验证完整性：传输过程中可能被篡改

5.2 HTTPS = HTTP + TLS/SSL ​

HTTP
  ↓
TLS 握手（加密通道建立）
  ↓
加密的 HTTP 通信

5.3 TLS 1.3 握手过程（1-RTT） ​

客户端                                  服务器
  │                                      │
  │ ─ Client Hello (支持的加密套件) ─→  │
  │                                      │
  │ ← Server Hello + Certificate ──────  │
  │   (服务器证书 + 公钥)              │
  │                                      │
  │ 验证证书合法性                       │
  │                                      │
  │ ─ Key Share + Finished ─→          │
  │   (用服务器公钥加密的预主密钥)      │
  │                                      │
  │ ← Finished ───────────────────────  │
  │                                      │
  │ ──── 加密的 HTTP 通信 ─────────→   │

对比 TLS 1.2（2-RTT）：TLS 1.3 把握手从 2-RTT 降到 1-RTT，速度提升 50%+。

5.4 证书验证 ​

浏览器收到证书后验证：
1. 证书是否过期
2. 证书是否被 CA 签名（证书链验证）
3. 域名是否匹配（example.com vs www.example.com）
4. 是否被吊销（CRL / OCSP）

8. HTTP 缓存机制（重头戏） ​

8.1 缓存流程 ​

首次请求：服务器返回资源 + 缓存标识
    ↓
二次请求：先看浏览器缓存
    ├── 强缓存命中 → 直接用本地，不发请求
    └── 强缓存未命中 → 发请求，看协商缓存
        ├── 协商缓存命中 → 304，浏览器用本地
        └── 协商缓存未命中 → 200，返回新资源

8.2 强缓存（Cache-Control / Expires） ​

http
# HTTP/1.1（推荐）
Cache-Control: max-age=31536000, immutable

# HTTP/1.0（兼容）
Expires: Wed, 21 Oct 2026 07:28:00 GMT

Cache-Control 指令：

指令含义
max-age=N缓存 N 秒
no-cache不直接用缓存，每次问服务器
no-store完全不缓存
private只允许浏览器缓存，CDN 不能
public所有代理都能缓存
s-maxage=NCDN 缓存 N 秒
immutable永不过期（带 hash 的文件名用）
must-revalidate过期后必须重新验证
stale-while-revalidate=N过期后 N 秒内用旧值

8.3 协商缓存（Last-Modified / ETag） ​

http
# 首次请求，服务器返回资源 + 标识
Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT
ETag: "abc123"

# 二次请求，浏览器带上
If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT
If-None-Match: "abc123"

# 服务器判断
资源未变 → 304 Not Modified（不带 body）
资源变了 → 200 OK（带新资源）

ETag vs Last-Modified：

ETagLast-Modified
精度哈希指纹，精确到内容秒级，文件内容变了但 mtime 没变会漏
性能计算哈希略慢直接读文件时间，快
适用文件经常改动文件改动频率低

8.4 真实项目：缓存策略 ​

js
// 真实代码：来自简历项目
// Next.js 静态资源自动加 hash
import Image from 'next/image'

// webpack/Vite 自动生成：/static/chunks/main.abcd1234.js
// 配合 Cache-Control: max-age=31536000, immutable
// 永不过期，因为 hash 变了文件名就变了

// API 接口：通常不缓存或短期缓存
res.setHeader('Cache-Control', 'no-cache, no-store, must-revalidate')

// 用户头像：协商缓存
res.setHeader('Cache-Control', 'no-cache')
res.setHeader('ETag', generateETag(user.avatar))

8.5 用户操作场景的缓存策略 ​

HTML：no-cache（每次验证最新）
静态资源（带 hash）：max-age=31536000, immutable（永不过期）
静态资源（不带 hash）：no-cache（防止更新后用户拿不到新版本）
API 接口（GET）：no-cache（实时性要求高）
API 接口（POST）：no-store（绝不缓存）

10. HTTP 跨域（CORS） ​

10.1 简单请求 vs 预检请求 ​

http
# 简单请求（不触发预检）
GET /api/data HTTP/1.1
Content-Type: application/x-www-form-urlencoded

# 预检请求（触发 OPTIONS）
POST /api/data HTTP/1.1
Content-Type: application/json    ← 触发预检

触发预检：

  • 非简单方法（PUT、DELETE、PATCH）
  • 非简单请求头（Content-Type: application/json、自定义头）
  • 带 credentials

10.2 真实项目：CORS 配置 ​

js
// 服务端（Node.js）
app.use((req, res, next) => {
  const origin = req.headers.origin
  const allowOrigins = ['https://app.example.com', 'https://admin.example.com']

  if (allowOrigins.includes(origin)) {
    res.header('Access-Control-Allow-Origin', origin)
  }

  res.header('Access-Control-Allow-Methods', 'GET,POST,PUT,DELETE,OPTIONS')
  res.header('Access-Control-Allow-Headers', 'Content-Type,Authorization')
  res.header('Access-Control-Allow-Credentials', 'true')
  res.header('Access-Control-Max-Age', '86400')  // 预检缓存 24h

  // 预检请求直接返回
  if (req.method === 'OPTIONS') return res.sendStatus(200)

  next()
})

12. HTTPS 握手完整流程 ​

客户端                                         服务器
  │                                              │
  │ ─ Client Hello ─────────────────────────→   │
  │   (TLS 版本、加密套件、随机数)               │
  │                                              │
  │ ← Server Hello ───────────────────────────  │
  │   (选定的加密套件、随机数、证书)             │
  │                                              │
  │ 验证证书（用本地 CA 公钥验证签名）          │
  │                                              │
  │ ─ Key Exchange ──────────────────────────→  │
  │   (用服务器公钥加密的预主密钥)               │
  │                                              │
  │ ← Server Finished ────────────────────────  │
  │                                              │
  │ 双方用预主密钥生成对称密钥                   │
  │                                              │
  │ ─ Client Finished ────────────────────────  │
  │                                              │
  │ ─── 加密的 HTTP 通信 ──────────────────────  │

关键点： ​

  • 非对称加密（RSA/ECDHE）用于交换密钥
  • 对称加密（AES）用于加密实际数据
  • 散列（SHA-256）用于完整性校验

13. HTTP/3 和 QUIC ​

13.1 QUIC 解决什么问题 ​

TCP 的队头阻塞：
  TCP 是可靠传输，丢包会重传
  HTTP/2 虽然多路复用，但 TCP 层丢包阻塞所有流

QUIC 基于 UDP：
  - 独立流（一个流丢包不影响其他流）
  - 内置 TLS 1.3
  - 握手 0-RTT（更快）
  - 连接迁移（IP 变了不用重新连接）

13.2 真实项目：HTTP/3 支持 ​

nginx
# Nginx 1.25+ 支持 HTTP/3
server {
  listen 443 ssl;
  http2 on;
  http3 on;       # 启用 HTTP/3
  quic_retry on;

  # QUIC 需要 UDP 443
  add_header Alt-Svc 'h3=":443"; ma=86400';
}

14. DNS 解析流程 ​

1. 浏览器缓存 → 命中返回
2. 系统缓存（hosts）→ 命中返回
3. 本地 DNS 服务器 → 命中返回
4. 根 DNS 服务器 → 返回顶级域（TLD）服务器地址
5. TLD 服务器（.com）→ 返回权威 DNS 服务器地址
6. 权威 DNS 服务器 → 返回 IP

DNS 优化：

html
<link rel="dns-prefetch" href="//api.example.com">
<link rel="preconnect" href="https://cdn.example.com" crossorigin>

15. TCP 三次握手与四次挥手 ​

15.1 三次握手（建立连接） ​

客户端                                    服务器
  │                                       │
  │ ─ SYN seq=x ────────────────────────→ │  ← 第一次
  │                                       │
  │ ← SYN seq=y, ACK=x+1 ─────────────── │  ← 第二次
  │                                       │
  │ ─ ACK=y+1 ──────────────────────────→ │  ← 第三次
  │                                       │
  │ ──── 数据传输 ──────────────────────→ │

为什么是 3 次：确保双方都能收发。

15.2 四次挥手（关闭连接） ​

客户端                                    服务器
  │                                       │
  │ ─ FIN seq=x ────────────────────────→ │  ← 第一次
  │                                       │
  │ ← ACK=x+1 ────────────────────────── │  ← 第二次
  │                                       │
  │ ← FIN seq=y, ACK=x+1 ─────────────── │  ← 第三次
  │                                       │
  │ ─ ACK=y+1 ──────────────────────────→ │  ← 第四次
  │                                       │

为什么是 4 次：服务器可能还有数据要发，FIN 和 ACK 分开发。

16. WebSocket ​

16.1 为什么需要 WebSocket ​

HTTP 缺点：
- 单向：只能客户端发起请求
- 实时性差：长轮询效率低
- 头部冗余：每次请求都带 header

WebSocket 优点：
- 全双工：双向通信
- 实时：基于 TCP 长连接
- 轻量：建立连接后只需 2 字节帧头

16.2 握手过程 ​

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...

17. 真实项目完整网络流程 ​

17.1 会员登录完整流程 ​

1. 用户输入账号密码
2. 前端 RSA 加密密码（来自 merchant 项目）
3. POST https://api.example.com/login
   - Body: { username: "tom", password: "x8j$k2..." }
   - Headers: { Content-Type: application/json, timezone: "Asia/Shanghai" }
4. 服务器验证账号密码，签发 token
5. 返回 { token: "eyJhbGc..." } + Set-Cookie
6. 前端存储 token（Cookie 或 localStorage）
7. 后续请求自动带 Authorization: Bearer xxx

18. 面试常考 ​

题目答案要点
HTTP/1.1 队头阻塞一个连接只能处理一个请求-响应
HTTP/2 多路复用单连接并行多个请求-响应，二进制分帧
HTTP/2 头部压缩HPACK 算法，相同 header 复用
HTTP/3 基于什么协议QUIC（UDP）
强缓存 vs 协商缓存强不发请求；协商发请求看 304
Cache-Control 常用值max-age / no-cache / no-store / immutable
HTTPS 握手过程TLS 1.3 是 1-RTT，TLS 1.2 是 2-RTT
CORS 预检OPTIONS 请求，检查方法/头部是否允许
SameSite 三个值Strict / Lax / None
TCP 三次握手SYN → SYN+ACK → ACK
TCP 四次挥手FIN → ACK → FIN → ACK

19. 项目踩过的坑 ​

  1. HTTPS 混合内容：页面 HTTPS，但图片/JS 是 HTTP，浏览器会拦截。
  2. Cookie 没设 SameSite=Lax：CSRF 攻击窗口。
  3. Cookie 没设 HttpOnly：XSS 直接偷 token。
  4. 静态资源没设缓存：每次都重新下载，浪费带宽。
  5. 带 hash 的 JS 设了 no-cache：反而更慢。
  6. Nginx 没开 HTTP/2：HTTPS 性能没完全发挥。
  7. 跨域 CORS 漏配预检：非简单请求失败。
  8. Token 没设过期时间：永久有效的 token 是定时炸弹。

20. 网络安全清单 ​

[ ] 全站 HTTPS（含子域名）
[ ] HSTS 强制 HTTPS
[ ] Cookie 设 HttpOnly + Secure + SameSite
[ ] 启用 CSP
[ ] 静态资源带 hash + Cache-Control: immutable
[ ] API 接口设 no-cache
[ ] 接口合并到 BFF 层（减少跨域请求）
[ ] 关键接口要求 CSRF Token
[ ] 登录异常检测
[ ] 限流保护（防止 DDoS）
[ ] 错误监控 + 告警
