Cookie 与 Session 深度解析

一、为什么需要会话管理

Section titled “一、为什么需要会话管理”

HTTP 是无状态协议——每次请求都是独立的,服务端不知道“这个请求和上一个是不是同一个用户发的”。

要实现“登录后保持登录状态”,需要一种会话机制:

  • 服务端:Session(服务端内存/存储中的状态)
  • 客户端:Cookie(浏览器自动带上的小数据)

二、Cookie 是什么

Section titled “二、Cookie 是什么”

Cookie 是服务端通过 Set-Cookie 头让浏览器存储、之后自动在请求中带上的一小段数据。

关键认识:

  • Cookie 是服务端通过 Set-Cookie 响应头让浏览器存储的一小段数据
  • 浏览器只在同源 + 符合属性条件时才会自动带上,这是和 localStorage 的核心区别

2.1 Cookie 容量与数量

Section titled “2.1 Cookie 容量与数量”
  • 单个 Cookie 4KB 左右(浏览器差异)
  • 一个域名最多 ~50 个 Cookie
  • 总数有限,大数据用 localStorage / IndexedDB

Section titled “三、Cookie 六大属性”

3.1 Domain

Section titled “3.1 Domain”
  • 不指定:只对当前域生效
  • 指定:对当前域和所有子域生效

3.2 Path

Section titled “3.2 Path”

只对 /api 及子路径生效。

实战经验:默认用 Path=/,简化配置。

3.3 Max-Age / Expires

Section titled “3.3 Max-Age / Expires”
  • 不设置:会话 Cookie(浏览器关闭就删除)
  • 设置:持久化

3.4 HttpOnly

Section titled “3.4 HttpOnly”

JS 读不到(document.cookie 看不到)——防 XSS 偷 cookie。

3.5 Secure

Section titled “3.5 Secure”

只在 HTTPS 传输——防明文泄露。

3.6 SameSite

Section titled “3.6 SameSite”
SameSite 跨域 GET 跨域 POST 表单 跨域 AJAX
Strict ❌ ❌ ❌
Lax(默认) ✅ ❌ ❌
None ✅ ✅ ✅

实战配置:

  • 支付/转账/敏感:Strict
  • 一般登录态:Lax(默认)
  • 跨站必需(嵌入场景):None + Secure

实战配置建议:

  • 支付/银行/敏感操作:Strict — 任何跨站都不带,最安全(代价:从外部链接进入会丢登录态)
  • 一般登录态:Lax(默认) — 平衡安全(防 POST CSRF)与体验(允许链接跳转带登录态)
  • 跨站必需(SSO / 嵌入场景):None + Secure — Chrome 拒绝 SameSite=None 但不带 Secure 的 Cookie

🎯 面试常考

Section titled “🎯 面试常考”

Q1：Cookie 的六大属性分别是什么?HttpOnly 和 Secure 一定要加吗?

Section titled “Q1：Cookie 的六大属性分别是什么?HttpOnly 和 Secure 一定要加吗?”
属性 作用 风险
Domain 限定发送的域 不设则只发当前域;设成 .a.com 会发给所有子域,子域被 XSS 时 token 就泄漏了
Path 限定路径 默认当前目录,常见做法设 /
Expires / Max-Age 过期时间 Max-Age 优先
HttpOnly 禁止 JS 读取 必加,否则 XSS 能直接偷 token
Secure 只走 HTTPS 必加
SameSite 跨站是否携带 Lax(默认)/ Strict / None

Secure 一定要加,但要注意:开发环境是 http,加了 Secure cookie 在 http 下不会被存, 本地调试会「登录状态莫名其妙丢了」。本地用 Secure: process.env.NODE_ENV === 'production'。

Q2：Session 是什么?Session 存在服务端还是客户端?

Section titled “Q2：Session 是什么?Session 存在服务端还是客户端?”

Session 是服务端保存的会话状态,客户端只拿一个不可猜测的 ID(通常放在 Cookie 里)。

为什么 Session ID 要足够随机:它是唯一的凭证,被猜到就能冒用别人的会话。 所以要用加密随机数(不是自增 ID),并设置过期 + 空闲超时。

服务端存哪:内存(重启即丢)、Redis(常用)、数据库。 集群部署必须用共享存储,否则用户在 A 节点登录、请求打到 B 节点就「掉线」了。

Q3：Cookie 和 Session 怎么选?JWT 是不是更好?

Section titled “Q3：Cookie 和 Session 怎么选?JWT 是不是更好?”
Cookie + Session JWT
状态存哪 服务端 客户端(自带)
服务端能否主动失效 ✅ 能(删 session) ❌ 难(要等过期或加黑名单)
载荷大小 小(只有 ID) 大(自带信息,每个请求都带)
水平扩展 需要共享存储 ✅ 无状态
续期 服务端可刷新 麻烦

建议:

  • 后台管理系统、需要「踢人下线」→ Session(或短 JWT + 服务端黑名单)
  • 微服务 / 多端 / 第三方接入 → JWT

JWT 的常见误区:「JWT 无状态所以更快」——但每次请求都要带完整 token 并验签, 大载荷反而更慢;而且无法主动失效,只能等过期或加黑名单。

Q4：SameSite 三个值分别什么时候用?

Section titled “Q4：SameSite 三个值分别什么时候用?”
  • Strict:跨站请求完全不带 Cookie。最安全,但从外部链接跳过来会「掉登录态」
  • Lax(现代浏览器默认):顶级导航的 GET 会带 Cookie,POST 不带。这是平衡点
  • None:跨站也带,必须配 Secure,用于跨站 iframe / 第三方登录回调

默认值的历史:老浏览器默认 None(不限制),Chrome 80(2020)开始默认 Lax。 这导致一批老系统升级后突然「跨站登录回调丢失 Cookie」。

CSRF 防护:SameSite=Lax 能挡掉大部分 CSRF(表单 POST 是跨站非导航,不带 Cookie), 但不能完全替代 Token 校验 —— 因为存在「顶级导航 GET」这种 Lax 也拦不住的场景 (比如 <img src="https://evil.com/transfer?to=attacker&amount=1000"> 就能触发 GET)。

📝 小结

Section titled “📝 小结”
  • Cookie 六大属性里 HttpOnly / Secure / SameSite 是三个安全属性,生产环境都要配。
  • Session 的状态在服务端,客户端只拿不可猜测的随机 ID;集群部署必须用共享存储(Redis)。
  • Session vs JWT 的核心差别是能不能主动失效,不是「谁更快」——JWT 每次都要带完整载荷验签,大载荷反而更慢。
  • SameSite 默认 Lax 是 2020 年后的浏览器行为,老系统升级后可能突然出现「跨站回调丢 Cookie」。
