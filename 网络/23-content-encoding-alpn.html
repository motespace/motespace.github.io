内容压缩与 ALPN ​

压缩决定「传输多少字节」,ALPN 决定「用什么协议传输」——两个都在 HTTP 协商阶段完成。

一、Content-Encoding:传输层压缩 ​

浏览器怎么协商 ​

http
# 请求:我能接受这些压缩
GET /app.js HTTP/1.1
Accept-Encoding: gzip, deflate, br, zstd
http
# 响应:我用了 br
HTTP/1.1 200 OK
Content-Encoding: br
Content-Length: 84213
Vary: Accept-Encoding

Vary: Accept-Encoding 很重要 —— CDN 要靠它区分「gzip 版」和「br 版」的缓存,否则会把压缩过的版本发给不支持的客户端。

各算法对比 ​

算法压缩率解压速度支持情况
gzip基准快全部
Deflate≈ gzip快全部(但有 zlib 头,兼容性坑)
Brotli (br)比 gzip 小 15~25%慢一点Chrome / Firefox / Edge / Safari 16.4+
Zstd比 br 略好,接近 gzip 速度最快Chrome 123+ / Safari 18+

关键:br 的收益要动态压缩才拿得到。Nginx 静态文件用 gzip_static 预压缩成 .gz 文件,而不是实时压缩,这样 br 也享受得到。

nginx
gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;
gzip_min_length 1024;

# 预压缩:构建时生成 .br / .gz 文件
brotli_static on;
gzip_static on;

为什么不是所有资源都压缩 ​

资源压缩收益原因
HTML / CSS / JS / JSON / SVG大文本冗余多,能压 60~80%
图片(JPG/PNG/WebP)无本身已是压缩格式
视频 / 音频无已是压缩编码
已压缩的字体(woff2)无压不动还白费 CPU

别压图片 —— 这是最常见的无效优化,白白消耗 CPU 还可能让体积变大。

压缩和图片格式是两件事 ​

photo.jpg (500KB)  --图片优化--> photo.avif (200KB)  --再 gzip--> 195KB

图片走「格式转换 + 尺寸适配」,不走 gzip。两者的收益不叠加。

二、ETag 与压缩的配合 ​

压缩后每次请求的字节都不一样(取决于客户端支持的算法),所以缓存要用 ETag:

http
ETag: "a1b2c3-17482943"

服务端根据「内容 + 压缩算法」算 ETag,不同算法对应不同 ETag,客户端带的 If-None-Match 不匹配时才重新发。

三、ALPN:在 TLS 握手里协商应用层协议 ​

HTTP/2 和 HTTP/3 都不是「在 HTTP 里升级」,而是在** TLS 握手里直接协商好**。ALPN(Application-Layer Protocol Negotiation)就是干这个的扩展。

握手过程 ​

http
# 客户端在 ClientHello 里带上支持的协议列表
ALPN: h2, http/1.1
http
# 服务端在 ServerHello 里回一个
ALPN: h2

之后这条连接上跑的全是 HTTP/2,不需要再发 Upgrade 请求。

支持矩阵 ​

协议传输层协商方式
HTTP/1.1TCP直接用
HTTP/2TCPTLS ALPN(h2c 除外)
HTTP/3QUIC(UDP)QUIC 自己的 ALPN,不需要 TLS

HTTP/3 的特殊之处:它跑在 QUIC 上,QUIC 把 TLS 1.3 集成进了协议内部,所以不用先建 TLS 连接再协商 ALPN —— 一次 UDP 往返就完成了加密握手 + 协议协商。

为什么 HTTP/3 不走 TCP ​

问题TCPQUIC
多路复用有队头阻塞(丢一个包,整个连接卡住)每个流独立,丢一个只影响那条流
连接迁移换网络要重连用 Connection ID,换网继续用
握手1-RTT(TLS1.3)1-RTT(加密集成)
首包需要先建连接0-RTT(会话恢复时)

注意:HTTP/2 的队头阻塞在传输层被解决了(多路复用),但TCP 层的队头阻塞还在 —— 一个 TCP 包丢了,后面所有流都得等重传。HTTP/3 用 UDP + 独立重传彻底解决了这个问题。

四、浏览器怎么选 ​

http
# Chrome 的请求头
Accept-Encoding: gzip, deflate, br, zstd

顺序不重要 —— 服务端按自己的优先级选,通常 br > gzip > zstd。Nginx 的 gzip_vary 和 brotli 模块都支持。

服务端优先级可配:

nginx
brotli on;
brotli_types text/plain text/css application/javascript application/json image/svg+xml;
brotli_comp_level 5;      # 1~11,默认 6,5 是压缩率和速度的平衡点

gzip on;
gzip_types text/plain text/css application/javascript application/json image/svg+xml;
gzip_comp_level 5;

br_comp_level 怎么选 ​

level压缩率速度适合
1低极快动态响应、CPU 紧张
5中高快大多数场景的推荐值
11最高慢静态资源、预压缩

动态内容(每个请求都不一样)用低 level,静态文件用高 level 预压缩。

五、完整优化清单 ​

nginx
# 1. 传输压缩:静态资源预压缩 br + gzip
brotli_static on;
gzip_static on;

# 2. HTTP/2 + HTTP/3
http2 on;

# 3. 长连接 + 多路复用(默认就是)
keepalive_timeout 65;

# 4. 不要压图片
# gzip_types 里不要加 image/*
✓ 文本资源开 br(静态预压缩)
✓ 图片转 AVIF/WebP 而不是压缩
✓ 开启 HTTP/2,条件允许上 HTTP/3
✓ Vary: Accept-Encoding 必须有
✓ ETag 要包含压缩算法维度

🎯 面试常考 ​

Q1: Brotli 比 gzip 好在哪? 压缩率高 15~25%(同样设置下),而且支持「静态字典」,对 HTML 中的常见字符串压缩尤其有效。代价是解压稍慢、CPU 占用略高。对静态资源收益最大。

Q2: 为什么要预压缩而不是实时压缩? 实时压缩每个请求都要压一次,消耗 CPU 且增加 TTFB。预压缩(build 时生成 .br / .gz)只压一次,运行时直接发文件,零 CPU 成本。Nginx 的 brotli_static on 就是干这个的。

Q3: Vary: Accept-Encoding 忘了配会怎样? CDN 会把 gzip 版缓存给不支持 br 的客户端(或者反过来),导致浏览器解不开而报错。必须配 Vary: Accept-Encoding,让缓存按压缩能力分桶。

Q4: ALPN 是什么? TLS 握手中的扩展。客户端在 ClientHello 里列出支持的协议(h2、http/1.1),服务端在 ServerHello 里选一个,之后这条连接就用该协议。HTTP/2 和 HTTP/3 都靠它协商,而不是运行时 Upgrade。

Q5: HTTP/2 已经解决了队头阻塞,为什么还要 HTTP/3? HTTP/2 只解决了 HTTP 层的队头阻塞(多路复用),TCP 层的还在:一个 TCP 段丢失,所有流都要等它重传。HTTP/3 基于 QUIC(UDP),每条流独立重传,并支持连接迁移和 0-RTT,彻底解决了 TCP 层的队头阻塞。

Q6: 为什么不该 gzip 图片? JPG / PNG / WebP / AVIF 本身是压缩格式,再 gzip 基本压不动(通常还可能变大),纯粹浪费 CPU。图片优化靠格式转换和尺寸适配,不走 Content-Encoding。

📝 小结 ​

  • 压缩要分清:文本资源用 br/gzip,图片走格式转换,两者收益不叠加。
  • 静态资源预压缩(br_static)收益最大:零运行时 CPU。
  • Vary: Accept-Encoding 和带算法维度的 ETag 是压缩方案的必需配套。
  • ALPN 在 TLS 握手里协商 HTTP 协议;HTTP/3 基于 QUIC,连 TLS 握手都省了一次往返。
