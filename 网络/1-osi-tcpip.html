OSI 七层模型 vs TCP/IP 四层 ​

一、为什么需要分层 ​

网络通信是复杂的:从浏览器输入 https://example.com 到看到页面,数据经历了应用、传输、网络、链路多个处理步骤。

分层的好处:

  • 关注点分离:每层只关心自己的职责
  • 替换性:某一层升级不影响其他层(如 HTTP/1.1 → HTTP/2)
  • 标准化:各层有统一协议,不同厂商可以互操作
  • 调试方便:出问题能定位到具体哪一层

二、OSI 七层模型(理论) ​

OSI 是 1984 年 ISO 提出的理论模型,实际互联网用的少,但概念常被引用:

前端开发关注:主要是 7(应用层)和 4(传输层)。

数据流方向:发送方自顶向下封装,接收方自底向上解封装。每层只处理自己的协议头,不关心上层数据。

三、TCP/IP 四层模型(实际) ​

实际互联网用的是 TCP/IP 四层(或五层) 模型:

前端工程师关注:

应用层 + 传输层是前端的主战场 — 协议选择、性能调优、跨域、缓存都在这两层。

注:TCP/IP 模型由 DARPA 在 1970s 提出,先有实践后有标准 · OSI 反之。

  • 应用层:HTTP/HTTPS 是日常打交道最多的
  • 传输层:TCP vs UDP 选择会影响性能(如 WebSocket 用 TCP,HTTP/3 用 UDP+QUIC)

四、各层数据包格式 ​

封装/解封装:

  • 发送方:数据 → 应用 → 传输 → 网络 → 链路 → 物理
  • 接收方:物理 → 链路 → 网络 → 传输 → 应用 → 数据

每层只处理自己的头部,不关心上层数据。

每层 PDU(协议数据单元)的名字:

  • L7 报文(Message) · L4 段(Segment) · L3 包(Datagram) · L2 帧(Frame) · L1 比特流(Bits)

解封装过程:接收方反向操作 — 物理层接收 → 链路层剥 MAC 头 → 网络层剥 IP 头 → 传输层剥 TCP 头 → 应用层拿到 HTTP 报文。

前端不直接接触这个过程,但理解它有助于排查 HTTPS、跨域、连接复用等问题。

五、实际例子:打开 https://example.com 的过程 ​

浏览器输入 URL → 解析域名
  ↓ DNS 解析(应用层,DNS 协议)
得到 IP 地址 1.2.3.4
  ↓ TCP 三次握手(传输层)
建立到 1.2.3.4:443 的连接
  ↓ TLS 握手(表示层,SSL/TLS)
加密通道建立
  ↓ HTTP 请求(应用层)
GET / HTTP/1.1
  ↓ 数据包经过链路层(以太网)、物理层(网线)
到达服务器
  ↓ 服务器响应,反向链路
浏览器接收 HTML → 解析渲染

前端优化点在应用层和传输层:

  • 应用层:缓存、压缩、HTTPS、HTTP/2
  • 传输层:TCP 连接复用、长连接、QUIC

八、性能优化与分层 ​

不同层有不同的优化策略:

应用层:
├── HTTP/2 多路复用
├── HTTP/3 QUIC
├── 缓存(强缓存 / 协商缓存)
├── 压缩(Brotli / gzip)
└── 减少请求数(雪碧图、合并、懒加载)

传输层:
├── TCP 连接复用(Keep-Alive)
├── TCP Fast Open
└── QUIC(0-RTT 握手)

网络层:
├── CDN(就近访问)
└── Anycast IP

链路层:
└── 网络硬件优化(无能为力,运营商决定)

🎯 九、面试 ​

9.1 输入 URL 到页面渲染经历了什么? ​

1. URL 解析
2. DNS 解析(应用层)
3. TCP 连接(传输层)
4. TLS 握手(表示层)
5. HTTP 请求(应用层)
6. 服务器响应
7. 浏览器解析 HTML → DOM 树
8. 解析 CSS → CSSOM
9. 合并 → Render Tree
10. 布局 + 绘制 + 合成
11. 显示

9.2 OSI 七层 vs TCP/IP 四层的对应? ​

面试回答要点:

  • OSI 是理论参考,实际工程不用;TCP/IP 是事实标准;浏览器/服务器都是按 TCP/IP 实现的
  • OSI 的表示层(SSL/TLS 加密)与会话层(连接管理)在 TCP/IP 中被并入应用层
  • OSI 的数据链路层 + 物理层在 TCP/IP 中合并为网络接口层,因为驱动同时管两者

9.3 TCP 三次握手为什么不是两次? ​

为什么是三次,不是两次?

两次握手的隐患:服务端发出 SYN+ACK 后,无法确认客户端是否真的收到了。如果历史 SYN 延迟到达,客户端会丢弃;但服务端的 SYN+ACK 会一直等,浪费资源。

三次 = 双方各确认一次对方能收能发 — 最小可靠次数。

9.4 HTTPS 的 TLS 握手过程? ​

TLS 1.3 主要改进:

  • 握手从 2-RTT 压到 1-RTT — 客户端首次请求就带上 key share 假设密钥,服务端回复时直接协商
  • 移除不安全算法(RSA 密钥交换、MD5、SHA-1),仅支持前向保密(PFS)的密钥交换(ECDHE)

0-RTT 模式(可选项):客户端可在首次连接时发送加密数据,服务端立即处理,但有重放攻击风险
