预取、预渲染与优先级提示 ​

用户还没点,就把下一页准备好 —— 这一组技术专门解决「点击到看到内容」之间的空白。

一、四个层次 ​

从轻到重:

手段做什么成本适用
<link rel="prefetch">下载资源,不解析最低下个页面大概率会用到
<link rel="preload">下载 + 提前解析低当前页面马上要用的关键资源
<link rel="prerender">下载 + 完整渲染成 HTML中下一个路由几乎确定
Speculation Rules浏览器自动按规则执行上面的可配有明确导航模式的站点

关键区别:preload 是「这个页面马上要用」,prefetch 是「下个页面可能要用」,用错会抢带宽。

二、preload vs prefetch ​

html
<!-- 首屏关键 CSS:必须 preload(它会阻塞渲染) -->
<link rel="preload" href="/critical.css" as="style" />
<link rel="stylesheet" href="/critical.css" />

<!-- 下个页面才用的 chunk:prefetch -->
<link rel="prefetch" href="/next-page-chunk.js" as="script" />
preloadprefetch
优先级HighLow
什么时候用当前页面马上要空闲时下载,不确定要不要
滥用后果抢带宽,拖慢关键资源浪费流量和电量

常见错误:把 prefetch 当 preload 用,或者把所有资源都 preload,结果关键资源反而更慢。

三、优先级提示(Priority Hints) ​

浏览器给每个请求一个默认优先级,但可以用 fetchpriority 覆盖:

html
<!-- 首屏 LCP 图片:最高优先级 -->
<img src="/hero.jpg" fetchpriority="high" alt="封面" />

<!-- 预加载字体 -->
<link rel="preload" href="/font.woff2" as="font" type="font/woff2" crossorigin />

<!-- 明确不要的 -->
<img src="/below-fold.jpg" fetchpriority="low" alt="" />
html
<!-- 关键 CSS 高优先级 -->
<link rel="preload" href="/critical.css" as="style" fetchpriority="high" />

注意:fetchpriority 只影响优先级,不改变「什么时候开始下载」。要提前下载还得配 preload/prefetch。

四、Speculation Rules ​

让浏览器按规则自动决定预取什么:

html
<script type="speculationrules">
{
  "prerender": [
    {
      "where": { "href_matches": "/products/*" },
      "eagerness": "moderate"
    }
  ],
  "prefetch": [
    {
      "where": { "href_matches": "/docs/*" },
      "eagerness": "low"
    }
  ]
}
</script>

eagerness 的三档 ​

值触发时机用途
low页面加载后,空闲时保守,省流量
moderate指针悬停 / 聚焦链接时最常用,用户有意图才预取
eager页面加载立刻激进,只给确定会去的页面

moderate 是最佳实践 —— 用户鼠标移到链接上才预取,既准又不浪费。

规则可以按条件组合 ​

json
{
  "prefetch": [{
    "where": {
      "href_matches": "/articles/*",
      "selector_matches": ".article-link",
      "not": { "href_matches": "/articles/premium/*" }
    },
    "eagerness": "moderate"
  }]
}

五、预渲染的副作用 ​

prerender 会真的执行页面的 JS,意味着:

  • 埋点会重复上报
  • 接口请求会真的发出去
  • 有可能触发写操作(如果页面里有)

防护:

js
// 在页面里判断是否处于预渲染状态
if (document.prerendering) {
  // 跳过埋点、跳过非必要请求
}
document.addEventListener('prerenderingchange', () => {
  if (!document.prerendering) {
    // 真正被展示了,这时再上报埋点
  }
})
html
<!-- 也可以用 referrerPolicy 区分 -->
<script type="speculationrules">
{ "prerender": [{ "where": {...}, "eagerness": "moderate" }] }
</script>

六、效果怎么验证 ​

js
// Resource Timing 里能看到请求的优先级信息
performance.getEntriesByType('resource').forEach(r => {
  if (r.name.includes('next-page')) {
    console.log(r.name, r.responseStart - r.startTime, r.nextHopProtocol)
  }
})

对比开/关预取的 LCP 和 INP:

js
import { onLCP, onINP } from 'web-vitals'
onLCP(report)
onINP(report)

注意:预取的效果在实验室里不明显(网络太快),必须在真实弱网下用 RUM 验证。

七、什么时候别用 ​

情况原因
用户只停留 2 秒就跳走预取的内容没用,纯浪费
移动端流量敏感prefetch 会耗电耗流量
站点导航模式不可预测预取命中率低
后端扛不住预渲染带来的请求prerender 会真的发请求

先看数据再决定:统计用户的后续导航路径,找出命中率最高的几个模式,只对那几个做预取。

🎯 面试常考 ​

Q1: preload 和 prefetch 的区别? preload 是「当前页面马上要用」,优先级 High,配合 as 属性指明资源类型;prefetch 是「下个页面可能要用」,优先级 Low,空闲时下载。用错(把 prefetch 当 preload)会抢带宽拖慢关键资源。

Q2: fetchpriority 解决什么问题? 浏览器给资源分配的默认优先级不一定符合你的意图。fetchpriority="high" 可以让首屏 LCP 图片优先下载,"low" 让折叠下方的图片让路。它只调优先级,不改变下载时机。

Q3: Speculation Rules 的 eagerness 怎么选?low 页面加载后空闲时执行;moderate 指针悬停/聚焦时执行(最常用,用户有意图才预取);eager 立刻执行(激进)。生产环境推荐 moderate。

Q4: 预渲染有什么风险? prerender 会真的执行页面 JS,导致埋点重复上报、接口请求重复发出,甚至触发写操作。用 document.prerendering 判断状态并跳过副作用。

Q5: 预取的效果怎么衡量? 用 RUM 对比开/关前后的 LCP 和 INP,并统计预取命中率(预取后用户是否真的去了那个页面)。实验室环境网络太快,看不出真实效果。

📝 小结 ​

  • 四个层次:prefetch(下载) < preload(下载+解析) < prerender(下载+渲染)< Speculation Rules(自动编排)。
  • preload 给当前页面的关键资源,prefetch 给下个页面,别用混。
  • fetchpriority 调优先级不改变时机,和 preload 是配合关系。
  • Speculation Rules 推荐 eagerness: "moderate",并用 document.prerendering 防副作用。
