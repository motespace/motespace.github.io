性能监控体系:从 SDK 到看板 ​

一、为什么需要性能监控 ​

没有监控,性能优化就是"凭感觉"。真实用户的体验和本地 Lighthouse 可能差很多:

  • 不同地区用户网络环境不同(国内 4G vs 5G vs 弱网)
  • 不同设备性能差异巨大(iPhone 15 vs 千元安卓)
  • 不同入口差异(直访 / 落地页 / 第三方链接)

只有 RUM(Real User Monitoring)数据才能反映真实场景。

二、监控的三大类指标 ​

2.1 Core Web Vitals(核心) ​

Google 钦定的三个核心指标,直接影响 SEO 排名:

指标含义优秀需优化
LCP(Largest Contentful Paint)最大内容绘制时间< 2.5s> 4.0s
INP(Interaction to Next Paint)交互到下一帧< 200ms> 500ms
CLS(Cumulative Layout Shift)累积布局偏移< 0.1> 0.25

注:2024 年起 FID(First Input Delay)已被 INP 取代。

2.2 加载性能 ​

  • FCP(First Contentful Paint):首次内容绘制
  • TTFB(Time to First Byte):首字节时间,衡量服务端响应
  • TBT(Total Blocking Time):总阻塞时间(主线程被长任务阻塞的累计时长)

2.3 业务自定义 ​

  • 首屏接口响应时间
  • 关键按钮点击到反馈时间
  • 路由切换耗时
  • 表单提交耗时

核心 vs 业务的关系:Core Web Vitals 是"通用健康度",业务指标是"用户行为路径"——两者结合才能定位真问题。

三、SDK 选型与自建 ​

3.1 商业方案 ​

方案优势劣势
Sentry错误 + 性能 + Session Replay 一体海外服务,国内慢
Datadog RUM全栈可观测性贵
阿里云 ARMS国内快,集成度高阿里云绑定
神策 / GrowingIO行为分析 + 性能重业务,性能弱

3.2 自建(web-vitals + 自有上报) ​

适合场景:对成本敏感、数据安全要求高、需要完全自定义。

ts
// web-vitals v4+ 标准用法
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals'

function sendToMonitor(name: string, value: number, rating: string) {
  navigator.sendBeacon('/api/perf', JSON.stringify({
    metric: name,
    value,
    rating,
    url: location.pathname,
    ua: navigator.userAgent,
    t: Date.now(),
  }))
}

// 自动绑定
onLCP((m) => sendToMonitor('LCP', m.value, m.rating))
onINP((m) => sendToMonitor('INP', m.value, m.rating))
onCLS((m) => sendToMonitor('CLS', m.value, m.rating))
onFCP((m) => sendToMonitor('FCP', m.value, m.rating))
onTTFB((m) => sendToMonitor('TTFB', m.value, m.rating))

关键点:

  • 用 sendBeacon 而非 fetch——页面卸载时也能保证上报成功
  • 上报字段要包含 URL、UA、时间戳——后续才能切片分析
  • 用 rating 字段直接判定"好/中/差",省去服务端计算

四、长任务监控 ​

为什么要单独监控:Core Web Vitals 看的是用户感知,但主线程长任务是 INP 的根因,需要单独抓。

ts
const longtaskObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // entry.duration > 50ms 即为长任务
    if (entry.duration > 50) {
      navigator.sendBeacon('/api/perf/longtask', JSON.stringify({
        duration: entry.duration,
        startTime: entry.startTime,
        name: entry.name,
        url: location.pathname,
      }))
    }
  }
})

longtaskObserver.observe({ entryTypes: ['longtask'] })

实战经验:

  • 单个长任务 > 50ms 就要警惕

  • 200ms 几乎必然导致 INP 掉档

  • 看到长任务优先用 scheduler.yield()(Chrome 129+)或 MessageChannel 拆解

五、错误监控与性能关联 ​

性能问题常常是错误的副作用:

ts
// 捕获未处理的 Promise rejection + 性能打点
window.addEventListener('unhandledrejection', (e) => {
  // 上报时附带当前页 LCP,方便关联分析
  sendToMonitor('error', {
    type: 'unhandledrejection',
    reason: String(e.reason),
    lcp: performance.getEntriesByType('largest-contentful-paint')[0]?.startTime,
  })
})

Sentry 自带 BrowserTracing 集成,自动把 trace 和 error 关联——看一个错误,能看到发生前的完整事务链路。

六、自定义业务指标 ​

ts
// 性能 API 打点
performance.mark('list-start')
await fetchList()
performance.mark('list-end')
performance.measure('list-fetch', 'list-start', 'list-end')

const measure = performance.getEntriesByName('list-fetch')[0]
sendToMonitor('step', { name: 'list-fetch', duration: measure.duration })
ts
// 用户交互延迟
button.addEventListener('click', () => {
  const t0 = performance.now()
  // 业务逻辑...
  requestAnimationFrame(() => {
    sendToMonitor('click-feedback', {
      duration: performance.now() - t0,
    })
  })
})

七、看板设计 ​

性能监控不是为了看数据,是为了定位问题。看板要能回答:

  1. 整体健康度:P50/P75/P95 的 LCP/INP/CLS 趋势(按周)
  2. 分页面性能:哪个页面最慢(LCP Top10 页面)
  3. 分地区/网络:4G / 5G / WiFi / 弱网下分别多少
  4. 长任务热点:哪些脚本频繁触发长任务
  5. 错误关联:性能下降 + 错误率上升同时发生的时间窗口

实战经验:把"性能告警阈值"配置在 P95(而不是 P50)——前端 LCP 偶尔高很正常,只有 P95 持续恶化才是真问题。

八、采样与成本 ​

性能上报很贵——每个用户每个 PV 都会触发。

ts
// 采样:10% 用户上报完整数据
if (Math.random() > 0.1) return

// 或按用户分桶
const userBucket = hashUserId(userId) % 100
if (userBucket >= 10) return

实战经验:用 hashUserId(id) % 100 而不是 Math.random()——同一用户始终在同一桶,数据有连贯性。

🎯 面试常考 ​

Q1：性能监控应该埋哪些指标?

三大类:核心体验(Core Web Vitals)、加载性能(TTFB、FCP、LCP、资源耗时)、运行时(内存、Long Task、慢接口)。

Q2：RUM 和合成监控怎么选?

RUM(真实用户监控)反映真实体验,是判断优化效果的唯一依据;合成监控(Lighthouse/WebPageTest)可控可重复,适合发版前的回归验证。两者互补,不能互相替代。

📝 小结 ​

  • 监控体系分三层:SDK 采集(错误 / 性能 / 行为)→ 上报聚合 → 看板告警,缺一层都闭环不了。
  • 采集端要控制上报体积,否则监控系统本身会拖垮业务。
  • 看板要能按维度下钻(机型 / 网络 / 地域 / 版本),否则只能看到平均值,定位不了问题。
  • 每条告警都要有明确的阈值和对应的处理预案,否则告警只会变成噪音。
