首屏优化:从 4s+ 到 < 1s 的实战路径 ​

来自简历项目"02 会员 Web / H5"首屏优化复盘。

一、首屏到底在等什么 ​

首屏时间 = 用户看到第一屏内容所需时间,包含:

  1. DNS 查询:域名解析(几十 ms)
  2. TCP 连接:三次握手(几十~几百 ms)
  3. TLS 握手:HTTPS(比 HTTP 多 1~2 个 RTT)
  4. 服务器响应:HTML 返回(几十~几百 ms)
  5. HTML 解析 + CSS 阻塞:构建 DOM 和 CSSOM
  6. JS 下载 + 执行:阻塞渲染
  7. 首屏内容渲染:FCP

真正的瓶颈常常不是网络,而是 JS 体积和阻塞渲染。

二、优化手段全景 ​

首屏时间
├── 网络层
│   ├── HTTP/2 / HTTP/3
│   ├── Brotli 压缩
│   ├── CDN
│   ├── 预连接(preconnect)
│   └── 预加载关键资源(preload)
├── 资源层
│   ├── 关键 CSS 内联
│   ├── 非关键 CSS 异步
│   ├── JS defer / async
│   ├── 字体 preload + font-display: swap
│   └── 图片 lazy + 显式宽高
├── 渲染层
│   ├── SSR / SSG / Streaming
│   ├── Suspense 边界
│   ├── 骨架屏
│   └── 服务端数据预取
└── JS 层
    ├── 路由懒加载
    ├── 第三方按需引入
    └── tree-shaking

三、SSR vs SSG vs CSR vs Streaming ​

3.1 对比 ​

方案首屏SEO服务器压力适用
CSR(客户端渲染)❌ 慢❌ 差小后台、工具型
SSR(服务端渲染)✅ 快✅ 好大内容站、电商
SSG(静态生成)✅✅ 最快✅✅ 最好最小文档、博客
ISR(增量静态)✅ 快✅ 好小内容偶变
Streaming(流式 SSR)✅✅ 极快✅ 好中数据依赖重的页面

3.2 选型决策 ​

你的页面类型?
├── 内容站/博客 → SSG(Next.js 默认)
├── 电商/feed → SSR + Streaming
├── 后台/工具 → CSR
└── 静态文档 → SSG + ISR

四、Streaming SSR(Next.js App Router) ​

4.1 原理 ​

传统 SSR:等所有数据准备好,一次性返回完整 HTML。

Streaming:分块返回——HTML 主体先返回,慢的部分用 Suspense 包起来,流式追加。

tsx
// app/page.tsx
import { Suspense } from 'react'

export default function Page() {
  return (
    <>
      {/* 立即渲染(不依赖数据) */}
      <Header />
      <HeroSection />

      {/* 慢的部分用 Suspense 包,fallback 是骨架屏 */}
      <Suspense fallback={<ProductListSkeleton />}>
        <SlowProductList />  {/* 这个组件会 await 数据 */}
      </Suspense>

      <Suspense fallback={<CommentsSkeleton />}>
        <Comments />  {/* 另一个慢组件,独立流式 */}
      </Suspense>
    </>
  )
}

4.2 收益 ​

  • 首屏字节数减少 50%+:用户先看到 HTML 框架,数据流式补充
  • TTFB 不变但 FCP 提前:用户感知到的"看到内容"变快
  • 后端不需要等所有数据:并行处理多个数据源

五、骨架屏 ​

5.1 设计原则 ​

  • 结构相似:占位元素大小接近真实内容
  • 避免抢眼动画:闪烁/脉冲太抢眼会让人焦虑
  • 首次加载才显示:二次进入直接显示内容,不要再"skeleton 一下"

5.2 实现 ​

tsx
function ProductListSkeleton() {
  return (
    <div className="skeleton-list">
      {[...Array(10)].map((_, i) => (
        <div key={i} className="skeleton-item">
          <div className="skeleton-image" />
          <div className="skeleton-text-line" />
          <div className="skeleton-text-line short" />
        </div>
      ))}
    </div>
  )
}
css
.skeleton-item {
  background: #f5f5f5;
  padding: 12px;
  margin-bottom: 8px;
  border-radius: 4px;
}

.skeleton-image {
  width: 60px;
  height: 60px;
  background: linear-gradient(90deg, #f0f0f0 25%, #e0e0e0 50%, #f0f0f0 75%);
  background-size: 200% 100%;
  animation: shimmer 1.5s infinite;
  border-radius: 4px;
}

.skeleton-text-line {
  height: 14px;
  margin-top: 8px;
  background: #f0f0f0;
  border-radius: 4px;
}
.skeleton-text-line.short {
  width: 60%;
}

@keyframes shimmer {
  0% { background-position: 200% 0; }
  100% { background-position: -200% 0; }
}

不要用旋转 spinner——研究表明骨架屏比 spinner 感知快 30%。

六、关键 CSS 内联 ​

将首屏所需的 CSS 内联到 <head>,其他 CSS 异步加载:

html
<head>
  <style>
    /* 首屏关键样式(几个 KB 内) */
    body { margin: 0; background: #fafafa; font-family: -apple-system; }
    .skeleton { /* 骨架屏样式 */ }
    .header { /* 顶部导航 */ }
  </style>
</head>

<!-- 主样式异步,加载完才应用 -->
<link rel="preload" href="/main.css" as="style" onload="this.onload=null;this.rel='stylesheet'">

<!-- 不支持的浏览器兜底 -->
<noscript><link rel="stylesheet" href="/main.css"></noscript>

实战经验:首屏关键 CSS 一般 < 5KB(Vue/React 的 reset + 容器布局)。

七、图片优化 ​

7.1 显式宽高(避免 CLS) ​

html
<!-- ❌ 错误:没宽高,加载时布局跳动 -->
<img src="banner.jpg">

<!-- ✅ 正确 -->
<img src="banner.jpg" width="1200" height="600" loading="lazy" decoding="async">

7.2 现代格式 ​

html
<picture>
  <source srcset="banner.avif" type="image/avif">
  <source srcset="banner.webp" type="image/webp">
  <img src="banner.jpg" alt="" loading="lazy">
</picture>

AVIF 比 PNG/JPG 小 50%+,WebP 小 30%+。但 CDN 要支持。

7.3 响应式 ​

html
<img
  srcset="
    banner-400.jpg 400w,
    banner-800.jpg 800w,
    banner-1200.jpg 1200w
  "
  sizes="(max-width: 600px) 400px, (max-width: 1024px) 800px, 1200px"
  src="banner-800.jpg"
  alt=""
>

八、JS 加载策略 ​

8.1 defer vs async ​

html
<!-- async:下载完立即执行,可能阻塞渲染 -->
<script async src="analytics.js">

<!-- defer:等 DOM 解析完才执行,不阻塞 -->
<script defer src="main.js">

<!-- type="module" 默认 defer -->
<script type="module" src="main.js">

实战经验:

  • 主入口用 defer 或 type="module"
  • 独立功能(analytics、广告)用 async
  • 千万不要 async 主入口——会阻塞 + 执行顺序不确定

8.2 代码分割 ​

ts
// 路由懒加载
const routes = [
  { path: '/', component: () => import('./Home.vue') },
  { path: '/list', component: () => import('./List.vue') },
]

// 第三方按需
import { useDialog } from 'element-plus'  // 只引入用到的

九、字体优化 ​

html
<!-- preload 关键字体 -->
<link rel="preload" as="font" href="/font.woff2" crossorigin>

<!-- 避免 FOIT(文字闪烁) -->
<style>
  @font-face {
    font-family: 'Custom';
    src: url('/font.woff2') format('woff2');
    font-display: swap;  /* 用 fallback 字体先渲染 */
  }
</style>

实战经验:font-display: swap 比 block 体验好很多,但fallback 字体和自定义字体的大小差距不能太大,否则会有明显抖动。

十、真实项目案例:会员端 H5 ​

改前:

  • 首屏 4.2s
  • LCP 4.0s
  • 首屏 JS 1.8MB
  • Lighthouse 评分 51

做的优化:

  1. 关键 CSS 内联(原 14KB → 内联 4KB)
  2. 非关键 CSS media="print" onload 异步
  3. 图片全部 loading="lazy" decoding="async" + AVIF
  4. 字体 font-display: swap + preload
  5. 第三方 SDK(分享/统计)动态加载
  6. 路由懒加载(主入口从 1.8MB 降到 380KB)

改后:

  • 首屏 1.4s(-67%)
  • LCP 1.6s
  • 首屏 JS 380KB(-79%)
  • Lighthouse 评分 92

🎯 面试常考 ​

Q1：首屏 4 秒怎么优化到 1 秒?

先量:定位首屏耗时是 TTFB、关键 CSS、还是接口;再按「服务端出数据 → 减少关键资源 → 提前渲染」三段改:TTFB 走缓存/CDN,关键 CSS 内联,配合 Streaming SSR 或骨架屏让用户尽早看到内容。

Q2：骨架屏什么时候不该用?

数据一次性返回且很快(<200ms)时用骨架屏反而多一次闪烁;骨架屏结构要和真实内容一致,否则骨架消失时会产生布局偏移(CLS)。

📝 小结 ​

  • 首屏优化先要回答一个问题:用户等的是「数据」还是「代码」——前者是服务端问题,后者才是前端优化。
  • Streaming SSR(Next.js App Router)能把「等全部数据」变成「边渲染边吐」,是最有效的结构性优化。
  • 骨架屏 + 关键 CSS 内联 + 图片显式宽高,三者配合能同时改善感知性能与 CLS。
  • 优化完必须用真实用户指标(RUM)验证,实验室数据不能代表线上。
