长列表性能:虚拟列表原理与实战 ​

一、问题:为什么长列表卡 ​

渲染 10000 个 DOM 节点会导致:

  • 首屏渲染慢:浏览器要创建 10000 个 DOM 节点,布局/绘制耗时
  • 滚动卡顿:每次滚动都要重排/重绘所有节点
  • 内存占用大:每个 DOM 节点几十字节,10000 个就几百 KB

核心思路:只渲染用户当前看到的 DOM,滚动时动态替换,DOM 总数始终保持在一个常数。

二、虚拟列表原理 ​

2.1 三要素 ​

可视区:屏幕可见的列表区域(高度 600px)
滚动区:完整列表的总高度(10000 * 50px = 500000px)
DOM 池:可视区内的 DOM 节点池(约 12 个,足够覆盖可视区)

2.2 核心计算 ​

ts
// 用户滚动时
const scrollTop = container.scrollTop              // 滚动距离
const startIndex = Math.floor(scrollTop / itemHeight)   // 起始索引
const endIndex = Math.ceil((scrollTop + viewportHeight) / itemHeight)  // 结束索引

// 渲染 startIndex ~ endIndex 之间的 DOM
// 通过 transform: translateY(startIndex * itemHeight) 偏移

2.3 关键概念 ​

概念含义
FixedSizeList固定行高(简单场景)
VariableSizeList变高行(复杂场景,需要维护高度缓存)
Overscan视区外多渲染几个节点(避免快速滚动白屏)
Anchor Scroll滚动时记录锚点节点位置,避免回弹
动态高度估算未测量前先用默认值,测量后修正

三、方案选型 ​

3.1 主要库对比 ​

库包大小维护状态适用场景
react-window6KB✅ 活跃简单场景(固定高度 + 少量变高)
react-virtuoso30KB✅ 活跃复杂场景(聊天、表格、分组)
@tanstack/react-virtual15KB✅ 活跃Tanstack 生态、Headless UI
antd VirtualList内置✅中后台表格
react-virtualized30KB⚠️ 半弃老项目维护

实战建议:

  • 简单表格/列表 → react-window(小、轻、稳定)
  • 复杂场景(聊天窗口、分组、动态高度) → react-virtuoso(功能全,API 友好)
  • 已经在用 Tanstack Table/Query → @tanstack/react-virtual(生态一致)

3.2 自研 vs 用库 ​

用库的场景:90% 的项目

  • 节省开发时间(虚拟列表的边缘情况非常多)
  • 维护成本低(库作者替你修 bug)

自研的场景:

  • 极致性能要求(库有 overhead)
  • 高度定制化(库的 API 不够灵活)
  • 不想引入依赖(包体积敏感)

四、react-window 实战 ​

4.1 固定行高 ​

tsx
import { FixedSizeList } from 'react-window'

function Row({ index, style }) {
  return <div style={style}>Row {index}</div>
}

function App() {
  return (
    <FixedSizeList
      height={600}
      itemCount={10000}
      itemSize={50}
      width="100%"
      overscanCount={5}
    >
      {Row}
    </FixedSizeList>
  )
}

4.2 变高行 ​

tsx
import { VariableSizeList } from 'react-window'

function App() {
  const heightsRef = useRef(new Map())

  const getItemSize = (index: number) => {
    // 优先用已测量的高度
    if (heightsRef.current.has(index)) {
      return heightsRef.current.get(index)!
    }
    // 默认估算高度
    return 80
  }

  // 测量后更新缓存
  const Row = ({ index, style }) => {
    const ref = useRef<HTMLDivElement>(null)
    useEffect(() => {
      if (ref.current) {
        const height = ref.current.getBoundingClientRect().height
        if (height !== heightsRef.current.get(index)) {
          heightsRef.current.set(index, height)
          // 通知 react-window 重新布局
          listRef.current?.resetAfterIndex(index)
        }
      }
    }, [])
    return <div ref={ref} style={style}>...</div>
  }
}

变高行的坑:必须调用 resetAfterIndex 通知 react-window,否则布局会错。

五、react-virtuoso 实战(复杂场景) ​

5.1 聊天窗口特性 ​

  • 自动滚到新消息
  • 加载历史消息(滚动到顶部)
  • 动态高度(表情、图片)
  • 跳转到指定消息
tsx
import { Virtuoso } from 'react-virtuoso'

function Chat({ messages }) {
  return (
    <Virtuoso
      data={messages}
      itemContent={(index, message) => <Message {...message} />}
      followOutput="smooth"     // 自动滚动到底部
      initialTopMostItemIndex={messages.length - 1}
      firstItemIndex={messages.length}
      // ... 还有很多 hooks
    />
  )
}

六、真实踩坑 ​

6.1 滚动到底部"跳" ​

问题:新数据到达后,列表跳到底部,用户丢失上下文。

解法:react-virtuoso 用 followOutput="smooth" + initialTopMostItemIndex。

6.2 搜索定位不准确 ​

问题:搜索 "张三" 要跳到第 5000 行,实际滚动位置不对。

解法:

  • 先确保搜索结果按列表顺序排列
  • 用 scrollToIndex({ index, align: 'center' })
  • 变高行场景下,提前预热所有目标项的高度

6.3 动态高度白屏 ​

问题:首次渲染用默认 50px,实际是 200px,滚动时突然变高导致抖动。

解法:

  • 用 ResizeObserver 监听每个 item 的真实高度
  • 测量后调用 resetAfterIndex(index) 重排
  • 列表底部加 padding 留出"未测量"区域

6.4 滚动事件性能 ​

问题:每像素都触发 scroll,性能浪费。

解法:

  • 用 passive: true 监听 scroll
  • React 17+ 用 useTransition 延迟非紧急更新
  • requestAnimationFrame 节流

八、何时不要用虚拟列表 ​

  • < 100 行:DOM 完全可以承受
  • 高度无法预估 + 没有好的 fallback:不如分页
  • SEO 要求高:虚拟列表的搜索引擎支持有限(SSR 列表优于 CSR)

🎯 面试常考 ​

Q1：长列表卡顿怎么解决?

虚拟列表:只渲染可视区 + 上下缓冲区,DOM 节点数从 1 万降到几十。核心是三项计算——可视区起止索引、滚动偏移量、缓冲区补偿。

Q2：什么时候不该用虚拟列表?

列表项高度不可预测且频繁变化、总数很小(<100)、需要 SEO 抓取全部内容、或者列表内含复杂的富交互(拖拽排序)时,虚拟列表反而更麻烦。

📝 小结 ​

  • 虚拟列表的三个核心量:可视区起始索引、结束索引、滚动偏移量,再配合缓冲区避免快速滚动露白。
  • 变高行是难点,方案有三种:预估高度 + 动态修正、ResizeObserver 实测、第三方库(virtuoso)的测量缓存。
  • 真实踩坑比原理更重要:滚动到底跳变、搜索定位不准、动态高度白屏、滚动事件本身卡顿,这四个坑都有对应解法。
  • 先测再上:如果瓶颈是接口而不是渲染,虚拟列表帮不上忙。
