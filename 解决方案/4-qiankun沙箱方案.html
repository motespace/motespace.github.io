qiankun 沙箱机制 ​

微前端最核心的技术点：JS 沙箱、CSS 隔离、应用通信。 本文按"沙箱原理 → 隔离机制 → 实战"组织，覆盖面试深挖。

一、为什么需要沙箱 ​

1.1 子应用冲突问题 ​

主应用 window.someUtil = () => { /* A 团队实现 */ }
子应用 1 window.someUtil = () => { /* B 团队实现，覆盖了 A */ }
子应用 2: window.someUtil() // 用的是 B 的实现，A 团队代码炸了

问题：子应用直接挂全局变量 + 改 window，主应用和其他子应用被污染。

1.2 沙箱的目标 ​

  • ✅ 子应用挂全局变量不影响主应用
  • ✅ 子应用卸载时清理副作用
  • ✅ 子应用之间隔离

二、3 种沙箱方案 ​

2.1 Proxy 沙箱（qiankun 主推） ​

js
class ProxySandbox {
  constructor() {
    this.modifiedProps = new Map()  // 子应用改的属性
    this.originalProps = new Map()  // 原始值（恢复用）

    this.proxy = new Proxy(window, {
      get: (target, key) => {
        // 优先返回子应用修改值
        if (this.modifiedProps.has(key)) {
          return this.modifiedProps.get(key)
        }
        return target[key]
      },
      set: (target, key, value) => {
        // 记录子应用的修改
        this.modifiedProps.set(key, value)
        return true
      },
      has: (target, key) => {
        return this.modifiedProps.has(key) || (key in target)
      },
    })
  }

  // 卸载时恢复
  deactivate() {
    this.modifiedProps.forEach((value, key) => {
      if (this.originalProps.has(key)) {
        window[key] = this.originalProps.get(key)
      } else {
        delete window[key]
      }
    })
  }
}

优点：不影响原始 window，性能好

缺点：Proxy 不支持 with 语句

2.2 with + Proxy 沙箱 ​

js
class WithSandbox {
  constructor() {
    this.modifiedProps = {}

    this.proxy = new Proxy(window, {
      get: (target, key) => {
        if (key in this.modifiedProps) return this.modifiedProps[key]
        return target[key]
      },
      set: (target, key, value) => {
        this.modifiedProps[key] = value
        return true
      },
    })

    // 用 with 把子应用代码包起来
    this.run = (code) => {
      with (this.proxy) {
        eval(code)
      }
    }
  }
}

// 用法
const sandbox = new WithSandbox()
sandbox.run(`
  window.myApp = { name: 'subapp' }  // 走 proxy
  console.log(myApp.name)              // 走 proxy
`)

优点：子应用代码"看起来"在真 window 上运行

缺点：with 在严格模式报错；性能差

2.3 快照沙箱（SnapshotSandbox） ​

js
class SnapshotSandbox {
  constructor() {
    this.modifyMap = {}      // 原状态
    this.snapshot = {}        // 初始快照

    this.active = () => {
      // 记录当前 window 状态
      for (const key in window) {
        if (typeof window[key] === 'function' || typeof window[key] === 'object') continue
        this.snapshot[key] = window[key]
      }
    }

    this.inactive = () => {
      // 恢复
      for (const key in this.snapshot) {
        window[key] = this.snapshot[key]
      }
    }
  }
}

优点：兼容性好

缺点：性能差（每次 mount 都要遍历 window）

三、qiankun 沙箱实现 ​

3.1 默认沙箱（legacy） ​

js
// qiankun 内部源码（简化）
import { ProxySandbox } from './ProxySandbox'

const sandbox = new ProxySandbox(name)
// 把 window 替换成 proxy，子应用代码用 proxy 跑
window.proxy = sandbox.proxy

// 子应用 mount
window.proxy.eval(subAppCode)

3.2 多实例沙箱 ​

qiankun 3.0+ 支持多个子应用同时挂载，每个独立沙箱：

子应用 A:  ProxySandbox A → 挂载到 #container-a
子应用 B:  ProxySandbox B → 挂载到 #container-b
两个互不影响

四、CSS 隔离 ​

4.1 方案 1：动态加载 + scope ​

js
// qiankun 加载子应用时：
// 1. 解析 entry html 提取 <link> <style>
// 2. 动态插入到 <head>
// 3. 卸载时移除

function loadCSS(url) {
  return new Promise(resolve => {
    const link = document.createElement('link')
    link.rel = 'stylesheet'
    link.href = url
    link.onload = resolve
    document.head.appendChild(link)
  })
}

// 卸载时清理
function unloadCSS() {
  document.head.querySelectorAll('link[data-qiankun]').forEach(el => el.remove())
}

4.2 方案 2：CSS Modules / Shadow DOM ​

js
// Shadow DOM（最彻底）
const container = document.querySelector('#subapp')
const shadow = container.attachShadow({ mode: 'open' })
shadow.innerHTML = '<div>子应用</div>'

// 子应用样式只在 shadow 内生效

4.3 方案 3：CSS 前缀（qiankun 旧方案） ​

js
// qiankun 会给子应用 CSS 加前缀
// .button → .subapp-button

问题：可能影响第三方组件库样式。

4.4 推荐方案 ​

隔离严格度方案
最严Shadow DOM（不完美支持所有库）
次严CSS Modules + 子应用约定前缀
常规动态加载 + scope（qiankun 默认）

5.2 子应用间通信（基于 qiankun 全局状态） ​

js

  console.log('主应用 state:', state)

六、路由同步 ​

6.1 问题 ​

子应用切换时，主应用侧边栏激活项不更新。

6.2 方案 ​

js
// 主应用监听 popstate
window.addEventListener('popstate', () => {
  updateSidebarActive(window.location.pathname)
})

// 子应用跳转用 history.pushState
history.pushState(null, '', '/subapp/user/123')

// 主应用拦截 router.push 但同步
router.beforeEach((to, from, next) => {
  // 不实际跳转主应用路由，只更新状态
  updateSidebarActive(to.path)
  // 子应用自己处理路由
  next(false)
})

6.3 qiankun 内置 ​

qiankun 通过 activeRule 配置激活规则，自动同步：

  {
    name: 'subapp',
    entry: '//localhost:8080',
    container: '#subapp-container',
    activeRule: '/subapp',  // ⬅️ /subapp 路径下激活
  },

// react-subapp/src/public-path.js
if (window.__POWERED_BY_QIANKUN__) {
  __webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__
}

// react-subapp/src/index.js
import { createRoot } from 'react-dom/client'

  root = createRoot(container)
  root.render(<App />)
}

  console.log('react 子应用启动')
}

export async function mount(props) {
  console.log('react 子应用挂载', props)
  render(props)
}

export async function unmount(props) {
  root?.unmount()
}

// 独立运行（不通过 qiankun）
if (!window.__POWERED_BY_QIANKUN__) {
  render({})
}

八、面试高频追问 ​

Q1: 沙箱的实现原理？ ​

答：基于 Proxy 拦截 window 的 get/set，子应用的全局变量都写入 proxy 自己的 modifiedProps，不影响真实 window。卸载时遍历恢复。

Q2: CSS 沙箱为什么难？ ​

答：

  • CSS 全局污染（不依赖 JS）
  • 动态加载 CSS 后，卸载需要清理
  • 第三方组件库样式不能简单加前缀
  • Shadow DOM 完美但兼容性有限

Q3: qiankun 的 JS 沙箱有什么坑？ ​

答：

  • 不支持 with 语句（严格模式报错）
  • 浏览器 API（localStorage、location）需要单独处理
  • 第三方库如果用 eval 会逃逸沙箱

Q4: 子应用之间怎么共享依赖？ ​

答：

  1. external：qiankun 配置 external，子应用不打包公共依赖
  2. Module Federation：运行时共享
  3. CDN 引入：全局 script 标签，UMD 包

Q5: 微前端性能优化怎么做？ ​

答：

  1. 预加载：空闲时加载子应用 entry
  2. Keep-alive：子应用切走不卸载
  3. 公共依赖 external：避免重复加载
  4. 路由级懒加载：子应用内也用 dynamic import

Q6: 微前端怎么排查问题？ ​

答：

  1. qiankun start 时加 { sandbox: { strictStyleIsolation: true } }（开启严格样式隔离）
  2. 打开子应用独立调试：?subapp_xxx=1 跳过主应用
  3. 监听 addGlobalUncaughtErrorHandler
  4. 打 console.log：qiankun 内置事件追踪

面试追问(深化原 Q1-Q6) ​

  • qiankun 沙箱 3 种? SnapshotSandbox(兼容,慢)、LegacySandbox(Proxy,中)、ProxiesSandbox(最优,新)
  • JS 沙箱原理? Proxy 代理 window;子应用改 window 走代理,主应用不受影响
  • CSS 隔离方案? 严格模式(子应用样式 scoped);实验性(Shadow DOM);动态加载
  • 子应用间通信? props 传值、全局状态(Redux/Pinia)、EventBus、qiankun 全局 hooks

📝 小结 ​

  • 沙箱要解决三件事:JS 全局变量隔离(防止子应用改 window)、样式隔离(防止 CSS 互相污染)、应用生命周期。
  • 三种沙箱:Proxy 沙箱(劫持 window 属性,qiankun 默认)、快照沙箱(用 iframe 复制一份 window,性能好但有兼容问题)、VM 沙箱(eval 隔离,最彻底但慢)。
  • qiankun 的 Proxy 沙箱核心:用 Proxy 拦截 get/set/has/deleteProperty,set 时把属性写到沙箱自己的 globalThis,读取时优先沙箱。
  • CSS 隔离用 scoped + 动态改写选择器(div → div[data-v-xxx]),或用 Shadow DOM;动态插入的第三方样式要单独处理。
  • 路由同步:主应用改 hash,子应用监听并响应;子应用内部跳转要通知主应用同步 URL。
  • 面试高分点:能讲清「为什么 Proxy 沙箱里拿不到真实的 DOM 与原型链」以及 qiankun 如何用 hasOwnProperty 与 getPrototypeOf 特殊处理。
