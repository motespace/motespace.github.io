微前端通信方案 ​

子应用和主应用、子应用之间怎么通信？本文按"通信方式 → 实战"组织。

一、通信场景 ​

主应用 ↔ 子应用 A
主应用 ↔ 子应用 B
子应用 A ↔ 子应用 B

每种通信方式各有优劣。

二、通信方式对比 ​

方式适用场景优点缺点
Props主 → 子启动参数简单、类型安全只能启动时传
全局状态（qiankun GlobalState）子应用间共享状态qiankun 内置、跨子应用调试不直观
Event Bus（mitt/EventEmitter）父子通信、广播灵活需手动清理
CustomEvent父子通信浏览器原生跨子应用麻烦
URL / Hash父子路由同步浏览器原生、可分享只能简单数据
localStorage跨子应用持久化简单监听需要 storage 事件
BroadcastChannel同源跨 Tab / 子应用浏览器原生、实时同源限制
postMessageiframe 子应用跨域API 复杂

三、Props（主 → 子） ​

3.1 qiankun 实现 ​

js
// 主应用
registerMicroApps([
  {
    name: 'subapp',
    entry: '//localhost:8080',
    container: '#subapp-container',
    activeRule: '/subapp',
    props: {
      userInfo: { name: 'tom', role: 'admin' },
      token: 'xxx',
      onLogout: () => console.log('子应用请求登出'),
    },
  },
])

start()
js
// 子应用
export async function mount(props) {
  // props.userInfo 拿到主应用传的用户信息
  console.log(props.userInfo)
  // props.onLogout 是主应用暴露的方法
}

3.2 micro-app 实现 ​

html
<micro-app
  name="subapp"
  url="http://localhost:8080/"
  :data="userInfo"
  @event="onSubAppEvent"
></micro-app>
js
// 子应用监听
window.addEventListener('datachange', (e) => {
  console.log(e.detail.data)  // 主应用传的 userInfo
})

四、全局状态（qiankun GlobalState） ​

4.1 主应用初始化 ​

js
import { initGlobalState } from 'qiankun'

const initialState = {
  user: { name: 'tom' },
  theme: 'light',
  locale: 'zh',
}

const actions = initGlobalState(initialState)

// 主应用监听
actions.onGlobalStateChange((state, prev) => {
  console.log('主应用 state 变化:', state, prev)
})

// 主应用修改
actions.setGlobalState({ theme: 'dark' })

4.2 子应用使用 ​

js
// 子应用
export async function mount(props) {
  // 监听主应用 state 变化
  props.onGlobalStateChange((state, prev) => {
    console.log('子应用收到 state 变化:', state)
  })

  // 修改全局 state
  props.setGlobalState({ user: { name: 'jerry' } })
}

4.3 优点 ​

  • ✅ qiankun 内置，无需额外依赖
  • ✅ 跨子应用共享
  • ✅ 支持类型推断（TS）

4.4 缺点 ​

  • ❌ 全局 state 不易调试（任何子应用都能改）
  • ❌ 状态污染风险

五、Event Bus ​

5.1 基于 mitt（推荐） ​

ts
// main-app/src/event-bus.ts
import mitt from 'mitt'

type Events = {
  'user-login': { userId: string }
  'theme-change': 'light' | 'dark'
  'sub-app-mounted': { name: string }
}

export const bus = mitt<Events>()

5.2 主应用 ​

js
import { bus } from './event-bus'

// 发送事件
bus.emit('user-login', { userId: '123' })

// 监听
bus.on('theme-change', (theme) => {
  document.documentElement.dataset.theme = theme
})

5.3 子应用（共享同一个 bus） ​

js
// 子应用通过 props 拿到 bus
export async function mount(props) {
  const bus = props.bus

  bus.on('user-login', (data) => {
    console.log('子应用收到登录:', data)
  })
}

5.4 卸载时清理 ​

js
export async function unmount() {
  bus.all.clear()  // 清理所有监听
}

六、CustomEvent（浏览器原生） ​

6.1 主应用 ​

js
// 派发事件
window.dispatchEvent(new CustomEvent('main-to-sub', {
  detail: { type: 'theme-change', value: 'dark' },
}))

6.2 子应用监听 ​

js
window.addEventListener('main-to-sub', (e) => {
  console.log(e.detail)  // { type: 'theme-change', value: 'dark' }
})

6.3 优缺点 ​

  • ✅ 浏览器原生，无依赖
  • ❌ 跨子应用需要共享一个事件源
  • ❌ 类型不安全

七、BroadcastChannel（同源跨 Tab） ​

7.1 场景 ​

主应用打开多个 Tab，每个 Tab 是不同子应用，需要同步状态。

js
// 主应用 / 子应用 / 任意页面
const channel = new BroadcastChannel('app-channel')

// 发送
channel.postMessage({ type: 'logout', payload: { userId: '123' } })

// 接收
channel.onmessage = (e) => {
  console.log(e.data)
}

7.2 优缺点 ​

  • ✅ 同源跨 Tab、跨 iframe 实时通信
  • ✅ 比 localStorage 事件更可靠
  • ❌ 同源限制（跨域 iframe 不行）

八、URL / Hash 同步 ​

8.1 简单传参 ​

js
// 主应用跳转带 query
router.push('/subapp?userId=123')

// 子应用解析
const params = new URLSearchParams(location.search)
const userId = params.get('userId')

8.2 复杂状态用全局状态或 EventBus ​

URL 长度有限（通常 2KB），不适合传大对象。

九、localStorage 跨子应用 ​

9.1 写入 ​

js
localStorage.setItem('user', JSON.stringify({ id: '123', name: 'tom' }))

9.2 监听变化（同源） ​

js
window.addEventListener('storage', (e) => {
  if (e.key === 'user') {
    console.log('storage 变化', e.newValue)
  }
})

9.3 优缺点 ​

  • ✅ 简单、持久化
  • ❌ 同源限制（跨子域要共享 localStorage）
  • ❌ 监听 storage 事件需要同源

十、postMessage（iframe 子应用） ​

10.1 主应用发送 ​

js
const iframe = document.querySelector('#subapp-iframe')
iframe.contentWindow.postMessage({
  type: 'theme-change',
  payload: { theme: 'dark' },
}, '*')  // 或指定 origin

10.2 子应用接收 ​

js
window.addEventListener('message', (e) => {
  // 校验 origin
  if (e.origin !== 'http://main-app.com') return
  console.log(e.data)
})

// 子应用回传
window.parent.postMessage({ type: 'mounted' }, 'http://main-app.com')

10.3 优缺点 ​

  • ✅ 跨域 iframe 唯一方案
  • ❌ API 复杂、需要序列化
  • ❌ 必须校验 origin（安全）

十一、实战：组合通信方案 ​

11.1 选型决策 ​

1. 主应用传启动参数 → Props
2. 子应用间共享状态 → GlobalState（qiankun）
3. 子应用间事件触发 → EventBus
4. 子应用内跨页面 → 各自的状态管理（Vuex/Redux）
5. 跨 Tab 同步 → BroadcastChannel
6. iframe 子应用 → postMessage

11.2 实战项目示例 ​

ts
// 完整的微前端通信层（主应用）
import { initGlobalState } from 'qiankun'
import mitt from 'mitt'

const events = mitt<{
  'sub-app-logout': { name: string }
  'sub-app-error': { error: Error }
}>()

const state = {
  user: null as { id: string; name: string } | null,
  theme: 'light' as 'light' | 'dark',
}

const actions = initGlobalState(state)

// 子应用通过 props 拿到：
const props = {
  ...actions,
  events,  // 事件总线
  onLogout: () => {
    // 子应用触发登出时调用
    events.emit('sub-app-logout', { name: 'subapp-a' })
  },
}

registerMicroApps([
  { name: 'subapp-a', props },
  { name: 'subapp-b', props },
])

// 主应用监听子应用登出
events.on('sub-app-logout', ({ name }) => {
  console.log(`子应用 ${name} 请求登出`)
  router.push('/login')
})

十二、面试高频追问 ​

Q1: 子应用通信方式怎么选？ ​

答：看通信类型：

  • 配置 / 启动参数 → Props
  • 共享状态 → GlobalState / localStorage
  • 事件触发 → EventBus / CustomEvent
  • 跨 Tab → BroadcastChannel
  • iframe → postMessage

Q2: GlobalState 有什么坑？ ​

答：

  • 任何子应用都能改 → 不易调试
  • 状态污染 → 需要命名空间（appA.theme 而不是 theme）
  • 卸载时记得 offGlobalStateChange

Q3: 跨域 iframe 怎么通信？ ​

答：postMessage + origin 校验，监听 message 事件。

Q4: 微前端通信安全怎么做？ ​

答：

  • 所有跨子应用通信校验来源
  • 敏感数据不通过 URL 传
  • postMessage 必须校验 origin
  • GlobalState 不能存敏感信息（Token、密码）

面试追问(深化原 Q1-Q4) ​

  • 微前端通信 4 种? props(父子)、CustomEvent(子间)、全局 Store(跨子)、URL params(轻量)
  • 数据共享性能? 避免大对象全局;用 selector 订阅;子应用按需加载
  • 主子路由同步? 主应用统一 history 模式;子应用 hash 模式(简单但丑)
  • 微前端 vs BFF? BFF 解决数据聚合;微前端解决代码/团队解耦;可叠加使用

📝 小结 ​

  • 通信场景先分类:父子一次传值(props)、跨应用状态共享(GlobalState/store)、事件通知(Event Bus / CustomEvent)、跨 Tab(BroadcastChannel / storage)、iframe(postMessage)。
  • 选型原则:能用 props 就不用全局状态,能用框架状态就别用事件总线;事件总线的成本是「谁在监听、谁负责解绑」。
  • qiankun 的 initGlobalState 是发布订阅式的状态容器,主应用能监听子应用的修改(需 onGlobalStateChange)。
  • CustomEvent 是浏览器原生事件机制,适合解耦的跨应用通知;BroadcastChannel 适合同源多 Tab。
  • 通信方案必须配套约定:命名空间、消息格式、版本兼容、清理时机,否则后期会变成垃圾场。
  • 面试加分:能说清「事件总线在微前端里的隐患」——无法追踪来源、无法类型约束、跨应用解绑困难。
