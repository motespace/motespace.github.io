Agent 原理:它到底在做什么,什么时候会失败 ​

前五篇讲的是「怎么做」——MCP、多 Agent、记忆、反思。这一篇讲「为什么」:Agent 的运行机制、第一性原理,以及在没有框架的时候也该知道的事。

面试里最值钱的一句话是「Agent 没什么高深的技术,它就是 LLM 加工具调用加一个循环」。但要把这个「没什么高深」讲透,才显得你真懂 —— 而不是读过几篇教程。

一、Agent 的最小模型 ​

1.1 一句话定义 ​

Agent = LLM(决策) + 工具(执行) + 状态(记忆) + 循环(重复直到目标达成)

1.2 四个部件,四个不同的问题 ​

部件解决的问题工程形态
LLM「下一步做什么」的判断一个函数调用:输入 prompt + 工具列表,输出「文本」或「工具调用」
工具「做」的能力确定性代码,不是 LLM
状态「记住已经发生了什么」显式的 state 对象,不是模型的隐式记忆
循环「直到够了为止」while + max_iterations

关键认知:Agent 的工程量绝大部分在「工具」和「状态」,不在「决策」。

决策质量受模型能力限制,你优化不了;你能优化的是:给它更好的工具、更准的状态、更清晰的边界。

1.3 LLM 在循环里到底能决定什么 ​

这是理解 Agent 最关键的一点。LLM 每轮只能输出三样东西:

  1. 调哪个工具(以及参数)
  2. 是否结束(返回最终答案,还是继续下一轮)
  3. 下一轮的输入(把工具结果拼回上下文)

它不能决定的:工具内部怎么实现、数据从哪来、业务规则是什么。

所以「Agent 能力很强」是一种错觉。真正强的是工具集设计得好。

给 Agent 一个 query_users(sql) 和只给它一个 search(keyword),能力差一个量级 —— 后者只能靠猜 SQL 文本。

推论:做 Agent 平台,一半的工程量在写工具,不是在调 prompt。

1.4 循环的四种终止方式 ​

终止方式判定方式用在哪
目标达成LLM 返回最终答案常规路径
步数上限max_iterations必备兜底
成本上限累计 token / 卡时Agent 会跑飞时的兜底
人工中断HITL 暂停等输入高风险动作

只做前两种的 Agent,迟早会烧钱。 见第五章的失败模式。

二、上下文工程 > 提示词 ​

2.1 上下文就是 Agent 唯一的工作空间 ​

Agent 的「记忆」就是上下文窗口。窗口里放什么,直接决定它的行为。 提示词只是上下文的一部分。

2.2 上下文的四个来源 ​

来源内容常见错误
指令系统提示、角色定义越写越长,互相矛盾
状态已有产出、已完成步骤只写「做过什么」,不写「为什么」
工具结果检索 / 查询的返回塞满原始 JSON,又长又是噪声
记忆长期知识、用户偏好不管相关性,全量注入

2.3 三条实用规则 ​

① 工具结果要摘要后再进上下文

原始 5000 行 JSON 会挤爆窗口并稀释信号。给 Agent 一个「search → 返回 top-5 摘要」的工具,远好过给它原始查询能力。

② 状态要写「为什么」

「第 3 镜用角色 v2,因为 v1 的发型和第 2 镜不连续」 比 「第 3 镜用角色 v2」

有用一个量级。前者让下一个 Agent(或人)能判断要不要相信它。

③ 给 Agent 一个「够用就停」的信号

让它能回答「我还需要什么」,比让它盲目循环便宜得多 —— 成本上限只有在 Agent 知道目标时才有效。

三、什么时候不该用 Agent ​

这一节比「怎么用 Agent」值钱。

场景更好的选择为什么
流程固定、步骤确定写代码(Workflow)Agent 只会增加不确定性
需要 100% 可复现确定性代码 + 校验Agent 有随机性
单步就能做完直接调一次 LLM加循环纯属浪费
错误代价高且不可逆人工主导,Agent 只出建议试错成本太高
强依赖精确计算让 LLM 输出参数,让代码去算LLM 不擅长算数

一句话判据:如果一个流程你能用 if/else 写出来,就先用 if/else。

Agent 的价值只在路径不确定的地方 —— 分镜怎么拆、这个镜头该用哪个模型、这段对话到底在问什么。

四、单 Agent 还是多 Agent ​

4.1 先问:能不能用一个 Agent + 更多工具 ​

多 Agent 几乎总是更贵、更慢、更难调试。 拆分前先确认三件事:

  1. 这个 Agent 的职责是否真的不同(不是「同一件事换个角度」)?
  2. 它们的输出是否能用结构化契约交接(不是自由文本)?
  3. 失败时能不能独立重试(一个挂了不用全部重来)?

三个都满足,再考虑拆。

4.2 协作模式与判据 ​

模式拓扑什么时候用代价
Single + Tools一个循环默认选它上下文压力大
Pipeline固定顺序阶段清晰、可并行早期错误会往下传
Supervisor主管路由步骤类型确实不确定主管本身是瓶颈
Swarm / 辩论互相通信需要多视角对抗成本爆炸、难收敛

各模式的实现见 Multi-Agent 多智能体系统。

4.3 多 Agent 真正的难点不是编排,是契约 ​

多数人把多 Agent 理解成「画图连线」。真正难的是三件事:

① 状态所有权

状态谁能写谁能读
剧本剧本 Agent全部
角色资产角色 Agent(人也可改)全部
分镜分镜 Agent生成 / 一致性 / 剪辑
任务队列只有调度器全部

一个状态只能有一个写入者。 两个 Agent 都能写同一个状态,结果就是不可复现的竞态 —— 而且这种 bug 极难定位。

② 交接契约

Agent 之间的交接必须结构化、带版本、带理由:

python
class Handoff(BaseModel):
    version: int          # 契约版本,升级时能识别旧数据
    payload: dict
    reason: str           # 为什么这么判断 —— 下一棒才知道能不能信
    unresolved: list[str] # 我不知道的事,显式传下去

自由文本交接 = 两个 Agent 互相猜。

③ 裁决

冲突时谁说了算?必须显式指定,不能靠模型自觉。

五、失败模式清单 ​

这一节最值钱 —— 面试官问「你觉得 Agent 哪里容易出问题」,答得出这张表就直接赢了。

失败模式症状根因对策
无限循环反复调同一个工具目标不清晰 / 没有终止判据max_iterations + 成本上限 + 重复调用检测
级联幻觉第一个 Agent 编了数据,后面全信下游不校验上游每个 Agent 输出都做 schema + 业务双重校验
上下文污染早期错误留在上下文里,越走越歪状态没有回滚机制关键状态分片,允许丢弃重来
重复劳动两个 Agent 做同一件事职责边界模糊契约里写清谁负责什么
局部最优每个 Agent 都做对了,合起来很差没有全局目标Supervisor 或全局评审 Agent
静默降级某步失败后走了降级路径,没人知道错误被吞失败路径必须显式上报到界面
成本失控一个任务烧掉几百倍预算没有成本闸门每个 Agent 设 token / 卡时上限
提示词漂移改了 prompt,某条链路行为变了没有回归集Agent 输出做快照回归测试
状态竞态两个 Agent 写同一状态,结果不可复现写入权不明确一个状态一个写入者

面试里说得出这张表,比说得出任何框架都值钱。 因为它证明你踩过坑,而不是读过文档。

六、如果只记三句话 ​

  1. Agent = LLM + 工具 + 状态 + 循环;决定能力上限的是工具,不是 prompt。
  2. 能写成 if/else 的就别用 Agent;Agent 只用在路径不确定的地方。
  3. 多 Agent 的难点不是编排,是契约、状态所有权和失败恢复。

🎯 面试常考 ​

Q1:Agent 到底是什么?和普通 LLM 调用有什么区别?

「多了一层循环和状态管理。普通调用是问一次答一次;Agent 是模型自己决定下一步调哪个工具、传什么参数,工具返回结果再喂回去,直到目标达成。真正的区别不在模型,在工具和状态的设计 —— 很多场景下决定效果的是这两样,不是 prompt。」

Q2:什么时候不该用 Agent?

「流程能写成 if/else 的时候就不该用。或者需要 100% 可复现、错误不可逆、强依赖精确计算的场景 —— 这些该用确定性代码,LLM 只负责输出参数。」

Q3:多 Agent 最难的是什么?

「不是编排,是契约。三个点:状态所有权(一个状态只能一个写入者)、交接契约(结构化、带版本、带理由)、冲突裁决(必须显式指定)。这三点没定清楚,画出来的图再漂亮也是不可复现的。」

Q4:Agent 常见的失败模式?

见第五章那张表。现场展开讲三到四个即可,但要能说清根因和对策,不能只列名字。

Q5:上下文工程是什么?

「Agent 的记忆就是上下文窗口,所以上下文的组织方式比提示词措辞重要得多。核心三条:工具结果要摘要后再进上下文;状态要写清为什么而不只是做了什么;要给 Agent 够用就停的信号,否则成本闸门也没用。」

📝 小结 ​

  • Agent 的最小模型是 LLM + 工具 + 状态 + 循环;决策质量靠模型,你能优化的是工具和状态。
  • LLM 在循环里只能决定调哪个工具、是否结束、下一轮输入 —— 它不负责业务逻辑,那些必须在工具里。
  • 上下文工程 > 提示词:工具结果摘要、状态写理由、给够用就停的信号。
  • 能写 if/else 的别用 Agent;Agent 的价值在路径不确定的地方。
  • 多 Agent 前先确认三件事:职责真的不同、能结构化交接、能独立重试。
  • 多 Agent 的真难点是状态所有权、交接契约、冲突裁决,不是画图连线。
  • 失败模式清单是 Agent 岗面试里最能体现经验的东西 —— 讲根因和对策,别只背名字。
