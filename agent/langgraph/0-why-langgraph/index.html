为什么需要 LangGraph?

LangChain 的链是直线的,但真实的 Agent 不是。

一、线性链的三个致命限制

Section titled “一、线性链的三个致命限制”

LCEL 链的形态是 A | B | C,一条直线。但真实业务里:

需求 线性链做不到的原因
循环 ReAct 模式是“思考 → 调工具 → 看结果 → 再思考”,天然是环
条件分支 “如果工具返回置信度低,就转人工审核”,链没法分支
状态回溯 工具失败要回退到上一步重来,链只能往前走

举个具体例子。做一个“数据分析 Agent”,用户问“上周异常设备有多少”:

C → B 是环,C → E 是分支,B 需要记住“上一版 SQL 错在哪” —— 这就是一个典型的 LangGraph 场景。

二、LangGraph 的抽象:图 = 节点 + 边 + 状态

Section titled “二、LangGraph 的抽象:图 = 节点 + 边 + 状态”

对比一下同一个流程用两种方式写:

LangChain(写不出环):

LangGraph:

多了大概 20 行代码,换来:能循环、能分支、能中断恢复。

三、LangGraph 的四个杀手级能力

Section titled “三、LangGraph 的四个杀手级能力”

1. Checkpoint(检查点)

Section titled “1. Checkpoint(检查点)”

每执行完一个节点就把 State 存下来。出错了、进程挂了、用户明天接着聊,可以从最近的检查点恢复,不用从头跑。

2. Human-in-the-Loop(人工介入)

Section titled “2. Human-in-the-Loop(人工介入)”

在任意节点前挂起,等人工审批通过再继续。金融、审批类 Agent 必备。

3. 状态收敛与归约

Section titled “3. 状态收敛与归约”

多个分支可能同时改 State,LangGraph 提供了 reducer 来定义“怎么合并”(覆盖?追加?求和?),避免并发写冲突。

4. 流式输出与可视化

Section titled “4. 流式输出与可视化”

app.stream(..., stream_mode="values") 可以把每个节点的 State 打出来,调试 Agent 时非常关键 —— 能直接看到“模型这一步到底把 State 改成什么样了”。

四、什么时候用 LangGraph

Section titled “四、什么时候用 LangGraph”
场景 建议
固定 2-3 步的流程 LangChain LCEL,别上图
ReAct 循环、需要调用多次工具 ✅ LangGraph
有分支、有审批、有回退 ✅ LangGraph
长时间运行、要能恢复 ✅ LangGraph + Checkpoint
简单问答 都不用,直接调模型

判断标准:流程能不能画成图? 能画成一条直线就用 LCEL,画不出直线(有环有分支)才上 LangGraph。

🎯 面试常考

Section titled “🎯 面试常考”

Q1:LangChain 和 LangGraph 的区别? LangChain 是线性管道(LCEL),适合确定性的多步流程;LangGraph 是有状态图,节点 + 边 + 共享 State,支持循环、条件分支、检查点恢复和人工介入。LangGraph 常常与 LangChain 混用。

Q2:Agent 为什么要用图,不能用链? 因为 Agent 核心是 ReAct 循环 —— 调工具后要根据结果决定下一步,可能重复调同一个工具。链只能表达线性流程,表达不了环;图可以用条件边实现回退。

Q3:Checkpoint 有什么用? 把每个节点执行后的 State 持久化,实现:失败重试、进程重启后从断点恢复、长时间任务断点续跑、人工审批后继续执行。

Q4:什么是 Human-in-the-Loop? 在敏感节点前让图挂起(interrupt),把当前 State 交给人审批,人确认后再恢复执行。高风险操作(付款、删除、对外发送)必须走这一步。

📝 小结

Section titled “📝 小结”
  • 线性链表达不了循环和分支,而 ReAgent 的本质是循环,这是引入 LangGraph 的根本原因。
  • LangGraph 的三个要素:State(共享数据)、Node(处理函数)、Edge(下一步走向)。
  • 四个杀手级能力:Checkpoint 断点恢复、Human-in-the-Loop 人工审批、状态归约并发安全、流式可视化调试。
  • 判断标准:流程能画成直线用 LCEL,画不出直线才上图。
