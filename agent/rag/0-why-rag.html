为什么需要 RAG? ​

在动手写第一行 RAG 代码之前,先想清楚:模型为什么答不对你的业务问题?

一、模型的三类"不知道" ​

大模型是一个通用知识快照,它的知识有三个边界:

不知道典型场景举例
私有知识你的业务数据它训练时没见过公司内部的报销制度、你的客户订单、商品库存
时效知识训练截止之后的新东西昨天刚发布的 Next.js 15 特性、今天的汇率
可溯源要求答案必须能指到原文出处法务/客服场景,不能只给结论

这三类问题,对应三种解法。

二、三条路,为什么选了 RAG ​

路线 A:继续微调(Fine-tuning) ​

让模型"记住"你的知识。

  • ✅ 改变的是模型的风格和格式偏好(比如让它固定输出某种 JSON)
  • ❌ 改变不了具体事实。用 1 万条制度文档微调一个模型,不如把这 1 万条文档放进向量库
  • ❌ 成本高:每次知识更新都要重新训练

路线 B:把资料塞进 Prompt ​

python
prompt = f"请基于以下资料回答问题:\n{全部文档内容}\n问题:{question}"
  • ✅ 实现最简单,几行代码
  • ❌ 上下文窗口有限,文档一多就塞不下
  • ❌ 每次请求都把全量文档传一遍,token 成本随知识库规模线性增长
  • ❌ 上下文里塞 100 份文档,模型很容易"大海捞针"失败 —— 中间信息丢失是长上下文最典型的失效模式

路线 C:RAG(检索增强生成) ​

先检索出最相关的几段,再让模型基于这几段回答。

  • ✅ 知识更新只需重建索引,不用重训模型
  • ✅ 只传 Top-K 相关片段,token 成本可控
  • ✅ 天然支持溯源:把检索到的片段带引用返回
  • ✅ 效果可观测:检索命中了什么、召回率多少,都能量化

三、RAG 的代价(先说清楚) ​

RAG 不是银弹,它把"模型不知道"换成了"检索不准":

  • 切分(chunking)策略直接决定召回质量
  • Embedding 模型选不对,语义检索就废了
  • 向量库选型影响延迟和成本
  • **重排序(rerank)**往往比换更大模型更有效

这四件事,正好对应本目录的 4 篇:

0-why-rag (本页)        为什么需要
0-hello-world           20 行跑通
1-intro                 整体流程与 5 个核心步骤
2-embedding             检索准不准,一半取决于 Embedding
3-vector-store          存哪儿
4-retrieval             怎么检回来(改写/HyDE/重排/混合检索)
5-real-rag              完整项目

四、什么时候不该用 RAG ​

  • 文档极少(几条 FAQ)→ 直接塞 prompt 更简单
  • 问题不需要引用原文 → 微调风格 or 直接调模型
  • 强结构化查询(精确数值、聚合统计)→ SQL 比 RAG 靠谱
  • 实时性要求极高且数据变动频繁 → 慎用 RAG,索引重建跟不上

🎯 面试常考 ​

Q1:为什么不用微调而要用 RAG? 微调改变的是模型的行为,RAG 改变的是模型的输入。要注入具体事实,应该改输入;要固定输出格式/语气/风格,才考虑微调。微调的知识更新成本也远高于重建索引。

Q2:RAG 和长上下文(RAG 替代方案)怎么选? 文档量在上下文窗口内(如 20 万 token)且查询不聚焦时,直接塞长上下文更简单;文档量大、查询聚焦、需要溯源、需要频繁更新时,RAG 更优。实践中常混用:先用检索缩小范围,再长上下文精读。

Q3:RAG 的效果怎么评估? 分两段:检索侧看召回率(正确片段有没有被检回来,常用 Recall@k / MRR);生成侧看忠实度(回答是否只依赖检索到的内容)。检索没召回,生成再好也没用,所以先查检索。

📝 小结 ​

  • 模型的"不知道"分私有知识、时效知识、可溯源三类,RAG 主要解决前两类并顺带解决第三类。
  • 三条路的取舍:微调改行为、RAG 改输入、塞 prompt 是最朴素的方案。
  • RAG 的真实成本在检索侧 —— 切分、Embedding、向量库、重排,这四件事决定效果上限。
  • 文档少、查询不聚焦、需要精确统计的场景,RAG 未必是更好的选择。
