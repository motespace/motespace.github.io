AI 影视开发流程 · 具体实现 ​

上一篇讲的是「这个平台长什么样、为什么这么设计」。这一篇把它写出来 —— 从领域模型、模型适配层、Agent 编排、任务队列、一致性绑定、成本核算,到前端的流式交互与候选对比,每一层都给可落地的代码。

技术栈:Python 3.11 + FastAPI + Pydantic v2 + asyncio(生产换 Celery)+ PostgreSQL + Redis + Next.js 15 + React + TypeScript

代码是骨架级的:省略了重复的校验分支,但结构完整,可以直接照着搭。

一、全链路总览 ​

1.1 一次镜头生成要经过哪些系统 ​

用户点「生成这 20 个镜头」
  → POST /api/batches        写入 shot + job 记录,返回 batch_id
  → 调度器按优先级扫队列        派发到 GPU worker
  → worker 组装参数(含角色绑定)  调模型 API
  → 轮询 / 回调拿结果           落对象存储 + 回写 shot
  → SSE 推给浏览器              前端更新候选列表
  → 用户选定候选 → 版本锁定 → 成片时间线引用

注意第 3 步和第 6 步:一致性是在组装参数时注入的,进度是靠 SSE 推的。这两处是整个系统最关键的两个点,后面都有代码。

class Job(BaseModel):
    """Job = 一次生成执行。

    Shot 是静态定义,Job 是运行实例。两者分开,才能支持
    「同一分镜重跑 5 次」「失败只重试失败的那个」。
    """

    id: str
    shot_id: str
    batch_id: str | None
    status: Literal["queued", "running", "succeeded", "failed", "canceled"]
    priority: int = 0
    attempts: int = 0
    provider: str | None = None
    error_code: str | None = None      # 区分可重试 / 不可重试
    idempotency_key: str                # 幂等键
    seed: int = 0
    created_at: datetime
    started_at: datetime | None = None
    finished_at: datetime | None = None

为什么 Shot 和 Job 必须拆开

问题拆开之后怎么答
一条分镜要生成 N 个候选1 个 Shot : N 个 Job
失败重试新建 Job,Shot 保留全部历史候选
「这集花了多少卡时」该集所有 Job 的 cost 求和,与候选列表无关
抽卡次数统计count(Job) / count(Shot),这是最能反映工作流质量的一个数

三、模型适配层:一套 schema 管所有厂商 ​

这是让前端不用为每个模型硬编码一套表单的关键。

python
# providers/base.py
from typing import Any, Literal

from pydantic import BaseModel


class ParamOption(BaseModel):
    label: str
    value: str
    cost_factor: float = 1.0      # 该选项对成本的影响倍率


class ParamSpec(BaseModel):
    key: str
    label: str
    type: Literal["select", "slider", "switch", "image", "text"]
    default: Any = None
    min: float | None = None
    max: float | None = None
    step: float | None = None
    options: list[ParamOption] = Field(default_factory=list)
    cost_factor: float = 1.0
    universal: bool = False       # 是否所有模型都支持;前端据此决定显不显示


class ProviderSpec(BaseModel):
    id: str
    label: str
    supports: set[str]            # {"t2v","i2v","first_last_frame","camera","lipsync"}
    params: list[ParamSpec]
    async_only: bool = True        # 全部是异步任务
    callback_may_repeat: bool = True   # 回调是否会重复到达

成本估算直接从 schema 算,前端不用另写一份逻辑:

python
BASE_GPU_SECONDS = 12.0


def estimate_cost(spec: ProviderSpec, values: dict) -> float:
    factor = 1.0
    for p in spec.params:
        if p.key not in values:
            continue
        v = values[p.key]
        if p.type == "select":
            opt = next((o for o in p.options if o.value == v), None)
            if opt:
                factor *= opt.cost_factor
        else:
            factor *= p.cost_factor
    return BASE_GPU_SECONDS * factor

前端拿到的就是这个 spec,按 type 动态渲染表单;后端做参数校验时也用同一份,不会出现两边定义不一致。

四、Agent 编排 ​

4.1 Agent 基类:结构化输出 + 错误回灌重试 ​

LLM 返回的 JSON 经常不合规。不要让前端去兜这个错 —— 在 Agent 层校验,把错误回灌让模型自己修。

python
# agents/base.py
import json
from typing import Generic, TypeVar

from pydantic import BaseModel, ValidationError

T = TypeVar("T", bound=BaseModel)


class AgentFailed(Exception):
    def __init__(self, agent: str, reason: str) -> None:
        super().__init__(f"{agent} failed: {reason}")
        self.agent, self.reason = agent, reason


class StructuredAgent(Generic[T]):
    """要求 LLM 返回严格 JSON,并用 Pydantic 校验。"""

    name: str
    schema: type[T]
    system: str
    max_repairs: int = 2

    async def run(self, client, prompt: str, context: dict | None = None) -> T:
        messages = [
            {"role": "system", "content": self.system},
            {"role": "user", "content": prompt},
        ]
        last_error = ""
        for _ in range(self.max_repairs + 1):
            raw = await client.chat(messages)
            try:
                return self.schema.model_validate(json.loads(raw))
            except (json.JSONDecodeError, ValidationError) as e:
                last_error = str(e)[:500]
                # 把校验错误回灌,让模型自己修 —— 比重试一次有效得多
                messages.append({"role": "assistant", "content": raw})
                messages.append(
                    {
                        "role": "user",
                        "content": f"JSON 不合法,错误如下,请只返回修正后的 JSON:\n{last_error}",
                    }
                )
        raise AgentFailed(self.name, last_error)

from typing import Literal

)

关键设计:Agent 输出的是「人名」,不是资产 ID。

因为模型不知道数据库里角色的 ID 和版本号 —— 让它编 ID 只会产出垃圾数据。映射由后端做:

python
def bind_characters(shots: list[ShotSpec], assets: list[CharacterAsset]) -> list[Shot]:
    """把 Agent 输出的人名映射到具体的角色资产版本。

    映射不到必须报错 —— 静默丢弃是这类系统最常见的线上事故:
    用户看到"这个角色不见了",但没有任何报错信息。
    """
    by_name: dict[str, list[CharacterAsset]] = {}
    for a in assets:
        by_name.setdefault(a.name, []).append(a)

    out: list[Shot] = []
    for s in shots:
        refs: list[CharacterRef] = []
        for name in s.character_names:
            cands = by_name.get(name)
            if not cands:
                raise CharacterNotFound(f"分镜引用了不存在的角色:{name}")
            latest = max(cands, key=lambda a: a.version)
            refs.append(
                CharacterRef(
                    character_id=latest.id,
                    version=latest.version,
                    role="lead" if s.index == 0 else "support",
                )
            )
        data = s.model_dump(exclude={"character_names"})
        out.append(Shot(**data, character_refs=refs))
    return out

边界很重要:调度 Agent 只能在候选集里选,不能凭空造参数值。约束来自 ProviderSpec,由代码强制:

python
def validate_decision(decision: ShotDecision, registry: dict[str, ProviderSpec]) -> None:
    spec = registry.get(decision.provider)
    if spec is None:
        raise ValueError(f"未知 provider:{decision.provider}")

    for p in spec.params:
        if p.key not in decision.params:
            continue
        value = decision.params[p.key]
        if p.type == "select":
            allowed = {o.value for o in p.options}
            if value not in allowed:
                raise ValueError(f"{decision.provider}.{p.key} 取值非法:{value}")
        elif p.type == "slider":
            if p.min is not None and value < p.min:
                raise ValueError(f"{decision.provider}.{p.key} 低于下限 {p.min}")
            if p.max is not None and value > p.max:
                raise ValueError(f"{decision.provider}.{p.key} 高于上限 {p.max}")

约束交给代码,不交给提示词。 提示词只负责"帮我选得好",代码负责"不许乱来"。

5.1 队列抽象:本地 asyncio / 生产 Celery ​

python
# app/queue.py
import asyncio
from typing import Protocol


class JobQueue(Protocol):
    async def enqueue(self, job_id: str, priority: int = 0) -> None: ...
    async def dequeue(self, timeout: float = 1.0) -> str | None: ...
    def qsize(self) -> int: ...


class AsyncioQueue:
    """单机开发用。PriorityQueue 默认小值先出,所以用负数把优先级反过来。"""

    def __init__(self) -> None:
        self._q: asyncio.PriorityQueue = asyncio.PriorityQueue()

    async def enqueue(self, job_id: str, priority: int = 0) -> None:
        await self._q.put((-priority, job_id))

    async def dequeue(self, timeout: float = 1.0) -> str | None:
        try:
            _, job_id = await asyncio.wait_for(self._q.get(), timeout)
            return job_id
        except asyncio.TimeoutError:
            return None

    def qsize(self) -> int:
        return self._q.qsize()

换 Celery / Redis 只需实现同一个 Protocol,调度器一行都不用改。这是队列抽象唯一的价值。

5.2 调度器:并发上限 + 分级重试 + 幂等 ​

python
# app/scheduler.py
import asyncio

RETRYABLE = {"timeout", "rate_limited", "provider_5xx", "provider_busy"}
MAX_ATTEMPTS = 3


class Scheduler:
    def __init__(self, queue, store, providers, max_concurrency: int = 8) -> None:
        self.queue = queue
        self.store = store
        self.providers = providers
        self.sem = asyncio.Semaphore(max_concurrency)   # 并发上限

    async def run_forever(self) -> None:
        while True:
            job_id = await self.queue.dequeue(timeout=1.0)
            if job_id is None:
                continue
            asyncio.create_task(self._process(job_id))

    async def _process(self, job_id: str) -> None:
        async with self.sem:
            job = await self.store.get_job(job_id)
            if job.status == "canceled":
                return
            try:
                await self.store.mark_running(job_id)
                shot = await self.store.get_shot(job.shot_id)
                params = await self._build_params(shot, job)
                result = await self.providers[job.provider].submit(params)
                await self.store.complete_job(job_id, result)
            except Exception as exc:
                code = classify(exc)
                if code in RETRYABLE and job.attempts < MAX_ATTEMPTS:
                    await self.store.requeue(job_id, code)      # 退避后重入队
                else:
                    await self.store.fail_job(job_id, code)

三个必须有的细节:

细节不做会怎样
并发上限 Semaphore一次批量 500 个任务把 GPU 端打爆,整批失败
分级重试 RETRYABLE参数非法也重试 —— 重试一百次也不会成功,只是烧钱
幂等键超时重发导致重复生成、重复扣费

5.3 一致性是怎么落地的:参数注入 ​

角色一致性发生在前端看不见的地方:

python
async def _build_params(self, shot: Shot, job: Job) -> dict:
    values = dict(shot.params)

    # 把角色资产注入模型参数 —— 一致性在这一步生效
    for ref in shot.character_refs:
        asset = await self.store.get_character(ref.character_id, version=ref.version)
        values["reference_images"] = list(asset.reference_images.values())
        if asset.form == "realistic":
            values["swap_model"] = asset.swap_model
        else:
            values["style_anchor"] = asset.style_anchor

    values["duration"] = shot.duration_ms / 1000
    values["seed"] = job.seed
    # 幂等键:重试不会重复扣费
    values["idempotency_key"] = f"{shot.id}:{job.attempts}"
    return values

注意 version=ref.version:按引用的版本取资产,不是取最新的。这两行的差别,就是"历史剧集会不会被角色更新毁掉"的差别。

六、回调幂等 ​

模型侧回调会重复到达(超时重发、网关重试、用户手动刷新)。不幂等就会重复入库、重复扣费。

python
@app.post("/api/providers/{provider}/callback")
async def provider_callback(provider: str, req: CallbackRequest):
    key = req.idempotency_key

    # 已经处理过就直接吞掉,并且**返回成功**
    if await self.store.callback_seen(key):
        return {"ok": True, "duplicate": True}

    await self.store.mark_callback_seen(key)

    job = await self.store.find_job_by_idempotency_key(key)
    if job is None:
        return {"ok": False, "error": "unknown job"}

    await self.store.complete_job(job.id, req.result)
    return {"ok": True}

回调接口永远要返回 2xx。返回错误会让模型侧无限重推,把你自己的服务打挂。

七、成本核算 ​

python
# app/billing.py
PRICE_PER_GPU_SECOND = {"kling": 0.09, "jimeng": 0.07, "internal-diffusion": 0.12}


async def record_cost(store, job: Job, gpu_seconds: float) -> None:
    """成本三级归集:项目 → 集 → 镜头。

    只记总量没法优化,必须能下钻到「哪个模型、哪类镜头最烧钱」。
    """
    shot = await store.get_shot(job.shot_id)
    await store.insert_cost(
        job_id=job.id,
        shot_id=job.shot_id,
        episode_id=shot.episode_id,
        project_id=shot.project_id,
        provider=job.provider,
        shot_type=shot.shot_size,       # 景别,成本分桶的关键维度
        gpu_seconds=gpu_seconds,
        amount=gpu_seconds * PRICE_PER_GPU_SECOND.get(job.provider, 0.1),
    )


async def cost_breakdown(store, project_id: str) -> dict:
    rows = await store.cost_by_episode(project_id)
    by_provider: dict[str, float] = {}
    by_shot_type: dict[str, float] = {}
    for r in rows:
        by_provider[r.provider] = by_provider.get(r.provider, 0) + r.amount
        by_shot_type[r.shot_type] = by_shot_type.get(r.shot_type, 0) + r.amount
    return {
        "by_episode": rows,
        "by_provider": by_provider,
        "by_shot_type": by_shot_type,
    }

按镜头类型分桶是最有用的一张表 —— 它直接告诉你「哪类镜头在烧钱」。比如"全景镜头的卡时是中景的 4 倍",那成本优化就该先从全景镜头的时长和候选数下手。

八、前端:流式、批量与对比 ​

8.1 SSE 订阅 + 指数退避重连 ​

ts
// web/lib/jobs-stream.ts
export type JobEvent =
  | { type: "job"; batchId: string; job: JobDTO }
  | { type: "progress"; batchId: string; done: number; total: number }
  | { type: "cost"; batchId: string; gpuSeconds: number; amount: number };

export function subscribeBatch(
  batchId: string,
  onEvent: (e: JobEvent) => void,
): () => void {
  let es: EventSource | null = null;
  let closed = false;
  let retry = 0;

  const connect = () => {
    if (closed) return;
    es = new EventSource(`/api/jobs/stream?batch_id=${batchId}`);

    es.onopen = () => {
      retry = 0;
    };
    es.onmessage = (ev) => {
      onEvent(JSON.parse(ev.data));
    };
    es.onerror = () => {
      es?.close();
      if (closed) return;
      retry += 1;
      // 指数退避重连,上限 30s
      setTimeout(connect, Math.min(30_000, 1000 * 2 ** retry));
    };
  };

  connect();
  return () => {
    closed = true;
    es?.close();
  };
}

为什么用 SSE 而不是 WebSocket

进度是单向的(服务端 → 浏览器),SSE 自带断线重连语义、能走 HTTP/2、实现只有十几行。只有需要双向交互(比如用户中途下指令改生成参数)才值得上 WebSocket。

8.2 批量提交:前端生成幂等键 ​

// web/lib/batches.ts
export async function submitBatch(shots: ShotDTO[]) {
  // 幂等键放前端生成,避免用户连点两次提交两遍
  const idempotencyKey = shots.map((s) => s.id).join(",");

  const res = await fetch("/api/batches", {
    method: "POST",
    headers: {
      "content-type": "application/json",
      "idempot-key": idempotencyKey,
    },
    body: JSON.stringify({
      episodeId: shots[0].episodeId,
      shotIds: shots.map((s) => s.id),
      provider: shots[0].provider,
      params: shots[0].params,
    }),
  });

  // 409 = 同样的批次已经提交过,直接复用原 batch_id
  if (res.status === 409) return res.json();
  return res.json();
}

📝 小结 ​

  • 分层:内容结构(Shot / CharacterAsset)与执行记录(Job / Cost)必须分开建模,否则重试、抽卡统计、成本核算全都会拧在一起。
  • 一致性落在三个点:Agent 输出人名 → 后端映射到资产版本 → 参数注入时按版本取。版本引用错了,历史剧集会被角色改版毁掉。
  • 约束归代码,判断归模型:调度 Agent 只能从 ProviderSpec 里选,参数取值由 validate_decision 强制。
  • 队列抽象的价值就是能换实现:本地 asyncio,生产 Celery,调度器不动。
  • 三个必须有的工程细节:并发上限、分级重试、幂等键。少一个就会在批量场景下炸。
  • 前端三个关键交互:SSE + 指数退避、候选并排对比(用 poster 不用 video)、角色版本不一致提示。
  • 开发先用 mock provider 跑通全链路,再接真 API —— 否则逻辑问题和环境问题会搅在一起。
  • 最被低估的指标:按镜头类型分桶的卡时成本。它不只能省钱,还能反过来指导分镜设计。
