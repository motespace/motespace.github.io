影视 Agent 流水线:六个 Agent 如何配合 ​

Agent 原理 讲了单个 Agent 的运行机制和失败模式。这一篇讲六个 Agent 怎么配合 —— 谁负责什么、状态归谁管、交接传什么、哪里要人插一手、某一步挂了怎么恢复。

这是《AI 短剧生产平台》的编排篇。原理层的通用概念(状态所有权、交接契约、HITL)在这里都有一个具体的落点。

一、六个 Agent 的职责 ​

Agent输入输出写入的状态
剧本 Agent小说 / 大纲分集剧本剧本
角色 Agent角色设定多视角参考图 + 资产记录角色资产
分镜 Agent分集剧本 + 角色资产分镜表(景别 / 运镜 / 台词 / 角色引用)分镜
调度 Agent单个镜头模型 + 参数决策无(只出建议)
一致性 Agent全部镜头 + 资产一致性报告 + 修复建议一致性报告
剪辑 Agent选定候选时间线 + 字幕 + 音轨成片

注意「调度 Agent」不写任何状态 —— 它只输出决策,执行由队列负责。

这是把 Agent 和执行层分开的关键:调度 Agent 是「决策」,队列 worker 是「执行」。混在一起就没法异步、没法扩、没法单独重试。

二、为什么是 Pipeline,而不是 Swarm ​

Swarm(Agent 互相通信、辩论)在这个场景下是错的选择,三个理由:

  1. 成本:几百个镜头的流水线,任何「讨论」都会把调用量放大到指数级
  2. 可复现性:创作者要能只重跑第 37 镜,而不是重跑整集
  3. 职责边界是业务定的,不是模型定的:剧本、分镜、剪辑的边界本来就清楚,让模型去「商量」只会引入不确定性

判断标准:能用 Pipeline 表达的,不要用 Swarm。 Agent 每多一个,调试难度是超线性增长的。

那什么时候才用「商量」的思路?只有两处:

  • 分镜 Agent 对角色设定有歧义 → 退回角色 Agent 重新生成,而不是两个 Agent 讨论
  • 一致性 Agent 发现问题 → 产出修复建议给人,而不是自己改资产

协作的终点是回到某个明确的写入者,不是让一群 Agent 达成共识。

三、状态所有权表(最重要的一张表) ​

状态唯一写入者读者人可否直接改
剧本剧本 Agent角色 / 分镜 / 剪辑可
角色资产角色 Agent全部可(且版本化)
分镜分镜 Agent调度 / 一致性 / 剪辑可
生成任务队列 / 调度器全部可(取消 / 重试)
候选版本生成 Worker一致性 / 剪辑可(选定 / 淘汰)
一致性报告一致性 Agent人报告不改任何状态
成片时间线剪辑 Agent人可

一个状态只能有一个写入者。

「角色资产」能被两方写是最典型的翻车点:角色 Agent 想升级角色版本,一致性 Agent 又想「顺手修一下」—— 于是资产被改了,但已生成的镜头还引用着老版本,整集作废。

规则:Agent 只能提出修改,由状态的唯一写入者执行。

四、Agent 之间的交接契约 ​

python
class StoryboardHandoff(BaseModel):
    version: int = 1
    episode_id: str
    shots: list[ShotSpec]

    # 下一棒需要知道「为什么」,而不只是「是什么」
    decisions: list[str]         # 例:"第 3 镜改为中景,因为要交代环境关系"
    unresolved: list[str]        # 例:"主角在第 5 镜的服装未指定"

unresolved 字段最容易被忽略,但它极其重要 —— 它把「Agent 不知道的事」显式传下去。

没有这个字段,下游 Agent 遇到缺失信息时会自己编一个默认值(比如默认给主角一件白衬衫),然后这个默认值一路传下去,直到成片才发现全片主角穿白衬衫。显式暴露未知,比悄悄填默认值安全一个量级。

decisions 同理:它让下游能判断上游的判断是否合理,让人类审核时能快速定位争议点。

五、什么时候要人插一手(HITL) ​

节点为什么需要人人做什么
剧本定稿剧情是创作,不该被 Agent 定死改剧情、砍集数、调节奏
角色资产创建角色是 IP 资产,一次定终身选参考图、锁版本
批量生成前一次几百镜头 = 真实花钱确认预算、确认 provider
一致性报告出来后机器只能发现「不一致」,决定不了「哪个才对」选保留哪版
成片导出前合规与版权终审确认标识、确认授权

原则:把人的介入放在「创作决策」和「花钱决策」上,不要放在「技术执行」上。

让人去点「重新生成第 12 镜」是浪费人力;让人去决定「主角这集用 v1 还是 v2 角色」才是不可替代的判断。

实现方式见 反思机制 + Human-in-the-Loop 的 interrupt 用法。

六、某一步挂了怎么恢复 ​

失败点恢复策略绝对不要
剧本 Agent 输出不合法错误回灌自修(≤2 次),仍失败则降级为模板剧本无限重试
分镜 Agent 引用了不存在的角色抛错中断,把缺失角色名回灌给它静默丢弃该镜头
生成任务超时队列内重试(≤3 次),分级退避新建分镜
一致性 Agent 报告不一致产出修复建议,不自动改资产自动升版本
成本超预算暂停批次并上报偷偷降质量继续跑

两条通用原则:

  1. 重试永远发生在同一个 Job 上,不新建业务对象。 新建分镜会让用户看到一堆重复镜头。
  2. 失败必须显式上报到界面。 静默降级比直接失败更危险 —— 用户会在成片阶段才发现问题。

七、成本归因:决策费和制作费要分开 ​

python
AGENT_COST = {
    "script": 0.02,        # 剧本:LLM 成本
    "character": 0.35,     # 角色:含参考图生成
    "storyboard": 0.08,
    "director": 0.01,      # 调度:最便宜,因为只做决策
    "consistency": 0.05,
    "edit": 0.04,
}

Agent 层的 LLM 成本 和 生成层的 GPU 成本 必须分开记。

前者是「决策费」,后者是「制作费」。混在一起你就没法回答一个关键问题:

「这集成本高,是分镜拆得不好导致反复抽卡,还是Agent 本身太贵?」

分开之后答案很清楚:如果生成费远高于 Agent 费,问题在工作流(分镜参数没定对,抽卡多);如果 Agent 费占比高,问题在编排(Agent 在互相扯皮)。

再进一步,按镜头类型分桶(景别 / 有无对白 / 运动幅度),就能直接指导分镜设计。

八、完整编排骨架 ​

python
from langgraph.graph import StateGraph, END


class FilmState(TypedDict):
    episode_id: str
    script: dict | None
    characters: list[dict]
    storyboard: list[dict]
    jobs: list[dict]
    candidates: dict
    consistency_report: dict | None
    timeline: dict | None


def build_pipeline():
    graph = StateGraph(FilmState)

    graph.add_node("script", script_node)
    graph.add_node("character", character_node)
    graph.add_node("storyboard", storyboard_node)
    graph.add_node("generate", generate_node)     # 内部是队列,不是 Agent
    graph.add_node("consistency", consistency_node)
    graph.add_node("edit", edit_node)

    graph.set_entry_point("script")
    graph.add_edge("script", "character")
    graph.add_edge("character", "storyboard")
    graph.add_edge("storyboard", "generate")
    graph.add_edge("generate", "consistency")
    graph.add_edge("consistency", "edit")     # 生产环境这里接 HITL 中断
    graph.add_edge("edit", END)

    return graph.compile()

注意 generate 节点里没有 Agent —— 它是队列 worker,内部是 asyncio 队列 + 并发上限 + 分级重试。

把 Agent 和执行层分开,是整条编排能异步、能横向扩、能单独重试的前提。 详见 AI 影视开发流程 · 具体实现 的调度器部分。

九、什么时候才值得改成 Supervisor ​

只有一种情况:镜头类型差异极大,需要完全不同的生成策略(比如对话戏走口型模型、动作戏走运动模型、情绪特写走另一种模型)。

但代价是实打实的:

代价Supervisor 模式Pipeline 模式
可复现性路由依赖 LLM 判断,同一集两次跑可能不同确定
局部重跑难,主管可能重排整条链路易,重跑单个 Job
调试要看主管的每一次决策直接看节点
成本主管本身也要调模型无额外开销

除非产品明确需要「动态策略」,否则默认 Pipeline。

十、给 Agent 团队的分工建议 ​

如果这个产品要养一支 Agent 团队,分工不是按「模型能力」,而是按状态边界:

角色负责核心产出
编排/流程Pipeline 结构、状态所有权、HITL 位置能重跑、能复现
工具工程生成适配层、成本核算、幂等一套 schema 管所有厂商
领域 Agent剧本 / 分镜 / 一致性 Agent 的提示与校验结构化输出 + 业务校验
评测快照回归、成本分桶、一致性指标能说清「改了什么变好了」

「工具工程」是最被低估的一岗 —— 它的产出(一套 schema 管所有厂商)决定了所有 Agent 的开发效率。

🎯 面试常考 ​

Q1:影视生产平台要用几个 Agent?为什么不是越多越好?

「六个,但这六个是按状态边界分的,不是按模型能力分的。每多一个 Agent 就多一份上下文开销、一条失败路径、一个调试对象。判断要不要加一个 Agent 的标准是:它的状态边界是不是真的独立、交接能不能结构化、失败能不能独立重试 —— 三个都满足才加。」

Q2:这些 Agent 之间怎么传数据?状态归谁管?

「结构化交接,带版本号、决策理由和未解决项。每个状态有唯一写入者 —— 比如角色资产只能由角色 Agent 写,一致性 Agent 发现不一致只能给修复建议,不能自己改。一个状态两个写入者,结果就是不可复现的竞态。」

Q3:某一环失败怎么办?

「分级处理:能自修的回灌错误让模型改(≤2 次);能重试的留在同一个 Job 上队列重试(≤3 次,分级退避);不能修的显式上报到界面,让创作者决定。三条铁律:不新建业务对象、不静默降级、不偷偷降质量。」

Q4:哪里需要人工介入?为什么是这些地方?

「两个地方:创作决策和花钱决策。剧本定稿、角色定版、批量生成前确认预算、一致性冲突时裁决、成片导出前合规终审。让人去点重新生成是浪费人力;让人决定用哪个角色版本才是不可替代的判断。」

Q5:一致性问题怎么发现和修?

「发现靠一致性 Agent:它读全部镜头和资产,比对角色版本引用、风格锚点、服装,产出报告。修不自动做 —— 机器只能发现不一致,决定不了哪个才对。修复走人工裁决,由角色 Agent 升版本,再重跑受影响的镜头。」

Q6:为什么不用 Supervisor?

「Supervisor 的路由依赖 LLM 判断,同一个输入两次跑可能给出不同策略,而创作者要的是「只重跑第 37 镜」。Pipeline 确定性更强、可局部重跑、调试成本低。只有当镜头类型需要完全不同的生成策略时才值得换。」

✅ 六个 Agent 按状态边界划分,不是按模型能力
✅ 调度 Agent 不写状态,执行交给队列
✅ Pipeline 而非 Swarm,除非策略需要动态
✅ 状态所有权表:一个状态一个写入者
✅ 交接契约带 version / decisions / unresolved
✅ HITL 放在创作决策与花钱决策上
✅ 失败分级:自修 → 队列重试 → 上报,绝不静默降级
✅ Agent 成本与 GPU 成本分开归因
✅ 编排里 generate 节点是队列而非 Agent

📝 小结 ​

  • 六个 Agent 按状态边界划分:剧本 / 角色 / 分镜 / 调度 / 一致性 / 剪辑。
  • 调度 Agent 不写状态,只出决策;执行交给队列 —— 这是能异步、能扩、能重试的前提。
  • 用 Pipeline,不用 Swarm:可复现、可局部重跑、调试成本低。协作的终点是回到明确的写入者,不是达成共识。
  • 一个状态一个写入者;Agent 只能提出修改,由写入者执行。
  • 交接契约必须带 version / decisions / unresolved,其中 unresolved 防止下游默默编默认值。
  • HITL 放在创作决策和花钱决策上,不放技术执行。
  • 失败三级处理:自修 → 队列重试 → 上报。不新建业务对象、不静默降级、不偷偷降质量。
  • 成本上把 Agent 的决策费和 GPU 的制作费分开记,才能回答「是分镜拆得不好还是 Agent 太贵」。
