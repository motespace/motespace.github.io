MySQL 备份恢复与运维 ​

备份是"后悔药"。没做过备份恢复演练,等于没备份。 本文讲清三种备份方式 + 主从复制 + 日常运维。

🎯 学到这步能做什么 ​

  • 用 mysqldump / xtrabackup 做备份
  • 用 binlog 做增量恢复
  • 搭主从复制
  • 监控 MySQL 关键指标

📚 章节目录 ​

  • 备份方式对比
  • mysqldump 逻辑备份
  • binlog 增量恢复
  • xtrabackup 物理备份

⚖️ 备份方式对比 ​

方式工具特点适用
逻辑备份mysqldump导出 SQL,慢小库 / 迁移
物理备份xtrabackup / mysqlbackup拷数据文件,快大库 / 热备
增量备份binlog只记变更,极快PIT(Point-In-Time)恢复

原则:

  • 至少每周全量 + 每天 binlog
  • 定期演练恢复(数据备份了但恢复不出来,等于没有)
  • 备份存异地(不同机房、不同云)

📦 mysqldump 逻辑备份 ​

bash
# 1. 全库备份
mysqldump -u root -p \
  --single-transaction \
  --routines \
  --triggers \
  --events \
  --master-data=2 \
  --all-databases > all.sql

# 关键参数:
#   --single-transaction: InnoDB 一致性快照(不锁表)
#   --master-data=2:      注释掉 master 位置(binlog 位置)
#   --routines:           备份存储过程
#   --triggers:           备份触发器
#   --events:             备份事件

# 2. 单库备份
mysqldump -u root -p --single-transaction myapp > myapp.sql

# 3. 单表备份
mysqldump -u root -p myapp users > users.sql

# 4. 排除某些表
mysqldump -u root -p --ignore-table=mysql.user --all-databases > no_user.sql

# 5. 压缩备份
mysqldump -u root -p --single-transaction myapp | gzip > myapp.sql.gz

恢复 ​

bash
# 全库恢复
mysql -u root -p < all.sql

# 解压恢复
gunzip < myapp.sql.gz | mysql -u root -p

# 指定库恢复
mysql -u root -p myapp < myapp.sql

📜 binlog 增量恢复 ​

MySQL 默认开启 binlog(ROW 模式,推荐)。记录所有数据变更,做"时间点恢复"(PIT)。

开启 binlog ​

/etc/mysql/my.cnf:

ini
[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW
expire_logs_days = 7                # 自动清理 7 天前的
max_binlog_size = 1G

查看 binlog ​

bash
# 看所有 binlog
mysql -u root -p -e "SHOW MASTER LOGS;"

# 看当前 binlog 位置
mysql -u root -p -e "SHOW MASTER STATUS;"

# 用 mysqlbinlog 解析
mysqlbinlog /var/log/mysql/mysql-bin.000001 | less

# 看具体某个时间范围
mysqlbinlog --start-datetime="2024-01-15 10:00:00" \
            --stop-datetime="2024-01-15 11:00:00" \
            /var/log/mysql/mysql-bin.000001

实战:删库后恢复 ​

text
1. 13:00 全量备份 myapp.sql
2. 14:00 DBA 误执行:DELETE FROM users; (无 WHERE)
3. 14:30 发现,开始恢复

恢复流程:

bash
# 1. 先全量恢复(覆盖)
mysql -u root -p myapp < myapp.sql
# 此时是 13:00 的状态

# 2. 从 binlog 找到误操作 SQL 位置
mysqlbinlog --start-datetime="2024-01-15 13:00:00" \
            /var/log/mysql/mysql-bin.000001 > binlog.sql

# 3. 在 binlog.sql 里找到误操作位置,手动跳过
#    或者用 mysqlbinlog --start-position / --stop-position

# 4. 应用 binlog 到 14:00 之前
mysqlbinlog --stop-position=12345 /var/log/mysql/mysql-bin.000001 | mysql -u root -p

关键:有 --master-data=2 的全量备份,可以告诉你在哪个 binlog 位置开始重放。

💾 xtrabackup 物理备份 ​

bash
# 安装
# Ubuntu:apt install percona-xtrabackup-80
# macOS:brew install percona-xtrabackup

# 1. 全量备份
xtrabackup --user=root --password=xxx \
           --target-dir=/backup/2024-01-15 \
           --backup

# 2. 准备(应用 redo log)
xtrabackup --prepare --target-dir=/backup/2024-01-15

# 3. 恢复(拷贝数据文件)
xtrabackup --copy-back --target-dir=/backup/2024-01-15

# 4. 改权限
chown -R mysql:mysql /var/lib/mysql

优势:

  • 物理拷文件,快得多(GB 级)
  • 支持热备,不锁 InnoDB
  • 支持增量备份

🔁 主从复制 ​

一主多从 = 主库写、从库读,分担压力 + 备份。

text
┌─────┐    binlog    ┌─────┐
│主库 │ ────────────> │从库 │
│(写) │               │(读) │
└─────┘               └─────┘

主库配置 ​

my.cnf:

ini
[mysqld]
server_id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW

从库配置 ​

my.cnf:

ini
[mysqld]
server_id = 2
relay_log = /var/log/mysql/relay-bin.log
read_only = ON                  # 从库只读(防误写)
log_slave_updates = ON

建立主从 ​

sql
-- 主库:建复制账号
CREATE USER 'repl'@'%' IDENTIFIED BY 'replpass';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 主库:看 binlog 位置(假设是 file=binlog.000003, pos=100)
SHOW MASTER STATUS;

-- 从库:配置主库
CHANGE MASTER TO
  MASTER_HOST = 'master.example.com',
  MASTER_USER = 'repl',
  MASTER_PASSWORD = 'replpass',
  MASTER_LOG_FILE = 'binlog.000003',
  MASTER_LOG_POS = 100;

-- 从库:启动复制
START SLAVE;

-- 看状态
SHOW SLAVE STATUS\G
-- 关键看:Slave_IO_Running: Yes, Slave_SQL_Running: Yes, Seconds_Behind_Master: 0

复制模式 ​

模式binlog_format特点
STATEMENT记录 SQL节省空间,但 NOW() / UUID() 可能不一致
ROW(推荐)记录行变更安全,但 binlog 大
MIXED混合MySQL 自己选

📊 运维监控指标 ​

系统指标 ​

sql
-- 连接数
SHOW STATUS LIKE 'Threads_connected';       -- 当前连接
SHOW STATUS LIKE 'Max_used_connections';    -- 峰值
SHOW VARIABLES LIKE 'max_connections';      -- 上限

-- QPS / TPS(粗略)
SHOW STATUS LIKE 'Queries';
SHOW STATUS LIKE 'Com_commit';
SHOW STATUS LIKE 'Com_rollback';

InnoDB 指标 ​

sql
-- buffer pool 命中率(应 > 99%)
SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';
-- 命中率 = 1 - reads / read_requests

-- 行锁等待
SHOW STATUS LIKE 'Innodb_row_lock_waits';
SHOW STATUS LIKE 'Innodb_row_lock_time';

-- 当前锁
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;  -- 谁在等谁

推荐监控方案 ​

工具特点
Prometheus + mysqld_exporter + Grafana开源主流,自定义 dashboard
PMM(Percona Monitoring)MySQL 专用,开箱即用
云数据库自带监控阿里云 / AWS RDS 等

⚠️ 容易踩的坑 ​

坑表现解决
--master-data=1 但又 STOP SLAVE主从挂掉主库用 =2(注释掉),从库手动写
没做恢复演练真出事恢复不出来每季度演练一次
备份在同机房机房炸了备份也没了异地备份(OSS / S3 / 异地机房)
binlog 没开没 PIT 恢复能力log_bin = ON + ROW 模式
从库 read_only 没开应用误写从库,主从不一致read_only = ON(super 权限也能绕,生产用 super_read_only)
主从延迟大从库读到旧数据接受(用缓存补偿) 或 强制读主
CHANGE MASTER TO 后没 START SLAVE复制没启动完整两步:CHANGE ... + START SLAVE
xtrabackup 恢复后启动不了权限错 / InnoDB log 文件残留chown -R mysql:mysql /var/lib/mysql
