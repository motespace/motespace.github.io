MySQL 索引

索引是 MySQL 性能优化的头号杠杆。一个好索引能把查询从 10 秒降到 10 毫秒。 本文讲清原理 + 实战用法,不背八股。

🌲 索引的底层数据结构

Section titled “🌲 索引的底层数据结构”

MySQL InnoDB 用 B+ 树做索引。

B+ 树相对 B 树的好处:

  • 叶子节点用链表串起来,范围查询不用回上层
  • 非叶子节点只存键值,一页能装更多指针,树更矮(一般 3-4 层)
  • 所有数据访问都要走到叶子,查询性能稳定

磁盘 IO 模型:每层是一次 IO,3-4 层 = 3-4 次 IO 就能查到百万行。这也是为什么“走索引”快。

🏛️ 聚簇索引 vs 二级索引

Section titled “🏛️ 聚簇索引 vs 二级索引”
维度 聚簇索引(主键索引) 二级索引(普通索引)
数据存储 叶子节点存完整行数据 叶子节点存主键值
数量 每张表只有一个 可以多个
决定因素 默认主键;无主键找第一个 UNIQUE NOT NULL;都没有则隐藏 ROW_ID 任何索引字段

回表:用二级索引查时,先找到主键,再用主键去聚簇索引查完整行 —— 这就是“回表”。

实战建议:

  • 主键用自增 BIGINT(顺序写,避免页分裂)
  • 不用 UUID 当主键(无序 + 占空间 + 页分裂多)
  • 业务字段做主键要谨慎(订单号、身份证号都不推荐当聚簇键)

🎯 覆盖索引

Section titled “🎯 覆盖索引”

如果查询的列全部在一个索引里,就不用回表 —— 叫“覆盖索引”,性能最优。

实战:用 SELECT col1, col2 代替 SELECT *,不光省 IO,还能走覆盖索引。

🔍 EXPLAIN 调优

Section titled “🔍 EXPLAIN 调优”

EXPLAIN 是 MySQL 调优的“听诊器”:

返回字段含义:

字段 含义 关键值
id 查询序号 越大越先执行
select_type 查询类型 SIMPLE / PRIMARY / SUBQUERY
table 表名
type 访问类型 system > const > eq_ref > ref > range > index > ALL
possible_keys 可能用到的索引
key 实际用到的索引 NULL 表示全表扫
key_len 用到的索引长度 越短越好
rows 预估扫描行数 越小越好
Extra 额外信息 见下表

type 字段(从快到慢)

Section titled “type 字段(从快到慢)”
type 含义 何时出现
system 系统表 单行系统表
const 主键 / 唯一索引等值 WHERE id = 1
eq_ref JOIN 时用主键 JOIN ON u.id = o.user_id
ref 普通索引等值 WHERE name = '张三'
range 索引范围 WHERE id > 100
index 全索引扫 SELECT id FROM users(无 WHERE)
ALL 全表扫 需要优化

Extra 关键信息

Section titled “Extra 关键信息”
Extra 含义 严重度
Using index 走了覆盖索引 ✅ 好
Using where 用 WHERE 过滤 正常
Using filesort 额外排序 ⚠️ 慢,看能否走索引排序
Using temporary 用临时表(GROUP BY 等) ⚠️ 慢
Using join buffer JOIN buffer ⚠️ 关联字段没索引

🚫 常见索引失效场景

Section titled “🚫 常见索引失效场景”

⚠️ 容易踩的坑

Section titled “⚠️ 容易踩的坑”
坑 表现 解决
索引越多越好 写慢、占空间 只建必要索引(查询频繁、过滤强)
小表建索引 维护成本大于收益 几百行以下可以不建
区分度低的字段建索引 索引选择性差 WHERE sex = '男' 不建索引(扫描行太多)
排序字段不建索引 Using filesort ORDER BY 字段走索引
LIMIT 深分页 + ORDER BY 巨慢 改游标分页 / 主键分页
JOIN 字段类型不一致 索引失效 保证关联字段类型完全一致
用了 != / <> / NOT IN 索引可能失效 改 id NOT IN (...) 通常没事,字段上视场景
删了索引忘了回滚 生产事故 ALTER TABLE 前先在从库试
