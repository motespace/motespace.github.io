MySQL 数据类型与表设计 ​

选错类型 = 浪费空间 + 查询慢 + 数据污染。 本文给"类型怎么选" + "表怎么设计"两条主线。

🎯 学到这步能做什么 ​

  • 给字段选最合适的类型
  • 用主键 / 外键维护数据完整性
  • 知道 1NF / 2NF / 3NF 是什么
  • 用反范式做性能优化

🔢 数值类型 ​

类型字节范围用途
TINYINT1-128 ~ 127 / 0~255 UNSIGNED年龄、状态码
SMALLINT2±3.2 万枚举数量
INT4±21 亿主键、计数
BIGINT8±9.2 × 10¹⁸订单号、雪花 ID
FLOAT47 位精度不用
DOUBLE815 位精度科学计算
DECIMAL(M,D)变长精确小数钱

要点:

  • 钱永远用 DECIMAL(10, 2),不要用 FLOAT / DOUBLE(浮点误差)
  • 主键自增用 INT UNSIGNED AUTO_INCREMENT,够 21 亿单表
  • 超大表 / 分布式用 BIGINT,可放雪花 ID(19 位)
  • 状态码 / 枚举用 TINYINT,省 3 字节比 INT
sql
-- 钱的正确写法
price DECIMAL(10, 2) NOT NULL DEFAULT 0

-- 主键
id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY

-- 状态(枚举用 tinyint + 注释)
status TINYINT NOT NULL DEFAULT 0 COMMENT '0=待付款 1=已付款 2=已发货 3=已完成'

📝 字符串类型 ​

类型长度上限用途
CHAR(N)255固定长度(国家代码、MD5、UUID)
VARCHAR(N)65535 / 实际 65533可变长度(姓名、邮箱)
TEXT65535长文本(评论)
MEDIUMTEXT16 MB文章正文
LONGTEXT4 GB不推荐,文件存磁盘
ENUM65535 个固定选项
JSON1 GBJSON 数据(MySQL 5.7+)

要点:

  • VARCHAR(N) 的 N 是字符数不是字节数
  • CHAR(32) 存 MD5、UUID(去掉 -)刚好,长度固定用 CHAR 比 VARCHAR 快
  • TEXT 字段不参与内存临时表,大字段考虑单独存表
  • JSON 类型(MySQL 5.7+)可以查询内部字段,比 TEXT + JSON.parse 好
sql
-- 邮箱
email VARCHAR(255) NOT NULL

-- 文章正文
content MEDIUMTEXT NOT NULL

-- 标签数组(JSON)
tags JSON

-- 查询 JSON 内字段
SELECT * FROM articles
WHERE JSON_EXTRACT(tags, '$[0]') = 'python';

⏱️ 时间类型 ​

类型格式占用范围用途
DATEYYYY-MM-DD31000-01-01 ~ 9999-12-31生日
TIMEHH:MM:SS3±838 小时时长
DATETIMEYYYY-MM-DD HH:MM:SS81000-01-01 ~ 9999-12-31创建时间(业务时间)
TIMESTAMP同上41970 ~ 2038更新时间(UTC 自动转换)
YEARYYYY11901 ~ 2155年份

要点:

  • 业务时间用 DATETIME(不受时区影响,不踩 2038 问题)
  • TIMESTAMP 有 2038 年问题,数据量大时慎用
  • 不用 VARCHAR 存时间,排序 / 比较 / 函数全失效
  • 时区:DB 服务器时区 + 应用服务器时区 + 用户时区,统一存 UTC 展示时转
sql
created_at DATETIME DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

🔑 主键设计 ​

自然主键 vs 代理主键 ​

类型含义例子
自然主键业务字段本身唯一身份证号、订单号
代理主键与业务无关,只为唯一自增 ID、UUID

经验:默认用代理主键(BIGINT AUTO_INCREMENT),除非业务字段真的稳定唯一。

sql
CREATE TABLE orders (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    order_no VARCHAR(32) NOT NULL UNIQUE,        -- 业务订单号(可查询)
    user_id BIGINT UNSIGNED NOT NULL,
    amount DECIMAL(10, 2) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id)
);

UUID / 雪花 ID ​

分布式系统需要全局唯一 ID:

方案长度特点
自增 ID8 字节单库最快,不能分布式
UUIDv436 / 32无序,索引性能差
UUIDv7(新)36 / 16 字节时间有序,推荐
雪花 ID8 字节 long分布式有序,Twitter / 美团用
雪花字符串18 字符业务可见,但要存 VARCHAR
sql
-- 雪花 ID 存 BIGINT(性能最好)
id BIGINT UNSIGNED NOT NULL
-- 雪花 ID 存字符串(业务友好)
id VARCHAR(20) NOT NULL

🔗 外键与关联 ​

sql
CREATE TABLE comments (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    post_id BIGINT UNSIGNED NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    content TEXT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_post_id (post_id),                  -- 外键必须有索引
    FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE
);

-- CASCADE:posts 删了,comments 一起删
-- RESTRICT(默认):禁止删 posts(有 comments 引用)
-- SET NULL:posts 删了,comments.post_id = NULL

实际项目里很多团队不用外键约束,理由:

  1. 性能开销(每次 INSERT/UPDATE 都要检查)
  2. 分布式 / 分库分表后外键失效
  3. ORM 自己维护关联关系

推荐做法:业务逻辑保证完整性,数据库只建索引不建外键约束(代码层用 SQLAlchemy / Prisma 关联)。

📐 三大范式 ​

范式 = 减少冗余、避免数据异常。

1NF:字段不可分 ​

sql
-- ❌ name 里塞了电话和地址
name = '张三 13800001111 杭州'

-- ✅ 拆开
name = '张三', phone = '13800001111', city = '杭州'

2NF:非主键字段完全依赖主键 ​

sql
-- ❌ order_items 表里存了 product_name
--    (product_name 只依赖 product_id,不是完全依赖 (order_id, product_id))
( order_id, product_id, product_name, quantity, price )

-- ✅ 拆 product_name 到 products 表
( order_id, product_id, quantity, price )

3NF:非主键字段不能传递依赖 ​

sql
-- ❌ users 表里存了 dept_name,而 dept_name 依赖 dept_id
( user_id, dept_id, dept_name )

-- ✅ dept_name 放 departments 表
( user_id, dept_id )

🔄 反范式:为了性能而冗余 ​

范式越严,JOIN 越多。高并发 / 高 QPS 读场景,适度反范式:

sql
-- 帖子表冗余作者名(避免列表页 JOIN users)
CREATE TABLE posts (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    author_name VARCHAR(50) NOT NULL,           -- 冗余,JOIN 时省掉
    title VARCHAR(200) NOT NULL,
    content MEDIUMTEXT NOT NULL,
    view_count INT UNSIGNED DEFAULT 0,           -- 计数冗余
    comment_count INT UNSIGNED DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id)
);

反范式原则:

  • 读多写少 → 反范式划算
  • 数据要严格一致(钱、库存) → 不反范式,事务保证
  • 冗余字段更新成本要可控(异步、消息队列)

⚠️ 容易踩的坑 ​

坑表现解决
用 VARCHAR(255) 存一切浪费空间、查询慢按实际长度选
钱用 FLOAT / DOUBLE计算误差(0.1 + 0.2 ≠ 0.3)永远用 DECIMAL
时间存 VARCHAR排序 / 比较失效,索引无用DATETIME / TIMESTAMP
状态用中文 VARCHAR存 '已付款' 占空间用 TINYINT + 注释
TEXT 当主键 / 索引不支持用前缀索引:INDEX (content(50))
自增 ID 归零 / 溢出21 亿后 BIGINT 续命评估数据量,大表用 BIGINT
主键 UUID 用 VARCHAR(36)索引性能差,占空间用 BINARY(16) 或 UUIDv7
字段都 NOT NULL 不设默认值业务代码到处 if is None关键字段必设默认值
