MySQL 事务与锁 ​

事务是数据库的"保险丝":保证一组操作要么全成、要么全败。 本文讲清 ACID、隔离级别、行锁、间隙锁、怎么排查死锁。

  • 解释 ACID 是什么

  • 选合适的隔离级别
  • 排查死锁、看懂 lock info

⚖️ ACID 四大特性 ​

特性含义实现机制
Atomic 原子性全成或全败undo log
Consistent 一致性数据从不合法状态过渡到合法应用 + DB 约束
Isolation 隔离性并发事务互不干扰锁 + MVCC
Durable 持久性提交后不丢redo log

🎮 事务控制语句 ​

sql
-- 开启事务
START TRANSACTION;          -- 或 BEGIN
-- MySQL 默认 autocommit=1,每条 SQL 自动提交
-- 事务里要手动 COMMIT / ROLLBACK

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 没问题就提交
COMMIT;
-- 有问题就回滚
ROLLBACK;

-- 保存点(部分回滚)
SAVEPOINT sp1;
UPDATE ...;
ROLLBACK TO sp1;            -- 回滚到 sp1,但 sp1 之前的不影响
COMMIT;

自动提交关闭 ​

sql
-- 关闭自动提交(进入"事务模式")
SET autocommit = 0;

-- 改完手动 COMMIT
UPDATE ...;
COMMIT;

-- 重新打开
SET autocommit = 1;

🔬 四种隔离级别 ​

并发问题有 3 类:脏读 / 不可重复读 / 幻读。

隔离级别脏读不可重复读幻读性能
READ UNCOMMITTED✅✅✅最高
READ COMMITTED❌✅✅高
REPEATABLE READ(MySQL 默认)❌❌✅(InnoDB 大部分场景无)中
SERIALIZABLE❌❌❌最低
sql
-- 查看隔离级别
SELECT @@transaction_isolation;
-- MySQL 8.0+:transaction_isolation
-- MySQL 5.x:tx_isolation

-- 设置(会话级)
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 设置(全局,需重启连接)
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

概念解释 ​

  • 脏读:读到别人未提交的数据(别人回滚你就用了错的数据)
  • 不可重复读:同一事务内,两次读同一行,数据不一样(被别的事务改了)
  • 幻读:同一事务内,两次查同一范围,行数不一样(被别的事务插入/删除了)

MySQL InnoDB 在 REPEATABLE READ 下通过 MVCC + 临键锁基本避免了幻读。

🔐 锁的类型 ​

按粒度:

锁类型范围开销并发度
全局锁整个 DB极大极低
表级锁整张表大低(MyISAM 用)
行级锁单行 / 范围小高(InnoDB 默认)

按模式:

锁描述兼容
共享锁(S)读锁,可多人共持S 与 S 兼容
排他锁(X)写锁,独占X 与谁都不兼容
sql
-- 加共享锁(其他事务可读不可写)
SELECT * FROM users WHERE id = 1 LOCK IN SHARE MODE;
-- MySQL 8.0+:FOR SHARE

-- 加排他锁(其他事务不能读也不能写)
SELECT * FROM users WHERE id = 1 FOR UPDATE;

🔒 行锁 / 间隙锁 / 临键锁 ​

InnoDB 的行锁是索引上的锁,不是"行记录"上的锁。

锁范围何时用
Record Lock索引上的具体一条记录等值查询命中
Gap Lock索引记录之间的"间隙"防止插入新行(防幻读)
Next-Key LockRecord + Gap,左开右闭默认,REPEATABLE READ 用

间隙锁例子 ​

sql
-- users 表 id 有索引:1, 5, 9
-- 事务 A:
SELECT * FROM users WHERE id BETWEEN 1 AND 9 FOR UPDATE;
-- 会锁住 (1, 5) (5, 9) (9, +∞) 三个间隙
-- 此时事务 B 想 INSERT id = 3 会被阻塞

实战:

  • 查询走索引 → 行锁 / 间隙锁(细)
  • 查询没走索引 → 表锁(粗)
  • REPEATABLE READ + 索引查询是最常用的高并发方案

⚠️ 死锁与排查 ​

两个事务互相等对方的锁:

text
事务 A:                          事务 B:
UPDATE users WHERE id=1;         UPDATE users WHERE id=2;
UPDATE users WHERE id=2;  -- 等 B  UPDATE users WHERE id=1;  -- 等 A
                                ↓ 互相等
                              DEADLOCK

MySQL 自动检测死锁,回滚其中一个事务(ERROR 1213: Deadlock found)。

排查 ​

sql
-- 1. 看最近死锁日志
SHOW ENGINE INNODB STATUS\G

-- 2. 找 LATEST DETECTED DEADLOCK 段

-- 3. 关键看:
--    - 涉及哪些事务
--    - 持有什么锁
--    - 等待什么锁
--    - MySQL 选择了回滚哪个

避免死锁 ​

  • 加锁顺序一致:多表操作约定统一的加锁顺序
  • 尽量用主键或唯一索引查(锁范围小)
  • 大事务拆小事务(长时间持锁是死锁温床)
  • 设置锁等待超时:SET innodb_lock_wait_timeout = 5(秒)
  • 用 SELECT ... FOR UPDATE NOWAIT / SKIP LOCKED(MySQL 8+)不阻塞

⚖️ 乐观锁 vs 悲观锁 ​

悲观锁(数据库行锁) ​

sql
BEGIN;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;  -- 加 X 锁
-- 应用判断 stock > 0
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;

适合:写多读少、冲突严重(抢购、库存扣减)

乐观锁(版本号,无锁) ​

sql
-- 表加 version 字段
ALTER TABLE products ADD COLUMN version INT NOT NULL DEFAULT 0;

-- 更新时
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;     -- 假设当前 version 是 5
-- 受影响行数 = 0 表示被别人改了,需要重试

适合:读多写少、冲突少(更新个人信息)

⚠️ 容易踩的坑 ​

坑表现解决
事务里做 HTTP 调用长时间持锁,阻塞别人事务内只做 DB 操作,HTTP 放外面
事务里 SELECT sleep(10)等同持锁 10 秒不要在事务里 sleep
大事务(改 100 万行)undo log 暴涨,锁竞争拆小批量
用 SERIALIZABLE 解决并发性能暴跌大部分场景 REPEATABLE READ 足够
FOR UPDATE 没走索引表锁,锁全表必须走索引
RC 隔离级别下没加 FOR UPDATE不可重复读业务允许就用 RC,不能就用 RR + 锁
死锁就重试同一个事务死循环加最大重试次数 + 退避
innodb_lock_wait_timeout 默认 50 秒用户等不及改 5-10 秒,失败快速返回
