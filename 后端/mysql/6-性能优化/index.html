案例:订单列表页慢

Section titled “案例:订单列表页慢”

症状:加载 30 秒。

步骤:

  1. mysqldumpslow 找出:SELECT * FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20(执行 5 秒/次)
  2. EXPLAIN:type: ALL,全表扫
  3. 加索引:CREATE INDEX idx_user_created ON orders(user_id, created_at DESC);
  4. 再 EXPLAIN:type: ref, rows: 20
  5. 加载降到 50ms

案例:统计查询慢

Section titled “案例:统计查询慢”

扫全表 1 亿行,慢。

解决:

  • 加索引 → GROUP BY 不一定走索引,看场景
  • 改用预计算:定时任务跑统计,结果存 city_stats 表
  • 用近似统计(缓存 / 物化视图)

⚠️ 容易踩的坑

Section titled “⚠️ 容易踩的坑”
坑 表现 解决
加了索引性能没变化 索引选错 / 没生效 EXPLAIN 确认 key 不为 NULL
改了索引但线上没生效 从库加的索引没同步 主从都改 / 用 gh-ost 在线改
ALTER TABLE 锁表 几十分钟无法写入 用 pt-online-schema-change / gh-ost
改了 my.cnf 没生效 配置文件路径不对 SHOW VARIABLES LIKE 'basedir' 找路径
innodb_buffer_pool_size 设太大 swap 飙升 留 30% 内存给 OS / 其他进程
慢查询日志塞满磁盘 DB 挂掉 logrotate / 单独挂日志盘
改 SQL 破坏了业务逻辑 查到的数据不对 上线前在从库跑 + 数据对比
