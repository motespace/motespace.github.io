Vite 的 HMR 原理是什么？和 Webpack HMR 有什么区别？ ​

📚 深度专题推荐：本文是关于「Vite HMR」的精炼回答。如需对比 Webpack HMR，建议阅读 Webpack HMR 原理。

一、Vite HMR 原理：基于原生 ESM + WebSocket ​

核心机制 ​

源码修改
  ↓
Vite 监听文件变化（chokidar）
  ↓
通过 WebSocket 推送更新消息（update 模块）
  ↓
浏览器收到消息 → 找到对应模块 → 重新请求
  ↓
新模块替换旧模块 → 触发组件 HMR API
  ↓
页面局部更新（不刷新）

关键文件：WebSocket 客户端 ​

js
// Vite 自动注入到每个页面的 client 代码（简化）
import { HMRClient } from '/@vite/client'

HMRClient.connect({
  // 1. 建立 WebSocket 连接（Vite dev server 推送更新）
  // 2. 收到 update 消息 → 浏览器重新请求模块
  // 3. 调用模块的 hot.accept() 回调
})

二、模块边界精确替换 ​

Webpack HMR：重建依赖图 ​

修改 User.vue
  ↓
Webpack 重新编译 User.vue + 所有依赖 User 的模块
  ↓
通过 HMR Runtime 替换
  ↓
任何依赖 User 的父组件都会重新渲染

问题：哪怕只改一行，整个依赖链都会重新执行。

Vite HMR：精确到模块 ​

修改 User.vue
  ↓
Vite 只让 User.vue 模块失效（invalidate）
  ↓
通过 import.meta.hot 通知浏览器
  ↓
浏览器只重新请求 User.vue
  ↓
只有直接 import User 的父组件触发 HMR 回调

优势：HMR 影响范围更小，速度更快。

三、import.meta.hot API ​

js
// Vite 的 HMR API
if (import.meta.hot) {
  // 1. 接受自身模块的更新（自己处理 HMR）
  import.meta.hot.accept((newModule) => {
    // newModule 是更新后的新模块
    console.log('模块更新了', newModule)
  })

  // 2. 接受某个依赖的更新（向上冒泡）
  import.meta.hot.accept('./utils.js', (newUtils) => {
    console.log('utils 更新了', newUtils)
  })

  // 3. 销毁前的清理
  import.meta.hot.dispose(() => {
    // 清理定时器、事件监听等
    clearInterval(this.timer)
  })

  // 4. 拒绝冒泡（强制刷新页面）
  import.meta.hot.accept(() => {})
  import.meta.hot.invalidate()  // 触发整页刷新
}

Vue 3（@vitejs/plugin-vue 自动处理） ​

// Vite 编译 .vue 文件时自动注入 HMR 边界
// 父组件 import 的子组件更新时，Vite 会保留组件状态

React（@vitejs/plugin-react 用 React Fast Refresh） ​

js
// Fast Refresh 会保留组件 state
// 只重新渲染组件，不丢失状态

第三方库支持 ​

  • vue-loader 自动处理
  • react-refresh 自动处理
  • 自己写的普通 JS 模块 → 需要手动写 import.meta.hot.accept()

五、性能对比 ​

实测中型项目，修改一个普通组件文件：

维度Webpack HMRVite HMR
编译时间800-2000ms< 100ms
浏览器更新100-300ms< 50ms
整体感知卡顿明显几乎无感

六、为什么 Vite HMR 这么快？ ​

1. 依赖图局部 ​

Webpack 必须维护完整依赖图，任何改动都重新计算。Vite 只关心浏览器当前加载了哪些模块。

2. 按需编译 ​

修改的文件 + 其依赖被浏览器请求时，Vite 才编译它们。未访问的路由不会被处理。

3. 不需要 bundle ​

Webpack HMR 推送的是「编译后的 chunk」，Vite 推送的是「单文件 + 路径」。传输量更小。

4. 浏览器原生 ESM ​

模块替换由浏览器自己完成，Vite 不需要拦截 patch。

七、面试追问 ​

Q：Vite HMR 为什么能保留组件状态？

A：因为 Vue 3 / React Fast Refresh 在编译时给每个组件加了唯一 ID 和状态映射表。组件实例不变，只替换渲染函数。

Q：HMR 失败了会怎样？

A：

  • 框架插件处理过 → 自动 fallback 整页刷新
  • 自己写的模块没写 accept → 整页刷新
  • 不可恢复的错误 → 强制刷新

Q：怎么手动实现一个模块的 HMR？

A：

js
// counter.js
export let count = 0

if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // 把新模块的值同步到当前模块
    if (newModule) count = newModule.count
  })
}

Q：Vite HMR 用 WebSocket，会不会很耗资源？

A：WebSocket 只传元数据（哪个文件变了 + hash），不传文件内容。文件内容走 HTTP 缓存。实际开销很小。

🎯 面试常考 ​

Q1：Vite 的 HMR 为什么比 Webpack 快?

Vite 只需要让浏览器重新请求发生变更的那个模块,不需要重新打包整个依赖图;而 Webpack 需要重新生成 chunk 并让浏览器接受更新。

Q2：Vite HMR 的边界在哪?

纯 CSS 热更新是全量替换;组件 HMR 靠 Vue/React 插件;修改某些配置需要重启 dev server(插件会提示)。

📝 小结 ​

  • Vite HMR 的本质是「按需编译 + 浏览器原生 ESM 的模块替换能力」。
  • 框架的 HMR 能力来自官方插件(Vite 的 @vitejs/plugin-vue 等),不是 Vite 内置的。
  • 改 vite.config 本身必须重启,这属于设计上的取舍。
