Vite 为什么 dev 用 esbuild、prod 用 Rollup（双构建）？ ​

📚 深度专题推荐：本文是关于「Vite 双构建策略」的精炼回答。如需了解 HMR 原理，建议阅读 Vite HMR 原理。

一、Vite 双构建策略 ​

npm run dev（开发环境）    →   esbuild（速度优先）
npm run build（生产环境）  →   Rollup（产物质量优先）

二、Dev 用 esbuild ​

原因 ​

维度esbuildRollup
速度极快（Go 机器码）慢（JS）
代码分割弱强
Tree-shaking一般优秀
适用场景dev transformprod build

Dev 阶段 esbuild 做什么？ ​

  1. 依赖预构建（最关键）
  2. TypeScript / JSX 转译（去掉类型、不做类型检查）
  3. CSS 处理（部分）
  4. CommonJS → ESM

Dev 不需要完美产物的理由 ​

  • dev 产物只在浏览器跑一次，下次改代码就重建
  • 速度 > 完美度
  • 浏览器对 dev 产物体积不敏感（gzip 前几 MB 完全 OK）

三、Prod 用 Rollup ​

原因 ​

维度esbuildRollup
产物质量一般（未优化）优秀
Tree-shaking实验性业界最强
代码分割弱强
兼容性部分 ES 高级语法没处理完善
生态插件较少极其丰富

Rollup 在 prod 阶段做什么？ ​

  1. 完整的代码分割（vendor 拆分、动态 import、chunk 优化）
  2. 深度 tree-shaking（DCE 算法）
  3. CSS 提取 / 压缩
  4. 资源 hash / 文件名优化
  5. 多页面 / 库模式打包
  6. 完整的浏览器兼容性处理

生产产物要求 ​

  • 体积小（gzip 前）
  • 加载快（preload、prefetch、HTTP/2 push）
  • 缓存友好（hash 文件名、长缓存）
  • 兼容目标浏览器（es5 / es2015）

四、为什么不用 esbuild 做 prod？ ​

Evan You 的官方解释 ​

"esbuild 的 production build 还不成熟，主要在两个方面：

  1. Type stripping 不完整（TypeScript 的 enum / namespace 等不处理）
  2. 浏览器兼容性、产物优化、tree-shaking 都还不够"

实际原因 ​

  1. TypeScript 支持不完整

    • esbuild 只去类型，不做类型检查
    • enum / namespace 转换有问题

  2. CSS 处理弱

    • 复杂的 PostCSS 插件链不支持
    • CSS Modules / 预处理器兼容性差

  3. 产物优化不够

    • tree-shaking 实验性
    • 代码分割策略单一

  4. 生态

    • Rollup 插件生态极其丰富（Vite 直接复用）
    • esbuild 插件需要自己写

五、未来的可能性 ​

Vite 团队一直在尝试用 esbuild 做 prod build（性能更优）：

2023  Vite 5：prod 仍用 Rollup
2024  Vite 6/7：尝试 esbuild 做 prod，fallback 到 Rollup
未来   Rolldown（Rust 版的 Rollup）成熟后，可能替代 Rollup

Rolldown 是 Vite 团队用 Rust 重写的 Rollup，目标是同时具备 esbuild 的速度和 Rollup 的产物质量。

六、性能对比 ​

实测中型 Vue 项目（500 模块）：

工具dev 启动prod 构建产物体积
Vite（esbuild dev + Rollup prod）0.4s28s1.2MB
Webpack 5（全程自己）28s65s1.4MB
假设 esbuild 全程0.3s8s1.6MB（更大）
假设 Rollup 全程18s22s1.1MB

结论：Vite 取了 dev 速度 + prod 产物质量的最佳平衡。

七、面试追问 ​

Q：dev 用 esbuild，prod 用 Rollup，构建配置要写两套吗？

A：不用。Vite 的 vite.config.ts 是统一的。dev 阶段 Vite 自动选择 esbuild，prod 阶段自动选择 Rollup。你只需要写一份配置。

Q：Vite 为什么不用 Webpack 风格的「统一」构建？

A：dev 和 prod 阶段的目标不同：

  • dev：速度、实时反馈 → 牺牲产物质量
  • prod：产物质量、加载性能 → 牺牲构建速度

强行统一 = 两者都做不好。

Q：有没有可能 Vite 6 全部用 esbuild？

A：短期内不会。esbuild 的 prod 能力还在追赶。等 esbuild 完善了 type stripping、tree-shaking、代码分割后，Vite 可能切换。Rolldown（Rust Rollup） 是另一个备选。

🎯 面试常考 ​

Q1：Vite 为什么 dev 用 esbuild、prod 用 Rollup?

dev 要的是「快」,esbuild 转换速度是 Rollup 的 10 倍量级;prod 要的是「产物质量与可优化空间」,Rollup 的 tree-shaking、chunk 策略更成熟。

Q2：生产构建怎么进一步优化?

build.target 降级语法、build.minify 换 terser、build.rollupOptions.output.manualChunks 手动分包、build.reportCompressedSize 看产物体积。

📝 小结 ​

  • 双构建是 Vite 的核心取舍:开发要快、生产要稳。
  • 生产构建的 manualChunks 是首屏优化的主要抓手,值得在项目里显式配置。
  • Vite 5+ 默认用 esbuild 压缩,想要更好的压缩率可以换 terser。
